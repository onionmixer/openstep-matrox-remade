# M1-4 4b — 정점에 텍스처 좌표를 싣는다 (Mesa 쪽)

2026-08-22.  **유저랜드만 바뀐다.**  커널 쪽 4b(좌표 모형과 검증기)는
`M1_4C2_TEXREACH_PLAN.md` 에서 끝났다.

## 1. 이제 아는 것 (전부 실기에서 잰 값)

| 사실 | 어떻게 쟀나 |
|---|---|
| `u = TMR6 + (x − lx0)·TMR0 + (행)·TMR2`, `lx0` 은 **프리미티브 첫 행의 왼쪽 변** | 같은 사각형을 두 자리에 그려 램프가 둘 다 0..63 (§C2 11-3) |
| `v = TMR7 + (배치 안 누적 행)·TMR3 + (x − lx0)·TMR1` | 높이 5, 11, flat 7, 3 에서 v = 3, 8, 19 |
| u 는 열·행 둘 다 프리미티브마다 다시 심긴다 | 행 기울기를 줘도 두 프리미티브가 같은 텍셀에서 시작 |
| **표본은 화소의 왼쪽 모서리**다 | 화소당 두 텍셀·시작 0 에서 열 0,1,2 가 **0, 2, 4** |
| **텍셀 색인은 버림**이다 | 반 텍셀 시작·화소당 한 텍셀에서 열 0,1 이 0, 1 |
| 텍스처 한 장이 `1<<20` 을 채운다 | 한 텍셀 = `1 << (20 − log2 size)` |
| 결합은 `GL_REPLACE` | 같은 `dr[]` 로 씌운 띠는 텍셀, 안 씌운 띠는 보간색 |
| 좌표는 음수 불가, 프리미티브 구간에서 `8<<20` 이내 | 검증기 |

Mesa 는 삼각형 하나를 배치 하나로 보내므로 **v 의 누적은 지금 문제가 아니다**
(배치마다 다시 심긴다 — 잰 값).  묶어 보내게 되면 그때 다시 본다.

## 2. 그러므로 무엇을 계산해야 하는가

GL 이 요구하는 것은 **화소 중심에서의 표본**이다.  엔진은 왼쪽 모서리에서
뜬다.  그러니 반 화소를 **우리가** 접어 넣는다 — 색 보간자에서 이미 한 것과
같은 종류의 보정이고, 그때 `osmgaStartFixed` 가 그 자리였다.

삼각형의 세 꼭짓점이 `(x_i, y_i, s_i, t_i)` 일 때, 아핀이면 `u = s·2^20` 과
`v = t·2^20` 은 각각 `(x, y)` 의 평면이다.  그 평면을 지금 색·깊이·알파에
쓰는 것과 같은 방식으로 푼다.  그리고

```
TMR0 = ∂u/∂x        TMR2 = ∂u/∂y
TMR1 = ∂v/∂x        TMR3 = ∂v/∂y
TMR6 = u(lx0 + ½, y0 + ½)
TMR7 = v(lx0 + ½, y0 + ½)
```

`lx0` 과 `y0` 은 빌더가 이미 아는 값이다 — 사다리꼴의 첫 행과 그 행의 왼쪽 변.
**삼각형이 둘로 쪼개지면 각 사다리꼴이 자기 `lx0`, `y0` 을 쓴다** (엔진이
프리미티브마다 다시 심으므로 그것이 맞다).

## 3. 무엇을 거절해야 하는가 (빌더에서, 커널에 닿기 전에)

커널이 거절하면 그 삼각형은 `osmgaMesaSoftly` 로 가긴 하지만, **빌더가 먼저
알 수 있는 것은 빌더가 거절한다** — 배치를 만들고 ioctl 을 돌고 거절을 받는
왕복이 없다.

* 아핀이 아니면 (`w` 가 셋 다 같지 않거나 `q ≠ 1`) — 부동소수 정확 비교로.
  엡실론은 **맞는 것을 거절할 수는 있어도 틀린 것을 들여서는 안 된다**.
* 좌표가 프리미티브 구간에서 음수가 되거나 `8<<20` 을 넘으면.
  **검증기와 같은 식으로** 계산한다: 구간은 `[-spanLo, +spanHi] × [0, h−1]`.
* 텍스처가 없거나 크기가 범위 밖이면.

전부 `OSMGA_MESA_TRI_UNSUPPORTED` 다 — 0 이 아니다.  0 은 삼각형을 잃는다
(그 교훈은 `M1_4B7` 에서 값을 치렀다).

## 4. 자료구조

`OSMGAMesaVertex` 에 `double u, v` 를 더한다 — 엔진 고정소수점이 아니라
**텍셀 좌표**로 담는다(`s·texW`, `t·texH`).  이유: 크기는 배치 상태이고
꼭짓점이 아니며, `1<<20` 스케일은 빌더가 마지막에 한 번 곱하는 편이 크기를
바꿀 때 꼭짓점을 다시 만들지 않아도 된다.

`OSMGAMesaBuildTriangle` 은 텍스처 상태(크기·포맷·origin)를 인자로 받지
않는다 — 그건 배치 상태이고 훅이 채운다.  빌더가 만드는 것은 `tmr[0..3]` 과
`tmr[6..7]` 뿐이다.

## 5. 어떻게 증명하는가

1. **호스트 산술 시험** — 알려진 삼각형과 알려진 `s,t` 에 대해 빌더가 내는
   여섯 값을, **빌더를 부르지 않는 독립 오라클**(python 으로 계산해 표에
   박아 넣은 값)과 비교한다.  빌더의 식을 다시 쓰는 것은 시험이 아니다.
2. **실기 화소 시험** — 텍셀이 자기 좌표를 담은 텍스처를 삼각형에 씌우고,
   그린 화소가 **화소 중심에서 평가한 평면의 버림**과 같은지 본다.
   반 화소를 안 접으면 여기서 **정확히 반 텍셀 밀린다** — 그게 이 시험이
   가르는 것이다.
3. **거절 시험** — 원근 삼각형, 범위 밖 좌표가 `UNSUPPORTED` 로 나가고
   소프트웨어가 그리는지.  `drawn`·`unsupported` 계기로 확인한다.
4. **변이 시험** — 반 화소 보정을 빼면 2번이 **반드시** 실패해야 한다.

## 6. 이 단계가 하지 않는 것

* 텍스처를 VRAM 에 올리지 않는다 (4c).  이 단계의 시험은 raw 클라이언트처럼
  아레나에 직접 써 넣고 그 위에서 잰다.
* 선택기는 아직 `TEXTURE_BIT` 를 받지 않는다 (4d).  그러니 이 단계가 끝나도
  일반 GL 프로그램은 아직 텍스처를 가속하지 않는다.
* 원근을 근사하지 않는다.

사다리꼴마다 따로 실린다(`:382`, `:423` 이 각 절반의 `left`·`y` 로 계산).
TMR 만 state 에 있다.

### 7-2 고른 답: 사다리꼴 하나에 배치 하나

세 갈래를 봤다.

| 안 | 값 |
|---|---|
| (a) 사다리꼴마다 배치를 하나씩 제출 | **유저랜드만.** 쪼개진 삼각형에서 제출이 두 번 — 제출은 동기라 비용이 실재한다 |
| (b) 쪼개지는 삼각형을 거절 | **못 쓴다.** 가운데 꼭짓점이 있는 일반 삼각형은 거의 다 쪼개진다 |
| (c) ABI 를 바꿔 TMR 을 삼각형별로 | 구조적으로 옳고 묶어 보내기까지 열리지만 **커널 변경 → 재부팅** |

**(a) 로 간다.  다만 (c) 가 나중에 작은 걸음이 되도록 짓는다**: 빌더는
**사다리꼴마다** TMR 여섯 값을 내놓고, 그것을 어떻게 제출할지는 훅이 정한다.
지금은 사다리꼴마다 배치 하나, 나중에 ABI 가 바뀌면 배치 하나에 삼각형마다.
빌더 쪽 산술은 어느 쪽이든 그대로 쓰인다 — 버려지는 작업이 없다.

(c) 를 먼저 하지 않는 이유: **TMR 산술이 이 단계의 어려운 부분**이고, 그것을
이미 증명된 커널에 대고 맞추는 편이 안전하다.  커널과 유저랜드를 같이 바꾸면
어느 쪽이 틀렸는지 가리기 어렵다.

## 8. 결과 1 — 빌더가 사다리꼴마다 TMR 을 낸다 (2026-08-22)

`mesa/test-mesa-texcoord.c` 는 빌더가 낸 여섯 값과 **빌더의 식을 공유하지 않는**
오라클을 비교한다.  오라클은 세 꼭짓점에서 평면을 스스로 풀고 `(left+½, y+½)`
에서 평가한다.  닻(`left`, `y`)은 빌더가 낸 배치에서 읽는데, 그건 사다리꼴의
성질이지 검사 대상인 식이 아니므로 순환이 아니다.

| 경우 | 텍스처 | 사다리꼴 | 결과 |
|---|---|---|---|
| A 쪼개짐, 소수 좌표, 네 기울기 전부 0 아님 | 64×64 (POT) | 2 | 여섯 값 **일치** |
| B 같은 도형 | **48×40 (NPOT)** | 2 | 여섯 값 **일치** |
| C 기울기 역방향 | 64×64 | 2 | 여섯 값 **일치** |
| D 좌표가 범위를 벗어남 | 64×64 | — | **거절**(UNSUPPORTED) |

두 사다리꼴이 서로 다른 왼쪽 변(10, 14)과 **서로 다른 TMR6**(8575, 143812)을
가진다 — 엔진이 프리미티브마다 다시 심으므로 그래야 한다.  opcode 는 둘 다
6(TEXTURE_TRAP)이다.

### 8-1 변이 시험

반 화소를 빼고 빌드하니 TMR6 이 8575 → **−8698** 로 바뀐다.  오라클이 즉시
잡고, 덤으로 **음수가 되어 커널도 거절할 값**이 된다.  반 화소는 자리만이
아니라 시작값의 부호까지 지키고 있었다.

### 8-2 아직 안 한 것

* 훅이 아직 텍스처를 쓰지 않는다 — 아핀 게이트도, 사다리꼴마다 배치를
  하나씩 내는 제출 고리도 없다.
* 그러므로 **실기 화소 시험(증명 2번)이 아직 없다.**  지금까지 증명된 것은
  산술이지 그림이 아니다.

## 9. 결과 2 — 그림을 그려보니 두 레지스터가 바뀌어 있었다 (2026-08-22)

### 9-1 첫 텍스처 삼각형은 틀리게 그려졌다

커널 쪽 도달 검사를 고친 뒤 삼각형이 통과했고(사다리꼴 둘, verdict 0,
4410 화소), 그 화소를 오라클과 대니 **2275 개가 어긋났다.**  u 는 대체로
맞고 v 가 크게 틀렸다.

### 9-2 원인 — `TMR1` 과 `TMR2` 의 뜻

증분을 하나씩만 켜서 고립시켰다.  u 행방향은 완벽(0/4410), u 열방향은 87,
v 행방향은 15, 그리고 **v 열방향은 3315** 였다.  v 열방향만 켰을 때 v 는
행 전체에서 **움직이지 않았다** — 5, 5, 5, …

참고 코드가 답을 갖고 있었다.  `xf86-video-mga`, `mga_storm.c:332-335`:

```c
OUTREG(MGAREG_TMR0, (1 << 20) / tex_padw);  /* sx inc */
OUTREG(MGAREG_TMR1, 0);                     /* sy inc */
OUTREG(MGAREG_TMR2, 0);                     /* tx inc */
OUTREG(MGAREG_TMR3, (1 << 20) / tex_padh);  /* ty inc */
```

**`TMR1` 은 s per Y 이고 `TMR2` 는 t per X 다.**  나는 반대로 넣었다.

### 9-3 왜 앞선 시험이 이것을 못 잡았나

`texreach-probe` §12 가 바로 그 둘을 재는 시험이었는데, **두 항에 같은 값을
넣었다.**  그래서 어느 쪽이 어느 역할이든 같은 그림이 나왔고, 나는 그것을
내 배정의 확인으로 읽었다.  *가르지 못하는 시험을 고른* 이 실수는 이 저장소에서
세 번째다(반쪽 화소 꼭짓점, 같은 정밀도 사각형 넷, 그리고 이것).

### 9-4 확인

배정을 바꾸어 모형을 다시 맞추니 4410 화소에서 **u 어긋남 2, v 어긋남 0**
(원래 215 / 2157).  빌더를 고치고 다시 그려서 세 가지 텍스처 크기로 쟀다.

### 9-5 남은 것: 좌표에 실린 상수 편향

하드웨어의 좌표는 모형보다 **일정하게 약 502 단위** 앞선다(텍스처 한 장이
2^20 이므로 0.05%).  증분에 비례하지 않고(v 행방향이 반례) 텍셀 크기에도
비례하지 않는다.  최적 상수와 잔차:

| 텍스처 | 텍셀 크기 | 최적 K | 남는 어긋남 |
|---|---|---|---|
| 16 | 65536 | 504 | 0 / 8820 |
| 64 | 16384 | 504 | 1 / 8820 (0.011%) |
| 256 | 4096 | 500 | 8 / 8820 (0.091%) |

보정하지 않으면 어긋남은 **전부 ±1 텍셀**이고, 그 비율은 편향이 텍셀에서
차지하는 몫 그대로다: 0.8% / 3.1% / 12.3%.  눈에는 안 보이지만 소프트웨어와
화소 단위로 비교하면 잡힌다.

**지금은 보정하지 않는다.**  보정하려면 시작값에서 502 를 빼야 하는데, 꼭짓점의
s 가 0 인 흔한 경우에 시작값이 음수가 되고 검증기가 그것을 거절한다.  검증기가
`-K` 까지 허용하도록 바꾸는 것은 커널 변경이므로 다음 묶음에 넣는다.

## 10. 상수를 정확히 쟀다 — 511 (2026-08-22)

교차분석이 요구한 측정이 회신 직전에 이미 돌아가 있었다: **증분을 전부 0 으로
두고 시작값만 쓸면** 좌표는 시작값 하나뿐이므로, 텍셀이 넘어가는 시작값이 곧
상수를 준다.

```
16. the constant, exactly
   u turns over at start 15873  ->  K = 511
   v turns over at start 15873  ->  K = 511
```

**K = 511 = 2^9 − 1**, 두 축이 같다.  즉 하드웨어는

```
텍셀 = floor((u + 511) / 텍셀크기)
```

로 색인한다.  달리 말하면 좌표를 **512 배수로 올림**한다 — 512 는 텍스처 한
장(2^20)을 최대 텍스처 크기 2048 로 나눈 값, 즉 가장 잘게 쪼갠 텍셀 하나다.

그리고 **증분이 0 인 자리에서 K ≠ 0** 이므로, 이것은 "표본 위치가 조금
어긋났다"가 아니라 **하드웨어가 더하는 상수**다.  증분을 500·1000·5533 으로
바꿔 첫 텍셀 경계를 본 §15 도 같은 답을 준다(32, 16, 3 — 표본 위치 가설은
33, 17, 3 을 예측했다).

### 10-1 그래도 남는 것

`K = 511` 을 넣고 그린 삼각형과 대면 8820 표본 중 0 / 5 / 19 가 남는다
(텍스처 16 / 64 / 256).  삼각형에서 최적 상수는 ~502 이므로, **기울기에
따라 열 단위쯤 움직이는 작은 항이 더 있다.**  교차분석이 제안한
`K(g) = K0 + δx·gx + δy·gy` 의 δ 항이고, 크기는 10 단위 안팎이다.
지금은 그 이상 파고들지 않고 값을 적어 둔다.

## 12. 보정은 지금 하지 않는다

`K` 를 빼려면 시작값이 음수가 되고, 그것을 하드웨어가 어떻게 다루는지는 안
쟀다.  게다가 보정의 이득은 **눈에 안 보이는** 차이다 — 어긋남은 전부 ±1
텍셀이고 그 비율은 편향이 텍셀에서 차지하는 몫이다.

**4d 에서 소프트웨어와 화소 단위로 비교할 때** 이 차이가 잡힐 것이므로,
그때 실제 비용을 보고 정한다.  그 전에 재부팅을 쓰지 않는다.
