# M1-4 B5 — 혼합 프레임: 하드웨어 삼각형 옆의 소프트웨어 삼각형

2026-08-21. §8-4 가 남긴 미지 둘 중 첫째.

## 1. 왜 이것이 아직 안 밝혀졌나

지금까지의 모든 측정은 **한 프레임 전체가 한 경로**였다.  `OSMGA_MESA_ACCEL`
로 하드웨어 또는 소프트웨어를 고르고, 그 안에서만 비교했다.  실제 응용은
그렇지 않다.  Mesa 는 상태가 바뀔 때마다 삼각형 함수를 다시 고르고,
`osmgaMesaChooseTriangle` 이 거절하면 그 다음 삼각형부터는 소프트웨어가
그린다.  **한 프레임 안에서 두 경로가 섞인다.**

## 2. 코드에서 확인한 구조 (추측 아님)

* `OpenStepMGAMesaHook.c:565` — 표면이 묶여 있으면 `RenderStart=osmgaMesaSoil`,
  `RenderFinish/Finish/Flush=osmgaMesaMirror` 를 **가속 여부와 무관하게** 건다.
  주석이 이유를 적어두었다: *"소프트웨어 래스터라이저도 비디오 메모리에
  그리고 있으므로"*.
* 즉 **두 경로가 같은 VRAM 표면에 쓴다.**  소프트웨어는 CPU 스팬 쓰기로,
  하드웨어는 엔진으로.  되비추기는 프레임 끝에 한 번.
* 삼각형 단위 되돌림도 이미 있다: `osmgaMesaSoftly`(:149)가
  `savedTriangle` 로 넘기고 `OSMGAMesaBufferSoiled()` 를 부른다.
  `n == OSMGA_MESA_TRI_UNSUPPORTED` 일 때(:255) 그리로 간다.

## 3. 그래서 위험은 이음매만이 아니다

세 갈래를 나눠 봐야 한다.

1. **이음매** — 두 경로의 커버리지 규칙이 다르다.  §8 에서 소프트웨어가
   자기 오라클과 도형 B 에서 5화소, C 에서 4화소 어긋나는 것을 이미 봤다.
   그러니 hw 삼각형과 sw 삼각형이 변을 나눠 가지면 **틈이나 이중 소유가
   생길 수 있고, 그건 이 드라이버의 결함이 아니라 두 규칙의 차이**다.
   측정해서 크기를 아는 것이 목적이지, 0 을 기대하는 것이 아니다.
2. **순서** — 처음에 "엔진은 비동기이므로 hw 뒤의 sw 쓰기가 엔진에
   추월당할 수 있다"고 적었다.  **그 전제가 틀렸다.**  제출 ioctl 은 동기다:
   `OpenStepMGAReplacementDisplay.m:3727` 이 DMA 완료(`MGA_DMA_DONE_VALUE`)를
   기다리고, :3734 가 이어서 `osmgaStormWaitIdle` 까지 건 다음에야 돌아온다.
   그러니 hw→sw 순서에서 엔진이 뒤늦게 덮어쓸 일은 없고, 그 검사는
   **어떤 결과가 나와도 실패할 수 없다** — 내가 §5 에서 스스로 경고한
   공허한 검사가 계획 안에 이미 들어와 있었다.

   그러나 동기 제출이 닫지 못하는 위험이 하나 남는다: **캐시 일관성**이다.
   CPU 는 매핑된 구멍을 통해 쓰고, 엔진은 DMA 로 VRAM 에 직접 쓴다.
   **sw 를 먼저, hw 를 나중에** 그리면 CPU 가 남긴 더러운 캐시 줄이
   엔진이 쓴 뒤에 밀려나와 **엔진의 결과를 지울 수 있다.**  이 저장소는
   이미 그 계열의 staleness 를 알고 있다(:3740 의 주석: 앞 64바이트를
   읽어서는 아무것도 안 정해지고 그 뒤를 읽으면 정해진다).
   그래서 표적은 `over` 가 아니라 **`overrev`** 다.
3. **장부** — soil/mirror 가 두 경로의 결과를 모두 되비추는가.  한쪽만
   반영되면 절반이 사라진다.

## 4. 되돌림을 어떻게 강제하나

`osmgaMesaChooseTriangle` 이 거절하는 상태 중 **화소를 바꾸지 않는** 것을
골라야 한다.  안 그러면 경로 차이인지 상태 차이인지 구별이 안 된다.

고른 것: **`glEnable(GL_POLYGON_STIPPLE)` + 전부 1인 스티플 마스크.**
`:403` 이 `ctx->Polygon.StippleFlag` 를 무조건 거절하므로 소프트웨어로
가고, 전부 1인 마스크는 어느 화소도 걸러내지 않으므로 그려지는 그림은
스티플이 없을 때와 같아야 한다.

후보로 검토했다 버린 것:
* 좌표를 범위 밖으로 — `osmgaCoordOK` 는 통과하지만 Mesa 가 뷰포트로
  이미 잘라내므로 화면 안 도형으로는 도달하지 못한다.
* `glDepthFunc(GL_LEQUAL)` — 거절되지만 동점에서 결과가 달라진다.
* 혼합 함수 변경 — 색이 바뀐다.

## 5. 측정

`test/openstep-mga-mesa-seam-test.c` 에 모드를 더한다(도형은 그대로 A~E).

| 모드 | 뜻 |
|---|---|
| `mix` | 삼각형 1 은 그대로(hw), 2 부터는 스티플 켠 채(sw) |
| `mixrev` | 역순 — 1 이 sw, 나머지가 hw |
| `over` | 겹침: hw 삼각형을 크게 그리고, 그 위에 sw 삼각형을 다른 색으로 |
| `overrev` | 겹침 역순 — sw 먼저, hw 나중 |

판정:
* `mix`/`mixrev` — 각 삼각형을 **자기 오라클 마스크**와 비교(§8 과 같은 방법).
  이중 소유·틈을 센다.  기대는 0 이 아니라 *"소프트웨어 쪽이 자기 규칙만큼만
  어긋난다"* 이다.  hw 삼각형이 solo 일 때와 달라지면 그건 오염이다.
* `overrev`(sw 먼저, hw 나중) — 겹친 영역은 **전부 hw 색**이어야 한다.
  한 화소라도 sw 색이 남으면 캐시 줄이 엔진 결과를 지운 것이다.
  통과/실패가 분명한 항목은 이것 하나다.
* `over`(hw 먼저, sw 나중) — 동기 제출 때문에 실패할 수 없다.  버리지 않고
  **대조군으로** 남긴다: 여기서 뭔가 어긋나면 그건 순서가 아니라 되비추기
  장부의 문제라는 뜻이므로, 진단을 가르는 값이 있다.
* 세 모드 모두 `OSMGAMesaHookDrawn()`/`HookSoftware()`/`HookDeclined()` 를
  찍어서 **분할이 실제로 일어났는지** 증명한다.  전부 hw 로 갔거나 전부
  sw 로 갔다면 시험이 공허하다 — 깊이 이음매에서 정수 평면을 골랐던 실수와
  같은 종류다.

## 6. 미리 밝히는 한계

* 스티플 경로는 Mesa 의 스티플 삼각형 함수를 쓴다.  전부 1인 마스크라
  화소는 같아야 하지만, **같은지 자체를 먼저 확인**한다: 전 프레임
  소프트웨어 + 스티플과 전 프레임 소프트웨어를 비교해 차이가 0 임을 보인다.
  이 대조를 건너뛰면 스티플 경로의 차이를 혼합의 결함으로 오독한다.
* 실기 자원은 읽기 전용으로만 쓴다.  새 레지스터 프로그래밍은 없다.
  전부 유저랜드이고 재부팅이 필요 없다.

### 판정에 따른 최종 설계

* 소프트웨어 강제 = **전면 가위**(`glEnable(GL_SCISSOR_TEST); glScissor(0,0,W,H)`).
* **새 카운터** `hookSoftState` — chooser 가 `NULL` 을 돌려줄 때마다 센다.
  이것 없이는 분할을 증명할 수 없다.
* 대조군은 **가속을 켠 채** 전 삼각형을 가위로 소프트웨어에 보낸 것.
  `ACCEL=0` 은 쓰지 않는다.
* 장부는 **단계 검문**으로 본다: hw 만 그리고 `glFlush` → 응용 버퍼 확인,
  이어서 sw 만 그리고 `glFlush` → 둘 다 확인.
* 겹침 판정은 **관측된 solo 마스크의 교집합** 위에서만.
* 이 시험이 다루는 것은 **선택 단계의 혼합**이다.  삼각형 단위 되돌림
  (`osmgaMesaSoftly`, 빌더가 표현 못 하는 도형)은 다른 길이고 여기 없다.

## 8. 결과 (2026-08-21 실기 측정)

### 8-1 분할이 실제로 일어났는가

`hookHardState`/`hookSoftState` 를 새로 넣고 나서야 답할 수 있게 됐다.
그리고 codex 가 예측한 문자열이 그대로 나왔다 — 도형 A `mix` 의 출력은

```
# counters drawn=1 software=0 declined=0
# select hard 0 soft 1
```

`software=0` 은 되돌림이 없었다는 뜻이 아니다.  선택 단계의 되돌림은
저 카운터를 지나지 않는다.  분할을 말해주는 것은 `drawn` 과 새 선택
카운터뿐이고, 둘은 모든 모드에서 설계와 정확히 맞았다:

| 모드 | 엔진에 닿은 삼각형 | 기대 |
|---|---|---|
| `allsoft` | 0 | 0 |
| `mix` | 1 | 1 |
| `mixrev` | n−1 (D·E 에서 3) | n−1 |
| `over`/`overrev` | 2 중 1 | 1 |

(`hard 0` 이 나오는 것은 결함이 아니라 측정 창이다.  chooser 는 상태가
바뀔 때만 돌고, 첫 하드웨어 선택은 기준선을 잡기 전에 끝나 있다.)

### 8-2 각 경로가 서로를 건드리는가 — 아니다

처음 판정에서 소프트웨어 삼각형의 대조군으로 **전면 소프트웨어 두 삼각형
런**을 썼고, 도형 B 에서 5, C 에서 4의 차이가 나왔다.  그건 결함이 아니라
**덮어쓰기에 오염된 대조군**이었다: 두 삼각형이 함께 그려진 런에서 앞 삼각형의
관측 마스크는 뒤 삼각형이 빼앗아간 화소만큼 이미 짧다.  codex 가 정확히 이
함정을 경고했고, 나는 그 경고를 읽고도 그 대조군을 썼다.

`ssoloN`(소프트웨어 단독)·`hsoloN`(하드웨어 단독)을 따로 받아
**기대 마스크 = 자기 solo − 뒤에 그린 삼각형들의 solo** 로 다시 재니:

```
  도형 A~E × allsoft/mix/mixrev, 15 조합 전부
  하드웨어 solo = 오라클        0
  삼각형별 어긋남               [0, 0, ...]  전부 0
  각 경로 solo 합집합의 틈       0
```

**한 프레임 안에서 두 경로가 같은 VRAM 표면에 그려도, 어느 쪽도 상대의
화소를 잃게 하거나 더 칠하게 만들지 않는다.**

### 8-3 순서 — 캐시 줄이 엔진 결과를 지우는가, 아니다

도형 F 는 겹치는 삼각형 두 개다.  겹침은 **관측된 solo 마스크의 교집합**으로
정의했다(오라클 교집합을 쓰면 이미 아는 규칙 차이가 순서 결함으로 둔갑한다).

| 모드 | 겹침 화소 | 나중 삼각형이 못 가진 화소 |
|---|---|---|
| `over` (hw→sw) | 7696 | 0 |
| `overrev` (sw→hw) | 7696 | **0** |

`overrev` 가 표적이었다.  제출 ioctl 의 펜스는 엔진을 기다릴 뿐 CPU 의 더러운
캐시 줄을 밀어내지 않으므로, 소프트웨어가 먼저 쓴 줄이 엔진이 쓴 뒤에 밀려나와
엔진의 결과를 지울 수 있었다.  7696 화소 중 하나도 그러지 않았다.

### 8-4 장부 — 두 경로 모두 응용 버퍼에 닿는가

삼각형마다 `glFlush` 하고 응용 버퍼의 칠해진 화소를 셌다(카운터로는 증명할
수 없다 — Clear 와 RenderStart 가 무조건 더럽히므로 되비추기는 어느 쪽이
장부를 빠뜨려도 일어난다).  누계는 매 검문마다 늘었다:

```
도형 D mix     0:hw=5440  1:sw=6050  2:sw=13228  3:sw=22012
도형 D mixrev  0:sw=5440  1:hw=6044  2:hw=13228  3:hw=22108
```

### 8-5 깊이 혼합

`mixz` — t0 은 엔진, 나머지는 소프트웨어, §9 와 같은 분수 깊이 평면 하나를
나눠 가진다.

| 도형 | 화소 | 잔차 최대 | 이웃차 이탈 | 클램프 |
|---|---|---|---|---|
| A | 22400 | −0.560 | 0.890 | 0 |
| B | 22395 | −0.530 | 0.890 | 0 |
| C | 13451 | −0.530 | 0.890 | 0 |
| D | 22012 | −0.540 | 0.890 | 0 |
| E | 20164 | −0.520 | 0.890 | 0 |

잔차 −0.56 은 소프트웨어 쪽 값 그대로다(하드웨어 단독은 ±0.500).  1 코드
이상 튀는 인접쌍은 **hw/sw 경계를 포함해 하나도 없다.**

### 8-6 그래도 남는 것: 이상에 대한 실금

혼합이 무엇도 잃게 하지 않는다는 것과, 혼합 프레임이 이상적인 커버리지와
같다는 것은 다른 말이다.  오라클 합집합에 대고 재면:

| 도형 | allsoft 안칠함 | mix 안칠함 | mixrev 안칠함 |
|---|---|---|---|
| A | 0 | 0 | 0 |
| B | 0 | **5** | 0 |
| C | 4 | 4 | 4 |
| D | 98 | 98 | 0 |
| E | 0 | 0 | 0 |

C 의 4 와 D 의 98 은 `allsoft` 에도 똑같이 있으므로 **소프트웨어 규칙 자체의
값**이지 혼합이 만든 것이 아니다.  B 의 5 는 다르다: 전면 소프트웨어에도,
전면 하드웨어에도 없고 `mix` 에만 있다.  소프트웨어가 자기 쪽 변에서 덜
가져가는데 이웃한 하드웨어 삼각형은 규칙대로 그 화소를 자기 것으로 보지
않으므로, 둘 사이에 **폭 1의 실금**이 남는다.

이건 드라이버가 고칠 수 있는 결함이 아니다.  두 래스터화 규칙이 공유 변의
소유권에서 다를 때 나타나는 필연이고, 없애려면 소프트웨어 쪽을 엔진의 규칙에
맞춰야 한다 — Mesa 를 고치는 일이다.  **알려진 결과로 적어둔다.**
