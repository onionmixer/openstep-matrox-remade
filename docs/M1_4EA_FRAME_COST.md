# M1.4EA — 프레임 비용은 그린 픽셀이 아니라 표면 크기에 붙어 있다

## 왜 쟀나

`mesa/OpenStepMGAMesaBuffer.c` 의 미러 주석이 이 저장소에서 **코드가 스스로 열어둔
유일한 작업**을 적어두고 있다: 표면 전체를 매 프레임 복사하며, 좁히려면 엔진과
소프트웨어 래스터라이저 **양쪽이** 무엇을 건드렸는지 말해야 하므로 "추측하지 않고
작업으로 기록한다".

좁히는 일은 오늘 시저에서 겪은 것과 같은 종류의 위험 — **조용히 빠지는 픽셀** — 을
안는다. 그래서 설계하기 전에 **그게 실제로 비싼지** 먼저 쟀다.

## 크기 스윕 (`tmc`)

삼각형은 세 크기에서 **똑같다**. 변하는 것은 표면뿐이다.

```
   surface       pixels     ms/frame       ns/pixel
   128x96         12288       20.0           1631
   512x384       196608      305.9           1556
   1024x768      786432     1238.1           1574
```

면적 64.0배, 프레임 61.8배. **ns/픽셀이 사실상 상수다.** 프레임 비용은 그린
픽셀이 아니라 **표면 전체 픽셀**에 붙어 있다. 1024×768 에서 프레임 하나가
**1.24초** — 0.8 fps 이고, 그 전부가 표면을 훑는 일이다.

(두 번 돌렸고 세 숫자 모두 1% 이내로 반복됐다.)

## 어디로 가는가

표면 전체를 훑는 일은 **둘**이고 둘 다 면적에 비례하므로 크기 스윕으로는 갈리지
않는다. 그래서 clear 를 뺀 프레임을 다시 쟀다.

```
512x384
   clear + triangle + finish :  309.8 ms
   triangle + finish         :  145.5 ms
   -> clear                  :  164.2 ms   (53%)
   -> mirror + 삼각형 하나    :  145.5 ms   (47%)
```

**둘은 비슷하고, 큰 쪽은 clear 다.**

## 그래서 기록된 작업은 절반이 안 된다

미러를 완벽하게 좁혀도 프레임의 **47% 이하**가 줄고 clear 가 그대로 남는다.
그리고 미러 좁히기는 위험하다: 소프트웨어 래스터라이저가 무엇을 건드렸는지
보이지 않고, 우리 훅을 거치지 않는 원시(점·선)는 아예 보이지 않는다.

더 큰 쪽인 `glClear` 는 **위험하지 않고** 훨씬 곧다: 지금은 Mesa 가 치환된 VRAM
표면을 CPU 로 쓴다(`osmgaMesaClear` 가 드라이버의 이전 Clear 에 체인할 뿐이다).
엔진이 채우면 된다.

* 색: 상수 색의 **표면 전체 평면 TRAP**. 오늘의 배치 경로로 그대로 표현된다
  (`SOLID` 비트 11 은 클라이언트 마스크 `0x77F` 밖이지만, 평평한 gouraud TRAP 이면
  같은 그림이다).
* 깊이: `NOZCMP` 의 ZI TRAP 이 상수 z 를 쓴다 — NOZCMP 가 깊이를 쓴다는 것은
  이미 실측돼 있다.

둘 다 **커널 변경이 필요 없다.**

## 다음

`glClear` 가속을 계획하고 codex 교차검토를 받은 뒤 구현한다. 미러 좁히기는 그
다음이며, 그때는 이 문서의 47% 가 상한이라는 것을 알고 시작한다.

## `glClear` 가속 계획에 대한 codex 판정

먼저: codex 는 Mesa 를 `openstep-sdl20/upstream/...` 에서 인용했는데 그건 이
워크스페이스의 **다른 프로젝트** 사본이다. `cmp` 로 대어 보니 `buffers.c`,
`dd.h`, `depth.c` 가 **바이트 단위로 동일**하므로 인용 내용은 맞다. 경로만
엉뚱했다.

| codex 주장 | 내 검증 | 결과 |
| --- | --- | --- |
| `Driver.Clear` 는 `GL_COLOR_BUFFER_BIT` 가 아니라 **`DD_*` 비트**를 받는다. 색은 `ctx->Color.DrawDestMask` 로 치환된다 | `buffers.c:276-278` 이 `ddMask |= ctx->Color.DrawDestMask`, `dd.h` 의 계약이 "a bitmask of the DD_*_BIT values ... return a new bitmask indicating which buffers should be cleared by software Mesa" | ✅채택 — **내 계획이 틀렸다** |
| `ColorMask` 네 바이트가 모두 `0xff` 일 때만 가속하라 | `types.h:346` `GLubyte ColorMask[4]; /* Each flag is 0xff or 0x0 */` | ✅채택 |
| 깊이 지우기 값은 `ctx->Depth.Clear * ctx->Visual->DepthMax` 로, 손으로 만든 반올림 규칙을 쓰지 말라 | `types.h:1357` 에 `DepthMax` 존재 | ✅채택 |
| 색 바이트는 Mesa 처럼 `(GLint)(ClearColor[c] * 255.0F)` — **절사** | `buffers.c:147-152` 그대로 | ✅채택 |
| 디더링은 거절 사유가 아니다 (clear 는 `DitherFlag` 를 안 본다) | `buffers.c` 의 clear 경로에 `Dither` 참조 없음 | ✅채택 |
| 깊이 단독 지우기는 가속 불가 (ZI 가 색도 쓴다) | 내가 낸 결론과 같다 | ✅채택 |
| 제출부를 뽑을 때 **텍스처·블렌드·알파시험·시저를 살아 있는 ctx 에서 읽는 것**이 최대 위험이다 | `Hook.c:612` 이하가 실제로 그렇다. 배치는 재사용되는 매핑이라 안 쓴 필드는 이전 값이 남는다 | ✅채택 — 헬퍼는 명시적 인자만 받게 한다 |
| 성능은 **아직 증명되지 않았다**. clear 가 53% 라는 것이 엔진 채우기가 더 빠르다는 뜻은 아니다 | 옳다. 제출은 동기이고 setup·ioctl·DMA 완료 대기를 매번 문다 | ✅채택 — **코드를 쓰기 전에 잰다** |

### 내가 스스로 찾은 위험 (codex 가 언급하지 않은 것)

* 제출부의 `hookBatches++` / `hookTraps++` 는 시험들이 "엔진이 그렸는가" 로 세는
  값이다. clear 가 여기에 끼면 `tsc` 처럼 clear 를 포함한 구간을 재는 시험이
  **"소프트웨어 패스가 가속됐다"로 뒤집힌다**. 가속 clear 는 별도 계수기를 쓴다.
* 같은 이유로 가속 clear 는 `hookForcedSoftware` 를 존중해야 한다. 아니면 강제
  소프트웨어 패스에서도 clear 만 엔진으로 가서 비교가 흔들린다.
* Mesa 의 clear 는 `UseSoftwareAlphaBuffers` 일 때 소프트웨어 알파 버퍼도
  지운다(`buffers.c:306-310`). 우리 문맥에서는 거짓이지만(블렌딩이 실제로
  가속되고, 블렌딩 경로가 그 플래그를 거절한다), 가드는 둔다.

## 코드를 쓰기 전에 재는 것

엔진 clear 가 할 일은 **전면 사각형 하나**다. 그건 지금 경로로 이미 그릴 수 있으니,
`tmc` 에 "전면 사각형, clear 없음" 을 넣어 512×384 에서 잰다. CPU clear 164 ms 와
대면 만들 가치가 있는지 없는지가 바로 나온다 — 한 줄도 새로 쓰지 않고.

## 답: 176배

```
512x384
   whole-surface quad + finish :  146.468 ms   (40 batches = 2 per frame)
   small triangle + finish     :  145.556 ms   (20 batches)
   -> 표면 전체를 엔진으로 덮는 비용 :   0.912 ms
   -> 같은 표면의 CPU clear         : 160.662 ms
```

엔진이 표면 전체를 채우는 데 **1 ms 가 안 걸린다.** 같은 일을 CPU 가 하면 161 ms 다.
동기 제출·ioctl·DMA 완료 대기를 **전부 포함한** 숫자다 — 사각형 두 개가 배치 두 개로
나가고 프레임마다 그 왕복을 문다.

그래서 `glClear` 가속은 프레임의 **절반을 통째로 없앤다**:

| | 지금 | 엔진 clear 뒤 (예상) |
| --- | --- | --- |
| 512×384 | 306 ms | ~146 ms |
| 1024×768 | 1223 ms | ~590 ms |

codex 가 요구한 "성능을 이긴다고 부르기 전에 후보를 재라"가 이것으로 충족됐다.
그리고 남는 절반은 미러다 — 그때 가서 좁히면 된다.

## 구현

`osmgaMesaClearOnEngine` 이 상자를 덮는 사각형 둘을 **평범한 빌더**로 만들어
평범한 제출 경로로 보낸다. 손으로 배치를 조립하지 않는다 — 오늘까지 측정해 온
산술을 그대로 쓴다.

접근 유형이 두 경우를 다 처리한다:

| 요청 | zmode / depthWrite | 결과 |
| --- | --- | --- |
| 색만 | `NONE` / 0 → atype **I** | 색만 쓴다 |
| 색+깊이 | `ALWAYS` / 1 → atype **ZI** + NOZCMP | **한 번에** 둘 다 쓴다 |
| 깊이만 | — | **안 받는다.** ZI 는 색도 쓰고, 막을 수 있는 건 배치에 없는 PLNWT 뿐이다 |

### 공유부를 뽑았다

`osmgaMesaSubmitBatch` 와 `osmgaMesaBatchUntextured` 를 삼각형 경로에서 뽑아
clear 도 **같은 길**을 쓰게 했다. 배치는 재사용되는 매핑이라 안 쓴 필드가 남으므로,
텍스처 상태는 매번 전부 쓴다.

**결과 처리는 공유하지 않는다**: 거절된 삼각형은 Mesa 래스터라이저로 가고 거절된
clear 는 Mesa 의 clear 로 간다. 그리고 그 둘은 안전성이 다르다 — 반쯤 그려졌을 수
있는 삼각형은 다시 그리면 안 되지만, 반쯤 지워졌을 수 있는 표면은 같은 색을 다시
덮어도 된다. 두 번째 패스가 첫 번째가 남긴 것에 의존하지 않기 때문이다.

**계수기도 공유하지 않는다.** `hookBatches`/`hookTraps` 는 시험이 "엔진이 그렸는가"로
읽는 값이다. clear 가 거기 끼면 강제-소프트웨어 비교가 "소프트웨어 패스가
가속됐다"로 뒤집힌다. clear 는 `hookClears` 를 쓴다. 같은 이유로 가속 clear 는
`hookForcedSoftware` 를 존중한다 — 아니면 강제 패스에서 clear 만 엔진으로 샌다.

### 받지 않는 상태

`ColorMask` 가 넷 다 `0xff` 가 아니면(엔진에 색 쓰기 마스크가 없다), 색 목적지가
`DD_FRONT_LEFT_BIT` 하나가 아니면, 소프트웨어 알파 버퍼가 있으면(Mesa 는 그것도
지운다), RGBA 모드가 아니면 — 전부 Mesa 에게 남긴다.

양자화는 Mesa 를 **글자 그대로** 따른다: 색은 절사 `(GLint)(c * 255.0F)`,
깊이는 `(GLushort)(Depth.Clear * Visual->DepthMax)`. 다르게 반올림하면 몇몇 값에서
두 경로의 색이 갈리고, 그건 반년 뒤에 발견되는 종류의 차이다.

### 정확성 회귀

`tv trh trs tbg tdf tbf tat tpo tsc tdm` 0 실패, `tdc` PASS, `tsa` 그대로.
**가속 clear 는 그림을 바꾸지 않는다.**

## 붙이고 나서 — 그리고 아직 설명되지 않은 간극

### 처음에는 아무것도 달라지지 않았다

붙인 뒤 프레임을 다시 재니 clear 가 166.6 → **166.6 ms**, 그대로였다. 진단을
만들어(`tcp`, 몇 초짜리) 물어보니 답이 나왔다:

```
colour only : not cleared -- the driver refused the batch
     verdict 7, triangle 1 of 2, destination 128x96
     y 0 h 0  ar0 0 ar6 0  fxbndry 00000000  dwgctl 00000000
```

`verdict 7` 은 `E_DWGCTL` 이고, 문제의 삼각형은 **전부 0** 이었다. 원인: 나는
`triCount` 를 세워놓고 **`built[]` 를 `batch->tri[]` 로 복사하지 않았다.** 그 복사는
내가 뽑아내지 않은 위쪽 코드에 있었다. 배치는 재사용되는 매핑이라 슬롯 0 에는
직전 제출이 남아 있었고 슬롯 1 은 비어 있었다. codex 가 경고한 "낡은 필드" 함정을
다른 방식으로 밟은 셈이다.

고친 뒤 `tcp` 는 `CLEARED on the engine` 을 말하고 정확성 회귀는 전부 통과한다.

### 그런데 속도는 예고만큼 오르지 않았다

| | 붙이기 전 | 붙인 뒤 |
| --- | --- | --- |
| 512×384 프레임 | 312 ms | **297 ms** |
| 그중 clear 로 귀속 | 166.6 ms | **151.6 ms** |

후보 측정(전면 사각형 0.9 ms)대로라면 clear 는 몇 ms 여야 하고 프레임은 ~150 ms 로
떨어져야 한다. **15 ms 만 줄었고, 그 간극은 설명되지 않았다.**

(그 0.478 ms 라는 첫 수치는 **버그가 살아 있을 때** 잰 것이라 무효였다. 고친 뒤의
숫자는 아래에 있다.)

### 512×384 로 재려던 시도가 실패한 이유 (도구의 한계)

같은 프로그램에서 두 번째 `OSMesaContext` 를 만들어 재려 했으나, **두 번째 문맥은
가속되지 않는다** — 버퍼 코드가 한 번에 한 문맥에만 표면을 묶는다. 그래서 나온
숫자(128×96 에서 0.017 ms, 512×384 에서 0.749 ms)는 VRAM 도 미러도 없는 평범한
시스템 메모리 지우기이고, 함께 찍힌 "0 taken -- the colour bit was not asked for"
는 훅이 아예 불리지 않아 **직전 값이 남은 것**이지 그 문맥의 사유가 아니다.

→ 이 도구로는 큰 표면의 clear 를 가를 수 없다. 가르려면 한 문맥 안에서 크기를 바꾸거나
   (`OSMesaMakeCurrent` 로 같은 문맥에 다른 버퍼를 붙이거나) 프로세스를 나눠야 한다.

**미해결로 남긴다.** 가속 clear 는 옳고 실제로 엔진에서 돌지만, 프레임에서 기대만큼
줄지 않는 이유는 아직 모른다.

## 고친 뒤, 같은 문맥에서 잰 진짜 숫자

```
128x96, 스무 번의 clear + glFinish
   on the engine : 14.212 ms   (스무 번 다 엔진이 가져감)
   left to Mesa  : 25.516 ms
   차이          : 11.304 ms
```

**프레임이 25.5 ms 에서 14.2 ms 로, 1.8배.** 두 쪽 다 미러를 물었으므로 차이는
clear 자체다. 이 크기는 미러가 프레임의 대부분인데도 이만큼 줄었다.

### 512×384 는 아직 못 쟀다 — 도구의 두 번째 한계

같은 문맥에 **더 큰 버퍼를 다시 붙여** 재려 했더니 가속이 풀렸다:

```
twenty clears of 512x384
   surface is the engine's here: NO -- ignore the above
```

크기를 바꿔 다시 붙이면 백엔드가 표면을 다시 잡아주지 않는다. 그래서 큰 표면의
clear 는 여전히 프레임 전체 측정(`tmc`, 312 → 297 ms)으로만 보이고, 그 15 ms 가
왜 128×96 에서 본 비율과 다른지는 **미해결로 남는다.**

가르려면 프로세스를 나누어 크기마다 따로 재야 한다 — `tmc` 가 크기마다 새 문맥을
만드는 것과, 그 문맥들이 실제로 가속되는지(배치 수는 20 으로 나오니 삼각형은
가속된다)와, 그 안에서 clear 가 실제로 엔진에 가는지를 각각 확인해야 한다.

## 프로세스를 나눠 재니 큰 표면도 나왔다 — 그리고 앞의 귀속과 모순된다

크기를 인자로 받게 해서 **크기마다 새 프로세스**로 돌렸다. 그래야 그 문맥이
표면을 쥔다.

```
128x96    엔진   9.753 ms   Mesa  16.597 ms   차이   6.844 ms
512x384   엔진 146.710 ms   Mesa 167.516 ms   차이  20.806 ms
```

가속 clear 는 **옳게 돌고 실제로 이득**이다. 그러나 이득은 512×384 에서 **21 ms** 이지
160 ms 가 아니다.

### 모순

`tcp` 의 엔진-clear 프레임 **146.7 ms** 는 `tmc` 의 **clear 가 아예 없는** 프레임
145.5 ms 와 사실상 같다. 그러면 엔진 clear 는 ~1 ms 이고, 같은 논리로 Mesa clear 는
167.5 − 145.5 = **22 ms** 여야 한다.

그런데 `tmc` 는 Mesa clear 를 **160 ms** 로 귀속한다(clear+삼각형 306 ms 빼기
삼각형만 145.5 ms).

두 측정이 같은 것을 두고 22 ms 와 160 ms 를 말한다. 차이는 `tmc` 의 프레임에
**삼각형이 함께 있다**는 것뿐이다. CPU 가 uncached VRAM 을 통째로 쓴 직후에 엔진이
같은 표면을 건드리고 그 다음 미러가 다시 읽는 조합이 어느 한 쪽만 할 때보다 훨씬
비싸다는 설명이 물리적으로는 그럴듯하지만, **측정하지 않았으므로 설명이 아니라
가설이다.**

또한 128×96 은 같은 시험을 두 번 돌렸을 때 (14.2 / 25.5) 와 (9.8 / 16.6) 로
40% 가까이 흔들렸다. 이 기계의 타이밍 잡음이 작지 않다.

**미해결로 남긴다.** 확실한 것은 두 가지다: 가속 clear 는 정확하고(회귀 전 항목
통과), 두 크기 모두에서 프레임을 줄인다.

## 가설은 틀렸고, 대신 더 쓸모 있는 답이 나왔다

"CPU 가 표면 전체를 쓴 직후의 엔진 작업이 비싸진다"를 재 봤다. 같은 프레임에
작은 삼각형을 넣어 양쪽 clear 로 각각:

```
512x384
   엔진 clear              : 146.665 ms
   Mesa clear              : 174.029 ms
   엔진 clear + 삼각형     : 146.696 ms    삼각형 비용 +0.031 ms
   Mesa clear + 삼각형     : 160.554 ms    삼각형 비용 -13.475 ms (잡음)
```

**삼각형은 어느 쪽에서도 공짜다.** 상호작용 가설은 반증됐다.

그리고 같은 작업(clear + 삼각형 + finish)을 `tmc` 는 **306 ms**, `tcp` 는 **160 ms**
로 잰다. 어긋남이 ~146 ms — 표면을 한 번 더 훑는 값과 같다. 통제가 나은 쪽은
`tcp` 다(문맥 하나, 워밍업 있음, 두 팔이 같은 문맥). `tmc` 는 크기마다 문맥을
새로 만들고 부수며, 그 절대값에 `tcp` 에 없는 무언가가 들어 있다 — **미해결**.

## 그래서 다음은 미러다

`tcp` 의 숫자가 말하는 것:

```
512x384, 가속 clear 를 켠 뒤의 프레임 : 146.7 ms
   그중 clear                        :   ~0 ms  (엔진)
   그중 삼각형                        :   ~0 ms
   나머지                             : 146.7 ms  = 미러
```

clear 를 가속하고 나니 **미러가 프레임의 사실상 전부다.** 처음에 "미러를 좁혀도
47% 가 상한"이라고 적었는데, 그 47% 는 CPU clear 가 나머지를 먹고 있을 때의
비율이었다. 이제는 100% 에 가깝다.

즉 저장소가 코드에 적어둔 그 작업 — 미러를 실제로 건드린 곳으로 좁히기 — 이
이제 남은 유일한 항목이고, 값어치도 처음 생각보다 크다. 다만 그것은 여전히
위험한 쪽이다: 소프트웨어 래스터라이저가 무엇을 건드렸는지 보이지 않고, 훅을
거치지 않는 원시는 아예 보이지 않는다.
