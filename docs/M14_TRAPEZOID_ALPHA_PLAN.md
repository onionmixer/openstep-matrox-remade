# M14 — 사다리꼴 층의 알파 결함 (2026-08-29, 코딩 전)

`M12 §11` 이 크기를 잰 것을 고친다.  **출하 중인 층**의 결함이므로 고치는
쪽보다 **깨뜨리지 않는 쪽**이 어렵다.

## 1. 확립된 사실

`blrr`(RGB 텍스처, REPLACE), 128x128 사각형, `GL_SMOOTH`:

```
팔           dA/dx     dA/dy     상수     최악 잔차
소프트웨어  1.00000   0.00000   57.000     0.00
WARP        1.00000   0.00000   56.000     0.00   (§8 의 한 레벨 잘라내기)
사다리꼴   -0.06680   0.58750  151.966    75.79
```

그런데 그 적합은 **두 삼각형을 섞은 것**이었다.  대각선으로 갈라 보면:

```
대각선 위(T1)  8128 화소   평균 0.00   최소 0   최대   0    <- 정확
대각선 아래(T2) 8256 화소  평균 107.59  최소 0   최대 128   <- 틀림
```

**한 삼각형은 완전히 정확하고 다른 하나가 통째로 어긋난다.**

T2 안에서 기울기는 맞다 — 행을 따라 화소마다 +1, 열을 따라 변화 없음, 즉
`dA/dx = 1, dA/dy = 0` 으로 소프트웨어와 같다.  **시작값만 +128 높다**
(x=40 에서 97 이어야 하는데 225).  "평균 107.59, 최대 128" 은 255 에서
**포화**해서 깎인 값이다 — 16384 중 4753 화소가 0 또는 255 다.

네 장면이 규칙을 준다:

```
blar  RGBA + REPLACE   알파가 텍스처에서만        두 팔 다 정확
blrr  RGB  + REPLACE   알파가 프래그먼트에서      사다리꼴 T2 틀림
blrm  RGB  + MODULATE  같음                       사다리꼴 T2 틀림
blam  RGBA + MODULATE  프래그먼트 x 텍스처        사다리꼴 틀림
```

## 2. 읽어서 배제한 것

* **평면 풀이는 삼각형 안에서 일관된다.**  `x1,y1,x2,y2,den` 이 알파와
  같은 `a,b,c` 에서 한 번 계산되고(`:983-987`), 주석이 *"a, b and c are
  never reassigned in this function"* 이라고 못박는다.  스왑 없음.
* **두 사다리꼴이 같은 `aplane` 과 같은 `a` 를 받는다**(`:1358`, `:1380`).
  삼각형 안에서 앵커가 갈릴 여지가 없다.
* **T2 는 사다리꼴이 하나다.**  꼭짓점 y 가 40, 168, 168 이라 `rM == rL`
  이고 둘째 사다리꼴은 건너뛴다.
* **의도한 꼭짓점 값으로 손계산하면 평면이 맞는다.**
  `a=(40,40,96) b=(168,168,224) c=(40,168,96)` →
  `den 16384, d1 128, d2 0, dx 1.0, dy 0.0, at_a 96`.  그리고 첫 행의
  시작값은 `96 + 1x0.5 = 96.5 -> 97` 로 **정확**하다.

**그러므로 읽어서는 못 찾았다.**  손계산은 *의도한* 꼭짓점 값을 가정하는데,
그 가정 자체가 검사 대상이다.

## 3. 남은 용의자

| | 내용 | 왜 아직 살아 있나 |
|---|---|---|
| **S1** | 빌더가 받은 **꼭짓점 알파가 96/224/96 이 아니다** | 훅은 x·y·z 만 기록한다(`hookLastWin`).  알파는 `VB->ColorPtr->data[idx][3]` 에서 오고, 재생 기록이 존재하는 이유 자체가 *"two-side lighting points ColorPtr ... according to this triangle's facing"* 다 |
| **S2** | 시작값이 `osmgaStartFixed` 의 **클램프**에 걸린다 | `v<0 -> 0`, `v>255 -> 255`.  주석은 *"the cost is at most one level at one corner"* 라고 하지만 그것은 **평면이 옳을 때**의 이야기다 |
| **S3** | 두 삼각형이 한 배치에 들어가면서 **레지스터가 이어진다** | 색·깊이·텍스처는 사다리꼴마다 다시 쓰는데 알파도 그런지 확인 안 됨 |
| **S4** | `osmgaClampSlope` 가 알파 증분을 자른다 | `dA/dx = 1` 은 작아서 그럴 리 없어 보이지만 **재지 않았다** |

색 채널이 멀쩡하다는 것이 S1 을 약하게 만든다(`blrm` 의 MODULATE 에서
빨강·초록·파랑이 2/1/1 안).  그러나 **알파 바이트만** 틀릴 수도 있다.

## 4. 설계

### P1 — 두 삼각형을 떼어 놓는다 (코드 최소, 판정 확실)

사각형이 둘을 섞고 있다.  같은 두 삼각형을 **따로** 그려 알파를 덤프하고,
각각을 유리수 평면 신탁에 대고 채점한다.  예상: T1 정확, T2 시작값 +128.

이것만으로도 `M12 §11` 의 "한쪽만 틀리다" 가 **적합의 부산물이 아니라
직접 관측**이 된다.

### P2 — 빌더가 **받은** 알파를 기록한다

`hookLastWin` 과 같은 자리에 알파를 넣는다(세 꼭짓점, 마지막 삼각형).
`OSMGAMesaHookLastAlpha(v)`.  그러면 S1 이 한 줄로 갈린다:

```
96 / 224 / 96 이 아니면   -> 결함은 훅의 입력이고 빌더가 아니다
96 / 224 / 96 이면        -> 입력은 옳고 빌더 아래가 틀렸다  -> P3
```

### P3 — 빌더의 산출을 기록한다 (P2 가 입력을 결백하게 만든 경우에만)

`t->a0 / adx / ady` 를 그대로 찍어 python 이 손계산과 대조한다.  세 갈래:

```
a0 가 기대와 다르다              -> 시작값 계산 (S2 포함)
a0 는 맞는데 그림이 틀리다       -> 커널 인코딩이나 레지스터 이어짐 (S3)
adx/ady 가 다르다                -> 기울기 (S4)
```

## 5. 고치기 전에 정할 것 — 회귀망

**출하 중인 층이다.**  지금 통과하는 것을 깨뜨리면 고친 것보다 손해다.
고침 전후로 **전부** 돌린다:

```
coverage-compare   아홉 도형 x 세 패스     현재 nothing to report
seam-compare       다섯 도형 x 여덟 모드   현재 nothing to report
attrib-compare     두 도형                 현재 색 위상 정상
mesh-compare       mesh16 512 삼각형       현재 (0,0,0)
texdraw-test       스위트 전체             현재 0 failing
blend-compare      네 장면 x 두 팔         현재 ok 16384 전부
depth-agree/func/polyoffset                현재 통과
```

특히 `attrib-compare` 는 **알파를 채널로 채점한다**(`NAME = red green blue
alpha`).  거기서 알파가 지금 정상이라는 것은, 고침이 **그 장면을 깨뜨리면
안 된다**는 뜻이다 — 그리고 그 장면이 왜 지금 통과하는지가 결함의 조건을
말해 줄 수도 있다.

### 6.1 내가 놓쳤고 codex 도 놓친 것

내가 회신을 기다리는 동안 데이터로 확인한 것: **`attrib` 장면은 삼각형이
하나다**(`:121-127`).  그래서 "두 번째 삼각형" 결함을 드러낼 수가 없었다.
그리고 무텍스처 빌더는 텍스처 빌더에 `tex = 0` 으로 **위임**한다(`:1412`) —
같은 함수다.  그러므로 "텍스처가 붙어야 틀린다" 도 빌더로는 설명되지 않는다.

네 장면을 사각형의 대각선으로 갈라 보면 규칙이 분명하다:

```
장면   T1(위)  평균   T2(아래) 평균
blrr    0.00           107.59
blrm    0.00           107.59
blar    0.00             0.00     <- 알파가 텍스처에서 온다
blam    0.24            53.29
```

**언제나 둘째 삼각형만 틀린다.**

## 7. 기전 — 확인됨

인코더는 레지스터 24 개를 여섯 그룹으로 나누고, **직전 사다리꼴과 값이
같은 그룹은 쓰지 않는다**:

```c
static const signed char osmgaDmaGroup[OSMGA_DMA_GROUPS][4] = {
    ...
    { 20, 23, -1, -1 }    /* alpha start, alpha control */
};
...
for (sl = 0; !dirty && sl < 4; sl++)
    if (ix >= 0 && v[ix] != prevV[ix]) dirty = 1;
if (!dirty) continue;
```

이 사각형에서 **두 삼각형의 알파 시작값은 같다** — 둘 다 `(40,40)` 에
앵커하고 그 꼭짓점의 알파가 96 이다.  그러므로 그룹 5 가 T2 에서
**건너뛰어진다.**

그런데 `MGA_ALPHASTART` 는 멱등한 상태 레지스터가 아니라 **엔진이 그리면서
전진시키는 보간의 시작값**이다.  T1 이 x=168 까지 그리고 나면 그 레지스터는
약 224 를 들고 있다.  T2 는 거기서 시작한다.

```
관측된 T2 시작값 225 = 224 + 0.5 반올림
기대값            97 =  96 + 0.5 반올림
```

**색이 멀쩡한 이유도 같은 표가 말한다.**  그룹 4 는 `{11,14,8,15}` =
Gstart, Bstart, Rstart, Bdx 인데, 이 사각형의 두 삼각형은 **꼭짓점 색이
다르므로** 그룹이 dirty 가 되어 매번 쓰인다.  알파만 우연히 같아서
건너뛰어졌다.

**그러므로 이것은 알파의 결함이 아니라 추적의 결함이고, 색 시작값도 두
사다리꼴이 우연히 같은 값을 원하는 순간 똑같이 틀린다.**  잠재 범위가 훨씬
넓다.

## 8. 수정된 설계

### P0 — 스위치 하나로 진단을 확정한다 (재부팅 없음, 코드 없음)

`OSMGAHW3DTune` 의 세 번째 워드가 `osmgaTrackState` 다.  클라이언트는 이미
있다(`test/openstep-mga-hw3d-waits.m`).

```
현재 값을 읽는다 -> 추적 끔 -> blrr 무블렌딩 덤프 -> 알파를 소프트웨어와 대조 -> 값 복원
```

**미리 적는 예측**: 추적을 끄면 T2 의 알파가 옳아지고 사다리꼴 팔이
소프트웨어와 맞는다.  틀리면 §7 이 틀린 것이다.

### P1 — 폭이 128 이 아닌 장면 (codex 4)

꼭짓점 알파 `16, 80, 16`(기울기 0.5).  포화가 없고, `+128` 이 유지되면
span 과 무관하고, 크기가 따라 변하면 span 결합이다.

### P2 — 무텍스처 두 삼각형 (codex 2)

같은 기하·같은 알파 평면을 **텍스처 없이** 그린다.  거기서도 T2 가 틀리면
텍스처는 무관하고 §7 이 유일한 설명이 된다.

### P3 — 고침

추적표에서 `MGA_ALPHASTART`(그리고 같은 성질의 색 시작값 `Rstart/Gstart/
Bstart`, 깊이 시작값 `DR0`)를 **추적에서 제외**한다 — 값이 같아도 매번 써야
하는 레지스터다.  **커널 변경이므로 재부팅이 필요하다.**  P0~P2 를 먼저
끝내고 한 번에 간다.

## 9. 회귀망 — codex 가 구멍을 짚었다

`blend-compare.py` 는 무블렌딩 원천 차이를 **보고만 하고 채점하지 않는다**.
그래서 지금의 "전부 깨끗함" 은 이 결함과 **공존한다**.  고치기 전에 관문을
만든다: 네 장면의 무블렌딩 알파를 소프트웨어와 대조해 **실패시킨다**, 포화
없는 변종을 더한다, 그리고 추적 켬/끔이 같은 그림을 내는 것을 요구한다.
