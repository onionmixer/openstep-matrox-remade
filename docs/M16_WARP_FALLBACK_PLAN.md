# M16 — WARP 층의 거절·재생·순서 (2026-08-29, 코딩 전)

`M9 §9.4` 의 4 단계 중 시간 측정은 `M15` 가 했다.  남은 것은 **거절이
일어났을 때 그림이 온전한가**이고, 이것은 정책보다 앞선다 — 어떤 정책도
되돌림이 정확하지 않으면 안전하지 않다.

## 1. 지금 상태 — 시험 둘이 "안 했다" 고 말한다

기존 시험 둘을 두 팔에 돌렸다.

```
narrowreplay   사다리꼴 PASS
               WARP     "NOT TRIGGERED: no offset made the sliver refuse
                         -- the frozen triple no longer reaches TRICROSS"
replaystate    사다리꼴 PASS
               WARP     "NOT TESTED: nothing was replayed"
```

**둘 다 계약을 어긴 게 아니라, 자기가 아무것도 시험하지 못했다고 말한
것이다.**  공허하게 통과하지 않는 설계라 이 사실이 드러났다.

이유는 하나다.  얼어붙은 슬리버는 **`TRICROSS`** 로 거절되는데 그것은
**사다리꼴 기하의 판정**이다.  WARP 경로는 사다리꼴을 만들지 않으므로 그
판정에 닿을 수 없고, 그 삼각형은 **엔진까지 간다.**

## 2. 그리고 주입이 이 층에 닿지 않는다 — 세 번째다

`OSMGAMesaHookInjectRefusal` 은 `batch->magic` 을 망가뜨린다 —
**v9 플러시 안에서만**(`Hook.c:1432`).  WARP 플러시에는 대응물이 없다.

`M12` Stage 0 의 **카운터**, `M15` 의 **타이밍**에 이어 **세 번째**로,
WARP 플러시가 v9 플러시의 시험 장치 없이 쓰였다.

그 헤더가 주입에 대해 이렇게 적어 놓았다:

> Refusing every batch and getting a byte-identical picture back out is the
> clearest demonstration this project has that the fallback is exact.

**그 시연이 이 층에는 아직 없다.**

## 3. 할 일

```
S4-0  주입이 WARP 플러시에도 닿게 한다 (wb->magic, v9 와 대칭)
S4-a  되돌림이 정확한가 — 주입 켜고 mesh16 을 WARP 으로,
      그림이 전(全) 소프트웨어와 바이트 동일해야 한다
S4-b  재생 계약 — 누적된 소스 **전부**가 순서대로 한 번씩.
      v9 의 좁히기를 쓰지 않는다는 것이 M9 §9.2(c) 의 명시적 결정이므로,
      이 시험은 v9 과 **반대**를 단언한다
S4-c  문맥 네 값 (replaystate 를 WARP 팔에서)
S4-d  혼합 층 순서 — 겹치는 삼각형에 블렌딩을 켜고, 층을 번갈아
S4-e  슬리버 — v9 이 거절하는 기하를 v10 이 받는다.  옳게 그리는가
```

## 4. 미리 보이는 위험

**두 층의 수용 집합이 다르다.**  `TRICROSS` 는 한 예일 뿐이다.  같은
삼각형이 한 층에서는 소프트웨어로, 다른 층에서는 엔진으로 간다는 뜻이고,
그러면 "같은 그림" 은 두 층이 각자 자기 되돌림을 정확히 할 때만 성립한다.
이것은 측정으로 닫을 문제가 아니라 **결정**이 필요한 자리일 수 있다.

## 6. 수정된 설계

### 6.0 먼저, WARP 플러시에 없는 시험 장치 (네 번째)

```
주입          wb->magic 을 v9 과 대칭으로
hookReplayed  WARP 재생도 세게
hookWarpTried 제출에 들어간 WARP 소스 — 결과와 무관하게.
              이것이 없으면 "전부 거절" 실행에서 층이 관여했음을 못 세운다
```

### 6.1 S4-a 는 주장을 좁힌다

> **인코딩 전 검증 거절**은 그림을 바꾸지 않는다.

`verdict == OK` 뒤의 실패는 범위 밖이다 — 그때는 일부러 철회하고 버린다.

그리고 프레임 수를 **셋 미만**으로 잡거나, 철회가 일어나는 것을 **단언**한다
(python: 배치 3/프레임, 한계 8, 성공 없음 → 3 프레임).  둘 중 하나를 고르되
모른 채로 지나가지 않는다.

관문: WARP 검증 거절 셋, `E_MAGIC`, 소스 512 구조됨, **버려짐 0**,
`hookWarpTried == 512`.

### 6.2 S4-b 는 관측 신탁이 필요하다

개수로는 부족하다.  **겹치고, 블렌딩하고, 소스마다 고유한** 고정물 —
순서가 바뀌면 그림이 바뀌도록.  그리고 재생 순서 로그.

경계를 고정물이 직접 만든다: 240 소스(가득 참)와 마지막 부분 배치,
배치 안의 런 여럿(`dwgctl`/`alphactrl` 변화), 명시적 플러시 경계.

### 6.3 S4-d 는 둘 다

```
1  시험 훅으로 결정적 스케줄 — 렌더 상태를 고정한 채 층만 번갈아.
   "앞선 WARP 를 플러시하고 소스 순서를 지킨다" 를 **정책과 무관하게** 세운다
2  정책이 자연히 번갈게 하는 통합 사례 — 실제 층별 개수를 단언
```

### 6.4 수용 집합 — 계약을 먼저 정한다

```
(A) 보수적 교집합: 두 층이 다 받는 것만 엔진으로
(B) 층별 수용: 각 층이 독립적으로 렌더링 계약을 만족하면 허용
```

**정하지 않고 S4-e 를 재면 안 된다.**  (B) 라면 슬리버도 소프트웨어에 대고
커버리지·색·깊이·텍스처·블렌딩 신탁을 통과해야 하고, (A) 라면 정책이 그
차이를 배제해야 한다.

## 8. S4-0 과 S4-c 결과 (2026-08-29)

### 8.1 WARP 플러시가 갖고 있지 않던 것 넷

```
주입           wb->magic 을 v9 과 대칭으로   (Hook.c:1432 의 한 줄이 없었다)
hookReplayed   WARP 재생도 센다              (v9 의 :1509 :1567 :1585 뿐이었다)
hookWarpTried  제출에 들어간 WARP 소스       (새로 만듦)
(그리고 M12 의 카운터, M15 의 타이밍)
```

`hookWarpTried` 가 필요한 이유는 codex 가 짚었다: `hookWarp` 는 **성공한**
제출 뒤에만 늘어서, **모든 배치가 거절되는 실행**은 `warp 0` 을 보고하고
층이 관여했는지조차 말하지 못한다 — 그리고 그것이 되돌림 시험이 필요로 하는
바로 그 실행이다.

### 8.2 S4-c 는 섰다 — 문맥 네 값이 복원된다

`replaystate` 를 두 팔에 돌렸다.  **둘 다 PASS.**

```
사례                    hw     replay   soft   replayed
no offset at all      16383    16384   16384      2
units only            17407    17408   17408      2
units only, other way 15359    15360   15360      2
factor and units      16639    16640   16640      2
```

(WARP 팔)  **재생 열이 소프트웨어와 정확히 같다.**  그러므로 Mesa 가
삼각형 콜백마다 흔드는 네 값 — 폴리곤 오프셋, `ColorPtr`, `IndexPtr`,
`Specular` — 이 WARP 플러시에서도 제대로 저장·복원된다.

`hw` 열이 네 사례 전부에서 **정확히 −1** 인 것은 `M12 §9.3` 의 그 한
코드다.  시험이 이제 **층을 보고** 그 한 코드만 허용하며 이름을 붙여
찍는다(허용은 WARP 을 실제로 그린 팔에만 준다).  `polyoffset` 의 세 실패와
같은 부류였고, 같은 방식으로 정직해졌다.

### 8.3 회귀

```
mesh16   사다리꼴 (0,0,0)    WARP (0,0,56)
blend    두 팔 다 네 장면 ok
```

깨진 것 없음.

## 9. S4-a 결과 (2026-08-29) — **되돌림이 그림을 바꾸지 않는다**

고정물은 **겹치고 블렌딩한다**.  닿지 않는 메시라면 재생이 순서를 바꾸거나
하나를 두 번 그리거나 하나를 잃어도 그림이 같을 수 있다 — 바꿀 것이 없으니.
겹치고 블렌딩하면 결과가 **교환법칙을 따르지 않으므로**, 순서가 틀리면
화소가 달라진다.

그리고 비교를 **정확히** 할 수 있다: 주입이 켜지면 엔진에 아무것도 안
가므로 그림이 전부 Mesa 것이고, 이 층의 측정된 차이 셋(색 한 레벨, 깊이 한
코드, 변에 붙은 소유권)이 나타날 수가 없다.

```
                                      512 삼각형   200 삼각형
WARP 제출에 들어간 소스                    512          200
거절된 배치                                  8            3
그중 magic 판정                              8            3
소프트웨어로 재생된 소스                   512          200
구조된 소스                                512          200
버려진 소스                                  0            0
엔진이 그린 삼각형                           0            0
전(全) 소프트웨어와 다른 화소            0/76800      0/76800
백스톱                                     걸림       안 걸림
```

**둘 다 PASS.**  512 쪽은 백스톱을 밟아 **가속이 철회되고도 그림이 그대로**
였다 — 철회 경로가 아무것도 잃지 않는다.

### 9.1 예측이 또 틀렸고, 이유가 유용하다

나는 거절이 **셋**일 줄 알았다(512 소스 / WARP 용량 240).  **여덟**이다.

```
512 / 8 = 64 삼각형/배치   -- 용량 240 보다 훨씬 적다
mesh16 도 512 에 제출 9 회 = 57 삼각형/제출
```

**배치를 끝내는 것은 용량이 아니라 렌더 브래킷이다.**  `REMAINING_WORK 3-46`
이 제출 횟수에 대해 이미 적어 놓은 것과 같다.  그리고 여덟은 정확히 거절
한계라, 한 프레임이 백스톱에 **딱 닿는다.**  시험이 이제 어느 쪽이었는지
스스로 말한다 — 콘솔 한 줄에 맡기지 않고.

## 10. S4-b — 용량 (2026-08-29)

### 10.1 두 용량 다 immediate 모드로는 닿지 않는다

allocator 자신의 단위로 쟀다(입력 삼각형을 세어 나누는 것은 다른 질문이다 —
런은 `dwgctl`·`alphactrl` 이 움직일 때 끝나고 삼각형 수는 그것을 못 본다).

```
장면            가장 큰 배치        이유
상태 균질       213 정점 / 1 런     Mesa VB_MAX = 216+VB_START 정점
상태 교대         3 정점 / 1 런     GL 상태 변경이 정점 버퍼를 끝낸다

용량            720 정점 / 16 런
닿는 비율          29.6%  /  6.2%
```

**런 경계는 GL 상태 변경을 요구하고, GL 상태 변경은 배치를 끝낸다.**
그러므로 immediate 모드에서 **한 배치는 결코 런 하나를 넘지 못한다** —
부하의 우연이 아니라 구조다.

그리고 이것이 `M15` 의 churn 결과(163% 느림)를 완전히 설명한다: 배치마다
삼각형 하나이고, 그 하나를 위해 약 110 dword 의 상태 목록을 전부 낸다.

### 10.2 그래서 시험용 상한을 만들었다 — 사다리꼴에 이미 있는 것의 대응물

`OSMGAMesaHookBatchLimit` 이 사다리꼴에 하는 일을 WARP 에 한다.  **문턱만
옮긴다** — 버퍼·인코더·제출·리셋·재시도는 전부 생산 경로 그대로이고,
`Reset` 이 실제 용량으로 채운 뒤 caller 는 **낮추기만** 할 수 있다.

주입과는 **같이 쓸 수 없다**.  상한을 낮추면 배치가 많아지고, 주입이 켜져
있으면 그것이 연속 거절이 되어 **백스톱이 먼저 철회한다**(200 삼각형을 10 씩
= 20 배치, 한계는 8).  그래서 용량 모드는 주입하지 않고, **같은 층의
상한 없는 실행과** 비교한다 — 상한은 배치의 시작과 끝만 옮기므로 **관용치가
필요 없고**, 다르면 그것이 배치 결함이다.

```
상한            상한 없이      상한 걸고     상한 없는 실행과 다른 화소
30 정점         213 / 1 런     30 / 1 런            0 / 76800
12 정점         213 / 1 런     12 / 1 런            0 / 76800
```

**가득 참 → 플러시 → 리셋 → 같은 삼각형 재시도**가 그림을 바꾸지 않는다.
상한이 실제로 물렸음도 시험이 단언한다(안 물리면 실패).

### 10.3 무엇을 세우지 **못하는가**

물리적 720 정점 경계 — 디스크립터 크기, 카운터 폭, 큰 패킷에 대한
마이크로코드 동작.  낮춘 상한은 **제어 흐름**을 시험하지 그것을 시험하지
않는다.  더 큰 프론트엔드나 직접 하네스가 필요하고, 이것은 그 대체물이
아니다.

**용량 자체는 줄이지 않는다.**  지금 Mesa 가 못 채운다는 이유로 줄이면
미래의 프론트엔드를 위한 여유를 정확성 이득 없이 버리는 것이다.  물리 용량은
두고, 시험 상한을 두고, 관측된 프론트엔드 천장을 적어 둔다.

## 11. 수용 집합 — 계약을 정했다 (B, 공통 바닥과 함께)

```
공통 의미 자격  ∩  층별로 안전이 입증된 자격   ->  그 층
그 밖             ->  정확한 소프트웨어 되돌림
```

**백엔드 선택은 관측 가능해서는 안 된다.**  삼각형이 사다리꼴로 갔는지
WARP 으로 갔는지 소프트웨어로 갔는지는 구현 세부이고, 화소·순서·색·깊이·
텍스처·블렌딩은 아니다.

(A) 보수적 교집합을 **영구 구조로는** 택하지 않는다: WARP 이 하드웨어를
써도 되는지 알기 위해 **사다리꼴 빌더/검증기를 돌려야** 하고, 그러면 셋업
이득의 일부를 버리며 사다리꼴 구현의 우연에 WARP 의 범위가 묶인다.  그리고
그렇게 해도 **교집합 안에서 WARP 이 옳다는 것은 여전히 증명되지 않는다** —
공통 허가는 공통 래스터화가 아니다.

그러므로 얼어붙은 슬리버(`TRICROSS`)는 **WARP 의 보수적 거부 집합**에 둔다.
사다리꼴의 판정은 WARP 에 대한 **유용한 시험 입력**이지 영구적 문지기가
아니고, WARP 이 그것을 그리려면 소프트웨어 대비 신탁을 먼저 통과해야 한다.

## 12. S4-d — 혼합 층 순서 (2026-08-29)

### 12.1 신탁이 바이트 비교가 아닌 이유

두 층은 색 한 레벨이 다르다(`M12 §8`).  전부 사다리꼴인 프레임과 섞인
프레임을 바이트로 비교하면 **그 차이에서 실패**하고 순서에 대해서는 아무
말도 못 한다.

그래서 삼각형을 **불투명**하게 하고 깊이 시험을 끈다: 마지막에 쓴 삼각형이
화소를 갖고, 그게 누구인지는 **순서만으로** 정해진다.  색을 **4 레벨씩**
띄우면 한 레벨 밀려도 같은 인덱스로 반올림되므로 **승자의 신원이 살아남는다.**
그러면 물을 것은 하나다 — **모든 화소에서 승자가 같은가.**

```
한 층으로만       warp 62, 사다리꼴  0
번갈아            warp 31, 사다리꼴 62   (31 삼각형 x 최대 2 사다리꼴)
소유자가 있는 화소   31426
소유자가 바뀐 화소       0
```

**PASS.**

### 12.2 층을 바꾸려면 플러시가 필요하다 — 구조다

첫 시도는 `warp 32, 사다리꼴 0` 이 나왔다.  플래그를 삼각형마다 토글했는데
**아무것도 결정하지 못했다** — `glEnd` 는 그리지 않고, Mesa 는 즉시 버퍼에
표시했다가 그 버퍼가 찰 때 래스터화하므로 **삼각형을 그리는 경로는 플러시
시점에 선택된 것**이다(메시 시험이 비싸게 배운 것이고 그 주석이 적어 놓았다).

그래서 삼각형마다 `glFlush` 한다.  그리고 그것이 일반적 사실을 말해 준다:

> **이 백엔드에서 층 전환은 언제나 플러시와 함께 일어난다.**  층을 바꾸는
> 길은 정책이 거절하는 GL 상태(그 자체가 Mesa 버퍼를 플러시한다)이거나
> 플러시 시점에 읽히는 플래그뿐이고, **버퍼에 쌓인 무리 한가운데서 층을
> 바꿀 방법은 없다.**

그러므로 "쌓인 WARP 를 다른 경로 전에 제출한다" 는 보장은 **모든 전환에서
구조적으로 지켜진다.**

### 12.3 그런데 정책은 지금 아무것도 거절하지 않는다

`osmgaHW3DWarpAdmits` 는 널 포인터 말고는 **`OSMGA_HW3D_OK` 만 돌려준다** —
T7·T7e·T8b 가 답한 뒤 repeat 와 블렌딩이 다 허용됐다.

그러므로 **생산 경로에서 층을 번갈게 하는 상태가 오늘은 없다.**  층은
프로세스 단위로 전부거나 전무다.  남은 생산 경로는 **정점 변환 실패**뿐이다
— `OSMGAMesaBuildWarpVertex` 가 좌표 한계나 `rhw` 범위 밖을 거절하면
헬퍼가 `declineOne` 으로 간다.  강한 원근을 섞은 장면이 그 길이고, 그것이
S4-d 의 남은 절반이다.

이것은 `§11` 의 계약과 함께 읽어야 한다: 수용 집합 차이가 **지금은
한쪽뿐**이다 — WARP 은 빌더가 변환할 수 있는 것을 전부 받는다.

### 12.4 생산 경로로도 잰다 — 훅 없이

정책이 아무것도 거절하지 않으므로 남은 길은 **빌더의 변환 실패**뿐이다.
`rhw = qw x tq` 가 `[0.125, 128]` 밖이면 거절되는데, 직교 투영에서 `qw` 는
언제나 1 이라 물지 않는다.  `glFrustum` 이면 `qw` 가 눈 깊이의 역수이므로
**깊이 8 을 넘는 삼각형이 사다리꼴로 떨어진다.**

층은 프로세스 단위로 정해지므로 두 **프로세스**를 비교한다.

```
사다리꼴 팔   warp  0, 사다리꼴 124, 소프트웨어 0
WARP 팔       warp  7, 사다리꼴 110, 소프트웨어 0
```

python 이 미리 계산한 값과 정확히 맞는다: 눈 깊이 2..8 이 7 개, 나머지
55 개가 사다리꼴(110 = 55 x 2).  **훅 없이, 정책 없이, 생산 경로 그대로
섞였다.**

```
소유자가 있는 화소   두 팔 다 31426
한쪽에만 있는 화소             0
소유자가 어긋난 화소           0
```

**S4-d 완료** — 훅 스케줄과 생산 경로 양쪽에서 순서가 지켜진다.
