# T1 — GLQuake 가 가속을 잃는 이유와 그 수정 계획

## 0. 상태

관측: GLQuake 가 실기에서 매우 느리다. 원인은 드라이버가 연속 8회 배치 거절 후
`OSMGAMesaProbeRevoke()` 로 가속을 영구히 반납하는 것이며, 거절 판정은 13
(`OSMGA_HW3D_E_TEXCOORD`) 이다. teapot 등 기존 예제는 멀쩡하다.

이 문서는 **계획서**다. 코드는 아직 고치지 않았다.

## 1. 재현 (실기 불필요, 수초)

`mesa/test-mesa-texcoord.c` 는 **실제 빌더**(`OSMGAMesaBuildTriangleTex`)와
**실제 검증기**(`osmgaHW3DValidate`)를 직접 링크한다. 여기에 무작위 탐색을 넣었다.
각 회차는 삼각형을 무작위로 뽑되 **세 꼭짓점의 텍스처 좌표를 빌더가 허용하는
대역 안에서만** 뽑는다 — 따라서 빌더의 자체 검사는 구성상 통과하고, 거절은
전부 빌더 이후에 일어난다.

길고 얇은 삼각형 수천 개 — 지는 쪽이 정확히 후자다.

## 3. 진단

3번 검사는 `room = OSMGA_HW3D_TEX_COORD_MAX` (2^23 = 8 반복) 을 써서
"기울기 × 상자 변 ≤ 8 반복" 을 요구한다. 그런데 상자 모서리는 그려지는 픽셀이
아니다.

정책 — "측정된 8배 확대를 넘는 텍셀 주소를 만들지 않는다" (헤더 주석: CLAMPUV 가
검증된 범위가 8배 확대 한 경우뿐이고 "그 너머는 아무도 시험하지 않은 성질에
기댄다") — 는 4번이 **정확히, 그리고 따로** 집행한다. 4번은 `lx >= rx` 인 행을
건너뛰고 각 행의 실제 두 끝점만 본다.

그 시점에서 3번에 남은 실제 임무는 코드 자신이 4번 자리에 적어놓았다:
"The slopes have been bounded above, so these products are inside a long."
**즉 오버플로 방지다.** 그런데 오버플로가 요구하는 값은 8 반복보다 훨씬 크다.

## 4. 수정안

상수를 쪼갠다. 3번은 남기되 **좌표 정책이 아니라 오버플로 예산**으로 재단한다.

행 순회가 계산하는 값:

```
ux  = tu0 + tmr[0]*(lx-lx0) + tmr[1]*row
ly  = ux  + tmr[0]*(rx-1-lx)
```

`|tu0| <= 2^23` 은 앞서 실행되는 1번이 이미 보장한다. 각 기울기 항의 예산을 B 라
하면 최악은 `|ly| <= 2^23 + 3B`. long 은 4바이트(빌드가 단언)이므로

```
(2^31 - 1 - 2^23) / 3 = 713,031,679  (= 680 반복)
```

`OSMGA_HW3D_TEX_SLOPE_ROOM = 1<<29` (536,870,912 = **512 반복**) 을 택하면
최악 `|ly| = 1,619,001,344`, 여유 528,482,303. `1<<30` 은 넘친다(계산 python).

그러면 상자 경계는 "이 사다리꼴 상자 안에서 좌표가 512 반복 이상 흔들리지는
않는다" 만 요구하고, **그려지는 픽셀이 ±8 반복 안인지는 4번이 판정한다.**

### 하드웨어 표현 가능성

G400 사양서(`ref/G400SPEC_Jun1999.txt`): TMR0·TMR1 (s/wc 의 x·y 증분),
TMR6·TMR7 (s/wc·t/wc 시작값) 모두 **signed 12.20** — 정수부 12비트, 즉
±2048 반복이 표현된다. 512 반복은 그 안에 넉넉히 든다. 이 완화는 레지스터에
표현 불가능한 값을 절대 싣지 않는다. 다만 "표현 가능"이 "측정됨"은 아니다(§6).

## 6. 검토받고 싶은 위험

1. **`goto texDone` 지름길**(`boxOK && reach == 0 && bands == 0`)과 그 앞의
   상자 모서리 평가는 행 순회보다 먼저 돈다. 커진 기울기 예산에서 그쪽 산술도
   long 안에 남는가? 같은 감사가 필요하다.
2. `texSpanLo/texSpanHi` 누산과 바이어스 사다리(`reach`, `bands`)가 좁은 경계를
   전제하고 있지는 않은가.
3. **하드웨어 보간기가 그려지지 않는 행을 통과할 때 누산기가 포화하는가
   순환하는가?** 검증기는 그 행을 건너뛰지만 하드웨어는 안 건너뛸 수 있다.
   s12.20 과 512 반복 예산이면 표현은 되지만, 사양서는 포화 여부를 말하지 않는다.
   이것이 이 계획의 가장 큰 미지수다.
4. 예산을 더 작게(예: `1<<26` = 64 반복) 잡아 측정된 봉투에 더 가까이 남으면서도
   거절이 충분히 사라지는가? §5-1 이 답한다. 답이 "그렇다"면 그쪽이 낫다.
5. 1번(앵커)이 남긴 0~3건은 무시해도 되는가, 아니면 같은 성질의 잔여인가.
6. 애초에 3번을 "정책 검사"로도 쓰려던 의도가 있었다면, 그것을 없애는 게 아니라
   **완화**하는 이 방향이 맞는가. 아니면 3번은 그대로 두고 빌더가 상자 경계를
   미리 알고 소프트웨어로 떨어뜨리는 편이 정직한가(그러면 GLQuake 는 여전히
   느리지만 revoke 는 안 난다).

## 7. 검토 요청 전 자체 검증 (codex 회신 대기 중 수행)

### 7.1 위험 1 은 내가 잘못 세웠다 — 지름길은 **빠른 수용**이다

`goto texDone` 은 상자 네 모서리가 **전부 범위 안**일 때만(`boxOK`) 탄다.
상자는 그리는 픽셀을 전부 포함하므로 "상자에서 범위 안" 은 "픽셀에서 범위 안"
을 함의한다 — 즉 지름길은 범위 밖 삼각형을 통과시킬 수 없다. 소스 주석이
같은 논거를 적어두었다: `p/q <= m` 은 `p - m*q <= 0` 이고 이는 두 오프셋에
대해 아핀이므로 상자 전체에서의 부호는 네 모서리가 결정한다(파이썬 20만 상자로
확인했다고 기록됨).

완화 후 오늘 1071 에서 걸리던 삼각형이 `else` 로 들어가면 둘 중 하나다:
모서리가 범위를 벗어나 `boxOK = 0` → 정밀 행 순회가 돌거나, 모서리가 전부
범위 안이면 → 그리는 픽셀도 전부 범위 안이므로 수용해도 옳다. **어느 쪽도
정책을 새지 않는다.** 위험 1 은 해소.

### 7.2 오버플로 계수 3 은 안전 측으로 맞다

`lx0 = lx` (:873) 는 앵커 행의 왼쪽 끝이고 `bx0/bx1` 은 전 행에 걸친 최소·최대
(:901–904) 이므로 `lx0 ∈ [bx0, bx1]`, 따라서 모서리 평가의 `|dx| <= ex`.

행 순회에서 `lx` 가 `lx0` 보다 왼쪽일 수 있으므로 `(lx-lx0)` 과 `(rx-1-lx)` 의
부호가 갈릴 수 있고, 각각 `ex` 로만 묶인다 → x 항이 최대 `2B`. 여기에 y 항 `B`
를 더해 `|ly| <= 2^23 + 3B`. 계수 3 은 이 최악을 덮는다(부호가 같으면 실제로는
`2^23 + 2B`).

모서리 평가는 `|ux| <= 2^23 + 2B` 로 행 순회보다 작다.

`osmgaHW3DRatioOK` 는 `p <= roomHi * q` 와 `p >= -(q * 16)` 뿐이라 **p 를 곱하지
않는다** — 예산이 커져도 자라지 않는다. `roomHi * q <= 128 * 2^23 = 2^30`.
`osmgaHW3DQAt` 의 분모 기울기는 site 2 의 별도 예산이 묶으므로 무관하다.

### 7.3 `reach` 는 출력이지 입력이 아니다

`reach` 는 `OSMGAHW3DTexReach *` 출력 파라미터(:568, :1208–1210)로, 호출자가
바이어스 밴드를 고르는 데 쓴다. 거절된 배치에서는 호출자가 쓰지 않으므로
예산 완화가 만드는 큰 `reach` 는 소비되지 않는다. 수용된 배치에서는 모든 행이
`RatioOK` 를 통과했으므로 `reach` 는 예산이 아니라 **정책**이 묶는다.
남은 확인 하나: 호출자가 판정이 0 이 아닐 때 `reach` 를 정말 무시하는가.

### 7.4 그래서 남는 진짜 미지수는 하나다

§6 의 3번 — 하드웨어 보간기가 그려지지 않는 행을 지날 때 누산기가 포화하는가
순환하는가. 나머지 위험은 위에서 코드로 닫혔다.

## 9. 반사실 측정 — 예산을 넓히면 site 4 가 잡는가

`OSMGA_HW3D_TEX_SLOPE_ROOM` 을 분리(기본값은 오늘 값과 동일, 동작 무변경)하고
예산만 바꿔 재빌드해 같은 탐색을 돌렸다. 좌표 `[-0.9, 7.9]` 대역, 19972 빌드:

| 예산 | 반복 | 거절계 | 판정13 | 기울기-x | **행끝점** | 기타(기하) |
|---|---|---|---|---|---|---|
| 2^23 (오늘) | 8 | 6114 | 6054 | 5740 | **2** | 60 |
| 2^24 | 16 | 2612 | 2545 | 2483 | **2** | 67 |
| 2^26 | 64 | 587 | 514 | 505 | **2** | 73 |
| 2^28 | 256 | 177 | 103 | 95 | **4** | 74 |
| 2^29 | 512 | 124 | 49 | 42 | **4** | 75 |

좌표 `[0, 1]` 대역만 보면 판정 13 이 455 → 201 → 38 → 4 → **3**.

**해석**: 2^29 에서 풀려난 6005 건 중 정밀 검사가 새로 잡은 것은 **2 건**이다.
즉 상자 경계가 거절하던 삼각형은 거의 전부 그리는 픽셀이 정책 안에 있다.
C1 이 요구한 반사실이며, 결과는 완화를 지지한다. 판정 13 감소율 99.2%(최악 대역),
99.3%([0,1] 대역).

부수 관찰: 실패 항은 압도적으로 **x 항**(`tmr[0]/tmr[2] × ex`)이다. y 항은 최악
대역에서도 157/152 에 그친다. 그리고 예산을 넓히면 "기타"(기하 판정 17, 거절
카운터가 사면하는 것)가 60 → 75 로 는다 — 전에 13 으로 거절되던 일부가 이제
기하 판정에 걸린다는 뜻이고, 사면 대상이므로 revoke 를 부르지 않는다.

## 10. 수정된 결론

- 방향은 유지: 상자 경계를 오버플로 예산으로 재단하고 정책은 site 4 가 집행한다.
- **단 예산은 2^29 가 아니라 2^26(64 반복)이 낫다.** 판정 13 을 6054 → 514
  (91.5%), `[0,1]` 대역은 455 → 38 로 줄이면서 측정된 봉투(8 반복)에서 8배만
  떨어진다. 2^29 가 추가로 얻는 것은 514 → 49 뿐인데 하드웨어 미지수는 8배 더
  커진다. §5-1 이 답을 내라고 한 질문이고, 답은 "더 작게".
- 다만 이 선택은 §11 이 남는 한 잠정이다.

## 11. 남은 차단 사항 (실기 전에 닫아야 함)

1. **빈 행(`lx == rx`)**: 상자는 그 위치를 포함하고 site 4 는 건너뛴다. 하드웨어
   보간기가 그 행을 지나며 누산기를 진행시키는지, 진행한다면 포화하는지
   순환하는지 미확인. 이것이 유일한 실질 미지수다.
2. `-tmr[4]`/`-tmr[5]` 의 `LONG_MIN` 통과 구멍 (C5) — 이 변경과 무관하게 먼저 고칠 것.
3. 실기 절차: 예산을 2^23 → 2^24 → 2^26 순으로 한 단계씩, 매 단계 복원·검증.
   기록 항목은 revoked 수뿐 아니라 site 별 감소, 실제 software fallback 수,
   화면 정확성.
