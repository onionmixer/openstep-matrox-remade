# M1-4D4 — 음수 텍스처 좌표의 도달거리 (계획)

## 1. 측정된 사실

### 1-1 도달거리가 2048 : 1 로 비대칭이다

```
   양수  COORD_MAX = 8 * SPAN = 8388608 단위 = 텍스처 8 장
   음수  NEG_ALLOW =            4096 단위 = 텍스처 1/256 장
```

### 1-2 평범한 타일링이 소프트웨어로 간다

`tile`(s,t 0…3)과 같은 그림을 한 장 왼쪽·아래로 옮긴 `tileneg`(−1…2)를 넣었다.
GL_REPEAT 아래에서 둘은 **같은 그림**이어야 한다.

```
   # tileneg: drawn 0 software 2 persp 0 unsupported 2 declined 0
```

두 삼각형 다 폴백이고, 그 이유는 커널의 `declined` 가 아니라 **`unsupported`** —
빌더가 거절한다.

### 1-3 거절 지점은 빌더다

`mesa/OpenStepMGAMesaTriangle.c:841`

```c
   if (lo < 0.0 || hi > (double)OSMGA_HW3D_TEX_COORD_MAX)
       return OSMGA_MESA_TRI_UNSUPPORTED;
```

정점 좌표가 하나라도 음수면 커널을 보지도 않는다.  그래서 도달거리는 **두 군데**
따로 있다:

| | 대상 | 음수 쪽 한계 |
|---|---|---|
| 빌더 | 정점 좌표 | `0` (전면 거절) |
| 커널 | 걷다 평가된 좌표 | `-4096` |

원근 사각형의 음수 좌표가 커널까지 닿았던 것은 모순이 아니다 — 정점은 모두
음수가 아니었고, 음수는 **변 걷기가 삼각형 바깥의 정수 x 에서 평가**하며 생겼다.

### 1-4 엔진은 음수에서 GL 이다 (M1-4D3)

크기 8·64·1024·2048 에서 `floor(좌표/텍셀) mod 크기`(= GL_REPEAT)와 텍셀 0
(= GL_CLAMP), 경계는 512 단위마다 같은 위상, 선형 필터도 이음매에서 GL 의
straddle 규칙.  **단 −4096 까지만 재봤다.**

## 2. 하고 싶은 것

`glTexCoord2f(-1, 2)` 같은 평범한 타일링을 하드웨어로 그린다.  그러려면 두
한계를 **모두** 넓혀야 한다.

## 3. 닭과 달걀 — 순서가 강제된다

−4096 아래를 재려면 커널이 그 좌표를 통과시켜야 한다.  탐침은 커널 검증을 거쳐
제출하므로 **측정이 커널 변경보다 앞설 수 없다.**  따라서:

1. 커널의 음수 도달거리를 넓힌다 (양수와 대칭)
2. 재부팅
3. 넓힌 구간 전체를 M1-4D3 식으로 **반증 지향** 측정
4. 결과가 깨끗하면 빌더를 넓힌다 (사용자 영역 — 재부팅 불필요)
5. 깨끗하지 않으면 커널을 되돌린다

즉 3 단계에서 실패하면 되돌린다는 전제 위에서만 1 단계가 정당하다.

## 4. 위험 판단

커널 검증기의 임무는 엔진을 나쁜 상태로 프로그램하지 않는 것이다.  음수 좌표가
할 수 있는 일은 주소 계산뿐이고, 그 계산은 −4096 까지 이미 GL 과 같음이 측정됐다.
더 음수인 값이 **산술적으로 다른 연산이 되는 것은 아니다** — 다만 그것이
"그러므로 안전하다"는 증명은 아니며, 그래서 3 단계가 있다.

되돌릴 수 없는 손상(하드 행) 가능성은 낮다고 보지만, 이는 판단이지 측정이 아니다.
[[hardware-nondestructive-testing]] 원칙상 이 판단이 이 계획의 가장 약한 고리다.

## 5. 선택지

| | 커널 음수 한계 | 성격 |
|---|---|---|
| **A** `-COORD_MAX` (양수와 대칭, 8 장) | 텍스처 8 장 아래까지 | 대칭이 곧 근거 |
| **B** `-SPAN` (한 장) | 흔한 타일링만 | 좁게 열고 필요하면 더 |
| **C** 지금 그대로 | 없음 | 타일링은 계속 소프트웨어 |

`p <= roomHi * q` 와 대칭이 되려면 `p >= -roomHi * q` 이므로 A 는 검사식이
**대칭 한 줄**로 단순해진다는 부수 이점이 있다.  B 는 상수가 하나 더 는다.

## 6. 아직 모르는 것

- 큰 음수에서 `q` 가 작을 때(`Q_MIN` 근처) 나눗셈 잔차가 경계를 옮기는지 —
  M1-4D3 §15 에 이미 남긴 항목이고, 여기서 더 커진다
- 빌더의 `lo < 0.0` 을 넓히면 λ 산정(`osmgaPerspPlanes`)의 상한이 음수 쪽에서도
  맞는지 — 지금 λ 는 **음이 아닌 좌표**를 전제로 상한을 고른다
- 음수 쪽에서 텍셀 편향 사다리(`512 - g`)의 대역이 좌표 크기로 정해지는데,
  −8 장이면 크기가 2^23 에 이르러 **다른 대역**이 된다.  `g` 가 달라지면 커널이
  빼는 496 이 더는 맞지 않는다 — 이것이 이 계획에서 **가장 실질적인 위험**이다

## 8. 갱신 (2026-08-24) — 그 사이에 알게 된 것

이 계획을 쓴 뒤로 사다리와 bias 규칙이 통째로 바뀌었다.  다시 읽어야 한다.

### 8-1 엔진은 음수 구간에서 GL 이다 (M1-4D3 §52…§55)

크기 8·64·1024·2048 에서 repeat 이 `floor(좌표/텍셀) mod 크기`, 클램프가 텍셀 0,
경계는 512 단위마다 같은 위상, 선형 필터도 이음매에서 GL 의 straddle 규칙.
**단 −4096 까지만.**

### 8-2 새로 생긴 제약: bias 계약

이제 인코더는 `bias = min(496, 덧값(도달범위))` 를 뺀다.  그 계약은
**"좌표가 caller 가 둔 자리보다 아래로 내려가지 않는다"** 이고, 잔여가 음이 아니려면

```
   모든 화소에서  덧값(p) ≥ bias
```

여야 한다.  덧값은 `|p|` 의 대역으로 정해지고(원근 측정, M1-4D7 §2), 도달범위는
**부호 있는 최댓값**이다(`OpenStepMGAHW3D.c:707`, 0 에서 시작).

지금은 안전하다 — 음수가 `p ≥ -(q/16)` 로 묶여 `|p| ≤ 2^19`, 덧값 504 ≥ 496 ≥ 어떤
bias.  **음수를 넓히면 그게 무너진다.** python:

```
   |p 음수| = 2^22, 양수 도달범위 2^20 : 덧값 448, bias 496, 잔여 -48   계약 위반
   |p 음수| = 2^23, 양수 도달범위 2^20 : 덧값 384, bias 496, 잔여 -112  계약 위반
```

**그러므로 음수 범위를 넓히려면 도달범위가 `p` 가 아니라 `|p|` 를 좇아야 한다.**
이것은 원래 계획에 없던 항목이고, 빌더·커널 어느 쪽을 넓히든 먼저 와야 한다.

### 8-3 닭과 달걀은 그대로다

−4096 아래를 재려면 커널이 통과시켜야 한다.  다만 이제는 되돌릴 근거가 더 분명하다:
`|p|` 추적을 **먼저** 넣으면 넓히더라도 계약이 유지되고, 엔진 거동만 새로 재면 된다.

### 8-4 순서 (제안)

1. 도달범위를 `|p|` 로 바꾼다.  **이것만으로는 거동이 바뀌지 않아야 한다** —
   지금 음수는 작아서 `|p|` 가 양수 최댓값을 넘지 못한다.  차등 시험으로 확인한다.
2. 커널의 음수 한계를 넓힌다 (얼마나?  §8-5)
3. 재부팅, 넓힌 구간을 M1-4D3 식으로 반증 지향 측정
4. 깨끗하면 빌더의 `lo < 0.0` 을 함께 넓힌다 (사용자 영역, 재부팅 불필요)
5. 깨끗하지 않으면 2 를 되돌린다

### 8-5 얼마나 넓힐 것인가

| | 음수 한계 | 성격 |
|---|---|---|
| **A** `-COORD_MAX` (양수와 대칭) | 텍스처 8 장 | 대칭이 근거, 검사식이 한 줄로 단순해진다 |
| **B** `-SPAN` (한 장) | 흔한 타일링만 | 좁게 열고 필요하면 더 |
| **C** 지금 그대로 | 없음 | 타일링은 계속 소프트웨어 |

## 10. 확정된 순서

1. **도달범위를 크기로 바꾼다.**  출력 중립임을 python 으로 전수 확인했고, 차등
   시험에 **음수 전용·혼합 부호** 배치를 넣어 실측으로도 확인한다.
2. **커널의 음수 한계를 −SPAN 으로 넓힌다.  빌더는 닫아 둔다** — 이 상태에서
   음수 좌표에 닿을 수 있는 것은 탐침뿐이므로, 전제가 틀려도 그림에 나오지 않는다.
3. 재부팅.  음수 분자의 덧값을 대역마다 잰다(양수와 같은 2^25 까지).  양·음 축,
   아핀·원근, 경계와 그 전이창.  반증 지향으로.
4. 사다리가 대칭이면 크기 기반 bias 가 정당해진다.  그러고 나서 빌더를 연다.
5. 대칭이 아니면 2 를 되돌린다.

## 11. 1·2 단계가 들어갔다 (재부팅 대기)

### 11-1 도달범위가 크기를 좇는다

python 이 전수로 중립을 보였고(모든 도달 가능 조합에서 bias 동일), 차등 시험이
실측으로 확인했다.  **다만 처음엔 공허했다** — 시험이 시작값을 음수가 아니게
잘라내고 있었고(codex 지적), 고친 뒤에도 기울기가 늘 0 이 아니라 음수만인 배치가
살아남지 못했으며, 게다가 내가 비교 대상을 **크기 오라클**로 잘못 걸어 항상 0 이
나왔다.  셋 다 고치니 **5725 배치**에서 두 도달범위가 실제로 갈렸다.

### 11-2 단언을 안전 성질로 바꿨다

"크기가 부호 최댓값과 같은 bias 를 고른다"는 단언은 **넓히는 순간 깨진다** — 그게
이 변경의 목적이므로 당연하다.  그래서 항상 성립해야 하는 것으로 바꿨다:

> 크기는 부호 최댓값보다 작지 않으므로 bias 는 **더 커지지 않고**, 더 커지지
> 않는 bias 는 잔여가 음수가 되지 않는다는 뜻이다.

### 11-3 음수 한계를 −SPAN 으로 넓혔다

검사가 나눗셈에서 곱셈으로 바뀐다(`p ≥ -(q × 16)`).  `q ≤ 2^23` 이라 곱은 2^27 로
long 안이고, 빌드가 `ALLOW % Q_ONE == 0` 을 강제한다.

**빌더는 그대로 닫혀 있다** (`OpenStepMGAMesaTriangle.c:849`, `lo < 0.0`).  지금
음수 좌표에 닿을 수 있는 것은 raw 탐침뿐이다.

### 11-4 경계를 단언하던 시험들을 옮겼다

넓힘이 유저랜드 단언 셋을 깼고, 셋 다 "0 아래는 거절"을 전제하고 있었다 —
의도된 결과다.  기대값을 뒤집지 않고 **의도를 새 경계로 옮겼다**:

- 음의 증분: `-span` 은 이제 허용 안이므로 `-span*2` 로 벗어나게 하고, `-span` 이
  **통과**하는 것도 짝으로 단언한다
- 왼쪽으로 열리는 변: 기울기를 16 텍스처의 한 텍셀로 키워 31 열의 이탈이 두
  텍스처 아래로 가게 하고, **허용 경계를 정확히 걷는 쌍**을 새로 넣었다 —

### 11-6 재부팅 뒤 (3 단계)

1. 모든 기준값 불변이어야 한다 — 빌더가 닫혀 있으므로 그림은 음수에 닿지 않는다
2. 탐침 §51…§65 전부
3. **음수 분자의 덧값을 대역마다 잰다.**  양수 쪽과 같은 2^25 까지면 된다 —
   앵커 검사와 기울기 상한이 둘 다 대칭이라 `|p| ≤ 3·COORD_MAX` 이기 때문이다
   (codex 는 `16·Q_MAX = 2^27` 이라 했지만 비율 상한은 구속력이 없다)
4. 사다리가 대칭이면 빌더를 연다.  아니면 §11-3 을 되돌린다

## 12. 3·4 단계 — 재고, 열었다

### 12-1 새 절차가 처음으로 값을 했다

재부팅 뒤 `/usr/local/nxbuild/bin` 의 일곱 바이너리가 그대로 있었다.  재빌드 없이
바로 측정에 들어갔다.  `/tmp` 는 `console.log` 뿐이었다.

### 12-2 사다리는 대칭이 아니다 (§66)

`q = 65536` 에서 다섯 대역을 걸었다.  **양수 대조군 두 줄**이 같은 산술로
504·496 을 재현하는 것이 먼저다 — 그게 부호를 못 박고, 실제로 내 첫 출력의 부호
오류를 잡았다(`496 + 계단` 이 아니라 `496 − 계단`).

```
   -2^16 … -2^20   계단 -15   덧값 511   (다섯 대역 전부)
   +2^19           계단  -8   덧값 504   <- 대조군
   +2^20           계단  +0   덧값 496   <- 대조군
```

**음수 분자는 크기와 무관하게 511 을 받는다.**  양수 쪽 사다리가 아니다.

이것이 넓힘을 안전하게 만든다: 음수 화소의 잔여는 `511 − bias ≥ 15 ≥ 0` 이다.

### 12-3 반증을 시도했고 견뎠다 (§68)

§66 은 `q = 65536` 뿐이라 대역 2^16…2^20 만 봤다.  **허용은 좌표에 걸리는데 대역은
분자로 정해지므로**, 큰 `q` 를 쓰면 좌표가 허용 안에 있으면서 분자는 훨씬 더
음수가 된다 — 아무것도 넓히지 않고 남은 대역에 닿는 길이다.  `q = 2^23` 에서:

```
   -2^23  계단 -127   bias 384 -> 덧값 511
   -2^24  계단 -255   bias 256 -> 덧값 511
   -2^25  계단 -511   bias   0 -> 덧값 511
```

세 경우의 **bias 가 서로 다르다.**  계단이 그에 맞춰 −127·−255·−511 로 움직이고
덧값이 셋 다 511 로 떨어지는 것은 우연일 수 없다.  그리고 §68 은 **원근 경로**다 —
codex 가 (a)에서 요구한 실험이 이것이다.

두 번 헛짚었다: 앵커를 한계에 붙여 놓아 계단 대신 **거절**을 잡았고, bias 가 496 이
아닌데 496 으로 나누어 "덧값 744" 같은 불가능한 값이 나왔다.  목표를 텍셀 하나 위로
옮기고 공식을 중립으로 바꾸니 사라졌다.

### 12-4 큰 음수도 GL 이 원하는 텍셀을 읽는다 (§67)

허용 전 구간의 여섯 좌표 × 네 크기(8·64·1024 폭, 2048 높이) × 두 래핑 모드 =
**48 개 읽기, 전부 python 과 일치**.

### 12-5 선형 필터 (§69)

감김 주기가 텍스처 한 장이므로 −2^20 허용 안에는 이음매가 **하나뿐**이고 그것은
§55 가 이미 쟀다.  남는 것은 내부 보간이라 그것을 쟀다 — 열한 점이 전부 **한 레벨
이내**이고, 차이의 부호와 크기가 기록된 반올림(`(a·(b+1))>>8`)과 같다.

### 12-6 그래서 빌더를 열었다

`OpenStepMGAMesaTriangle.c` 의 `lo < 0.0` 이 `lo < -SPAN` 이 됐다.

```
   # tileneg: drawn 2 software 0 persp 0 unsupported 0 declined 0
```

이전에는 `drawn 0 software 2 unsupported 2` 였다.

| 비교 | 어긋난 화소 |
|---|---|
| `tileneg` 하드웨어 vs 소프트웨어 | **0** |
| `tile` 하드웨어 vs 소프트웨어 | 0 |
| `tileneg` vs `tile` (소프트웨어끼리) | **0** |
| `tileneg` vs `tile` (하드웨어끼리) | **0** |

`s` 가 −1…2 인 것과 0…3 인 것은 GL_REPEAT 아래에서 같은 그림이어야 하고, 실제로
**같은 그림**이다.

기준값 아홉 개 전부 유지된다.  `tileneg` 가 **0** 으로 새 기준값에 들어간다.
