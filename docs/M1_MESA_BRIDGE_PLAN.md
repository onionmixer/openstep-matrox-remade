# M1 — Mesa 연결: 구조 결정과 첫 종단 슬라이스

기준일: 2026-08-19
상태: 계획. **codex 교차검토 1회 완료(2026-08-19)** 후 개정판 — §2-A, §4-4, §5.
선행: D3-0~5 완료. **하드웨어 기능은 전부 실증됐다.** 남은 것은 배관이다.

## 0. 이 문서의 범위

D3까지는 "이 하드웨어가 3D를 할 수 있는가"였고 답은 **예**다. 이 문서는
**"유저랜드 Mesa가 그 하드웨어에 어떻게 닿는가"** 를 정한다.

**Mesa 코드는 아직 건드리지 않는다.** M1은 Mesa보다 앞선 단계로,
**맨손 유저랜드 클라이언트가 삼각형 하나를 그리는 것**까지다. 배관이
증명되기 전에 Mesa를 손대면 실패했을 때 원인이 두 겹이 된다 — D3-3a에서
배치를 모른 채 프로브를 짜서 두 개의 측정 버그를 낸 것과 같은 실수다.

## 1. 이미 증명된 조각

| 조각 | 어디서 | 상태 |
| --- | --- | --- |
| Storm 엔진 구동(기하·색·깊이·텍스처·알파) | D3-0~5 | 실증 |
| 물리 연속 시스템 RAM 64 KiB (`IOMallocLow`) | D1 | 실증 |
| 카드가 시스템 RAM에서 명령을 버스마스터로 읽음 | D1 | 실증 |
| 폴링 완료 대기(22~26 스핀) | D1 | 실증 |
| **레지스터 화이트리스트 DMA 인코더** | D1 | 실증 |
| 유저랜드 → 커널 RPC(`get/setIntValues`) | S3a | 실증 |
| **오프스크린 VRAM을 유저 태스크에 매핑**(cdevsw `d_mmap`) | S4a | 실증 |
| Mesa 3.4.2 소프트웨어 렌더러가 실기에서 동작 | `opennstep-mesa342/` | 실증 |

**M1이 새로 만드는 것은 이 조각들을 잇는 접착제뿐이다.**

## 2. 구조 결정 — 세 안 중 하나

### 2-A. MMIO BAR를 유저랜드에 매핑 (기각)

S4a의 `d_mmap`은 `물리주소 + offset`의 페이지 프레임을 돌려주는 순수 함수다.
**같은 방식으로 BAR0(레지스터)도 매핑할 수 있다.** 그러면 Mesa가 커널을
거치지 않고 엔진을 직접 몬다. 가장 빠르다.

**기각한다.** `PRIMADDRESS`/`PRIMEND`가 노출되면 **유저 프로세스가 카드에게
임의의 물리 메모리를 읽고 쓰게 시킬 수 있다.** 커널 메모리 포함이다.
디스플레이 드라이버 하나 때문에 시스템 전체의 격리를 깨는 것은
정당화되지 않는다.

기각 근거를 남기는 이유: **이 안이 가장 매력적이라 나중에 다시 제안될
것이기 때문**이다.

**중간안은 있으나 이득이 없다.** 교차검토가 짚었듯 DRM은 MMIO를 유저랜드에
**읽기 전용**으로 매핑한다(`mga_dma.c:723`, `_DRM_REGISTERS |
_DRM_READ_ONLY`). 읽기 전용이면 상태 조회에 안전하지만 **그리기는 전혀
빨라지지 않는다.** 쓰기를 허용하는 어떤 부분집합도 결국 스트림 제어를
넘겨야 하므로 같은 위험으로 돌아온다.

### 2-B. **유저랜드는 타입이 있는 상태를 쓰고, 커널이 명령을 만든다** (채택)

**초안은 "유저랜드가 명령 목록을 만들고 커널이 그것을 검증한다"였다.
소스를 확인하고 바꿨다.** DRM은 그렇게 하지 않는다.

DRM에서 유저랜드가 공유 메모리(SAREA)에 쓰는 것은 **원시 명령 목록이 아니라
필드 이름이 붙은 구조체**다(`mga_drm.h`의 `drm_mga_context_regs_t`,
`drm_mga_texture_regs_t`, `drm_mga_server_regs_t`). 커널은 그중 위험한
필드만 검사하고 — `DSTORG`는 front/back 둘 중 하나여야 하고
(`mga_state.c:407-423`), `TEXORG`는 PCI 시스템 메모리를 가리키면 안 되며
(`:426-441`), ILOAD 목적지는 텍스처 힙 안이어야 한다(`:472-489`) —
**레지스터 쓰기는 커널이 만든다**(`:73-120`).

**이 차이가 결정적이다.**

| | 초안(원시 목록 검증) | 채택(타입 상태) |
| --- | --- | --- |
| 커널이 확인할 것 | **위험한 레지스터 전부를 빠짐없이** 열거 | 필드 몇 개의 값 범위 |
| 빠뜨렸을 때 | 유저랜드가 그 레지스터를 씀 | **그 레지스터는 애초에 쓰이지 않는다** |
| D1의 화이트리스트 | 새로 만든 검증기로 대체 | **그대로 계속 적용된다** |

원시 목록 검증은 **화이트리스트가 완전해야만** 안전하다. 타입 상태는
**커널이 어떤 레지스터가 쓰이는지 자체를 결정**하므로 열거가 필요 없다.
D3-3a에서 배웠듯 "빠뜨렸을 때 조용히 틀리는" 설계는 피한다.

```
유저랜드 Mesa                  커널 드라이버                    카드
  상태 구조체 + 삼각형 배열
        ──(공유 버퍼)────────▶ 필드 범위 검사
                              명령 목록 생성(기존 인코더)
                   ──(RPC 1회)──▶ PRIMADDRESS/PRIMEND ──▶ 버스마스터 읽기
                              ◀── 폴링 완료               ◀──
```

- 배치당 RPC **1회**. 삼각형당이 아니다.
- 유저랜드가 삼각형당 보내는 것은 **`AR`/`DR`/`FXBNDRY`/`YDSTLEN` 값**이지
  레지스터 지정이 아니다. 유저랜드가 이미 변환된 정점을 갖고 있으므로
  계산은 그쪽에서 하는 편이 맞고, 커널은 인코딩만 한다.
- **기하 값은 봉쇄를 깨지 못한다.** 클립 레지스터(`CXBNDRY`/`YTOP`/`YBOT`)와
  `PITCH`/`DSTORG`/`ZORG`를 커널이 소유하고, 하드웨어 클립이 색과 깊이를
  모두 막는다는 것을 D3-2와 D3-4b가 실측했다. 유저랜드가 이상한 변을 보내면
  이상한 그림이 나올 뿐 창 밖으로 못 나간다.

`PITCH`가 DRM에서 **X 서버 전용 구조체**(`drm_mga_server_regs_t`)에 들어
있는 것도 같은 이유다 — 3D 클라이언트가 만질 것이 아니다.

### 2-C. 커널이 모든 레지스터를 쓴다 (기각)

삼각형당 RPC가 되어 느리다. 측정하지 않았지만 `getIntValues` 왕복 비용이
DMA 배치 하나보다 클 것이 명백하다.

## 3. 프레젠테이션 — 전체화면만 성립한다

`S5_HW3D_DMA_FEASIBILITY.md` §2가 실측으로 확정한 것:

- **창 안 가속은 불가능하다.** WindowServer와의 협조 프로토콜이 없고
  (`IODisplayDoBlit`은 사문화, S3b), 우리가 가시 영역에 직접 그리면
  리페인트 때 지워진다.
- **전체화면은 정당하게 성립한다.** 우리가 화면을 소유한다.

**M1은 화면에 아무것도 올리지 않는다.** 전부 오프스크린이며, 결과는
유저랜드가 mmap으로 되읽어 확인한다. 프레젠테이션은 M2의 주제다.

## 4. 새로 만들어야 하는 것

### 4-1. 유저랜드에 매핑 가능한 명령 버퍼

D1의 링은 `IOMallocLow`로 잡은 **커널** 메모리다. 유저랜드가 여기에 명령을
쓰려면 매핑돼야 한다.

S4a의 `d_mmap`은 `osmgaMmapFbPhysical + offset`을 돌려주는데, 이는
**VRAM 물리 주소**에 고정돼 있다. 명령 버퍼는 시스템 RAM이므로 **두 번째
매핑 창**이 필요하다.

**미지수 1**: `d_mmap`의 offset 하나로 두 개의 물리 영역을 구분해 줄 수
있는가. offset 구간을 나누면 된다(예: `0` ~ `VRAM끝`은 VRAM,
`0x8000_0000` 이상은 명령 버퍼). **순수 산술이어야 한다는 S4a의 계약을
깨지 않는다** — 상수 둘이 더 늘 뿐이다.

**미지수 2**: `IOMallocLow`가 64 KiB로 제한된다(D1 §3-2). 명령 버퍼가
그 안에 들어가는가. 삼각형 하나가 대략 몇 개의 5워드 블록인지 §6에서
센다.

### 4-2. 공유 구조체와 그 필드 검사

§2-B대로 유저랜드는 레지스터를 지정하지 않는다. 공유 버퍼의 배치:

```c
struct osmgaShared {
    unsigned long magic, version;
    struct { unsigned long dstorg, zorg, texorg, alphactrl,
                           dwgctl, texctl, texctl2, texfilter,
                           tmr[9]; } state;        /* 배치당 1회 */
    unsigned long triCount;
    struct { long y, h;
             long arL[4], arR[4], sgn;             /* 변 */
             unsigned long dr[12];                 /* 색 */
             unsigned long z0, zdx, zdy;           /* 깊이 */
             unsigned long a0, adx, ady;           /* 알파 */
             unsigned long fxbndry; } tri[];       /* 삼각형당 */
};
```

**커널이 검사하는 것 — 이것이 전부다:**

| 필드 | 검사 | 왜 |
| --- | --- | --- |
| `dstorg` | 우리 오프스크린 창 안 | 아니면 가시 프레임버퍼에 쓴다 |
| `zorg` | 우리 깊이 창 안 | 같음 |
| `texorg` | 우리 텍스처 창 안 | 임의 VRAM을 읽는다 |
| `dwgctl` | opcode·atype이 허용 집합 안 | ILOAD 계열은 소스 주소지정이 달라 별도 검토가 필요하다 |
| `y`, `h` | 배치의 클립 창 안 | 이중 방어. 클립이 이미 막지만 값이 터무니없으면 엔진 시간을 낭비한다 |
| `triCount` | 버퍼 크기와 정합 | |

**`SRCORG`는 아예 노출하지 않는다.** D3-5b에서 블렌드가 `DSTORG`를 읽는
것을 확인했으므로 3D 경로에 `SRCORG`가 필요 없다. **필요 없는 것은 구조체에
넣지 않는 것이 가장 강한 검사다.**

`PITCH`/`CXBNDRY`/`YTOP`/`YBOT`/`YDSTORG`/`PLNWT`/`MACCESS`도 마찬가지로
노출하지 않는다. 커널이 배치 시작에 `osmgaStormInitState`로 정한다.

### 4-4. **인코더의 화이트리스트에 구멍이 있었다** (교차검토 소득)

D1 이래 우리는 "group0/group1 규칙상 DMA 주소 레지스터는 인코딩될 수
없다"고 적어 왔다. **`PRIMADDRESS`(0x1e58)/`PRIMEND`(0x1e5c)에 대해서만
참이다** — 그 둘은 두 그룹 밖이다.

그런데 **부차 링과 셋업 링의 주소 레지스터는 group1 안에 있다**:

| 레지스터 | 주소 | 근거 |
| --- | --- | --- |
| `SECADDRESS` | 0x2c40 | `mga_drv.h:500` |
| `SECEND` | 0x2c44 | `:501` |
| `SETUPADDRESS` | 0x2cd0 | `:502` |
| `SETUPEND` | 0x2cd4 | `:503` |

group1은 0x2c00~0x2dff이므로(`mga_drv.h:228-229`) 넷 다 규칙에 걸린다.
확인해 보니 우리 `osmgaDmaIndex`가 **넷을 전부 받아들이고 있었다.**

**오늘 노출은 없다.** 커널이 유일한 호출자이고 그 넷을 지목한 적이 없다.
그래도 고쳤다 — 인코더는 "호출자가 실수해도 막히는 층"이어야지 "호출자가
착하기를 기대하는 층"이면 안 된다. 넷을 명시적으로 거부한다.

**추적**: 이 변경은 D1 경로가 config에서 꺼져 있는 동안 만들어졌으므로
**실기에서 DMA 경로를 다시 켤 때 함께 회귀 확인한다**
(`REMAINING_WORK.md` §3-7).

### 4-3. 인코딩은 커널에만 있다

초안은 유저랜드와 커널이 인코더를 공유하게 했는데, §2-B로 바꾸면서
**유저랜드는 인코딩을 알 필요가 없어졌다.** 공유하는 것은 위 구조체 정의
하나뿐이다. 코드 중복도 줄고 공격면도 줄었다.

## 5. 단계

### M1-0 — 두 개의 매핑 창 (§4-1)

`d_mmap`에 두 번째 창을 더하고, 유저랜드에서 명령 버퍼를 매핑해 **CPU가
쓴 값을 커널이 읽어 확인**한다.

**검증 방법**
- **V1-0-1**: 유저랜드가 패턴을 쓰고 커널이 되읽어 일치. 물리 연속성은
  D1이 이미 확인했다.
- **V1-0-2 (경계)**: **S4a의 계약상 거부는 매핑 실패로 나타나야 하며,
  잘못된 PFN을 돌려주면 임의의 물리 메모리가 유저 프로세스에 노출된다.**
  교차검토가 제시한 목록을 그대로 쓴다:
  `0`, `창0끝-1`, `창0끝`, `창1시작-1`, `창1시작`, `창1끝-1`, `창1끝`,
  그리고 **같은 페이지를 반복 호출**(커널이 두 번 부르고 두 번째 반환값을
  검사하지 않으므로 결정성이 필수다), 페이지 정렬·비정렬 요청.
- **V1-0-2b (오버플로)**: 경계 산술을 `base > 최대 - off` 꼴로 쓴다.
  `base + off`는 감싼다. S4a 핸들러가 이미 그렇게 돼 있으니 새 코드도
  같은 규율을 따른다.
- **V1-0-3**: VRAM 창이 여전히 동작(회귀).

### M1-1 — 필드 검사 단위 시험 (하드웨어 없이)

검사 코드를 **커널에 넣기 전에** 같은 코드를 호스트에서 돌린다. 입력은
- 정상 상태(통과해야 함)
- `dstorg`가 가시 프레임버퍼를 가리킴
- `zorg`가 창 밖
- `texorg`가 창 밖
- `dwgctl`이 ILOAD opcode
- `triCount`가 버퍼를 넘음
- 각 경계의 **바로 안쪽과 바로 바깥쪽**(off-by-one)

**검증 방법**: 각 입력이 예상대로 통과/거부되는가. **하드웨어 위험이 0이므로
실기 이전에 끝낸다.** 경계의 양쪽을 모두 넣는 것은 D3에서 "통과만 보고
거부를 안 본" 실수를 되풀이하지 않기 위해서다.

### M1-2 — 유저랜드가 만든 삼각형 하나

유저랜드 클라이언트가 D3-2의 기울어진 사다리꼴 하나를 명령 목록으로 만들어
제출하고, mmap으로 결과를 되읽는다.

**검증 방법**
- **V1-2-1**: 커널이 직접 같은 도형을 그린 D3-2 결과와 **픽셀 단위로 일치**
  하는가. 대조군이 이미 있다는 것이 이 설계의 장점이다.
- **V1-2-2**: 가드·화면 무변화.
- **V1-2-3 (음성 대조)**: 일부러 `dstorg`를 가시 영역으로 지목한 상태를
  제출해 **거부되는지** 확인한다. 거부되지 않으면 §4-2가 실패한 것이며
  **즉시 중단**한다. 그리고 **거부된 뒤 화면이 무변인지** 함께 본다 —
  검사가 통과시켰는데 그리기가 우연히 무해했던 경우와 구분된다.

### M1-3 — Mesa `dd_function_table` 백엔드 (별도 문서)

여기부터가 Mesa다. M1-2가 통과한 뒤에 착수하며 범위가 커서 별도 계획서로
다룬다. 참고 구조는 Mesa 3.4.2 내장 FX 드라이버이며, 그것이 `VB->Win`
(변환 후 좌표)을 읽는 방식이 우리에게 맞는다.

## 6. 규모 추정 — 명령 버퍼가 64 KiB로 되는가

삼각형 하나에 필요한 레지스터 쓰기(D3에서 실측한 것 기준):

| 묶음 | 개수 |
| --- | --- |
| 색 보간기 `DR4`~`DR15` | 9 |
| 깊이 `DR0`/`DR2`/`DR3` | 3 |
| 알파 `ALPHASTART`/`XINC`/`YINC` | 3 |
| 변 `AR0`~`AR6` + `SGN` | 8 |
| `FXBNDRY` + `YDSTLEN+EXEC` | 2 |
| **합계(상태 변화 없을 때)** | **25** |

DMA 블록은 5워드에 값 4개이므로 삼각형당 약 7블록 = 35워드 = 140바이트.
텍스처·상태가 바뀌면 늘지만, **64 KiB면 삼각형 400개 이상**이다.

**충분하다.** 한 프레임이 그보다 많으면 배치를 나눈다 — 배치당 RPC 1회이므로
비용은 선형이다.

## 7. 이 계획이 결정하지 않은 것

- 전체화면 소유를 어떻게 얻는가(M2). WindowServer를 어떻게 비키게 할지는
  별도 문제다.
- 더블 버퍼링과 vsync.
- 텍스처 업로드 경로. S4a로 유저랜드가 VRAM에 직접 쓸 수 있으므로 CPU
  복사가 가능하며, ILOAD는 필요해진 뒤에 본다.
- 인터럽트 기반 완료 통지. 지금은 폴링이고 D1에서 22~26 스핀으로 충분했다.

## 8. 정직한 규모 평가

`S5_HW3D_DMA_FEASIBILITY.md` §5는 이 작업을 "차원이 다른 규모"라고 적었다.
**그 평가는 그때 맞았고 지금은 절반이 틀렸다** — 그 목록의 1·3·5번이
D1~D3로 끝났기 때문이다. 남은 것은 6번(Mesa 드라이버)과 이 문서의 배관이다.

그래도 **M1-3(Mesa 백엔드)이 지금까지의 어느 단계보다 크다.** M1-0~2는
각각 하루 규모지만 M1-3은 그렇지 않다.

## 9. M1-0 결과 (2026-08-19) — **PASS**

```
vram 400000..700000, cmd base 40000000 bytes 65536 phys 20000; 14 cases, 0 wrong
PASS -- both windows decide as specified and repeat themselves
```

`osmgaDevMmap`이 순수 함수이므로 **아무것도 매핑하지 않고 직접 호출**해
14개 경계를 검사했다. 각 사례를 두 번 불러 반환값이 같은지도 확인했다 —
커널이 두 번 부르고 **두 번째를 검사하지 않으므로** 결정성이 안전의 전제다.

### 9-1. 배치 검산 (`scratchpad/m1_0.py`)

| 항목 | 값 | 확인 |
| --- | --- | --- |
| 가시 프레임버퍼 | 0 ~ `0x300000` | |
| VRAM 창 시작 | `0x400000` | 가시 영역 + 256행 가드를 페이지 정렬한 값과 일치 |
| VRAM 창 끝 | `0x700000` | 실증 7 MiB 경계 |
| **가시 영역이 창에 없다** | | 봉쇄의 핵심 |
| 링 물리주소 | `0x20000` (128 KiB) | 페이지 정렬(pfn 16), 컨벤셔널 메모리 안 |
| 명령 base | `0x40000000` | signed int 안(`< 2^31`), 끝도 안 |
| 두 창의 간격 | 1017 MiB | 16 MiB VRAM이어도 안 닿는다 |

### 9-2. 하드웨어가 못 흔드는 구석은 모형으로 훑었다

`cmdBytes`와 `cmdPhysical`은 공표 후 불변이라 실기에서 바꿀 수 없다.
교차분석이 지목한 구석(`cmdBytes` = 0/`PAGE±1`/비배수, `cmdPhysical`이
32비트 상한 근처·비정렬)을 **핸들러 술어를 그대로 옮긴 모형**으로 훑었다
(`scratchpad/mmap_model.py`).

- 허용된 모든 페이지가 할당 안에 온전히 들어가는가 → **탈출 0건**
- `cmdPhysical = 0`일 때 허용되는 경우 → **없음**
- 두 페이지에 걸쳐 바이트 단위로 훑어 비정렬 허용·잘못된 페이지 → **0건**

**첫 시도에서 3건이 보고됐는데 핸들러가 아니라 내 검증식이 틀린 것이었다** —
할당의 두 번째 페이지를 첫 페이지여야 한다고 단정했다. 고치니 0건이다.

### 9-3. 교차분석 지적 하나를 코드로 고쳤다

명령 분기가 먼저 시도되므로, **VRAM 창이 명령 base에 닿으면 그 오프셋을
명령 분기가 가로챈다.** 오늘은 못 닿지만(VRAM 최대 16 MiB, base 1 GiB)
**그것은 숫자의 성질이지 코드의 성질이 아니다** — 정확한 지적이다.

등록 시점에 `end > OSMGA_CMD_MMAP_BASE`면 **명령 창을 아예 제공하지 않도록**
바꿨다. 불변식이 가정에서 검사로 바뀐다. 모형으로도 확인했다:
`windowEnd`가 base를 넘는 순간에만 가로채기가 발생한다.

### 9-4. 미해결 — 언로드/재로드 수명

교차분석의 남은 지적이며 **해결하지 못했다.**

- 링을 해제하지 않으므로 드라이버를 다시 로드할 때마다 컨벤셔널 메모리
  64 KiB가 샌다.
- 더 나쁜 경우: **cdevsw 항목이 물리 메모리보다 오래 살면** 이미 열린
  매핑이 재사용된 메모리를 가리킬 수 있다.
- `addToCdevswFromDescription`으로 등록한 항목이 언로드 때 제거되는지
  **확인한 적이 없다.**

이 저장소에는 이미 kern_loader 관련 함정 기록이 있다(0바이트 번들 →
무한 루프). 즉 언로드/재로드는 이 환경에서 검증되지 않은 경로다.

**닫는 조건**: (a) 언로드 후 `/dev` 항목이 사라지는지 확인하거나,
(b) 언로드를 지원하지 않는다고 명시하고 그렇게 문서화한다.
`REMAINING_WORK.md`에 올린다.

### 9-5. 낮은 물리 메모리를 유저에게 매핑하는 것

교차분석이 `0x20000`(128 KiB)을 의심하라고 했다. 그 자체는 커널의 저역
할당자가 자기 아레나에서 준 것이라 용도에 맞다. 다만 **유저 프로세스가
DMA가 닿는 물리 64 KiB를 고정 주소로 읽고 쓰게 되는 것**은 사실이며,
그것이 문제가 되는 시나리오는 §9-4와 같다 — 매핑이 할당보다 오래 사는
경우다. **두 항목은 같은 하나로 추적한다.**

## 10. M1-1 결과 (2026-08-19) — **40개 사례 전부 통과**

`hw3d/OpenStepMGAHW3D.{h,c}`가 유저랜드·커널 공유 계약이고,
`hw3d/test-hw3d-validate.c`가 그 검사기를 시험한다.

```
struct sizes: batch 28080, state 68, tri 112
all cases behave as specified (0 failing)
```

### 10-1. 시험을 어디서 돌렸는가 — 호스트가 아니라 실기다

계획은 "호스트에서 하드웨어 없이"였다. 호스트에서 돌렸더니 **한 건이
실패했고 원인은 검사기가 아니라 시험 환경**이었다: 64비트 호스트에서
`unsigned long`이 8바이트라 `sizeof`로 계산하는 용량 검사가 다른 구조체를
쟀다. `-m32`는 이 호스트에 32비트 libc 헤더가 없어 못 쓴다.

**실기의 유저랜드에서 컴파일해 돌렸다.** 드라이버도 엔진도 건드리지 않으므로
하드웨어 위험은 여전히 0이고, **실제 32비트·실제 `cc 2.7.2.1`** 이라 호스트
근사보다 정확하다.

그 사고를 계기로 헤더에 **빌드 시점 단언**을 넣었다 — 배치 구조체가 자기
몫(28 KiB)을 넘거나 워드 크기가 4바이트가 아니면 **컴파일이 실패한다.**
공유 레이아웃이 조용히 어긋나는 것을 런타임까지 미루지 않는다.

### 10-2. 무엇을 검사하는가

| 검사 | 근거 |
| --- | --- |
| magic / version | 쓰레기 버퍼를 배치로 오인하지 않는다 |
| `triCount` ≤ 상한, 그리고 **실제 버퍼 크기와 정합** | 두 값이 어긋날 수 있다 |
| `dstorg` + (클립 행 수 × pitch) 가 색 창 안 | **도달 범위**로 검사한다. 원점만 보면 끝이 넘칠 수 있다 |
| `zorg` — **`atype`이 ZI일 때만** | 아니면 깊이는 주소지정되지 않는다 |
| `texorg` — **opcode가 TEXTURE_TRAP일 때만** | 아니면 텍스처는 인출되지 않는다 |
| `dwgctl`: opcode ∈ {TRAP, TEXTURE_TRAP}, atype ∈ {I, ZI}, **LINEAR 비트 금지** | BITBLT·ILOAD는 우리가 검사하지 않는 `AR`로 소스를 주소지정하고, LINEAR는 x·y를 평면 오프셋으로 바꿔 **클립을 그냥 지나간다** |
| 삼각형마다 `y`/`h`가 클립 안, `fxbndry`가 클립 안이고 좌 ≤ 우 | |

**도달 범위 검사가 핵심이다.** 원점만 보는 검사는 창 끝 근처의 원점을
통과시키고 그리기가 밖으로 넘친다. 커널이 클립과 pitch를 소유하므로
**최대 도달 바이트를 계산할 수 있다.**

산술은 전부 `a > 한계 - b` 꼴이다. `a + b > 한계`는 감싼다 — S4a 핸들러와
같은 규율이다.

### 10-3. 경계를 양쪽에서 쟀다

40개 중 상당수가 **마지막 허용값과 첫 거부값의 쌍**이다:

- `dstorg`가 맞는 마지막 원점 / 그보다 1바이트 뒤
- `zorg`, `texorg`도 같은 쌍
- `triCount`가 상한 / 상한 + 1
- `y`가 마지막 행에 1행 / 마지막 행에 2행
- `fxbndry`가 클립 끝까지 / 한 칸 더

**통과만 보고 거부를 안 보는 시험은 off-by-one을 전부 놓친다.** 이 프로젝트는
이미 그 실수를 했다(D3-3a-1의 판정식이 재현 밴드의 실패를 전제했다).

또 **"검사하지 않아야 할 때 검사하지 않는지"** 도 쌍으로 넣었다 — `atype`이
I인데 `zorg`가 엉터리면 통과해야 하고, 실제로 통과한다.

### 10-4. 남은 것

- `alphactrl`은 아직 검사하지 않는다. 블렌드 계수는 메모리 안전과 무관하다.
  단 `AC_amode`의 예약값 3(§D3-5 §7-5)은 동작이 미상이므로 **거부 목록에
  올릴지 정해야 한다.**
- `texctl`의 pitch 필드와 `TEXWIDTH`/`TEXHEIGHT`는 아직 안 받는다. 텍스처
  도달 범위를 `texMaxBytes` 상수로 눌러 두었으므로 지금은 안전하지만,
  실제 텍스처 크기를 받게 되면 **그 값으로 도달 범위를 계산해야 한다.**

## 11. M1-2a 결과 (2026-08-19) — **PASS**, 그리고 이것이 증명하지 **않는** 것

```
list 55 dwords (tail 50); MMIO drew 900, DMA drew 900;
differing 0 of which 0 differ below the top byte; guard 0; spins 12
dstorg aimed at the visible framebuffer -> validator says 4 (refused)
PASS -- the batch drew exactly what MMIO drew, pixel for pixel
```

검산(`scratchpad/m1_2a_pass.py`): 900 = `Σ(63-2y+1)`로 도형 면적과 일치,
11블록 = 55 dword에 `PRIMEND` 50으로 예측과 일치.

### 11-1. 세 번의 실행에서 배운 것

**실행 1 — `STATUS 0x80820024`, 타임아웃.** `SOFTRAPEN`만 clear이고
`ENDPRDMASTS`는 set. 즉 **목록은 끝까지 돌았는데 트랩이 안 터졌다.**
원인은 내 인코더가 `tail`을 `SOFTRAP` **앞**에 기록하고 패딩 블록을 안 붙인
것이다. DRM은 정확히 반대다 — `tail`을 잡고, 패딩 한 블록을 붙이고,
`PRIMEND`에 그 `tail`을 쓴다(`mga_dma.c:130-159`, "카드가 명령을 부분적으로
읽는다"는 주석과 함께). **원시 상태값을 찍어 둔 덕에 비트 하나로 끝났다.**

**실행 2 — 완료(12스핀), 양쪽 900픽셀, 그런데 900개 전부 값이 다름.**
기하는 완전히 같고 색만 달랐다. **값을 안 찍어서 진단이 불가능했다** —
D3-3a에서 이미 한 실수의 반복이다.

**실행 3 — 두 경로가 같은 레지스터 집합을 쓰게 하니 차이 0.**

### 11-2. 일반 규칙: **emit 집합에 없는 것은 상속된다**

교차분석이 결정적 근거를 댔다: **`ALPHASTART`/`ALPHAXINC`/`ALPHAYINC`는
DRM의 추적 컨텍스트 구조체에 없다**(`mga_drm.h:114-144`). 상태 emit은
추적 필드만 쓰므로(`mga_state.c:73-125`) 그 셋은 그리기 사이에 그대로
상속된다. **참조 구현의 정상 동작이지 우리 특유의 문제가 아니다.**

따라서 두 경로를 비교할 때는 **값을 맞추는 것으로 부족하고 어떤 레지스터를
쓰는지가 같아야 한다.** MMIO 경로가 빠뜨리던 일곱을 채우니 일치했다:
`ALPHASTART`/`ALPHAXINC`/`ALPHAYINC`/`ZORG`/`DR0`/`DR2`/`DR3`.

### 11-3. **실행 2의 가설은 검증되지 않았다**

가설은 "두 경로가 표시되지 않는 상위 바이트에서만 다르다"였다. 실행 3은
차이가 아예 0이므로 **그 가설을 시험하지 못했다** — 일곱을 한꺼번에 바꿔서
**어느 레지스터가 원인이었는지 분리되지 않는다.**

역추적할 방법은 없고 새 실험이 필요하다(하나씩 되돌리는 이분 탐색).

**지금 하지 않는다.** 실제 수정은 §11-2의 규칙이고 그것은 이미 근거가
확실하다. 어느 레지스터였는지는 동작에 영향이 없다.
**닫는 조건**: 알파 보간기가 32비트 목적지의 상위 바이트에 실리는지가
나중에 문제가 되면, MMIO 쪽에서 `ALPHASTART`만 되돌려 한 번 재면 된다.

### 11-4. 이 결과가 증명하지 **않는** 것 (교차분석 정리)

| # | 증명되지 않은 것 | 왜 |
| --- | --- | --- |
| 1 | **클리핑이 스트림 내부 논리로 강제된다** | 클립 경계는 MMIO로 설정하고 목록 밖에 있다. 비교 대상이 아니었다 |
| 2 | **봉쇄** | 음성 대조는 **검사기가 옳은 코드를 돌려준다**는 것만 보였다. 검사기를 우회했을 때 엔진이 창 밖에 못 쓴다는 것은 안 보였다 |
| 3 | 적대적 기하에 대한 견고성 | `AR` 값(변 기울기)은 검사기가 **경계 짓지 않는다.** 하드웨어 클립이 막는다는 것이 우리 주장인데 **적대적 변으로 시험한 적이 없다** |
| 4 | 링 재사용·wrap 부기 | 매번 영역 처음부터 다시 만들고 폴링하므로 우회했다. DRM은 `prim.tail`/`space`/`last_wrap`을 관리한다(`mga_drv.h:251-275`) |
| 5 | 깊이·텍스처·블렌딩이 이 경로로 동작 | 삼각형 하나, 색 하나, `atype I`만 시험했다 |

**3번이 가장 중요하다.** 우리 봉쇄 논거 전체가 "하드웨어 클립이 막는다"에
걸려 있는데, 검사기가 `AR`을 안 보므로 **클립이 유일한 방어선**이다.
그런데 그 방어선을 적대적 입력으로 밀어 본 적이 없다.

### 11-5. 다음 — M1-2c: 봉쇄를 실제로 민다

교차분석 제안대로, **허용된 `dstorg`를 쓰면서 적대적인 변·행 값**으로
그려 보고 창 밖 카나리아가 무변인지 본다. 검사기를 통과하는 입력으로
하드웨어 클립만을 시험하는 것이 요점이다.

- 변 기울기를 창을 크게 벗어나게 잡는다(`AR`은 검사기가 안 본다)
- `fxbndry`는 검사기 한계 안이되 변이 밖으로 걷게 한다
- 그린 행 범위 위·아래·좌·우에 카나리아를 두고 **한 워드라도 변하면 중단**

이것이 통과해야 §11-4의 2·3번이 닫힌다. **M1-2b(유저랜드 클라이언트)보다
먼저 한다** — 봉쇄가 확인되기 전에 유저랜드를 붙이는 것은 순서가 틀렸다.

## 12. M1-2c 결과 (2026-08-19) — 봉쇄를 밀어 봤다

```
drew inside the clip 1280 1280 1280 1280 1248 1248 of 1280 each
bands 4,5 start inside and walk out -- drew 1248 and 1248
  (engaged wants 1248, ignored would be 640); their first rows 32 and 32
canary 248 rows x 1024 cols; words changed outside the intended rectangle: 0
PASS -- edges that walk far outside the clip wrote nothing outside it
```

### 12-1. 첫 판은 **공허할 뻔했다**

처음엔 밴드 0~3만 있었고 넷 다 1280을 그렸다. 그런데 모형을 세워 보니
**변이 밖으로 걸어 나간 경우와 `AR`이 아예 실행되지 않은 경우가 똑같이
1280을 낸다**(`scratchpad/m1_2c.py`). 즉 그 PASS는 "클립이 막았다"와
"기계가 돌지도 않았다"를 구분하지 못한다.

밴드 4·5를 더했다 — **클립 안에서 시작해 밖으로 걸어 나가게** 한다.
동작하면 1248, 무시되면 640. **1248이 나왔다.**

**내 판정식의 한 조건도 검산이 잡았다**: "첫 행이 32px"을 증거로 넣었는데
**두 모형에서 모두 32**라 판별력이 없다. 가르는 것은 총합뿐이다. 판정식에는
위생 검사로 남기되 증거로 삼지 않는다.

### 12-2. 카나리아

248행 × 1024열 = 253,952워드를 검사했고 의도한 사각형(7,680워드)을 뺀
**246,272워드가 전부 무변**이다. **전체 행 폭을 본 것이 요점**이다 —
x 방향 탈출은 같은 행의 더 뒤에 떨어지므로 좁게 보면 놓친다.

### 12-3. 기울기 크기를 작게 잡은 이유, 그리고 그 논거의 한계

`2^17`/행이면 미클립 주소가 **음수로 가 가시 프레임버퍼에 닿는다**(계산함).
800/행이면 미클립 도달점도 카나리아 안이다. **측정과 도박의 차이다.**

논거는 "클립은 픽셀당 경계라 동작하면 크기와 무관하다"였는데, 교차분석이
정당하게 좁혔다: **중간 오버플로가 없을 때만 참이다.** 그래서 필드 폭을
확인했다(`mgareg_flags.h:87-109`):

| 레지스터 | 폭 |
| --- | --- |
| `AR0`/`AR2`/`AR4`/`AR5`/`AR6` | **18비트** |
| `AR1`/`AR3` | 24비트 |

18비트면 최대 표현 기울기가 **131,071/행**이고, 클립 높이를 곱하면 VRAM을
훨씬 넘는다. **즉 필드 폭은 안전을 보장하지 않는다.** 우리는 한 가지 크기만
시험했고, 최대치는 시험하면 가시 영역이 위험하다.

### 12-4. 그래서 **검사기가 기울기를 경계 짓게 했다**

교차분석의 원래 지적("검사기가 `AR`을 직접 경계 지어야 한다")을 받아들였다.
`OSMGAHW3DLimits.maxEdgeWalk`(픽셀)를 더하고, 삼각형마다
`max(|ar1|,|ar2|,|ar4|,|ar5|) × h ≤ maxEdgeWalk`를 확인한다. 곱셈은
`slope > limit / h` 꼴로 나눠서 넘침을 피한다.

**봉쇄가 이제 하드웨어 클립 하나에만 걸려 있지 않다.** 단위 시험 7건을
더해 47건 전부 통과한다(한계값 정확히, 한계값 + 1, 18비트 최대, h=1에서의
전 예산과 그 +1).

`OSMGA_HW3D_EDGE_WALK`는 16384로 뒀다 — 실제 삼각형이 필요로 하는 것보다
훨씬 크고(768행 변이 행당 1픽셀이면 768) 창 여백보다 훨씬 작다.
**본래 형태는 목적지 원점과 창 가장자리의 거리에서 유도하는 것**이며,
원점이 런타임에 클라이언트 선택이 되면 그렇게 바꾼다.

### 12-5. 이것이 증명하지 **않는** 것

| # | 내용 |
| --- | --- |
| 1 | `AR` 걷기가 **선형**이라는 것. 밴드 4·5는 "아예 안 돎"만 배제한다. 첫 행에서 즉시 클램프되는 모형 등은 같은 1248을 낸다 |
| 2 | y 방향 탈출 없음. 클립이 y를 막고 검사기가 `y`/`h`를 보지만 **밀어 본 적이 없다.** 카나리아 ±64행은 유계 탐침이지 증명이 아니다 |
| 3 | `SGN` 극단값, 다른 opcode, 스테이트 이월 |
| 4 | 최대 표현 기울기(131,071)에서의 동작 |

**DRM도 클라이언트 변 데이터를 검증하지 않는다**(교차분석 확인). 우리 설계가
특이한 것은 아니지만, §12-4를 넣은 지금은 **참조 구현보다 엄격하다.**

## 13. M1-2b 결과 (2026-08-19) — **유저랜드에서 종단까지 PASS**

```
submit returned 0
kernel: verdict 0 (accepted), triangle 0, list 55 dwords, 12 spins
drew 900 pixels, guard band disturbed 0
first row spans: row0=64 row5=54 row10=44 row15=34
destination aimed at the visible framebuffer -> returned -706
kernel: verdict 4 (destination origin), triangle 0, list 0 dwords, 0 spins
PASS
```

검산: 행 폭이 `64 - 2y`로 요청한 기울기와 정확히 일치하고 총합 900,
**M1-2a에서 커널이 만든 배치가 그린 것과 같은 900**이다. 즉 두 경로가
개수뿐 아니라 기하에서도 일치한다.

거부 쪽은 **목록 0 dword** — 검사가 인코딩을 막으므로 **거부된 배치는
명령으로 바뀌지도 않는다.**

### 13-1. 이제 구조가 완성됐다

클라이언트는 **레지스터를 하나도 이름 대지 않고 MMIO를 만지지 않는다.**
클립과 pitch는 커널이 정하므로 **배치가 자기가 그려질 벽을 옮길 수 없다.**

진단은 별도 읽기 파라미터로 돌려준다. `IOReturn` 하나로는 "왜 거부됐는지"를
말할 수 없어 거부된 클라이언트가 커널 로그를 뒤지게 된다.

### 13-2. **교차분석이 실제 보안 결함을 찾았다 — TOCTOU**

배치는 **유저랜드에 쓰기 가능하게 매핑된 채**이고 커널은 그것을 **두 번
읽는다** — 검사기에서, 그리고 인코더에서. 그 사이에 다른 스레드가 값을
바꾸면 **검사된 값과 카드에 가는 값이 다르다.**

`stormBusy` 플래그는 도움이 안 된다. **제출끼리를 직렬화할 뿐 쓰기와
제출을 직렬화하지 않는다.**

특히 위험한 필드: `triCount`, `dwgctl`(opcode·atype·LINEAR), 원점 셋,
`y`/`h`/`fxbndry`, `AR` 값. 전부 검사 후에 바뀌면 인코더가 검증되지 않은
값을 내보낸다.

**수정**: 제출 경로가 **먼저 커널 메모리로 복사**하고 그 복사본만 검사·
인코딩한다. `triCount`는 **정확히 한 번** 읽는다 — 복사 후 다시 읽으면
닫으려던 창을 다시 여는 것이다. 상한을 넘으면 복사 전에 거부한다.

복사 비용은 삼각형 하나면 192바이트이고 250개라도 28 KiB로, DMA 제출
하나에 비하면 무시할 수준이다.

### 13-3. 운영상 발견 — cdevsw major는 동적이다

클라이언트가 `/dev/osmgavram`을 열지 못했다. 드라이버는 **character major
1**로 등록됐는데(로그에 찍힌다) 노드는 예전 세션의 **255**였다.

**단순한 불편이 아니다**(교차분석 지적): 낡은 major가 다른 드라이버를
가리키면 open이 **엉뚱한 드라이버에 간다.** 노드를 하드코딩할 것이 아니라
**등록된 major를 확인해서 만들어야 한다.**

- **현재 조치**: 로그의 major로 노드를 다시 만든다.
- **닫는 조건**: 드라이버가 major를 조회 가능한 파라미터로 노출하고
  클라이언트(또는 설치 스크립트)가 그것으로 노드를 만든다.

### 13-4. 아직 증명되지 않은 것

| # | 내용 |
| --- | --- |
| 1 | 한 배치에 **여러 삼각형** |
| 2 | 이 경로로 **깊이**·**텍스처**·**블렌딩** |
| 3 | 배치 사이의 **상태 변경** |
| 4 | 링을 0부터 다시 만들지 않고 **재사용**(wrap 부기) |
| 5 | 동시 클라이언트. 지금은 busy 플래그로 거부만 한다 |

교차분석의 우선순위도 같은 순서이며, **1번부터** 한다.
