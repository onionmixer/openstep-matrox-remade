# M1 — Mesa 연결: 구조 결정과 첫 종단 슬라이스

기준일: 2026-08-19
상태: 계획. **codex 교차검토 1회 완료(2026-08-19)** 후 개정판 — §2-A, §4-4, §5.
선행: D3-0~5 완료. **하드웨어 기능은 전부 실증됐다.** 남은 것은 배관이다.

## 0. 이 문서의 범위

D3까지는 "이 하드웨어가 3D를 할 수 있는가"였고 답은 **예**다. 이 문서는
**"유저랜드 Mesa가 그 하드웨어에 어떻게 닿는가"** 를 정한다.

**Mesa 코드는 아직 건드리지 않는다.** M1은 Mesa보다 앞선 단계로,
**맨손 유저랜드 클라이언트가 삼각형 하나를 그리는 것**까지다. 배관이
증명되기 전에 Mesa를 손대면 실패했을 때 원인이 두 겹이 된다 — D3-3a에서
배치를 모른 채 프로브를 짜서 두 개의 측정 버그를 낸 것과 같은 실수다.

## 1. 이미 증명된 조각

| 조각 | 어디서 | 상태 |
| --- | --- | --- |
| Storm 엔진 구동(기하·색·깊이·텍스처·알파) | D3-0~5 | 실증 |
| 물리 연속 시스템 RAM 64 KiB (`IOMallocLow`) | D1 | 실증 |
| 카드가 시스템 RAM에서 명령을 버스마스터로 읽음 | D1 | 실증 |
| 폴링 완료 대기(22~26 스핀) | D1 | 실증 |
| **레지스터 화이트리스트 DMA 인코더** | D1 | 실증 |
| 유저랜드 → 커널 RPC(`get/setIntValues`) | S3a | 실증 |
| **오프스크린 VRAM을 유저 태스크에 매핑**(cdevsw `d_mmap`) | S4a | 실증 |
| Mesa 3.4.2 소프트웨어 렌더러가 실기에서 동작 | `opennstep-mesa342/` | 실증 |

**M1이 새로 만드는 것은 이 조각들을 잇는 접착제뿐이다.**

## 2. 구조 결정 — 세 안 중 하나

### 2-A. MMIO BAR를 유저랜드에 매핑 (기각)

S4a의 `d_mmap`은 `물리주소 + offset`의 페이지 프레임을 돌려주는 순수 함수다.
**같은 방식으로 BAR0(레지스터)도 매핑할 수 있다.** 그러면 Mesa가 커널을
거치지 않고 엔진을 직접 몬다. 가장 빠르다.

**기각한다.** `PRIMADDRESS`/`PRIMEND`가 노출되면 **유저 프로세스가 카드에게
임의의 물리 메모리를 읽고 쓰게 시킬 수 있다.** 커널 메모리 포함이다.
디스플레이 드라이버 하나 때문에 시스템 전체의 격리를 깨는 것은
정당화되지 않는다.

기각 근거를 남기는 이유: **이 안이 가장 매력적이라 나중에 다시 제안될
것이기 때문**이다.

**중간안은 있으나 이득이 없다.** 교차검토가 짚었듯 DRM은 MMIO를 유저랜드에
**읽기 전용**으로 매핑한다(`mga_dma.c:723`, `_DRM_REGISTERS |
_DRM_READ_ONLY`). 읽기 전용이면 상태 조회에 안전하지만 **그리기는 전혀
빨라지지 않는다.** 쓰기를 허용하는 어떤 부분집합도 결국 스트림 제어를
넘겨야 하므로 같은 위험으로 돌아온다.

### 2-B. **유저랜드는 타입이 있는 상태를 쓰고, 커널이 명령을 만든다** (채택)

**초안은 "유저랜드가 명령 목록을 만들고 커널이 그것을 검증한다"였다.
소스를 확인하고 바꿨다.** DRM은 그렇게 하지 않는다.

DRM에서 유저랜드가 공유 메모리(SAREA)에 쓰는 것은 **원시 명령 목록이 아니라
필드 이름이 붙은 구조체**다(`mga_drm.h`의 `drm_mga_context_regs_t`,
`drm_mga_texture_regs_t`, `drm_mga_server_regs_t`). 커널은 그중 위험한
필드만 검사하고 — `DSTORG`는 front/back 둘 중 하나여야 하고
(`mga_state.c:407-423`), `TEXORG`는 PCI 시스템 메모리를 가리키면 안 되며
(`:426-441`), ILOAD 목적지는 텍스처 힙 안이어야 한다(`:472-489`) —
**레지스터 쓰기는 커널이 만든다**(`:73-120`).

**이 차이가 결정적이다.**

| | 초안(원시 목록 검증) | 채택(타입 상태) |
| --- | --- | --- |
| 커널이 확인할 것 | **위험한 레지스터 전부를 빠짐없이** 열거 | 필드 몇 개의 값 범위 |
| 빠뜨렸을 때 | 유저랜드가 그 레지스터를 씀 | **그 레지스터는 애초에 쓰이지 않는다** |
| D1의 화이트리스트 | 새로 만든 검증기로 대체 | **그대로 계속 적용된다** |

원시 목록 검증은 **화이트리스트가 완전해야만** 안전하다. 타입 상태는
**커널이 어떤 레지스터가 쓰이는지 자체를 결정**하므로 열거가 필요 없다.
D3-3a에서 배웠듯 "빠뜨렸을 때 조용히 틀리는" 설계는 피한다.

```
유저랜드 Mesa                  커널 드라이버                    카드
  상태 구조체 + 삼각형 배열
        ──(공유 버퍼)────────▶ 필드 범위 검사
                              명령 목록 생성(기존 인코더)
                   ──(RPC 1회)──▶ PRIMADDRESS/PRIMEND ──▶ 버스마스터 읽기
                              ◀── 폴링 완료               ◀──
```

- 배치당 RPC **1회**. 삼각형당이 아니다.
- 유저랜드가 삼각형당 보내는 것은 **`AR`/`DR`/`FXBNDRY`/`YDSTLEN` 값**이지
  레지스터 지정이 아니다. 유저랜드가 이미 변환된 정점을 갖고 있으므로
  계산은 그쪽에서 하는 편이 맞고, 커널은 인코딩만 한다.
- **기하 값은 봉쇄를 깨지 못한다.** 클립 레지스터(`CXBNDRY`/`YTOP`/`YBOT`)와
  `PITCH`/`DSTORG`/`ZORG`를 커널이 소유하고, 하드웨어 클립이 색과 깊이를
  모두 막는다는 것을 D3-2와 D3-4b가 실측했다. 유저랜드가 이상한 변을 보내면
  이상한 그림이 나올 뿐 창 밖으로 못 나간다.

`PITCH`가 DRM에서 **X 서버 전용 구조체**(`drm_mga_server_regs_t`)에 들어
있는 것도 같은 이유다 — 3D 클라이언트가 만질 것이 아니다.

### 2-C. 커널이 모든 레지스터를 쓴다 (기각)

삼각형당 RPC가 되어 느리다. 측정하지 않았지만 `getIntValues` 왕복 비용이
DMA 배치 하나보다 클 것이 명백하다.

## 3. 프레젠테이션 — 전체화면만 성립한다

`S5_HW3D_DMA_FEASIBILITY.md` §2가 실측으로 확정한 것:

- **창 안 가속은 불가능하다.** WindowServer와의 협조 프로토콜이 없고
  (`IODisplayDoBlit`은 사문화, S3b), 우리가 가시 영역에 직접 그리면
  리페인트 때 지워진다.
- **전체화면은 정당하게 성립한다.** 우리가 화면을 소유한다.

**M1은 화면에 아무것도 올리지 않는다.** 전부 오프스크린이며, 결과는
유저랜드가 mmap으로 되읽어 확인한다. 프레젠테이션은 M2의 주제다.

## 4. 새로 만들어야 하는 것

### 4-1. 유저랜드에 매핑 가능한 명령 버퍼

D1의 링은 `IOMallocLow`로 잡은 **커널** 메모리다. 유저랜드가 여기에 명령을
쓰려면 매핑돼야 한다.

S4a의 `d_mmap`은 `osmgaMmapFbPhysical + offset`을 돌려주는데, 이는
**VRAM 물리 주소**에 고정돼 있다. 명령 버퍼는 시스템 RAM이므로 **두 번째
매핑 창**이 필요하다.

**미지수 1**: `d_mmap`의 offset 하나로 두 개의 물리 영역을 구분해 줄 수
있는가. offset 구간을 나누면 된다(예: `0` ~ `VRAM끝`은 VRAM,
`0x8000_0000` 이상은 명령 버퍼). **순수 산술이어야 한다는 S4a의 계약을
깨지 않는다** — 상수 둘이 더 늘 뿐이다.

**미지수 2**: `IOMallocLow`가 64 KiB로 제한된다(D1 §3-2). 명령 버퍼가
그 안에 들어가는가. 삼각형 하나가 대략 몇 개의 5워드 블록인지 §6에서
센다.

### 4-2. 공유 구조체와 그 필드 검사

§2-B대로 유저랜드는 레지스터를 지정하지 않는다. 공유 버퍼의 배치:

```c
struct osmgaShared {
    unsigned long magic, version;
    struct { unsigned long dstorg, zorg, texorg, alphactrl,
                           dwgctl, texctl, texctl2, texfilter,
                           tmr[9]; } state;        /* 배치당 1회 */
    unsigned long triCount;
    struct { long y, h;
             long arL[4], arR[4], sgn;             /* 변 */
             unsigned long dr[12];                 /* 색 */
             unsigned long z0, zdx, zdy;           /* 깊이 */
             unsigned long a0, adx, ady;           /* 알파 */
             unsigned long fxbndry; } tri[];       /* 삼각형당 */
};
```

**커널이 검사하는 것 — 이것이 전부다:**

| 필드 | 검사 | 왜 |
| --- | --- | --- |
| `dstorg` | 우리 오프스크린 창 안 | 아니면 가시 프레임버퍼에 쓴다 |
| `zorg` | 우리 깊이 창 안 | 같음 |
| `texorg` | 우리 텍스처 창 안 | 임의 VRAM을 읽는다 |
| `dwgctl` | opcode·atype이 허용 집합 안 | ILOAD 계열은 소스 주소지정이 달라 별도 검토가 필요하다 |
| `y`, `h` | 배치의 클립 창 안 | 이중 방어. 클립이 이미 막지만 값이 터무니없으면 엔진 시간을 낭비한다 |
| `triCount` | 버퍼 크기와 정합 | |

**`SRCORG`는 아예 노출하지 않는다.** D3-5b에서 블렌드가 `DSTORG`를 읽는
것을 확인했으므로 3D 경로에 `SRCORG`가 필요 없다. **필요 없는 것은 구조체에
넣지 않는 것이 가장 강한 검사다.**

`PITCH`/`CXBNDRY`/`YTOP`/`YBOT`/`YDSTORG`/`PLNWT`/`MACCESS`도 마찬가지로
노출하지 않는다. 커널이 배치 시작에 `osmgaStormInitState`로 정한다.

### 4-4. **인코더의 화이트리스트에 구멍이 있었다** (교차검토 소득)

D1 이래 우리는 "group0/group1 규칙상 DMA 주소 레지스터는 인코딩될 수
없다"고 적어 왔다. **`PRIMADDRESS`(0x1e58)/`PRIMEND`(0x1e5c)에 대해서만
참이다** — 그 둘은 두 그룹 밖이다.

그런데 **부차 링과 셋업 링의 주소 레지스터는 group1 안에 있다**:

| 레지스터 | 주소 | 근거 |
| --- | --- | --- |
| `SECADDRESS` | 0x2c40 | `mga_drv.h:500` |
| `SECEND` | 0x2c44 | `:501` |
| `SETUPADDRESS` | 0x2cd0 | `:502` |
| `SETUPEND` | 0x2cd4 | `:503` |

group1은 0x2c00~0x2dff이므로(`mga_drv.h:228-229`) 넷 다 규칙에 걸린다.
확인해 보니 우리 `osmgaDmaIndex`가 **넷을 전부 받아들이고 있었다.**

**오늘 노출은 없다.** 커널이 유일한 호출자이고 그 넷을 지목한 적이 없다.
그래도 고쳤다 — 인코더는 "호출자가 실수해도 막히는 층"이어야지 "호출자가
착하기를 기대하는 층"이면 안 된다. 넷을 명시적으로 거부한다.

**추적**: 이 변경은 D1 경로가 config에서 꺼져 있는 동안 만들어졌으므로
**실기에서 DMA 경로를 다시 켤 때 함께 회귀 확인한다**
(`REMAINING_WORK.md` §3-7).

### 4-3. 인코딩은 커널에만 있다

초안은 유저랜드와 커널이 인코더를 공유하게 했는데, §2-B로 바꾸면서
**유저랜드는 인코딩을 알 필요가 없어졌다.** 공유하는 것은 위 구조체 정의
하나뿐이다. 코드 중복도 줄고 공격면도 줄었다.

## 5. 단계

### M1-0 — 두 개의 매핑 창 (§4-1)

`d_mmap`에 두 번째 창을 더하고, 유저랜드에서 명령 버퍼를 매핑해 **CPU가
쓴 값을 커널이 읽어 확인**한다.

**검증 방법**
- **V1-0-1**: 유저랜드가 패턴을 쓰고 커널이 되읽어 일치. 물리 연속성은
  D1이 이미 확인했다.
- **V1-0-2 (경계)**: **S4a의 계약상 거부는 매핑 실패로 나타나야 하며,
  잘못된 PFN을 돌려주면 임의의 물리 메모리가 유저 프로세스에 노출된다.**
  교차검토가 제시한 목록을 그대로 쓴다:
  `0`, `창0끝-1`, `창0끝`, `창1시작-1`, `창1시작`, `창1끝-1`, `창1끝`,
  그리고 **같은 페이지를 반복 호출**(커널이 두 번 부르고 두 번째 반환값을
  검사하지 않으므로 결정성이 필수다), 페이지 정렬·비정렬 요청.
- **V1-0-2b (오버플로)**: 경계 산술을 `base > 최대 - off` 꼴로 쓴다.
  `base + off`는 감싼다. S4a 핸들러가 이미 그렇게 돼 있으니 새 코드도
  같은 규율을 따른다.
- **V1-0-3**: VRAM 창이 여전히 동작(회귀).

### M1-1 — 필드 검사 단위 시험 (하드웨어 없이)

검사 코드를 **커널에 넣기 전에** 같은 코드를 호스트에서 돌린다. 입력은
- 정상 상태(통과해야 함)
- `dstorg`가 가시 프레임버퍼를 가리킴
- `zorg`가 창 밖
- `texorg`가 창 밖
- `dwgctl`이 ILOAD opcode
- `triCount`가 버퍼를 넘음
- 각 경계의 **바로 안쪽과 바로 바깥쪽**(off-by-one)

**검증 방법**: 각 입력이 예상대로 통과/거부되는가. **하드웨어 위험이 0이므로
실기 이전에 끝낸다.** 경계의 양쪽을 모두 넣는 것은 D3에서 "통과만 보고
거부를 안 본" 실수를 되풀이하지 않기 위해서다.

### M1-2 — 유저랜드가 만든 삼각형 하나

유저랜드 클라이언트가 D3-2의 기울어진 사다리꼴 하나를 명령 목록으로 만들어
제출하고, mmap으로 결과를 되읽는다.

**검증 방법**
- **V1-2-1**: 커널이 직접 같은 도형을 그린 D3-2 결과와 **픽셀 단위로 일치**
  하는가. 대조군이 이미 있다는 것이 이 설계의 장점이다.
- **V1-2-2**: 가드·화면 무변화.
- **V1-2-3 (음성 대조)**: 일부러 `dstorg`를 가시 영역으로 지목한 상태를
  제출해 **거부되는지** 확인한다. 거부되지 않으면 §4-2가 실패한 것이며
  **즉시 중단**한다. 그리고 **거부된 뒤 화면이 무변인지** 함께 본다 —
  검사가 통과시켰는데 그리기가 우연히 무해했던 경우와 구분된다.

### M1-3 — Mesa `dd_function_table` 백엔드 (별도 문서)

여기부터가 Mesa다. M1-2가 통과한 뒤에 착수하며 범위가 커서 별도 계획서로
다룬다. 참고 구조는 Mesa 3.4.2 내장 FX 드라이버이며, 그것이 `VB->Win`
(변환 후 좌표)을 읽는 방식이 우리에게 맞는다.

## 6. 규모 추정 — 명령 버퍼가 64 KiB로 되는가

삼각형 하나에 필요한 레지스터 쓰기(D3에서 실측한 것 기준):

| 묶음 | 개수 |
| --- | --- |
| 색 보간기 `DR4`~`DR15` | 9 |
| 깊이 `DR0`/`DR2`/`DR3` | 3 |
| 알파 `ALPHASTART`/`XINC`/`YINC` | 3 |
| 변 `AR0`~`AR6` + `SGN` | 8 |
| `FXBNDRY` + `YDSTLEN+EXEC` | 2 |
| **합계(상태 변화 없을 때)** | **25** |

DMA 블록은 5워드에 값 4개이므로 삼각형당 약 7블록 = 35워드 = 140바이트.
텍스처·상태가 바뀌면 늘지만, **64 KiB면 삼각형 400개 이상**이다.

**충분하다.** 한 프레임이 그보다 많으면 배치를 나눈다 — 배치당 RPC 1회이므로
비용은 선형이다.

## 7. 이 계획이 결정하지 않은 것

- 전체화면 소유를 어떻게 얻는가(M2). WindowServer를 어떻게 비키게 할지는
  별도 문제다.
- 더블 버퍼링과 vsync.
- 텍스처 업로드 경로. S4a로 유저랜드가 VRAM에 직접 쓸 수 있으므로 CPU
  복사가 가능하며, ILOAD는 필요해진 뒤에 본다.
- 인터럽트 기반 완료 통지. 지금은 폴링이고 D1에서 22~26 스핀으로 충분했다.

## 8. 정직한 규모 평가

`S5_HW3D_DMA_FEASIBILITY.md` §5는 이 작업을 "차원이 다른 규모"라고 적었다.
**그 평가는 그때 맞았고 지금은 절반이 틀렸다** — 그 목록의 1·3·5번이
D1~D3로 끝났기 때문이다. 남은 것은 6번(Mesa 드라이버)과 이 문서의 배관이다.

그래도 **M1-3(Mesa 백엔드)이 지금까지의 어느 단계보다 크다.** M1-0~2는
각각 하루 규모지만 M1-3은 그렇지 않다.

## 9. M1-0 결과 (2026-08-19) — **PASS**

```
vram 400000..700000, cmd base 40000000 bytes 65536 phys 20000; 14 cases, 0 wrong
PASS -- both windows decide as specified and repeat themselves
```

`osmgaDevMmap`이 순수 함수이므로 **아무것도 매핑하지 않고 직접 호출**해
14개 경계를 검사했다. 각 사례를 두 번 불러 반환값이 같은지도 확인했다 —
커널이 두 번 부르고 **두 번째를 검사하지 않으므로** 결정성이 안전의 전제다.

### 9-1. 배치 검산 (`scratchpad/m1_0.py`)

| 항목 | 값 | 확인 |
| --- | --- | --- |
| 가시 프레임버퍼 | 0 ~ `0x300000` | |
| VRAM 창 시작 | `0x400000` | 가시 영역 + 256행 가드를 페이지 정렬한 값과 일치 |
| VRAM 창 끝 | `0x700000` | 실증 7 MiB 경계 |
| **가시 영역이 창에 없다** | | 봉쇄의 핵심 |
| 링 물리주소 | `0x20000` (128 KiB) | 페이지 정렬(pfn 16), 컨벤셔널 메모리 안 |
| 명령 base | `0x40000000` | signed int 안(`< 2^31`), 끝도 안 |
| 두 창의 간격 | 1017 MiB | 16 MiB VRAM이어도 안 닿는다 |

### 9-2. 하드웨어가 못 흔드는 구석은 모형으로 훑었다

`cmdBytes`와 `cmdPhysical`은 공표 후 불변이라 실기에서 바꿀 수 없다.
교차분석이 지목한 구석(`cmdBytes` = 0/`PAGE±1`/비배수, `cmdPhysical`이
32비트 상한 근처·비정렬)을 **핸들러 술어를 그대로 옮긴 모형**으로 훑었다
(`scratchpad/mmap_model.py`).

- 허용된 모든 페이지가 할당 안에 온전히 들어가는가 → **탈출 0건**
- `cmdPhysical = 0`일 때 허용되는 경우 → **없음**
- 두 페이지에 걸쳐 바이트 단위로 훑어 비정렬 허용·잘못된 페이지 → **0건**

**첫 시도에서 3건이 보고됐는데 핸들러가 아니라 내 검증식이 틀린 것이었다** —
할당의 두 번째 페이지를 첫 페이지여야 한다고 단정했다. 고치니 0건이다.

### 9-3. 교차분석 지적 하나를 코드로 고쳤다

명령 분기가 먼저 시도되므로, **VRAM 창이 명령 base에 닿으면 그 오프셋을
명령 분기가 가로챈다.** 오늘은 못 닿지만(VRAM 최대 16 MiB, base 1 GiB)
**그것은 숫자의 성질이지 코드의 성질이 아니다** — 정확한 지적이다.

등록 시점에 `end > OSMGA_CMD_MMAP_BASE`면 **명령 창을 아예 제공하지 않도록**
바꿨다. 불변식이 가정에서 검사로 바뀐다. 모형으로도 확인했다:
`windowEnd`가 base를 넘는 순간에만 가로채기가 발생한다.

### 9-4. 미해결 — 언로드/재로드 수명

교차분석의 남은 지적이며 **해결하지 못했다.**

- 링을 해제하지 않으므로 드라이버를 다시 로드할 때마다 컨벤셔널 메모리
  64 KiB가 샌다.
- 더 나쁜 경우: **cdevsw 항목이 물리 메모리보다 오래 살면** 이미 열린
  매핑이 재사용된 메모리를 가리킬 수 있다.
- `addToCdevswFromDescription`으로 등록한 항목이 언로드 때 제거되는지
  **확인한 적이 없다.**

이 저장소에는 이미 kern_loader 관련 함정 기록이 있다(0바이트 번들 →
무한 루프). 즉 언로드/재로드는 이 환경에서 검증되지 않은 경로다.

**닫는 조건**: (a) 언로드 후 `/dev` 항목이 사라지는지 확인하거나,
(b) 언로드를 지원하지 않는다고 명시하고 그렇게 문서화한다.
`REMAINING_WORK.md`에 올린다.

### 9-5. 낮은 물리 메모리를 유저에게 매핑하는 것

교차분석이 `0x20000`(128 KiB)을 의심하라고 했다. 그 자체는 커널의 저역
할당자가 자기 아레나에서 준 것이라 용도에 맞다. 다만 **유저 프로세스가
DMA가 닿는 물리 64 KiB를 고정 주소로 읽고 쓰게 되는 것**은 사실이며,
그것이 문제가 되는 시나리오는 §9-4와 같다 — 매핑이 할당보다 오래 사는
경우다. **두 항목은 같은 하나로 추적한다.**

## 10. M1-1 결과 (2026-08-19) — **40개 사례 전부 통과**

`hw3d/OpenStepMGAHW3D.{h,c}`가 유저랜드·커널 공유 계약이고,
`hw3d/test-hw3d-validate.c`가 그 검사기를 시험한다.

```
struct sizes: batch 28080, state 68, tri 112
all cases behave as specified (0 failing)
```

### 10-1. 시험을 어디서 돌렸는가 — 호스트가 아니라 실기다

계획은 "호스트에서 하드웨어 없이"였다. 호스트에서 돌렸더니 **한 건이
실패했고 원인은 검사기가 아니라 시험 환경**이었다: 64비트 호스트에서
`unsigned long`이 8바이트라 `sizeof`로 계산하는 용량 검사가 다른 구조체를
쟀다. `-m32`는 이 호스트에 32비트 libc 헤더가 없어 못 쓴다.

**실기의 유저랜드에서 컴파일해 돌렸다.** 드라이버도 엔진도 건드리지 않으므로
하드웨어 위험은 여전히 0이고, **실제 32비트·실제 `cc 2.7.2.1`** 이라 호스트
근사보다 정확하다.

그 사고를 계기로 헤더에 **빌드 시점 단언**을 넣었다 — 배치 구조체가 자기
몫(28 KiB)을 넘거나 워드 크기가 4바이트가 아니면 **컴파일이 실패한다.**
공유 레이아웃이 조용히 어긋나는 것을 런타임까지 미루지 않는다.

### 10-2. 무엇을 검사하는가

| 검사 | 근거 |
| --- | --- |
| magic / version | 쓰레기 버퍼를 배치로 오인하지 않는다 |
| `triCount` ≤ 상한, 그리고 **실제 버퍼 크기와 정합** | 두 값이 어긋날 수 있다 |
| `dstorg` + (클립 행 수 × pitch) 가 색 창 안 | **도달 범위**로 검사한다. 원점만 보면 끝이 넘칠 수 있다 |
| `zorg` — **`atype`이 ZI일 때만** | 아니면 깊이는 주소지정되지 않는다 |
| `texorg` — **opcode가 TEXTURE_TRAP일 때만** | 아니면 텍스처는 인출되지 않는다 |
| `dwgctl`: opcode ∈ {TRAP, TEXTURE_TRAP}, atype ∈ {I, ZI}, **LINEAR 비트 금지** | BITBLT·ILOAD는 우리가 검사하지 않는 `AR`로 소스를 주소지정하고, LINEAR는 x·y를 평면 오프셋으로 바꿔 **클립을 그냥 지나간다** |
| 삼각형마다 `y`/`h`가 클립 안, `fxbndry`가 클립 안이고 좌 ≤ 우 | |

**도달 범위 검사가 핵심이다.** 원점만 보는 검사는 창 끝 근처의 원점을
통과시키고 그리기가 밖으로 넘친다. 커널이 클립과 pitch를 소유하므로
**최대 도달 바이트를 계산할 수 있다.**

산술은 전부 `a > 한계 - b` 꼴이다. `a + b > 한계`는 감싼다 — S4a 핸들러와
같은 규율이다.

### 10-3. 경계를 양쪽에서 쟀다

40개 중 상당수가 **마지막 허용값과 첫 거부값의 쌍**이다:

- `dstorg`가 맞는 마지막 원점 / 그보다 1바이트 뒤
- `zorg`, `texorg`도 같은 쌍
- `triCount`가 상한 / 상한 + 1
- `y`가 마지막 행에 1행 / 마지막 행에 2행
- `fxbndry`가 클립 끝까지 / 한 칸 더

**통과만 보고 거부를 안 보는 시험은 off-by-one을 전부 놓친다.** 이 프로젝트는
이미 그 실수를 했다(D3-3a-1의 판정식이 재현 밴드의 실패를 전제했다).

또 **"검사하지 않아야 할 때 검사하지 않는지"** 도 쌍으로 넣었다 — `atype`이
I인데 `zorg`가 엉터리면 통과해야 하고, 실제로 통과한다.

### 10-4. 남은 것

- `alphactrl`은 아직 검사하지 않는다. 블렌드 계수는 메모리 안전과 무관하다.
  단 `AC_amode`의 예약값 3(§D3-5 §7-5)은 동작이 미상이므로 **거부 목록에
  올릴지 정해야 한다.**
- `texctl`의 pitch 필드와 `TEXWIDTH`/`TEXHEIGHT`는 아직 안 받는다. 텍스처
  도달 범위를 `texMaxBytes` 상수로 눌러 두었으므로 지금은 안전하지만,
  실제 텍스처 크기를 받게 되면 **그 값으로 도달 범위를 계산해야 한다.**

## 11. M1-2a 결과 (2026-08-19) — **PASS**, 그리고 이것이 증명하지 **않는** 것

```
list 55 dwords (tail 50); MMIO drew 900, DMA drew 900;
differing 0 of which 0 differ below the top byte; guard 0; spins 12
dstorg aimed at the visible framebuffer -> validator says 4 (refused)
PASS -- the batch drew exactly what MMIO drew, pixel for pixel
```

검산(`scratchpad/m1_2a_pass.py`): 900 = `Σ(63-2y+1)`로 도형 면적과 일치,
11블록 = 55 dword에 `PRIMEND` 50으로 예측과 일치.

### 11-1. 세 번의 실행에서 배운 것

**실행 1 — `STATUS 0x80820024`, 타임아웃.** `SOFTRAPEN`만 clear이고
`ENDPRDMASTS`는 set. 즉 **목록은 끝까지 돌았는데 트랩이 안 터졌다.**
원인은 내 인코더가 `tail`을 `SOFTRAP` **앞**에 기록하고 패딩 블록을 안 붙인
것이다. DRM은 정확히 반대다 — `tail`을 잡고, 패딩 한 블록을 붙이고,
`PRIMEND`에 그 `tail`을 쓴다(`mga_dma.c:130-159`, "카드가 명령을 부분적으로
읽는다"는 주석과 함께). **원시 상태값을 찍어 둔 덕에 비트 하나로 끝났다.**

**실행 2 — 완료(12스핀), 양쪽 900픽셀, 그런데 900개 전부 값이 다름.**
기하는 완전히 같고 색만 달랐다. **값을 안 찍어서 진단이 불가능했다** —
D3-3a에서 이미 한 실수의 반복이다.

**실행 3 — 두 경로가 같은 레지스터 집합을 쓰게 하니 차이 0.**

### 11-2. 일반 규칙: **emit 집합에 없는 것은 상속된다**

교차분석이 결정적 근거를 댔다: **`ALPHASTART`/`ALPHAXINC`/`ALPHAYINC`는
DRM의 추적 컨텍스트 구조체에 없다**(`mga_drm.h:114-144`). 상태 emit은
추적 필드만 쓰므로(`mga_state.c:73-125`) 그 셋은 그리기 사이에 그대로
상속된다. **참조 구현의 정상 동작이지 우리 특유의 문제가 아니다.**

따라서 두 경로를 비교할 때는 **값을 맞추는 것으로 부족하고 어떤 레지스터를
쓰는지가 같아야 한다.** MMIO 경로가 빠뜨리던 일곱을 채우니 일치했다:
`ALPHASTART`/`ALPHAXINC`/`ALPHAYINC`/`ZORG`/`DR0`/`DR2`/`DR3`.

### 11-3. **실행 2의 가설은 검증되지 않았다**

가설은 "두 경로가 표시되지 않는 상위 바이트에서만 다르다"였다. 실행 3은
차이가 아예 0이므로 **그 가설을 시험하지 못했다** — 일곱을 한꺼번에 바꿔서
**어느 레지스터가 원인이었는지 분리되지 않는다.**

역추적할 방법은 없고 새 실험이 필요하다(하나씩 되돌리는 이분 탐색).

**지금 하지 않는다.** 실제 수정은 §11-2의 규칙이고 그것은 이미 근거가
확실하다. 어느 레지스터였는지는 동작에 영향이 없다.
**닫는 조건**: 알파 보간기가 32비트 목적지의 상위 바이트에 실리는지가
나중에 문제가 되면, MMIO 쪽에서 `ALPHASTART`만 되돌려 한 번 재면 된다.

### 11-4. 이 결과가 증명하지 **않는** 것 (교차분석 정리)

| # | 증명되지 않은 것 | 왜 |
| --- | --- | --- |
| 1 | **클리핑이 스트림 내부 논리로 강제된다** | 클립 경계는 MMIO로 설정하고 목록 밖에 있다. 비교 대상이 아니었다 |
| 2 | **봉쇄** | 음성 대조는 **검사기가 옳은 코드를 돌려준다**는 것만 보였다. 검사기를 우회했을 때 엔진이 창 밖에 못 쓴다는 것은 안 보였다 |
| 3 | 적대적 기하에 대한 견고성 | `AR` 값(변 기울기)은 검사기가 **경계 짓지 않는다.** 하드웨어 클립이 막는다는 것이 우리 주장인데 **적대적 변으로 시험한 적이 없다** |
| 4 | 링 재사용·wrap 부기 | 매번 영역 처음부터 다시 만들고 폴링하므로 우회했다. DRM은 `prim.tail`/`space`/`last_wrap`을 관리한다(`mga_drv.h:251-275`) |
| 5 | 깊이·텍스처·블렌딩이 이 경로로 동작 | 삼각형 하나, 색 하나, `atype I`만 시험했다 |

**3번이 가장 중요하다.** 우리 봉쇄 논거 전체가 "하드웨어 클립이 막는다"에
걸려 있는데, 검사기가 `AR`을 안 보므로 **클립이 유일한 방어선**이다.
그런데 그 방어선을 적대적 입력으로 밀어 본 적이 없다.

### 11-5. 다음 — M1-2c: 봉쇄를 실제로 민다

교차분석 제안대로, **허용된 `dstorg`를 쓰면서 적대적인 변·행 값**으로
그려 보고 창 밖 카나리아가 무변인지 본다. 검사기를 통과하는 입력으로
하드웨어 클립만을 시험하는 것이 요점이다.

- 변 기울기를 창을 크게 벗어나게 잡는다(`AR`은 검사기가 안 본다)
- `fxbndry`는 검사기 한계 안이되 변이 밖으로 걷게 한다
- 그린 행 범위 위·아래·좌·우에 카나리아를 두고 **한 워드라도 변하면 중단**

이것이 통과해야 §11-4의 2·3번이 닫힌다. **M1-2b(유저랜드 클라이언트)보다
먼저 한다** — 봉쇄가 확인되기 전에 유저랜드를 붙이는 것은 순서가 틀렸다.

## 12. M1-2c 결과 (2026-08-19) — 봉쇄를 밀어 봤다

```
drew inside the clip 1280 1280 1280 1280 1248 1248 of 1280 each
bands 4,5 start inside and walk out -- drew 1248 and 1248
  (engaged wants 1248, ignored would be 640); their first rows 32 and 32
canary 248 rows x 1024 cols; words changed outside the intended rectangle: 0
PASS -- edges that walk far outside the clip wrote nothing outside it
```

### 12-1. 첫 판은 **공허할 뻔했다**

처음엔 밴드 0~3만 있었고 넷 다 1280을 그렸다. 그런데 모형을 세워 보니
**변이 밖으로 걸어 나간 경우와 `AR`이 아예 실행되지 않은 경우가 똑같이
1280을 낸다**(`scratchpad/m1_2c.py`). 즉 그 PASS는 "클립이 막았다"와
"기계가 돌지도 않았다"를 구분하지 못한다.

밴드 4·5를 더했다 — **클립 안에서 시작해 밖으로 걸어 나가게** 한다.
동작하면 1248, 무시되면 640. **1248이 나왔다.**

**내 판정식의 한 조건도 검산이 잡았다**: "첫 행이 32px"을 증거로 넣었는데
**두 모형에서 모두 32**라 판별력이 없다. 가르는 것은 총합뿐이다. 판정식에는
위생 검사로 남기되 증거로 삼지 않는다.

### 12-2. 카나리아

248행 × 1024열 = 253,952워드를 검사했고 의도한 사각형(7,680워드)을 뺀
**246,272워드가 전부 무변**이다. **전체 행 폭을 본 것이 요점**이다 —
x 방향 탈출은 같은 행의 더 뒤에 떨어지므로 좁게 보면 놓친다.

### 12-3. 기울기 크기를 작게 잡은 이유, 그리고 그 논거의 한계

`2^17`/행이면 미클립 주소가 **음수로 가 가시 프레임버퍼에 닿는다**(계산함).
800/행이면 미클립 도달점도 카나리아 안이다. **측정과 도박의 차이다.**

논거는 "클립은 픽셀당 경계라 동작하면 크기와 무관하다"였는데, 교차분석이
정당하게 좁혔다: **중간 오버플로가 없을 때만 참이다.** 그래서 필드 폭을
확인했다(`mgareg_flags.h:87-109`):

| 레지스터 | 폭 |
| --- | --- |
| `AR0`/`AR2`/`AR4`/`AR5`/`AR6` | **18비트** |
| `AR1`/`AR3` | 24비트 |

18비트면 최대 표현 기울기가 **131,071/행**이고, 클립 높이를 곱하면 VRAM을
훨씬 넘는다. **즉 필드 폭은 안전을 보장하지 않는다.** 우리는 한 가지 크기만
시험했고, 최대치는 시험하면 가시 영역이 위험하다.

### 12-4. 그래서 **검사기가 기울기를 경계 짓게 했다**

교차분석의 원래 지적("검사기가 `AR`을 직접 경계 지어야 한다")을 받아들였다.
`OSMGAHW3DLimits.maxEdgeWalk`(픽셀)를 더하고, 삼각형마다
`max(|ar1|,|ar2|,|ar4|,|ar5|) × h ≤ maxEdgeWalk`를 확인한다. 곱셈은
`slope > limit / h` 꼴로 나눠서 넘침을 피한다.

**봉쇄가 이제 하드웨어 클립 하나에만 걸려 있지 않다.** 단위 시험 7건을
더해 47건 전부 통과한다(한계값 정확히, 한계값 + 1, 18비트 최대, h=1에서의
전 예산과 그 +1).

`OSMGA_HW3D_EDGE_WALK`는 16384로 뒀다 — 실제 삼각형이 필요로 하는 것보다
훨씬 크고(768행 변이 행당 1픽셀이면 768) 창 여백보다 훨씬 작다.
**본래 형태는 목적지 원점과 창 가장자리의 거리에서 유도하는 것**이며,
원점이 런타임에 클라이언트 선택이 되면 그렇게 바꾼다.

### 12-5. 이것이 증명하지 **않는** 것

| # | 내용 |
| --- | --- |
| 1 | `AR` 걷기가 **선형**이라는 것. 밴드 4·5는 "아예 안 돎"만 배제한다. 첫 행에서 즉시 클램프되는 모형 등은 같은 1248을 낸다 |
| 2 | y 방향 탈출 없음. 클립이 y를 막고 검사기가 `y`/`h`를 보지만 **밀어 본 적이 없다.** 카나리아 ±64행은 유계 탐침이지 증명이 아니다 |
| 3 | `SGN` 극단값, 다른 opcode, 스테이트 이월 |
| 4 | 최대 표현 기울기(131,071)에서의 동작 |

**DRM도 클라이언트 변 데이터를 검증하지 않는다**(교차분석 확인). 우리 설계가
특이한 것은 아니지만, §12-4를 넣은 지금은 **참조 구현보다 엄격하다.**

## 13. M1-2b 결과 (2026-08-19) — **유저랜드에서 종단까지 PASS**

```
submit returned 0
kernel: verdict 0 (accepted), triangle 0, list 55 dwords, 12 spins
drew 900 pixels, guard band disturbed 0
first row spans: row0=64 row5=54 row10=44 row15=34
destination aimed at the visible framebuffer -> returned -706
kernel: verdict 4 (destination origin), triangle 0, list 0 dwords, 0 spins
PASS
```

검산: 행 폭이 `64 - 2y`로 요청한 기울기와 정확히 일치하고 총합 900,
**M1-2a에서 커널이 만든 배치가 그린 것과 같은 900**이다. 즉 두 경로가
개수뿐 아니라 기하에서도 일치한다.

거부 쪽은 **목록 0 dword** — 검사가 인코딩을 막으므로 **거부된 배치는
명령으로 바뀌지도 않는다.**

### 13-1. 이제 구조가 완성됐다

클라이언트는 **레지스터를 하나도 이름 대지 않고 MMIO를 만지지 않는다.**
클립과 pitch는 커널이 정하므로 **배치가 자기가 그려질 벽을 옮길 수 없다.**

진단은 별도 읽기 파라미터로 돌려준다. `IOReturn` 하나로는 "왜 거부됐는지"를
말할 수 없어 거부된 클라이언트가 커널 로그를 뒤지게 된다.

### 13-2. **교차분석이 실제 보안 결함을 찾았다 — TOCTOU**

배치는 **유저랜드에 쓰기 가능하게 매핑된 채**이고 커널은 그것을 **두 번
읽는다** — 검사기에서, 그리고 인코더에서. 그 사이에 다른 스레드가 값을
바꾸면 **검사된 값과 카드에 가는 값이 다르다.**

`stormBusy` 플래그는 도움이 안 된다. **제출끼리를 직렬화할 뿐 쓰기와
제출을 직렬화하지 않는다.**

특히 위험한 필드: `triCount`, `dwgctl`(opcode·atype·LINEAR), 원점 셋,
`y`/`h`/`fxbndry`, `AR` 값. 전부 검사 후에 바뀌면 인코더가 검증되지 않은
값을 내보낸다.

**수정**: 제출 경로가 **먼저 커널 메모리로 복사**하고 그 복사본만 검사·
인코딩한다. `triCount`는 **정확히 한 번** 읽는다 — 복사 후 다시 읽으면
닫으려던 창을 다시 여는 것이다. 상한을 넘으면 복사 전에 거부한다.

복사 비용은 삼각형 하나면 192바이트이고 250개라도 28 KiB로, DMA 제출
하나에 비하면 무시할 수준이다.

### 13-3. 운영상 발견 — cdevsw major는 동적이다

클라이언트가 `/dev/osmgavram`을 열지 못했다. 드라이버는 **character major
1**로 등록됐는데(로그에 찍힌다) 노드는 예전 세션의 **255**였다.

**단순한 불편이 아니다**(교차분석 지적): 낡은 major가 다른 드라이버를
가리키면 open이 **엉뚱한 드라이버에 간다.** 노드를 하드코딩할 것이 아니라
**등록된 major를 확인해서 만들어야 한다.**

- **현재 조치**: 로그의 major로 노드를 다시 만든다.
- **닫는 조건**: 드라이버가 major를 조회 가능한 파라미터로 노출하고
  클라이언트(또는 설치 스크립트)가 그것으로 노드를 만든다.

### 13-4. 아직 증명되지 않은 것

| # | 내용 |
| --- | --- |
| 1 | 한 배치에 **여러 삼각형** |
| 2 | 이 경로로 **깊이**·**텍스처**·**블렌딩** |
| 3 | 배치 사이의 **상태 변경** |
| 4 | 링을 0부터 다시 만들지 않고 **재사용**(wrap 부기) |
| 5 | 동시 클라이언트. 지금은 busy 플래그로 거부만 한다 |

교차분석의 우선순위도 같은 순서이며, **1번부터** 한다.

## 14. M1-2d 결과 (2026-08-19) — **한 배치에 삼각형 셋, 각자 제 모양**

```
verdict 0 (accepted), triangle 0, list 125 dwords, 25 spins
triangle 0: wanted 900 pixels, got 900
triangle 1: wanted 1280 pixels, got 1280
triangle 2: wanted 900 pixels, got 900
triangle 0 row 10 spans x=20..63
triangle 1 row 10 spans x=0..63
triangle 2 row 10 spans x=0..43
guard band disturbed 0
triangle 1 put past the clip -> verdict 8 (triangle rows), triangle 1
destination aimed at the visible framebuffer -> verdict 4
```

목록 크기도 예측과 일치한다: `1 + 3×7 + 1 + 1 + 1 = 25`블록 × 5 = **125**.

### 14-1. 총합으로 세지 않았다

**밴드마다 자기 예측과 따로 비교했다.** 셋이 개별로는 틀렸는데 합만 맞는
경우가 정확히 총합이 숨기는 것이다.

그리고 **삼각형 0과 2는 면적이 같은 거울상**이다 — 행 10에서 둘 다 44px
폭이다. 개수로는 **뒤바뀌어도 통과한다.** 그래서 스팬 범위를 함께 쟀다:

| 삼각형 | 행 10 스팬 | 어느 변이 움직였나 |
| --- | --- | --- |
| 0 | `x=20..63` | 왼쪽 변이 오른쪽으로 |
| 1 | `x=0..63` | 없음 |
| 2 | `x=0..43` | **오른쪽 변이 왼쪽으로** |

### 14-2. 거부가 **문제 삼각형을 지목한다**

가운데 삼각형(인덱스 1)을 클립 밖으로 밀었더니 판정이
`verdict 8 (triangle rows), triangle 1`이다. 삼각형별 루프가 실패 지점을
정확히 보고한다. 목록은 **0 dword** — 검사가 인코딩을 막는다.

### 14-3. 스냅샷 경로 검증 — **닫혔다**

첫 실행은 §13-2의 TOCTOU 수정이 들어가기 **전** 드라이버였다(부팅 09:22,
설치 09:27). 재부팅 후 같은 클라이언트를 다시 돌린 결과가 **동일하다**:

```
verdict 0 (accepted), triangle 0, list 125 dwords, 24 spins
triangle 0/1/2: 900 / 1280 / 900, 스팬 x=20..63 / 0..63 / 0..43
guard 0; 두 거부 모두 같은 판정
```

스핀만 25→24로 다르고(폴링 횟수라 실행마다 변동) 나머지는 전부 같다.
**삼각형이 하나보다 많은 배치가 스냅샷 코드의 첫 시험이었고 통과했다.**

복사 길이의 경계도 검산했다(`scratchpad/`):

| `triCount` | 복사 바이트 | dword | 비고 |
| --- | --- | --- | --- |
| 0 | 80 | 20 | 고정부만 |
| 3 | 416 | 104 | 이번 실행 |
| 250 (상한) | **28080** | 7020 | **구조체 끝에 정확히 맞는다** |

상한에서 복사량이 구조체 크기와 **정확히** 일치하고 넘지 않는다. 251은
복사 **전에** 거부되므로 루프가 보지 않는다. 세 크기 모두 4로 나누어져
dword 복사가 정확하다.

### 14-4. 부수 — 클라이언트의 첫 판은 메모리 폴트였다

밴드가 둘에서 넷으로 늘었는데 **VRAM 매핑 크기를 안 늘렸다.** 4.2BSD mmap은
`vm_allocate`한 자리에 덮어 매핑하므로, 매핑 밖을 쓰면 조용히 어긋나는
대신 **폴트가 난다** — 이 경우엔 그것이 유용했다.

## 15. M1-2e — 깊이를 이 경로로 (계획)

기준일: 2026-08-19
상태: 계획. **codex 교차검토 1회 완료(2026-08-19)** 후 개정판 — §15-3, §15-4, §15-7.

### 15-1. 배관은 이미 있고, 한 번도 안 지나갔다

깊이를 위한 조각이 전부 자리에 있지만 **어느 것도 실행된 적이 없다**:

| 조각 | 어디 | 실행됨? |
| --- | --- | --- |
| `state.zorg`, `tri.z0/zdx/zdy` | 공유 구조체 | 아니오 |
| `ZORG`·`DR0`/`DR2`/`DR3` emit | 인코더 | 값은 0으로만 |
| `atype == ZI`일 때만 `zorg` 도달범위 검사 | 검사기 | 단위시험만 |

D3-3c가 **MMIO로** 깊이 판정을 실증했고, 이제 **배치 경로로** 같은 것을
확인한다. D3-4b가 기울어진 변에서도 깊이 쓰기가 클립을 지킨다는 것을 이미
보였으므로, 남은 질문은 **전송 수단**뿐이다 — M1-2a와 같은 구도다.

### 15-2. 깊이 클리어는 클라이언트가 CPU로 한다

배치에는 "채우기" 같은 것이 없고, 넣을 생각도 없다 — `atype RPL`을 허용하면
검사기가 막고 있는 opcode 집합이 넓어진다.

대신 **클라이언트가 VRAM 창을 통해 직접 쓴다.** 깊이 영역(5 MiB)은 등록된
창(4~7 MiB) 안이므로 mmap이 허용한다. 배치가 만질 수 없는 것을 클라이언트가
자기 매핑으로 만지는 것이고, 그 매핑은 이미 검증된 봉쇄 안이다.

**배치는 D3-3의 실측 배치를 써야 한다** — 깊이는 **16비트 원소**이고 행
간격은 `PITCH`(원소 1024개 = 2048바이트)다. 색 버퍼 기하로 클리어하면
D3-3a의 버그를 클라이언트에서 되풀이한다.

### 15-3. 밴드 구성 — 판별력 있게

D3-3c에서 배운 것: **같은 깊이값에 판정 방향만 뒤집는 밴드**가 있어야
"비교가 걸렸다"와 "다른 이유로 안 그려졌다"가 갈린다.

깊이는 전부 `0x8000`(중간값)으로 클리어한다.

| 밴드 | `zmode` | 깊이 | `DR0` = 깊이<<15 | 기대 |
| --- | --- | --- | --- | --- |
| 0 | `NOZCMP` | **`0x7000`** | `0x38000000` | **그려짐**, 그리고 **깊이가 `0x7000`으로 바뀜** |
| 1 | `ZLT` | `0x4000` (가까움) | `0x20000000` | 그려짐, 깊이 `0x4000` |
| 2 | `ZLT` | `0xC000` (멈) | `0x60000000` | **거부**, 깊이 `0x8000` 그대로 |
| 3 | `ZGTE` | `0xC000` (같은 값) | `0x60000000` | **그려짐** ← 판별기 |

**밴드 0의 값을 `0x8000`에서 `0x7000`으로 바꿨다 — 교차검토 지적이다.**
초안은 클리어값과 같은 `0x8000`을 썼는데, 그러면 깊이 되읽기로
**"그리고 깊이도 썼다"와 "그렸지만 깊이는 안 썼다"가 구분되지 않는다.**
값을 다르게 하면 되읽기가 **쓰기가 일어났음을 증명**한다.

`DR0 = 깊이 << 15`는 D3-3b 실측값이다. `0xC000 << 15 = 0x60000000`으로
32비트를 넘지 않으며(교차검토가 재확인) `DR0` 비트 15~30이 깊이 비트
0~15로 가는 선형 구간 안이다.

### 15-4. 검증 방법

- **V2e-0 (대조군 먼저)**: 밴드 0이 그려져야 한다. 아니면 `atype ZI`가 이
  경로로 그리지 못하는 것이고 **나머지를 읽지 않는다.**
- **V2e-1 (주 판정)**: 밴드 1 그려짐, 밴드 2 **안 그려짐**, 밴드 3 그려짐.
  2와 3이 **같은 깊이값**이라는 것이 요점이다.
- **V2e-2 (깊이 되읽기)**: 클라이언트가 깊이 버퍼를 16비트 기하로 되읽어
  **밴드마다 기대값과 비교**한다 — 0은 `0x7000`, 1은 `0x4000`, 2는
  `0x8000`(불변), 3은 `0xC000`. 밴드 0이 `0x7000`이어야 한다는 것이
  **깊이 쓰기가 실제로 일어났다는 증거**이고, 밴드 2가 `0x8000`이어야
  한다는 것이 **거부가 색과 깊이를 함께 막는다는 증거**다.
- **V2e-2b (클리어가 실제로 내려갔는지)**: 클라이언트가 클리어를 쓴 뒤
  **제출 전에 한 원소를 되읽어** 확인한다. 유저 매핑의 캐시 속성이
  확인된 바 없고(§15-7), 클리어가 안 내려간 상태로 비교하면 결과 전체가
  무의미해진다.
- **V2e-3 (검사기 양방향)**:
  - `zorg`를 창 밖으로 → **거부, 판정 5(`E_ZORG`)**
  - `atype`을 `I`로 되돌리고 `zorg`는 그대로 엉터리 → **통과해야 한다**
    (깊이가 주소지정되지 않으므로). **과잉 검사를 하지 않는다는 확인**이며,
    통과만 보는 시험이 놓치는 쪽이다.
- **V2e-4 (봉쇄)**: 색 가드, 그리고 **깊이 창 밖 카나리아**. 깊이 영역
  5~6 MiB 중 우리가 쓰는 행 범위 위아래에 카나리아를 둔다.
- **V2e-5**: 화면 무변화.

### 15-4b. 교차검토가 남긴 모형 하나

`DR0`의 **스케일이 틀렸어도** 이 네 값에서는 같은 통과/거부 판정이 나올
수 있다는 지적이다. 맞다 — 다만 **V2e-2의 깊이 되읽기가 그것을 잡는다**:
스케일이 틀리면 되읽은 값이 `0x7000`/`0x4000`/`0xC000`이 아니다.
**판정만 보면 놓치고, 값을 보면 걸린다.**

### 15-5. 검사하지 않는 것과 그 이유

`zmode`(`DWGCTL` 비트 8-10)는 **검사하지 않는다.** 어떤 값이든 통과/거부만
결정하고 **주소를 바꾸지 않는다.** 검사할 것이 없는 필드를 검사 목록에 넣으면
목록의 의미가 흐려진다.

`ALPHACTRL`도 여전히 검사하지 않는다. 단 §D3-5 §7-5에서 확인한
`AC_amode` 예약값 3은 동작이 미상이므로 **거부 목록에 올릴지 정해야 한다** —
이번 단계의 결정 사항이다.

### 15-6. 중단 조건

- 밴드 0이 안 그려짐 → 중단.
- 깊이 카나리아 오염 → **즉시 중단.** D3-4b가 축 정렬·기울어진 변 모두에서
  깊이가 클립을 지키는 것을 봤으므로, 여기서 새는 것은 전송 경로 문제다.
- 색 가드 오염, 화면 이상.

### 15-7. 알아두는 위험 두 개 (교차검토)

**(1) CPU 클리어와 엔진 읽기 사이의 일관성.** 클라이언트가 유저 매핑으로
깊이를 클리어하고 곧 엔진이 그것을 읽는다. 그 매핑의 캐시 속성은
**소스로 확인되지 않는다**(교차검토도 "cannot verify"). S4a가 stale-cache
시험을 했다는 기록이 있으나 이 경로에 대한 것은 아니다.
→ **V2e-2b**가 최소한 클리어가 내려갔음을 확인한다. 그래도 어긋나면
클리어를 엔진 쪽으로 옮기는 설계 변경이 필요하다.

**(2) 클라이언트는 창(4~7 MiB) 안 어디든 쓸 수 있다.** 검사기 밖이다.
이것은 **결함이 아니라 의도된 신뢰 부여**다 — 검사기는 *엔진*을
클라이언트로부터 지키고, mmap 창은 *나머지 시스템*을 지킨다. 창이
4 MiB에서 시작하므로 **가시 프레임버퍼(0~3 MiB)와 시스템 메모리에는
닿지 못한다.**

한계는 정확히 하나다: **클라이언트 둘이 서로의 버퍼를 망칠 수 있다.**
이미 §13-4의 미검증 항목(동시 클라이언트)에 속하며, 그 항목이
"창을 클라이언트별로 나눠야 한다"까지 포함하도록 범위를 넓힌다.

## 16. M1-2e 결과 (2026-08-19) — **깊이가 배치 경로로 동작한다**

```
depth cleared to 8000, guard c0de, both read back
band                       drew     want depth!=want
NOZCMP z=7000              1280     1280        0
ZLT near z=4000            1280     1280        0
ZLT far  z=C000               0        0        0
ZGTE far z=C000            1280     1280        0
guard: colour 0, depth 0
zorg at the visible framebuffer, atype ZI -> verdict 5 (depth origin)
the same bad zorg with atype I  -> verdict 0 (accepted)
```

**깊이 되읽기가 밴드마다 요청한 값과 정확히 일치한다**(`depth!=want`가 전부 0):
`0x7000` / `0x4000` / `0x8000`(불변) / `0xC000`. 이것이 §15-4b가 노린 것이다 —
`DR0` 스케일이 틀렸으면 통과/거부 패턴은 같아도 **값이 다르다.**

### 16-1. 확정된 것과 그 범위

| # | 사실 | 범위의 한계 |
| --- | --- | --- |
| 1 | 배치 경로로 깊이 비교·갱신·거부가 동작 | **이 명령 스트림 하나**에 대해서다. 다른 기하·클립·퇴화 케이스는 안 봤다 |
| 2 | 써진 깊이가 **요청한 값 그대로** → 이 경로의 `DR0` 스케일이 맞다 | 중간값 셋에서다. 부호 경계·정밀도 경계는 안 봤다 |
| 3 | 거부는 색과 깊이 쓰기를 **함께** 막는다 | 밴드 하나에서다 |
| 4 | 검사기는 깊이가 **주소지정될 때만** `zorg`를 본다 | 음성 대조 하나에서다 |

교차분석이 넷 다 "표본 경로 주장"임을 정확히 지적했고, 위 표가 그것이다.

### 16-2. **CPU 클리어를 엔진이 봤는가 — 두 번째 실행으로 닫혔다**

§15-7 (1)의 위험이다. 클리어를 되읽어 확인했지만 그것은 **CPU가 자기 쓰기를
본다**는 것뿐이고, 엔진이 봤다는 증명이 아니다(교차분석 지적).

첫 실행만으로는 stale 깊이 `S`를 좁힐 수 있을 뿐이다:
밴드 1이 그려지려면 `0x4000 < S`, 밴드 2가 거부되려면 `0xC000 ≥ S`
→ `S ∈ (0x4000, 0xC000]`. `0x8000`은 **가능하지만 확정되지 않는다.**

**같은 클라이언트를 한 번 더 돌렸다.** 두 번째 실행에서는 클리어 전에 각
밴드의 깊이 행이 **첫 실행 결과**를 담고 있다 — 밴드 1의 영역은 `0x4000`이다.

| 밴드 1(`ZLT`, 깊이 `0x4000`) | 판정 | 결과 |
| --- | --- | --- |
| 엔진이 클리어를 봤다 | `0x4000 < 0x8000` = 참 | **그려짐** |
| 엔진이 stale을 봤다 | `0x4000 < 0x4000` = 거짓 | 안 그려짐 |

**두 번째 실행에서 밴드 1이 1280을 그렸다.** → 엔진은 CPU의 클리어를 읽었다.
`S`가 정확히 `0x4000`이었을 자리라 이번엔 확정된다. **추가 부팅 없이
닫혔다.**

### 16-3. 교차분석이 드러낸 방어적 약점 하나를 고쳤다

인코더는 `atype`이 ZI가 아닐 때 **`ZORG = 0`** 을 썼다. 검사기가 그때
`zorg`를 안 보는 것은 옳다 — 주소지정되지 않으므로. 그런데 **`0`은 가시
프레임버퍼다.** 즉 "주소지정되지 않는다"는 하드웨어에 대한 주장이 틀렸을
때 **가장 나쁜 곳**을 겨냥해 두고 있었다.

깊이 창 시작(`OSMGA_D3_ZORG`)을 쓰도록 바꿨다. 비용이 없고, **주장이
틀려도 결과가 우리 깊이 영역에 떨어진다.** 교차분석 3번의 "stale ZORG"
우려도 같이 무해해진다.

### 16-4. 미해결로 남는 것

| # | 내용 |
| --- | --- |
| 1 | **`state.dwgctl`이 배치 단위다.** Mesa는 프리미티브마다 깊이 모드를 바꾼다 → 삼각형 구조체로 옮겨야 하고, 그러면 검사기가 **삼각형마다** opcode·atype·LINEAR를 확인해야 한다 |
| 2 | 한 배치에 **여러 zmode**를 섞는 경우. 이번엔 네 번 제출로 우회했다 |
| 3 | 깊이 값의 경계(0, 0xFFFF, 부호 경계) |
| 4 | 텍스처를 이 경로로 |
| 5 | 링 재사용·wrap, 동시 클라이언트 |

**1번이 다음 설계 결정**이다. 네 번 제출은 연속 제출을 검증한 부수 효과가
있었지만, Mesa에는 배치당 상태 하나로는 부족하다.

## 17. M1-2f — 삼각형마다 상태 (계획)

기준일: 2026-08-19
상태: 계획. **codex 교차검토 1회 완료(2026-08-19)** 후 개정판 — §17-3이 통째로 바뀌었다.

### 17-1. 왜 필요한가

`state.dwgctl`이 **배치 단위**다. M1-2e는 깊이 모드가 네 가지 필요해서
**네 번 제출**했다. 연속 제출을 검증한 부수 효과는 있었지만, Mesa는
프리미티브마다 깊이 모드·블렌드·텍스처 on/off를 바꾸므로 **배치당 상태
하나로는 성립하지 않는다.**

DRM도 컨텍스트 상태가 dispatch당 하나이지만, 그쪽은 상태가 바뀔 때마다
새 dispatch를 낸다(`mga_state.c:653-697`의 dirty 프로토콜). 우리는 배치당
RPC가 한 번이므로 **같은 방식이면 상태 변경마다 RPC가 늘어난다** —
그것이 이 설계의 유일한 비용 축이다.

### 17-2. 무엇을 옮기는가 — **최소만**

전부 옮기지 않는다. **프리미티브마다 바뀌는 것만** 옮기고 나머지는 배치에
남긴다. 옮길 것이 적을수록 삼각형당 바이트와 검사 비용이 작다.

| 필드 | 어디로 | 이유 |
| --- | --- | --- |
| `dwgctl` | **삼각형** | opcode(텍스처 on/off) · atype(깊이 on/off) · zmode |
| `alphactrl` | **삼각형** | Mesa가 `glBlendFunc`/`glDepthFunc`를 프리미티브 사이에 바꾼다 |
| `dstorg`/`zorg`/`texorg` | 배치 유지 | 프레임 안에서 버퍼가 바뀌지 않는다 |
| `texctl`/`texctl2`/`texfilter`/`tmr[9]` | 배치 유지 | **텍스처 바인딩이 바뀌면 새 배치**로 한다. 삼각형마다 13워드를 더 나르는 것보다 싸다 |

`tmr`을 배치에 남기는 것은 **결정이지 누락이 아니다.** 같은 텍스처로 여러
삼각형을 그리는 것이 흔한 경우이고, 텍스처를 바꾸는 경우는 배치 경계로
표현한다.

### 17-3. 검사가 아니라 **마스크** — 교차검토가 초안을 바꿨다

초안은 삼각형마다 opcode·atype·LINEAR **셋을 검사**하려 했다. 교차검토가
정확히 짚었다: `dwgctl`을 통째로 클라이언트가 쓰게 되면 그 셋 말고도
**BOP·투명도·BLTMOD·SOLID·SHIFTZERO·ARZERO·SGNZERO**까지 손에 들어간다.
주소를 바꾸지는 않지만, **내가 근거를 세운 적 없는 비트를 신뢰하게 된다.**

**검사 대신 마스크로 바꾼다.** 클라이언트가 쓸 수 있는 비트만 통과시키고
나머지는 커널의 고정값에서 온다:

```c
dwgctl = OSMGA_HW3D_DWG_FIXED | (t->dwgctl & OSMGA_HW3D_DWG_CLIENT)
```

| 필드 | 비트 | 누가 정하나 |
| --- | --- | --- |
| opcode | 0-3 | **클라이언트** (`TRAP`/`TEXTURE_TRAP`만 유효값 검사) |
| atype | 4-6 | **클라이언트** (`I`/`ZI`만) |
| LINEAR | 7 | **커널** — 마스크에 없으므로 표현 불가 |
| zmode | 8-10 | **클라이언트** (전 값 허용, 주소를 안 바꿈) |
| SOLID | 11 | 커널 |
| ARZERO / SGNZERO | 12-13 | 커널 (인코더가 sloped 형태로 지운다) |
| SHIFTZERO | 14 | 커널 |
| BOP / 투명도 | 16-19 등 | 커널 |

→ `OSMGA_HW3D_DWG_CLIENT = 0x0000077F` (비트 0-6, 8-10).
**비트 7이 마스크에 없다** — LINEAR 금지가 검사에서 **구조적 불가능**으로
바뀐다. 빠뜨릴 수 있는 검사가 하나 줄어든다.

`alphactrl`도 같이 마스크한다. 주소를 바꾸는 비트는 없다(교차검토 확인).
필드 지도를 헤더에서 직접 뽑아 **미정의 인코딩까지 전수 확인**했다
(`mgareg_flags.h`의 `AC_*_MASK`는 **반전 저장**이므로 뒤집어 계산):

| 필드 | 비트 | 정의된 값 | **거부할 값** |
| --- | --- | --- | --- |
| `AC_src` | 0-3 | 0~8 | **9~15** |
| `AC_dst` | 4-7 | 0~7 | **8~15** |
| `AC_amode` | 8-9 | 0~2 + `3 = RSVD` | **3** |
| `AC_astipple` | 11 | 0,1 | — |
| `AC_aten` | 12 | 0,1 | — |
| `AC_atmode` | 13-15 | 0, 2~7 | **1** (매크로 자체가 없다) |
| `AC_atref` | 16-23 | 수치 | — |
| `AC_alphasel` | 24-25 | 0~3 | — |

이름 있는 필드의 합집합은 `0x03FFFBFF`이고 **비트 10과 26~31은 이름이
없다** → 마스크에서 뺀다.

즉 `alphactrl` 규칙은 "마스크 + 네 필드의 미정의 인코딩 거부"다.
`amode = 3`만 막을 생각이었는데 **`atmode = 1`과 `src`/`dst`의 상위
인코딩도 미정의**였다 — 헤더를 계산으로 훑지 않았으면 놓쳤다.

**여전히 삼각형마다 확인해야 하는 것**: opcode와 atype의 *값*(마스크는
자리만 제한하고 값은 아니다), 그리고 원점 조건 —

- `atype == ZI`인 삼각형이 **하나라도** 있으면 `zorg` 도달범위 검사
- `opcode == TEXTURE_TRAP`인 삼각형이 **하나라도** 있으면 `texorg` 검사

이것을 "**전부** ZI일 때만"으로 잘못 쓰면 **ZI 삼각형 하나가 검사되지 않은
`zorg`로 그려진다.** 조합을 전수 확인했다(`scratchpad/`):

| opcode | atype | 필요한 원점 |
| --- | --- | --- |
| `TRAP` | `I` | `dstorg` |
| `TRAP` | `ZI` | `dstorg`, `zorg` |
| `TEXTURE_TRAP` | `I` | `dstorg`, `texorg` |
| `TEXTURE_TRAP` | `ZI` | 셋 다 |

두 any-규칙이 독립으로 발동하므로 **동시 경우가 세 번째 규칙 없이 덮인다.**
opcode·atype이 각각 두 값으로 제한되므로 다른 조합은 없다.

### 17-4. 인코더가 바뀌는 것

지금 상태 블록에서 `ZORG`/`ALPHACTRL`을 한 번 emit한다. 옮기면:

- `ZORG`/`TEXORG` 등 원점은 여전히 **배치 시작에 한 번** — 안 바뀌므로
- `DWGCTL`은 이미 삼각형마다 emit한다(sloped 변형). 값만 삼각형에서 온다
- `ALPHACTRL`을 **삼각형마다** emit해야 한다 → 삼각형당 블록이 하나 늘 수
  있다. §17-6에서 센다

### 17-5. 검증 방법

- **V2f-1 (혼합 zmode 한 배치)**: M1-2e의 네 밴드를 **한 배치**로 낸다.
  결과가 네 번 제출과 **동일**해야 한다. 대조군이 이미 측정돼 있다.

  **이 시험이 판별력이 있는지 먼저 확인했다**(`scratchpad/`). 올바른 결과는
  `Y Y N Y`이고, 인코더가 `dwgctl`을 잘못 재사용하는 세 가지 방식은 전부
  다른 패턴을 낸다:

  | 인코더가 쓰는 값 | 패턴 | 결과 |
  | --- | --- | --- |
  | 삼각형마다 자기 것 (정상) | `Y Y N Y` | — |
  | 마지막 것(`ZGTE`)을 전부 | `N N Y Y` | 걸림 |
  | 첫 것(`NOZCMP`)을 전부 | `Y Y Y Y` | 걸림 |
  | 밴드 1의 것(`ZLT`)을 전부 | `Y Y N N` | 걸림 |
- **V2f-2 (혼합 atype)**: 같은 배치에 `I` 삼각형과 `ZI` 삼각형을 섞고,
  `I` 밴드는 깊이를 **건드리지 않아야** 한다(깊이 되읽기로 확인).
- **V2f-3 (혼합 opcode)**: 같은 배치에 텍스처 삼각형과 비텍스처 삼각형.
- **V2f-4 (검사기 — 하나라도 걸리면 거부)**: 삼각형 셋 중 **하나만** ZI이고
  `zorg`가 창 밖 → **거부, 판정 5**. 그리고 그 하나를 `I`로 바꾸면
  **수락**. §17-3의 실수를 정면으로 잡는다. `texorg`도 같은 쌍으로 한다.
- **V2f-4b (마스크가 실제로 마스크하는지)**: 클라이언트가 `dwgctl`에
  LINEAR·`SOLID`·`ARZERO`를 켜서 보낸다. 마스크가 동작하면 **결과가 그
  비트가 없는 경우와 같아야** 한다 — 거부가 아니라 **무시**다.
  그리고 `alphactrl`의 미정의 인코딩 넷 — `amode=3`, `atmode=1`,
  `src=9`, `dst=8` — 이 각각 **거부**돼야 하고, 바로 아래 유효값
  (`amode=2`, `atmode=0`, `src=8`, `dst=7`)은 **통과**해야 한다.
- **V2f-5 (블렌드 전환)**: 한 배치에서 불투명 삼각형과 반투명 삼각형.
  반투명 쪽 결과가 D3-5b의 `(a*src+(255-a)*dst)/255`와 일치하는가.
- **V2f-6**: 가드·화면 무변화. 목록 크기를 예측과 대조.

### 17-6. 크기 영향

삼각형 구조체가 `dwgctl`+`alphactrl` 2워드 늘어 **30워드(120바이트)**가
된다. 레지스터는 삼각형당 `ALPHACTRL` 하나가 늘어 **29개 → 8블록(40워드)**.

28 KiB/36 KiB 분할에서 다시 계산해야 하며, 상한이 250에서 줄어들 것이다.
**구현 전에 python으로 재계산하고, 헤더의 빌드 시점 단언이 그것을 강제한다.**

### 17-7. 하지 않는 것

- `tmr`을 삼각형으로 옮기지 않는다(§17-2).
- `zmode`를 검사하지 않는다 — 주소를 바꾸지 않는다(§15-5, 교차검토 확인).
- 배치 안에서 `dstorg`를 바꾸는 것을 허용하지 않는다. 허용하면 도달범위
  검사가 삼각형마다 필요해지고, 이득이 없다.

## 18. M1-2f 결과 (2026-08-20) — **삼각형마다 상태, 마스크로**

```
one batch of 4 triangles accepted
band                       drew     want depth!=want
NOZCMP z=7000              1280     1280        0
ZLT near z=4000            1280     1280        0
ZLT far  z=C000               0        0        0
ZGTE far z=C000            1280     1280        0
guard: colour 0, depth 0
zorg 가시 프레임버퍼 + atype ZI -> verdict 5 / 같은 zorg + atype I -> verdict 0
```

**네 밴드가 한 배치로 네 번 제출과 정확히 같은 결과를 냈다.** 그리고
3삼각형 클라이언트도 회귀로 그대로 통과한다(900/1280/900, 스팬 동일,
목록 125 dword).

### 18-1. 판별력을 먼저 확인했다

인코더가 어느 한 삼각형의 `dwgctl`을 전부에 재사용하면:

| 재사용하는 값 | 결과 | |
| --- | --- | --- |
| 정상(각자 것) | `1280 1280 0 1280` | — |
| 마지막(`ZGTE`) | `0 0 1280 1280` | 걸림 |
| 첫째(`NOZCMP`) | `1280 1280 1280 1280` | 걸림 |
| 밴드 1(`ZLT`) | `1280 1280 0 0` | 걸림 |

세 가지 모두 다른 패턴이므로 이 시험은 공허하지 않다.

### 18-2. 마스크가 **거부가 아니라 무시**한다

밴드 0의 `dwgctl`에 `LINEAR|SOLID|ARZERO`(`0x1880`)를 일부러 실어 보냈다.
마스크 `0x077F`와 겹치는 비트가 없으므로 **전부 지워지고**, 밴드 0은
1280을 정상으로 그렸다. **검사였다면 거부됐을 것이고, 마스크라서 무시된다** —
클라이언트가 모르고 켠 비트가 배치 전체를 실패시키지 않는다.

### 18-3. 마스크가 실증된 명령어를 그대로 재현하는가 — 검산

`FIXED | (client & 0x077F)`가 우리가 실증한 워드와 같은지 확인했다:

| | Gouraud | 텍스처 |
| --- | --- | --- |
| 실증된 워드 | `0x000C7074` | `0x000C7076` |
| `FIXED\|mask` | `0x000C4074` | `0x000C4076` |
| 차이 | `0x3000` = `ARZERO`+`SGNZERO` | 같음 |
| **sloped 형태 적용 후** | **동일** | **동일** |

**마스크가 표현할 수 없는 것은 `ARZERO`/`SGNZERO`뿐인데, 인코더가 어차피
둘 다 지운다** — 모든 프리미티브가 사다리꼴 형태로 나가기 때문이다.
사각형은 기울기 0인 사다리꼴로 표현되며, 그것이 D3-2의 실측이고 M1-2e가
1280 밴드로 그린 방식이다.

### 18-4. 단위시험 55종

47 → 55로 늘었다. 새로 넣은 것:

- 마스크 밖 비트(`LINEAR`/`SOLID`/`ARZERO`/`SGNZERO`)가 **거부가 아니라 통과**
- `zmode` 전 값 허용
- `alphactrl` 미정의 인코딩 넷과 **바로 아래 유효값**의 쌍
- 원점의 **ANY 규칙**: 가운데만 ZI / 마지막만 ZI / 하나도 아님, 텍스처도 동일

**실패한 3건은 전부 시험 코드 버그였다** — `reset()`이 `dwgctl`을 삼각형
0에만 넣어 복사본이 opcode 0이 됐고, `texorg` 기본값이 이미 유효했다.
검사기 쪽 결함은 없었다.

### 18-5. 규모

| | 이전 | 지금 |
| --- | --- | --- |
| 삼각형 구조체 | 28워드 / 112 B | **30워드 / 120 B** |
| 삼각형당 블록 | 7 | **7** (`ALPHACTRL`이 기존 패딩 자리에 들어감) |
| 상한 | 250 | **200** |

28 KiB / 36 KiB 분할에서 입력 238개·인코딩 262개가 들어가므로 200은 여유가
있다. 헤더의 빌드 시점 단언이 이를 강제한다.

### 18-6. 교차검토를 당분간 쓸 수 없다

`GPT-5.3-Codex-Spark`가 **사용 한도에 걸렸다(2026-08-26까지)**. §18-3의
검산은 codex에 보내려던 질문을 **직접 계산한 것**이다.

그동안은 **계산으로 대체 가능한 검토는 python으로**, 소스 대조는 직접
한다. 대체할 수 없는 것은 "설계에 구멍이 있는가" 류의 판단이며, 그것은
**한도가 풀린 뒤로 미루고 미해결로 표시한다** — 검토 없이 통과시킨 것을
통과했다고 적지 않는다.

## 19. M1-2g — 텍스처를 배치 경로로 (계획)

기준일: 2026-08-20
상태: 계획. **codex 교차검토 1회 완료(2026-08-20, `gpt-5.6-terra`)** 후 개정판 — §19-2·§19-3이 바뀌었다.

### 19-1. 지금 상태 — 구조체에는 있고 인코더에는 없다

`state`에 `texorg`/`texctl`/`texctl2`/`texfilter`/`tmr[9]`가 있고 검사기가
`texorg`를 확인한다. 그런데 **인코더가 그중 어느 것도 emit하지 않는다.**
`opcode = TEXTURE_TRAP`인 배치를 내면 검사는 통과하고 **텍스처 상태는
이전에 남은 값으로 그려진다.**

이건 §11-2에서 배운 것의 재발이다 — **emit 집합에 없는 것은 상속된다.**
지금은 아무도 텍스처 배치를 안 보내서 드러나지 않았을 뿐이다.

**따라서 M1-2g는 기능 추가가 아니라 구멍 메우기이기도 하다.**

### 19-2. 구조체에 빠진 것

`TEXWIDTH`/`TEXHEIGHT`가 없다. 둘 다 필요하고, 인코딩은 D3-4에서 확인했다:

```
TEXWIDTH = (w-1)<<18 | ((8 - log2w) & 63)<<9 | log2w
```

**클라이언트가 `w`와 `log2w`를 따로 보내게 하지 않는다** — 서로 모순되는
값을 보낼 수 있고, 그러면 하드웨어가 무엇을 하는지 우리가 모른다.
**폭과 높이를 그대로 받고 커널이 인코딩한다.**

**교차검토가 초안의 제약 하나를 뒤집었다: 2의 거듭제곱이 아니어도 된다.**
`GetPowerOfTwo()`(`mga_storm.c:267-280`)와 `MGA_LOG2()`(`mga_exa.c:280-292`)가
**올림(ceiling)** 을 돌려주고, 정확한 크기는 별도로 `(w-1)<<18`에 들어간다
(`mga_exa.c:430-431`). log2 필드는 "이 크기를 담는 2의 거듭제곱"이고 실제
크기는 따로 전달된다. **거듭제곱을 요구했으면 정당한 텍스처를 거부했을
것이다.**

상한도 고쳤다. 초안은 256이라 했는데 소스가 명시하는 값은 **2048**이다
(`mga_storm.c:300-304`, 세 경로가 같은 검사를 반복한다). 인코딩을 크기별로
계산해 보면 `(8-log2)&63`이 log2 > 8에서 63,62,61로 감싸는데, 그것이
이 필드의 정의이므로 커널도 같은 식으로 계산한다.

### 19-3. 검사기 — `texMaxBytes` 상수를 실제 크기로 바꾼다

지금은 `texorg`가 `[texStart, texEnd - texMaxBytes]` 안인지만 본다
(M1-1 §10-4에 남긴 항목). 폭·높이를 받게 되면 **실제 도달 범위**로 바꾼다:

```
texBytes = texH * texPitch * 4      (32bpp)
```

**초안은 `texPitch`를 커널이 `texW`로 강제하려 했다. 교차검토가 그 대가를
보여줬다** — EXA는 픽스맵의 실제 stride를 그대로 쓰고(`mga_exa.c:400-403`),
Storm은 스크래치 텍스처를 **16의 배수로 올림**해 그 stride로 저장하고 같은
값을 `TEXCTL`에 넣는다(`mga_storm.c:308-309`, `:533-540`). **pitch ≠ width는
정상 구성**이고, 강제하면 패딩된 배치를 못 쓴다.

강제할 이유도 없었다. 걱정한 것은 "도달 범위가 클라이언트 말에 의존한다"
였는데, **커널이 그 같은 값을 `TEXCTL`에 쓰므로 검사와 하드웨어가 같은 수를
쓴다.** pitch를 크게 부르면 검사도 그만큼 크게 잡아 거부한다. 안전은
"값을 못 정하게 하는 것"이 아니라 **"검사와 하드웨어가 같은 값을 쓰는
것"** 이다.

검사 목록:

| 항목 | 규칙 | 근거 |
| --- | --- | --- |
| `texW`, `texH` | `1 ≤ n ≤ 2048`. **거듭제곱일 필요 없다** | `mga_storm.c:300-304` |
| `texPitch` | `texW ≤ pitch ≤ 2047` (`TEXCTL` 필드 11비트) | `mga_exa.c:406` |
| `texorg` | `[texStart, texEnd - texH*texPitch*4]` | 도달 범위 |
| `texctl` 포맷 필드 | 허용 목록(우선 `TW32`) | |
| `texctl`의 `CLAMPUV`·`NOPERSPECTIVE` | **커널이 채운다** | §19-5 |
| `tmr[9]` | 검사하지 않음 | §19-5 |

`TEXCTL`의 pitch 필드는 **바이트가 아니라 텍셀 단위**이며 텍스처 자신의 행
stride다(`mga_exa.c:123-126`이 바이트 pitch를 bpp로 나눠 넘긴다). 필드는
비트 9-19로 정의돼 있으나 출하 코드는 `pitch & 0x7FF`만 쓴다 — 우리도
그렇게 한다.

### 19-4. 인코더가 emit할 것

상태 블록에 **텍스처 상태 전체**를 넣는다. `TEXTRANS`/`TEXTRANSHIGH`도
DRM처럼 `0x0000ffff`로 쓴다(D3-4 §1-5). `TDUALSTAGE0/1 = 0`.

레지스터 수: `TEXORG`, `TEXWIDTH`, `TEXHEIGHT`, `TEXCTL`, `TEXCTL2`,
`TEXFILTER`, `TEXTRANS`, `TEXTRANSHIGH`, `TDUALSTAGE0`, `TDUALSTAGE1`,
`TMR0`~`TMR8` = **19개** → 5블록. 기존 상태 1블록과 합쳐 6블록.
목록 크기 예측을 그에 맞춰 고치고 python으로 재검산한다.

**텍스처를 안 쓰는 배치에서는 emit하지 않는다** — 삼각형 중 하나도
`TEXTURE_TRAP`이 아니면 19개를 보낼 이유가 없다. `anyTex`는 검사기에
이미 있다.

### 19-5. `tmr`을 검사하지 않는 근거

D3-4c가 실측했다: **`CLAMPUV`가 좌표뿐 아니라 인출 주소를 텍스처 할당
안으로 묶는다.** 8배 확대로 미클램프 인출이 40 KiB 밖까지 갔어야 하는
설정에서 카나리아가 한 워드도 변하지 않았다.

그러므로 `tmr`이 아무 값이어도 **읽기는 텍스처 안에 머문다.** 쓰기는
목적지뿐이고 그것은 클립이 막는다.

**단, `CLAMPUV`가 커널이 정하는 비트여야 이 논거가 성립한다** — §19-3에서
마스크에 넣은 이유다. 클라이언트가 `CLAMPUV`를 끌 수 있으면 이 근거가
무너진다.

### 19-6. 검증 방법

- **V2g-0 (대조군)**: 텍스처 없는 배치가 여전히 통과(회귀).
- **V2g-1 (주 판정)**: 클라이언트가 D3-4a와 같은 좌표 인코딩 텍스처를
  올리고 항등 매핑으로 그린다. **픽셀 `(x,y)`가 텍셀 `(x,y)`를 받는가.**
  4096/4096이면 통과. D3-4a가 커널 MMIO로 같은 것을 했으므로 **대조군이
  이미 측정돼 있다.**
- **V2g-2 (혼합)**: 한 배치에 텍스처 삼각형과 비텍스처 삼각형. 비텍스처
  쪽이 텍셀 값이 아닌 보간기 색을 내야 한다.
- **V2g-3 (검사기 양방향)**: `texorg`가 창 밖 → 거부(판정 6);
  같은 `texorg`인데 삼각형이 전부 비텍스처 → **수락**.
  `texW`가 2의 거듭제곱이 아님 → 거부. `texW = 256`(상한) → 수락,
  `512` → 거부.
- **V2g-4 (상속 확인)**: **텍스처 배치를 낸 다음 비텍스처 배치를 내고**,
  두 번째가 텍셀이 아니라 보간기 색을 내는지 본다. §19-1의 상속 문제가
  반대 방향으로도 없는지 보는 것이다.
- **V2g-5**: 텍스처 영역 무변, 색·깊이 가드, 화면 무변화.

### 19-7. 중단 조건

- 텍스처 영역이 변함 → 즉시 중단.
- 가드 오염 → 즉시 중단.

## 20. M1-2g 결과 (2026-08-20) — **텍스처가 배치 경로로 동작한다**

```
submit returned 0, verdict 0 (accepted)
textured band: drew 4096, identity 4096 of 4096
flat band: drew 3584 of 3584; its colour at (0,0) is c86432
texture region modified: 0 words
texorg at the visible framebuffer -> verdict 6 (texture origin)
the same bad texorg with no textured triangle -> verdict 0 (accepted)
```

**픽셀 4096개가 전부 자기 텍셀을 받았다.** 대조군은 D3-4a가 커널 MMIO로
같은 것을 4096/4096으로 측정해 둔 것이다.

### 20-1. 상속이 없다는 것을 같은 배치에서 확인했다

한 배치에 **텍스처 삼각형과 평면 삼각형**을 함께 넣었다. 평면 밴드의 색이
`c86432`인데, 이는 보간기에 넣은 `200/100/50`이다. 텍셀이었다면 하위
바이트가 `0x40`이었을 것이다 — **텍스처 상태가 옆 삼각형으로 새지 않는다.**

이것이 §19-1에서 지적한 구멍의 반대편이다. 인코더가 텍스처 상태를 전혀
emit하지 않던 상태에서는 **텍스처 배치가 남은 값으로 그려졌을 것**이고,
이제는 emit하되 **텍스처를 쓰지 않는 배치에서는 안 보낸다.**

### 20-2. 첫 실행은 거부됐고, 검사기가 옳았다

`verdict 8` — 커널 클립이 120행인데 64행짜리 밴드 둘을 128행에 놓았다.
**검사기가 맞고 시험 기하가 틀렸다.** 평면 밴드를 56행으로 줄여 정확히
120행에 맞췄다.

### 20-3. `tmr`을 검사하지 않으려던 근거가 부족했다 — 교차검토

§19-5는 "D3-4c가 `CLAMPUV`가 인출 주소를 묶는 것을 실측했으므로 `tmr`은
검사하지 않는다"였다. 교차분석이 그 근거의 범위를 정확히 좁혔다:
**그 측정은 고쪽(high-side) 좌표 하나**이며, 소스가 답하지 못하는 것이 둘
남는다.

| # | 안 잰 것 | 소스 |
| --- | --- | --- |
| a | `NOPERSPECTIVE`일 때 H 계열(`TMR4`/`5`/`8`)이 무시되는가 | **cannot verify** |
| b | 음수 시작값에서 저쪽(low-side) 클램프가 걸리는가 | **cannot verify** |

**AR 기울기 때와 같은 대응을 했다** — 검증되지 않은 하드웨어 성질에 기대지
않고 검사기가 직접 경계 짓는다:

- **H 계열은 클라이언트 손에서 뺐다.** 커널이 `TMR4 = TMR5 = 0`,
  `TMR8 = 1<<16`을 쓴다. (a)가 통째로 사라진다.
- 나머지 여섯은 **음수 금지**, 그리고 클립 전체에서 도달하는 좌표가
  **실측한 배율(8배) 안**이어야 한다. 곱셈은 나눗셈으로 바꿔 넘침을 피한다.

**8배라는 숫자는 임의가 아니라 D3-4c가 실제로 잰 배율이다.** 그 너머는
아무도 시험하지 않은 성질에 답이 걸리므로 거부한다.

### 20-4. 시험 스위트에서 내가 지운 섹션

M1-2f에서 슬라이스 치환을 쓰며 **깊이·텍스처 원점의 경계 시험을 통째로
지웠다.** 스위트는 계속 "0 failing"이었다 — **시험을 잃은 스위트도 성공이라
보고한다.** 사례 수가 47 → 55로만 는 것이 신호였는데 놓쳤다.

복원하고 텍스처·좌표 시험을 더해 **84개**가 됐다. 앞으로 사례 수를 판정에
같이 적는다.

### 20-5. 검산

| 항목 | 계산 | 실측 |
| --- | --- | --- |
| 텍스처 밴드 | 64×64 = 4096 | 4096 |
| 평면 밴드 | 56×64 = 3584 | 3584 |
| 두 밴드 합 | 120행 = 클립 정확히 | — |
| 평면 색 | `200/100/50` → `c86432` | `c86432` |
| `TEXWIDTH`(64, log2 6) | `0x00fc0406` | — |
| 한 텍셀 | `1 << (20-6)` = `0x4000` | 클라이언트가 보낸 값 |
| `texorg` 도달 | `64 × 64 × 4` = 16 KiB, 6~7 MiB 창 안 | 수락 |

### 20-6. 남은 것

- **`tmr` 좌표 경계를 실기에서 확인하지 않았다.** 단위시험만 통과했다.
  다음 부팅에서 음수 시작값과 8배 초과가 실제로 거부되는지 본다.
- 텍스처 필터(bilinear) 플래그는 코드에만 있고 시험하지 않았다.
- 여러 텍스처를 한 프레임에 쓰는 경우는 **배치 경계로 표현**한다(§17-2).
