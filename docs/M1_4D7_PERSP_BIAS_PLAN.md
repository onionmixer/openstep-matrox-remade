# M1-4D7 — 원근에서도 bias 를 도달범위에 맞춘다 (계획)

## 1. 왜 원근만 남았나

M1-4D5 는 아핀에서 `bias = min(496, 덧값(도달범위))` 로 고쳤지만 **원근은 496 에
남겼다.**  이유는 하나였다 — 엔진이 대역을 **무엇으로** 고르는지 몰랐다.  검증기가
분자를 `128·q` 까지 허용하므로, 분자가 대역을 정한다면 `q = 2^23` 에서 분자가
2^30 에 이르고 사다리는 2^23 까지만 측정돼 있었다.

## 2. 실측 (§64) — 분자다

`q` 를 쓸어 좌표를 2^19 로 고정했다.  그러면 좌표의 대역은 고정이고 분자의
대역만 움직인다.  한 좌표 단위는 `q/65536` 분자 단위이므로 그 폭으로 걸었다.

```
         q      분자    계단   덧값   분자의 대역   좌표의 대역
     65536    524288     -8    504    2^19 (504)    2^19 (504)
    131072   1048576      0    496    2^20 (496)    2^19 (504)
    262144   2097152    +16    480    2^21 (480)    2^19 (504)
    524288   4194304    +48    448    2^22 (448)    2^19 (504)
```

python: **덧값 = 분자의 대역 덧값**이 네 경우 모두 일치하고, 좌표의 대역 가설은
넷 중 셋이 반증한다.

> 원근에서 엔진의 덧값은 **분자 단위**로 적용되고, 그 대역은 **분자**에서 골라진다.

인코더가 빼는 496 도 분자에서 빼므로(`tmr[7] - bias`) 단위가 맞는다.

### 2-1 다섯째 점은 측정이 아니라 거절이었다

`q = 2^20`(분자 2^23)은 계단이 아니라 verdict 13 이었다.  원인을 좁혔다:

```
   분자 8388608  통과       (= COORD_MAX)
   분자 8388624  verdict 13
```

시작값 범위 검사가 `tmr[6]/tmr[7]` 을 `±COORD_MAX` 로 묶는다.  **원근에서 이건
앵커에만 걸린다** — 화소에서 평가된 분자는 `p ≤ 128·q` 로 따로 묶인다.

## 3. 그래서 무엇을 할 수 있나

같은 규칙이 그대로 쓰인다.  검증기의 도달범위(`ux`,`vx2`,`ly`,`ry`)는 **이미
분자**다 — 아핀에서는 `q = 65536` 이라 좌표와 같았을 뿐이다.

막는 것은 하나뿐이다: 평가된 분자가 `128·q` 까지, 즉 최대 **2^30** 까지 갈 수
있는데 사다리는 2^23 까지만 재봤다.

## 4. 선택지

| | 내용 | 대가 |
|---|---|---|
| **P1** | 도달범위 ≤ 2^23 인 원근 배치에만 새 bias, 그 위는 496 유지 | 흔한 경우를 고치고, 높은 분자는 **오늘 그대로**(회귀 아님).  새 측정 불필요 |
| **P2** | 2^24…2^30 대역의 덧값을 먼저 재고 표를 늘린다 | 정확하지만 측정이 더 든다.  앵커가 2^23 에 묶여 있어 **기울기로** 분자를 올려야 한다 |
| **P3** | 원근 분자를 2^23 이하로 **제한**한다 | 단순하지만 지금 되는 것을 거절하게 된다 — 회귀 |

P1 이 회귀 없이 대부분을 고친다.  P2 는 P1 위에 얹을 수 있다.

## 5. P1 이 건드려야 하는 것

지금 도달범위는 **원근에서 항상 0** 이다(`reach != 0 && !persp`).  이는 codex 가
"반쯤 채워진다"고 지적한 것을 막으려고 그렇게 한 것이고, 그 이유는 **상자 지름길**
때문이다: 원근은 상자를 통과하면 walk 을 건너뛴다.

내가 원근에서 walk 을 강제하지 않은 근거는 *"행 walk 은 몫을 행마다의 분모로
검사하는데 상자는 모서리의 분모로 검사하므로, 상자가 통과시킨 것을 걷다가 거절할
수 있다"* 였다.  **그 근거는 추론이지 측정이 아니다.**

그래서 P1 의 첫 단계는 코드가 아니라 측정이다:

> `test-hw3d-reach.c` 를 원근 배치로 확장해, `Validate` 와 `ValidateReach` 의
> 판정이 갈리는 경우가 **하나라도** 있는지 수만 건으로 본다.

갈리지 않으면 원근에서도 walk 을 강제하고 도달범위를 모은다.  갈리면 그 경우를
들여다보고 P1 을 다시 생각한다.

  문제다.
- 원근 배치의 도달범위가 실제로 얼마나 높이 가는가.  `perspfar` 는 얼마인가?

## 8. 실측이 계획을 단순하게 만들었다

### 8-1 codex 의 반증 실험 — 결론은 그대로

codex 가 짚었다: §2 의 네 점은 `q` 와 분자의 대역이 **함께** 움직여 둘을 못
가른다.  그래서 **일치-분자** 대조를 하나 넣었다 — `q = 262144`, 좌표 2^18 이면
분자는 `q = 131072` 행과 **똑같은 2^20** 이고 좌표의 대역만 2^18 로 다르다.

```
   matched numerator: q=262144 coordinate 2^18 numerator 1048576  step +0
```

`+0` 은 덧값 496 = **분자**의 대역이다.  좌표 대역이면 508 이라 `-12` 여야 했다.
상관관계가 끊긴 뒤에도 답은 같다.

### 8-2 상자 검사는 원근에서도 건전하다 — 내가 틀렸다

내가 원근에서 walk 을 강제하지 않은 근거는 *"몫은 선형이 아니니 모서리 논증이
안 통한다"* 였다.  codex 가 대수로 반박했고 맞다:

> `p/q ≤ m` 는 `p − m·q ≤ 0` 이고, `p − m·q` 는 **아핀**이다.  네 모서리에서
> 음이 아니면 상자 전체에서 음이 아니다.  `q > 0` 도 같은 이유로 전체에서 성립한다.

python 으로 무작위 상자 20 만 개를 돌려 내부가 모서리를 앞선 경우 **0** 을 확인했다.
검증기의 그 주석은 **틀린 추론**이었고 고쳤다.

### 8-3 분자는 2^30 까지 가지 않는다 — codex 도 틀렸다

codex 는 "분자가 128·q = 2^30 에 이르러 사다리 밖으로 나간다"고 했고 나도 그걸
받아 원근을 미뤘다.  **기울기 상한이 그걸 막는다:**

```
   |p| ≤ |tmr[7]| + |tmr[2]|·ex + |tmr[3]|·vy ≤ 3 × COORD_MAX = 25165824 < 2^25
```

앵커는 시작값 검사가, 각 기울기는 `room / 자기 축의 span` 이 묶는다.  비율 검사가
허용하는 2^30 에는 결코 도달하지 못한다.  빠진 단은 **둘뿐**이었다.

### 8-4 그 둘을 쟀다 (§65)

한 도형, 여러 분자.  대조군이 먼저다 — 이 도형에서 2^23 이 아핀 측정과 같은
**384** 를 주는지:

```
   2^23        분자  8388608   덧값 384      <- 대조군 통과
   (2^23,2^24) 전 구간         덧값 256
   2^25        분자 16842752   덧값   0
               분자 20971520   덧값   0
```

`g = 2^(대역−16)` 이 그대로 이어진다.  **사다리가 완성됐다:**

```
   2^16  511    2^19  504    2^22  448    2^25    0
   2^17  510    2^20  496    2^23  384
   2^18  508    2^21  480    2^24  256
```

곁가지로 두 번 속았다: `+1`·`+2` 로 보이던 "계단"은 텍셀 변화가 아니라 **앵커가
COORD_MAX 를 넘어 거절**된 자리였다.  앵커를 상한에서 떼자 사라졌다.

### 8-5 그래서 P1 의 절단이 필요 없다

2^23 에서 자를 이유가 없어졌고, codex 가 (c)에서 걱정한 **절단 이음매도 생기지
않는다.**  규칙 하나가 아핀과 원근 모두를 덮는다:

```
   bias(축) = min(496, 덧값(그 축의 분자 도달범위))
```

## 10. 재부팅 검증

### 10-1 아핀은 전부 불변, 원근만 움직였다

```
   near 24   lin 257   rgba 24/24   tile 0   tilelin 16384   tilebnd 0     불변
   persp 6                                                                 불변
   perspfar 5 -> 9                                                         움직임
```

아핀 도달범위는 `p ≤ 128·65536 = 2^23` 이 상한이라 새로 넣은 두 단(2^24, 2^25)에
닿지 않는다 — 예상대로 아무것도 바뀌지 않았다.

### 10-2 원근의 잔여가 0 이 됐다 (§65)

재부팅 **전** 같은 점들이 +112 / +240 / +496 이었다.  지금은:

```
   2^23 … 2^25 의 아홉 지점 전부  step +0   (잔여 0)
```

인코더가 원근에서도 엔진의 덧값을 그 배치의 최대 분자에서 **정확히** 상쇄한다.
이것이 원근판 `tilebnd` 다: 이전에는 텍셀 경계에 정확히 앉은 좌표가 **아래
텍셀**을 읽었고(잔여 −112 … −496), 지금은 제 텍셀을 읽는다.

### 10-3 `perspfar` 가 5 → 9 인 이유

덤프된 레지스터로 변 걷기를 python 에서 재현했다:

```
   삼각형 A: 스팬 54..266, 90 행, u 분자 도달범위 8306571
             대역 2^23 -> 덧값 384 -> bias 496 -> 384
             낮은 좌표 화소의 잔여: 15 -> 127
   삼각형 B: 도달범위 968496, 대역 2^20 -> bias 496 그대로
```

어긋난 9 화소는 **전부 R +16**, 즉 u 방향으로 **한 텍셀 높게** 읽는다.  양수
잔여의 서명이다.  이전에는 삼각형 A 의 잔여가 낮은 쪽 +15 에서 먼 쪽 **−112** 로
부호가 갈렸고, 지금은 낮은 쪽 +127 에서 먼 쪽 0 으로 **전부 양수**다.

즉 "일부가 한 텍셀 **낮게**"를 "조금 더 많은 수가 한 텍셀 **높게**"와 맞바꾼 것이고,
이는 §16-1 의 `tile lin` 과 같은 성질이다.  낮게 읽는 쪽이 경계 정렬 그림을
무너뜨리는 쪽이므로 이 방향이 설계 의도다.  10200 중 5 에서 9 로, 둘 다 0.1% 미만.

### 10-4 곁가지

`mesa/OpenStepMGAMesaTriangle.c` 의 `OSMGA_TMR_DUMP` 에 v 와 분모를 찍는 줄을
더했다.  **다만 가속 libGL 은 다시 만들지 못했다** — 그 빌드는 스테이징된 Mesa
트리를 요구하는데 그것은 `/tmp` 에 있어 재부팅에 사라졌고, NFS 의 업스트림 트리는
스테이징 패치 전이라 헤더가 맞지 않는다.  그래서 이 줄은 소스에는 있고 지금
동작하는 라이브러리에는 없다.  다음번 Mesa 빌드에서 나타난다.

위 §10-3 의 도달범위는 그래서 **이미 찍히던 u 평면**만으로 계산했다 — u 의 bias 를
정하는 것이 u 의 도달범위이므로 그것으로 충분하다.

| 옛 다섯 건의 내역을 예측으로 복원한 뒤 **한 번의 재부팅**으로 검증하라 | 예측하려면 화소별 `q` 가 필요하고, 그건 확장한 덤프 줄이 라이브러리에 들어가야 나온다 — 그 빌드는 스테이징된 Mesa 트리를 요구한다 | ⏭️**미해결로 남긴다.** 덮지 않는다 |
| 원근 경계 정렬 **장면**을 따로 만들어라 (탐침은 도구지 그림이 아니다) | codex 자신도 "경계 규칙 증명에는 합성 시험이 그림보다 낫다"고 했다.  §65 는 실기 종단 시험이고 세 대역·아홉 분자를 덮는다 | ⚖️부분 — 다음 항목으로 세운다 |
| 프리미티브를 사다리 경계에서 **쪼개면** 낮은 쪽이 더 큰 bias 를 갖는다 | 높은 쪽은 여전히 높은 대역이라 이득이 없고, 새 내부 변에서 균열·중복 그리기·반올림 변화 위험 | ⏭️미착수 — 이 부류가 흔해야 값이 있다 |

### 11-1 정당화를 다시 쓴다

"둘 다 0.1% 미만"은 근거가 아니다.  근거는 **계약**이다:

> **좌표는 caller 가 둔 자리보다 아래로 내려가지 않는다.**

그 아래로 내려가는 것이 텍셀 경계에 정렬된 그림을 무너뜨리는 실패이고,
아핀에서 56 열 중 48 열이 그 형태였다.  그 계약을 지키는 대가가 잔여를 전부
양수로 만드는 것이고, `perspfar` 의 5 → 9 와 `tile lin` 의 9984 → 16384 은 둘 다
그 대가다 — 방향이 같고, 크기가 한 텍셀(혹은 한 레벨)을 넘지 않는다.

### 11-2 잔여가 음이 아님은 표본이 아니라 증명이다

```
   bias = 덧값(최대 도달범위)
   덧값은 |p| 에 대해 비증가
   모든 화소의 p ≤ 최대 도달범위
   => 덧값(p) ≥ 덧값(최대) = bias   =>  잔여 ≥ 0
```

음수 허용 구간도 안전하다: `p ≥ -(q/16)` 이고 `q ≤ 2^23` 이므로 `|p| ≤ 2^19`,
덧값 504 이며 규칙이 고를 수 있는 가장 작은 bias 는 0 이다.  python 으로 모든
대역쌍을 전수 확인해 음수 잔여 **0 건**.

## 12. 남긴 것

- **옛 다섯 건의 내역.**  화소별 `q` 가 필요하고, 그건 Mesa 재빌드(스테이징
  포함)를 요구한다.  덮지 않고 미해결로 둔다.
- **원근 경계 정렬 장면.**  §65 가 기전을 실기에서 증명하지만 그림은 아니다.
- **사다리 경계에서의 프리미티브 분할.**  이 부류가 흔한지부터 재야 한다.

## 13. 옛 다섯을 복원했다 — 그리고 내 정당화를 정정한다

codex 가 "옛 내역을 예측한 뒤 재부팅 한 번으로 검증하라"고 했다.  재부팅 없이
됐다.  Mesa 스테이징을 **재부팅을 견디는 곳**(`/usr/local/mesastage`)으로 옮기니
— 스테이징 스크립트의 주석이 *"재시작 뒤에도 남기려는 것이 이 변수의 존재
이유"* 라고 이미 적어두었다 — 라이브러리를 다시 만들 수 있었고, 확장한 덤프가
v 와 분모를 찍었다.

### 13-1 모형을 먼저 검증했다

전체 레지스터로 화소마다 좌표를 계산해 **살아 있는 하드웨어와 대조**했다.

```
   나눗셈 덧값 없음        10200 중 14 불일치
   E = 512·f              13
   E = 512 (고정)          8
   E = 512·(f − 1)         1        <- 채택
```

`f` 는 `q` 의 정규화 가수다.  10200 중 1 만 어긋나므로 오라클로 쓸 수 있다.
(기록된 법칙은 `512·f` 였다.  여기서는 `512·(f−1)` 이 훨씬 잘 맞는다 — 두 측정의
규약이 다를 수 있으니 **불일치로 남겨** 둔다.)

### 13-2 그 오라클이 낸 답

```
   옛 bias 496 : 5 화소 틀림 — 전부 한 텍셀 HIGH, LOW 는 0
   새 bias     : 10 화소 틀림(모형) / 9(실측) — 전부 HIGH, LOW 는 0
   옛 집합 ⊂ 새 집합            고쳐진 화소: 없음
   새로 깨진 화소: (81,36) (105,65) (143,91) (150,62) (184,42)
```

옛 다섯의 개수가 지난 재부팅의 실측 **5 와 일치**한다.

### 13-3 그래서 내 정당화는 틀렸다

직전 커밋에 나는 *"이전에는 낮은 쪽 +15, 먼 쪽 −112 로 부호가 갈려 일부가 낮게
읽었다"* 고 적었다.  **이 장면에서는 낮게 읽은 화소가 하나도 없다.**  −112 잔여는
존재했지만 텍셀 경계 아래 112 단위 안에 표본이 들지 않아 오류를 내지 않았다.

정확한 문장은 이것이다:

> `perspfar` 에서 이 변경은 **아무것도 고치지 못하고 네 화소를 더 틀리게 했다.**
> 이득은 이 그림에 없다 — §65 의 아홉 분자에 있고, 거기서는 텍셀 경계에 정확히
> 앉은 좌표가 아래 텍셀을 읽던 것이 제 텍셀을 읽게 됐다.

### 13-4 그러면 유지할 것인가

유지한다.  근거는 그림이 아니라 계약이다:

- 경계에 정렬된 내용은 **텍스처를 제 크기로 그릴 때 나오는 것**이고 흔하다.
  아핀에서 그 형태가 56 열 중 48 열을 무너뜨렸다.
- 원근에서 같은 형태가 무너지던 것을 §65 가 실기에서 세 대역·아홉 분자로 보였고,
  지금은 잔여가 0 이다.
- 대가는 유계다 — 경계 아래 `511 − bias` 단위 안의 화소가 한 텍셀 높게 읽는다.

**다만 그림 하나에서는 순손실이라는 것을 기록한다.**  숨기지 않는다.

### 13-5 대가를 줄이는 길 (다음 설계 항목)

잔여가 큰 이유는 **도달범위는 높은데 화소 대부분은 낮기** 때문이다 — `perspfar`
의 삼각형 A 가 정확히 그렇다(도달범위 8306571, 대부분의 화소는 훨씬 아래).
codex 가 제안한 대로 **사다리 경계에서 프리미티브를 쪼개면** 각 조각의 bias 가
제 화소에 맞는다.  높은 쪽 조각은 이득이 없지만 낮은 쪽은 잔여가 확 준다.

대가: 프리미티브가 늘고, 새 내부 변에서 균열·중복 그리기 위험이 있으며, 분할
자체가 반올림을 바꾼다.  **이 부류가 얼마나 흔한지부터 재야 한다.**

## 14. λ 를 줄이는 길은 막혀 있다 (그리고 왜 그런지)

원근에서는 분자와 분모를 함께 `λ` 로 재도 몫이 변하지 않으므로, `λ` 를 낮추면
분자의 대역이 내려가고 bias 가 좋아진다.  기하를 쪼개는 것보다 훨씬 싸 보였다.
`perspfar` 의 삼각형 A(p 8306571, q 519777)로 재봤다:

```
      s      p reach          q   bias  잔여   좌표 단위   나눗셈 오차
   1.0000    8306571     519777    384   127    16.01 un    0.0039 tx
   0.5000    4153285     259888    448    63    15.89 un    0.0079 tx
   0.2500    2076642     129944    480    31    15.63 un    0.0158 tx
   0.1250    1038321      64972    496    15    15.13 un    0.0315 tx
   0.0625     519160      32486    496    15    30.26 un    0.0630 tx
```

**좌표 단위 잔여가 거의 변하지 않는다.**  bias 가 좋아지는 만큼 `q` 도 줄기
때문이다.  이유는 산술로 나온다:

```
   대역 n 의 분자에서  잔여 = 511 − bias = 2^(n−16) − 1 ≈ p / 65536
   좌표 단위로는       (p/65536) × 65536/q = p/q = 좌표/65536
```

즉 **보정이 남기는 것은 좌표의 2^-16 짜리 상대오차**이고, `λ` 는 `p/q` 를 바꾸지
못하므로 그것을 이길 수 없다.  텍스처 한 장 크기의 좌표에서 16 좌표 단위이고,
텍셀로는 TD 16 에서 0.00024, TD 2048 에서 0.031 이다.

이 관계는 아핀에도 그대로 성립한다(`q = 65536`, 좌표 = 분자).

**남는 지렛대는 프리미티브를 대역 경계에서 쪼개는 것 하나뿐이다** — 각 조각이 한
대역 안에 들면 잔여가 0 이 된다.  다만 이 삼각형은 2^16 부터 2^23 까지 여덟
대역에 걸쳐 있어 여덟 조각이 되고, 자르는 선은 `p` 가 일정한 직선이라 다시
삼각형으로 나눠야 한다.  **값을 적어둘 뿐 치르지는 않는다.**
