# W2 — WARP 렌더링 경로 계획

계획만. 코드는 아직 없다.

**5 판.** 2 판은 codex 와 서브에이전트가 독립으로 검토했고 둘이 다른 것을
잡았다. 3 판은 codex 가 다시 검토했다. 4 판은 **우리 구현을 기준으로** 검토했고,
그것이 가장 많이 잡았다 — 참고 소스가 아니라 **이 프로젝트의 코드가 무엇을
허용하는가**를 물으니 계획의 뼈대 두 곳이 무너졌다. §14~§16 에 판정표가 있다.

**현재 판정: 착수 불가.** 이유는 §3 이다 — 착수를 승인할 측정이 **만들어지지
않는다**. 그것을 먼저 고쳐야 나머지가 의미를 갖는다.

---

## 1. 왜 — 그리고 이 문단이 주장하지 않는 것

WARP 는 삼각형 셋업을 하드웨어로 옮긴다. 정점을 주면 카드가 셋업한다.

`docs/W1_WINDOWS_DRIVER_FINDINGS.md` §Y-3: 출하 Windows 드라이버조차 DWG 로
기울어진 변을 그리지 않고 셋업을 전부 WARP 에 맡긴다. X.Org DRI 도 같다.
**우리가 걷는 경로 B 에 3D 선례가 없다.**

**주장하지 않는 것: "측정이 CPU 셋업을 병목으로 특정했다."** 근거로 인용했던
25 ms 는 `hw3d/test-hw3d-validate-cost.c` 의 **1200 행짜리 삼각형 180 개**
합성 워크로드다. 우리 teapot 삼각형은 52 픽셀이고, 같은 하니스의 128 행 경우는
프리미티브당 15 us 다(`docs/M1_4D5_LADDER_ABOVE_2E20.md:321`). **둘 다 52 픽셀
삼각형의 비용을 말해주지 않는다.**

## 2. 지금 있는 것 — 그리고 **없는 것** (2 판이 과장했다)

실기 PASS (`docs/D2_2_WARP_PIPE_START_PLAN.md`):

```
D2-0a WARP 설정          PASS  WMISC 0 -> 3
D2-0b 전체 warp_init     PASS
D2-1b 마이크로코드 배치    PASS  16 pipes @ 00020000
D2-2a/start 파이프 기동   PASS  10 blocks, spins=26, WMISC=3
```

2 판은 이것을 "엔진은 켜졌고 마이크로코드는 자리에 있다, 없는 것은 정점을
먹이는 경로뿐" 이라고 요약했다. **틀렸다.**

**(a) 마이크로코드의 수명은 균일하지 않다.** 3 판은 "테스트 전용이고 해제된다"
고 뭉뚱그렸는데 실제로는 두 갈래다:

- 배치 시험은 자기 사본을 **해제한다**(`:7088`).
- `runWarpPipeStartTest` 는 **따로 잡아 일부러 남긴다**(`:7216`).

그런데 남긴 포인터와 물리 주소표가 **지역 변수**라 시험이 끝나면 운영 코드가
그 할당을 되찾을 수 없다. 그리고 이 시험들은 `warpTestEnabled` 뒤에 있고
기본값이 꺼짐(`:3002`)이라, 평소에는 마이크로코드가 저메모리에 **없고**, 시험을
켠 부팅에서는 **그 부팅 내내 새는 채로 남는다.**

**(a-2) 그리고 이 시험들은 엔진 claim 을 잡지 않는다.** `runWarpConfigTest`,
배치 시험, `runWarpPipeOnce`, `runWarpPipeStartTest` 어느 범위에도 `stormLock`
사용이 없다. 운영으로 옮기려면 claim·사전 정지·경계 있는 완료·복구·영구 실패
래치·마지막 idle·2 차 DMA 완료 규칙을 전부 새로 입혀야 하고, `pipePhys[0]` 하드
코딩(`:7247`)도 선택된 파이프로 바꿔야 한다. 재사용할 수 있는 것은 마이크로코드
블롭과 레지스터 상수, 그리고 `osmgaWarpPlaceUcode`(`:6778`) 정도다.

**(b) 이 드라이버가 한 줄도 쓴 적 없는 레지스터가 많다.** 실제 WARP 경로가
내보내야 하는 것(`scratch/mga-drm/mga_state.c:271-350`, `mga_g400_emit_pipe`):

| | |
| --- | --- |
| `WFLAG`, `WFLAG1` | `mga_state.c:328` — **cull 레지스터다.** `mgastate.c:627` 이 `ctx->Polygon.CullFlag` 에서 만들고, `warp_pipe & MGA_TEX1_BIT` 반전에는 원저자가 `/* why??? */` 라고 적어뒀다 |
| `WR49,52,53,54,56,57,60,61,62` | `mga_state.c:332-341`, 매직 상수 `MGA_G400_WR_MAGIC`, `MGA_G400_WR56_MAGIC = 0x46480000`(= 12800.0f) |
| `DMAPAD 0xffffffff` × 3 | `mga_state.c:343`. D1 의 tail 패딩과 **별개** |
| `DWGCTL_FLUSH` + `TEXCTL2`/`DUALTEX` 순서 | `mga_state.c:301-313`, 이중 텍스처 파이프에서 나올 때 |

지금 드라이버가 쓰는 것은 `WIADDR2`, `WGETMSB`, `WVRTXSZ`, `WACCEPTSEQ`,
`WMISC` 다섯뿐이다(`:7069-7073`).

`WR24..WR62` 는 `0x2d60..0x2df8` 로 `OSMGA_DWGREG1`(`0x2c00..0x2dff`) 안이라
DMA 인코딩이 된다. `WMISC`(`0x1e70`)는 아니고 MMIO 전용이다(`:295`).

D1 의 1 차 DMA 링은 PASS 이고(`checksum dbeef000, spins=23`), D1-0 이 **물리
연속 시스템 메모리의 버스 마스터링**을 증명했다 — §5 가 재사용한다.

## 3. 착수 조건 — **지금은 만들어지지 않는다 (블로커)**

### 2 판의 4 팔이 왜 성립하지 않는가

2 판은 arm B 를 "커널은 돌되 doorbell 없음" 으로 정의했다. 커널 층에는 실제로
깨끗한 이음매가 있다 — `osmgaHW3DEncode`(`:5577`) 뒤, doorbell(`:5718`) 앞.
**문제는 유저랜드다.**

doorbell 을 건너뛰면 ioctl 이 `IO_R_RESOURCE` 를 돌려주는데 verdict 는
`OSMGA_HW3D_OK` 다(검증은 통과했고 실행만 안 했으므로). 그 조합을 훅이 이렇게
받는다:

```c
mesa/OpenStepMGAMesaHook.c:840   if (res.verdict == OSMGA_HW3D_OK) {
                          :844       OSMGAMesaProbeRevoke("a batch failed after the engine had it");
```

**첫 프레임에 가속을 영구 회수하고 재생도 하지 않는다.** arm B 는 한 프레임
뒤부터 소프트웨어 렌더러가 된다. `A − B` 는 "실행 + fill" 이 아니라 음수이거나
소프트웨어 래스터화가 지배하는 값이다.

거기에 더해, doorbell 없이 완료 폴이 도는 경로는 `OSMGA_S1_SPIN_LIMIT`
100,000 회를 두 번 돌고 읽기당 약 1.08 us 다:

```
200,000 x 1.08 us = 216 ms   -- 첫 dry-run 제출 한 번에
```

그리고 `osmgaStormInitState`(`:5701`)가 doorbell **앞에서** `CXBNDRY`/`YTOP`/
`YBOT` 를 프로그램하고 되돌리지 않는다(§3-64, 미해결). arm B 는 그리지도 않으면서
엔진의 클립을 좁혀 놓는다.

**"매 프레임" 이라고 쓴 3 판은 자기모순이었다** — 첫 실패에서 가속이 회수되므로
그 뒤 프레임은 소프트웨어이고 커널에 오지 않는다. 클립은 **첫 제출 한 번** 좁혀
지고 그대로 남는다. 고친 dry-run 에서는 매번이 되므로, 그때 §3-64 를 함께 고치는
편이 낫다.

### 그러니 게이트를 먼저 고쳐야 한다

**W2-(-1) — dry-run 을 일급 모드로 만든다.** 실패가 아니라 **의도된 결과**로
돌아와야 한다. 필요한 것:

- **먼저: 요청할 방법이 없다.** `OSMGAHW3DSubmitBlock` 은 결과만 담고
  (`hw3d/OpenStepMGAHW3D.h:886`), `OSMGA_IOC_SUBMIT` 는 `OSMGA_IOC_OUT_BIT` 만
  세운 **출력 전용** ioctl 이다(`:893`). 유저랜드가 "이번은 dry-run" 이라고 말할
  입력이 존재하지 않는다. 별도 ioctl 을 두거나, 배치에 검증되는 모드 필드를
  넣거나, 입출력 요청 블록으로 바꿔야 한다.

  그리고 배치에 필드를 넣으면 **공유 ABI 가 바뀌므로** 버전 정확 일치 게이트
  (`mesa/OpenStepMGAMesaProbe.c:145`)가 **이 단계에서 이미** 걸린다. 즉
  라이브러리와 드라이버를 함께 올려야 하는 것이 W2-4 가 아니라 **W2-(-1) 부터**다.
- 커널: doorbell·세 대기·완료 폴을 건너뛰는 경로. **인코더 호출 뒤에** 갈라져야
  한다 — 앞에서 `total3` 을 0 으로 만들면 arm B 가 인코딩 비용을 재지 못한다.
  인코딩 길이는 진단용으로 남긴다.
- 커널: 그 경로만의 **전용 반환값**. `IO_R_RESOURCE` 재사용 금지이고, ioctl 층이
  모르는 반환을 `EIO` 로 뭉개므로(`:2422`) 거기까지 통해야 한다.
- 유저랜드: **성공도 거절도 아닌 세 번째 결과**가 제출 블록·프로브 래퍼·삼각형
  flush·clear 경로·카운터·soil 장부를 전부 관통해야 한다. 성공으로 매핑하면
  그리지도 않은 것을 그린 것으로 세고 표면을 soil 하며, 실패로 매핑하면 거절·
  재생·회수 논리로 들어간다.
- **clear 를 제외해야 한다.** 가속된 clear 가 **같은 제출 함수**를 쓴다
  (`mesa/OpenStepMGAMesaHook.c:2746`). 제출 단위 모드가 아니면 arm B 가 clear 의
  실행과 fill 까지 건너뛴다. **그리고 더 나쁘다** — 그 자리에서 실패로 보이면
  `return 0` 이고, 그러면 **Mesa 가 소프트웨어로 clear 한다**(`:2748` 주석).
  arm B 가 clear 비용을 빼는 게 아니라 **소프트웨어 clear 를 더한다.** 팔마다 clear·삼각형 제출·
  present 를 **따로 세고**, clear 뒤 표면 체크섬으로 실제로 지워졌는지 확인한다.
- `osmgaStormInitState` 를 dry-run 에서 건너뛰거나 클립을 되돌린다(§3-64).
- **고장 주입 소비를 dry 분기 아래로 옮긴다.** 지금 자리(`:5337`)면 dry 제출마다
  `osmgaInjectTimeouts` 를 소비하면서 정작 주입하려던 타임아웃은 겪지 않는다.
- 그리고 **`A − B` 의 뜻을 정확히 적을 것.** 인코더 직후에 갈라지면 진입 대기와
  상태 프로그래밍(`:5588`, `:5701`)은 **B 에 없고 A 에 있다.** 그러니 그 둘은
  `B − C` 가 아니라 `A − B` 에 들어간다.

**양 끝을 함께 고쳐야 하고 커널 쪽은 재부팅을 부른다.** 그래서 arm B 만 다른
빌드가 된다 — "네 팔이 전부 같은 장면" 이라는 전제가 그만큼 약해진다. 그 사실을
측정 보고에 적어야 한다.

**그리고 `A − B` 는 여전히 "실행 + fill" 이 아니다.** 그 차이에는
`osmgaStormWaitIdle`, DMA 정지 스핀, FIFO 진입 대기, `osmgaStormInitState` 의
레지스터 쓰기(정적으로 세어 **최대 12 곳**, 3 판이 적은 13 은 틀렸다), 목록
체크섬 배리어(`:5714`), 상태 읽기, trap 클리어, doorbell(`:5718`), 완료·복구 폴,
마지막 idle, 선택적 settle 읽기(`:5895`), 그리고 유저랜드 장부가 함께 들어 있고
**WARP 는 그중 아무것도 없애지 않는다.**

### 고친 뒤의 네 팔

| 팔 | 하는 일 |
| --- | --- |
| A 정상 | 기하 + 사다리꼴 빌드 + 커널(검증·인코딩) + 실행·fill |
| B dry-run | 기하 + 빌드 + 스냅숏·검증·인코딩·ioctl, doorbell 없음, **회수 없음** |
| C ioctl 없음 | 기하 + 빌드 |
| D 빌드도 없음 | 기하와 동일한 훅·상태 순회만 |

```
커널 작업(인코딩·검증·진입·상태) = B - C
사다리꼴 빌드                    = C - D
WARP 가 없앨 상한                ≤ B - D
```

`B − D` 조차 상한이다. WARP 는 정점 포장·정점 검증·제출·자기 셋업을 새로 낸다.

**계측 제약**: 제출마다 `gettimeofday` 를 넣지 말 것. 두 번 부르는 데 제출당
9.2 us 이고(`mesa/OpenStepMGAMesaHook.c:1211`, 4.58 us × 2), 타이밍 전용 계측은
§7 의 프리즈 조합의 한쪽이다(`REMAINING_WORK.md:4019` 가 `scissor 120 i1` 로
한 번 얼어붙은 것을 기록한다).

## 4. 이득의 상한 — 2 판보다 낮고, 바닥이 두 군데 물렁하다

2 판은 12.874 ms / 프레임의 62.2% / 128 fps 를 적었다. **뒤의 둘이 틀렸다** —
분모 20.71 은 계측 구간이고 벽시계는 21.01 ms(47.6 fps)다. 그리고 바닥 항 둘이
과소평가였다.

```
fill 항:    5.53 ns/px 는 512x384 clear 를 역산한 값이다.
            800x600 clear 실측 3.48 ms 는 7.25 ns/px 다 -> fill 0.370 ms
왕복 항:    ceil(981/76) = 13 이 아니라, glwin 은 glEvalMesh2 때문에
            프레임당 65 블록이고 블록마다 flush 한다(R21) -> 0.871 ms
```

**둘 다 "바닥" 이 아니다. 아래 두 문단이 왜인지 적는다 — 3 판은 이것을
"정정된 사실" 처럼 썼고 그것이 틀렸다.**

`7.25 ns/px` 는 **clear 픽셀**의 벽시계 평균이고 그 안에 셋업·검증·인코딩·
대기·제출이 다 들어 있다. teapot 픽셀은 깊이 시험을 받고, 기각될 수도 있고,
겹쳐 그려질 수도 있다. **teapot 그리기의 하한이라는 증명이 없다.**

> **이 항목을 재는 방법으로 이 문서가 적어 두었던 것 — 기하·프리미티브 수·
> 상태·제출 수를 고정한 채 scissor 로 fragment 면적만 쓸어 정상 − dry-run 의
> 절편과 기울기를 맞추는 것 — 은 2026-08-28 에 철회되었다.**
>
> **그 방법은 §7 이 금지하는 조합 그 자체다.** `REMAINING_WORK.md` §3-62 가
> `scissor + 계측` 을 여섯 번의 하드 프리즈 끝에 금지했고(`:4118`), 이 문단은
> 22 줄 위(§3 끝)에서 그 사실을 스스로 인용하면서도 여기서 그것을 처방했다.
> **문서가 자기와 모순돼 있었고, 그 모순이 2026-08-28 에 일곱 번째 프리즈를
> 만들었다** — 시저 8 단계 스윕에 프레임당 타이밍 클럭 다섯 개. 기계는 ICMP
> 까지 죽어 전원 재시작이 필요했다. 경위는 §21.
>
> **그러니 fragment 면적은 시저로 재지 않는다.** 대안은 §21.3 에 있고, 없으면
> 이 항목은 **미측정으로 남긴다.** 미측정으로 남기는 것이 프리즈보다 싸다.

`65` 는 **블록 수이지 왕복 수가 아니다.** 훅은 조건부로 flush 하므로 렌더 블록과
제출은 다른 사건이고, `REMAINING_WORK.md:2858` 에는 다른 제출 수가 기록돼 있다.
재려면 그 arm 빌드의 glwin 에서 **제출 카운터의 프레임당 증분**을 쓴다.

python 확인:

```
draw 13.330 - fill 0.370 - 왕복 0.871 = 12.089 ms
  draw 의 90.7%, 벽시계 21.01 ms 프레임의 57.5%
  물리적으로 불가능한 최선의 프레임 8.92 ms = 112 fps
```

**그리고 아무도 재지 않은 항이 있다: 엔진 자신의 프리미티브당 비용.**

프레임당 사다리꼴이 몇 개인지 **이 문서는 모른다.** 아는 것은 소스 삼각형이
약 981 개라는 것뿐이다. 하나가 둘로 쪼개질 수도 있고, **하나도 안 만들 수도
있다** — `mesa/OpenStepMGAMesaTriangle.c:1218` 이 행이 없으면 0 을 돌려준다.
그러니 981 은 하한도 아니다. 사다리꼴 수는 **0 에서 1,962 사이**이고, 그 폭이
이 표를 쓸모없게 만든다. 초판·2 판이 쓴 1,962 는 R21 의 **오프라인** 실행에서 나온
제출 횟수이고, 그 데모는 teapot 을 **두 개** 그린다 — glwin 은 하나다.

`OSMGAMesaHookTraps()` 가 있으므로(`mesa/OpenStepMGAMesaHook.h:219`) **실측할
수 있는 값이다.** 아래 표는 그것을 재기 전까지의 감도 분석일 뿐이고, 어느 칸도
사실이 아니다:

| 가정한 프리미티브당 비용 | 사다리꼴 981 개면 | 1,962 개면 | draw(13.33 ms) 대비 |
| --- | --- | --- | --- |
| 0.5 us | 0.491 ms | 0.981 ms | 3.7% ~ 7.4% |
| 1.0 us | 0.981 ms | 1.962 ms | 7.4% ~ 14.7% |
| 2.0 us | 1.962 ms | 3.924 ms | 14.7% ~ 29.4% |
| 5.0 us | 4.905 ms | 9.810 ms | 36.8% ~ 73.6% |

WARP 는 **CPU 가 짓는 비용**만 없애지 엔진이 걷는 비용은 없애지 않는다. 이 항이
크면 상한은 훨씬 낮다. **미측정, 그리고 두 가지를 재야 한다** — (1) `OSMGAMesaHookTraps()` 로 glwin 의
프레임당 사다리꼴 수, (2) 같은 총 면적을 더 적은 삼각형으로 그려 덮인 픽셀당
draw 시간을 비교. grid 8 → grid 2 는 삼각형이 grid 제곱에 비례하므로
**0.0625 배**이지 3 판이 적은 "1/10" 이 아니다. 큰 텍스처 quad 는 텍스처와 상태
비용까지 바꾸므로 프리미티브 비용의 깨끗한 대조군이 **아니다**.

**이 절은 결론이 아니라 감도 분석이다.** 두 항이 바닥이 아니고 프리미티브당
비용이 미측정이므로, "작은 조각을 쫓는 프로젝트는 아니다" 는 **§3 의 측정이
나오기 전까지는 주장할 수 없다.** 3 판은 그것을 결론처럼 적었다.

## 5. 정점을 어디에 두는가

DRM 의 PCI 경로가 2 차 버퍼를 `drm_addbufs_pci` 로 **시스템 메모리**에 잡고
(`scratch/mga-drm/mga_dma.c:681`), 그 `bus_address` 를 `SECADDRESS` 로 쏜다
(`mga_state.c:658`). D1-0 이 이 카드의 물리 연속 버스 마스터링을 증명했다.

**2 판의 오기 정정**: `drm_addbufs_pci` 는 681 행이고(675 아님),
`mga_dma.c:699` 는 `dev_priv->dma_access = 0;` — PCI 에서는 접근 모드를 **세우는
게 아니라 지운다.** `SECEND | dma_access` 를 그대로 옮기면 없는 비트를 찾게 된다.

## 6. 안전 설계 — 2 차 DMA 는 새 비동기 독자다

현재 경로가 갖고 있고 W2 도 반드시 가져야 하는 것:

- 복사·검증·인코딩·실행 **전에** 전역 엔진 claim (`:5299`)
- 검증 전에 클라이언트 입력 **스냅숏** (`:5398`)
- 레지스터를 건드리기 전에 1 차 DMA 정지 증명 (`:5597`)
- 경계 있는 완료, 복구, **영구 실패 래치** (`:5773`)

**새로 져야 하는 것:**

- **2 차 DMA 완료 판정.** ~~지금 `MGA_DMA_DONE_MASK` 는 1 차만 본다~~ →
  **2026-08-28 해소.** 사양서 4-13: *"Use of the primary DMA channel is
  complete when the primary, **secondary** and setup DMA transfers are
  finished."* **지금 예측이 이미 2 차를 덮는다**(W9 §1.6). 아래 문단은
  사양서를 찾기 전의 판단이므로 남겨 두되, 결론은 뒤집혔다.

  ~~지금 `MGA_DMA_DONE_MASK` 는
  `SOFTRAPEN | DWGENGSTS | ENDPRDMASTS` 로 **1 차 DMA 만** 본다(`:275`).~~
  `SECADDRESS`/`SECEND` 는 소스 전체에서 `#define` 둘과 인코더의 거부 한 줄,
  **총 세 곳에만** 나오고 완료 확인에는 없다. 1 차가 soft trap 에 닿아 "끝났다"
  고 판정하는 동안 2 차가 아직 메모리를 읽고 있을 수 있다.
- **정점 버퍼의 수명 규칙.** 정지가 증명되지 않으면 할당을 **영원히 보유**한다 —
  1 차 DMA 시험이 이미 그렇게 한다(`:6647`).
- **클라이언트 매핑 버퍼를 그대로 `SECADDRESS` 에 넘기지 않는다.** 카드가 읽는
  동안 클라이언트가 고칠 수 있다 — 엔진 claim 은 커널 이용자끼리의 것이고
  클라이언트 매핑을 쓰기 금지로 만들지 않는다(mmap 처리기는 배치를 노출하고
  링만 숨긴다, `:2452`).

  **순서가 중요하고, 3 판은 그것을 거꾸로 적었다.** 3 판은 "검증한 정점을 복사"
  라고 썼는데 그러면 검증과 복사 사이에 경주가 남는다. 옳은 순서는

  ```
  claim  ->  클라이언트 바이트를 커널 스테이징으로 복사  ->  스테이징을 검증
         ->  그 스테이징을 제출
  ```

  기존 사다리꼴 경로가 이미 그렇게 한다 — claim `:5322`, **복사 `:5398`**
  ("Copy before checking"), 검증 `:5488`. 새 경로는 그 자리를 그대로 쓰면 된다.

  덧붙여 이 복사는 **추가 비용이 아니라 교체**일 수 있다. 지금 스냅숏이 최대
  23,868 바이트이고 정점 업로드가 최대 24,492 바이트라 차이는 624 바이트다.
  다만 **복사에 걸리는 시간은 아무도 재지 않았다.**
- **인코더를 넓히지 않는다.** `osmgaDmaIndex`(`:6030`)는 `SECADDRESS`/`SECEND`/
  `SETUPADDRESS`/`SETUPEND` 를 의도적으로 거부한다. 커널 전용 이미터를 좁게 만든다.
- **`DWGCTL.CLIPDIS` 강제 해제와 커널 소유 클립.** DRM 은 `DWGCTL` 을 고쳐
  `CLIPDIS` 를 없애고 2 차 발사 **직전마다** 클립을 내보낸다
  (`mga_state.c:48`, `:653`). 2 판은 클립을 그림 디버깅 변수로 다뤘다 — 격리
  계약의 일부다.

**되돌릴 수 없는 실패.** 이 드라이버에는 **엔진 리셋이 없다.** 자기 주석이
그렇게 적는다: *"Closing it needs a reset or a quarantine, and this driver has
neither"*(`:5834`). `stormBlitFailed = YES` 는 커널이 더 일을 넘기지 않게 할 뿐
이미 나간 버스 마스터를 멈추지 못한다. 그리고 모드 claim 은 `stormBlitFailed` 를
보지 않으므로(`:5928`), 나중의 모드셋이 **아직 버스 마스터 중인 엔진을
프로그램**할 수 있다. 그 뒤 복구는 전원 재투입뿐이다.

처방하고 있었기 때문이다**(§21). §4 의 처방은 철회했다.

2 차 DMA 는 같은 전역 엔진과 1 차 스트림에 **또 하나의 비동기 독자**를 붙인다.
체크박스나 남겨둔 코드는 격리가 아니다. 실기 시험은: 제출 **한 번**, 격리된
오프스크린 canary, 외부 로그 캡처, **scissor 계측 금지**, 전후 정지 확인,
이상이 보이면 **재시도 금지**.

**§8 W2-1 의 음성 대조에는 무장 해제가 없다.** `SECADDRESS` 만 쓰고 `SECEND` 를
쓰지 않는 것은 "가설이지 알려진 사실이 아니다" 라고 2 판이 적었는데, **가설이
틀렸을 때의 회수 수단이 계획에 없다.** `SECADDRESS` 를 되돌리는 절차를 먼저
정하거나, 그 대조를 하지 않는다.

## 9. 정점 레이아웃 — 형식은 해소, **규약은 아니다**

### 출처

XFree86 4.1.0 의 `xc/lib/GL/mesa/src/drv/mga/` 를 `scratch/mga-dri-xf410/` 에
두었다(33 파일). 이 시대의 MGA DRI 드라이버는 Mesa 자체 트리가 아니라 **XFree86
트리 안**에 있었다. Mesa 자신의 `src/mesa/drivers/dri/mga/` 는 6.3.2 에 처음
들어가 **7.11.x 가 마지막**이고 8.0 에서 사라졌다.

### 구조체 — `mgavb.h:42-71`

```c
typedef struct mga_warp_color_t  { GLubyte blue, green, red, alpha; } mga_warp_color;
typedef struct mga_warp_vertex_t { GLfloat x,y,z; GLfloat rhw;
                                   mga_warp_color color, specular;
                                   GLfloat tu0,tv0,tu1,tv1; } mga_warp_vertex;
union mga_vertex_t { mga_warp_vertex v; float f[16]; GLuint ui[16]; };
```

| 바이트 | dword | 뜻 |
| ---: | ---: | --- |
| 0,4,8 | 0,1,2 | 화면 공간 `x,y,z` |
| 12 | 3 | `rhw` |
| 16 | 4 | diffuse, 메모리 순서 **B,G,R,A** |
| 20 | 5 | specular **B,G,R**, **알파 바이트가 fog** |
| 24,28 | 6,7 | `tu0, tv0` |
| 32,36 | 8,9 | `tu1, tv1` (이중 텍스처) |

색 순서는 구조체에 박혀 있고 조건부가 아니다. `mgavb.c:61` 이
`color.blue = col[2]` 로 쓴다.

### 세 가지 크기를 혼동하지 말 것

```
구조체   40 바이트
union    64 바이트   <- mgatris.h 가 배열로 인덱싱하는 원소 (mgavb.c:436)
레코드   32 바이트   <- 실제로 전송되는 것 (8 dword)
```

2 판은 "함정은 40 이다" 라고 적었다. **틀렸다** — 40 은 전송 경로에 나오지
않는 수다. 배열 원소는 **64 바이트 union** 이고, 8 dword 는 그 앞부분이다.
배열을 40 이나 32 로 잡으면 인덱싱이 어긋난다.

### `WVRTXSZ` 인코딩

2 판은 primsz 만 적었다. 규칙은 **`(vertsize-1) | (3*vertsize) << 8`** 이다:

```
vertsize  8 -> 0x1807  (wvrtxsz 7, primsz 24)
vertsize 10 -> 0x1e09  (wvrtxsz 9, primsz 30)
```

primsz 만 보고 이중 텍스처를 유도하면 `0x1e0a` 가 나오고 **틀린다.**

### **진짜 남은 위험 — 좌표 규약** (`mgavb.c:87`)

```c
#define COORD  GLfloat *win = VB->Win.data[i];
    v->v.rhw = win[3];  v->v.z = depth_scale * win[2];
    v->v.x = win[0] + xoffset;  v->v.y = - win[1] + yoffset;
```

- **y 가 뒤집힌다.** 우리 표면은 y-up 이다(`OpenStepMGAMesaHook.c:1183`).
  그대로 옮기면 안 된다.
- `xoffset = drawX + SUBPIXEL_X`, `yoffset = h + drawY + SUBPIXEL_Y`,
  `SUBPIXEL_X = -0.5`, `SUBPIXEL_Y = -0.375`(`mgacontext.h:306`).
- `z` 는 `depth_scale` 로 미리 곱해져 있다(1/0xffff, 1/0xffffff, 1/0xffffffff —
  `mga_xmesa.c:364`).
- `mgavb.c:73`(`TEX0_4`)은 4 성분 텍스처 좌표일 때 **rhw 에 q 를 곱하고 tu/tv 를
  q 로 나눈다.**

W2-2 에서 픽셀이 어긋나면 **이 다섯이 먼저 의심할 것**이지 형식이 아니다.

### Mesa 출처

`X410src-1.tgz` 에는 Mesa 코어가 없어 버전 문자열을 못 뽑았다. 대신 이 드라이버가
손대는 내부가 우리 트리에 있다 — `VB->Win`(`vb.h:248`), `Spec`(`:252`),
`ClipMask`(`:257`), `TexCoordPtr`(`:229`), `Count`(`:212`).

**이것은 API 호환이지 같은 버전의 증명이 아니다.** 2 판은 "우리가 포팅한 그
Mesa 에 대고 짜여 있다" 고 적었는데 과장이었다. 실용적 뜻은 남는다: W2-5 에서
`mgavb.c` 의 채우기 코드를 거의 그대로 읽을 수 있다.

## 10. 할당 — 2 판이 엉뚱한 둘을 비교했다

2 판은 사다리꼴 배치(23,868)와 WARP 페이로드(17,280)를 더해 24,576 바이트
클라이언트 영역과 비교하고 "안 들어간다" 고 했다. **비교 대상이 틀렸다** —
§6 이 정점을 **커널 소유** 메모리에 두라고 하므로 40 KiB 반쪽 문제다.

```
정점 96 바이트/삼각형 (3 x 8 dword)
배치 고정 헤더         108 바이트 (magic, version, triCount, state)
클라이언트 창          (24576 - 108) // 96 = 254 삼각형, 남는 84 바이트
커널 반쪽              40960 // 96 = 426 삼각형
teapot 한 판(981)      클라이언트 창이 한계이므로 네 번 올려야 한다
```

**3 판의 256 과 "커널이면 세 배치" 는 둘 다 틀렸다.** 256 은 헤더를 0 으로 놓고
나눈 값이고, 우리 배치에는 magic·version·triCount·state 로 **108 바이트** 헤더가
있다(그래서 지금 사다리꼴 배치가 `108 + 132 x 180 = 23,868` 이다). 그리고 커널
반쪽이 426 을 담더라도 **클라이언트가 한 번에 254 개밖에 올리지 못하므로**
업로드 창이 병목이고 네 번이다. 커널 스테이징을 키워도 mmap 창을 바꾸지 않으면
그 수는 줄지 않는다.

**"평균 배치 76 삼각형" 도 이 표에서 뺐다.** 그 값은 오프라인 데모의
`1962 / 26` 에서 왔고 glwin 의 값이 아니다. §4 가 이미 같은 이유로 왕복 수를
철회했다.

**"할당 위기는 없다" 는 아직 주장할 수 없다.** 요청 산술이 그것을 증명하지
않는다 — 기존 명령 할당이 잡힌 뒤에 실제로 저메모리에서 **동시에** 잡히는지,
물리 연속인지, 남은 아레나가 얼마인지를 재야 한다. `IOMallocLow` 64 KiB 상한은
드라이버 주석이 적은 값이지 할당기 구현이나 실측이 아니다.

**2 판이 놓친 진짜 제약 셋:**

- **프리미티브 정수배 — 하드웨어 요구가 아니라 우리가 고르는 계약이다.**
  참고 DRM 은 `buf->used` 를 그대로 길이로 쓰고 나머지 검사를 하지 않는다
  (`mga_state.c:659`, `:681`). 그러니 "정수배여야 한다" 는 3 판의 단정은 근거가
  없다. **새 드라이버가 온전한 프리미티브만 받겠다고 정하는 것**이고, 그러면
  primsz 24 dword = 96 바이트에 대해 `40960 % 96 = 64`, `65536 % 96 = 64` 이라
  지금 두 영역 다 배수가 아니다. 하드웨어가 실제로 어떻게 구는지는 canary 를 둔
  단발 시험으로만 갈린다 — 정확한 레코드, 레코드+꼬리, 레코드−꼬리 셋.
- **`IOMallocLow` 는 한 요청을 64 KiB 로 제한한다**(`:231`). 동작하는 WARP
  경로는 영구 할당이 **셋** 필요하다: 지금의 64 KiB 명령 블록, 18,432 바이트
  마이크로코드(§2 에서 보았듯 지금은 해제된다), 정점 스테이징.
- 저메모리 예산. 3 판은 마이크로코드를 **원본 바이트**로 더했는데, 할당기가
  페이지로 올림한다(`:6784`, `PAGE_SIZE` 8192): `18,432 → 24,576`. 그래서
  `65,536 + 24,576 + 17,280 = 107,392` 바이트이지 101,248 이 아니다.

## 11. 무엇이 함께 깨지는가

**데모의 GL 코드는 안 고쳐도 된다. 계측은 고쳐야 한다.** `glwin` 은 백엔드
호출이 넷뿐이고 앞의 셋은 2D 전달이라 무관하다. `teapot` 은 열둘을 부르고
상당수가 사다리꼴/배치 모델을 전제한다.

**2 판의 오류 정정 — `Unsupported` 는 0 이 되지 않는다.** 2 판은 "WARP 가
셋업하면 446 이 0 이 된다" 고 적었다. **틀렸다.** `FXBNDRY` 가 부호 없는
16 비트인 것은 **레지스터의 성질**이고(`REMAINING_WORK.md:4457`) WARP 도 같은
레지스터에 쓴다. 더 나쁜 것은 **CPU 가 엣지를 계산하지 않으므로 예심조차 못
한다**는 것이다. 참고 클라이언트가 이 문제를 안 겪는 이유는 X11 drawable 이
`drawX >= 0` 이고 Mesa 가 뷰포트로 클립하기 때문이지 WARP 가 해결해서가 아니다.
**미검증** — x = −50 인 정점 하나를 격리된 오프스크린에 WARP 로 그려 경로 B 의
소프트웨어 재생과 열을 비교하면 갈린다.

**`InjectRefusal` 의 진짜 파손 지점은 magic 이 아니다.** 정점 배치에도 magic 은
있다. 깨지는 것은 하류다: 배치 단위 verdict 를 받은 narrowing 이 소스 삼각형
단위로 재생하는데, 그 사상이 `pendSrc[].firstTrap` — **사다리꼴 인덱스**다
(`OpenStepMGAMesaHook.c:993`). 정점 경로에는 사다리꼴이 없으므로 §3-65 의
narrowing 기계 전체를 다시 지어야 한다.

## 12. 계약과 검증 — W2-4 가 대체해야 하는 것

지금 격리는 **사다리꼴마다의 산술 증명**이다: `E_TRIROW`, `E_TRICOL`,
`E_TRISLOPE`, `E_TRICROSS`, `E_EDGEDIV`, `E_TRISGN`, `E_TEXCOORD`, `E_TEXSIZE`,
`E_TRIEMPTY`(`hw3d/OpenStepMGAHW3D.h:96-112`), 목적지·깊이·텍스처 원점, 피치,
행 수, 엣지 워크를 커널이 계산해 가둔다(`hw3d/OpenStepMGAHW3D.c:323,389,461`).

정점만 보면 커널은 `AR0..AR6`/`FXBNDRY`/`YDSTLEN` 을 **계산할 수 없다.** 카드가
한다. 무엇이 남고 무엇이 사라지는지를 함수 단위로 적으면:

| 오늘의 보증 | 정점 계약에서 |
| --- | --- |
| `osmgaHW3DReach`(`:16`) — 목적지·깊이·텍스처·스테이징의 바이트 격리 | **남는다.** 선언된 객체 전체를 보수적으로 가둘 수 있다 |
| 배치 파싱·상태 검증(`:227`) — magic, ABI, 개수, 형식, 피치, 원점, 크기 | **남는다.** 직접 대응이 있다 |
| `E_TRIROW`, `E_TRICOL` | **사라진다.** 실제 시작 행·행 수·초기 `FXBNDRY` 는 셋업 결과다 |
| `E_TRISLOPE`, `E_EDGEDIV`, `E_TRISGN` | **사라진다.** 엣지 계수·제수·방향이 셋업 결과다 |
| `E_TRICROSS` — 행마다 엣지가 안 넘는가 (`osmgaHW3DStep`, `:616`) | **사라진다** |
| `E_TEXCOORD` — 덮인 픽셀의 실제 도달 (`osmgaHW3DRatioOK`, `:842`) | **사라진다** |
| `E_TRIEMPTY` — 셋업이 픽셀을 하나라도 내는가 (`:1030`) | **사라진다** |

`osmgaHW3DRatioOK`(`:53`), `osmgaHW3DQAt`(`:79`), `osmgaHW3DStep`(`:90`)은
**사다리꼴의 셋업 계수와 실제 걷는 스팬을 먹는다.** 정점 계약에는 그 입력이
없다.

**그래서 §12 가 아래에 적는 "보수적 텍스처 도달 범위" 는 아직 검증기 설계가
아니다.** 유한한 `tu/tv/rhw` 의 경계는 계산할 수 있지만, 그것을 **덮인 픽셀의
도달 보증**으로 바꾸는 것은 CPU 셋업을 되살리지 않는 한 **정책이지 증명이
아니다.** 커널이 좌표 한계를 강제하면 위험은 줄지만, 마이크로코드가 무엇을
만들어내는지는 증명하지 못한다. 그 구분을 계약 문서에 명시해야 한다.

새 계약이 정의하고 검증해야 하는 것:

- 유한하고 경계 있는 `x/y/z/rhw/tu/tv` — **NaN 과 무한대를 명시적으로 거부**
- 목적지·깊이·텍스처 원점, 크기, 피치, 형식
- **원근 보간·clamp/repeat·필터링 하의 보수적 텍스처 도달 범위.** 지금 텍스처
  안전 논증은 셋의 결합이다 — 커널 소유 `CLAMPUV`, 그리는 픽셀마다 좌표가
  음수가 되지 않음을 검증기가 확인, 그리고 실측이 "여덟 텍스처 스팬까지" 만
  성립한다는 것. 가운데가 사라진다. `tu0 = 1e6` 인 정점은 아무도 잰 적 없는
  영역이다.
- 파이프 인덱스와 레코드 크기의 합치
- 커널 소유 클립과 `DWGCTL.CLIPDIS` 강제 해제
- 넘침 없는 SEC 시작/끝 구성과 할당 수명

**호스트 시험 코퍼스는 좁아지지 무의미해지지 않는다.** 3 판은 "무의미해진다"
고 썼는데 과했다. `hw3d/test-hw3d-validate.c`, `test-hw3d-reach.c`,
`mesa/test-mesa-trapezoid.c` 는 **남는 사다리꼴 경로의 회귀 그물로 계속 유효**
하고, 정점 경로에도 호스트에서 시험할 것이 있다 — ABI 파싱, 정점 포장, 상태
라우팅, 유한/범위 검사, 주소 산술, 스테이징 복사, 1 차 DMA 로 내보낼 상태.

**호스트에서 못 하는 것은 하나다: 셋업 결과.** 그것이 마이크로코드 안이다.
헤더 첫 문단의 방법 — *"the validation can be tested where a mistake costs
nothing"* — 이 그 한 조각에만 안 통한다.

**20 장면 게이트에 대한 3 판의 서술도 틀렸다.** 그 게이트는 CPU 가 만든 명령
바이트를 비교하는 것이 아니라 **그려진 덤프를 바이트 단위로** 비교한다
(`docs/REMAINING_WORK.md:2878`, `tools/check-matrox-track-identity.sh`). 그러니
WARP 경로도 **출력 이미지 동일성 게이트는 건널 수 있어야 한다.** 래스터화 규약이
정당하게 다른 자리가 있다면, 그때 필요한 것은 게이트를 버리는 것이 아니라
**이름 붙인 허용 오차나 픽셀별 오라클**이다.

**체크박스와 ABI 버전.** `OSMGA_HW3D_VERSION` 은 9 이고 프로브가 **정확히
일치**를 요구한다(`mesa/OpenStepMGAMesaProbe.c:145`). W2-4 가 `OSMGAHW3DBatch` 를
바꾸면 버전이 오르고, **이미 출하된 버전 9 라이브러리**는 새 드라이버에서 폴백이
아니라 아예 거부된다 — 업그레이드 경로에 그 사실을 적어야 한다.

3 판은 여기서 "체크박스는 폴백이 될 수 없다" 고 단정했는데 **과했다.** 버전
일치가 막는 것은 *낡은* 라이브러리와 *새* 드라이버의 조합이다. **함께 올린**
라이브러리는 런타임에 옛 경로를 고를 수 있고, 옛 ABI 를 보존하는 별도 ioctl 을
두는 길도 있다. 즉 체크박스는 가능하되 **라이브러리와 드라이버를 함께 올려야
한다**는 조건이 붙는다.

## 13. 기대하면 안 되는 것

- **T&L 은 여전히 소프트웨어다.** WARP 가 가져가는 것은 셋업이지 변환·조명이
  아니다. §4 의 상한이 반영한다.
- **전달 경로는 안 바뀐다.** 창 데모의 3.7 배는 VRAM→VRAM blit 에서 온다.

## 16. 4 판이 틀렸던 곳 (codex 4 차, 우리 구현 기준, 전부 확인함)

이번 검토는 참고 소스가 아니라 **우리 코드**를 기준으로 물었고, 그래서 앞의 세
번이 못 잡은 것을 잡았다.

| 4 판 | 판정 |
| --- | --- |
| dry-run 을 "커널에 경로를 하나 더" 로 다룸 | **요청할 방법이 없다.** `OSMGAHW3DSubmitBlock` 은 결과만 담고(`hw3d/OpenStepMGAHW3D.h:886`), `OSMGA_IOC_SUBMIT` 는 `OSMGA_IOC_OUT_BIT` 뿐인 **출력 전용**이다(`:893`). 유저랜드가 "이번은 dry" 라고 말할 입력이 없다. 그리고 배치에 필드를 넣으면 버전 게이트가 **W2-(-1) 에서 이미** 걸린다 |
| "clear 를 제외해야 한다" | **맞지만 절반.** 제외 안 하면 빼는 게 아니라 **더한다** — 실패로 보이면 `return 0` 이고 Mesa 가 소프트웨어로 clear 한다(`mesa/OpenStepMGAMesaHook.c:2748`) |
| "검증한 정점을 커널 메모리로 복사" | **순서가 거꾸로.** 검증과 복사 사이에 경주가 남는다. 기존 경로가 이미 옳은 순서를 보여준다 — claim `:5322`, **복사 `:5398`**, 검증 `:5488` |
| 클라이언트 영역 256 삼각형 | **틀림.** 헤더 108 바이트를 뺀 **254** 이고 84 바이트가 남는다 |
| "커널 반쪽이면 세 배치" | **틀림.** 커널이 426 을 담아도 **클라이언트가 254 씩만 올린다.** 업로드 창이 병목이라 네 번이다 |
| "평균 배치 76 삼각형" | **glwin 의 값이 아니다.** 오프라인의 `1962 / 26` 이다. §4 가 왕복 수를 철회한 것과 같은 이유로 뺐다 |
| "마이크로코드는 테스트 전용이고 해제된다" | **균일하지 않다.** 배치 시험은 해제하고(`:7088`) 파이프 시작 시험은 **일부러 남긴다**(`:7216`) — 다만 포인터가 지역 변수라 운영이 되찾을 수 없고, 켠 부팅에서는 그 부팅 내내 샌다 |
| WARP 시험을 "운영으로 옮기면 된다" | **엔진 claim 을 안 잡는다.** 네 루틴 어디에도 `stormLock` 이 없다. claim·정지·완료·복구·래치를 전부 새로 입혀야 하고 `pipePhys[0]` 하드코딩(`:7247`)도 바꿔야 한다 |
| §12 의 "보수적 텍스처 도달 범위" | **아직 검증기 설계가 아니다.** `osmgaHW3DRatioOK`/`QAt`/`Step` 은 사다리꼴 셋업 계수를 먹는데 정점 계약에 그 입력이 없다. `E_TRIROW`·`E_TRICOL`·`E_TRISLOPE`·`E_EDGEDIV`·`E_TRISGN`·`E_TRICROSS`·`E_TEXCOORD`·`E_TRIEMPTY` 이 **증명에서 정책으로** 바뀐다 |
| 고장 주입 | **dry 분기 위에 있으면** 주입 예산만 소비하고 정작 타임아웃은 안 겪는다(`:5337`) |
| `A − B` 의 뜻 | 인코더 직후에 갈라지면 진입 대기와 상태 프로그래밍(`:5588`, `:5701`)은 **A 에만 있다** — `B − C` 가 아니라 `A − B` 에 든다 |

### 아직 남은 측정 부채

- **스테이징 복사 시간.** 최대 24,492 바이트이고 지금 스냅숏 23,868 바이트를
  교체할 수 있어 차이는 624 바이트지만, 걸리는 시간은 아무도 재지 않았다.
- **저메모리 동시 할당.** 요청 산술은 가능성을 증명하지 않는다. 같은 부팅에서

  남은 아레나를 봐야 한다.
- **카운터의 뜻.** `OSMGAMesaHookTraps()` 는 **제출 시도**를 세지 만들어진

## 17. 측정 도구 — 그리고 출하 전에 반드시 할 일

측정용으로 넣은 것이 이제 **넷**이고, **지금은 전부 릴리스 라이브러리와
드라이버에 들어가 있다. 그대로 포장하면 출하된다.**

| 심볼 / 상수 | 어디에 | 무엇 |
| --- | --- | --- |
| `OSMGAMesaHookMeasureArm()` | `mesa/OpenStepMGAMesaHook.c` | arm B/C/D 선택 |
| `OSMGAMesaHookDryCount()` / `...DryStatus()` | 같은 곳 | arm B 양성 확인용 |
| `OSMGAMesaProbeSubmitDry()` | `mesa/OpenStepMGAMesaProbe.c` | dry ioctl 래퍼 |
| `OSMGA_IOC_SUBMIT_DRY` + `runHW3DSubmitDry:` | `hw3d/OpenStepMGAHW3D.h`, 드라이버 | 커널 쪽 dry 경로 |

### 완료 (2026-08-28)

**스위치는 하나가 아니라 둘이고, 그 쌍이 arm B 가 무엇을 필요로 하는지에 대한
정직한 진술이다.**

| 스위치 | 무엇을 켜는가 |
| --- | --- |
| `OSMGA_MESA_TESTHOOKS` | 라이브러리의 arm 선택기 (arm C·D 는 이것만 있으면 된다) |
| `OSMGA_HW3D_SUBMIT_DRY` | **ioctl 자체** — 헤더의 명령 번호, 드라이버의 핸들러, 프로브의 래퍼 |

arm B 는 **둘 다** 필요하다. arm 을 가진 라이브러리를 **출하 드라이버**에 물리면
답하지 않는 명령을 보내게 되기 때문이다. 스위치를 하나로 뭉쳤다면 그 조합이
조용히 실패했을 것이다.

릴리스에서는 `OSMGA_ARM(n)` 이 **상수 0** 이라 모든 검사가 컴파일 단계에서
사라진다. "아무도 설정하지 않는 변수" 보다 강하다 — **설정할 변수가 없다.**

거부 목록에 네 개를 더했다(`tools/build-matrox-mesa.csh`,
`pkg/build-accel-pkg.sh`, `pkg/verify-accel-pkg.sh`). 빌더는 **양방향**으로
검사한다: 릴리스에 있으면 거부, 테스트에 없으면 거부 — 조용한 빌드 실패가
깨끗한 릴리스로 읽히지 않도록.

**드라이버 쪽은 다르게 다뤘고, 그 차이가 핵심이다.** `OSMGA_IOC_SUBMIT_DRY` 는
심볼이 아니라 **번호**다. 기계 위 아무 프로세스나 보낼 수 있다. 남겨 두면
라이브러리 없이도 제출 경로를 검증·인코딩까지 — 엔진 락을 잡고 공유 스냅샷을
쓰면서 — 돌릴 수 있다. 그래서 **핸들러 자체를 뺐다.** 게이트가 꺼진 드라이버는
이 명령을 모르는 명령처럼 답한다. 명령 **번호 4 는 예약으로 남긴다** — 지우면
나중 명령이 4 를 재사용해 옛 클라이언트에 다른 뜻이 된다.

`OSMGA_HW3D_VERSION` 은 9 그대로다 — 구조체가 안 움직였으므로 프로브의
정확일치 게이트는 안 걸린다.

**양성 확인 (주장이 아니라 측정):**

```
드라이버   413,512 -> 413,268 바이트   -244, 빠진 핸들러 크기
릴리스 오브젝트   MeasureArm/DryStatus/DryCount/ProbeSubmitDry = 0 0 0 0
테스트 오브젝트   같은 넷 = 1 1 1 1
양쪽 모두        InjectRefusal = 1   (출하 기능이므로 남아야 한다)
```

측정 팔은 사라지지 않고 **`glwin_arm`** 으로 옮겼다
(`tools/build-matrox-tests.sh`) — 테스트 라이브러리에 링크되는 별도 바이너리다.
`glwin` 은 데모 패키지가 출하하는 그 바이너리로 남는다.

## 18. 측정 결과 (2026-08-28) — §3 과 §4 가 이것으로 대체된다

**게이트가 통째로 막혀 있다는 4 판까지의 전제가 틀렸다.** 빌더는
`osmgaMesaTriangle` 에서, 제출은 flush 에서 돈다 — **다른 함수**다. 그래서
arm C 와 arm D 는 훅에 스위치 하나(`OSMGAMesaHookMeasureArm`)만 넣으면 되고
**커널 변경도 ABI 변경도 재부팅도 필요 없다.** ABI 문제는 arm B 하나에만
해당한다.

- arm C: 사다리꼴을 만들어 쌓되 제출하지 않고 버린다
- arm D: 빌더 앞에서 돌아온다 (Mesa 의 평가자·변환·조명은 이미 끝난 뒤다)

### 측정

800×600 창, 1600×1200 화면, teapot 하나, 다른 것 없이, 셀마다 한 번씩
직렬로. **사다리꼴 수는 `OSMGAMesaHookTraps()` 로 실측했다** — 4 판이 추정으로
적었던 값이다.

| grid | traps/frame | A draw | C draw | D draw | C−D | A−C |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 1,032.0 | 8.47 | 3.89 | 1.29 | 2.60 | 4.58 |
| 4 | 1,831.8 | 13.05 | 6.50 | 2.07 | 4.43 | 6.55 |
| 6 | 3,933.1 | 25.14 | 13.39 | 4.24 | 9.15 | 11.75 |

사다리꼴 수에 대한 회귀, **피팅 오차 1.2% 이하**:

```
D    기하 + 훅   = 0.2222 ms + 1.0201 us x traps   (오차 1.2%)
C-D  빌드        = 0.2834 ms + 2.2554 us x traps   (오차 0.4%)
A-C  ioctl 전체  = 2.0257 ms + 2.4721 us x traps   (오차 0.1%)
```

### grid 4 에서 draw 13.05 ms 의 내역

| | 고정 | 삼각형당 | 합 |
| --- | ---: | ---: | ---: |
| Mesa 기하 + 훅 진입 | 0.22 | 1.87 | **2.09** |
| CPU 사다리꼴 빌드 | 0.28 | 4.13 | **4.41** |
| ioctl (커널 + 실행 + fill) | 2.03 | 4.53 | **6.55** |

### 그래서 WARP 가 없앨 수 있는 것

- **CPU 빌드 4.41 ms — 확정.** 이것이 호스트 쪽에서 사라진다.
- **커널의 삼각형당 몫 4.53 ms — 아직 안 갈렸다.** 그 안에 검증·인코딩(줄일 수
  있음)과 엔진 실행(못 줄임)이 섞여 있다. **arm B 가 필요한 유일한 이유가
  이것뿐이다.**
- 못 없애는 것: 기하 2.09 ms, ioctl 고정 2.03 ms.

프레임 20.92 ms (47.8 fps) 기준:

```
빌드만 없애면              16.51 ms = 60.6 fps
삼각형당 커널 몫까지 전부   11.98 ms = 83.5 fps   <- 물리적 최선, 도달 불가
```

### 4 판이 미측정으로 남긴 것들이 갚였다

| §16 의 부채 | 지금 |
| --- | --- |
| 프레임당 사다리꼴 수 | **1,831.8** (grid 4). 4 판의 "0~1,962" 범위 안이고, 소스 삼각형 979 개당 1.87 개 |
| 엔진의 프리미티브당 비용 | **삼각형당 2.47 us 를 넘을 수 없다** — ioctl 전체의 기울기가 그 값이고 커널 작업이 그 안에 함께 있다. 4 판 감도 분석의 5.0 us 칸은 배제된다 |
| fill 의 실측 | ioctl 항의 절편 **2.03 ms**. clear 에서 역산한 0.37 ms 가 아니다 — 절편에는 fill 말고도 제출당 고정비가 들어 있으므로 이것은 **fill 의 상한**이다 |
| 배치 수 | **프레임당 32 개** (grid 3·4·6 에서 모두 32). 4 판이 쓴 "13 회" 도 "65 블록" 도 아니다 |

### 남은 부채

- `A − C` 안에서 **커널 작업과 엔진 실행의 비율.** arm B 가 있어야 갈린다.
- 스테이징 복사 시간, 저메모리 동시 할당.

### 착수 판정

**빌드 4.41 ms 는 프레임의 21% 이고 이것만으로 47.8 → 60.6 fps 다.** "작은
조각을 쫓는 프로젝트가 아니다" 를 이제는 **주장할 수 있다** — 4 판이 철회했던
그 문장이 측정으로 돌아왔다.

다만 착수 불가의 **다른 이유들은 그대로다**: 2 차 DMA 완료 판정 부재(§6),
엔진 리셋 없음(§6), 격리 증명이 정책으로 바뀌는 것(§12), 그리고 미해결
프리즈(§7). 바뀐 것은 **"할 값어치가 있는가" 가 풀렸다**는 것이고, "안전하게 할
수 있는가" 는 아직이다.

## 19. arm B — 마지막 항이 갈렸다, 그리고 §3 이 옳았다 (2026-08-28)

§18 이 남긴 부채는 하나였다: `A − C` 안에서 **커널 작업**과 **엔진 실행**의
비율. arm B 가 그것을 잘랐다. **다만 자른 자리가 §18 이 기대한 자리가
아니었다** — 이 절의 첫 판은 그 사실을 틀리게 적었고, codex 5 차 검토가
잡았다. 정정본이다.

### 19.1 무엇이 arm B 인가

`OSMGA_IOC_SUBMIT_DRY` — 커널이 제출 블록을 **평소와 똑같이 검증하고
인코딩한 다음**, 첫 진입 대기 직전에 돌아온다(`:5622`).

### 19.2 양성 확인 — 두 가지로 했다

dry 제출이 거부되거나 빈 리스트를 만들면, 일어나지도 않은 검증을 잰 값을
믿게 된다. 그래서 두 가지를 봤다.

```
glwin: arm B check: 1980 dry submissions, last status 0
glwin: per frame: dwords 38105 (20.8 per trap), spins 0 (0 of 33 submits spun)   <- arm B
glwin: per frame: dwords 38055 (20.8 per trap), spins 1652 (max 777, 33 of 33)   <- arm A
```

**두 번째 줄이 결정적이다.** `status 0` 은 마지막 한 번만 남고, dry 분기는
인코더가 길이 0 을 돌려줘도 성공을 보고한다(codex 지적, 코드로 확인). 그런데
**arm B 가 인코딩한 리스트 길이가 arm A 와 0.11% 안에서 같다** — 프레임당
38,102 대 38,060 dwords, 사다리꼴당 둘 다 20.8. 빈 인코딩도, 짧은 경로도
아니다. `sub->dwords` 는 dry 핸들러가 `osmgaHW3DLast[2]` 에서 그대로 실어
보내므로(`:2405`) 이 값은 커널이 실제로 만든 것이다.

그리고 **spins 0 대 1652** 가 arm B 가 정말로 엔진 앞에서 멈췄음을 보인다.

**여기까지 오는 데 두 번 틀렸고 둘 다 내 코드였다.**

1. dry 결과를 평소 rc 처리에 흘려보냈다 → 8 프레임 만에 가속 회수.
   **codex 가 4 차에서 경고한 그대로** — 세 번째 결과가 전 경로를 관통해야
   한다. 지금은 rc 를 0 으로 강제한다.
2. `goto submitDone` 이 `stormBusy = NO` 를 뛰어넘어 엔진을 영구 busy 로
   남겼다. 데모가 CPU 0:00 으로 멈췄다. 레이블을 해제 코드 앞으로 옮겼다.

### 19.4 **정정 — `A − B` 는 "엔진 실행" 이 아니다**

이 절의 첫 판은 `A − B` 를 "엔진 실행 + 완료 대기" 라고 적었다. **틀렸고,
§3 이 이미 옳게 적어 둔 것을 내가 뒤집은 것이다.** §3 은 이렇게 썼다:

> 인코더 직후에 갈라지면 진입 대기와 상태 프로그래밍(`:5588`, `:5701`)은
> **B 에 없고 A 에 있다.** 그러니 그 둘은 `B − C` 가 아니라 `A − B` 에
> 들어간다.

dry 가 건너뛰는 것 중 **엔진 시간이 아닌 호스트 작업**을 전부 세면:

| 건너뛰는 것 | 어디 | 무엇 |
| --- | --- | --- |
| 사전 idle 대기 | `:5627` | MMIO 폴링 |
| DMA 정숙 폴링 | `:5664` | MMIO 폴링 |
| FIFO 진입 대기 | `:5683` | MMIO 폴링 |
| 시저 교집합·빈-시저 조기탈출 | `:5709` | CPU |
| MMIO 상태 방출(클립·피치 등) | `:5740` → `:1606` | MMIO 쓰기 |
| **DMA 리스트 체크섬 배리어** | `:5752` | **CPU, 리스트 전체를 읽는다** |
| 도어벨 쓰기 | `:5757` | MMIO 쓰기 |
| 완료 폴링·트랩 확인 | `:5783` | MMIO 폴링 |
| 타임아웃 복구 폴링 | `:5835` | MMIO 폴링 |
| 최종 idle 대기 | `:5893` | MMIO 폴링 |

측정으로 두 항의 크기를 잡을 수 있다:

```
스핀:   프레임당 1,652 회, 제출당 50.1 회, 최대 778, 33/33 제출이 스핀함
배리어: 프레임당 38,060 dwords = 148.7 KiB 를 한 번 훑음
```

MMIO 읽기 한 번을 0.5 / 1.0 / 1.5 / 2.0 us 로 놓으면 스핀만으로
`A − B` 의 **17.8% / 35.5% / 53.3% / 71.1%** 다. 배리어는 캐시 상태에
따라 4.1% ~ 40.9% 다. **둘 다 실측하지 않았다.** 그러므로:

> **`A − B` = 4.65 ms 는 "인코더 이후의 전부" 이고, 그 안에서 엔진이 실제로
> 픽셀을 채우는 몫은 아직 갈리지 않았다.** WARP 가 그중 얼마를 못 건드리는지도
> 따라서 아직 모른다.

### 19.5 clear 는 같은 분할을 **재현**하지만 독립 증거는 아니다

```
clear, 엔진 있음 (A,C,D)   3.49 ms  =  7.271 ns/픽셀
clear, 인코더까지만 (B)    0.09 ms  =  0.188 ns/픽셀   (2.58%)
차                         3.40 ms  =  7.083 ns/픽셀
```

§4 가 "증명이 없다" 고 적어 둔 7.25 ns/px 가 0.29% 오차로 재현됐다.
**픽셀 위치당 값이 맞는 척도다** — clear 는 두 번 blit 하는 것이 아니라
사각형을 삼각형 두 개로 만들어 **한 배치, 한 래스터 패스**로 색과 깊이를 같이
쓴다(`OpenStepMGAMesaHook.c:2789` 에서 `OSMGAMesaBuildTriangle` 두 번, 제출은
한 번). 그러니 3.54 ns/plane-write 는 "두 번째 패스" 가 아니라 다른 통계다.

**다만 이것은 독립 확인이 아니다.** 같은 dry 분기를 쓰므로 §19.4 가 나열한
MMIO·폴링·배리어를 똑같이 빼먹는다. 확인해 주는 것은 "인코더 이후가
지배적이다" 이지 "그 전부가 하드웨어다" 가 아니다.

### 19.6 arm B 화면에는 주전자가 없다

arm B 는 clear 도 삼각형도 실행하지 않으면서 소프트웨어 대체도 막는다. 그런데
`hookDrawn` 은 합성 성공(`OpenStepMGAMesaHook.c:861`)에서 그대로 올라간다.
**그러니 `drawn 979.1` 은 장부이지 픽셀이 아니고, 화면에는 초기화되지 않은
앱 버퍼가 present 될 뿐이다.** 타이밍이 오염되지는 않는다 — 검증·인코딩은
제출된 레코드만 보고 목적지 픽셀을 안 보며, arm B 에는 깊이 기각이 일어날
엔진 실행 자체가 없다. `present` 가 네 arm 모두 3.70 인 것이 내용 비의존을
보인다.

### 19.7 정정 — 거부 하나로 `drawn` 차이를 설명할 수 없다

첫 판은 `drawn` 이 A 978.9, B 979.1 인 것을 "그 배치가 Mesa 로 떨어진 흔적"
이라고 적었다. **틀렸다.** 0.2/프레임 x 약 1,038 프레임 = 208 소스인데
거부는 한 번이었다. 실제 원인은 **런 사이 방향 표본 차이**다 — `traps` 도
A 1831.3 / B 1832.5 / C 1833.0 으로 갈리고, arm A 한 런 안에서도
1831.3 → 1831.8 로 흐른다.

거부 자체(`status 22 verdict 17` = `OSMGA_HW3D_E_TRICROSS`)는 설계대로
처리됐다: 훅이 배치를 좁혀 그 소스만 소프트웨어로 재생하고, 회수는 일어나지
않는다. **약 30,000 배치 중 한 번이므로 측정에 미치는 영향은 무시할 수준이지만,
격리 증명이 아직 살아 있다는 증거이기도 하다** — §12 가 이것을 정책으로
바꾸려 한다는 점을 기억할 것. 다만 그 거부가 어느 창에 떨어졌는지는 모른다.

### 19.8 첫 창을 고른 것 — 결론은 안 흔들리지만 사후 선택이다

네 창 전부를 싣는다(누적 평균, ms):

| arm | 창1 | 창2 | 창3 | 창4 | 최대 timed-span |
| --- | --- | --- | --- | --- | --- |
| A draw | 13.11 | 13.44 | 13.32 | 13.27 | 20.94 → 173.06 |
| B draw | 8.46 | 8.46 | 8.54 | 8.52 | 12.65 → 70.12 |
| C draw | 6.48 | 6.48 | 6.48 | 6.67 | 14.12 → 197.25 |
| D draw | 2.10 | 2.10 | 2.10 | 2.10 | 9.80 |

첫 창으로 계산하면 빌드 4.38 / 커널 1.98 / 나머지 4.65, 최종 누적으로 하면
4.57 / 1.85 / 4.75 다(+4.3% / −6.6% / +2.2%, 합계 +1.5%). **결론은 안
바뀐다.** 그러나 **뒤 창의 이상치를 보고 나서 앞 창을 고른 것이므로 사후
선택이 맞다**(codex 지적, 인정). 다음 측정부터는 창을 미리 정하고 절사평균을
쓰고 원자료를 함께 싣는다.

### 19.9 WARP 가 없애는 것이 아니라 **바꾸는** 것

첫 판은 "빌드 4.38 이 사라진다" 고 적었다. **`C − D` 는 대체 없이 증발하는
일이 아니다.** WARP 경로도 정점 레코드를 채우고, 상태 호환 배치와 flush 경계를
유지하고, 제출 영역으로 복사하고, 커널이 정점을 검증하고, WARP 상태를
프로그래밍해야 한다.

바이트로 보면 이렇다:

```
지금  : 38,060 dwords 인코딩 = 148.7 KiB  (사다리꼴 1,832 개, 개당 20.8 dwords)
WARP  : 979.1 x 3 = 2,937 정점 x 8 dwords = 23,498 dwords = 91.8 KiB
        + 먼저 채워야 할 호스트측 정점 구조 114.7 KiB (40 B/정점)
-> 전송량은 38.3% 줄지만 사라지지 않는다
```

**측정된 정점 패킹 비용은 없다.** 그러므로 아래 표의 WARP 행은 **패킹이
공짜라는 가정 위에 있고, 그것은 상한이다.**

| 시나리오 | draw | 벽시계 | fps | 배수 |
| --- | --- | --- | --- | --- |
| 지금 (실측) | 13.11 | 21.20 ms | 47.2 | 1.00 |
| **엔진을 호스트와 겹침 (WARP 없이)** | 8.46 | 16.55 ms | **60.4** | **1.28** |
| WARP, 패킹 공짜 가정 (상한) | 6.75 | 14.84 ms | 67.4 | 1.43 |
| 바닥 (기하 + present) | 2.10 | 10.19 ms | 98.1 | 2.08 |

fps 는 **벽시계 주기**(계측 구간 + unaccounted 0.70)로 낸다. 첫 판의 표는
계측 구간을 "프레임" 칸에 적고 fps 는 벽시계로 냈다 — 산술은 맞았지만 칸
이름이 틀려 읽는 사람이 `1000/16.12 = 62.0` 을 기대하게 만들었다(codex 지적).
지금 표는 두 칸이 같은 기준이다.

### 19.10 **가장 큰 발견은 WARP 가 아니다**

`33 / 33` 제출이 스핀한다. 제출은 **동기이고 호스트를 막는다** — 커널은
도어벨을 울린 뒤 완료까지 MMIO 를 폴링하고, 그동안 CPU 는 다른 일을 하지
않는다.

```
프레임당 호스트 작업   8.46 ms  (기하 2.10 + 빌드 4.38 + 인코딩 1.98)
프레임당 인코더 이후   4.65 ms  (그 대부분을 막힌 채 보냄)
직렬인 지금           13.11 ms
완전히 겹치면          8.46 ms  = max(호스트, 나머지)
```

**겹치기만 해도 1.28 배이고, 이것은 마이크로코드를 한 줄도 안 쓴다.** WARP 의
상한 1.43 배와 같은 자릿수다. 그리고 **둘은 곱해진다** — WARP 로 호스트 몫이
줄면 겹침의 이득은 오히려 커진다.

이것은 §7 의 프리즈 문제와 §6 의 2 차 DMA 완료 판정 부재와 **같은 문제의 뒷면**
이다: 완료를 판정할 방법이 폴링밖에 없어서 겹칠 수가 없다. 그러니 순서는
**"완료 판정을 먼저, WARP 는 그 다음"** 이다.

### 19.11 아직 안 갈린 것 — 정직하게

- `A − B` 안의 **배리어 / MMIO 쓰기 / 엔진에 막힌 시간** 세 갈래. **"스핀" 을
  네 번째 항으로 세면 안 된다** — 폴링하는 동안 엔진이 돌므로 스핀 시간과 엔진
  시간은 같은 구간이고, 더하면 이중 계산이다(codex 6 차, §21.2 에서 채택).
  §19.4 의 감도 범위가 너무 넓어서 WARP 의 실제 상한을 못 정한다.
  **다음 측정이지만 유저랜드로는 못 한다 — §21.3.**
- 정점 패킹 비용. 재기 전에는 1.43 배가 상한이지 예상치가 아니다.
- teapot 의 fragment 면적. clear 의 7.083 ns/px 를 teapot 에 대입하면 안 된다.
  **시저 스윕으로 재려 하지 말 것 — §7 금지 조합이다(§4 의 인용 상자, §21).**
- 스테이징 복사 시간, 저메모리 동시 할당.

### 19.12 착수 판정 — 바뀌었다, 그러나 착수 쪽은 아니다

값어치는 §18 에서 풀렸고 arm B 는 그 값을 **낮췄다**(60.6 → 상한 67.4 fps,
그나마 패킹 공짜 가정). 대신 **WARP 가 아닌 더 싼 1.28 배를 찾아냈다.**

착수 불가 사유는 그대로다: 2 차 DMA 완료 판정 부재(§6), 엔진 리셋 없음(§6),
격리 증명이 정책으로 바뀌는 것(§12), 미해결 프리즈(§7). **그리고 §19.10 은
그중 첫 번째가 성능 문제이기도 하다는 것을 보였다.**

## 21. 일곱 번째 프리즈 (2026-08-28) — 문서가 자기 금지를 어기게 시켰다

### 21.1 무엇을 했고 무엇이 났는가

`A − B = 4.65 ms` 를 더 가르려고 **시저 스윕**을 만들어 돌렸다. 데모에
`scis <h>` 팔을 넣어 h 를 600·400·300·200·120·60·30·12 로 쓸고, 각 점을
16 초씩 돌리며 프레임마다 타이밍 클럭 다섯 개를 읽었다.

**기계가 얼었다. ICMP 도 안 돌아왔다. 전원 재시작이 필요했다.** 스윕은
어느 h 에서 얼었는지도 남기지 못했다 — 출력이 `tail` 뒤에 물려 있어서 통째로
사라졌다.

### 21.2 왜 했는가 — 기전을 적는다

**이 문서가 모순돼 있었다.**

| 어디 | 무엇을 말했나 |
| --- | --- |
| §3 의 마지막 문단 | 시저는 §7 프리즈 조합의 **한쪽**이다 |
| §4 의 두 번째 문단 — 그로부터 **22 줄 뒤** | fragment 면적은 **시저로 쓸어서** 재라 |
| §7 | **`scissor + 계측` 금지**, 이상 시 **재시도 금지** |

(줄번호로 적지 않는다. 이 정정 자체가 §4 와 §7 을 길게 만들어 번호를 밀었고,
썩은 줄번호는 이 저장소가 이미 값을 치른 실패 유형이다.)

§19.11 의 미측정 항목을 갚으려고 §4 를 찾았고, **그것을 허가로 읽고 거기서
멈췄다.** 금지를 찾는 grep 은 돌리지 않았다. 코드에는 `scissor` 를 다섯 번
grep 했고(`hook:1217`, `driver:5700`, `:5740`, `:5714`, `Mesa/scissor.c`)
**문서에는 한 번도 돌리지 않았다.** 한 번만 돌렸으면 183·315·319 가 같은
화면에 떴다.

그리고 §7 은 이 세션에서 **세 번 인용됐다**(§19.12, §20, HANDOFF). 전부
"미해결 프리즈(§7)" 라는 **라벨로만** 썼다. 인용은 읽음의 증거가 아니었다.

codex 교차검토도 받았지만 여덟 개 질문이 전부 **"이 측정이 타당한가"** 였다.
**"이것이 금지된 조합인가" 는 묻지 않았고 프리즈 기록을 주지도 않았다.**
검토자는 못 본 것을 답할 수 없다.

`REMAINING_WORK.md:4019` 의 표가 이 실험이 어느 칸인지 정확히 말한다:

```
scissor 20 / scissor 120 단독        정상
frame 120 inst (계측 단독)           정상
scissor 120 inst                     프리즈 (2회)
scissor 120 i1 (타이밍 두 번만)      프리즈 (1회)
```

**시저 단독도 계측 단독도 안 언다. 둘이 만나야 언다.** 그래서 구현을 아무리
읽어도 위험이 안 보였다 — 그 사실은 문서에만 있었다.

### 21.3 그래서 `A − B` 는 어떻게 가르는가

**codex 6 차의 지적을 채택한다: 스핀과 엔진은 더할 수 있는 두 항이 아니다.**
완료 폴은 `읽기 → 미완 → IODelay → 읽기` 이고 그 루프의 벽시계 시간이 곧
엔진의 남은 시간이다. "스핀 시간" 과 "엔진 시간" 은 같은 구간을 두 번 센 것
이다. 그러니 `A − B` 가 갈리는 것은 이 둘뿐이다:

```
(i)  엔진에 막혀 있는 시간      = 완료 폴 루프의 지속 시간
(ii) 막히지 않은 호스트 작업    = 체크섬 배리어 + MMIO 상태 쓰기 + 도어벨 + 정착 읽기
```

**(ii) 를 재려면 커널 안에 타임스탬프가 있어야 한다. 유저랜드로는 안 된다.**
시저는 이 목적에 쓸 수 없고(§7), 폴 지연 조절은 대상을 바꿔 버린다(`:2063`
이 지연을 늘리면 프레임이 **빨라진다**고 기록한다 — 폴이 자기가 기다리는 DMA
와 버스를 다툰다).

최소 드라이버 변경: **도어벨 전 구간에만** 누적 타임스탬프를 넣는다 — 진입
대기 후, 상태 쓰기 후, 배리어 후. **리스트가 아직 시작되지 않았으므로 이
구간은 엔진과 경합하지 않는다.** 완료 폴 안에는 넣지 않는다. 설치 한 번,
재부팅 한 번, 그 뒤로는 런타임 선택.

### 21.4 프리즈 이전에 얻은 것은 유효하다 (전부 read-only)

`OSMGAHW3DWaits` 텔레메트리, 82,452 회 제출 누적:

| 대기 | 제출당 읽기 | 최대 | 전체 읽기 중 |
| --- | --- | --- | --- |
| pre-idle | **1.00** | 1 | 1.3% |
| fifo admit | **1.00** | 1 | 1.3% |
| quiescence | **1.00** | 1 | 1.3% |
| **completion** | **71.19** | 780 | **94.7%** |
| final idle | **1.00** | 1 | 1.3% |

**네 대기는 언제나 첫 읽기에 만족한다. 대기라 부를 것이 아니라 읽기 한 번이다.**
`A − B` 의 대기는 전부 완료 폴 한 곳에 있다.

명목 모델의 대조(python): 데모 범위 읽기 1,685 회 × (읽기 1.08 + 지연 4.00 µs)
= **8.43 ms/프레임**, 설명해야 할 것은 clear 엔진 3.40 + draw 꼬리 4.65 =
**8.05 ms**. **+4.7%.** 모델은 선다.

> codex 는 `1652 × 4 µs = 6.6 ms > A − B 4.65 ms` 라며 모순이라고 했다.
> **codex 가 clear 의 몫을 못 봤다** — 데모의 스핀 카운터는 clear 제출까지
> 센다. 8.05 로 비교하면 모순이 아니다.

### 21.5 되돌린 것

- 데모의 `scis` 팔: **소스에서 제거**(커밋 전이었다).
- 스윕 스크립트: 삭제.

**재시도하지 않는다.** §3-62 의 판정 그대로다.

## 22. `A − B` 가 갈렸다 — 시저 없이, 드라이버 변경 없이 (2026-08-28)

§21.3 은 "(ii) 를 재려면 커널 안에 타임스탬프가 있어야 한다" 고 적었다.
**틀렸다. 이미 있는 것으로 됐고, 그것을 §17 게이팅 검증 중에 우연히 봤다.**

### 22.1 arm D 가 clear 를 격리한다

게이팅이 끝난 드라이버로 arm D 를 돌려 보니 이렇게 찍혔다:

```
glwin: per frame: dwords 70 (0.0 per trap), spins 680 (max 699, 1 of 1 submits spun)
```

**`1 of 1 submits`.** arm D 는 사다리꼴을 하나도 안 만드니 제출이 **clear 하나
뿐**이고, 그 하나가 프레임당 680 회 스핀한다. 스윕이 얻으려던 교정값이 바로
이것이다 — clear 의 폴 반복 수를, draw 의 것과 **섞이지 않은 채로**.

```
clear 의 읽기      680.5 회/프레임      (텔레메트리는 index+1 을 센다)
clear 의 엔진 시간   3.40 ms            (arm B 가 유효하던 부팅의 실측)
-> 폴 반복당        4.996 us
드라이버의 명목      1.08 + 4.00 = 5.08 us   -> 1.6% 일치
```

**순환이 아니다.** clear 의 반복 수는 draw 를 전혀 내지 않는 팔이 따로 셌다.

### 22.2 그래서 draw 의 폴

```
arm A 전체 읽기        1,556.0 /프레임   (스핀 1,523 + 제출 33)
빼기 clear 의          -680.5
= 32 개 draw 배치의     875.5 회
x 4.996 us            = 4.37 ms/프레임을 엔진에 막혀 보낸다
```

### 22.3 분할

```
A − C  = 6.70 ms   ioctl + 검증 + 인코딩 + 그 뒤 전부
B − C  = 1.98 ms   ioctl + 검증 + 인코딩            [arm B 가 유효하던 부팅]
A − B  = 4.72 ms   인코더 이후 전부
   엔진에 막힘        4.37 ms   92.7%
   막히지 않은 호스트  0.35 ms    7.3%   = 배치당 10.8 us
```

**막히지 않은 호스트 작업은 배치당 10.8 us 다** — 148.7 KiB 체크섬 배리어,
12 개 MMIO 상태 쓰기, 도어벨, 정착 읽기를 **전부 합쳐서**. `A − B` 의 7.3%.

### 22.4 이 값이 기대는 가정 — 명시한다

**clear 의 폴 반복과 draw 의 폴 반복이 같은 값이라고 놓았다.** 같을 이유는
없다: clear 는 큰 채우기 하나이고 draw 는 사다리꼴 ~57 개짜리 배치 32 개이며,
드라이버 자신이 폴 트래픽이 **자기가 기다리는 DMA 와 버스를 다툰다**고
기록한다(`:2045`).

| draw 의 반복 비용이 clear 의 | 엔진에 막힘 | 호스트 나머지 |
| --- | --- | --- |
| 90% | 3.94 ms | +0.78 ms |
| **100%** | **4.37 ms** | **+0.35 ms** |
| 110% | 4.81 ms | −0.09 ms |
| 120% | 5.25 ms | −0.53 ms |

**110% 에서 나머지가 음수가 된다.** 그러니 이 분할이 말하는 것은 정확한
0.35 ms 가 아니라 **"인코더 이후는 거의 전부 엔진 대기이고, 호스트 쪽 잔여는
1 ms 미만이다"** 이다. 그 진술은 표 전체에서 성립한다.

### 22.5 WARP 에 대한 결론 — 다시 낮아진다

WARP 는 CPU 빌드(4.38)와 커널 인코딩(1.98)을 **대체**한다. `A − B` 의 4.72 중
**4.37 은 엔진 대기라 WARP 로도 안 사라진다.** 남는 0.35 조차 배리어와 MMIO 라
정점 경로에도 그대로 있다.

**§19.10 의 결론이 더 강해졌다**: 겹치기(1.28 배)가 WARP(상한 1.43 배, 패킹
공짜 가정)보다 싸고, 겹칠 대상인 4.37 ms 가 실제로 거기 있다는 것이 이제
직접 세어졌다.

### 22.6 §21.3 의 정정

"유저랜드로는 안 된다" 고 적었던 것은 **틀렸다.** 필요한 것은 커널 타임스탬프가
아니라 **제출을 하나만 내는 팔**이었고, arm D 가 이미 그것이었다. 스윕도,
시저도, 재부팅도 필요 없었다. **금지된 실험을 하지 않았어도 답은 나왔을
것이다.**

## 23. 정점 패킹 비용 — 측정했다 (2026-08-28)

§19.11 이 남긴 부채 중 하나이고, **1.43 배가 "예상치가 아니라 상한" 이었던
이유**다. 이제 상한이 아니다.

### 23.1 방법 — §14 와 같은 형태, 하드웨어 무관

`test/openstep-mga-packprof.c`. 장치를 열지 않고, 아무것도 매핑하지 않고,
제출하지 않는다. 시저 없음, 시계는 run 당 두 번.

v->v.rhw = win[3];

곱 하나, 덧셈 둘, 부호 하나, 바이트 넷. 레코드는 40 바이트, union 스트라이드는

### 23.2 결과

같은 일을 여덟 번:

```
0.0178  0.0202  0.0219  0.0242  0.0269  0.0304  0.0321  0.0353  us/정점
최소 0.0178  중앙 0.0255  최대 0.0353     폭 98%
```

**폭이 98% 다.** §14 의 14% 바닥보다 훨씬 나쁘고, 이유는 크기 의존에서
드러난다 — 300 정점 0.0115, 3,000 정점 0.0202, 30,000 정점 0.0544 us.
**캐시에 매인 비용이다**(3,000 정점 x 64 B = 188 KiB). 그래서 중앙값이 아니라
**범위를 들고 다닌다.**

### 23.3 프레임당, 그리고 예산 대비

| 어디에 후크하느냐 | 정점/프레임 | 패킹 비용 |
| --- | --- | --- |
| Mesa `TriangleFunc` (삼각형당 3) | 2,937 | **0.052 ~ 0.104 ms** |
| 정점 버퍼 (공유 정점 한 번) | ~539 | 0.010 ~ 0.019 ms |

WARP 가 없애는 예산은 CPU 빌드 4.38 + 커널 인코딩 1.98 = **6.36 ms** 다.

```
패킹 / 예산 = 0.8% ~ 1.6%
```

### 23.4 그래서 상한이 예상치가 됐다

```
패킹이 공짜라 가정 (옛 상한)   draw 6.82 -> 67.1 fps   x1.427
패킹 실측, 최악값             draw 6.92 -> 66.6 fps   x1.417
```

**1.43 배와 1.42 배다.** 패킹은 WARP 의 이득을 갉아먹지 않는다.

> **착수 전에 세운 걱정이 크게 빗나갔다.** §19.11 을 정리하며 "정점 하나가
> 사다리꼴 하나(2.391 us)만큼만 들어도 7.02 ms 로 예산의 110%" 라고 적었다.
> **실측은 그 68 분의 1 이다.** 사다리꼴 빌드는 에지 워크·나눗셈·클리핑·서브픽셀
> 산술을 하고, 정점 패킹은 여덟 번 저장한다 — 같은 자릿수일 이유가 없었다.
> **비교 대상을 고를 때 "둘 다 정점 하나당" 이라는 것만 보고 하는 일의 크기를
> 안 본 것이다.**

### 23.5 이 측정이 덮지 않는 것 — 명시한다

정점 패킹만 쟀다. WARP 경로에는 더 있다:

- 프리미티브당 WARP 상태·셋업 레지스터 블록
- 배치 경계와 flush 규칙(지금 텍스처 키가 하는 역할)
- 커널의 정점 **검증** — 사다리꼴 검증이 사라지는 대신 생긴다
- 정점 스트림의 제출·완료

**그러므로 "WARP 는 1.42 배" 가 아니라 "패킹은 이득을 갉아먹지 않는다" 가
이 절의 결론이다.** 나머지 항목들은 여전히 미측정이고, 그중 커널 정점 검증은
없어지는 사다리꼴 검증(1.98 ms 의 일부)과 맞바꾸는 것이라 **순증이 아닐 수
있다.**

### 23.6 §19.11 의 부채 갱신

| 부채 | 상태 |
| --- | --- |
| `A − B` 세 갈래 | **갚음** (§22, 92.7% 가 엔진 대기) |
| **정점 패킹 비용** | **갚음 — 예산의 0.8~1.6%** |

| 스테이징 복사, 저메모리 동시 할당 | 미측정 |

## 24. 1 차 스트림 VERTEX 모드 — 조사 결과 **blocker 를 없애지 못한다** (2026-08-28)

W4 §7 이 "2 차 DMA 는 WARP 에 필수가 아니다 — PRIMADDRESS 자체가 VERTEX
모드를 갖는다" 고 적었고, 그것이 맞다면 §6 의 가장 큰 안전 blocker(2 차 DMA
완료 판정 부재)가 **통째로 사라진다.** 1 차의 완료 판정은 이미 있고 A0 이
86,554/86,554 로 검증했으니. 조사했다. **소스 읽기뿐, 하드웨어 무관.**

### 24.1 비트는 실재한다. 전례는 없다.

```
mgaregs.h:585   PDCA_primod_vertex  0x3     <- PRIMADDRESS 의 모드
mgaregs.h:626   SDCA_secmod_vertex  0x3     <- SECADDRESS 의 모드
mgaregs.h:558   OM_dmamod_vertex    0xc     <- OPMODE 의 모드 (bits 2-3)
```

세 곳에 같은 네 값이 있다. 그런데 **세 참조 구현의 PRIMADDRESS 쓰기를 전수로
훑으면 예외 없이 `MGA_DMA_GENERAL` 이다**:

```
mga_dma.c:216   MGA_WRITE(MGA_PRIMADDRESS, head | MGA_DMA_GENERAL)
mga_dma.c:911   MGA_WRITE(MGA_PRIMADDRESS, ...offset | MGA_DMA_GENERAL)
그 외 PRIMADDRESS 등장은 전부 READ (헤드 포인터)
```

정점은 언제나 `SECADDRESS | MGA_DMA_VERTEX` 로 가고, 그 쓰기는 **1 차 명령
스트림 안에서** 이뤄진다(`mga_state.c:679`).

**우리에게 매뉴얼이 없다.** 이 모드의 의미는 헤더의 이름 하나로만 안다.
Windows 드라이버 분석(W1)도 정점이 WARP 에 **어떻게** 도달하는지는 못 밝혔다 —
hot path 가 레지스터 경유라 추적이 중단됐다(`W1 §V-5`).

### 24.2 구조적 이유 — 그리고 이것이 결정적이다

**1 차는 명령 스트림이고 2 차는 페이로드다.** 모드는 run 전체에 걸린다.

우리 완료 판정은 **1 차 목록이 SOFTRAP 명령으로 끝나는 것**에 걸려 있다.
1 차를 정점 모드로 두면 그 run 은 정점을 소비하므로 **SOFTRAP 을 담을 수
없다** — 즉 "이미 검증된 완료 경로를 쓴다" 는 ② 의 전제 자체가 무너진다.

빠져나갈 길은 배치마다 **세 번의 run** 을 CPU 가 순서대로 내는 것뿐이다:

```
1) GENERAL : 상태 + WARP 셋업
2) VERTEX  : 정점
3) GENERAL : 우리가 실제로 검출할 수 있는 SOFTRAP
```

### 24.3 그 대가 — python

제출당 커널 소프트웨어는 실측 **61.9 us** 다(1.98 ms / 32 배치).

| 배치당 run | 프레임당 제출 | 커널 소프트웨어 |
| --- | --- | --- |
| 1 | 32 | 1.98 ms |
| 3 | 96 | **5.94 ms** |

**추가 두 run 이 프레임당 3.96 ms 다. WARP 예산 6.36 ms 의 62% 를 아무것도
그리기 전에 쓴다.**

```
2 차 DMA (run 한 번)        draw  6.92 -> 66.6 fps   x1.417
1 차 정점 (run 세 번)       draw 10.89 -> 52.7 fps   x1.121
```

### 24.4 판정

**② 는 blocker 를 없애지 못하고 옮긴다.**

- 없애려던 것: "2 차 DMA 완료를 판정할 수 없다"
- 대신 얻는 것: "1 차 정점 모드의 완료를 판정할 수 없고, **전례도 문서도
  없다**". 중간 run 은 `SOFTRAPEN` 없이 `ENDPRDMASTS` 만으로 판정해야 하는데,
  **A0 이 검증한 것은 전체 예측이지 그 반쪽이 아니다.**
- 그리고 이득의 62% 를 순서 비용으로 잃는다.

**W4 §7 의 "2 차 DMA 는 WARP 에 필수가 아니다" 는 레지스터 수준에서는 맞고
설계 수준에서는 쓸모가 없다.** 그 문장을 그대로 두되 이 절을 가리키게 한다.

### 24.5 그래서 WARP 의 안전 blocker 는 그대로다

| blocker | 상태 |
| --- | --- |
| 2 차 DMA 완료 판정 부재 (§6) | **그대로.** ② 로 우회 불가 |
| 검증된 리셋·격리 절차 없음 (§6) | 그대로 (`MGA_RST` 는 있고 절차가 없다) |
| 격리 증명이 정책으로 바뀜 (§12) | 그대로 |
| 미해결 프리즈 (§7) | 그대로 |
| `SECADDRESS` 회수 절차 없이 쓰기 금지 (§7) | 그대로 |

**값어치 쪽은 §23 에서 정리됐다(1.42 배, 패킹 포함). 안전 쪽은 한 칸도 움직이지
않았다.** 착수 판정은 여전히 **불가**이고, 이제 그 이유가 오직 안전이다.
