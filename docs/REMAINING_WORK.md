## 0. 지금 어디까지 왔나 (2026-08-24)

3D 가 **GL 1.1 의 래스터화 상태를 거의 다 표현한다.** 아래는 전부 실기에서
잰 것이고, 재지 않은 것은 재지 않았다고 적었다.

| | 상태 |
|---|---|
| 커버리지 | 시험 도형 전부 **규칙과 정확히 일치**, 소프트웨어와도 일치 |
| 색·알파 보간 | 화소 중심 정착 + 반올림. 소프트웨어와 **99% 이상 동일**, 남은 차이는 1 단계 |
| 깊이 보간 | 화소 중심 정착. 남은 계통 오차는 출력 절단 **−0.5 코드** 하나 |
| 공유 변·이음매 | 색·깊이 모두 **이음매 없음**. fan·strip·512 삼각형 메시까지 |
| 혼합 프레임 | 한 프레임 안에 엔진과 소프트웨어가 섞여도 서로 화소를 잃게 하지 않는다 |
| 텍스처 | `GL_RGB`·`GL_RGBA`, `GL_REPLACE`·`GL_MODULATE`, `GL_NEAREST`·`GL_LINEAR`, 감싸기 셋, **원근(q≠1) 포함**. 밉맵은 조사를 마치고 **닫았다** — 아래 |
| 깊이 비교 | **일곱 전부**. `GL_NEVER` 만 거절 — `zmode` 1 은 예약값이지 NEVER 가 아니다(Matrox 해독기) |
| 깊이 쓰기 | **`glDepthMask(GL_FALSE)` 동작**. 접근 유형이 그것이다 — ZI 는 비교하고 쓰고, I 는 비교만. 실측 |
| 블렌딩 | GL 1.1 의 소스·목적지 인자 전부. 엔진 산술을 262144 표본으로 적합(곱 두 번, 더하고, **한 번** 반올림) |
| 알파 시험 | 일곱 전부. **텍스처 스테이지의** 알파를 비교하고, 버린 프래그먼트는 깊이도 안 쓴다 |
| 폴리곤 오프셋 | python 과 정확히 일치 |
| 시저 | 엔진의 목적지 클립(`CXBNDRY`/`YTOP`/`YBOT`)으로. 경계 아홉 점·빈 상자·표면 밖·부분 겹침 전부 소프트웨어와 화소 일치 |
| `glClear` | **엔진 가속**. 512×384 에서 174 → 147 ms |
| 표면 계약 | 호출자의 버퍼를 바인딩 때 **들여온다**. 가속을 놓을 때 깊이를 **보존한다** |

**표현하지 못하는 것**(전부 근거 있음): 밉맵(아래), `GL_NEVER`(예약 인코딩),
`GL_SRC_ALPHA_SATURATE`(인자 8 은 색에 `SRC_ALPHA`·알파에 `ONE` 로 실측됨),
스텐실, polygon smooth/stipple, **깊이만 지우기**(`PLNWT` 미노출).

**밉맵은 미개척이 아니라 닫힌 조사다.** `M1_4D9_MIPMAP_PLAN.md` 가 정본이다.
프래그먼트마다 레벨을 고르는 절반(MIN/MAG 두 필드와 화소 단위 λ)은 실재하고
이미 쓰이고 있으나, **밉맵 비트 자체가 이 경로에서 무력하다**: 네 모드
(`mm1s`·`mm2s`·`mm4s`·`mm8s`)가 아핀과 원근 양쪽에서, 네 비율 전부에서 비밉맵
대응물과 **64/64 화소 동일**하고, 합법적인 텍스처 폭 여덟 가지 어느 `rfw` 도
깨우지 못한다. 왜인지는 **가르지 못했다** — WARP 가 front-end 일 수도 있고,
드라이버가 한 번도 건드리지 않는 레지스터의 전역 상태가 막고 있을 수도 있다.
결론은 교차검토까지 받았다: **이 경로에서 구현하지도 광고하지도 않는다.**
넣으려면 훨씬 큰 별개의 작업이다.

**다음에 할 일의 우선순위**:

1. §3 의 미해결 항목 — 특히 이번에 새로 생긴 §3-28~§3-32.
2. 성능은 §3-32 가 벽을 적어 두었다. 장부를 고쳐서 넘는 벽이 아니다.
3. §1 의 미착수 기능(dual head, VRAM 자동 검출, DDC/EDID 런타임, G400)은
   그대로다.

**닫힌 것** (2026-08-22~24): 텍스처 원근, 깊이 비교 일곱, 블렌딩 인자,
알파 시험, 폴리곤 오프셋, 시저, 깊이 마스크, `glClear` 가속, 표면 인바운드
복사, 후퇴 시 깊이 보존.

알려진 값으로 남기는 것 — 결함이 아니라 두 규칙의 차이다:
* **혼합 프레임의 실금**: 하드웨어 삼각형과 소프트웨어 삼각형이 변을
  공유하면 폭 1의 빈 화소가 남을 수 있다.  512 삼각형 메시에서 5 화소이고
  **메시가 길어져도 커지지 않는다**(`M1_4B6` §3).
* **좌표 양자화**: 꼭짓점이 1/256 격자 밖이면 신탁과 어긋난다.  288 삼각형
  56000 화소에서 52 화소(0.09%).  격자 위에 있으면 512 삼각형에서 0.
* **블렌딩의 한 단계**: 엔진은 한 번 반올림하고 Mesa 는 절사한다.  설계상
  차이이고, 장면 채점이 두 단계 이내로 묶어 둔다.

## 0-1. 왜 §1·§2 는 멈춰 있었나 (2026-08-19 기준, 그대로 둔다)

남은 항목은 전부 (a) 하드웨어가 없어 확인 불가, (b) 이득이 측정되지 않아
착수 근거가 없음, (c) 순수 정리 중 하나다. 3D 작업이 드라이버 구조를 크게
바꿀 가능성이 있으므로, 지금 손대면 두 번 하게 되는 것들이 섞여 있다.

## 1. 기능 — 미착수, 근거 있음

### 1-1. 두 번째 head (dual head)
G450은 dual head지만 secondary CRTC/DAC 경로를 한 번도 건드리지 않았다.
`docs/R6_G400_G450_REGISTER_DIVERGENCE.md`에 레지스터 차이가 일부 정리돼
있으나 secondary 계열은 조사 자체가 미완이다.
- **막는 것**: 없음. 순수 미착수.
- **필요 조건**: 두 번째 모니터 실물.

### 1-2. VRAM 자동 검출
`MGA Memory Size`는 보수적 고정 16 MiB다. 실제 보드는 32 MiB일 가능성이
있으나(`R2` 감사의 `0d43` → G45FMDVP32DSF 후보) **한 번도 실측하지 않았다.**
- **막는 것**: 없음. 16 MiB는 안전 하한.
- **주의**: 오프스크린 VRAM 창(S4a)이 이 값에 의존한다. 늘리려면 S4a의
  가드 범위도 함께 재검증해야 한다.

### 1-3. DDC/EDID 런타임 사용
`edid/OpenStepMGAEDID.c`는 빌드에 들어가 있으나 모드 선택에 쓰이지 않는다.
모드는 config-table 문자열로만 정해진다.
- **막는 것**: 없음. 고정 모드 목록으로 충분히 동작한다.
- **가치**: 낮음. 5×5 조합이 이미 Configure에서 선택 가능하다.

### 1-4. G400 지원
`chipIsG450`는 PCI revision ≥ `MGA_G450_MIN_REVISION`로만 갈린다. G400은
미착수이고 실물도 없다. PLL 계열이 다르므로 코드 분기가 필요하다.

## 2. 성능 — 이득이 측정되지 않았다

### 2-1. 2D 가속을 실제 화면에 쓰는 길
Storm 엔진은 동작이 실증됐지만(S1/S2/S3a) **평상시에는 한 번도 쓰이지
않는다.** WindowServer가 `IODisplayDoBlit`을 보내지 않기 때문이다(측정으로
확정, `S3B_PREP_INSTRUMENTATION_PLAN.md`).
- 우리가 가시 프레임버퍼에 직접 블릿하면 그려지기는 하나, damage 장부에
  없으므로 WindowServer가 리페인트할 때 지워진다.
- **결론**: 창 안 가속에는 협조 프로토콜이 없다. 전체화면 소유 구조에서만
  의미가 있으며, 그것은 3D stage의 주제다.

### 2-2. 커서 하드웨어 가속
G450에는 하드웨어 커서가 있으나 OPENSTEP의 커서는 **소프트웨어 커서**이고
(IDA로 확인: 프레임버퍼 대상 CPU 복사 루프), 그 락은 `@private`이라 공유할 수
없다. 하드웨어 커서로 바꾸려면 커널 쪽 커서 경로를 우회해야 한다.
- **막는 것**: 구조적. 이득도 측정되지 않았다.

## 3. 정리 — 미룬 것

### 3-1. 폐기 산출물 미삭제
`protocol/`, `profile/`, `recovery/`, `test/openstep-mga-lease-*`,
`test/openstep-mga-*mig*` 등 P2 MiG/R1 복구 매트릭스 시절 산출물이 남아 있다.
현재 드라이버는 이들을 링크하지 않는다(빌드 대상은 `OpenStepMGAManualConfig.c`
+ `OpenStepMGAEDID.c`뿐).
- **삭제하지 않은 이유**: 여러 `docs/` 문서가 이들을 참조하므로 지우면 링크가
  깨진다. 대신 `TEST_STATUS.md` 머리말과 `HANDOFF.md`에 "폐기된 경로"임을
  명시해 두었다.
- **하려면**: 문서 링크를 먼저 정리한 뒤 한 번에.

### 3-2. 초기 계획 문서군의 시제
`P0`~`P3`, `R1`~`R4`, `G1` 문서들은 당시 계획을 현재형으로 서술한다. 개별
수정 대신 상위 문서에 "역사적 기록" 표시만 달아 두었다.

### 3-3. 빌드 스크립트의 `MOUNTPT`
`/ndrv`가 wedge되면 `nx-mount.sh`가 `/ndrv2`로 폴백하므로 매번
`MOUNTPT=/ndrv2`를 넘겨야 한다. 자동 감지로 바꿀 수 있다. 사소함.

### 3-4. `gcdsd` 부팅 자동 기동
재부팅할 때마다 `tools/nx-daemon.sh start`와 `nx-mount.sh`를 손으로 돌린다.
이 저장소가 아니라 GCDS 쪽 사안.

### 3-5. `AR3` — 조사 완료. 남은 범위는 ILOAD 계열뿐

X.Org DDX 색상 확장 경로의 `OUTREG(MGAREG_AR3, 0); /* crashes occasionally
without this */`(`mga_storm.c:1768`, `:1813`)를 보고 우리도 방어적으로
0을 쓰려 했으나, 조사 결과 **그럴 필요가 없고 쓰지 않는 것이 맞다.**

`AR3`는 **BITBLT/ILOAD 계열의 소스 주소지정 레지스터**다. DDX의 복사 경로가
값을 넣고(`:1390`, `:1398`, `:1466`, `:1479`, `:1491`), 사다리꼴 경로는 전혀
건드리지 않으며(`:1566`~`:1590`), 둘은 같은 가속 테이블에 등록돼 X가 수시로
번갈아 부른다(`:647`, `:656`). 즉 **stale `AR3`로 사다리꼴을 그리는 것이
출하 동작**이다. 0으로 미는 곳은 색상 확장/ILOAD 계열뿐이다.

원본 OPENSTEP `MatroxMGA`는 참고가 되지 않았다 — 드로잉 엔진을 아예 쓰지
않는다(`AR3`·`FXBNDRY` 참조 0건, 검색 방법은 CRTC/DAC 대조군으로 검증).

**남은 범위**: 우리가 색상 확장/ILOAD를 구현하게 되면 그때는 `AR3` 정리가
필요하다. 그 전까지는 해당 없음. 정본: `docs/D3_2_SLOPED_TRAPEZOID_PLAN.md`
§1-0-1.

### 3-6. ~~깊이 값 클램프~~ — **해결(들어간 지 오래됐고 표시만 안 됐다)**

깊이는 16비트이므로 `DR0`의 유효 구간은 `[0, 0x7FFF8000]`이다. 그 밖에서
하드웨어 동작이 **일관되지 않다** — `0x80000000`은 `0xffff`로 포화하는데
`0xFFFFFFFF`는 0을 준다(실측, `D3_3_DEPTH_PLAN.md` §10-3).

**드라이버가 직접 자른다.** Mesa에서 온 깊이를 `[0, 0xFFFF]`로 클램프한 뒤
`<< 15`한다. 하드웨어에 맡기지 않는다.

- **막는 것**: 없음.
- ~~**닫는 조건**: 3D 경로에 클램프가 들어가면 끝.~~ — **들어갔다.**

빌더가 사다리꼴마다 시작 깊이를 `[0, 65535]` 로 자르고, 자른 횟수를 센다
(`mesa/OpenStepMGAMesaTriangle.c` 의 `osmgaDepthClamps`). 기울기도 ±65535 로
묶는다. 하드웨어에 맡기지 않는다.

측정도 붙어 있다: 236940 사다리꼴에 대해 자름이 몇 번 늘고 줄었는지 세었고,
가파른 도형의 모서리가 67461.8 을 계산해 잘린 뒤 `GL_LESS` 가 `65535 < 65535`
를 거절해 화소가 안 그려지는 것까지 깊이를 끈 같은 도형과 대어 확인했다.
§0 의 "깊이 시작값 클램프 — 발동 0" 도 같은 계기가 답한 것이다.

> 아래가 원래 기록이다. 고친 내용은 이 절 끝에 있다.

`revertToVGAMode`는 **아무 잠금 없이** `linearModeActive = NO`를 쓴다.
`stormLock`은 제출 경로가 **입장 검사를 통과한 뒤에야** 잡고, 모드 변경은

1. 제출이 `mmioMapped && linearModeActive && bpp==4`를 통과한다
2. 모드 변경이 시작된다
3. 제출이 그 사이에 DMA를 프로그램하고 MMIO를 쓴다

**이것은 M1-3a가 만든 문제가 아니다** — 제출 경로(M1-2)에 원래 있었고,

시험이 모드를 바꾸지 않는 동안에만 그렸기 때문이다.

`OSMGA_HW3D_CAP_READY`는 이 문제를 **키우지 않는다**(같은 술어를 볼 뿐이다).
그러나 **알려주지도 않는다.**

→ 필요한 것은 **세대 번호(generation)**다: 모드가 바뀔 때마다 증가시키고,
제출이 그 값을 입장 시점과 DMA를 킥하기 직전에 두 번 확인한다. 또는 모드
변경이 `stormLock`을 잡게 한다.

**M1-3b(실제로 그리기 시작할 때) 전에 정한다.** 그때부터는 화면을 쓰는
동안 모드가 바뀔 수 있는 상황이 실제로 생긴다.

### 고친 방법 (2026-08-21)

**모드 변경이 `stormBusy` 규약에 참여한다.** 제출은 원래 그 깃발을
잡았는데 모드 변경만 참여하지 않고 있었다 — 새 잠금을 만들 필요가 없었다.

1. `enterLinearMode`/`revertToVGAMode`가 `-claimEngineForMode`로 엔진을
   잡는다. **모드 변경은 실패할 수 없으므로**(윈도서버가 요청한 것이다)
   기다린다: 5ms씩 200번, 1초. 제출이 스핀할 수 있는 최대치의 **5배**다
   (제출 한계 100000회 × 2, MMIO 읽기 1µs 가정 시 0.2초).
2. `enterLinearMode`에서 claim은 **레지스터 프로그래밍만 감싼다.** 뒤의
   자체 시험까지 물면 시험들이 스스로 엔진을 잡으려다 각각 1초씩 막힌다.
3. 그래도 못 잡으면 **크게 로그를 남기고 진행한다.** 돌아오지 않는
   디스플레이가 덮어써진 배치보다 나쁘다.
4. 3번을 안전하게 만드는 것이 **epoch**다. 모드 변경이 끝날 때마다
   증가하고, 제출은 claim 시점의 값을 기억했다가 끝나고 비교한다.
   달라졌으면 **성공으로 보고하지 않는다.**
5. 그리고 제출이 **claim 뒤에 조건을 다시 확인한다.** 원래 검사는 엔진을
   갖기 전에 했으므로 그 사이에 모드가 끝날 수 있었다. stride도 claim
   뒤에 다시 읽는다 — 없어진 모드의 stride로 그릴 뻔했다.

## 3-34. ~~클라이언트가 커널의 커맨드 리스트를 매핑하고 있었다~~ — **고침(2026-08-24, 재부팅 대기)**

핸들러는 "배치만, 링은 절대" 를 `rel >= OSMGA_HW3D_BATCH_BYTES` 로 지켰다. 그런데

것은 페이지 **전체**였으므로, `rel=0x6000` 페이지가 `[0x6000,0x8000)` 을 덮어
**리스트의 첫 4096바이트가 매핑됐다** — 그것도 가속을 쓰는 모든 프로세스에서
(클라이언트는 창 전체를 매핑한다).

실측으로 증명했다(`tcw`, 읽기 전용): 리스트 자리에서 8 dword 를 읽고 배치를
제출하고 다시 읽으니 2가 바뀌었고 6이 0이 아니었다.

**매 부팅 찍히던 `M1-0: FAIL` 이 이것을 가리고 있었다.** 그 FAIL 은 자가진단의
기대값이 낡아서 난 것이고(배치/링 분리 때 안 따라옴), 항상 실패하는 시험은 아무도
읽지 않는다.

배치를 페이지 정수 배로 만들어 고쳤다 — `MAX_TRI` 200→180, `BATCH_BYTES`
28672→24576(정확히 세 페이지), 리스트 36864→40960, `VERSION` 8→9. 헤더의
`ENC_TRI_BLK` 가 8인데 실제 9라 선언 상한이 **과소평가**였던 것도 같이 고쳤다.
할당은 0으로 채우고, 분리가 페이지 배수인지 init 에서 검사하며, 자가진단은 이제

넘겼다 — 그 상한은 이 저장소가 이미 적어 둔 사실인데 확인하지 않고 계획을 세웠다.

## 3-35. 클라이언트가 둘이면 서로를 덮어쓴다 (미해결 · 관측 코드만 들어감, 2026-08-24)

### 왜 아직 안 고쳤나 — 모르는 사실 하나에 걸려 있다

명백한 답은 **배타적 open** 이다. 그런데 그건 **클라이언트가 사라질 때 `close` 가
불리는가**, 특히 정상 종료가 아니라 **죽임당했을 때** 불리는가에 전부 걸려 있고,
**이 저장소에 그걸 밝힌 것이 없다** — S4A 의 역분석은 `mmap` 과 VM object 를
다루지 `close` 경로를 다루지 않는다(교차검토도 같은 답).

풀리지 않는 배타적 open 은 문제보다 비싸다: 지금은 죽은 클라이언트가 아무 값도
안 치르지만, 그때는 **재부팅할 때까지 가속이 사라진다.**

### 들어간 것: 세는 것뿐 (재부팅 대기)

동작은 하나도 안 바꾸고 `open`/`close` 에 계수기와 로그를 넣었다. 거절된 open 은
짝이 되는 close 가 없으므로 세지 않되, **로그는 남긴다** — 원래 그 로그가 "우리
cdevsw 슬롯에 실제로 닿는가" 를 말해 주던 것이라 그 값을 잃으면 안 된다.

시험은 `tdl`(신규), 한 번에 한 경우씩 — 합계만으로는 경우를 구분할 수 없다는
지적을 받아 그렇게 만들었다:

```
plain        열고 닫는다
twice        한 프로세스가 두 번 연다
exitnoclose  열고 닫지 않고 exit(0)
forkchild    열고 fork, 자식이 바로 죽고 부모가 닫는다
forkboth     열고 fork, 아무도 안 닫고 둘 다 끝난다
kill         열고 자기를 SIGKILL
```

### 잰 것 (2026-08-24, 실기)

직접 실행할 때 — 로그인 csh 에서든 `sh -c 'prog > file'` 로든:

```
명시적 close                    open 1, close 1
닫지 않고 exit(0)               open 1, close 1
fd 를 든 채 SIGKILL             open 1, close 1
fork, 자식 먼저 죽고 부모가 닫음  open 1, close 1
fork, 아무도 안 닫음             open 1, close 1
커맨드 창을 매핑한 채 종료        open 1, close 1
한 프로세스가 두 번 열기          open 2, close 1
```

**`close` 는 온다 — 죽여도 온다.** 재고 나서 정하기로 했던 그 사실이 이것이고,
내가 두려워한 구체적 형태(죽은 클라이언트가 영영 안 놓는다)는 **틀렸다.**

**다만 `close` 는 마지막 참조가 사라질 때 한 번만 온다.** 그래서 `opens - closes`
는 **점유 수가 아니다** — 클라이언트가 겹치면 N번 열리고 1번 닫히므로 영구히
어긋난다. 이 기계에서 46까지 쌓인 잔여가 그것이고, 새는 것이 아니다.

### 내가 틀렸던 것: "회귀가 참조를 흘린다"

한동안 회귀 한 번에 open +15 / close +1 이라고 읽었고 누출이라고 적을 뻔했다.
**아니었다.** `sh` 는 파이프라인의 **첫 단계가 아직 살아 있는데 반환한다** —
`ps` 로 확인했다(클라이언트가 `RW` 상태로 남아 있었고 close 는 5초 뒤 도착).
계수기 읽기가 종료를 앞지른 것이다. 끝나고 45초 기다려 다시 재니 **+15 opens /
+15 closes**, 그 뒤로도 그대로였다.

### 걸쇠도 안 된다 — 드라이버가 보는 것을 재고 나서

한 번은 **불리언 걸쇠**로 가려 했다. 잰 모든 경우와 맞았기 때문이다(교차검토도
같은 결론이었다). 그런데 둘 다 재지 않은 것이 하나 있었다 — **회귀가 도는 동안
드라이버가 실제로 무엇을 보는가.**

```
22:41:11 open  opens=148 closes=87
22:41:12 open  opens=149 closes=87
   ... 열한 개 더, 전부 closes=87 ...
22:41:15 open  opens=162 closes=87
22:41:15 close opens=162 closes=88
```

**열다섯 클라이언트에 close 하나.** 로그 유실이 아니다 — 계수기는 누적이고 살아
남은 줄이 87→88 이라고 말한다. 그리고 `ps` 로 재면 그 사이 살아 있는 클라이언트는
**최대 둘**이다.

이 로그에 대고 걸쇠를 시뮬레이션하면 **8 허용 / 28 거절**이다. 거절되는 쪽은 겹친
클라이언트가 아니라 **앞사람이 이미 죽었는데 close 가 아직 안 온** 정당한 다음
클라이언트다.

### 원인: 사슬 (통제 실험으로 확증)

겹치게 둘 vs 4초 띄워 둘:

```
겹침:  open 163, open 164, close 89          -- 둘에 close 하나
띄움:  open 165 -> close 90; open 166 -> close 91  -- 둘에 close 둘
```

`d_close` 는 **장치가 참조되지 않게 될 때 한 번** 온다. 연달아 도는 클라이언트는
사슬을 이뤄 그 순간을 뒤로 밀고, 버스트 전체에 close 가 하나 온다. 이것 하나로 전부
설명된다 — 15:1, `ps` 로 본 5초 늦은 close, 띄워 돌리면 번갈아 나오는 것, 그리고
`opens - closes` 의 영구 잔여.

### 판정: 이 인터페이스로는 배타성을 표현할 수 없다

- **(a) 배타적 open — 불가.** close 가 클라이언트 단위가 아니라 버스트 단위로
  오므로, 걸쇠는 이미 사라진 앞사람 때문에 정당한 다음 사람을 거절한다.
- **(b) 제출 때 주인 정하고 close 에서 놓기 — 불가.** 같은 close 에 기댄다.
- **(c) 단일 클라이언트 계약 — 강제 불가.** 라이브러리가 볼 수 있는 것은 전역
  capability 와 자기 상태뿐이라 **다른 프로세스가 있다는 것을 알 방법이 없다**
  (교차검토 지적, 확인함). 협조적 문서 규칙 이상이 될 수 없다.

**진짜 해법은 S4A:294 가 이미 적어 둔 것뿐이다** — 클라이언트별 핸들/마이너와
클라이언트별 할당. 그건 인터페이스 변경이고 이 항목보다 크다.

한 가지는 이미 있다: 동시 **제출**은 `stormBusy` 가 막는다. 남는 창은 제출이 아니라
**공유 배치에 대한 유저 측 쓰기**다.

### 계수기는 남긴다

`opens - closes` 는 **참조 수가 아니라 콜백 수**다(잔여는 그래서 생긴다). 그래도
남겨 둔다 — 이 항목이 미해결인 동안, 다음 사람이 같은 길을 다시 걷지 않게 하는
증거가 그것이다.

### 폐기한 안: 불리언 걸쇠 잰 모든 경우와 맞는다: 첫 open 이 세우고,
마지막 참조가 사라질 때의 close 가 내린다. 겹친 두 번째 open 은 거절되고 —
그게 이 항목이 원하던 바다 — 거절된 open 은 짝이 되는 close 도 없으므로 계수의
비대칭도 타지 않는다. 교차검토도 같은 결론이고, 내가 "잔여 때문에 걸쇠도 못
쓴다" 고 한 것은 **지나치게 조심스러웠다**(잔여는 계수기의 성질이지 걸쇠의
성질이 아니다).

**켜기 전에 알고 있어야 할 값**: 우리 회귀 자체가 클라이언트를 `sh` 파이프라인에서
돌리고, 그 때문에 **겹치는 일이 실제로 있다.** 걸쇠가 서면 겹친 쪽은 거절되어
소프트웨어로 떨어지고, 회귀가 간헐적으로 실패한 것처럼 보인다. 걸쇠가 제 일을
하는 것이지만, 그걸 모르고 켜면 회귀가 흔들리는 것으로만 보인다.

### 여전히 덮지 않는 것: fd 배타성은 매핑 배타성이 아니다

교차검토가 짚었고 확인했다 — 이 저장소가 **`close()` 해도 매핑은 남는다**고 이미
적어 두었다(`S4A_VRAM_MMAP_PLAN` 7-2, :248). 그러니 배타적 open 이 걸쇠를 놓은
뒤에도 **닫고서 포인터를 들고 있는** 클라이언트는 그대로 있다. 우리 클라이언트는
그렇게 하지 않고 죽은 프로세스의 주소공간은 함께 사라지지만, **그 틈은 실재하고
세는 것으로도 배제로도 닫히지 않는다.** 진짜 방향은 S4A:295 가 적은 클라이언트별
할당과 검증된 핸들이다.

## 3-11. 프로브의 두 `Run`이 동시에 들어오는 경우 (M1-3a, 미해결)

`OSMGAMesaProbeRun`의 `probeDone`/`probeCached`에는 잠금이 없다.

**해결한 것**: 취소(revoke)를 별도의 단방향 플래그로 빼고 복사 **뒤에**
확인하게 했다. 그래서 "한 스레드가 취소하는 동안 다른 스레드의 프로브가
늦게 끝나 하드웨어로 덮어쓰는" 경우는 사라졌다 — 실패가 소프트웨어를
요청했는데 하드웨어가 쓰이는 것이 여기서 가장 나쁜 결과였다.

**남은 것**: 두 스레드가 동시에 `Run`에 처음 들어오면 **각각 디바이스를
열고**, `probeCached`에 섞여 쓰일 수 있다. 하나는 디스크립터가 샌다.

지금 이것을 잠그지 않은 이유는, 이 빌드의 Mesa 3.4.2 자체가 스레드 안전이
아니라서 **여러 스레드에서 GL을 부르는 것이 이미 정의되지 않은 동작**이기
때문이다. 프로브만 잠가도 얻는 것이 없다.

→ **libGL을 스레드 안전으로 만들 생각이 생기면 그때 같이 정한다.**
그 전까지는 이 항목이 "안 한 것"으로 남아 있어야 한다.

### (3) ~~알파를 쓰지 않는다~~ — **전제가 사라졌다(2026-08-24 확인)**

훅은 RGB만 넘긴다. 그리고 OSMesa는 알파 비트가 있는 형식마다 **소프트웨어
알파 버퍼**를 따로 잡는데(`AlphaBits > 0` → `UseSoftwareAlphaBuffers`),
**우리가 그린 픽셀을 그 버퍼는 모른다.**

지금 안전한 이유는 **알파를 읽는 것을 전부 거절**하기 때문이다 — 블렌딩과
알파 시험은 각자의 `RasterMask` 비트로 막힌다. 위험은 프로그램이 가속으로
그린 뒤 **프레임 중간에 블렌딩을 켜는** 경우다: 그때 소프트웨어가 낡은
알파를 읽는다.

→ ~~알파를 붙일 때(M1-3d 이후) 같이 정한다.~~

**정해졌고, 방법은 그 버퍼를 없애는 것이었다.** 표면을 치환할 때 포트가
`UseSoftwareAlphaBuffers` 를 끈다(`OSmesa/osmesa.c:613`). 이유가 주석에 있다:
이 하드웨어는 알파를 화소의 **네 번째 바이트**에 쓰는데, 별도 알파 버퍼가
있으면 방금 색 버퍼에서 읽은 알파를 그 버퍼의 것으로 덮어써서 **모든 블렌드가
하드웨어가 쓴 알파를 무시하게 된다.** 꺼 두면 양쪽이 한 곳을 읽고 쓴다.

그래서 "우리가 그린 픽셀을 그 버퍼는 모른다" 는 전제가 가속 중에는 성립하지
않는다. 블렌딩은 이제 받아들여지고, 목적지 알파를 읽는 인자들이 실제로 그
네 번째 바이트를 읽는다는 것은 `tbf` 가 목적지 알파 `0x60` 으로 잰다.

가속을 놓을 때 그 버퍼를 **되살리지 않는 것**도 결정이지 빠뜨림이 아니다 --
알파가 네 번째 바이트에 있다는 것은 애플리케이션이 준 버퍼에서도 여전히
참이고, 이제 거기에 그린다(`osmesa_leave_accel` 의 주석).

### 그리고 `ALPHABUF_BIT`를 허용해야만 했던 이유

`RasterMask != 0`으로 막으면 **훅이 절대 안 붙는다.** `OSMESA_RGBA`가
`alphaBits = 8`을 세우고 그것이 `UseSoftwareAlphaBuffers`가 되어
`ALPHABUF_BIT`가 평범한 컨텍스트에서도 늘 켜져 있다. 컴파일도 되고 죽지도
않고 **그냥 가속이 안 되는** 침묵의 무동작이 될 뻔했다.

(교차검토는 "항상 켜지는 비트는 없다"고 답했다. **틀렸고**, 원본
`osmesa.c`의 형식 분기와 `context.c`의 대입을 직접 읽어 확인했다.)

## 3-13. ~~되비추기가 `glReadPixels`의 목적지를 덮을 수 있다~~ — **해결(2026-08-24)**

`glReadPixels`도 `RENDER_START`/`RENDER_FINISH`를 부른다
(`readpix.c:776,806`). 우리는 `RenderStart`에서 "더러움"을 표시하고
`RenderFinish`에서 표면 전체를 앱 배열로 복사한다.

그래서 **읽기인데도 복사가 일어난다.** 두 가지 결과가 있다:

1. **낭비** — 아무것도 그리지 않았는데 표면 전체를 복사한다.
2. **위험** — 앱이 `glReadPixels`의 목적지로 **자기 OSMesa 배열을 준
   경우**, 방금 읽어 넣은 값을 우리가 덮는다. 형식이 다르면 다른 값이 된다.

**왜 지금 안 고치나**: "그렸는가"를 알려면 소프트웨어 경로가 픽셀을 쓴
것을 알아야 하는데, 그 span 함수는 OSMesa의 것이고 우리에게 알리지
않는다. `RenderStart`에서 표시하는 것이 **거절된 프리미티브만으로 이뤄진
프레임을 "아무 일도 없었다"로 흘려보내지 않는** 유일한 방법이다.

→ ~~dirty 사각형 추적(§3-12와 같은 작업)을 할 때 같이 푼다.~~

### 해결 (2026-08-24) — 상자는 못 얻지만 **불리언은 얻을 수 있다**

미뤄 둔 이유가 "무엇을 건드렸는지 알아야 한다" 였는데, 그건 **상자**가 필요할
때의 이야기다. 여기 필요한 것은 "무엇이든 썼는가" 하나뿐이다.

OSMesa 의 RGBA 기록 스팬 다섯과 읽기 스팬 둘을 감싸 깃발을 세운다. 판정은
`읽었다 && 쓰지 않았다` 하나이고, 그 밖의 모든 것은 예전처럼 복사한다.

**왜 상자는 못 얻는데 불리언은 얻는가**: 상자를 막는 구멍은 OSMesa 가 선과
깊이 시험 있는 삼각형에 **직접 기록기**를 설치해 어떤 콜백도 거치지 않고
`PIXELADDR4()` 로 쓴다는 것이다. 그런데 그 기록기들은 **원시 경로에만** 있고,
원시 구간은 읽기 스팬을 부르지 않는다. 그러니 "읽었고 쓰지 않았다" 는 그린
구간에서는 **성립할 수 없다** — 보이지 않는 쓰기가 사는 곳이 바로 거기다.

감싸는 자리는 `RenderStart` 다. 상태 갱신 훅은 OSMesa 가 스팬을 설치하기
**전에** 불리므로(`osmesa.c:1912` 대 `:1917`) 거기서 감싸면 즉시 덮어써진다.
`RENDER_START` 는 버퍼를 건드리는 모든 경로가 지난다.

`RenderStart` 의 무조건 표시는 **그대로 둔다**. 직접 기록기로만 그린 프레임을
잃지 않으려면 그래야 한다. 대신 읽기로 판정된 구간이 **진입 시점의 값으로
되돌린다** — 그러지 않으면 아무도 바꾸지 않은 표면을 다음 flush 가 복사한다.

시험(`trb`)은 호출자가 **자기 OSMesa 배열을** 읽기 목적지로 주고 `GL_RGB` 로
요청한다. 미러가 거기 내려앉으면 세 바이트마다 어긋난다. 읽기가 미러를 부르지
않고(계수기로 확인), 바이트가 요청한 그대로이며, 뒤따르는 `glFinish` 도
건드리지 않는다.

**고칠 수 있어 보인다**: 하드웨어의 변 기울기는 분자·분모라 분수를 표현할

## 3-14z. (원래 기록) 두 경로의 깊이 값 차이

두 경로가 같은 깊이 버퍼를 보는 것은 실기에서 확인했다(양방향). 그러나
같은 삼각형의 같은 픽셀에 **같은 16비트 값**을 쓰는 것은 아니다.

| 차이 | 소프트웨어 | 우리 |
| --- | --- | --- |
| 정점 좌표 | 소수부 유지 | **`(long)`으로 잘림** |
| 표본 위치 | 픽셀 중심(`FIXED_HALF`) 보정 | 사다리꼴 모서리 |
| 고정소수점 | Q11, 절사 | Q15, 반올림 |

그래서 **경계에 걸친 `GL_LESS`가 한쪽에서는 통과하고 다른 쪽에서는
거절될 수 있다.** 지금 시험이 이걸 못 잡는 이유는 0.25 대 0.75라는 큰
간격을 쓰기 때문이다 — 간격이 1~2 단위면 드러난다.

**고칠 수 있는 것이 아니다**: 엔진의 보간 규칙은 바꿀 수 없다. 선택지는
(가) 깊이가 켜지면 **한 프레임 전체를 한 경로로** 몰기, (나) 그대로 두고
경계 사례의 오차를 받아들이기.

→ **M1-3e(알파/블렌딩) 전에 정한다.** 그때는 목적지를 읽으므로 오차가
색으로 드러난다.

### 들어간 것 (2026-08-24, 설치됨 · 재부팅 대기)

**회복 대기는 완료의 세 조건 전부로 한다.** 완료란 셋이 동시에 참인 것이다 —
목록 끝의 트랩이 발생했고, 그리기 엔진이 유휴이고, DMA 읽기 포인터가 끝에
닿았다(`MGA_DMA_DONE_MASK`/`_VALUE`, `:244-259`).

처음 계획은 `osmgaStormWaitIdle` 로 기다리는 것이었는데 **그건 틀렸다.** 그
헬퍼는 셋 중 **가운데 하나**(`ENGBUSY`)만 본다(`:1043-1051`). 그러니 그것이
"유휴" 를 돌려준 뒤에도 DMA 는 아직 목록을 읽고 있을 수 있고 곧 그리기를 더
넣을 수 있다 — 확립하지 못한 안전을 보고했을 것이다. 교차검토가 잡았다.

**트랩은 묻기 전에 지우지 않는다.** 그것이 세 신호 중 하나이므로, 먼저 지우면
질문에 필요한 증거를 버리는 셈이다. 회복이 성공한 뒤에 지운다.

**회복도 실패하면 걸쇠를 세운다.** 새 기구가 아니라 EXEC 뒤 시간초과한 블릿이
세우는 그 `stormBlitFailed` 다 — 같은 이유, 같은 영구성. 그리고 3D 제출 진입도
이제 그 걸쇠를 본다: 세워져 있으면 즉시 거절한다. 전에는 블릿과 채우기만 보고
있어서, "손대면 안 된다" 고 선언된 엔진에 3D 가 새 목록을 건넬 수 있었다.

### 고치지 **못한** 절반 — 덮지 않는다

이것이 막는 것은 **커널이 엔진에 일을 더 주는 것**이다. 표면을 이미 매핑해 둔
클라이언트가 프로세서로 그 메모리를 쓰는 것은 막지 못하고, 이 항목이 말하는
경합이 바로 그것이다. 닫으려면 리셋이나 격리가 필요한데 이 드라이버에는 둘 다
없고, 참조본(우리가 가진 X.Org 2.0.0 사본과 DRM 사본)에도 쓰이는 엔진 리셋
레지스터가 없다.

### 아직 없는 것: 이 경로를 도달하게 만드는 방법

시간초과가 한 번도 관측된 적이 없으므로 **새 코드는 아직 어떤 시험도 닿지
않는다.** 교차검토가 제안한 형태는 개발 전용 일회성 고장 주입이다 — `PRIMEND`
**뒤에** 첫 완료 폴이 시간초과를 보고하도록 만들되 목록을 망가뜨리거나 하드웨어를
물리지는 않는 것. 그러면 "폴은 포기했는데 회복이 완료를 봤다" 가지는 도달한다.
진짜로 물린 엔진은 그렇게 만들 수 없고, 만들려 하지 않는다.

## 3-16. 텍스처 좌표 한계가 **프리미티브가 아니라 클립 전체**로 잰다 (미해결)

## 3-18z. (원래 기록) 제출 뒤 엔진의 마지막 쓰기

텍스처 클라이언트에서 픽셀 `(0,0)`이 **재현성 있게** 미청소값을 유지했다.
띠의 나머지 4095픽셀은 전부 정확했다.

한 번에 하나씩 바꿔가며 가려냈다:

| 가설 | 시험 | 결과 |
| --- | --- | --- |
| `u = 0`이 특별 | `tmr[6] = 1` | **아니다** — 그대로 |
| `u`와 `v` 둘 다 | `tmr[6] = tmr[7] = 1` | **아니다** |
| 텍스처 유닛 워밍업 | 같은 배치를 두 번 제출 | **아니다** |
| 그 캐시 줄이 낡음 | **멀리 떨어진** 곳을 읽음 | **고쳐짐** |
| 시간 | 어디를 읽든 고쳐짐 | **이것이다** |

교차검토가 "첫 픽셀이 아니라 **첫 읽기**일 수 있다"고 지적해 더 갈랐다:

| 시험 | 결과 |
| --- | --- |
| 뒤에서부터 검사 (선행 읽기 없이) | **낡은 것 0개** |
| **이웃 낱말**(1,0)을 먼저 읽음 | **(1,0)도 낡았고**, 이어서 (0,0)도 낡음 |
| 그 직후 검사 루프가 (1,0)에 도달 | **정확함** |

**이웃도 낡았다가 곧 정확해진다**는 것이 결정적이다. 낡음은 **특정 주소에
붙어 있지 않고**, 따라서 캐시 줄도 특정 픽셀의 쓰기도 아니다. **제출이
반환된 직후의 읽기가 옛 값을 본다**는 것이고, 버스 읽기 한 번의 시간이면
가라앉는다.

### 어디에 있는지는 확정됐다 (2026-08-21)

드라이버가 반환 전에 **같은 물리 메모리를 캐시 없이** 읽게 해보았다
(창의 한 페이지를 `IOMapPhysicalIntoIOTask`로 한 번 별칭 매핑해 보관):

```
클라이언트도 정착 읽기를 함  -> drew 4096, identity 4096 of 4096
드라이버만 믿음              -> drew 4095, identity 4095 of 4096
```

**충분하지 않다.** 커널이 캐시 없이 읽어도 클라이언트 쪽이 안 풀린다.

**그런데 거기서 "클라이언트 매핑이 캐시되어 낡은 줄을 쥔다"로 간 것은
틀렸다.** 계획 검토가 짚었고 확인해보니 맞았다 — 같은 기계의 기존 측정과
모순된다. `S4A_VRAM_MMAP_PLAN.md §9-1`의 stale-cache 게이트는 캐시를
**의도적으로 오염시킨 뒤** 확인했고(`before=a5000000` → `after=5aa55aa5`),
**유저 매핑이 엔진 쓰기와 일관함**을 실증했다.

**그 시험과의 차이는 매핑이 아니라 경로다** — 그때는 MMIO로 몬 2D 블릿,
지금은 **M1 primary DMA**. 그러므로 의심할 곳은 **완료 판정**이다:
`ENDPRDMASTS`는 명령 스트림을 다 **읽었다**는 뜻이지 그 쓰기가
**도착했다**는 뜻이 아닐 수 있다.

정본은 `M1_3G_SURFACE_READBACK_PLAN.md`로 옮겼다. 다음 작업은 **복사
기구를 짓는 것이 아니라**, 완료 판정 직후 커널이 캐시 없는 별칭으로 읽어
그 값이 옳은지 재는 **진단 하나**다.
효과가 없는 것으로 밝혀진 그 읽기는 다시 걷어냈다 — 하지 않는 일을
한다고 적어둔 장치는 없느니만 못하다.

**그리고 이건 S4a 계획서가 이미 차단 요건으로 적어둔 것이다**
(`S4A_VRAM_MMAP_PLAN.md` §7-1): *"`d_mmap`이 PFN을 반환하는 이 경로에는
uncached나 write-combining을 요청할 공개 수단이 없다"*, 그리고
*"Storm 쓰기 후 CPU 캐시에 낡은 라인이 남을 수 있다."* **예측이 그대로
관측됐다.** 헤더를 다시 뒤져도 `d_mmap` 경로에 캐시 억제 수단은 없다.

→ 남은 길은 둘이다:
  **(가)** 되비추기를 **커널이** 한다 — 커널은 캐시 없는 별칭을 만들 수
  있으므로, VRAM을 읽어 앱 버퍼로 옮기는 일을 ioctl로 옮긴다. 그러면
  클라이언트가 VRAM을 읽을 일이 없어진다.
  **(나)** 유저 매핑을 캐시 없이 얻는 다른 경로를 찾는다.

**(가)가 확실하다.** M1 되비추기가 지금 맞는 것은 표면 전체를 복사하느라
캐시 줄이 밀려나기 때문일 뿐이고, dirty 사각형으로 좁히는 순간 사라진다.

**기전은 확정하지 못했다.** 커널은 `MGA_DMA_DONE_VALUE`까지 돌고
`osmgaStormWaitIdle`까지 기다리지만, 그것이 **클라이언트가 보는 것**을
보장하지 못한다는 사실만 확립됐다. 원래 여기 적었던 "엔진의 쓰기가 늦게
도착한다"는 표현은 **증거보다 강했다** — 관측은 그것과도, "첫 관측이
이르다"와도 모두 들어맞는다.

**왜 중요한가**: Mesa 되비추기가 VRAM을 읽는다. 지금 맞게 나오는 이유는
표면 전체를 복사하느라 충분히 오래 걸리기 때문일 뿐이고, **보장이 아니다.**
dirty 사각형으로 좁히면(§3-12, §3-13) 그 여유가 사라진다.

→ **커널이 반환 전에 가시성을 보장해야 한다** — 마지막으로 쓴 위치를
되읽거나 적절한 장벽을 두어서. 클라이언트마다 추측하게 둘 일이 아니다.
시험 클라이언트에는 그때까지 되읽기 앞에 지연을 두었고, 왜 두는지 적어
두었다.

## 3-19. ~~`mmap` 의 오프셋이 무시된다~~ — **철회. 내 시험 클라이언트 버그였다**

**2026-08-21 결론: 오프셋은 제대로 먹는다.** 드라이버에는 아무 문제가 없었다.

독립 프로그램(`test/openstep-mga-mmap-offset-test.c`)으로 직접 쟀다. 두 후보
자리에 서로 다른 값을 두고, 오프셋 매핑을 통해 세 번째 값을 쓴 뒤 어느 쪽이
움직였는지 본다:

```
base mapping at offset 0 : at 0x32000, mmap reported 0
offset mapping at +1048576: at 0x134000, mmap reported 0
   window byte 0        holds a1a1a1a1  (그대로)
   window byte 1048576 holds c3c3c3c3  (여기로 갔다)
VERDICT -- the offset is honoured
```

### 왜 무시되는 것처럼 보였나

**argv 파싱이 매핑보다 뒤에 있었다.** 내가 인자를 나중에 덧붙이면서 파싱
블록을 매핑 호출 **아래**에 두었다. 그래서 매핑을 옮기는 그 인자는 매핑
시점에 언제나 0 이었고, **`dstorg` 만 움직였다.** 사각형이 클라이언트가
보는 자리에서 한 행 벗어난 것은 그 때문이다.

고쳤다 — 파싱을 main 맨 앞으로 옮겼다. 그러자 같은 시험이:

- 한 페이지(8192 B) 오프셋: `사각형 다음 행에 그려진 화소 0` — 제자리다.
- 반 페이지(4096 B) 오프셋: `a window will not map` — 거절된다.

### 덤으로 알게 된 두 가지

1. **이 시스템의 `mmap` 은 주소가 아니라 상태를 돌려준다.** 성공에 0,
   실패에 -1 이고, 매핑은 넘긴 주소에 놓인다. 처음에 반환값을 포인터로 쓰다가
   버스 에러를 봤다. **그러므로 기존 헬퍼들이 `vm_allocate` 주소를 돌려주는
   것은 올바르다** — codex 가 "반환값을 버린다"고 지적한 것은 이 시스템에서는
   효력이 없다.
2. **페이지 정렬이 아닌 오프셋은 조용히 반올림되지 않고 `EINVAL` 로
   거절된다.** 오프셋 × 길이 행렬로 확인했다 — +0, +8192, +16384 는 모두
   성공, +4096, +12288 은 길이와 무관하게 전부 거절.

이 두 번째 사실이 §3-20 을 추정이 아니라 **확인된 것**으로 만든다.

### 남은 관찰 (별건)

매핑을 한 페이지 옮긴 시험에서는 사각형이 제자리에 떨어지는데도 **행 0 과
행 16 이 통째로** 늦게 온다(2 개 연속 구간, 128 화소). 창 시작에서 보이는
64 바이트와는 다른 모양이다. 프로덕션에는 이런 매핑이 없다(Mesa 는 색을
오프셋 0 에, 깊이를 페이지 정렬 오프셋에 매핑한다). **시험 전용 경로의
미해결 관찰**로 세워 두고 지금은 쫓지 않는다.

## 3-20. ~~Mesa 쪽 깊이 매핑이 4 KiB 로 정렬한다~~ — **고쳤다 (2026-08-21)**

오프셋을 `vm_page_size` 에서 유도하도록 바꾸고, **길이 반올림은 없앴다**
(길이는 정렬이 필요 없다는 것을 오프셋 × 길이 행렬에서 이미 쟀다).
전제(0 이 아닌 2 의 거듭제곱)를 코드에서 검사하고, 자원 확보가 실패했을
때만 한 번 알린다 — 정상적인 거절에는 침묵한다.

실기 확인 (`test/openstep-mga-mesa-depth-size-test.c`):

| 크기 | h*w % 2048 | 깊이 원점 | 결과 |
| --- | --- | --- | --- |
| 800x600 | 768 | 6119424 | **하드웨어 깊이** (전에는 소프트웨어) |
| 320x240 | 1024 | 4505600 | **하드웨어 깊이** (전에는 소프트웨어) |
| 333x222 | 198 | 4497408 | **하드웨어 깊이** |
| 640x480 | 0 | 5423104 | 하드웨어 깊이 (전에도) |
| 1024x768 | 0 | 0 | 깊이 자리 없음 — **정렬이 아니라 용량** |

측정값 다섯 개가 python 산술과 **정확히** 일치한다. `1024x768` 의 0 은
색 표면만으로 3 MiB 창을 정확히 다 채우기 때문이고 고침 전후가 같다 —
시험이 그 둘을 구분해 찍도록 고쳤다.

## 3-20z. (원래 기록) Mesa 쪽 깊이 매핑이 4 KiB 로 정렬한다

```c
/* mesa/OpenStepMGAMesaBuffer.c:77 */
tail = (tail + 4095UL) & ~4095UL;
...
need = (need + 4095UL) & ~4095UL;
```

이 기계의 `PAGE_SIZE` 는 **8192** 이고, 드라이버의 `d_mmap` 은 페이지 정렬이
아닌 물리 주소를 거절한다:

```c
if ((phys & ((unsigned long)PAGE_SIZE - 1UL)) != 0UL) return -1;
```

**처음 계산은 전제가 틀렸다.** 보폭을 디스플레이 보폭으로 놓고 셌는데,
이 경로는 `if (bufStride != bufWidth) return 0;` 이라 **보폭이 곧 버퍼
너비**다. 다시 셌다.

`tail = (h*w*4 + 4095) & ~4095` 이고, 이것이 8192 의 배수여야 한다.
`h*w*4` 가 8192 의 배수인 것은 `h*w` 가 **2048 의 배수**일 때뿐이고,
아닐 때 4096 반올림은 4096 의 배수에만 떨어지므로 그중 절반이 어긋난다.

python 전수(너비 1..1024 × 높이 1..768, 786432 조합): **395172 개(50.2%)가
실패한다.** 그리고 흔한 크기가 걸린다:

| 크기 | tail | tail % 8192 | 깊이 mmap |
| --- | --- | --- | --- |
| 320x240 | 307200 | 4096 | **거절** |
| 640x480 | 1228800 | 0 | ok |
| **800x600** | 1921024 | 4096 | **거절** |
| 1024x768 | 3145728 | 0 | ok |
| 1024x767 | 3141632 | 4096 | **거절** |

**800×600 과 320×240 이 지금 하드웨어 깊이를 못 쓴다.** 시험이 늘
1024×768 이라 안 걸렸다.

실패하면 `mmap` 이 -1 을 돌려주고 `OpenStepMesaAccelDepthBuffer` 가 0 을
돌려주며, Mesa 는 **아무 말 없이 소프트웨어 깊이 버퍼를 쓴다.** 그림은
맞지만 하드웨어 깊이가 조용히 사라진다.

지금까지 안 걸린 것은 시험 높이가 768 이라 우연히 정렬됐기 때문이다.

**2026-08-21: 확인됐다.** §3-19 를 재면서 페이지 정렬이 아닌 오프셋이
`EINVAL` 로 **거절된다**는 것을 직접 쟀다(오프셋 × 길이 행렬: +4096 과
+12288 은 길이와 무관하게 전부 거절). 그러니 이것은 추정이 아니다 —
`tail` 이 8192 의 배수가 아닌 순간 깊이 `mmap` 이 실패하고, Mesa 는
소프트웨어 깊이로 조용히 되돌아간다.

고침은 4095 를 런타임 페이지 크기로 바꾸는 것이다. §3-19 가 철회됐으므로
막는 것은 이제 없다.

## 3-21. ~~pitch 가 32 배수가 아니면 틀리게 그린다~~ — **해결(2026-08-21)**

**「수락된 뒤 엉뚱한 자리에 그린다」가 없어졌다.** 세 겹으로 막았다:

- 커널 검증기가 `dstPitch % 32` 를 보고 `E_DSTPITCH` 로 거절한다
  (`hw3d/OpenStepMGAHW3D.c`).
- Mesa 표면이 생성 시점에 정렬 안 된 보폭을 거절한다
  (`mesa/OpenStepMGAMesaBuffer.c:322`).
- 검증기 시험에 경계 사례가 있다(1023 거절, 352 안의 333 수락).

남은 것은 **그 너비들이 가속을 못 탄다**는 것이고, 그건 §3-22 다 —
틀리게 그리는 것과 못 그리는 것은 다른 문제다. 아래는 원래 기록.


`test/openstep-mga-mesa-depth-agree.c` 를 크기 인자로 바꾸고 먼 구석에도
같은 삼각형을 그리게 하자 드러났다. 같은 삼각형을 가속과 강제 소프트웨어로
그려 커버리지를 비교한 것이다.

| 너비 | 하드웨어가 덮은 비율 |
| --- | --- |
| 64, 320, 352, 640, 800 | 98~100% |
| 322, 324, 328, 333, 336, 369, 655 | 1~14% |

**12 개 너비에서 예외 없이 갈리고, 가르는 것은 오직 "32 의 배수인가" 다.**
python 으로 확인했다 — 2·4·8·16·64 는 전부 못 가른다(336 은 16 의 배수인데
무너지고, 352·800 은 64 의 배수가 아닌데 멀쩡하다).

Mesa 쪽은 표면의 보폭을 그대로 `dstPitch` 로 넘기고
(`mesa/OpenStepMGAMesaHook.c:124`), 검증기는 `dstPitch != 0` 과
`dstWidth <= dstPitch` 만 본다(`hw3d/OpenStepMGAHW3D.c:132`). **정렬은
아무도 안 본다.**

배치는 **거절되지 않는다** — `hookDrawn` 이 오르고 revoke 도 안 걸린다.
수락된 뒤 엉뚱한 자리에 그린다.

**깊이 고침이 만든 버그가 아니라 드러낸 버그다.** §3-20 전에는 이 크기들의
깊이 매핑이 실패해 깊이를 쓰는 장면이 통째로 소프트웨어로 갔다. 깊이를 안
쓰는 프로그램은 예나 지금이나 이 너비에서 가속을 타고 틀리게 그렸을 것이다.

### 참조 구현이 같은 말을 한다 (X.Org `xf86-video-mga`)

측정에서 유도한 규칙을 원본과 대조했다. **두 곳에서 따로 확인된다:**

```c
/* mga_exa.c:869 */
/* Pitch alignment is in sets of 32 pixels, and we need to cover
 * 32bpp, so it's 128 bytes.
 */
pExa->pixmapPitchAlign = 128;
```

128 바이트 ÷ 4 바이트/화소 = **32 화소**.

```c
/* mga_dacG.c:2291 -- G 계열 DAC, 우리 것 */
pMga->Roundings[0] = 64;    /* 1 byte/px  */
pMga->Roundings[1] = 32;    /* 2 bytes/px */
pMga->Roundings[2] = 64;    /* 3 bytes/px */
pMga->Roundings[3] = 32;    /* 4 bytes/px  <- 우리 */
```

`Roundings` 는 `(bytesPerPixel - 1)` 로 색인하고, 4 바이트/화소는 **32** 다.

그러니 세 갈래가 같은 값을 가리킨다 — 실기 12 개 너비, `mga_exa.c` 의
주석과 상수, 그리고 G 계열 DAC 의 반올림 표. **추정이 아니다.**

덤으로: 16 비트 깊이는 `Roundings[1] = 32` 로 역시 32 화소다. 우리 깊이
보폭은 색 보폭과 같은 화소 수이므로, 색을 32 로 맞추면 깊이도 맞는다.

고침 후보(아직 계획 아님): 보폭을 32 화소의 배수로 올려서 가속을 유지하거나,
아니면 그런 보폭에서는 가속을 거절한다. 검증기도 함께 막는 편이 낫다.
정본 측정은 `M1_3L_PLAN.md` §6.

## 3-22. 보폭 패딩으로 32 화소가 아닌 너비도 가속할 수 있다 (후속, 색 전용)

§3-21 은 32 화소가 아닌 보폭에서 **가속을 거절**하는 쪽으로 고친다. 대신
보폭을 32 로 올리면 그 너비들도 가속할 수 있다. **색만 놓고 보면 안전하다**:

- Mesa 는 가속 표면에 애플리케이션 보폭과 다른 내부 보폭을 쓸 수 있다 —
  `OpenStepMesaAccelBuffer` 가 `appRowLength` 를 따로 기억하고 `rowLength`
  를 돌려주며, OSMesa 쪽 패치가 행 주소를 계산하기 전에 그것을 설치한다.
- 커널은 클라이언트가 준 pitch 를 그대로 쓴다. 두 쪽이 다른 주소를 계산할
  일이 없다.

**막는 것은 깊이 공유 하나다.** 커널은 깊이 보폭을 색 pitch 에서 유도하고
(`zstride = (pitchBytes/4) * DEPTH_BYTES`), Mesa 3.4 의 소프트웨어 깊이는
`DepthBuffer + Width*y + x` 로 너비 보폭을 가정한다. 그래서
`OpenStepMesaAccelDepthBuffer` 가 `bufStride != bufWidth` 를 거절한다.
패딩하면 깊이를 쓰는 장면이 소프트웨어로 갈 뿐이고 **틀리게 그려지지는
않는다.**

완전한 하드웨어 깊이까지 가려면 **계약에 깊이 pitch 를 따로** 넣어야 한다.
그건 별개의 작업이다.

## 3-23. ~~Mesa 표면의 소유·수명 계약이 상태 갱신 시점에 지켜지지 않는다~~ — **해결·확인(2026-08-24)**

pitch 수리를 교차분석하다 나온 **별개의, 이전부터 있던** 구멍 셋. 정렬
검사를 우회하지는 않지만, "거절하고 깨끗이 소프트웨어로 물러난다"는 의도된
동작을 무너뜨린다. 셋 다 소스에서 확인했다.

**(a) `OSMesaPixelStore` 가 상태를 갱신하지 않는다**

```c
/* osmesa.c, OSMesaPixelStore -- 이것이 전부다 */
ctx->rowlength = value;
ctx->yup = value ? GL_TRUE : GL_FALSE;
```

컨텍스트가 current 가 된 뒤 행 길이를 바꾸면 소프트웨어 행 주소는 다시
계산되지만 `osmesa_update_state` 가 안 불린다. 이미 설치된 하드웨어 삼각형
함수가 그대로 남아, **옛 보폭으로 제출하면서 Mesa 는 새 행 길이로 주소를
계산한다.** (`OpenStepMesaAccelUpdateState` 에 보폭 불일치 검사가 있지만
불릴 기회가 없다.)

**(b) 선택기가 소유를 안 본다**

```c
/* OpenStepMGAMesaHook.c */
if (OSMGAMesaBufferOrigin() == 0UL) return NULL;
```

원점과 보폭만 본다. `bufCtx == ctx` 는 안 본다. 그래서 다른 크기로 다시
바인딩했거나 두 번째 컨텍스트라 **표면을 못 받은 쪽도** 행 길이만 맞으면
하드웨어 함수를 받는다.

**(c) 해제가 자기 컨텍스트를 무시한다**

```c
OpenStepMesaAccelReleaseBuffer(void *ctx)
{
    (void)ctx;          /* <- */
```

두 번째 컨텍스트가 사라지면서 **첫 번째의 표면을 해제한다.**

### 시험 (2026-08-24 에 만들었다 — `town`)

셋 다 그 사이에 고쳐져 있었다. **읽어서 알았지만 읽기로 닫지 않았다** — 이
항목이 요구한 시험 셋을 만들어 재고 닫는다.

1. 행 길이를 표면이 갖지 못한 333 으로 바꾸면 표면을 놓고, 그 뒤로는 엔진에
   아무것도 가지 않는다.
2. 같은 컨텍스트를 다른 높이로 다시 바인딩하면 표면을 놓고, 그 뒤로는 엔진에
   아무것도 가지 않는다.
3. 두 번째 컨텍스트는 배치를 하나도 그리지 않고, **자기 버퍼에 2000 화소를
   칠하고 첫 번째 것에는 0 화소를 칠한다.** 그리고 그것이 파괴돼도 첫 번째의
   표면은 살아 있고 다시 엔진으로 그린다.

고쳐진 자리: (a) `OSMesaPixelStore` 가 배치가 더 이상 맞지 않으면 가속을 놓는다
(서브모듈 `OSmesa: end the substitution when the layout stops matching it`),
(b) 선택기는 `OpenStepMesaAccelUpdateState` 에서만 불리는데 그 함수가 소유
(`BoundTo`)·보폭·방향을 먼저 보고 물러난다, (c) 해제가 자기 컨텍스트만 놓는다.

### 시험을 쓰다 내가 틀린 것

첫 판은 두 번째 컨텍스트에 대해 `OSMGAMesaBufferOrigin() == 0` 을 단언했다가
**실패했다 — 드라이버가 아니라 내 단언이 틀렸다.** 그 접근자는 "표면이
있는가" 를 답하는 전역이지 "이 컨텍스트가 그것을 가졌는가" 가 아니고, 표면은
첫 번째가 여전히 쥐고 있으니 당연히 0 이 아니다. 중요한 성질은 그게 아니라
**두 번째가 첫 번째의 메모리에 그리지 않는다** 는 것이고, 지금은 그것을 잰다.

## 3-24. ~~정렬된 비표준 pitch 의 양성 시험이 없다~~ — **해결(2026-08-24)**

커널이 `dstPitch = 992` 를 **수락**하는 것은 확인했다(§`M1_3M_PLAN.md` §9).
확인 안 된 것은 **992 로 제대로 그리는가** 다 — 지금 클라이언트는 여전히
1024 보폭으로 색인하므로 화소 수치가 의미가 없다.

필요한 것: 요청한 pitch 로 채우고·세고·가드 화소를 두는 클라이언트. 여러 행에
걸치는 도형을 가로·세로 경계 근처에 그리고, 의도한 화소가 바뀌고 이웃
가드가 안 바뀌는지 본다. pitch 는 깊이 행 간격도 정하므로 깊이를 켠 경우도
포함한다.

"검증기는 992 를 통과시키는데 레지스터에는 1024 를 프로그램한다" 같은 회귀를
잡는 것은 이 시험뿐이다.

### 해결 (2026-08-24) — `tpq`

```
pitch 992, declared width 900, 16 rows, bar at columns 868..899
   words that changed              : 512
   intended words left untouched   : 0
   words written that should not be: 0
```

바뀐 워드의 **집합**이 기하가 지목한 집합과 정확히 같다. 엔진은 배치가 선언한
992 로 걷는다.

**형태가 요점이다.** 창 전체를 sentinel 로 채우고, 그린 뒤, **바뀐 집합**을
의도한 집합과 댄다. 수를 세는 것이 아니라 집합을 대므로 잘못된 보폭이 어디에
떨어지든 잡힌다 — 피치 오류, 좌표 밀림, 넘침 모두 실패하고, 어느 것도 "켜진
화소 수가 맞다" 뒤에 숨을 수 없다.

기하도 그렇게 골랐다. 폭(900)을 피치(992)보다 작게 두어 행마다 92 워드의
패딩이 실재하게 하고, 막대를 그 폭의 **오른쪽 끝**(868..899)에 32 워드로 둔다.
32 는 1024 − 992 다 — 잘못된 보폭이면 행마다 정확히 막대 하나만큼 밀려 패딩으로
떨어진다. 창은 32768 워드를 훑으므로 잘못된 보폭이 **훑는 범위 안에** 있다.

제출 뒤 첫 64 바이트 밖의 워드를 한 번 읽고 나서 훑는다. 그 구간의 쓰기는
늦게 보이며, 아직 나타나지 않은 워드를 피치 실패로 읽는 것을 막는다.

### 이 시험을 쓰다 내가 틀린 것

첫 판은 막대의 **색**까지 예측했다가 실패했다 — 기하는 완벽히 맞는데(512 변경,
밖으로 0) 예측한 색이 아니었다. `dr[]` 채널 순서를 추측한 탓이다. 이 시험이
물어야 할 것은 화소가 **어디에** 떨어지는가이지 무슨 색인가가 아니므로, 단언을
"sentinel 이 아니게 되었는가" 로 바꿨다.

### 함께 확인된 것

디스플레이 보폭은 **상한**이지 대체가 아니다: 제출 경로가 `dstPitch > stride3`
를 거절하고(`OpenStepMGAReplacementDisplay.m:3610`) 배치의 값을 프로그램한다.
클립도 `dstW3`/`dstH3` 와 `cy*dstP3` 로 전부 배치 값이고, 깊이 간격도 배치
피치에서 나온다.

## 3-26. ~~삼각형 단위 대체 경로에 시험이 없다~~ — **해결(2026-08-24)**

`M1-4a0` 이 만든 것 — 못 그리는 삼각형을 잃지 않고 소프트웨어로 넘기는 것 —
을 확인하던 시험이 **지렛대를 잃었다.**

- 그 지렛대는 "커널이 평범한 잘린 삼각형을 거절한다"(§3-25)였고, 그것이
  **잘못된 검사여서 고쳐졌다.** 이제 거절되지 않는다.
- 좌표 범위(16384) 밖 경로는 **Mesa 가 먼저 자르므로** GL 에서 닿지 않는다.

남은 것은 **시험 없는 정확성 기계**다. 그 경로가 정하는 것은 사소하지 않다:
검증 거절은 다시 그리고, DMA 이후 실패는 잃고 revoke 한다. 조용히 썩으면
어느 쪽으로 틀려도 안 보인다.

### 후보

1. **훅에 시험용 지렛대.** 이 백엔드에는 이미 환경변수 선례가 있다 —
   `OSMGA_PROBE_ENV` 가 가속을 통째로 끈다(`OpenStepMGAMesaProbe.c:80`).
   같은 결로 "N 개마다 하나는 소프트웨어로" 를 두면, 같은 장면을 전부 가속 /
   전부 소프트웨어 / 번갈아 그려 **셋이 화소로 일치하는지** 볼 수 있다 —
   `M1_4A0_FALLBACK_PLAN.md` §5 가 진짜 시험이라고 적은 바로 그것이다.
   그리고 시험 밖에서도 쓸모가 있다(그림 차이를 이분하는 스위치).
2. 선택기는 받아들이는데 커널은 거절하는 상태를 합성한다 — 지금은 그런
   상태를 찾기 어렵고, 찾더라도 다음 고침에 또 사라진다.

1 번이 낫다고 본다. 다만 **제품 코드에 시험용 손잡이를 두는 것**이므로,
계획을 세우고 교차검토를 거친다.

### 해결 (2026-08-24)

세 방식으로 같은 메시를 그려 셋을 다 판정한다. 지렛대는
`OSMGAMesaHookForceSoftware()`, 러너는 `tools/run-matrox-mesh-modes.sh`,
판정은 `tools/score-matrox-mesh-modes.sh`(호스트, python).

```
        엔진        소프트      안칠함  넘게  몫 부족
mesh    128/128 hw  0           0       0     0
        0/128   sw  128         0       0     6
        64/128  mix 64          6       0     6
mesh12  288/288 hw  0           0       0    52
        0/288   sw  288         0       0    12
        144/288 mix 144        35       0    58
mesh16  512/512 hw  0           0       0     0
        0/512   sw  512         0       0     5
        256/512 mix 256         5       0     5
```

`mix` 가 정확히 반반이다 — 홀수 삼각형은 소프트웨어, 짝수는 엔진이므로 **모든
공유 변이 하드웨어/소프트웨어 경계**다. 이 항목이 원하던 배치가 그것이다.

### 그 전에 고쳐야 했던 것 — `mix` 는 광고한 것을 만들지 못하고 있었다

루프가 `softOff(); glFinish();` 로 끝났다. **강제를 끈 뒤에 비운다.**

`glEnd` 는 아무것도 그리지 않는다. Mesa 는 즉시 버퍼에 표시만 하고
(`src/vbfill.c` 의 `gl_End`), 버퍼가 거의 찰 때(`gl_Begin` 의
`IM->Count > VB_MAX-4`)나 누가 비울 때 래스터화한다. 그러니 삼각형을 그리는
경로는 **비우는 시점**의 깃발이 정한다.

증거는 덤프 머리말이었다. 128 삼각형에서 `sw` 가 `drawn=57 software=71`(0 과
128 이어야 한다), 그리고 `mix` 가 **완전히 같은 수**. 삼각형마다 토글해도 결과가
같다는 것은 토글이 아무것도 정하지 않았다는 뜻이다.

고침은 강제가 걸린 구간 **안에서** 비우는 것이다. `sw` 는 루프 전체가 강제이니
끝에 한 번, `mix` 는 삼각형마다 `glFlush()`. 비용은 싸지 않다 — 이 백엔드는
`RenderFinish`·`Flush`·`Finish` 를 모두 미러에 걸어 두어서 비울 때마다 표면
전체를 훑는다(§3-32). 그래서 **빠른 회귀가 아니라 별도 스크립트**다.

### 왜 이렇게 됐나

옛 덤프의 머리말이 답이다: `# counters drawn=0 software=0 / # select hard 0
soft 1`. 그때의 강제는 **chooser 수준**이었고(표면 크기 시저로 chooser 가
소프트웨어를 고르게 했다), 그 방식에서는 비우는 시점이 상관없었다. 기구가
`OSMGAMesaHookForceSoftware` 로 옮겨졌을 때 시험이 함께 옮겨지지 않았다.

### 판정이 `hw` 만 실패시키고 있었다

`mesh-compare.py` 는 세 모드의 수를 **찍기만 하고** `hw` 일 때만 실패시켰다.
강제된 경로가 통째로 망가져도 성공이 나온다는 뜻이다 — 실제로 그런 상태였다.
지금은 세 모드를 다 판정하고, **먼저 어느 경로가 그렸는지**를 본다:
`hw` 는 소프트웨어 0, `sw` 는 엔진 0 이고 소프트웨어가 삼각형 수, `mix` 는 둘의
합이 삼각형 수이며 어느 쪽도 0 이 아니어야 한다. 그림은 그 다음이고, 기준값에서
움직였는지로 본다.

덤으로 둘: 목록이 `('mesh','mesh12')` 로 박혀 있어 **`mesh16`(512 삼각형) 덤프를
한 번도 보지 않았다**. 그리고 시험이 `OSMGAMesaHookForceSoftware` 를 **선언 없이**
부르고 있었다(C89 암시적 `int`) — 헤더를 include 하도록 고쳤다.

`# select hard/soft` 는 판정에 쓰지 않는다. 그 계수기는 chooser 의 선택 횟수이지
삼각형 수가 아니고, 강제 깃발은 chooser 를 거치지 않고 그리기 시점에 작동한다.

- 넓이로는 안 보였을 것: 도형 2 의 **40 행을 하드웨어가 통째로 안 그린다**.
- 원인 확정: 엔진은 화소의 **왼쪽 위 모서리**에서, GL 은 **중심**에서

이 회차의 도구는 `test/openstep-mga-mesa-coverage-test.c`,
`test/coverage-sweep.csh`, `test/coverage-compare.py` 로 남겼다.


§3-25 를 고친 뒤, 같은 잘린 삼각형이 소프트웨어로 42472 화소, 하드웨어로
42245 화소였다 — 227 차이, 0.53%.

**"두 래스터라이저의 알려진 불일치"라고 적었지만 그것은 논증이지 측정이
아니다.** 넓이 하나로는 가장자리 규칙 차이와 **속이 빈 것·이음매·잘림
분해 오류**를 구분할 수 없다.

제대로 재려면 **마스크 두 장**을 떠서:

- `소프트웨어만`, `하드웨어만`, 교집합, 각각의 경계 상자, 행별 런 길이
- 감는 방향을 뒤집고, 좌표를 평행이동하고, 잘림이 만든 대각선에서도

**무해한 차이는 가장자리의 한 화소 띠**이고 속에 구멍이 없다. 하드웨어만
칠한 화소, 가장자리에서 떨어진 구멍, 삼각분할 이음매의 불연속, 순서에 따라
달라지는 것은 전부 결함이다.

그리고 "같은 삼각형"이라는 말도 부정확하다 — Mesa 가 먼저 자르므로 원본
하나가 여러 개로 도착한다(거절 2 → 가속 3).

## 3-28. ~~프레임 측정 두 도구가 같은 작업을 다르게 잰다~~ — **해결(2026-08-24)**

`tmc` 와 `tcp` 가 **같은 작업**(clear + 작은 삼각형 + `glFinish`, 512×384)을
이렇게 잰다:

```
tmc : 306 ms      tcp : 160 ms
```

어긋남이 ~146 ms — 표면을 한 번 더 훑는 값과 같다. 통제가 나은 쪽은 `tcp` 다:
문맥 하나, 워밍업 있음, 두 팔이 같은 문맥. `tmc` 는 크기마다 문맥을 새로 만들고
부순다.

`RenderFinish` 에도 미러가 걸려 있어 프레임당 두 번 훑는 것 아니냐는 가설을
세웠으나, `tcp` 에서 삼각형을 넣어도 비용이 **+0.031 ms** 라 그 가설은 반증됐다.

### 원인: 두 도구는 같은 작업을 잰 적이 없었다

`tcp` 는 **투영 행렬을 한 번도 세우지 않는다** — 파일 어디에도 `glOrtho` 도
`glMatrixMode` 도 없었다. 단위행렬 아래서 `glVertex2d(10,10)` 은 w=1 인 클립
좌표 10 이고 세 꼭짓점 전부가 부피 밖이므로, **Mesa 는 삼각형을 통째로 버렸다.**
그 도구가 찍어 온 "the triangle cost +0.031 ms" 는 전부 **아무것도 아닌 것의
값**이었고, 아무것도 래스터화하지 않은 프레임은 `RenderFinish` 에 닿지 않으므로
미러도 하지 않는다. 어긋남 ~146 ms 가 정확히 미러 하나였던 이유가 이것이다.

그리고 **위에 적어 둔 반증도 무효다.** "삼각형을 넣어도 +0.031 ms 라 미러 두 번
가설은 반증됐다" 는 존재한 적 없는 삼각형에 근거한 것이었다. 실제로는 두 번
훑는다(아래).

### 고친 것과 재측정 (512×384)

`tcp` 에 투영을 넣고, 두 도구 모두에 **실제로 그린 배치 수와 미러 호출 수**를
찍게 했다. 배치가 0 이면 큰 글씨로 경고한다 — 같은 함정을 다시 밟지 않도록.

```
tcp  engine clear only        146.667 ms   (미러 호출 2/프레임)
tcp  Mesa   clear only        160.550 ms   (미러 호출 2/프레임)
tcp  engine clear + triangle  292.488 ms   (배치 20, 미러 호출 3/프레임)
tcp  Mesa   clear + triangle  306.567 ms   (배치  0, 미러 호출 3/프레임)
tmc  frame at 512x384         291.976 ms   (배치 20, 미러 호출 3/프레임)
```

`tcp` 의 Mesa 쪽과 `tmc` 가 **0.19 % 안에서 일치한다.** 예전의 "160 ms" 는
`tcp` 의 **clear 만 있는** 팔이었다.

## 3-28b. ~~한 프레임이 표면을 두 번 훑는다~~ — **해결(2026-08-24)**

§3-28 을 고치고 나니 훨씬 큰 것이 나왔다. `tmc` 를 세 크기에서:

```
128x96      18.682 ms   1520.35 ns/화소
512x384    291.976 ms   1485.07 ns/화소
1024x768  1169.741 ms   1487.40 ns/화소
```

5.36 MB/s 로 표면을 **두 번** 읽으면 4바이트 × 2 / 5.36e6 = **1492.5 ns/화소**.
맞춘 훑기 횟수: 2.037 / 1.990 / 1.993 — 세 크기 모두 정확히 둘이다.

그리고 clear 를 빼면 정확히 하나가 빠진다:

```
clear + triangle + finish   291.973 ms
triangle + finish           145.530 ms
```

**clear 는 엔진에서 돌고 프로세서로 화소를 하나도 쓰지 않는데** 요청하는 것만으로
146 ms 가 붙는다. 그건 clear 가 아니라 **clear 가 자기 렌더 괄호를 갖기 때문**이다
(`buffers.c:296-313`) — 이 백엔드는 괄호가 끝날 때마다 미러한다. 그 사이에 앱의
배열을 읽은 사람은 아무도 없으므로 **첫 번째 훑기는 순수한 낭비다.**

### 호출 3회, 복사 2회 — 세 번째는 어디서 오나

측정: clear 만 있는 프레임은 **호출 2회에 복사 1회**, clear+삼각형은 **호출 3회에
복사 2회**. 세 번째는 `RenderFinish` 가 아니다 — `glFinish` 가 부르는
`Driver.Finish` 이고(`context.c:2017-2023`), 이 백엔드는 거기에 같은 함수를
건다(`OpenStepMGAMesaHook.c:1818-1819`, `Driver.Flush` 도 같다). 짝이 되는
`RenderStart` 가 없으므로 직전 복사가 지운 `bufDirty` 가 그대로여서 복사하지
않는다. 계수기는 **복사가 아니라 호출**을 세며, 헤더 설명이 그렇게 안 되어 있어서
같이 고쳤다.

### 천장 수정 — 다만 범위를 붙여서

`3-32` 의 표(640×480 4.4 fps, 1024×768 1.7 fps)는 **훑기 한 번**으로 계산한
것이다. **clear + 그리기 + finish** 라는 잰 작업부하에 대해서는 2배 낙관이고,
그 작업부하의 천장은 **640×480 2.18 fps · 800×600 1.40 fps · 1024×768 0.85 fps**
이다.

이것을 "보편적 천장" 이라고 부르지는 않는다(교차검토 지적, 채택): clear 만 있는
프레임은 훑기 하나, 그리기만 있는 프레임도 하나이고, **한 프레임에서 여러 번
플러시되는 장면은 더 늘어날 수 있다** — 괄호마다 복사이기 때문이다. 그건 아직
재지 않았다.

### 왜 그냥 건너뛰지 않는가

clear 괄호의 미러를 미루면, 앱이 `glClear` 뒤 다음 괄호 전에 자기 배열을 들여다볼
때 낡은 것을 본다. 이 백엔드가 아는 지점은 `OSMesaMakeCurrent`·`glFinish`·
`glFlush`·`glReadPixels`·문맥 파괴뿐이고, **GL 호출 사이의 평범한 CPU 읽기는
알 수 없다.** 그러므로 지금 계약에서는 못 미룬다 — `3-32` 가 말한 "소유권 계약을
바꿔야 한다" 와 같은 결론이다.

### 들어간 것 (2026-08-24, 라이브러리만 — 재부팅 불필요)

계약을 안 건드리고 첫 훑기를 없앴다. 전면 clear 뒤 표면은 **상수 한 개**이고, 그
상수를 앱 배열에 쓰는 것은 시스템 RAM 쓰기다(1344 MB/s 대 5.36 MB/s, **250배**).
배달되는 바이트는 글자 그대로 같으므로 계약은 그대로다.

기구는 **다음 soil 이 가져가는 일회용 표시**다. `RenderStart` 의 무조건 더럽힘은
바꿀 수 없으므로(직접 기록자가 보이지 않는다) clear 가 표시를 남기고, 바로 뒤에
열리는 그 괄호만 그것을 쓴다. `Driver.Clear` 는 `buffers.c:280` 한 곳에서만 불리고
`RENDER_START` 가 `:296` 에서 바로 뒤따른다(전수 grep).

**조용히 프레임을 잃는 실패 하나**는 두 겹으로 막았다: 스팬 기록이 있으면(=Mesa 가
그렸으면) 평범한 미러로 돌아가고, **배치 수가 늘었으면**(=엔진이 그렸는데 스팬으로는
보이지 않으면) 역시 돌아간다.

**낱말은 표면에서 읽지 않는다.** 처음 계획은 submit 뒤 픽셀 하나를 읽는 것이었는데
**교차검토가 잡았다** — 하필 §3-18 이 "아무것도 정하지 못하는 유일한 오프셋" 이라고
기록해 둔 창의 첫 낱말이었다. 대신 OSMesa 자신이 `PACK_RGBA` 로 만든 `clearpixel`
을 건네받는다. 소프트웨어 clear 가 쓰는 바로 그 낱말이다.

전제와 검증은 재고 나서 넣었다 — `tcu`(네 색, 196608 화소 전부 동일하고 소프트웨어와
비트까지 같음, 대각선 이음매 없음)와 `tuf`(7개 주장 전부 통과, 그 중 하나가 "clear
뒤에 그린 삼각형이 살아남는가"). 설계와 수치는 `M1_4ED`.

```
                      전         후
clear 만 (512x384)   146.667    1.517 ms      (96배)
clear+삼각형          292.488  147.616 ms      (1.98배)
ns/화소 (세 크기)     1485~1520  749~807       (훑기 한 번 = 746.3)
```

천장(clear+그리기): 640×480 **4.36 fps**, 800×600 **2.79 fps**, 1024×768 **1.70 fps**.

남은 한 번의 훑기는 **그린 것을 배달하는 것**이고, 지금 계약에서는 줄일 수 없다.

## 3-29. `reach` 가 한 시간 넘게 걸린다 (미해결, 2026-08-24)

`reach`(§1~§87 텍스처 프로브)가 통과는 하는데 한 시간이 넘는다. 대부분 §87
알파 시험 구간이고, 프로세스는 CPU 를 거의 쓰지 않으면서 느리다 — 제출 RPC 안에서
자고 있다는 뜻이다.

**퇴행이라는 증거는 없다.** `nxrun` 의 타임아웃은 총 시간이 아니라 **무출력**
시간이고 `reach` 는 계속 출력을 내므로, 예전에 얼마나 걸렸는지 잰 적이 애초에
없다. 정상이라는 증거도 없다.

## 3-30. ~~`glResizeBuffersMESA` 와 가속 깊이~~ — **닿지만 무해하다(2026-08-24)**

`UseSoftwareDepthBuffer` 가 거짓이면 그 확장이 깊이 재할당을 건너뛴다
(`Mesa-3.4.2/src/buffers.c`). 가속 중에는 거짓이므로, 매핑된 깊이 표면이 **낡은
치수로 기술된 채** 남을 수 있다.

**닿는다. 그것도 확장을 통해서가 아니라 항상.** `matrix.c:1495` 가
`gl_Viewport` 끝에서 무조건 부르므로, 앱이 `glViewport` 를 할 때마다 실행된다.
"확장을 안 쓰면 안 닿는다" 는 전제부터 틀렸다.

그런데도 **두려워한 일은 일어날 수 없다.** 사슬은 이렇다:

1. `buffer_size`(`osmesa.c:1028`)가 돌려주는 것은 `osmesa->width/height` 이고,
   그 둘은 `OSMesaMakeCurrent` 에서만 바뀐다.
2. 색 표면 바인딩(`OpenStepMGAMesaBuffer.c:647-672`)은 **치수가 다른 재바인딩을
   거절한다** — 표면은 하나뿐이므로 크기를 바꿀 수 없다.
3. 거절되면 `osmesa.c:561-568` 이 `osmesa_leave_accel` 로 가속 자체를 벗는다.
   깊이는 소프트웨어로 되돌아가고(플래그까지), 내용은 복사되고, 표면은 풀린다.
4. 깊이 할당기(`:293`)도 색 표면과 치수가 정확히 같을 때만 내준다.

즉 **표면이 물려 있는 동안에는 `osmesa->width/height` 가 표면의 치수와 항상
같고**, 그래서 `ResizeBuffers` 는 `UseSoftwareDepthBuffer` 검사줄에 닿기 전에
"안 바뀌었다" 로 돌아간다. 치수가 바뀌는 유일한 길은 재바인딩이고, 그건 표면을
푼다.

**말을 정확히 해 둔다(교차검토 지적):** 새 크기의 재바인딩은 "가속인 채로 크기가
바뀌는" 것이 **아니라 가속에서 떨어지는 것**이다. `OSMesaMakeCurrent` 자체는
성공을 돌려주지만 그건 소프트웨어로 그린다는 뜻이다.

**있기는 한 창(窓), 닿을 수는 없는 것:** `OSMesaMakeCurrent` 는 `ctx->width/
height` 를 새 값으로 **먼저** 쓰고(`osmesa.c:529-531`) 그 다음에 할당기를 부르며,
할당기는 진입하자마자 `bufBound` 를 놓는다(`OpenStepMGAMesaBuffer.c:582-595`).
그 사이에는 `buffer_size` 가 새 치수를, 표면 기술은 옛 치수를 말한다. 그 구간에
GL 호출이 끼어들 수 없으므로 도달 불가이지만, 도달 불가인 이유가 "코드가 막아서"
가 아니라 "그 사이에 아무도 부르지 않아서" 라는 점은 적어 둔다.

**스텐실·누산은 무관하다.** 포팅이 건드리는 소프트웨어 플래그는 깊이와 알파뿐이고
(`osmesa.c:576-624`), `_mesa_ResizeBuffersMESA`(`buffers.c:560-572`)는 각 버퍼를
자기 플래그가 참일 때만 다시 잡는다. 스텐실·누산은 계속 소프트웨어 소유이므로
크기가 진짜로 바뀌면 정상적으로 다시 잡힌다. 알파를 되켜지 않는 이유는
`leave_accel` 주석에 적혀 있고 여전히 유효하다.

## 3-31. current 인 채로 앱이 자기 버퍼를 직접 쓰는 경우 (구조적, 2026-08-24)

바인딩 때 호출자의 버퍼를 들여오도록 고쳤다(`M1_4EC`). 그러나 **current 인 채로**
앱이 그 메모리를 직접 쓰면 아무도 볼 수 없고, 다음 프레임은 더 이상 일치하지
않는 비디오 메모리에서 그린다.

재바인딩이 두 쪽을 다시 맞추는 경계이며, 그렇게 문서화했다. 고칠 방법은 표면을
치환하지 않는 것뿐이므로 **결함이 아니라 계약**으로 남긴다.

## 3-32. 미러가 프레임의 전부이고, 그것은 장부가 아니라 계약 문제다 (2026-08-24)

`glClear` 를 가속하고 나니 512×384 프레임 146.7 ms 중 clear 가 ~0, 삼각형이 ~0,
나머지 전부가 미러다. 미러의 실제 속도를 두 크기에서 쟀다:

```
128x96 :    49152 B /   9.753 ms ->  5.04 MB/s
512x384:   786432 B / 146.665 ms ->  5.36 MB/s
```

두 크기가 일치한다 — 이 기계의 **uncached VRAM 읽기 속도**이고, "VRAM 에서 그리고
시스템 RAM 으로 배달한다"는 구조가 프레임마다 무는 값이다.

**아래의 상한은 훑기 한 번을 가정한 것이고, 실제로 잰 clear+그리기 프레임은 두 번
훑는다 — `3-28b` 참조. 그 작업부하의 천장은 이 표의 절반이다.**
훑기 한 번 기준: 640×480 4.4 fps, 800×600 2.8 fps, 1024×768 **1.7 fps**.
clear+그리기 기준(`3-28b` 을 고치기 **전**): 640×480 2.18 fps, 800×600 1.40 fps,
1024×768 0.85 fps.
clear+그리기 기준(**지금**, clear 가 표면을 읽지 않고 배달한 뒤): 640×480
**4.36 fps**, 800×600 **2.79 fps**, 1024×768 **1.70 fps** — 훑기 한 번으로 돌아왔다.

**더티 사각형은 이 작업부하를 못 돕는다** — 프레임마다 표면 전체를 지우면 바뀐
화소가 전부이고, 전부는 어차피 배달해야 한다. 부분만 바뀌는 작업부하에서만 값이
있으므로, 그것부터 재야 판단할 수 있다. 계획과 그것을 접은 이유는 `M1_4EB`.

넘으려면 **소유권 계약**을 바꿔야 한다(앱이 실제로 볼 때만 읽어오기, 또는 표면을
치환하지 않기). 그건 재고 나서 설계한다.

## 3-33. ~~mmap 창의 시작이 `rowBytes` 가 아니라 `width*bpp` 에서 나온다~~ — **해결(2026-08-24, 재부팅 대기)**

오프스크린 창의 시작을 정할 때 보이는 표면의 끝을 `wr->width * bytesPerPixel *
wr->height` 로 잡는다(`OpenStepMGAReplacementDisplay.m:2164-2166`). 디스플레이의
`rowBytes` 가 `width * bpp` 보다 크면(행마다 패딩이 있으면) 이 값이 실제 끝을
**과소평가**하고, 오프스크린 창이 스캔아웃의 꼬리와 겹칠 수 있다.

### 재고 나니 질문이 틀렸다

`rowBytes` 에는 **대입이 딱 하나** 있고(`.m:2073`), 그 식이 `.m:2164` 의 식과
글자까지 같다: `width * bytesPerPixel`. 그러니 "행마다 패딩이 있으면" 이라는 전제
자체가 이 드라이버에서는 성립하지 않는다. 패딩은 어디서도 만들어지지 않는다.

진짜로 물어야 했던 것은 **하드웨어가 스캔아웃하는 pitch 가 그 값과 같은가** 이다.
그건 `rowBytes` 가 아니라 CRTC[19] + CRTCEXT0 두 비트이고,

```
wd = width >> (4 - bppShift)        (.m:1800)   bppShift: 32bpp 2, 16bpp 1, 8bpp 0
pitch = wd * 16 bytes
```

단위가 16바이트라는 것은 1024×32bpp 에서 `wd=256`, `256*16=4096=1024*4` 로 맞고,
X.Org 의 mga 드라이버가 **같은 식과 같은 시프트 표**를 쓴다(`mga_dacG.c:1380`,
`mga_driver.c:2243-2246`) — 독립 구현이 같은 답을 낸다.

**시프트는 버림이다.** 행이 16바이트의 배수가 아니면 pitch 가 행보다 **짧게**
프로그램되어 화면이 어긋난다. 그러니 원래 걱정했던 "창이 스캔아웃 꼬리를 덮는다"
보다 **먼저, 더 크게** 깨진다.

파이썬으로 게시 중인 5해상도 × 5포맷 = **25조합 전수 확인: 불일치 0.** 필요한
배수는 32bpp 4화소·16bpp 8화소·8bpp 16화소이고 게시 폭은 모두 16의 배수다.

엔진 쪽도 따로 본다. X.Org 는 G 계열 스캔아웃 폭을 8bpp 64화소·16/32bpp 32화소로
올림한다(`mga_dacG.c:2291-2294`). 우리 폭 중 800 은 64의 배수가 아니지만, **엔진을
쓰는 경로는 전부 `bytesPerPixel != 4` 에서 되돌아가고**(`.m:2572, 2811, 2972,
3064, 3482, 3529, 4462, 5344, …`) 32bpp 기준 32화소 배수는 다섯 폭 모두 만족한다.

### 들어간 것 (설치됨 · 재부팅 대기)

산술은 그대로 두고 **검사 하나**를 넣었다 — `osmgaModePitchIsExact()`, 그리고
`selectModeFromConfig` 끝에서 고른 짝이 그것을 통과하지 못하면 기본 모드로
되돌린다. 오늘은 절대 발동하지 않는다. 넣는 이유는 이것이 **코드의 성질이 아니라
표 두 개에 적힌 숫자의 성질**이기 때문이고, 다음에 폭을 추가하는 사람이 그것을
깨는 자리이기 때문이다(`OSMGA_CMD_MMAP_BASE` 검사와 같은 취지).

**창 시작만 올림하지 않는 이유**: 같은 가정을 쓰는 자리가 셋이다 — 게시되는
`rowBytes`/`memorySize`(`.m:2073-2080`), 부팅 때 화면을 지우는 루프
(`.m:2514-2519`), 그리고 mmap 창의 시작(`.m:2164`). 창만 고치면 나머지 둘과
스캔아웃 어긋남이 그대로 남는다. 진짜로 패딩 pitch 를 지원하려면 pitch 를 올림해
**프로그램하고 그것을 `rowBytes` 로 게시하고** 모든 범위를 거기서 계산해야 한다.
그건 이 항목이 요구한 적 없는 별개의 기능이다.

### 덮지 않는 것

`rowBytes` 를 저장소 안에서 다시 쓰는 곳은 없다(전수 grep). 그러나
`IOFrameBufferDisplay` 나 윈도서버가 **게시 뒤에 구조체를 고치지 않는다는 증명은
없다** — 둘 다 바이너리다. 지금 쓰는 모드에 대해서는 간접 증거가 있다: 엔진
경로들이 매 호출 `di->rowBytes / 4` 를 새로 읽어 목적지 보폭으로 쓰는데
(`.m:3535, 4367, …`) 1024×768×32 에서 그림이 맞는다. 다른 모드에 대해서는 재지
않았다.
