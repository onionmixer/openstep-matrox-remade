## 0. 지금 어디까지 왔나 (2026-08-24)

3D 가 **GL 1.1 의 래스터화 상태를 거의 다 표현한다.** 아래는 전부 실기에서
잰 것이고, 재지 않은 것은 재지 않았다고 적었다.

| | 상태 |
|---|---|
| 커버리지 | 시험 도형 전부 **규칙과 정확히 일치**, 소프트웨어와도 일치 |
| 색·알파 보간 | 화소 중심 정착 + 반올림. 소프트웨어와 **99% 이상 동일**, 남은 차이는 1 단계 |
| 깊이 보간 | 화소 중심 정착. 남은 계통 오차는 출력 절단 **−0.5 코드** 하나 |
| 공유 변·이음매 | 색·깊이 모두 **이음매 없음**. fan·strip·512 삼각형 메시까지 |
| 혼합 프레임 | 한 프레임 안에 엔진과 소프트웨어가 섞여도 서로 화소를 잃게 하지 않는다 |
| 텍스처 | `GL_RGB`·`GL_RGBA`, `GL_REPLACE`·`GL_MODULATE`, `GL_NEAREST`·`GL_LINEAR`, 감싸기 셋, **원근(q≠1) 포함**. 밉맵은 조사를 마치고 **닫았다** — 아래 |
| 깊이 비교 | **일곱 전부**. `GL_NEVER` 만 거절 — `zmode` 1 은 예약값이지 NEVER 가 아니다(Matrox 해독기) |
| 깊이 쓰기 | **`glDepthMask(GL_FALSE)` 동작**. 접근 유형이 그것이다 — ZI 는 비교하고 쓰고, I 는 비교만. 실측 |
| 블렌딩 | GL 1.1 의 소스·목적지 인자 전부. 엔진 산술을 262144 표본으로 적합(곱 두 번, 더하고, **한 번** 반올림) |
| 알파 시험 | 일곱 전부. **텍스처 스테이지의** 알파를 비교하고, 버린 프래그먼트는 깊이도 안 쓴다 |
| 폴리곤 오프셋 | python 과 정확히 일치 |
| 시저 | 엔진의 목적지 클립(`CXBNDRY`/`YTOP`/`YBOT`)으로. 경계 아홉 점·빈 상자·표면 밖·부분 겹침 전부 소프트웨어와 화소 일치 |
| `glClear` | **엔진 가속**, 그리고 지운 표면은 **읽지 않고 배달**한다 — 512×384 clear 만 146.7 → **1.5 ms**, clear+삼각형 292 → **147.6 ms** |
| 표면 계약 | 호출자의 버퍼를 바인딩 때 **들여온다**. 가속을 놓을 때 깊이를 **보존한다** |
| 보폭 | 32 의 배수가 아닌 너비도 **표면을 패딩해 가속**한다(색 전용; 깊이는 소프트웨어로) |
| 프레임 비용 | 한 번의 표면 훑기 — 640×480 4.4 fps, 800×600 2.8 fps, 1024×768 1.7 fps. VRAM 낱말 단가 실측: 쓰기 31.7 MB/s, 읽기 5.49 MB/s |

**표현하지 못하는 것**(전부 근거 있음): 밉맵(아래), `GL_NEVER`(예약 인코딩),
`GL_SRC_ALPHA_SATURATE`(인자 8 은 색에 `SRC_ALPHA`·알파에 `ONE` 로 실측됨),
스텐실, polygon smooth/stipple, **깊이만 지우기**(`PLNWT` 미노출).

**밉맵은 미개척이 아니라 닫힌 조사다.** `M1_4D9_MIPMAP_PLAN.md` 가 정본이다.
프래그먼트마다 레벨을 고르는 절반(MIN/MAG 두 필드와 화소 단위 λ)은 실재하고
이미 쓰이고 있으나, **밉맵 비트 자체가 이 경로에서 무력하다**: 네 모드
(`mm1s`·`mm2s`·`mm4s`·`mm8s`)가 아핀과 원근 양쪽에서, 네 비율 전부에서 비밉맵
대응물과 **64/64 화소 동일**하고, 합법적인 텍스처 폭 여덟 가지 어느 `rfw` 도
깨우지 못한다. 왜인지는 **가르지 못했다** — WARP 가 front-end 일 수도 있고,
드라이버가 한 번도 건드리지 않는 레지스터의 전역 상태가 막고 있을 수도 있다.
결론은 교차검토까지 받았다: **이 경로에서 구현하지도 광고하지도 않는다.**
넣으려면 훨씬 큰 별개의 작업이다.

**다음에 할 일의 우선순위**:

1. **§3 은 거의 비었다.** 남은 것은 `3-11`(스레드, 의도적으로 미룸)과
   `3-35`(클라이언트별 소유권 — 이 인터페이스로는 표현 불가, 인터페이스 변경이
   필요하다) 둘뿐이고, `3-31`·`3-32` 는 결함이 아니라 기록된 계약이다.
2. **VRAM 증명치를 올릴 것인가**가 지금 가장 값이 큰 결정이다. 탐침은 16 MiB
   전 구간이 실재한다고 말하고, 올리면 오프스크린 창이 3 → 12 MiB, 1024×768 에서
   텍스처가 **없음 → 7.5 MiB** 가 된다. 다만 이 값은 격리 경계이므로 `1-2` 에
   적어 둔 조건을 먼저 갖춰야 한다.
3. 성능의 벽은 `3-32` 다 — 프레임마다 표면을 시스템 RAM 으로 배달하는 구조이고,
   장부를 고쳐서 넘는 벽이 아니다. `3-28b` 에서 두 번 훑던 것을 한 번으로 줄인
   것이 그 안에서 할 수 있는 전부에 가깝다.
4. §1 의 나머지 미착수(dual head, DDC/EDID 런타임, G400)는 그대로다.

**닫힌 것** (2026-08-22~25): 텍스처 원근, 깊이 비교 일곱, 블렌딩 인자,
알파 시험, 폴리곤 오프셋, 시저, 깊이 마스크, `glClear` 가속, 표면 인바운드
복사, 후퇴 시 깊이 보존, **지운 표면의 무읽기 배달**(`3-28b`), **보폭 패딩**
(`3-22`), **제출 뒤 낡음은 커널의 읽기가 고친다**(`3-18`), **커맨드 리스트
노출**(`3-34`), **DMA 시간초과 회복**(`3-15`, 절반), **`reach` 는 3 분이다**
(`3-29`).

알려진 값으로 남기는 것 — 결함이 아니라 두 규칙의 차이다:
* **혼합 프레임의 실금**: 하드웨어 삼각형과 소프트웨어 삼각형이 변을
  공유하면 폭 1의 빈 화소가 남을 수 있다.  512 삼각형 메시에서 5 화소이고
  **메시가 길어져도 커지지 않는다**(`M1_4B6` §3).
* **좌표 양자화**: 꼭짓점이 1/256 격자 밖이면 신탁과 어긋난다.  288 삼각형
  56000 화소에서 52 화소(0.09%).  격자 위에 있으면 512 삼각형에서 0.
* **블렌딩의 한 단계**: 엔진은 한 번 반올림하고 Mesa 는 절사한다.  설계상
  차이이고, 장면 채점이 두 단계 이내로 묶어 둔다.

## 0-1. 왜 §1·§2 는 멈춰 있었나 (2026-08-19 기준, 그대로 둔다)

남은 항목은 전부 (a) 하드웨어가 없어 확인 불가, (b) 이득이 측정되지 않아
착수 근거가 없음, (c) 순수 정리 중 하나다. 3D 작업이 드라이버 구조를 크게
바꿀 가능성이 있으므로, 지금 손대면 두 번 하게 되는 것들이 섞여 있다.

## 1. 기능 — 미착수, 근거 있음

### 1-1. 두 번째 head (dual head) — **범위에서 뺀다(2026-08-25, 결정)**
G450은 dual head지만 secondary CRTC/DAC 경로를 한 번도 건드리지 않았다.
`docs/R6_G400_G450_REGISTER_DIVERGENCE.md`에 레지스터 차이가 일부 정리돼
있으나 secondary 계열은 조사 자체가 미완이다.
- **막는 것**: 없음. 순수 미착수.
- **필요 조건**: 두 번째 모니터 실물.

**하지 않기로 했다.** 이유는 하드웨어가 없어서가 아니라 **OPENSTEP 이 dual head
에 어울리는 OS 가 아니기 때문**이다(프로젝트 결정). 드라이버 쪽으로는 secondary
CRTC/DAC 조사가 미완인 채로 남고, 그 상태 그대로 두는 것이 결론이다 — 언젠가
누군가 필요해지면 `R6_G400_G450_REGISTER_DIVERGENCE.md` 가 출발점이다.

이 항목은 이제 **"안 한 일"이 아니라 "안 하기로 한 일"** 이므로, 남은 작업을 셀
때 빼고 센다.

### 1-2. ~~VRAM 자동 검출~~ — **들어갔고 잰 값이 맞았다(2026-08-25)**
`MGA Memory Size`는 보수적 고정 16 MiB다. 실제 보드는 32 MiB일 가능성이
있으나(`R2` 감사의 `0d43` → G45FMDVP32DSF 후보) **한 번도 실측하지 않았다.**
- **막는 것**: 없음. 16 MiB는 안전 하한.
- **주의**: 오프스크린 VRAM 창(S4a)이 이 값에 의존한다. 늘리려면 S4a의
  가드 범위도 함께 재검증해야 한다.

#### 왜 지금 하는가

`OSMGA_S1_VRAM_PROVEN`(7 MiB)이 아래를 전부 묶는다 — 오프스크린 창이 3 MiB 로
나오고, Mesa 백엔드가 거기서 색·깊이·텍스처 아레나를 잘라 쓴다. 오늘 재보니
**1024×768 에서 아레나가 비어 있다**(색+깊이만으로 창을 넘는다). 즉 디스플레이
자기 크기에서 텍스처가 거절되는데, 이유는 보드에 메모리가 얼마나 있는지 아무도
확인한 적이 없다는 것뿐이다. 매핑은 16 MiB 다.

```
증명치 7 MiB  -> 창 3.0 MiB   (지금)
        16 MiB -> 창 12.0 MiB  (4배), 1024×768 에서 텍스처 7.5 MiB
```

#### 왜 X.Org 의 탐침을 그대로 쓰지 않는가

`MGACountRam`(`mga_driver.c:1061`)의 OPTION 레지스터 방식은 **믿을 수 없다며
`#if 0` 으로 꺼져 있다**(:1069-1073). 일반 경로(:1253-1265)는 단계마다 0xAA 를
쓰고 되읽어 남아 있는 가장 높은 곳을 답한다 — **쓰기가 남았는가**를 묻는 것이다.
구멍 밖 접근이 버려지지 않고 **별칭**이면 16 MiB 의 쓰기가 8 MiB 에 앉고 16 MiB
의 읽기가 그걸 되읽어, 8 MiB 보드가 16 으로 보고된다. 조용히 틀리고 망가지는 것은
텍스처다.

#### 들어간 것: 측정 전용 (`M1-4F0`)

**아무 동작도 바꾸지 않는다.** `OSMGA_S1_VRAM_PROVEN` 은 그대로고 창 크기도
그대로다. 클라이언트 수명 때와 같은 순서 — 계측하고, 재부팅하고, 읽고, 그 다음에
정한다.

묻는 질문이 다르다: **후보들이 서로 구별되는가.** 후보마다 자기 오프셋을 담은
서명을 주고, 전부 쓴 뒤에 전부 읽어, 자기 서명을 되읽은 것만 센다. 별칭이면 한
후보가 남의 서명을 들고 있고, 그건 "쓰기가 남았는가" 로는 안 보인다.

**비캐시 별칭으로만** 한다(`osmgaMapUncachedBlock`). 이 드라이버가 이미
"프레임버퍼 매핑의 캐시 속성은 미증명이고 `volatile` 로는 코히런트하지 않다" 고
적어 두었다 — 평범한 매핑으로 재면 CPU 캐시에서 되읽혀 **비디오 메모리가 그 쓰기를
받지 않았는데도 통과**할 수 있다. **교차검토가 잡았고, 첫 초안이 그랬다.**

**언제**: 모드를 프로그램한 뒤 **화면이 아직 블랭크인 동안.** 이 드라이버가
구멍을 소유하고 아무것도 스캔되지 않는 유일한 순간이다. 그 전에는 콘솔이 아직
거기 있을 수 있고, "우리 것이 표시되지 않는다" 는 같은 주장이 아니다(이것도
교차검토 지적).

후보는 **1 MiB 마다 두 낱말**(첫·마지막), 그림 위로 한 MiB 띄운 곳부터 16 MiB
까지 — 1024×768 에서 5..15 MiB 의 22 곳. 건드린 낱말은 전부 저장했다가 되돌리고,
되돌리지 못하면 그 사실을 로그로 남긴다.

**증명하지 못하는 것**: 1 MiB 에 두 낱말로는 구간 안의 구멍이나 죽은 주소선,
부분 디코드를 배제할 수 없다. 잰 것만 말한다 — 표본한 주소들이 서로 구별되고
넣은 값을 들고 있다.

#### 잰 값 (2026-08-24 부팅)

```
5242880 .. 16777212   후보 22 곳 전부 distinct, 남의 서명을 든 것 없음
sampled distinct up to 16777212 bytes (16 MiB); 증명치는 7340032 그대로
```

복원 실패 로그 없음. 디스플레이 정상, `M1-0` PASS, 회귀 통과, 장면 기준선 불변.
**보드에는 매핑된 16 MiB 전 구간에 걸쳐 실메모리가 있다**(표본 기준).

#### 탐침 자신의 결함을 하나 고쳤다 (교차검토 지적)

저장과 쓰기를 **한 패스**에서 하고 있었다. 별칭이 있으면 뒤 후보의 "원본" 이 이미
앞 후보의 서명이고, 마지막에 그걸 되돌리면 **비디오 메모리에 탐침 서명이 남는다**
— 탐침이 찾아내려는 바로 그 보드를 탐침이 망가뜨린다. 이번 보드에는 별칭이 없어
실제 피해는 없었지만, 그건 운이지 설계가 아니다. 저장 패스를 분리했고, **복원 뒤
되읽어 확인하는 패스**도 넣었다.

#### 들어간 것 2: 증명해야만 넓힌다 (`M1-4F1`, 재부팅 대기)

상수를 손으로 올리는 대신, **넓힐 수 있는 천장**을 사람이 정하고
(`OSMGA_S1_VRAM_CEILING` = 12 MiB) 그 아래 구간이 **이번 부팅에 실재함을
보여야만** 창을 거기까지 넓힌다. 못 보이면 보수적 경계 그대로다 — fail-closed.

**왜 12 인가.** 이득은 거의 다 여기 있다(1024×768 텍스처 아레나 없음 → 약 3.5
MiB, 16 이면 7.5). 위 4 MiB 는 보드가 무언가를 예약한다면 있을 자리라 남긴다.
**하드웨어 커서는 그 무언가가 아니다** — 이 드라이버는 모드셋마다 커서 베이스에
0, 커서 제어에 0 을 쓴다(`osmgaInitDAC[0x04..0x06]`; X.Org 의 `MGAGHideCursor`
가 커서를 끌 때 쓰는 값이 같은 0 이다). 그 밖에 무엇이 있는지는 모르고, 그래서
여백을 두는 것이지 논증으로 지우지 않는다.

**어떻게 증명하나.** 열리는 구간의 **모든 페이지**에 자기 오프셋을 담은 서명을
첫 낱말과 마지막 낱말에 넣고, 전부 넣은 뒤 전부 읽어 확인한다. 구간 **아래에
증인**을 하나 두어, 위쪽 쓰기가 아래로 내려앉는 별칭을 잡는다. 통과하면 그
구간을 0 으로 채운다 — 이제 우리 것이고, 클라이언트에게 탐침 찌꺼기를 넘기지
않는다. 모드셋마다 약 167 ms(대부분 0채우기).

**왜 게시 뒤에 넓혀도 되나.** 창은 init 에서 보수적 경계로 게시되고 이 코드는
**끝을 올리기만** 한다. 올리는 것은 안전하다 — 이미 만들어진 매핑은 그대로
동작하고, 핸들러는 호출마다 끝을 새로 읽는다. **내리는 것**이라면 전혀 다른
이야기이고, 여기서 그렇게 하는 것은 없다.

#### 위험의 등급 — 교차검토와 다르게 본 곳

교차검토는 "잘못된 mmap PFN 은 임의의 RAM/MMIO 를 노출할 수 있다" 고 했다.
그건 **BAR 밖**을 넘겨줄 때 참이다. 핸들러가 돌려주는 것은 언제나
`frameBufferPhysical + off`(off < 16 MiB)이고 BAR0 는 `0xf8000000` 이다. 그리고
PCI 에서 아무도 디코드하지 않는 주소는 읽으면 `0xFFFFFFFF` 이고 쓰기는 버려지므로,
**없는 메모리는 이 시험을 조용히 통과하는 것이 아니라 떨어진다.**

그래서 틀렸을 때의 값은 **카드 자기 메모리의 화소가 깨지는 것**이지 카드 밖으로
나가는 길이 아니다. 그 등급이라서 부팅 시 측정에 근거해 넓힐 만하다고 판단했다.
시스템에 닿을 수 있는 실패였다면 하지 않았을 것이다.

#### 교차검토가 맞았고 반영한 것

- **커서 전제가 틀렸다.** "우리는 커서 베이스를 안 건드린다" 고 적었는데
  `osmgaDacSkip` 은 `0x00..0x03` 과 `0x07` 만 건너뛰고 `0x04..0x06` 은 건너뛰지
  않는다. 모드셋이 그것들을 쓴다 — 다행히 **0 을**, 즉 커서를 끄는 값을.
  결론은 같지만 근거가 반대였고, 그래서 계획의 1 단계(커서 레지스터 읽기)는
  **필요 없어져 없앴다.**
- **시험이 게시 뒤에 돌면 클라이언트를 못 지킨다.** `M1-0` 은 산술만 보고
  VRAM 에 접근하지 않으며, 창은 init 에서 게시되고 자가진단은 나중이다. 그래서
  넓히는 것 자체를 시험 뒤로 옮겼다 — 시험이 게시를 막는 것이 아니라, 시험이
  통과해야 넓어진다.

#### 밀도 요구는 접었고, 그 이유를 적는다

"5~16 MiB 가 연속임을 보이라" 는 조건은 **표본으로는 얻을 수 없다** — 더 촘촘히
떠도 간격보다 작은 구멍은 못 배제한다고 교차검토 자신이 답했다. 그래서 밀도를
올리는 대신 **열리는 구간만 페이지 단위로 전수**한다. 여는 곳을 다 보는 편이,
안 여는 곳까지 성기게 보는 것보다 낫다.

#### 실기 결과 (2026-08-25)

```
M1-4F1: 7340032..12582912, 640 pages, 0 wrong -> the window may be widened
M1-4F1: offscreen window widened to 4194304..12582912 (8192 KiB)
caps:   vram +4194304, 8388608 bytes            (전에는 3145728)
```

텍스처 아레나를 백엔드에 직접 물었다(`tar`, 신규):

```
 512x384   6.88 MiB   (512² 6 장)
 800x600   5.24 MiB   (512² 5 장)
1024x768   3.50 MiB   (512² 3 장)   <- 전에는 없음
```

**세 크기 모두 파이썬으로 미리 계산한 값과 바이트 단위로 같다**(차 0).
7208960 / 5496832 / 3670016 을 예측했고 그대로 나왔다. 예측과 측정이 우연히
맞을 값이 아니므로, 둘 중 하나가 틀렸을 가능성이 크게 줄었다.

회귀 PROBLEM 0 건, 14 개 시험 0 failing, 장면 기준선 불변, `M1-0` PASS.

#### 결과 교차분석에서 나온 것 (2026-08-25, 실기 적용됨)

**증인 하나로는 부족했다.** 교차검토가 짚었고 옳다 — 구간 바로 아래 한 낱말은
"바로 밑으로 내려앉았는가" 만 답하는데, 배제해야 할 것은 **구간이 전혀 다른 곳으로
디코드되는 것**(예: 0 번지의 보이는 프레임버퍼)이다. 그래서 아래 전체를
**512 KiB 마다 표본**해 각각 자기 값을 심고, **두 번** 확인한다.

그리고 **첫 확인은 구간의 두 페이지만 쓴 뒤**에 한다. 이 구간이 살아 있는 메모리로
디코드된다면 피해가 5 MiB 가 아니라 두 낱말에서 멈춘다.

**실패했을 때 0 으로 안 채우는 것은 의도다**(교차검토 지적에 대한 답): 실패는
"이 구간이 남의 메모리일 수 있다" 는 뜻이기도 하므로, 0 을 덮는 것은 같은 실수를
더 크게 하는 일이다. 서명은 그대로 두고 그 구간은 아무에게도 안 넘긴다.

**보이는 화면과 겹칠 수 있는 모드는 이미 막혀 있다.** 파이썬으로 세 모드를 확인:
1600×1200 만 자국(7,680,000)이 탐침 구간과 겹치는데, 그 모드는 애초에 **창을
게시하지 않으므로**(`start >= end`) 탐침이 돌지 않는다. 1024×768·1280×1024 는
자국이 구간 아래다.

**창을 넓히는 쓰기에 락은 쓰지 않는다.** i386 에서 정렬된 32 비트 저장이고 값은
**커지기만** 한다 — 이전에 허용되던 오프셋은 같은 PFN 으로 계속 허용되고, 새로
허용되는 오프셋은 그전에는 통과할 수 없었다. 그리고 `d_mmap` 은 VM 락을 든 채
불릴 수 있어 제출 경로의 락을 여기서 쓰면 안 된다(교차검토도 같은 답).

**회귀가 이제 이것을 지킨다**: `tar` 가 세 크기의 아레나를 보고하고, 1024×768 에서
**창이 색+깊이보다 크면 아레나가 있어야 한다**고 단언한다 — 이 보드의 숫자가 아니라
창과의 정합성으로 쓴 단언이라, 창이 작은 보드에서는 그렇다고 말하고 실패하지 않는다.

**증인 범위를 넣고 재부팅해 확인했다(00:36:53)**: 640 페이지 0 wrong, 창이 다시
8192 KiB 로 넓어졌고, **증인이 하나도 어긋나지 않았다**(어긋나면 그 자리와 값을
찍는 줄이 나온다 — 로그에 없다). 회귀 PROBLEM 0 건, `tar` 단언 통과, 장면 기준선
불변.

#### 이제 이 값은 상수가 아니다

`OSMGA_S1_VRAM_PROVEN`(7 MiB)은 **보수적 바닥**으로 남고,
`OSMGA_S1_VRAM_CEILING`(12 MiB)이 사람이 정한 **천장**이며, 그 사이는 부팅마다
증명해야 열린다. 다른 보드에 꽂으면 증명이 실패하고 7 MiB 로 돌아간다 —
그것이 이 설계의 요점이다.

#### 그 밖에 아직 안 한 것

올리자는 계획을 냈고 **교차검토가 반대했으며, 받아들인다.**

이 값은 용량이 아니라 **격리 경계**다. `osmgaMmapWindowEnd` 가 여기서 나오고
(`.m:2290`), 살아 있는 제출 경로가 그것을 `lim.colourEnd`/`depthEnd`/`texEnd` 로
쓴다(`.m:3747-3751`). 3 → 12 MiB 는 **장치를 열 수 있는 누구나 9 MiB 를 더 직접
읽고 쓸 수 있게 된다**는 뜻이다. 거짓 양성은 접근 제어 실패이고, 거짓 음성은 그저
가속을 잃는 것이다 — 두 방향의 값이 다르다.

그리고 이 탐침은 **모드 설정마다** 돈다. 자동으로 경계를 정하게 하면 그 경계가
기계가 도는 중에 바뀔 수 있다. 넓히는 방향은 사람이 보고 정하고, 좁히는 방향만
자동으로 두는 것이 안전하다.

**올리기 전에 갖춰야 할 것**(교차검토 목록, 채택):
- 5~16 MiB 가 표본이 아니라 **연속된 한 덩어리**라는 근거
- 언블랭크 뒤 오프스크린 VRAM 의 **소유자**(커서·펌웨어·WindowServer)
- 새 경계 근처의 시험 — 마지막 허용 페이지, 첫 금지 페이지, 높은 주소에서의
  엔진 색·깊이·텍스처 도달
- 그리고 `3-35`(클라이언트별 소유권 없음)가 12 MiB 에서는 더 무거워진다

#### 곁가지: 주석이 값을 과장하고 있었다

`.m:205` 은 이 값을 *"1600x1200x32 스캔아웃으로 증명된 7.32 MiB"* 라고 적는데
매크로는 **7.00 MiB**(7340032)다. 그 스캔아웃의 실제 자국은 1600×1200×4 =
**7680000** 바이트로 매크로보다 **339968 바이트 크다.** 값이 보수적인 쪽이라
안전하지만 주석이 값과 다르다.

### 1-3. DDC/EDID 런타임 사용
`edid/OpenStepMGAEDID.c`는 빌드에 들어가 있으나 모드 선택에 쓰이지 않는다.
모드는 config-table 문자열로만 정해진다.
- **막는 것**: 없음. 고정 모드 목록으로 충분히 동작한다.
- **가치**: 낮음. 5×5 조합이 이미 Configure에서 선택 가능하다.

### 1-4. G400 지원
`chipIsG450`는 PCI revision ≥ `MGA_G450_MIN_REVISION`로만 갈린다. G400은
미착수이고 실물도 없다. PLL 계열이 다르므로 코드 분기가 필요하다.

## 2. 성능 — 이득이 측정되지 않았다

### 2-1. 2D 가속을 실제 화면에 쓰는 길
Storm 엔진은 동작이 실증됐지만(S1/S2/S3a) **평상시에는 한 번도 쓰이지
않는다.** WindowServer가 `IODisplayDoBlit`을 보내지 않기 때문이다(측정으로
확정, `S3B_PREP_INSTRUMENTATION_PLAN.md`).
- 우리가 가시 프레임버퍼에 직접 블릿하면 그려지기는 하나, damage 장부에
  없으므로 WindowServer가 리페인트할 때 지워진다.
- **결론**: 창 안 가속에는 협조 프로토콜이 없다. 전체화면 소유 구조에서만
  의미가 있으며, 그것은 3D stage의 주제다.

### 2-2. 커서 하드웨어 가속
G450에는 하드웨어 커서가 있으나 OPENSTEP의 커서는 **소프트웨어 커서**이고
(IDA로 확인: 프레임버퍼 대상 CPU 복사 루프), 그 락은 `@private`이라 공유할 수
없다. 하드웨어 커서로 바꾸려면 커널 쪽 커서 경로를 우회해야 한다.
- **막는 것**: 구조적. 이득도 측정되지 않았다.

## 3. 정리 — 미룬 것

### 3-1. 폐기 산출물 미삭제
`protocol/`, `profile/`, `recovery/`, `test/openstep-mga-lease-*`,
`test/openstep-mga-*mig*` 등 P2 MiG/R1 복구 매트릭스 시절 산출물이 남아 있다.
현재 드라이버는 이들을 링크하지 않는다(빌드 대상은 `OpenStepMGAManualConfig.c`
+ `OpenStepMGAEDID.c`뿐).
- **삭제하지 않은 이유**: 여러 `docs/` 문서가 이들을 참조하므로 지우면 링크가
  깨진다. 대신 `TEST_STATUS.md` 머리말과 `HANDOFF.md`에 "폐기된 경로"임을
  명시해 두었다.
- **하려면**: 문서 링크를 먼저 정리한 뒤 한 번에.

### 3-2. 초기 계획 문서군의 시제
`P0`~`P3`, `R1`~`R4`, `G1` 문서들은 당시 계획을 현재형으로 서술한다. 개별
수정 대신 상위 문서에 "역사적 기록" 표시만 달아 두었다.

### 3-3. 빌드 스크립트의 `MOUNTPT`
`/ndrv`가 wedge되면 `nx-mount.sh`가 `/ndrv2`로 폴백하므로 매번
`MOUNTPT=/ndrv2`를 넘겨야 한다. 자동 감지로 바꿀 수 있다. 사소함.

### 3-4. `gcdsd` 부팅 자동 기동
재부팅할 때마다 `tools/nx-daemon.sh start`와 `nx-mount.sh`를 손으로 돌린다.
이 저장소가 아니라 GCDS 쪽 사안.

### 3-5. `AR3` — 조사 완료. 남은 범위는 ILOAD 계열뿐

X.Org DDX 색상 확장 경로의 `OUTREG(MGAREG_AR3, 0); /* crashes occasionally
without this */`(`mga_storm.c:1768`, `:1813`)를 보고 우리도 방어적으로
0을 쓰려 했으나, 조사 결과 **그럴 필요가 없고 쓰지 않는 것이 맞다.**

`AR3`는 **BITBLT/ILOAD 계열의 소스 주소지정 레지스터**다. DDX의 복사 경로가
값을 넣고(`:1390`, `:1398`, `:1466`, `:1479`, `:1491`), 사다리꼴 경로는 전혀
건드리지 않으며(`:1566`~`:1590`), 둘은 같은 가속 테이블에 등록돼 X가 수시로
번갈아 부른다(`:647`, `:656`). 즉 **stale `AR3`로 사다리꼴을 그리는 것이
출하 동작**이다. 0으로 미는 곳은 색상 확장/ILOAD 계열뿐이다.

원본 OPENSTEP `MatroxMGA`는 참고가 되지 않았다 — 드로잉 엔진을 아예 쓰지
않는다(`AR3`·`FXBNDRY` 참조 0건, 검색 방법은 CRTC/DAC 대조군으로 검증).

**남은 범위**: 우리가 색상 확장/ILOAD를 구현하게 되면 그때는 `AR3` 정리가
필요하다. 그 전까지는 해당 없음. 정본: `docs/D3_2_SLOPED_TRAPEZOID_PLAN.md`
§1-0-1.

### 3-6. ~~깊이 값 클램프~~ — **해결(들어간 지 오래됐고 표시만 안 됐다)**

깊이는 16비트이므로 `DR0`의 유효 구간은 `[0, 0x7FFF8000]`이다. 그 밖에서
하드웨어 동작이 **일관되지 않다** — `0x80000000`은 `0xffff`로 포화하는데
`0xFFFFFFFF`는 0을 준다(실측, `D3_3_DEPTH_PLAN.md` §10-3).

**드라이버가 직접 자른다.** Mesa에서 온 깊이를 `[0, 0xFFFF]`로 클램프한 뒤
`<< 15`한다. 하드웨어에 맡기지 않는다.

- **막는 것**: 없음.
- ~~**닫는 조건**: 3D 경로에 클램프가 들어가면 끝.~~ — **들어갔다.**

빌더가 사다리꼴마다 시작 깊이를 `[0, 65535]` 로 자르고, 자른 횟수를 센다
(`mesa/OpenStepMGAMesaTriangle.c` 의 `osmgaDepthClamps`). 기울기도 ±65535 로
묶는다. 하드웨어에 맡기지 않는다.

측정도 붙어 있다: 236940 사다리꼴에 대해 자름이 몇 번 늘고 줄었는지 세었고,
가파른 도형의 모서리가 67461.8 을 계산해 잘린 뒤 `GL_LESS` 가 `65535 < 65535`
를 거절해 화소가 안 그려지는 것까지 깊이를 끈 같은 도형과 대어 확인했다.

## 3-10. ~~제출이 모드 변경과 경합한다~~ — **해결(2026-08-21)**

> 아래가 원래 기록이다. 고친 내용은 이 절 끝에 있다.

`revertToVGAMode`는 **아무 잠금 없이** `linearModeActive = NO`를 쓴다.
`stormLock`은 제출 경로가 **입장 검사를 통과한 뒤에야** 잡고, 모드 변경은
그 잠금을 아예 잡지 않는다.

그래서 이런 순서가 가능하다:

1. 제출이 `mmioMapped && linearModeActive && bpp==4`를 통과한다
2. 모드 변경이 시작된다
3. 제출이 그 사이에 DMA를 프로그램하고 MMIO를 쓴다

**이것은 M1-3a가 만든 문제가 아니다** — 제출 경로(M1-2)에 원래 있었고,
capability 파라미터를 검토하다 드러났다. 지금까지 부딪히지 않은 이유는
시험이 모드를 바꾸지 않는 동안에만 그렸기 때문이다.

`OSMGA_HW3D_CAP_READY`는 이 문제를 **키우지 않는다**(같은 술어를 볼 뿐이다).
그러나 **알려주지도 않는다.**

→ 필요한 것은 **세대 번호(generation)**다: 모드가 바뀔 때마다 증가시키고,
제출이 그 값을 입장 시점과 DMA를 킥하기 직전에 두 번 확인한다. 또는 모드
변경이 `stormLock`을 잡게 한다.

**M1-3b(실제로 그리기 시작할 때) 전에 정한다.** 그때부터는 화면을 쓰는
동안 모드가 바뀔 수 있는 상황이 실제로 생긴다.

### 고친 방법 (2026-08-21)

**모드 변경이 `stormBusy` 규약에 참여한다.** 제출은 원래 그 깃발을
잡았는데 모드 변경만 참여하지 않고 있었다 — 새 잠금을 만들 필요가 없었다.

1. `enterLinearMode`/`revertToVGAMode`가 `-claimEngineForMode`로 엔진을
   잡는다. **모드 변경은 실패할 수 없으므로**(윈도서버가 요청한 것이다)
   기다린다: 5ms씩 200번, 1초. 제출이 스핀할 수 있는 최대치의 **5배**다
   (제출 한계 100000회 × 2, MMIO 읽기 1µs 가정 시 0.2초).
2. `enterLinearMode`에서 claim은 **레지스터 프로그래밍만 감싼다.** 뒤의
   자체 시험까지 물면 시험들이 스스로 엔진을 잡으려다 각각 1초씩 막힌다.
3. 그래도 못 잡으면 **크게 로그를 남기고 진행한다.** 돌아오지 않는
   디스플레이가 덮어써진 배치보다 나쁘다.
4. 3번을 안전하게 만드는 것이 **epoch**다. 모드 변경이 끝날 때마다
   증가하고, 제출은 claim 시점의 값을 기억했다가 끝나고 비교한다.
   달라졌으면 **성공으로 보고하지 않는다.**
5. 그리고 제출이 **claim 뒤에 조건을 다시 확인한다.** 원래 검사는 엔진을
   갖기 전에 했으므로 그 사이에 모드가 끝날 수 있었다. stride도 claim
   뒤에 다시 읽는다 — 없어진 모드의 stride로 그릴 뻔했다.

## 3-34. ~~클라이언트가 커널의 커맨드 리스트를 매핑하고 있었다~~ — **해결·실기 확인(2026-08-24)**

핸들러는 "배치만, 링은 절대" 를 `rel >= OSMGA_HW3D_BATCH_BYTES` 로 지켰다. 그런데
`PAGE_SIZE` 는 8192, `BATCH_BYTES` 는 28672 = **3.5 페이지**이고, 커널은 받아들인
오프셋마다 **페이지 통째로** 매핑한다. 검사는 페이지의 **시작**을 묻고 노출되는
것은 페이지 **전체**였으므로, `rel=0x6000` 페이지가 `[0x6000,0x8000)` 을 덮어
**리스트의 첫 4096바이트가 매핑됐다** — 그것도 가속을 쓰는 모든 프로세스에서
(클라이언트는 창 전체를 매핑한다).

실측으로 증명했다(`tcw`, 읽기 전용): 리스트 자리에서 8 dword 를 읽고 배치를
제출하고 다시 읽으니 2가 바뀌었고 6이 0이 아니었다.

**매 부팅 찍히던 `M1-0: FAIL` 이 이것을 가리고 있었다.** 그 FAIL 은 자가진단의
기대값이 낡아서 난 것이고(배치/링 분리 때 안 따라옴), 항상 실패하는 시험은 아무도
읽지 않는다.

배치를 페이지 정수 배로 만들어 고쳤다 — `MAX_TRI` 200→180, `BATCH_BYTES`
28672→24576(정확히 세 페이지), 리스트 36864→40960, `VERSION` 8→9. 헤더의
`ENC_TRI_BLK` 가 8인데 실제 9라 선언 상한이 **과소평가**였던 것도 같이 고쳤다.
할당은 0으로 채우고, 분리가 페이지 배수인지 init 에서 검사하며, 자가진단은 이제
블록의 **모든 페이지**를 돌며 "받아들여짐 ⟺ 페이지 끝이 링에 안 닿음" 을 확인한다.

**두 번 틀렸고 둘 다 교차검토가 짚었다**: 리스트를 줄이는 첫 안은 인코더 최악값
(9040 dword)을 넘겼고, 할당을 키우는 둘째 안은 `dma_buf_alloc` 의 **64 KiB 상한**을
넘겼다 — 그 상한은 이 저장소가 이미 적어 둔 사실인데 확인하지 않고 계획을 세웠다.

**재부팅 뒤 확인(2026-08-24)**: 자가진단이 `PASS -- both windows decide as
specified and repeat themselves` 로 바뀌었고, 새 전 페이지 순회가 *"every page of
the block decides by whether it REACHES the list, not by where it starts
(3 mappable of 8)"* 라고 찍는다. 8페이지 중 배치 3개만 매핑 가능 — 계산과 같다.
유저랜드 쪽 `tcw` 도 *"the promise holds"* 로 바뀌었고 회귀에 들어가 있다.

자세히는 `M1_4EE`.

## 3-35. 클라이언트가 둘이면 서로를 덮어쓴다 — **이 인터페이스로는 못 고친다(2026-08-24, 재고 결론)**

**요약**: `close` 는 오는데(죽여도 온다) **버스트당 한 번** 온다. 그래서 open/close
로는 배타성을 표현할 수 없다 — 걸쇠는 이미 죽은 앞사람 때문에 정당한 후임을
거절한다(드라이버 로그에 시뮬레이션: 8 허용 / 28 거절). 라이브러리도 다른
프로세스가 있다는 것을 알 방법이 없다. 진짜 해법은 `S4A:294` 가 적은 클라이언트별
핸들과 클라이언트별 할당이고, 그건 인터페이스 변경이다. 계측만 남겨 두었다.


이 장치에는 **클라이언트별 상태가 하나도 없다.** 확인한 세 곳 전부:

- `osmgaDevOpen(int dev, int flag, int devtype)` — 잘못된 minor 와 미등록만
  거르고 0 을 돌려준다. 몇 개든 열 수 있다.
- `osmgaDevClose(int dev, int flag, int devtype)` — 셋 다 무시하고 0.
- `osmgaDevIoctl(int dev, int cmd, caddr_t data, int flag)` — **누가 내는지
  모른다.**

그래서 가속 프로세스 둘이 동시에 돌면 **배치 버퍼 하나와 VRAM 표면 하나를 중재
없이 공유한다** — 서로의 삼각형 자리에 자기 것을 쓰고, 상대가 채우는 중에 제출할
수 있다. 어느 쪽도 통보받지 않는다. 오늘 둘을 동시에 돌리는 것이 없어서 안 보였을
뿐이다. `S4A_VRAM_MMAP_PLAN:294` 가 이 고정 공유 매핑은 **단일 클라이언트 smoke
test 용**이라고 이미 적어 두었다.

### 왜 아직 안 고쳤나 — 모르는 사실 하나에 걸려 있다

명백한 답은 **배타적 open** 이다. 그런데 그건 **클라이언트가 사라질 때 `close` 가
불리는가**, 특히 정상 종료가 아니라 **죽임당했을 때** 불리는가에 전부 걸려 있고,
**이 저장소에 그걸 밝힌 것이 없다** — S4A 의 역분석은 `mmap` 과 VM object 를
다루지 `close` 경로를 다루지 않는다(교차검토도 같은 답).

풀리지 않는 배타적 open 은 문제보다 비싸다: 지금은 죽은 클라이언트가 아무 값도
안 치르지만, 그때는 **재부팅할 때까지 가속이 사라진다.**

### 들어간 것: 세는 것뿐 (실기에서 돌았고, 아래가 그 결과다)

동작은 하나도 안 바꾸고 `open`/`close` 에 계수기와 로그를 넣었다. 거절된 open 은
짝이 되는 close 가 없으므로 세지 않되, **로그는 남긴다** — 원래 그 로그가 "우리
cdevsw 슬롯에 실제로 닿는가" 를 말해 주던 것이라 그 값을 잃으면 안 된다.

시험은 `tdl`(신규), 한 번에 한 경우씩 — 합계만으로는 경우를 구분할 수 없다는
지적을 받아 그렇게 만들었다:

```
plain        열고 닫는다
twice        한 프로세스가 두 번 연다
exitnoclose  열고 닫지 않고 exit(0)
forkchild    열고 fork, 자식이 바로 죽고 부모가 닫는다
forkboth     열고 fork, 아무도 안 닫고 둘 다 끝난다
kill         열고 자기를 SIGKILL
```

### 잰 것 (2026-08-24, 실기)

직접 실행할 때 — 로그인 csh 에서든 `sh -c 'prog > file'` 로든:

```
명시적 close                    open 1, close 1
닫지 않고 exit(0)               open 1, close 1
fd 를 든 채 SIGKILL             open 1, close 1
fork, 자식 먼저 죽고 부모가 닫음  open 1, close 1
fork, 아무도 안 닫음             open 1, close 1
커맨드 창을 매핑한 채 종료        open 1, close 1
한 프로세스가 두 번 열기          open 2, close 1
```

**`close` 는 온다 — 죽여도 온다.** 재고 나서 정하기로 했던 그 사실이 이것이고,
내가 두려워한 구체적 형태(죽은 클라이언트가 영영 안 놓는다)는 **틀렸다.**

**다만 `close` 는 마지막 참조가 사라질 때 한 번만 온다.** 그래서 `opens - closes`
는 **점유 수가 아니다** — 클라이언트가 겹치면 N번 열리고 1번 닫히므로 영구히
어긋난다. 이 기계에서 46까지 쌓인 잔여가 그것이고, 새는 것이 아니다.

### 내가 틀렸던 것: "회귀가 참조를 흘린다"

한동안 회귀 한 번에 open +15 / close +1 이라고 읽었고 누출이라고 적을 뻔했다.
**아니었다.** `sh` 는 파이프라인의 **첫 단계가 아직 살아 있는데 반환한다** —
`ps` 로 확인했다(클라이언트가 `RW` 상태로 남아 있었고 close 는 5초 뒤 도착).
계수기 읽기가 종료를 앞지른 것이다. 끝나고 45초 기다려 다시 재니 **+15 opens /
+15 closes**, 그 뒤로도 그대로였다.

### 걸쇠도 안 된다 — 드라이버가 보는 것을 재고 나서

한 번은 **불리언 걸쇠**로 가려 했다. 잰 모든 경우와 맞았기 때문이다(교차검토도
같은 결론이었다). 그런데 둘 다 재지 않은 것이 하나 있었다 — **회귀가 도는 동안
드라이버가 실제로 무엇을 보는가.**

```
22:41:11 open  opens=148 closes=87
22:41:12 open  opens=149 closes=87
   ... 열한 개 더, 전부 closes=87 ...
22:41:15 open  opens=162 closes=87
22:41:15 close opens=162 closes=88
```

**열다섯 클라이언트에 close 하나.** 로그 유실이 아니다 — 계수기는 누적이고 살아
남은 줄이 87→88 이라고 말한다. 그리고 `ps` 로 재면 그 사이 살아 있는 클라이언트는
**최대 둘**이다.

이 로그에 대고 걸쇠를 시뮬레이션하면 **8 허용 / 28 거절**이다. 거절되는 쪽은 겹친
클라이언트가 아니라 **앞사람이 이미 죽었는데 close 가 아직 안 온** 정당한 다음
클라이언트다.

### 원인: 사슬 (통제 실험으로 확증)

겹치게 둘 vs 4초 띄워 둘:

```
겹침:  open 163, open 164, close 89          -- 둘에 close 하나
띄움:  open 165 -> close 90; open 166 -> close 91  -- 둘에 close 둘
```

`d_close` 는 **장치가 참조되지 않게 될 때 한 번** 온다. 연달아 도는 클라이언트는
사슬을 이뤄 그 순간을 뒤로 밀고, 버스트 전체에 close 가 하나 온다. 이것 하나로 전부
설명된다 — 15:1, `ps` 로 본 5초 늦은 close, 띄워 돌리면 번갈아 나오는 것, 그리고
`opens - closes` 의 영구 잔여.

### 판정: 이 인터페이스로는 배타성을 표현할 수 없다

- **(a) 배타적 open — 불가.** close 가 클라이언트 단위가 아니라 버스트 단위로
  오므로, 걸쇠는 이미 사라진 앞사람 때문에 정당한 다음 사람을 거절한다.
- **(b) 제출 때 주인 정하고 close 에서 놓기 — 불가.** 같은 close 에 기댄다.
- **(c) 단일 클라이언트 계약 — 강제 불가.** 라이브러리가 볼 수 있는 것은 전역
  capability 와 자기 상태뿐이라 **다른 프로세스가 있다는 것을 알 방법이 없다**
  (교차검토 지적, 확인함). 협조적 문서 규칙 이상이 될 수 없다.

**진짜 해법은 S4A:294 가 이미 적어 둔 것뿐이다** — 클라이언트별 핸들/마이너와
클라이언트별 할당. 그건 인터페이스 변경이고 이 항목보다 크다.

한 가지는 이미 있다: 동시 **제출**은 `stormBusy` 가 막는다. 남는 창은 제출이 아니라
**공유 배치에 대한 유저 측 쓰기**다.

### 계수기는 남긴다

`opens - closes` 는 **참조 수가 아니라 콜백 수**다(잔여는 그래서 생긴다). 그래도
남겨 둔다 — 이 항목이 미해결인 동안, 다음 사람이 같은 길을 다시 걷지 않게 하는
증거가 그것이다.

### 폐기한 안: 불리언 걸쇠 잰 모든 경우와 맞는다: 첫 open 이 세우고,
마지막 참조가 사라질 때의 close 가 내린다. 겹친 두 번째 open 은 거절되고 —
그게 이 항목이 원하던 바다 — 거절된 open 은 짝이 되는 close 도 없으므로 계수의
비대칭도 타지 않는다. 교차검토도 같은 결론이고, 내가 "잔여 때문에 걸쇠도 못
쓴다" 고 한 것은 **지나치게 조심스러웠다**(잔여는 계수기의 성질이지 걸쇠의
성질이 아니다).

**켜기 전에 알고 있어야 할 값**: 우리 회귀 자체가 클라이언트를 `sh` 파이프라인에서
돌리고, 그 때문에 **겹치는 일이 실제로 있다.** 걸쇠가 서면 겹친 쪽은 거절되어
소프트웨어로 떨어지고, 회귀가 간헐적으로 실패한 것처럼 보인다. 걸쇠가 제 일을
하는 것이지만, 그걸 모르고 켜면 회귀가 흔들리는 것으로만 보인다.

### 여전히 덮지 않는 것: fd 배타성은 매핑 배타성이 아니다

교차검토가 짚었고 확인했다 — 이 저장소가 **`close()` 해도 매핑은 남는다**고 이미
적어 두었다(`S4A_VRAM_MMAP_PLAN` 7-2, :248). 그러니 배타적 open 이 걸쇠를 놓은
뒤에도 **닫고서 포인터를 들고 있는** 클라이언트는 그대로 있다. 우리 클라이언트는
그렇게 하지 않고 죽은 프로세스의 주소공간은 함께 사라지지만, **그 틈은 실재하고
세는 것으로도 배제로도 닫히지 않는다.** 진짜 방향은 S4A:295 가 적은 클라이언트별
할당과 검증된 핸들이다.

## 3-11. 프로브의 두 `Run`이 동시에 들어오는 경우 (M1-3a, 미해결)

`OSMGAMesaProbeRun`의 `probeDone`/`probeCached`에는 잠금이 없다.

**해결한 것**: 취소(revoke)를 별도의 단방향 플래그로 빼고 복사 **뒤에**
확인하게 했다. 그래서 "한 스레드가 취소하는 동안 다른 스레드의 프로브가
늦게 끝나 하드웨어로 덮어쓰는" 경우는 사라졌다 — 실패가 소프트웨어를
요청했는데 하드웨어가 쓰이는 것이 여기서 가장 나쁜 결과였다.

**남은 것**: 두 스레드가 동시에 `Run`에 처음 들어오면 **각각 디바이스를
열고**, `probeCached`에 섞여 쓰일 수 있다. 하나는 디스크립터가 샌다.

지금 이것을 잠그지 않은 이유는, 이 빌드의 Mesa 3.4.2 자체가 스레드 안전이
아니라서 **여러 스레드에서 GL을 부르는 것이 이미 정의되지 않은 동작**이기
때문이다. 프로브만 잠가도 얻는 것이 없다.

→ **libGL을 스레드 안전으로 만들 생각이 생기면 그때 같이 정한다.**
그 전까지는 이 항목이 "안 한 것"으로 남아 있어야 한다.

**우리가 그린 픽셀을 그 버퍼는 모른다.**

지금 안전한 이유는 **알파를 읽는 것을 전부 거절**하기 때문이다 — 블렌딩과
알파 시험은 각자의 `RasterMask` 비트로 막힌다. 위험은 프로그램이 가속으로
그린 뒤 **프레임 중간에 블렌딩을 켜는** 경우다: 그때 소프트웨어가 낡은
알파를 읽는다.

→ ~~알파를 붙일 때(M1-3d 이후) 같이 정한다.~~

**정해졌고, 방법은 그 버퍼를 없애는 것이었다.** 표면을 치환할 때 포트가
`UseSoftwareAlphaBuffers` 를 끈다(`OSmesa/osmesa.c:613`). 이유가 주석에 있다:
이 하드웨어는 알파를 화소의 **네 번째 바이트**에 쓰는데, 별도 알파 버퍼가
있으면 방금 색 버퍼에서 읽은 알파를 그 버퍼의 것으로 덮어써서 **모든 블렌드가
하드웨어가 쓴 알파를 무시하게 된다.** 꺼 두면 양쪽이 한 곳을 읽고 쓴다.

그래서 "우리가 그린 픽셀을 그 버퍼는 모른다" 는 전제가 가속 중에는 성립하지
않는다. 블렌딩은 이제 받아들여지고, 목적지 알파를 읽는 인자들이 실제로 그
네 번째 바이트를 읽는다는 것은 `tbf` 가 목적지 알파 `0x60` 으로 잰다.

가속을 놓을 때 그 버퍼를 **되살리지 않는 것**도 결정이지 빠뜨림이 아니다 --
알파가 네 번째 바이트에 있다는 것은 애플리케이션이 준 버퍼에서도 여전히
참이고, 이제 거기에 그린다(`osmesa_leave_accel` 의 주석).

### 그리고 `ALPHABUF_BIT`를 허용해야만 했던 이유

`RasterMask != 0`으로 막으면 **훅이 절대 안 붙는다.** `OSMESA_RGBA`가
`alphaBits = 8`을 세우고 그것이 `UseSoftwareAlphaBuffers`가 되어
`ALPHABUF_BIT`가 평범한 컨텍스트에서도 늘 켜져 있다. 컴파일도 되고 죽지도
않고 **그냥 가속이 안 되는** 침묵의 무동작이 될 뻔했다.

(교차검토는 "항상 켜지는 비트는 없다"고 답했다. **틀렸고**, 원본
`osmesa.c`의 형식 분기와 `context.c`의 대입을 직접 읽어 확인했다.)

## 3-13. ~~되비추기가 `glReadPixels`의 목적지를 덮을 수 있다~~ — **해결(2026-08-24)**

`glReadPixels`도 `RENDER_START`/`RENDER_FINISH`를 부른다
(`readpix.c:776,806`). 우리는 `RenderStart`에서 "더러움"을 표시하고
`RenderFinish`에서 표면 전체를 앱 배열로 복사한다.

그래서 **읽기인데도 복사가 일어난다.** 두 가지 결과가 있다:

1. **낭비** — 아무것도 그리지 않았는데 표면 전체를 복사한다.
2. **위험** — 앱이 `glReadPixels`의 목적지로 **자기 OSMesa 배열을 준
   경우**, 방금 읽어 넣은 값을 우리가 덮는다. 형식이 다르면 다른 값이 된다.

**왜 지금 안 고치나**: "그렸는가"를 알려면 소프트웨어 경로가 픽셀을 쓴
것을 알아야 하는데, 그 span 함수는 OSMesa의 것이고 우리에게 알리지
않는다. `RenderStart`에서 표시하는 것이 **거절된 프리미티브만으로 이뤄진
프레임을 "아무 일도 없었다"로 흘려보내지 않는** 유일한 방법이다.

### 해결 (2026-08-24) — 상자는 못 얻지만 **불리언은 얻을 수 있다**

미뤄 둔 이유가 "무엇을 건드렸는지 알아야 한다" 였는데, 그건 **상자**가 필요할
때의 이야기다. 여기 필요한 것은 "무엇이든 썼는가" 하나뿐이다.

OSMesa 의 RGBA 기록 스팬 다섯과 읽기 스팬 둘을 감싸 깃발을 세운다. 판정은
`읽었다 && 쓰지 않았다` 하나이고, 그 밖의 모든 것은 예전처럼 복사한다.

**왜 상자는 못 얻는데 불리언은 얻는가**: 상자를 막는 구멍은 OSMesa 가 선과
깊이 시험 있는 삼각형에 **직접 기록기**를 설치해 어떤 콜백도 거치지 않고
`PIXELADDR4()` 로 쓴다는 것이다. 그런데 그 기록기들은 **원시 경로에만** 있고,
원시 구간은 읽기 스팬을 부르지 않는다. 그러니 "읽었고 쓰지 않았다" 는 그린
구간에서는 **성립할 수 없다** — 보이지 않는 쓰기가 사는 곳이 바로 거기다.

감싸는 자리는 `RenderStart` 다. 상태 갱신 훅은 OSMesa 가 스팬을 설치하기
**전에** 불리므로(`osmesa.c:1912` 대 `:1917`) 거기서 감싸면 즉시 덮어써진다.
`RENDER_START` 는 버퍼를 건드리는 모든 경로가 지난다.

`RenderStart` 의 무조건 표시는 **그대로 둔다**. 직접 기록기로만 그린 프레임을
잃지 않으려면 그래야 한다. 대신 읽기로 판정된 구간이 **진입 시점의 값으로
되돌린다** — 그러지 않으면 아무도 바꾸지 않은 표면을 다음 flush 가 복사한다.

시험(`trb`)은 호출자가 **자기 OSMesa 배열을** 읽기 목적지로 주고 `GL_RGB` 로
요청한다. 미러가 거기 내려앉으면 세 바이트마다 어긋난다. 읽기가 미러를 부르지
않고(계수기로 확인), 바이트가 요청한 그대로이며, 뒤따르는 `glFinish` 도
건드리지 않는다.

## 3-14b. ~~가장자리 픽셀의 커버리지가 다르다~~ — **해결(2026-08-21)**

```
어느 한쪽이라도 덮은 735 픽셀 중
  양쪽이 덮음   701 (95.4%)
  한쪽만 덮음    34 (4.6%)   <- 이것이 실제 차이
```

첫 측정에서 "범위의 54% 차이"로 보였던 것은 **전부 이 34픽셀**이었다 —

**고칠 수 있어 보인다**: 하드웨어의 변 기울기는 분자·분모라 분수를 표현할

Mesa의 표본 규칙에 맞출 수 있다. **재기 전에는 손대지 않는다.**

## 3-14z. (원래 기록) 두 경로의 깊이 값 차이

두 경로가 같은 깊이 버퍼를 보는 것은 실기에서 확인했다(양방향). 그러나
같은 삼각형의 같은 픽셀에 **같은 16비트 값**을 쓰는 것은 아니다.

| 차이 | 소프트웨어 | 우리 |
| --- | --- | --- |
| 정점 좌표 | 소수부 유지 | **`(long)`으로 잘림** |
| 표본 위치 | 픽셀 중심(`FIXED_HALF`) 보정 | 사다리꼴 모서리 |
| 고정소수점 | Q11, 절사 | Q15, 반올림 |

그래서 **경계에 걸친 `GL_LESS`가 한쪽에서는 통과하고 다른 쪽에서는
거절될 수 있다.** 지금 시험이 이걸 못 잡는 이유는 0.25 대 0.75라는 큰
간격을 쓰기 때문이다 — 간격이 1~2 단위면 드러난다.

**고칠 수 있는 것이 아니다**: 엔진의 보간 규칙은 바꿀 수 없다. 선택지는
(가) 깊이가 켜지면 **한 프레임 전체를 한 경로로** 몰기, (나) 그대로 두고
경계 사례의 오차를 받아들이기.

→ **M1-3e(알파/블렌딩) 전에 정한다.** 그때는 목적지를 읽으므로 오차가
색으로 드러난다.

두고 경합**한다.

놓아야 한다.~~ 지금도 시간초과 자체가 관측된 적이 없다.

### 들어간 것 (2026-08-24, 실기 적용됨 — 다만 아래대로 아직 어떤 시험도 닿지 않는다)

**회복 대기는 완료의 세 조건 전부로 한다.** 완료란 셋이 동시에 참인 것이다 —
목록 끝의 트랩이 발생했고, 그리기 엔진이 유휴이고, DMA 읽기 포인터가 끝에
닿았다(`MGA_DMA_DONE_MASK`/`_VALUE`, `:244-259`).

처음 계획은 `osmgaStormWaitIdle` 로 기다리는 것이었는데 **그건 틀렸다.** 그
헬퍼는 셋 중 **가운데 하나**(`ENGBUSY`)만 본다(`:1043-1051`). 그러니 그것이
"유휴" 를 돌려준 뒤에도 DMA 는 아직 목록을 읽고 있을 수 있고 곧 그리기를 더
넣을 수 있다 — 확립하지 못한 안전을 보고했을 것이다. 교차검토가 잡았다.

**트랩은 묻기 전에 지우지 않는다.** 그것이 세 신호 중 하나이므로, 먼저 지우면
질문에 필요한 증거를 버리는 셈이다. 회복이 성공한 뒤에 지운다.

**회복도 실패하면 걸쇠를 세운다.** 새 기구가 아니라 EXEC 뒤 시간초과한 블릿이
세우는 그 `stormBlitFailed` 다 — 같은 이유, 같은 영구성. 그리고 3D 제출 진입도
이제 그 걸쇠를 본다: 세워져 있으면 즉시 거절한다. 전에는 블릿과 채우기만 보고
있어서, "손대면 안 된다" 고 선언된 엔진에 3D 가 새 목록을 건넬 수 있었다.

### 고치지 **못한** 절반 — 덮지 않는다

이것이 막는 것은 **커널이 엔진에 일을 더 주는 것**이다. 표면을 이미 매핑해 둔
클라이언트가 프로세서로 그 메모리를 쓰는 것은 막지 못하고, 이 항목이 말하는
경합이 바로 그것이다. 닫으려면 리셋이나 격리가 필요한데 이 드라이버에는 둘 다
없고, 참조본(우리가 가진 X.Org 2.0.0 사본과 DRM 사본)에도 쓰이는 엔진 리셋
레지스터가 없다.

### 아직 없는 것: 이 경로를 도달하게 만드는 방법

시간초과가 한 번도 관측된 적이 없으므로 **새 코드는 아직 어떤 시험도 닿지
않는다.** 교차검토가 제안한 형태는 개발 전용 일회성 고장 주입이다 — `PRIMEND`
**뒤에** 첫 완료 폴이 시간초과를 보고하도록 만들되 목록을 망가뜨리거나 하드웨어를
물리지는 않는 것. 그러면 "폴은 포기했는데 회복이 완료를 봤다" 가지는 도달한다.
진짜로 물린 엔진은 그렇게 만들 수 없고, 만들려 하지 않는다.

## 3-16. ~~텍스처 좌표 한계가 프리미티브가 아니라 클립 전체로 잰다~~ — **이미 고쳐져 있었다(2026-08-24 확인)**

### 다시 보니 전제가 낡았다

검증기는 **이미 프리미티브 단위로 잰다.** 확인한 것:

- 가로: 프리미티브의 열 상자를 walk 로 직접 만들어(`bx0`/`bx1`), 그 폭을 쓴다 —

## 3-18. ~~제출이 반환된 뒤에도 엔진의 마지막 쓰기가 아직 안 보인다~~ — **커널이 고친다(2026-08-24 실측)**

**2026-08-21 경과**: "증상이 제출 방식(RPC vs ioctl)을 따라간다"고 적었다가
같은 규모로 재보고 **취소했다**. 40 회씩: ioctl 0 회, RPC 1 회. Fisher 정확
검정 p = 1.000 — 구분되지 않는다. 게다가 두 시험이 그리는 화소 수가 380 대
4096 이라 비교 자체가 공정하지 않았다.

**측정이 좁혀졌다** (정본: `M1_3G_SURFACE_READBACK_PLAN.md` §9):

- 창 시작 기준 **바이트 0..63**, 경계가 바이트 64 에서 칼같이 끊긴다.
- `dstorg` 가 창 시작일 때만, **레지스터 값이 바뀌는 첫 제출**에서만.
- **바이트 64 이상을 한 번 읽으면 낫는다.** 0..63 안을 읽어서는 안 낫는다.
- **시간으로는 안 낫는다** (CPU 공회전 20000 회 무효). 버스 읽기라야 낫는다.
  → 아래 3-18z 표의 *"시간이 원인"* 은 **오독이다.** 그 표는 읽기 없이
  시간만 준 경우를 시험한 적이 없다.
- 값은 결국 들어온다 — **늦은 것이지 잃은 것이 아니다.**

### 남아 있던 질문에 답했다 (2026-08-24)

드라이버 주석이 물어 둔 것: *"커널이 uncached 별칭으로 하는 읽기가 클라이언트
자신의 읽기와 같은 일을 하는가는 다른 질문이고 아직 답이 없다."*

`ttex trust-driver`(클라이언트 자신은 정착 읽기를 하지 않음)로 두 팔을 돌렸다.
`OSMGAHW3DSettle` 는 머신이 도는 중에 바꿀 수 있다.

```
정착 읽기 OFF (0)     : pass 0 이 낡음 — 5회 중 5회
정착 읽기 AUTO(word 16): pass 0 이 낡음 —  4회 중 0회
```

낡은 화소는 매번 **byte 0..60**, 즉 창 시작의 첫 64바이트뿐이고 40 시행 중 정확히
1 — 비율이 아니라 **결정적**이다(`pass 1` 은 어느 팔에서도 낡지 않는다; 레지스터가
바뀌는 첫 제출에서만이라는 기존 기록과 맞는다).

시행 단위로 세면 5/400 대 0/320, Fisher p = 0.069 로 **모자란다.** 그러나 시행은
교환 가능하지 않다 — 실행마다 pass 0 은 항상 1, pass 1 은 항상 0 이다. 실행 단위
결과(5 of 5 대 0 of 4)로는 **p = 0.0079**. 파이썬으로 계산했다.

**그래서: 커널이 word 16 을 한 번 읽으면 클라이언트의 낡음이 사라진다.** 그리고
그것이 이미 기본값(`OSMGA_HW3D_SETTLE_AUTO`)이다.

**설명한 것은 아니다.** 왜 버스 읽기 한 번이 정착시키는지는 여전히 모르고, 이
측정은 "듣는다" 만 말한다. 그 구별을 지운 채 닫지 않는다.

## 3-18z. (원래 기록) 제출 뒤 엔진의 마지막 쓰기

텍스처 클라이언트에서 픽셀 `(0,0)`이 **재현성 있게** 미청소값을 유지했다.
띠의 나머지 4095픽셀은 전부 정확했다.

한 번에 하나씩 바꿔가며 가려냈다:

| 가설 | 시험 | 결과 |
| --- | --- | --- |
| `u = 0`이 특별 | `tmr[6] = 1` | **아니다** — 그대로 |
| `u`와 `v` 둘 다 | `tmr[6] = tmr[7] = 1` | **아니다** |
| 텍스처 유닛 워밍업 | 같은 배치를 두 번 제출 | **아니다** |
| 그 캐시 줄이 낡음 | **멀리 떨어진** 곳을 읽음 | **고쳐짐** |
| 시간 | 어디를 읽든 고쳐짐 | **이것이다** |

교차검토가 "첫 픽셀이 아니라 **첫 읽기**일 수 있다"고 지적해 더 갈랐다:

| 시험 | 결과 |
| --- | --- |
| 뒤에서부터 검사 (선행 읽기 없이) | **낡은 것 0개** |
| **이웃 낱말**(1,0)을 먼저 읽음 | **(1,0)도 낡았고**, 이어서 (0,0)도 낡음 |
| 그 직후 검사 루프가 (1,0)에 도달 | **정확함** |

**이웃도 낡았다가 곧 정확해진다**는 것이 결정적이다. 낡음은 **특정 주소에
붙어 있지 않고**, 따라서 캐시 줄도 특정 픽셀의 쓰기도 아니다. **제출이
반환된 직후의 읽기가 옛 값을 본다**는 것이고, 버스 읽기 한 번의 시간이면
가라앉는다.

### 어디에 있는지는 확정됐다 (2026-08-21)

드라이버가 반환 전에 **같은 물리 메모리를 캐시 없이** 읽게 해보았다
(창의 한 페이지를 `IOMapPhysicalIntoIOTask`로 한 번 별칭 매핑해 보관):

```
클라이언트도 정착 읽기를 함  -> drew 4096, identity 4096 of 4096
드라이버만 믿음              -> drew 4095, identity 4095 of 4096
```

**충분하지 않다.** 커널이 캐시 없이 읽어도 클라이언트 쪽이 안 풀린다.

**그런데 거기서 "클라이언트 매핑이 캐시되어 낡은 줄을 쥔다"로 간 것은
틀렸다.** 계획 검토가 짚었고 확인해보니 맞았다 — 같은 기계의 기존 측정과
모순된다. `S4A_VRAM_MMAP_PLAN.md §9-1`의 stale-cache 게이트는 캐시를
**의도적으로 오염시킨 뒤** 확인했고(`before=a5000000` → `after=5aa55aa5`),
**유저 매핑이 엔진 쓰기와 일관함**을 실증했다.

**그 시험과의 차이는 매핑이 아니라 경로다** — 그때는 MMIO로 몬 2D 블릿,
지금은 **M1 primary DMA**. 그러므로 의심할 곳은 **완료 판정**이다:
`ENDPRDMASTS`는 명령 스트림을 다 **읽었다**는 뜻이지 그 쓰기가
**도착했다**는 뜻이 아닐 수 있다.

정본은 `M1_3G_SURFACE_READBACK_PLAN.md`로 옮겼다. 다음 작업은 **복사
기구를 짓는 것이 아니라**, 완료 판정 직후 커널이 캐시 없는 별칭으로 읽어
그 값이 옳은지 재는 **진단 하나**다.
효과가 없는 것으로 밝혀진 그 읽기는 다시 걷어냈다 — 하지 않는 일을
한다고 적어둔 장치는 없느니만 못하다.

**그리고 이건 S4a 계획서가 이미 차단 요건으로 적어둔 것이다**
(`S4A_VRAM_MMAP_PLAN.md` §7-1): *"`d_mmap`이 PFN을 반환하는 이 경로에는
uncached나 write-combining을 요청할 공개 수단이 없다"*, 그리고
*"Storm 쓰기 후 CPU 캐시에 낡은 라인이 남을 수 있다."* **예측이 그대로
관측됐다.** 헤더를 다시 뒤져도 `d_mmap` 경로에 캐시 억제 수단은 없다.

→ 남은 길은 둘이다:
  **(가)** 되비추기를 **커널이** 한다 — 커널은 캐시 없는 별칭을 만들 수
  있으므로, VRAM을 읽어 앱 버퍼로 옮기는 일을 ioctl로 옮긴다. 그러면
  클라이언트가 VRAM을 읽을 일이 없어진다.
  **(나)** 유저 매핑을 캐시 없이 얻는 다른 경로를 찾는다.

**(가)가 확실하다.** M1 되비추기가 지금 맞는 것은 표면 전체를 복사하느라
캐시 줄이 밀려나기 때문일 뿐이고, dirty 사각형으로 좁히는 순간 사라진다.

**기전은 확정하지 못했다.** 커널은 `MGA_DMA_DONE_VALUE`까지 돌고
`osmgaStormWaitIdle`까지 기다리지만, 그것이 **클라이언트가 보는 것**을
보장하지 못한다는 사실만 확립됐다. 원래 여기 적었던 "엔진의 쓰기가 늦게
도착한다"는 표현은 **증거보다 강했다** — 관측은 그것과도, "첫 관측이
이르다"와도 모두 들어맞는다.

**왜 중요한가**: Mesa 되비추기가 VRAM을 읽는다. 지금 맞게 나오는 이유는
표면 전체를 복사하느라 충분히 오래 걸리기 때문일 뿐이고, **보장이 아니다.**
dirty 사각형으로 좁히면(§3-12, §3-13) 그 여유가 사라진다.

→ **커널이 반환 전에 가시성을 보장해야 한다** — 마지막으로 쓴 위치를
되읽거나 적절한 장벽을 두어서. 클라이언트마다 추측하게 둘 일이 아니다.
시험 클라이언트에는 그때까지 되읽기 앞에 지연을 두었고, 왜 두는지 적어
두었다.

## 3-19. ~~`mmap` 의 오프셋이 무시된다~~ — **철회. 내 시험 클라이언트 버그였다**

**2026-08-21 결론: 오프셋은 제대로 먹는다.** 드라이버에는 아무 문제가 없었다.

독립 프로그램(`test/openstep-mga-mmap-offset-test.c`)으로 직접 쟀다. 두 후보
자리에 서로 다른 값을 두고, 오프셋 매핑을 통해 세 번째 값을 쓴 뒤 어느 쪽이
움직였는지 본다:

```
base mapping at offset 0 : at 0x32000, mmap reported 0
offset mapping at +1048576: at 0x134000, mmap reported 0
   window byte 0        holds a1a1a1a1  (그대로)
   window byte 1048576 holds c3c3c3c3  (여기로 갔다)
VERDICT -- the offset is honoured
```

### 왜 무시되는 것처럼 보였나

**argv 파싱이 매핑보다 뒤에 있었다.** 내가 인자를 나중에 덧붙이면서 파싱
블록을 매핑 호출 **아래**에 두었다. 그래서 매핑을 옮기는 그 인자는 매핑
시점에 언제나 0 이었고, **`dstorg` 만 움직였다.** 사각형이 클라이언트가
보는 자리에서 한 행 벗어난 것은 그 때문이다.

고쳤다 — 파싱을 main 맨 앞으로 옮겼다. 그러자 같은 시험이:

- 한 페이지(8192 B) 오프셋: `사각형 다음 행에 그려진 화소 0` — 제자리다.
- 반 페이지(4096 B) 오프셋: `a window will not map` — 거절된다.

### 덤으로 알게 된 두 가지

1. **이 시스템의 `mmap` 은 주소가 아니라 상태를 돌려준다.** 성공에 0,
   실패에 -1 이고, 매핑은 넘긴 주소에 놓인다. 처음에 반환값을 포인터로 쓰다가
   버스 에러를 봤다. **그러므로 기존 헬퍼들이 `vm_allocate` 주소를 돌려주는
   것은 올바르다** — codex 가 "반환값을 버린다"고 지적한 것은 이 시스템에서는
   효력이 없다.
2. **페이지 정렬이 아닌 오프셋은 조용히 반올림되지 않고 `EINVAL` 로
   거절된다.** 오프셋 × 길이 행렬로 확인했다 — +0, +8192, +16384 는 모두
   성공, +4096, +12288 은 길이와 무관하게 전부 거절.

이 두 번째 사실이 §3-20 을 추정이 아니라 **확인된 것**으로 만든다.

### 남은 관찰 (별건)

매핑을 한 페이지 옮긴 시험에서는 사각형이 제자리에 떨어지는데도 **행 0 과
행 16 이 통째로** 늦게 온다(2 개 연속 구간, 128 화소). 창 시작에서 보이는
64 바이트와는 다른 모양이다. 프로덕션에는 이런 매핑이 없다(Mesa 는 색을
오프셋 0 에, 깊이를 페이지 정렬 오프셋에 매핑한다). **시험 전용 경로의
미해결 관찰**로 세워 두고 지금은 쫓지 않는다.

## 3-20. ~~Mesa 쪽 깊이 매핑이 4 KiB 로 정렬한다~~ — **고쳤다 (2026-08-21)**

전제(0 이 아닌 2 의 거듭제곱)를 코드에서 검사하고, 자원 확보가 실패했을
때만 한 번 알린다 — 정상적인 거절에는 침묵한다.

실기 확인 (`test/openstep-mga-mesa-depth-size-test.c`):

| 크기 | h*w % 2048 | 깊이 원점 | 결과 |
| --- | --- | --- | --- |
| 800x600 | 768 | 6119424 | **하드웨어 깊이** (전에는 소프트웨어) |
| 320x240 | 1024 | 4505600 | **하드웨어 깊이** (전에는 소프트웨어) |
| 333x222 | 198 | 4497408 | **하드웨어 깊이** |
| 640x480 | 0 | 5423104 | 하드웨어 깊이 (전에도) |
| 1024x768 | 0 | 0 | 깊이 자리 없음 — **정렬이 아니라 용량** |

측정값 다섯 개가 python 산술과 **정확히** 일치한다. `1024x768` 의 0 은
색 표면만으로 3 MiB 창을 정확히 다 채우기 때문이고 고침 전후가 같다 —
시험이 그 둘을 구분해 찍도록 고쳤다.

아래는 원래 기록이다.

## 3-20z. (원래 기록) Mesa 쪽 깊이 매핑이 4 KiB 로 정렬한다

```c
/* mesa/OpenStepMGAMesaBuffer.c:77 */
tail = (tail + 4095UL) & ~4095UL;
...
need = (need + 4095UL) & ~4095UL;
```

이 기계의 `PAGE_SIZE` 는 **8192** 이고, 드라이버의 `d_mmap` 은 페이지 정렬이
아닌 물리 주소를 거절한다:

```c
if ((phys & ((unsigned long)PAGE_SIZE - 1UL)) != 0UL) return -1;
```

**처음 계산은 전제가 틀렸다.** 보폭을 디스플레이 보폭으로 놓고 셌는데,
이 경로는 `if (bufStride != bufWidth) return 0;` 이라 **보폭이 곧 버퍼
너비**다. 다시 셌다.

`tail = (h*w*4 + 4095) & ~4095` 이고, 이것이 8192 의 배수여야 한다.
`h*w*4` 가 8192 의 배수인 것은 `h*w` 가 **2048 의 배수**일 때뿐이고,
아닐 때 4096 반올림은 4096 의 배수에만 떨어지므로 그중 절반이 어긋난다.

python 전수(너비 1..1024 × 높이 1..768, 786432 조합): **395172 개(50.2%)가
실패한다.** 그리고 흔한 크기가 걸린다:

| 크기 | tail | tail % 8192 | 깊이 mmap |
| --- | --- | --- | --- |
| 320x240 | 307200 | 4096 | **거절** |
| 640x480 | 1228800 | 0 | ok |
| **800x600** | 1921024 | 4096 | **거절** |
| 1024x768 | 3145728 | 0 | ok |
| 1024x767 | 3141632 | 4096 | **거절** |

**800×600 과 320×240 이 지금 하드웨어 깊이를 못 쓴다.** 시험이 늘
1024×768 이라 안 걸렸다.

실패하면 `mmap` 이 -1 을 돌려주고 `OpenStepMesaAccelDepthBuffer` 가 0 을
돌려주며, Mesa 는 **아무 말 없이 소프트웨어 깊이 버퍼를 쓴다.** 그림은
맞지만 하드웨어 깊이가 조용히 사라진다.

지금까지 안 걸린 것은 시험 높이가 768 이라 우연히 정렬됐기 때문이다.

**2026-08-21: 확인됐다.** §3-19 를 재면서 페이지 정렬이 아닌 오프셋이
`EINVAL` 로 **거절된다**는 것을 직접 쟀다(오프셋 × 길이 행렬: +4096 과
+12288 은 길이와 무관하게 전부 거절). 그러니 이것은 추정이 아니다 —
`tail` 이 8192 의 배수가 아닌 순간 깊이 `mmap` 이 실패하고, Mesa 는
소프트웨어 깊이로 조용히 되돌아간다.

고침은 4095 를 런타임 페이지 크기로 바꾸는 것이다. §3-19 가 철회됐으므로
막는 것은 이제 없다.

## 3-21. ~~pitch 가 32 배수가 아니면 틀리게 그린다~~ — **해결(2026-08-21)**

**「수락된 뒤 엉뚱한 자리에 그린다」가 없어졌다.** 세 겹으로 막았다:

- 커널 검증기가 `dstPitch % 32` 를 보고 `E_DSTPITCH` 로 거절한다
  (`hw3d/OpenStepMGAHW3D.c`).
- Mesa 표면이 생성 시점에 정렬 안 된 보폭을 거절한다
  (`mesa/OpenStepMGAMesaBuffer.c:322`).
- 검증기 시험에 경계 사례가 있다(1023 거절, 352 안의 333 수락).

남은 것은 **그 너비들이 가속을 못 탄다**는 것이고, 그건 §3-22 다 —
틀리게 그리는 것과 못 그리는 것은 다른 문제다. 아래는 원래 기록.


`test/openstep-mga-mesa-depth-agree.c` 를 크기 인자로 바꾸고 먼 구석에도
같은 삼각형을 그리게 하자 드러났다. 같은 삼각형을 가속과 강제 소프트웨어로
그려 커버리지를 비교한 것이다.

| 너비 | 하드웨어가 덮은 비율 |
| --- | --- |
| 64, 320, 352, 640, 800 | 98~100% |
| 322, 324, 328, 333, 336, 369, 655 | 1~14% |

**12 개 너비에서 예외 없이 갈리고, 가르는 것은 오직 "32 의 배수인가" 다.**
python 으로 확인했다 — 2·4·8·16·64 는 전부 못 가른다(336 은 16 의 배수인데
무너지고, 352·800 은 64 의 배수가 아닌데 멀쩡하다).

Mesa 쪽은 표면의 보폭을 그대로 `dstPitch` 로 넘기고
(`mesa/OpenStepMGAMesaHook.c:124`), 검증기는 `dstPitch != 0` 과
`dstWidth <= dstPitch` 만 본다(`hw3d/OpenStepMGAHW3D.c:132`). **정렬은
아무도 안 본다.**

배치는 **거절되지 않는다** — `hookDrawn` 이 오르고 revoke 도 안 걸린다.
수락된 뒤 엉뚱한 자리에 그린다.

**깊이 고침이 만든 버그가 아니라 드러낸 버그다.** §3-20 전에는 이 크기들의
깊이 매핑이 실패해 깊이를 쓰는 장면이 통째로 소프트웨어로 갔다. 깊이를 안
쓰는 프로그램은 예나 지금이나 이 너비에서 가속을 타고 틀리게 그렸을 것이다.

### 참조 구현이 같은 말을 한다 (X.Org `xf86-video-mga`)

측정에서 유도한 규칙을 원본과 대조했다. **두 곳에서 따로 확인된다:**

```c
/* mga_exa.c:869 */
/* Pitch alignment is in sets of 32 pixels, and we need to cover
 * 32bpp, so it's 128 bytes.
 */
pExa->pixmapPitchAlign = 128;
```

128 바이트 ÷ 4 바이트/화소 = **32 화소**.

```c
/* mga_dacG.c:2291 -- G 계열 DAC, 우리 것 */
pMga->Roundings[0] = 64;    /* 1 byte/px  */
pMga->Roundings[1] = 32;    /* 2 bytes/px */
pMga->Roundings[2] = 64;    /* 3 bytes/px */
pMga->Roundings[3] = 32;    /* 4 bytes/px  <- 우리 */
```

`Roundings` 는 `(bytesPerPixel - 1)` 로 색인하고, 4 바이트/화소는 **32** 다.

그러니 세 갈래가 같은 값을 가리킨다 — 실기 12 개 너비, `mga_exa.c` 의
주석과 상수, 그리고 G 계열 DAC 의 반올림 표. **추정이 아니다.**

덤으로: 16 비트 깊이는 `Roundings[1] = 32` 로 역시 32 화소다. 우리 깊이
보폭은 색 보폭과 같은 화소 수이므로, 색을 32 로 맞추면 깊이도 맞는다.

고침 후보(아직 계획 아님): 보폭을 32 화소의 배수로 올려서 가속을 유지하거나,
아니면 그런 보폭에서는 가속을 거절한다. 검증기도 함께 막는 편이 낫다.
정본 측정은 `M1_3L_PLAN.md` §6.

## 3-22. ~~보폭 패딩으로 32 화소가 아닌 너비도 가속할 수 있다~~ — **들어갔다(2026-08-24, 색 전용)**

§3-21 은 32 화소가 아닌 보폭에서 **가속을 거절**하는 쪽으로 고친다. 대신
보폭을 32 로 올리면 그 너비들도 가속할 수 있다. **색만 놓고 보면 안전하다**:

- Mesa 는 가속 표면에 애플리케이션 보폭과 다른 내부 보폭을 쓸 수 있다 —
  `OpenStepMesaAccelBuffer` 가 `appRowLength` 를 따로 기억하고 `rowLength`
  를 돌려주며, OSMesa 쪽 패치가 행 주소를 계산하기 전에 그것을 설치한다.
- 커널은 클라이언트가 준 pitch 를 그대로 쓴다. 두 쪽이 다른 주소를 계산할
  일이 없다.

**막는 것은 깊이 공유 하나다.** 커널은 깊이 보폭을 색 pitch 에서 유도하고
(`zstride = (pitchBytes/4) * DEPTH_BYTES`), Mesa 3.4 의 소프트웨어 깊이는
`DepthBuffer + Width*y + x` 로 너비 보폭을 가정한다. 그래서
`OpenStepMesaAccelDepthBuffer` 가 `bufStride != bufWidth` 를 거절한다.
패딩하면 깊이를 쓰는 장면이 소프트웨어로 갈 뿐이고 **틀리게 그려지지는
않는다.**

완전한 하드웨어 깊이까지 가려면 **계약에 깊이 pitch 를 따로** 넣어야 한다.
그건 별개의 작업이다.

### 계획을 세워 교차검토에 걸었더니 세 가지가 나왔다 (2026-08-24)

**하나는 패딩과 무관한 기존 결함이었고, 먼저 고쳤다.**

`OpenStepMesaAccelBuffer` 의 **재바인딩 빠른 경로**가 `appRowLength` 를 그대로
`bufAppRow` 에 넣고 곧바로 import 를 부르는데, "행 길이가 너비보다 짧으면
거절" 검사는 **그 아래 신선 할당 경로에만** 있었다. 호출자의 배열을 훑는 것들은
전부 `bufWidth` 낱말을 `bufAppRow` 간격으로 읽고 쓰므로, 너비보다 짧은 행 길이는
**모든 행에서 끝을 넘고 마지막 행에서는 배열 끝을 넘는다.** 빠른 경로가 느린
경로보다 느슨했던 것이고, 쓰기를 버퍼 안에 가두는 검사에서는 반대여야 한다.
검사를 두 경로가 모두 지나는 자리로 올렸고, `tuf` 에 회귀를 붙였다.

**나머지 둘은 패딩을 넣을 때 같이 해야 한다 (아직 안 함):**

- `OSMesaGetIntegerv(OSMESA_ROW_LENGTH)` 는 `ctx->rowlength` 를 그대로 돌려주는데
  (`osmesa.c:792-794`), 패딩하면 그건 **표면의 보폭**이지 호출자 배열의 행 길이가
  아니다. 헤더는 그 값을 *"actual pixels per row in image buffer"* 라고 정의한다
  (`osmesa.h:176`). 그러니 패딩 중에는 `userRowLength ? userRowLength : width` 를
  돌려줘야 한다.
- `OSMesaGetColorBuffer` 는 치환된 **VRAM 포인터**를 돌려주면서 너비·높이만 주고
  보폭은 안 준다(`osmesa.c:844-859`). 지금도 이미 불친절하지만, 패딩하면 호출자가
  보폭을 알 방법이 아예 없어져 **어긋난 그림**을 읽게 된다. 가속 중에는 미러하고
  애플리케이션 버퍼를 돌려주는 쪽이 맞다.

그리고 장부가 "틀리게 그려지지는 않는다" 고 한 것은 **P2(OSMesa 에 보폭을
알리는 것) 없이는 거짓이다** — Mesa 가 500 보폭으로 주소를 만들고 배치는
`dstPitch = bufStride` 로 그리면 섞인 그림이 나온다. 둘은 같이 가야 한다.

### 들어간 것 (라이브러리만 — 재부팅 불필요)

- **패딩.** 32 배수가 아닌 행 길이는 거절하는 대신 32 로 올린다. 호출자의 행
  길이는 `bufAppRow` 에 그대로 남고, 바뀌는 것은 **표면**뿐이다. 반올림 전후로
  pitch 레지스터 한계를 검사해 덧셈이 넘치지 않게 했다.
- **P2 를 같이.** 신선 할당 경로가 `*rowLength = 0`("덮어쓰지 마라")를 돌려주던
  것을 패딩된 보폭으로 바꿨다. 소프트웨어 래스터라이저는 **표면**을 주소하므로,
  한쪽이 500 으로 걷고 다른 쪽이 512 로 걷게 두면 섞인 프레임이 어긋난다.
- **공개 질의 둘을 정직하게** (교차검토 지적, 둘 다 채택):
  - `OSMesaGetIntegerv(OSMESA_ROW_LENGTH)` 는 치환 중에 **호출자의** 행 길이를
    답한다. 헤더가 그 값을 *"actual pixels per row in image buffer"* 라고
    정의하고, 패딩된 보폭을 돌려주면 앱이 그걸 그대로 `PixelStore` 로 되먹여
    **자기가 갖지도 않은 행**을 선언하게 된다.
  - `OSMesaGetColorBuffer` 는 치환 중에 미러하고 **애플리케이션 버퍼**를
    돌려준다. 전에는 VRAM 포인터를 너비·높이만 붙여 돌려줬는데, 패딩하면
    호출자가 보폭을 알 방법이 없어 어긋난 그림을 읽는다.

### 잰 것 (`tps`, 신규 — 회귀에 들어감)

500 폭 · 호출자 행 길이 520:

```
표면은 엔진의 것          : 보폭 544
보폭이 32 의 배수         : 예
장면이 엔진에서 그려짐    : 배치 2개
호출자 그림 밖은 안 움직임: 500열 뒤 6000칸 전부 sentinel 그대로
행 길이 질의는 호출자 답  : 520 (표면은 544)
소프트웨어와 같은 그림    : 150000 중 42 다름
```

**42 가 무엇인지 물었다.** 세는 것으로 끝내지 않고 **어디인지** 물었더니 42 개
전부가 **색이 바뀌는 경계에 접해 있고** 300 행 중 41 행에 흩어져 있다. 패딩이
틀렸다면 행이 통째로 밀려 경계와 무관하게 어긋났을 것이다. 이것은 이미 기록된
가장자리 커버리지 차이(`3-27`, `3-12`(2))이고 패딩과 무관하다.

### 알아 둘 것

호출자가 **current 인 채로** `OSMesaPixelStore(OSMESA_ROW_LENGTH, …)` 를 부르면
`ctx->rowlength` 가 호출자 값이 되어 표면 보폭과 어긋나고, 그 자리의 가드가
치환을 끝낸다. 패딩 전에는 두 값이 늘 같아서 "자기 값을 다시 말하는" 호출이
무해했는데 이제는 가속이 풀린다. **속도만 잃는다**(그림은 맞는다).

그리고 `OSMesaPixelStore` 와 `OSMesaGetIntegerv` 는 **current 문맥이 없으면
널을 역참조한다** — 상류 OSMesa 그대로다. 이 시험이 처음 그렇게 죽었다. 순서는
호출자의 몫이라 상류 동작을 바꾸지 않았고, 적어만 둔다.

깊이는 여전히 `bufStride != bufWidth` 에서 공유를 거절하므로, 패딩된 표면에서
깊이를 쓰는 장면은 소프트웨어로 간다 — 계획대로다.

## 3-23. ~~Mesa 표면의 소유·수명 계약이 상태 갱신 시점에 지켜지지 않는다~~ — **해결·확인(2026-08-24)**

pitch 수리를 교차분석하다 나온 **별개의, 이전부터 있던** 구멍 셋. 정렬
검사를 우회하지는 않지만, "거절하고 깨끗이 소프트웨어로 물러난다"는 의도된
동작을 무너뜨린다. 셋 다 소스에서 확인했다.

**(a) `OSMesaPixelStore` 가 상태를 갱신하지 않는다**

```c
/* osmesa.c, OSMesaPixelStore -- 이것이 전부다 */
ctx->rowlength = value;
ctx->yup = value ? GL_TRUE : GL_FALSE;
```

컨텍스트가 current 가 된 뒤 행 길이를 바꾸면 소프트웨어 행 주소는 다시
계산되지만 `osmesa_update_state` 가 안 불린다. 이미 설치된 하드웨어 삼각형
함수가 그대로 남아, **옛 보폭으로 제출하면서 Mesa 는 새 행 길이로 주소를
계산한다.** (`OpenStepMesaAccelUpdateState` 에 보폭 불일치 검사가 있지만
불릴 기회가 없다.)

**(b) 선택기가 소유를 안 본다**

```c
/* OpenStepMGAMesaHook.c */
if (OSMGAMesaBufferOrigin() == 0UL) return NULL;
```

원점과 보폭만 본다. `bufCtx == ctx` 는 안 본다. 그래서 다른 크기로 다시
바인딩했거나 두 번째 컨텍스트라 **표면을 못 받은 쪽도** 행 길이만 맞으면
하드웨어 함수를 받는다.

**(c) 해제가 자기 컨텍스트를 무시한다**

```c
OpenStepMesaAccelReleaseBuffer(void *ctx)
{
    (void)ctx;          /* <- */
```

두 번째 컨텍스트가 사라지면서 **첫 번째의 표면을 해제한다.**

### 시험 (2026-08-24 에 만들었다 — `town`)

셋 다 그 사이에 고쳐져 있었다. **읽어서 알았지만 읽기로 닫지 않았다** — 이
항목이 요구한 시험 셋을 만들어 재고 닫는다.

1. 행 길이를 표면이 갖지 못한 333 으로 바꾸면 표면을 놓고, 그 뒤로는 엔진에
   아무것도 가지 않는다.
2. 같은 컨텍스트를 다른 높이로 다시 바인딩하면 표면을 놓고, 그 뒤로는 엔진에
   아무것도 가지 않는다.
3. 두 번째 컨텍스트는 배치를 하나도 그리지 않고, **자기 버퍼에 2000 화소를
   칠하고 첫 번째 것에는 0 화소를 칠한다.** 그리고 그것이 파괴돼도 첫 번째의
   표면은 살아 있고 다시 엔진으로 그린다.

고쳐진 자리: (a) `OSMesaPixelStore` 가 배치가 더 이상 맞지 않으면 가속을 놓는다
(서브모듈 `OSmesa: end the substitution when the layout stops matching it`),
(b) 선택기는 `OpenStepMesaAccelUpdateState` 에서만 불리는데 그 함수가 소유
(`BoundTo`)·보폭·방향을 먼저 보고 물러난다, (c) 해제가 자기 컨텍스트만 놓는다.

### 시험을 쓰다 내가 틀린 것

첫 판은 두 번째 컨텍스트에 대해 `OSMGAMesaBufferOrigin() == 0` 을 단언했다가
**실패했다 — 드라이버가 아니라 내 단언이 틀렸다.** 그 접근자는 "표면이
있는가" 를 답하는 전역이지 "이 컨텍스트가 그것을 가졌는가" 가 아니고, 표면은
첫 번째가 여전히 쥐고 있으니 당연히 0 이 아니다. 중요한 성질은 그게 아니라
**두 번째가 첫 번째의 메모리에 그리지 않는다** 는 것이고, 지금은 그것을 잰다.

## 3-24. ~~정렬된 비표준 pitch 의 양성 시험이 없다~~ — **해결(2026-08-24)**

커널이 `dstPitch = 992` 를 **수락**하는 것은 확인했다(§`M1_3M_PLAN.md` §9).
확인 안 된 것은 **992 로 제대로 그리는가** 다 — 지금 클라이언트는 여전히
1024 보폭으로 색인하므로 화소 수치가 의미가 없다.

필요한 것: 요청한 pitch 로 채우고·세고·가드 화소를 두는 클라이언트. 여러 행에
걸치는 도형을 가로·세로 경계 근처에 그리고, 의도한 화소가 바뀌고 이웃
가드가 안 바뀌는지 본다. pitch 는 깊이 행 간격도 정하므로 깊이를 켠 경우도
포함한다.

"검증기는 992 를 통과시키는데 레지스터에는 1024 를 프로그램한다" 같은 회귀를
잡는 것은 이 시험뿐이다.

### 해결 (2026-08-24) — `tpq`

```
pitch 992, declared width 900, 16 rows, bar at columns 868..899
   words that changed              : 512
   intended words left untouched   : 0
   words written that should not be: 0
```

바뀐 워드의 **집합**이 기하가 지목한 집합과 정확히 같다. 엔진은 배치가 선언한
992 로 걷는다.

**형태가 요점이다.** 창 전체를 sentinel 로 채우고, 그린 뒤, **바뀐 집합**을
의도한 집합과 댄다. 수를 세는 것이 아니라 집합을 대므로 잘못된 보폭이 어디에
떨어지든 잡힌다 — 피치 오류, 좌표 밀림, 넘침 모두 실패하고, 어느 것도 "켜진
화소 수가 맞다" 뒤에 숨을 수 없다.

기하도 그렇게 골랐다. 폭(900)을 피치(992)보다 작게 두어 행마다 92 워드의
패딩이 실재하게 하고, 막대를 그 폭의 **오른쪽 끝**(868..899)에 32 워드로 둔다.
32 는 1024 − 992 다 — 잘못된 보폭이면 행마다 정확히 막대 하나만큼 밀려 패딩으로
떨어진다. 창은 32768 워드를 훑으므로 잘못된 보폭이 **훑는 범위 안에** 있다.

제출 뒤 첫 64 바이트 밖의 워드를 한 번 읽고 나서 훑는다. 그 구간의 쓰기는
늦게 보이며, 아직 나타나지 않은 워드를 피치 실패로 읽는 것을 막는다.

### 이 시험을 쓰다 내가 틀린 것

첫 판은 막대의 **색**까지 예측했다가 실패했다 — 기하는 완벽히 맞는데(512 변경,
밖으로 0) 예측한 색이 아니었다. `dr[]` 채널 순서를 추측한 탓이다. 이 시험이
물어야 할 것은 화소가 **어디에** 떨어지는가이지 무슨 색인가가 아니므로, 단언을
"sentinel 이 아니게 되었는가" 로 바꿨다.

### 함께 확인된 것

디스플레이 보폭은 **상한**이지 대체가 아니다: 제출 경로가 `dstPitch > stride3`
를 거절하고(`OpenStepMGAReplacementDisplay.m:3610`) 배치의 값을 프로그램한다.
클립도 `dstW3`/`dstH3` 와 `cy*dstP3` 로 전부 배치 값이고, 깊이 간격도 배치
피치에서 나온다.

## 3-26. ~~삼각형 단위 대체 경로에 시험이 없다~~ — **해결(2026-08-24)**

`M1-4a0` 이 만든 것 — 못 그리는 삼각형을 잃지 않고 소프트웨어로 넘기는 것 —
을 확인하던 시험이 **지렛대를 잃었다.**

- 그 지렛대는 "커널이 평범한 잘린 삼각형을 거절한다"(§3-25)였고, 그것이
  **잘못된 검사여서 고쳐졌다.** 이제 거절되지 않는다.
- 좌표 범위(16384) 밖 경로는 **Mesa 가 먼저 자르므로** GL 에서 닿지 않는다.

남은 것은 **시험 없는 정확성 기계**다. 그 경로가 정하는 것은 사소하지 않다:
검증 거절은 다시 그리고, DMA 이후 실패는 잃고 revoke 한다. 조용히 썩으면
어느 쪽으로 틀려도 안 보인다.

### 후보

1. **훅에 시험용 지렛대.** 이 백엔드에는 이미 환경변수 선례가 있다 —
   `OSMGA_PROBE_ENV` 가 가속을 통째로 끈다(`OpenStepMGAMesaProbe.c:80`).
   같은 결로 "N 개마다 하나는 소프트웨어로" 를 두면, 같은 장면을 전부 가속 /
   전부 소프트웨어 / 번갈아 그려 **셋이 화소로 일치하는지** 볼 수 있다 —
   `M1_4A0_FALLBACK_PLAN.md` §5 가 진짜 시험이라고 적은 바로 그것이다.
   그리고 시험 밖에서도 쓸모가 있다(그림 차이를 이분하는 스위치).
2. 선택기는 받아들이는데 커널은 거절하는 상태를 합성한다 — 지금은 그런
   상태를 찾기 어렵고, 찾더라도 다음 고침에 또 사라진다.

1 번이 낫다고 본다. 다만 **제품 코드에 시험용 손잡이를 두는 것**이므로,
계획을 세우고 교차검토를 거친다.

### 해결 (2026-08-24)

세 방식으로 같은 메시를 그려 셋을 다 판정한다. 지렛대는
`OSMGAMesaHookForceSoftware()`, 러너는 `tools/run-matrox-mesh-modes.sh`,
판정은 `tools/score-matrox-mesh-modes.sh`(호스트, python).

```
        엔진        소프트      안칠함  넘게  몫 부족
mesh    128/128 hw  0           0       0     0
        0/128   sw  128         0       0     6
        64/128  mix 64          6       0     6
mesh12  288/288 hw  0           0       0    52
        0/288   sw  288         0       0    12
        144/288 mix 144        35       0    58
mesh16  512/512 hw  0           0       0     0
        0/512   sw  512         0       0     5
        256/512 mix 256         5       0     5
```

`mix` 가 정확히 반반이다 — 홀수 삼각형은 소프트웨어, 짝수는 엔진이므로 **모든
공유 변이 하드웨어/소프트웨어 경계**다. 이 항목이 원하던 배치가 그것이다.

### 그 전에 고쳐야 했던 것 — `mix` 는 광고한 것을 만들지 못하고 있었다

루프가 `softOff(); glFinish();` 로 끝났다. **강제를 끈 뒤에 비운다.**

`glEnd` 는 아무것도 그리지 않는다. Mesa 는 즉시 버퍼에 표시만 하고
(`src/vbfill.c` 의 `gl_End`), 버퍼가 거의 찰 때(`gl_Begin` 의
`IM->Count > VB_MAX-4`)나 누가 비울 때 래스터화한다. 그러니 삼각형을 그리는
경로는 **비우는 시점**의 깃발이 정한다.

증거는 덤프 머리말이었다. 128 삼각형에서 `sw` 가 `drawn=57 software=71`(0 과
128 이어야 한다), 그리고 `mix` 가 **완전히 같은 수**. 삼각형마다 토글해도 결과가
같다는 것은 토글이 아무것도 정하지 않았다는 뜻이다.

고침은 강제가 걸린 구간 **안에서** 비우는 것이다. `sw` 는 루프 전체가 강제이니
끝에 한 번, `mix` 는 삼각형마다 `glFlush()`. 비용은 싸지 않다 — 이 백엔드는
`RenderFinish`·`Flush`·`Finish` 를 모두 미러에 걸어 두어서 비울 때마다 표면
전체를 훑는다(§3-32). 그래서 **빠른 회귀가 아니라 별도 스크립트**다.

### 왜 이렇게 됐나

옛 덤프의 머리말이 답이다: `# counters drawn=0 software=0 / # select hard 0
soft 1`. 그때의 강제는 **chooser 수준**이었고(표면 크기 시저로 chooser 가
소프트웨어를 고르게 했다), 그 방식에서는 비우는 시점이 상관없었다. 기구가
`OSMGAMesaHookForceSoftware` 로 옮겨졌을 때 시험이 함께 옮겨지지 않았다.

### 판정이 `hw` 만 실패시키고 있었다

`mesh-compare.py` 는 세 모드의 수를 **찍기만 하고** `hw` 일 때만 실패시켰다.
강제된 경로가 통째로 망가져도 성공이 나온다는 뜻이다 — 실제로 그런 상태였다.
지금은 세 모드를 다 판정하고, **먼저 어느 경로가 그렸는지**를 본다:
`hw` 는 소프트웨어 0, `sw` 는 엔진 0 이고 소프트웨어가 삼각형 수, `mix` 는 둘의
합이 삼각형 수이며 어느 쪽도 0 이 아니어야 한다. 그림은 그 다음이고, 기준값에서
움직였는지로 본다.

덤으로 둘: 목록이 `('mesh','mesh12')` 로 박혀 있어 **`mesh16`(512 삼각형) 덤프를
한 번도 보지 않았다**. 그리고 시험이 `OSMGAMesaHookForceSoftware` 를 **선언 없이**
부르고 있었다(C89 암시적 `int`) — 헤더를 include 하도록 고쳤다.

`# select hard/soft` 는 판정에 쓰지 않는다. 그 계수기는 chooser 의 선택 횟수이지
삼각형 수가 아니고, 강제 깃발은 chooser 를 거치지 않고 그리기 시점에 작동한다.

## 3-28. ~~프레임 측정 두 도구가 같은 작업을 다르게 잰다~~ — **해결(2026-08-24)**

`tmc` 와 `tcp` 가 **같은 작업**(clear + 작은 삼각형 + `glFinish`, 512×384)을
이렇게 잰다:

```
tmc : 306 ms      tcp : 160 ms
```

어긋남이 ~146 ms — 표면을 한 번 더 훑는 값과 같다. 통제가 나은 쪽은 `tcp` 다:
문맥 하나, 워밍업 있음, 두 팔이 같은 문맥. `tmc` 는 크기마다 문맥을 새로 만들고
부순다.

`RenderFinish` 에도 미러가 걸려 있어 프레임당 두 번 훑는 것 아니냐는 가설을
세웠으나, `tcp` 에서 삼각형을 넣어도 비용이 **+0.031 ms** 라 그 가설은 반증됐다.

### 원인: 두 도구는 같은 작업을 잰 적이 없었다

`tcp` 는 **투영 행렬을 한 번도 세우지 않는다** — 파일 어디에도 `glOrtho` 도
`glMatrixMode` 도 없었다. 단위행렬 아래서 `glVertex2d(10,10)` 은 w=1 인 클립
좌표 10 이고 세 꼭짓점 전부가 부피 밖이므로, **Mesa 는 삼각형을 통째로 버렸다.**
그 도구가 찍어 온 "the triangle cost +0.031 ms" 는 전부 **아무것도 아닌 것의
값**이었고, 아무것도 래스터화하지 않은 프레임은 `RenderFinish` 에 닿지 않으므로
미러도 하지 않는다. 어긋남 ~146 ms 가 정확히 미러 하나였던 이유가 이것이다.

그리고 **위에 적어 둔 반증도 무효다.** "삼각형을 넣어도 +0.031 ms 라 미러 두 번
가설은 반증됐다" 는 존재한 적 없는 삼각형에 근거한 것이었다. 실제로는 두 번
훑는다(아래).

### 고친 것과 재측정 (512×384)

`tcp` 에 투영을 넣고, 두 도구 모두에 **실제로 그린 배치 수와 미러 호출 수**를
찍게 했다. 배치가 0 이면 큰 글씨로 경고한다 — 같은 함정을 다시 밟지 않도록.

```
tcp  engine clear only        146.667 ms   (미러 호출 2/프레임)
tcp  Mesa   clear only        160.550 ms   (미러 호출 2/프레임)
tcp  engine clear + triangle  292.488 ms   (배치 20, 미러 호출 3/프레임)
tcp  Mesa   clear + triangle  306.567 ms   (배치  0, 미러 호출 3/프레임)
tmc  frame at 512x384         291.976 ms   (배치 20, 미러 호출 3/프레임)
```

`tcp` 의 Mesa 쪽과 `tmc` 가 **0.19 % 안에서 일치한다.** 예전의 "160 ms" 는
`tcp` 의 **clear 만 있는** 팔이었다.

## 3-28b. ~~한 프레임이 표면을 두 번 훑는다~~ — **해결(2026-08-24)**

§3-28 을 고치고 나니 훨씬 큰 것이 나왔다. `tmc` 를 세 크기에서:

```
128x96      18.682 ms   1520.35 ns/화소
512x384    291.976 ms   1485.07 ns/화소
1024x768  1169.741 ms   1487.40 ns/화소
```

5.36 MB/s 로 표면을 **두 번** 읽으면 4바이트 × 2 / 5.36e6 = **1492.5 ns/화소**.
맞춘 훑기 횟수: 2.037 / 1.990 / 1.993 — 세 크기 모두 정확히 둘이다.

그리고 clear 를 빼면 정확히 하나가 빠진다:

```
clear + triangle + finish   291.973 ms
triangle + finish           145.530 ms
```

**clear 는 엔진에서 돌고 프로세서로 화소를 하나도 쓰지 않는데** 요청하는 것만으로
146 ms 가 붙는다. 그건 clear 가 아니라 **clear 가 자기 렌더 괄호를 갖기 때문**이다
(`buffers.c:296-313`) — 이 백엔드는 괄호가 끝날 때마다 미러한다. 그 사이에 앱의
배열을 읽은 사람은 아무도 없으므로 **첫 번째 훑기는 순수한 낭비다.**

### 호출 3회, 복사 2회 — 세 번째는 어디서 오나

측정: clear 만 있는 프레임은 **호출 2회에 복사 1회**, clear+삼각형은 **호출 3회에
복사 2회**. 세 번째는 `RenderFinish` 가 아니다 — `glFinish` 가 부르는
`Driver.Finish` 이고(`context.c:2017-2023`), 이 백엔드는 거기에 같은 함수를
건다(`OpenStepMGAMesaHook.c:1818-1819`, `Driver.Flush` 도 같다). 짝이 되는
`RenderStart` 가 없으므로 직전 복사가 지운 `bufDirty` 가 그대로여서 복사하지
않는다. 계수기는 **복사가 아니라 호출**을 세며, 헤더 설명이 그렇게 안 되어 있어서
같이 고쳤다.

### 천장 수정 — 다만 범위를 붙여서

`3-32` 의 표(640×480 4.4 fps, 1024×768 1.7 fps)는 **훑기 한 번**으로 계산한
것이다. **clear + 그리기 + finish** 라는 잰 작업부하에 대해서는 2배 낙관이고,
그 작업부하의 천장은 **640×480 2.18 fps · 800×600 1.40 fps · 1024×768 0.85 fps**
이다.

이것을 "보편적 천장" 이라고 부르지는 않는다(교차검토 지적, 채택): clear 만 있는
프레임은 훑기 하나, 그리기만 있는 프레임도 하나이고, **한 프레임에서 여러 번
플러시되는 장면은 더 늘어날 수 있다** — 괄호마다 복사이기 때문이다. 그건 아직
재지 않았다.

### 왜 그냥 건너뛰지 않는가

clear 괄호의 미러를 미루면, 앱이 `glClear` 뒤 다음 괄호 전에 자기 배열을 들여다볼
때 낡은 것을 본다. 이 백엔드가 아는 지점은 `OSMesaMakeCurrent`·`glFinish`·
`glFlush`·`glReadPixels`·문맥 파괴뿐이고, **GL 호출 사이의 평범한 CPU 읽기는
알 수 없다.** 그러므로 지금 계약에서는 못 미룬다 — `3-32` 가 말한 "소유권 계약을
바꿔야 한다" 와 같은 결론이다.

### 들어간 것 (2026-08-24, 라이브러리만 — 재부팅 불필요)

계약을 안 건드리고 첫 훑기를 없앴다. 전면 clear 뒤 표면은 **상수 한 개**이고, 그
상수를 앱 배열에 쓰는 것은 시스템 RAM 쓰기다(1344 MB/s 대 5.36 MB/s, **250배**).
배달되는 바이트는 글자 그대로 같으므로 계약은 그대로다.

기구는 **다음 soil 이 가져가는 일회용 표시**다. `RenderStart` 의 무조건 더럽힘은
바꿀 수 없으므로(직접 기록자가 보이지 않는다) clear 가 표시를 남기고, 바로 뒤에
열리는 그 괄호만 그것을 쓴다. `Driver.Clear` 는 `buffers.c:280` 한 곳에서만 불리고
`RENDER_START` 가 `:296` 에서 바로 뒤따른다(전수 grep).

**조용히 프레임을 잃는 실패 하나**는 두 겹으로 막았다: 스팬 기록이 있으면(=Mesa 가
그렸으면) 평범한 미러로 돌아가고, **배치 수가 늘었으면**(=엔진이 그렸는데 스팬으로는
보이지 않으면) 역시 돌아간다.

**낱말은 표면에서 읽지 않는다.** 처음 계획은 submit 뒤 픽셀 하나를 읽는 것이었는데
**교차검토가 잡았다** — 하필 §3-18 이 "아무것도 정하지 못하는 유일한 오프셋" 이라고
기록해 둔 창의 첫 낱말이었다. 대신 OSMesa 자신이 `PACK_RGBA` 로 만든 `clearpixel`
을 건네받는다. 소프트웨어 clear 가 쓰는 바로 그 낱말이다.

전제와 검증은 재고 나서 넣었다 — `tcu`(네 색, 196608 화소 전부 동일하고 소프트웨어와
비트까지 같음, 대각선 이음매 없음)와 `tuf`(7개 주장 전부 통과, 그 중 하나가 "clear
뒤에 그린 삼각형이 살아남는가"). 설계와 수치는 `M1_4ED`.

```
                      전         후
clear 만 (512x384)   146.667    1.517 ms      (96배)
clear+삼각형          292.488  147.616 ms      (1.98배)
ns/화소 (세 크기)     1485~1520  749~807       (훑기 한 번 = 746.3)
```

천장(clear+그리기): 640×480 **4.36 fps**, 800×600 **2.79 fps**, 1024×768 **1.70 fps**.

남은 한 번의 훑기는 **그린 것을 배달하는 것**이고, 지금 계약에서는 줄일 수 없다.

## 3-29. ~~`reach` 가 한 시간 넘게 걸린다~~ — **재보니 2분 43초다(2026-08-24)**

`reach`(§1~§87 텍스처 프로브)가 통과는 하는데 한 시간이 넘는다. 대부분 §87
알파 시험 구간이고, 프로세스는 CPU 를 거의 쓰지 않으면서 느리다 — 제출 RPC 안에서
자고 있다는 뜻이다.

**퇴행이라는 증거는 없다.** `nxrun` 의 타임아웃은 총 시간이 아니라 **무출력**
시간이고 `reach` 는 계속 출력을 내므로, 예전에 얼마나 걸렸는지 잰 적이 애초에
없다. 정상이라는 증거도 없다.

### 재봤다 (2026-08-24)

`date; reach; date` 로 그냥 쟀다:

```
Mon Aug 24 23:25:37 GMT+0900 2026
Mon Aug 24 23:28:20 GMT+0900 2026     -> 2 분 43 초, FAIL 0
```

앞선 한 번도 3 분 반이었다. **한 시간이 아니다.** 이 항목의 "한 시간" 은 애초에
측정이 아니라 인상이었고(위 문단이 그렇게 적고 있다), 지금은 재현되지 않는다.
무엇이 달라졌는지는 모른다 — 이번 회기에 `reach` 를 빠르게 하려고 한 일은 없으므로,
그때 다른 것과 같이 돌고 있었을 가능성이 가장 크다.

### 그리고 "제출 RPC 안에서 자고 있다" 도 틀렸다

`ps` 로 보면 경과 시간의 **97~99% 가 CPU 시간**이다(69 초 경과에 CPU 68 초,
161 초에 157 초). 자고 있는 것이 아니라 태우고 있다.

구간별로는 §1~86 이 약 2 분, 나머지가 §87 이다. §87 은 최대 256 걸음짜리 쓸기 두
개이고 걸음마다 `blank()` 와 제출 하나다.

### 부품의 값을 따로 쟀다 (`tvr`, 신규)

```
비디오 메모리, 클라이언트 매핑으로, 한 낱말씩
   쓰기   8.281 ms   31.66 MB/s   0.13 us/낱말
   읽기  47.758 ms    5.49 MB/s   0.73 us/낱말
```

읽기 값은 미러로 잰 5.36 MB/s 와 **2.4% 안에서** 일치한다 — 서로 다른 두 방법이
같은 답을 낸다. 쓰기는 이제 처음으로 단독으로 잰 값이다(전에는 clear 두 개의
차이로만 있었다).

그래서 `blank()`(65536 낱말) 는 **8.3 ms** 이고, §87 의 512 번은 다 합쳐 **4.2 초**
다. 비디오 메모리 트래픽은 이 구간의 시간을 설명하지 못한다. 남은 것이 무엇인지는
재지 않았고, 전체가 3 분이므로 급하지 않다.

## 3-30. ~~`glResizeBuffersMESA` 와 가속 깊이~~ — **닿지만 무해하다(2026-08-24)**

`UseSoftwareDepthBuffer` 가 거짓이면 그 확장이 깊이 재할당을 건너뛴다
(`Mesa-3.4.2/src/buffers.c`). 가속 중에는 거짓이므로, 매핑된 깊이 표면이 **낡은
치수로 기술된 채** 남을 수 있다.

**닿는다. 그것도 확장을 통해서가 아니라 항상.** `matrix.c:1495` 가
`gl_Viewport` 끝에서 무조건 부르므로, 앱이 `glViewport` 를 할 때마다 실행된다.
"확장을 안 쓰면 안 닿는다" 는 전제부터 틀렸다.

그런데도 **두려워한 일은 일어날 수 없다.** 사슬은 이렇다:

1. `buffer_size`(`osmesa.c:1028`)가 돌려주는 것은 `osmesa->width/height` 이고,
   그 둘은 `OSMesaMakeCurrent` 에서만 바뀐다.
2. 색 표면 바인딩(`OpenStepMGAMesaBuffer.c:647-672`)은 **치수가 다른 재바인딩을
   거절한다** — 표면은 하나뿐이므로 크기를 바꿀 수 없다.
3. 거절되면 `osmesa.c:561-568` 이 `osmesa_leave_accel` 로 가속 자체를 벗는다.
   깊이는 소프트웨어로 되돌아가고(플래그까지), 내용은 복사되고, 표면은 풀린다.
4. 깊이 할당기(`:293`)도 색 표면과 치수가 정확히 같을 때만 내준다.

즉 **표면이 물려 있는 동안에는 `osmesa->width/height` 가 표면의 치수와 항상
같고**, 그래서 `ResizeBuffers` 는 `UseSoftwareDepthBuffer` 검사줄에 닿기 전에
"안 바뀌었다" 로 돌아간다. 치수가 바뀌는 유일한 길은 재바인딩이고, 그건 표면을
푼다.

**말을 정확히 해 둔다(교차검토 지적):** 새 크기의 재바인딩은 "가속인 채로 크기가
바뀌는" 것이 **아니라 가속에서 떨어지는 것**이다. `OSMesaMakeCurrent` 자체는
성공을 돌려주지만 그건 소프트웨어로 그린다는 뜻이다.

**있기는 한 창(窓), 닿을 수는 없는 것:** `OSMesaMakeCurrent` 는 `ctx->width/
height` 를 새 값으로 **먼저** 쓰고(`osmesa.c:529-531`) 그 다음에 할당기를 부르며,
할당기는 진입하자마자 `bufBound` 를 놓는다(`OpenStepMGAMesaBuffer.c:582-595`).
그 사이에는 `buffer_size` 가 새 치수를, 표면 기술은 옛 치수를 말한다. 그 구간에
GL 호출이 끼어들 수 없으므로 도달 불가이지만, 도달 불가인 이유가 "코드가 막아서"
가 아니라 "그 사이에 아무도 부르지 않아서" 라는 점은 적어 둔다.

**스텐실·누산은 무관하다.** 포팅이 건드리는 소프트웨어 플래그는 깊이와 알파뿐이고
(`osmesa.c:576-624`), `_mesa_ResizeBuffersMESA`(`buffers.c:560-572`)는 각 버퍼를
자기 플래그가 참일 때만 다시 잡는다. 스텐실·누산은 계속 소프트웨어 소유이므로
크기가 진짜로 바뀌면 정상적으로 다시 잡힌다. 알파를 되켜지 않는 이유는
`leave_accel` 주석에 적혀 있고 여전히 유효하다.

## 3-31. current 인 채로 앱이 자기 버퍼를 직접 쓰는 경우 (구조적, 2026-08-24)

바인딩 때 호출자의 버퍼를 들여오도록 고쳤다(`M1_4EC`). 그러나 **current 인 채로**
앱이 그 메모리를 직접 쓰면 아무도 볼 수 없고, 다음 프레임은 더 이상 일치하지
않는 비디오 메모리에서 그린다.

재바인딩이 두 쪽을 다시 맞추는 경계이며, 그렇게 문서화했다. 고칠 방법은 표면을
치환하지 않는 것뿐이므로 **결함이 아니라 계약**으로 남긴다.

## 3-36. 화면 present — 프레임 경로에서 시스템 RAM 을 뺐다 — **실기 동작·HW 가 SW 의 8.8 배(2026-08-25)**

  `AR5`=소스 stride(별도 레지스터), `SRCORG`/`DSTORG` 분리. **`mga_exa.c:240-248`
  에서 줄 단위로 검증** — X.Org 가 서로 다른 pitch 픽스맵 간 복사를 정확히 이
  인코딩으로 한다. (내가 "실증된 적 없다" 고 계획서에 썼던 것이 틀렸다 —
  mga_storm 의 XAA 만 보고 mga_exa 를 안 봤다. codex 가 잡았다.)
  겹침은 불가능(소스 창은 보이는 영역 위 가드 1 MiB 뒤에서 시작, 파이썬 확인)
  이라 방향 처리 없음. 검증은 전부 나눗셈/뺄셈형(오버플로 불가). busy 는 짧은
  락으로 잡고 풀고 진행(`.m:3344` 기존 패턴), post-EXEC 시간초과는 기존
  `stormBlitFailed` 걸쇠.
- **present 모드(라이브러리, 버퍼 수준)**: 호출자 배열을 **명시적으로 낡은
  것**으로 선언 — 미러·clear 상수 배달·재바인딩 import 전부 정지. 훅이 아니라
  버퍼 수준인 이유: 세 경로가 모두 버퍼를 지나고, 훅의 플래그는 둘을 놓친다
  (codex 지적 채택; 특히 재바인딩 import 는 낡은 배열을 **살아 있는 프레임
  위에** 썼을 것이다).
- **`spin` 샘플**: 회전 삼각형, 같은 화면 경로로 HW/SW 두 팔, median/p95/min +
  GL·present 단계 분리 + 엔진 계수기로 팔 증명(codex 의 측정 설계 채택).

### 수용하고 기록한 한계 (샘플 단계)

- **화면 소유권 없음**: 장치를 열 수 있는 클라이언트는 아무 화면 사각형에나
  그릴 수 있다. WindowServer 는 중재하지 않고(실측: blit 을 보내지 않음), 커서·
  메뉴가 지나가면 덮이며 다음 프레임이 덮어쓴다. `3-35` 와 같은 뿌리.
- **tearing**: 블릿이 스캔아웃에 동기화되지 않는다.
- **SW 팔의 CPU→VRAM 쓰기 가시성**: `glFinish` 는 GPU 순서만 보장한다. 깨진
  그림이 보이면 그것이 다음 조사 대상.

### 예상 (재부팅 뒤 확인할 것)

배달 제거 시 프레임 잔여는 실측에서 0.158 초(기하 0.015 + 삼각형당 제출 0.143).
삼각형 **하나**인 spin 은 제출 몇 번뿐이라 HW 팔은 수 ms/프레임이어야 하고,
SW 팔은 CPU 가 VRAM 표면을 31.66 MB/s 로 지우므로 clear 만 39 ms — **화면에서
눈에 보이는 차이**가 나야 한다. 안 나면 그게 발견이다.

구 커널에서는 `spin` 이 "mode/window" 로 깨끗하게 거절된다(확인) — fail-closed.

### 실기 결과 (2026-08-25, 재부팅 뒤 — 화면에서 육안 확인)

같은 장면·같은 표면·같은 present, **순서대로 따로** 240 프레임씩:

```
HW : median  3.39 ms  p95  3.40  min  3.25  ->  295.2 fps   (엔진 배치 240, clear 240)
SW : median 29.82 ms  p95 29.90  min 29.67  ->   33.5 fps   (엔진 배치 0,   clear 0)
                                                 하드웨어가 8.8 배
```

단계 분리가 구조 진단을 확정한다: **present 는 두 팔에서 동일**(1.73 ms — 같은
엔진 블릿)하고, 차이는 전부 래스터화 절반(1.66 대 28.09 ms)이다. SW 팔의 28 ms
는 CPU 가 VRAM 표면을 지우는 규모와 맞고(낱말 단위 예측 38.8 ms), present
1.73 ms 는 1.2 MB = 유효 **710 MB/s** — 미러(5.49 MB/s)로 같은 프레임을 옮기던
것의 **129 배**다.

SW 팔의 CPU→VRAM 쓰기 가시성 우려는 이 실행에서 나타나지 않았다(정상 완주,
화면 표시).

**"소프트웨어보다 빨라야 그 다음이 있다" 는 관문을 통과했다.**

### AppKit 창 통합 (`glwin`, 2026-08-25 — 실기 동작)

같은 장면을 **사용자가 움직일 수 있는 창** 안에 넣었다. 매 프레임
`convertPoint:toView:nil` → `convertBaseToScreen:` 으로 content view 의 화면
위치를 묻고, `dstY = 화면높이 − (y + 480)` 로 프레임버퍼 좌표로 바꿔 present
한다. 화면을 벗어난 프레임은 present 를 생략한다(클립하지 않음).

실측: **프레임당 3.39 ms — 고정 사각형 spin 과 동일.** 좌표 질의·변환 비용은
측정에 안 잡힌다. 타이머가 60 Hz 로 페이스를 잡는다.

교차검토에서 받아 반영한 것: 좌표는 변환 사슬이 불변식(뷰 frame.origin 은
슈퍼뷰 좌표), 창은 **처음부터 Nonretained**(buffered 면 윈도서버가 낡은 배킹을
그림 위에 되칠하고, 나중에 못 바꿈), 타이머 60 Hz(0 이면 이벤트 굶김), 매
프레임 가시성 술어 + `windowWillClose:` 정리, present 거절은 로그가 아니라
상태 전이. 추가로 실기 헤더에서 직접 확인해 넣은 것: **타이머를
`NSEventTrackingRunLoopMode` 에도 등록**(`addTimer:forMode:` 존재 확인) —
드래그 중에도 프레임이 오게 하는 이 기계 고유의 길이다.

한계는 spin 과 같은 가족: z-순서 권한 없음, 노출 시 다음 프레임까지 어두운
배킹, tearing. 다음 후보:
삼각형 배치 묶기(지금은 삼각형당 제출 — 큰 장면에서 73 us/제출이 병목, 찻주전자
실측), AppKit 창 통합(창 위치 추적), 스캔아웃 동기화.

## 3-37. 삼각형 배치 묶기 — **들어갔고 그림은 한 픽셀도 안 변했다(2026-08-25)**

한 소스 삼각형이 제출 하나였다: 찻주전자 한 프레임에 제출 16106 번 × 73 us =
1.2 초, 기하 전체가 0.015 초인 장면에서. 이제 사다리꼴이 매핑된 배치에
쌓였다가 함께 나간다.

**무엇이 한 배치를 공유하나**: dwgctl·alphactrl 은 사다리꼴 단위라 깊이 모드·
깊이 마스크·블렌딩은 자유롭게 섞인다. 배치 상태 — 텍스처 블록(tmr 기울기·원점·
크기·플래그)과 시저 — 가 키이고, 키가 다르면 먼저 내보낸다.

**재생 계약**: 커널은 인코딩 전에 검증하므로 거절된 배치는 아무것도 안 그렸고,
쌓였던 소스 전부를 소프트웨어로 재생한다 — 단 VB 인덱스가 살아 있는 동안만.
그래서 (1) 렌더 괄호를 넘겨 쌓지 않고(RenderFinish 래퍼가 flush), (2) **클립하는
VB 는 아예 묶지 않는다** — 클립 삼각형은 임시 정점을 빌려 쓰고 나중 클립이
그것을 덮으므로, 재생 인덱스는 그 순간에만 유효하다(교차검토가 놓쳐서 우리가
넣은 게이트), (3) 멀티패스 드라이버도 묶지 않는다(RenderFinish 전에 루프를
반복한다).

**flush 지점**: 괄호 닫힘·키 변화·용량·소프트웨어 스팬 쓰기/읽기 전·소프트웨어
삼각형 전·가속 clear 전(같은 tri[] 배열을 쓴다)·상태 갱신 진입(재바인딩 import
와 uninstall 이 지나간다)·텍스처 아레나 쓰기 전(업로드는 게으르므로 residency
복사가 유일한 초크포인트다).

**측정**:

```
찻주전자 grid 12 : 제출 16106 -> 193   (제출당 83 소스)
        grid 4  : 제출  1951 ->  64   (제출당 30), 14.87 -> 14.63 초
동일성 관문     : limit 1 과 기본값의 TIFF 가 바이트 단위 동일
주입 거절       : 매 flush 를 커널이 거절하게 하면 253 재생 후 8 회 한도로
                  revoke, 최종 그림은 순수 소프트웨어와 바이트 단위 동일
회귀            : PROBLEM 0, 장면 기준선 14 개 불변, spin 3.39 ms 그대로
```

교차검토가 잡아 준 것: 측정 지표(`hookDrawn` 은 소스 수라 불변이어야 하고
줄어야 하는 것은 `hookBatches`), 멀티패스 가드, 재생 재진입(flush 가 계류를
떼어 놓고 시작), uninstall 전 flush. 첫 측정의 16.13 초는 배치 탓이 아니라
재빌드 직후 첫 실행 오염이었다 — 한계값 계단(4/16/64/180 전부 14.6 초)으로
가려냈다.

**눈에 보이는 결과**: `glwin` 이 삼각형 대신 **조명·깊이 테스트가 켜진 회전
유타 찻주전자**를 창 안에서 돌린다 — ~30 ms/프레임(33 fps), 실기 화면에서
확인. 배치 전에는 이 장면의 제출 오버헤드만으로 프레임이 수백 ms 였다.

## 3-38. 창 present 의 마무리 — 방향·near 평면·서버 진실 정지 판정 (2026-08-25)

찻주전자를 창에 넣고 사용자가 본 두 증상: 뒤집혀 있다, 드래그 잔상이 돌아왔다.

**뒤집힘**: 뒤집힌 프러스텀은 반사이고 모델 180° 회전은 회전이라 서로
상쇄되지 않는다 — 스핀 전에 x 축 180° 를 넣어야 바로 선다. 이번에는 눈대중으로
넣지 않았다: glwin 과 같은 변환의 오프라인 렌더(`.glwin-orient.c`, 커밋 안 함)를
만들어 straight-row TIFF 로 먼저 봤다.

**그 과정에서 나온 덤**: 프로브가 몸통에 구멍·허공에 뜬 조각을 보여줬는데,
소프트웨어 렌더도 동일했다 — 렌더링 버그가 아니라 **scale 1.3·z −5 에서
주둥이가 near 평면(2.0)을 넘어와 잘린 것**. yspin 0–30° 는 주둥이 축이 카메라
방향이라 몸통 뒤에 숨는 것도 겹쳤다(yspin 90° 에서 완전한 주전자). 장면을
z −6·scale 1.0 으로 물렸고 grid 4 로도 온전하다.

**잔상**: 두 겹이었다.

1. **이벤트 큐 피크** — 잔상의 경주는 프레임을 그리는 20–30 ms 사이에 눌린
   타이틀바다: 서버는 즉시 창을 옮기는데 willMove 는 이벤트가 디스패치돼야
   온다. 그러나 이벤트 자체는 누른 순간 큐에 보인다.
   `nextEventMatchingMask:... dequeue:NO`(소비 없는 피크)를 틱 초입과 present
   직전 두 곳에 넣었다.
2. **서버 진실 위치** — 피크만으로는 줄었을 뿐 남았다. 남은 원인은 앱의 프레임
   캐시가 서버 측 드래그보다 늦는 것. `PScurrentwindowbounds`(psopsNeXT.h:128,
   동기 서버 왕복)로 **렌더 전·후 두 번 서버에게 직접 물어** 둘이 같아야만
   스탬프한다. 프레임 원점→내용 원점 오프셋은 창을 막 놓은 직후, 캐시가 맞다고
   증명되는 순간에 한 번 보정한다(실측 1,1).

**측정** (실기, 5 초 리포트):

```
프레임        : 평균 23.3 ms ≈ 43 fps (min 22.4 / max 49.7, scale 1.3→1.0 효과)
드래그 구간   : while-moving 스킵 106, queue-peek 스킵 14
              — 피크 게이트가 실제로 14 번, 알림보다 먼저 이벤트를 봤다
유휴 구간     : 두 카운터 동결, 서버 왕복 2 회/프레임은 프레임 시간에 묻힌다
남는 창구     : 마지막 질의·피크와 블릿 사이 ~1 ms 에 드래그가 시작되는 경우뿐
```

**프레임 23.3 ms 의 내역** (오프라인 프로브, 240 프레임 평균, 실기):

```
엔진 clear + finish        :  1.5 ms
지오메트리 + 제출 (배칭)   : 19.8 ms   <- 프레임의 85%
present 블릿               :  1.7 ms
게이트·서버 질의           : ~0.3 ms
합                         : 23.3 ms   (glwin 실측 평균과 일치)

배칭 없이(limit 1) 지오메트리 : 36.1 ms  -- 배칭이 프레임당 16.3 ms 를 벌었다
순수 소프트웨어 전체 프레임   : 110 ms   -- 창 경로 HW 가 SW 의 4.8 배
```

측정 중 잡은 프로브 버그: 팔 인자 "hw" 가 atoi 로 0 이 되고 BatchLimit 이
그것을 1 로 클램프해서, "hw" 팔이 조용히 **비배칭**으로 돌고 있었다. 커밋된
코드가 아니라 프로브의 문제였지만, 같은 인자 규약을 쓰는 도구가 또 생기면
같은 함정이 생긴다 — 숫자가 서로 안 맞으면 팔이 정말 그 팔인지부터 확인.

다음 최적화가 있다면 대상은 19.8 ms 짜리 지오메트리 경로다: 매 프레임의
베지어 평가·변환·조명(Mesa CPU 파이프라인)과 사다리꼴 인코딩이 섞여 있고,
소프트웨어 래스터라이저가 55 ms 이상을 쓰던 자리는 이미 엔진이 먹었다.

사용자 확인: 주전자 바로 섬, 타이틀바 클릭 1 초 후 재개 유지, 잔상은 "사용
가능한" 수준. 문서의 경고("Don't use this function if you're using the
Application Kit")는 읽기 전용 질의라 받아들인 위험이다 — 창을 서버 쪽에서
바꾸는 게 아니라 묻기만 한다.

## 3-39. 프레임이 어디로 가는지 — 실측 프로파일, 그리고 내 예상은 틀렸다 (2026-08-25)

3-38 을 닫으면서 "다음 최적화 대상은 19.8 ms 짜리 지오메트리 경로(Mesa CPU
파이프라인)"라고 적었다. **틀렸다.** Mesa 의 지오메트리 전체는 1.4 ms 다.

### 프로파일러는 포팅할 게 없었다

`/usr/lib` 에 `libc_p.a` 도 `gcrt0.o` 도 없어서 gprof 를 못 쓰는 줄 알았는데,
런타임은 이미 `libsys_s.B.shlib` 안에 다 있다 — `_monstartup`, `_monitor`,
`_monoutput`, `_monreset`, `_profil`, 그리고 `cc -pg` 가 뱉는 바로 그
`mcount`(밑줄 없음). `/usr/ucb/gprof` 도 있다. 빠진 건 그것들을 호출해 주는
`gcrt0.o` 하나뿐이고, gcrt0 가 하던 일은 둘이다:

```c
sect = getsectbyname("__TEXT", "__text");
monstartup((char *)sect->addr, (char *)(sect->addr + sect->size));
... 일감 ...
monoutput("/tmp/gmon.out");
```

`-pg` 도 필요 없다. `profil()` 히스토그램만으로 평탄 프로파일이 나오고, Mesa 는
정적 링크라 실행 파일 `__text` 안에 있다(심볼 3016 개, static 포함). 호출
그래프가 필요할 때만 `-pg` 재빌드가 필요하다. 샘플링은 100 Hz(10 ms 틱).

**커버리지 검증**: user 시간 9.2 ms/프레임 중 gprof 가 계정한 것이 8.4 ms.
나머지 0.8 ms 가 libsys(공유 라이브러리, 히스토그램 범위 밖). 처음에는 CPU
21.2 ms 대비 8.4 ms 만 보여서 60% 가 사라진 줄 알았는데, `getrusage` 로
user/sys 를 갈라 보니 12.6 ms 가 **시스템 시간**이었다. profil 은 user PC 만
샘플링한다.

### 절제 실험이 잡아낸 것 (전부 0.3 ms 이하)

아예 만들지 않았다 — gprof 가 같은 답을 더 정직하게 준다.

DMA 리스트 작성, 킥 직전의 **리스트 전체 읽기 배리어**(`sum3` 루프, 프레임당
약 292 KB — DMA 버퍼가 캐시되지 않는다면 이것만으로도 수 ms 다), 그리고 DMA

프레임당 소프트웨어 폴백이 1 개꼴로 있다(60 프레임에 61 삼각형 replay,
declined 2). 그림에는 영향이 없지만 원인은 안 밝혔다.

## 3-40. 값을 하나도 바꾸지 않고 유저랜드 절반을 깎았다 (2026-08-25)

3-39 이 지목한 자리를 깎되, **그림이 한 픽셀도 변하지 않는 변환만** 했다.
나눗셈을 곱셈으로, 2의 거듭제곱 나눗셈을 시프트로, 다섯 번 쓰던 식을 한 번으로.

**컴파일러가 안 해 주는 것들** (실기 `cc -O -S` 로 확인, 추정 아님):

```
x / 256.0            -> fdivrl        (2의 거듭제곱이어도 강도 축소 안 함)
osmgaFloorDiv(a, b)  -> idivl + 보정   (b 가 런타임 값이라 시프트로 못 바꿈)
(long)double         -> fnstcw/fldcw/fistpl/fldcw  (제어워드 두 번)
long >> k            -> sarl          (산술 시프트 -- E1 의 전제)
```

**들어간 것**

- `/ (double)OSMGA_MESA_SUBONE` 31 곳 -> `* OSMGA_MESA_SUBINV`. 2^8 로
  나누기와 2^-8 곱하기는 둘 다 지수만 바꾸는 정확 연산이다. 유일한 차이
  가능성인 서브노멀 언더플로는 피연산자가 0 아니면 최소 1/256 이라 도달 불가.
- `osmgaEdgeRegs` 의 `osmgaFloorDiv(x, 1<<shift)` 넷 -> 산술 시프트,
  `osmgaCeilDiv(e2, 1<<s)` -> `-((-e2) >> s)`. `s` 는 0..8 로 갇혀 있다
  (`sub` 는 SUBBITS 에서 시작해 양수인 동안만 감소, 이 함수는 static 이고
  호출자는 둘뿐). python 으로 k=0..8 x 90054 쌍 전수 대조, 불일치 0.
  C89 는 음수의 우측 시프트를 구현 정의로 두므로 `((-1L) >> 1) == -1L` 이라는
  **상수식**으로 감쌌다 — 접히므로 비용 0 이고, 논리 시프트 구현에서는
  나눗셈 경로가 그대로 남는다.
- `BuildTriangleTex` 가 다섯 번 계산하던 `x1,y1,x2,y2` 와 행렬식 `den` 을
  한 번으로. 가드(널 검사·좌표 검사) **뒤에** 놓았다 — 앞에 두면 없던 널
  역참조와 없던 부호 있는 뺄셈 넘침이 생긴다(교차검토 지적, 채택).
  행렬식은 반올림을 전혀 타지 않는다: 좌표 차이가 1/256 단위로 최대 2^22 라
  각 곱은 2^-16 의 정확한 배수로 45 비트, 그 차이는 46 비트 — binary64 의
  53 비트와 x87 의 64 비트 안쪽. 그래서 레지스터 배정이 어떻게 되든 값이
  움직일 수 없다.

**결과** (600 프레임, 같은 장면):

```

wall ms/프레임  22.03 -> 20.22  (45.4 -> 49.5 fps)

osmgaFloorDiv   0.82 -> 0      (시프트로 접혀 osmgaEdgeRegs 안으로: +0.27)
osmgaCeilDiv    0.58 -> 0.32

de_casteljau    0.85 -> 0.67   (Mesa 쪽은 안 건드렸다; 캐시 효과로 본다)
```

**게이트** — 넷 다 통과:

```

빠른 회귀           PROBLEM/FAIL 0
훅 카운터           변경 전 실행과 완전 동일:
                    drawn 59304 batches 1952 traps 109681
                    software 61 declined 2 unsupported 0 replayed 61
```

카운터가 한 자리도 안 움직였다는 것이 기하가 비트 단위로 같다는 가장 강한
증거다 — 삼각형 수, 사다리꼴 수, 거절 수, 재생 수가 전부 그대로다.

**안 한 것**: `/ den` 10 곳을 역수 곱셈으로 바꾸는 것(값 보존 아님), 그리고
부동소수-정수 변환 자체(`osmgaFixed`/`osmgaFix`/`floor` 로 아직 user 의 24%).
더 빠른 형태는 전부 동점 반올림 규칙이 달라진다. 밀리초와 픽셀을 바꾸지 않는다.

**교차검토에서 받은 것과 물리친 것**: 음수 우측 시프트가 C89 구현 정의라는
지적은 사실이므로 상수식 가드로 받았고, 이 타깃에서는 `sarl` 이 나온다는
어셈블리 증거로 반증했다. 호이스팅 위치 지적은 그대로 채택. 반대로 커널
시간을 `spins` 로 가르자는 내 계획(A1)은 **내가 폐기**했다: 성공한 제출은
`*out` 을 채우지 않고(`OpenStepMGAMesaHook.c` 의 submit 헬퍼는 거절일 때만
쓴다), `spins` 는 네 곳의 대기 중 DMA 완료 폴 하나만 센다(드라이버
4225/4281/4298/4305). 커널 13 ms 를 가르려면 커널 안에서 재야 하고, 그것은
재부팅이 필요하다.

## 3-41. 커널 12.6 ms 의 정체 — 엔진이 레지스터를 삼키는 속도다 (2026-08-25)

재부팅 없이 알아낼 수 있는 데까지 갔다. 드라이버는 제출마다 verdict/triangle/
dwords/spins 를 **성공이든 거절이든** 블록에 채워 돌려준다(`.m:1594-1607`).
훅의 submit 헬퍼 안에서 그것을 누산하고, ioctl 자체를 `gettimeofday` 로 쌌다
(실측 시계 분해능 4 us, 호출 한 쌍이 4 us — 375 us 짜리 ioctl 에 1%).

**헬퍼 안에서 재는 이유**: 헬퍼는 거절일 때만 `*out` 을 채운다. 성공한 제출의
블록을 호출자 쪽에서 읽으면 초기화되지 않은 값을 읽는다(교차검토 지적, 사실).

### 측정 (60 프레임씩, present 모드)

```
            us/제출  dwords/제출  사다리꼴/제출  폴index/제출
grid2        151.4      582.7         14.0        139.4
grid4        374.9     2199.7         54.5        345.7
```

두 점을 잇는 직선:

```
us/제출      = 74.1 고정 + 5.52 x 사다리꼴
폴 index/제출 = 68.0 고정 + 5.10 x 사다리꼴
dwords/제출   = 23.1 고정 + 39.95 x 사다리꼴

=> ENGSTATUS 읽기 한 번이 1.08 us
=> 엔진이 사다리꼴 하나를 삼키는 데 5.52 us
=> 리스트 dword 당 138 ns, 곧 레지스터 트래픽 28.9 MB/s
```

프레임(사다리꼴 1828, 제출 33.5)로 환산하면 고정 2.48 ms + 사다리꼴 10.09 ms
= **12.58 ms**, 실측 sys 12.6~13.3 ms 와 맞는다. 모델이 닫힌다.

### 그래서 커널은 무엇을 하고 있나

CPU 가 리스트를 만드는 것이 아니다. **다 만들어 놓고 ENGSTATUS 를 1 us 마다
읽으며 기다린다** — 사다리꼴당 5 번씩. 기다리는 대상은 엔진이 DMA 로 리스트를
읽어 레지스터에 밀어 넣는 일이고, 그 속도가 29 MB/s 다.

시저로 픽셀을 거의 없애도(같은 사다리꼴 109681 개) 폴 수는 346 -> 285,
시간은 375 -> 331 us 로만 준다. 즉 **그리는 일이 아니라 설명하는 일**이 벽이다.

### 사다리꼴 하나가 왜 40 dword 인가

인코더는 사다리꼴마다 여덟 블록을 무조건 쓴다(`.m:7731-7810`): DWGCTL/AR0/
AR1/AR2, AR4/AR5/AR6/SGN, DR4/DR6/DR7/DR8, DR10/DR11/DR12/DR14, DR15/DR0/
DR2/DR3, ALPHASTART/XINC/YINC/CTRL, DMAPAD/DMAPAD/FXBNDRY/DMAPAD,
그리고 YDSTLEN|EXEC. 블록당 5 dword(인덱스 워드 + 값 넷)이고, 한 블록은 값
넷을 채워야 해서 **DMAPAD 로 메우는 자리가 있다**.

### 다음 두 가지 가설, 둘 다 커널이라 재부팅이 필요하다

1. **리스트를 줄인다.** 같은 배치 안에서 바뀌지 않은 레지스터는 다시 쓸
   이유가 없고(ALPHACTRL·DWGCTL 은 대개 배치 내내 같다), 블렌딩이 꺼진
   장면에서 ALPHASTART/XINC/YINC 는 아무것도 하지 않는다. 40 dword 를 24 로
   줄이면 사다리꼴당 5.52 us 가 비례해 준다면 프레임에서 4 ms 가 빠진다.
2. **폴이 DMA 대역을 빼앗고 있을 수 있다.** 완료 폴은 같은 PCI 버스를
   1 us 마다 읽는다 — 사다리꼴당 다섯 번. 엔진이 그 버스로 리스트를 읽는
   중이다. 폴 사이에 짧은 backoff 를 두면 DMA 가 더 빨리 끝날 수 있다.
   3 줄짜리 변경이고, 안 되면 그만이다.

두 가설 다 커널 안에서만 확인된다. 계측(다섯 곳의 대기 각각, 복구 경로 포함)과
켜고 끌 수 있는 backoff 를 한 번의 재부팅에 함께 싣는 것이 다음 단계다.

**교차검토가 바로잡은 것**: 대기는 세 곳이 아니라 다섯 곳이다 — `WaitIdle` 과
`WaitFifo` 가 각각 자기 스핀 루프를 갖는다(`.m:1099, 1128`). 완료 폴이
실패하면 두 번째 완전 폴을 돌고, 그것도 실패하면 가속을 영구히 내린다
(`.m:4350, 4373, 4387`) — 평균만 보면 이 꼬리가 안 보인다. `spins` 는 반복
횟수가 아니라 **인덱스**라 읽기 횟수는 그보다 하나 많다. 그리고 IOMallocLow
메모리가 캐시된다는 내 서술은 근거가 없었다(헤더는 저 16 MB 라고만 한다);
시계는 `IOGetTimestamp` 보다 `clock_value(System)` 이 낫다 —
`clock_attributes(System)->resolution` 이 자기 정확도를 알려주고 어떤 IPL
에서도 호출 가능하다고 명시돼 있다(`kernserv/clock_timer.h:18-31`).

## 3-42. 재부팅을 기다리는 것 — 대기 다섯 곳의 계수와 두 개의 스위치 (2026-08-25)

3-41 이 남긴 두 가설을 실기에서 물어보기 위한 드라이버가 **빌드·설치까지
끝났고 재부팅만 남았다**. 기본값은 둘 다 오늘의 동작과 완전히 같으므로,
재부팅 직후의 기계는 측정된 그 기계여야 한다.

### 들어간 것

**계측.** 제출 하나가 쓰는 대기는 다섯 곳인데 보고되던 것은 하나뿐이었다.
공용 대기 헬퍼 둘(`osmgaStormWaitIdle`, `osmgaStormWaitFifo`)이 자기 **읽기
횟수**를 남기고, 제출 경로가 다섯 곳 전부를 누산한다. 읽기 횟수이지 루프
인덱스가 아니다 — 첫 읽기에 끝난 대기는 여기서 1, 기존 `spins` 필드에서는 0
이다. 일부러 하나 차이가 나게 두었다. `OSMGAHW3DWaits` 파라미터 16 워드
(버전 + 대기별 진입수·읽기합·최대). 읽는 도구는 `test/openstep-mga-hw3d-waits.m`.

**스위치 1 — 완료 폴의 backoff** (`OSMGAHW3DTune` 첫 워드, 0/1/2/4 us 만 허용).
폴은 1.08 us 마다 ENGSTATUS 를 읽는데, 그 버스는 엔진이 바로 그 리스트를
읽어 오는 버스다. 지연은 **완료를 못 본 읽기 뒤에만** 넣으므로 즉시 끝나는
제출은 한 푼도 더 내지 않고, 한계값을 지연으로 나눠 최악의 벽시계 시간이
늘지 않게 했다. **복구 폴은 지연시키지 않는다** — 그것이 소프트웨어와 아직
쓰고 있을지 모르는 엔진 사이를 막는 유일한 장치다.

**스위치 2 — FXBNDRY 를 실행 블록에 태우기** (두 번째 워드, 0/1).
`fd078fd` **이전에는 FXBNDRY 가 YDSTLEN+EXEC 와 한 블록이었다**. 사다리꼴마다
텍스처 앵커를 그 사이에 써야 해서 갈라진 것이고, 앵커는 텍스처가 있을 때만
나간다. 그러니 텍스처 없는 사다리꼴은 여전히 둘 사이에 아무것도 없고, 예전
그 블록에 그대로 들어간다 — 같은 레지스터, 같은 순서, 열 dword 대신 다섯.
사다리꼴이 40 dword 이므로 리스트의 1/8 이다.

### 재부팅 뒤에 할 일 (순서대로)

```
1. 스위치 둘 다 0 인 채로: 장면 기준선 14 개, 빠른 회귀, 프레임 20.2 ms
   -- 계측이 잰 만큼의 시간을 쓴다면 그 자체로 실패다
2. waits 를 읽어 고정 74 us 가 어느 대기인지 본다
3. 스위치 2 (pack) 만 켜고 프레임과 그림을 본다 -- 리스트가 1/8 줄면
   대기도 1/8 주는가? 곧 H2 의 답이다
4. 스위치 1 (backoff 1, 2, 4) 을 차례로 -- H1
```

### 교차검토에서 고친 것

내 계획서는 FXBNDRY 를 "앞의 alpha 블록에 태운다"고 썼는데 **불가능하다**:
alpha 블록은 ALPHASTART/XINC/YINC/CTRL 로 슬롯 넷이 다 차 있다. 지적이
맞았고, 내가 실제로 노린 자리는 alpha 가 아니라 **실행 블록의 빈 DMAPAD
슬롯**이었다 — 계획서 쪽이 틀린 문장이었다. 그 자리는 저장소 자신의 이력이
보증한다(`fd078fd` 이전 형태).

받아들인 것: 대기는 다섯 곳(+상태 프로그래밍은 대기가 아니라 별도 구간),
`spins` 는 인덱스, backoff 는 임의값이 아니라 짧은 화이트리스트로 받고 제출
시작 시 `stormLock` 아래에서 스냅숏, 락을 폴이나 지연 위로 들고 가지 않기,
복구 폴은 지연 금지. 기각한 것: 없음. 다만 "이번 재부팅에는 계측만 실으라"는
권고는 따르지 않았다 — 스위치 둘 다 기본이 오늘의 동작이고, 재부팅 한 번이
비싸며, 두 스위치는 계측이 대답하지 못하는 것을 대답한다.

줄인 만큼 대기가 준다. 리스트를 더 줄이는 것이 그대로 성능이다.

### H1 — 폴이 자기가 기다리는 DMA 의 대역을 빼앗고 있었다 (스위치 1)

완료 폴 사이에 IODelay 를 넣으면(pack 켠 상태, 각 두 번 측정):

```
  0     19.27       337.9       310.1
  1     19.65       347.1       145.0   <- 더 느리다, 재현됨
```

읽기를 86% 줄였더니 **대기 자체가 짧아졌다** — 덜 기다린 게 아니라 엔진이 더
빨리 끝냈다. 폴은 엔진이 리스트를 읽어 오는 바로 그 버스를 두드리고 있었다.
1 us 만 넣으면 오히려 나빠지는 것도 두 번 다 재현됐다: 읽기는 절반으로 주는데
버스는 여전히 붐빈다.

### 합계

```

pack 1 delay 2   18.07      55.3  -11.9%
```

delay 4 + pack 1 에서 장면 기준선 14 개 불변, 회귀 PROBLEM 0 FAIL 0.
지금 실기는 이 설정으로 돌고 있다. 기본값으로 삼으려면 소스를 고치고 다음
재부팅에 반영한다.

## 3-44. 설치 하나가 화면을 VGA 로 떨어뜨린 경위 (2026-08-25)

재부팅했더니 800x600 4 색으로 떴다. 부팅 로그에 `OpenStepMGA` 줄이 하나도 없고
`Registering: VGADisplay0` 만 있었다. `kl_util` 은 Loaded 라고 했다.

**직접 원인**: 설치된 번들에 `Instance0.table` 이 없었다. 인스턴스 표가 없으면
설정할 인스턴스가 없어 카드를 잡지 않는다. 같은 기계의 정상 드라이버
(`SpaceSaver2Keyboard.config`)에는 있다.

**왜 없어졌나**: 나는 **틀린 스크립트를 썼다**. 이 드라이버에는 전용
`tools/install-matrox-driver.sh` 가 있고(README:62, AFTER_A_REBOOT.md:51),
그것은 빌드 산출물에 `Instance0.table` 과 `Display.modes` 를 얹는다. 내가 쓴
범용 `nx-install-driver.sh` 는 그러지 않고, `rm -rf $DEST` 로 설치본을 통째로
지운다 — 인스턴스 표는 빌드 산출물이 아니라 번들의 설정이므로 새 사본에 없다.

**왜 낡은 바이너리가 설치됐나**: 범용 스크립트의 빌드는 `make 2>&1 | tail -3`
이라 파이프라인 종료 상태가 `tail` 의 것이고, `||` 가 발동하지 않는다. 그리고
이 번들의 `make` 는 실제로 실패한다 — reloc 프로젝트는 EDID/WARP/HW3D 소스를
tproj 안에 복사해 줘야 하고 그것은 `build-matrox-driver.sh` 만 한다. 복사된
트리에는 내 작업 트리에 남아 있던 **8 월 18 일자 빌드 잔재**(`.config/` 는
gitignore 대상이라 커밋된 것이 아니다)가 딸려 왔고, 그것이 설치됐다. 설치된
reloc 은 그 파일과 바이트 단위로 같았다(83040, sum 09670 82).

**복구**: `build-matrox-driver.sh` 로 현재 소스를 새로 빌드(361292 bytes)하고
`Instance0.table`·`Display.modes` 와 함께 설치, `chmod -R go-w`. 재부팅 후
`enterLinearMode done`, RGB:888/32 복귀.

### 교차검토 판정

- ✅ **`.config/` 는 커밋된 것이 아니라 gitignore 된 빌드 산출물이다**
  (`.gitignore:20`). 내 사고 기록의 "checked-in" 은 틀렸다 — 작업 트리에 남아
  있던 잔재였다. 정정했다.
- ✅ **범용 설치본은 원자적이지 않다**: `rm -rf $DEST` 뒤 `cp` 가 실패하면
  부분 번들이 남는다. 사실이다. 이번 사고 자체가 그 형태였다.
- ✅ **같은 파이프라인 결함이 다른 데도 있다**: `openstep-intel1000` 과
  `openstep-spacesaver2ps2` 의 각자 `nx-install-driver.sh:26` 에 그대로 있다.
  두 프로젝트는 자립 구성이라 여기서 손대지 않고 기록만 남긴다.
- ❌ **"소스의 `Instance0.table` 로 덮어쓰는 것은 잘못이고 사용자 설정을
  보존해야 한다"** — 이 저장소에서는 **의도된 규약**이다. 실기 파일만 고쳤다가
  다음 설치에 되살아나 측정을 두 번 잃은 뒤 "실기가 아니라 저장소를 고쳐야
  한다"고 결정한 기록이 있다(이 문서 424-425 행). 일반론으로는 옳은 지적이나
  여기서는 반증한다.
- ⚖️ **"인스턴스 표가 없으면 인스턴스화되지 않는다는 전제는 미증명"** — 맞다.
  복구할 때 표와 바이너리를 동시에 바꿨으므로 둘을 분리하지 못했다. 표만
  빼고 재부팅해 보면 갈리겠지만 그 값어치가 재부팅 값보다 크지 않다. 미해결로
  둔다.

### 고친 것

범용 스크립트가 **이 드라이버를 아예 거부한다** — 전용 스크립트 두 줄을
알려주고 종료한다. 그밖에 복사본에서 빌드 산출물을 먼저 지우고, make 의 종료
상태를 직접 받아 실패 시 로그를 보여주며 설치본에 손대지 않고, 인스턴스 표와
`.modes` 를 명시적으로 넣고, 설치 후 인스턴스 표가 없으면 거부한다.

## 3-45. 복구 폴은 성공할 수 없었다, 그리고 리스트의 30% (2026-08-25, 재부팅 대기)

### 먼저: 안전망이 작동하지 않고 있었다

완료 조건은 `SOFTRAPEN | ENDPRDMASTS` 이고 **트랩이 켜져 있어야** 완료다
(`.m:258-277`, 주석이 DRM 의 반대 비교를 베끼면 안 되는 이유까지 적어 뒀다).
그런데 완료 폴 직후의 `ICLEAR` 가 **무조건** 실행됐다 — 폴이 실패한 경로에서도.

그래서 복구 폴(`.m:4562`)이 같은 질문을 다시 물을 때 트랩은 이미 지워져 있고,
같은 리스트의 트랩은 두 번 켜지지 않는다. 즉 **복구는 구조적으로 성공할 수
없었다**: 폴이 포기한 직후 1 us 뒤에 끝난 리스트도 "끝나지 않았다"로 답하고
가속을 영구히 내린다. 복구 폴 바로 위 주석은 이미 *"트랩은 묻기 전에
승인하지 않는다"* 고 적혀 있었다 — 코드가 주석을 따르지 않고 있었다.

고쳤다: **폴이 완료를 본 경우에만** 승인한다. 시간 초과한 폴은 트랩을 세워
둔 채 복구에 넘기고, 복구가 완료를 보면 그때 지운다.

지금까지 발동한 적은 없다(폴 인덱스 최대 2024, 한계 100000). 그래도 이것은
"안전망이 있다"와 "안전망이 있는 줄 알았다"의 차이다.

### 변화 추적 인코더 — 재기 전에 먼저 쟀다

사다리꼴 하나의 레지스터 25 개 중 앞 사다리꼴과 다른 것은 **12.8 개**다.
그리고 절약은 세 블록에 전부 몰려 있다(실측, 109803 사다리꼴):

```
dwgctl                 1.8%     ar0 75.9  ar1 99.8  ar2 75.8
ar4 99.7  ar5 76.4  ar6 76.5  sgn 62.0
DR4  R시작  62.1     DR6  Rdx 35.1   DR7  Rdy 34.9
DR8  G시작  62.0     DR10 Gdx 35.1   DR11 Gdy 35.0
DR12 B시작  61.7     DR14 Bdx 34.9   DR15 Bdy 34.8
DR0  Z시작  99.9     DR2  Zdx 54.0   DR3  Zdy 53.9
ALPHASTART/XINC/YINC/CTRL  각 1.8%
fxbndry 97.8
```

블록 단위로는 리스트의 74.9% 만 나가면 된다. 그래서 컬러 블록 둘과 alpha
블록만 "바뀌었을 때만" 쓰고, 나머지 넷은 그대로 매번 쓴다.

**왜 안전한가**: 그 레지스터들은 execute 를 넘어 유지된다. X.Org 의 MGA
드라이버가 그것에 의존한다 — `MGASetupForCPUToScreenTexture` 가 컬러 9 개와
alpha 3 개를 **한 번** 쓰고(`mga_storm.c:419-431`), 프리미티브마다 도는
`MGASubsequentCPUToScreenTexture` 는 TMR6/TMR7/FXBNDRY/YDSTLEN|EXEC 넷만
쓴다(`549-565`). execute 가 보간기 상태를 소비하거나 초기화한다면 그 코드는
두 번째 사각형을 못 그린다. (교차검토가 이 증거를 찾아냈고, 나는 열어서
확인했다. 나는 반대로 의심하고 있었다 — 텍스처 앵커가 사다리꼴마다 다시
쓰이는 이유가 "엔진이 프리미티브마다 u 를 다시 심는다" 였으므로 컬러 시작값도
그럴 것이라고 봤는데, 그것은 앵커에만 해당한다.)

**추적기는 인코더 안의 지역 변수**이고 호출마다 빈 상태로 시작한다. 리스트
이전에 엔진이 들고 있는 것은 앞 제출의 것이거나 blit 의 것이거나, 엔진을 못
잡고 그냥 진행한 모드 변경의 것이다. 그리고 인코더에는 진단용 호출자도 있다
(`.m:4374, 8782, 9044`) — 파일 static 이면 안 되는 또 하나의 이유다.

예상: 사다리꼴당 35 -> 26 dword. 대기가 dword 를 따라간다면 17.8 ms 에서
2 ms 안팎.

### 이번 재부팅에 싣는 것

```
ICLEAR 수정        항상            (버그 수정)
pack               기본 켜짐       (지난 재부팅에서 실증)
track              기본 꺼짐       (첫 하드웨어 노출)
poll delay         기본 0          (아래 이유로 승격 보류)
```

**delay 를 기본값으로 올리지 않은 이유**: 교차검토가 지적한 경주가 실재한다 —
마지막 실패 읽기 뒤의 `IODelay` 동안 완료가 도착하면 그 폴은 못 본 채 끝난다.
`ICLEAR` 수정이 그 경우를 복구 가능하게 만들지만, 그 수정 자체가 아직 실기에서
한 번도 돌지 않았다. 순서를 지킨다: 고치고, 돌려 보고, 그 다음 승격한다.
delay 는 살아 있는 상태로 언제든 켤 수 있으므로 잃는 것은 없다.

`OSMGAHW3DTune` 은 이제 세 워드를 받되 **두 워드 호출도 그대로 받는다**(세
번째를 건드리지 않는다) — 옛 헤더로 빌드된 도구가 계속 동작한다.

### 재부팅 뒤 순서

```
1. track 꺼짐: 기준선 14, 회귀, 프레임 (pack 이 기본이므로 19.3 ms 부근)
2. track 켬:  기준선과 회귀를 먼저, 숫자는 그 다음
3. dword/제출 이 1927 -> 1450 근처로 떨어지는지, 대기가 따라오는지
4. 그 다음에야 delay 스윕과 기본값 승격
```

## 3-46. 리스트를 4분의 1 줄였고, 프레임은 20.5 -> 16.9 ms (2026-08-25)

### 재부팅 후 검증 (계획한 순서대로)

```
track 꺼짐:  기준선 14 불변, 프레임 19.99/19.97/19.95 (pack 기본 켜짐 확인:
             dwords 1927.2)
track 켬:    기준선 14 불변, 회귀 PROBLEM 0 FAIL 0 -- 숫자보다 먼저
```

### 결과

```
설정                      프레임   fps    us/제출   dwords/제출
pack 0 track 0 delay 0    20.50   48.8     376.6      2199.7
pack 1 track 0 delay 0    19.97   50.1     340.8      1927.2
pack 1 track 1 delay 0    17.92   55.8     277.3      1449.4
```

**예측이 맞았다.** 인코더를 쓰기 전에 유저랜드에서 "리스트는 74.9% 로 준다"고
계산했고, 실제로 75.2% 가 됐다. 커널 시간은 프레임당 12.63 -> 8.19 ms.

### 제출 비용의 모형이 닫혔다

세 점(dwords 2199.7/1927.2/1449.4, us 376.6/340.8/277.3)의 최소제곱:

```
제출 = 85.4 us 고정 + 132.4 ns x dword     잔차 ±0.2 us
```

고정 85 us x 33.5 제출 = **프레임당 2.87 ms 는 리스트를 아무리 줄여도 안
줄어든다**. 다음 지렛대는 레지스터가 아니라 **제출 횟수**다. 지금 프레임당
33.5 제출(사다리꼴 54.6 개씩)이고, 이것을 정하는 것은 배치 한계가 아니라
렌더 괄호다 — `glEvalMesh2` 가 프레임에 32 번이라 괄호가 32 번 닫힌다.
괄호를 넘겨 쌓지 않는 것은 재생 계약(VB 인덱스가 살아 있는 동안만) 때문이므로,
합치려면 그 계약부터 다시 봐야 한다.

### 교차검토 — 내가 틀린 것부터

❌ **"기준선이 잘못된 skip 을 잡는다"는 내 주장은 약했다.** 두 가지가 겹친다:

1. 기준선은 하드웨어와 소프트웨어의 **차이 줄 수**를 기록된 숫자와 비교한다
   (`run-matrox-scene-baselines.sh:40-42`). 어느 픽셀이 다른지는 안 본다.
   skip 이 틀려서 다른 픽셀이 어긋나도 개수만 같으면 통과한다.
2. 그 장면 대부분이 **색과 알파가 상수**다 — `rgba` 는
   `glColor4f(1,1,1,0.5)`(`texdraw:283-287`), 곧 skip 이 옳은 쪽 경우다.
   정점마다 색이 다른 `modg`(`texdraw:958-972`)는 기준선 14 개에 없다.
   나는 `blendquad` 를 읽고 "rgba 는 색·알파가 변한다"고 적었는데, 그 함수는
   다른 장면 것이었다.

그래서 **하드웨어 대 하드웨어** 검사를 만들었다
(`tools/check-matrox-track-identity.sh`): 같은 장면을 트래커 끄고/켜고 두 번
그려 덤프를 **바이트 단위로** 비교한다. `modg`·`rgbalin` 을 포함한 20 장면,
0 이동. 이것이 실제 게이트이고, 기준선은 그 다음이다.

✅ **고정 비용 산술**: 교차검토가 두 점에서 "85 us + 133 ns/dword" 를 냈다.
세 번째 점을 넣어 확인했더니 85.4 + 132.4, 잔차 ±0.2 us. 맞다.

✅ **skip 조건은 기계적으로 옳다** — 리스트마다 빈 상태로 시작하므로 첫
사다리꼴은 세 블록을 다 쓰고, 배치 상태 블록은 DSTORG/ZORG 와 텍스처
레지스터만 쓰므로 추적 대상과 겹치지 않는다. 텍스처/비텍스처가 한 배치에
섞이는 것은 허용된다(`Hook.c:1119-1127` 의 플러시 조건은 텍스처 **키**
불일치뿐이다). 추적기에 텍스처 예외가 없는 것이 맞다 — 추적하는 것은
RGB/알파이지 텍스처 상태가 아니다.

⚖️ **"텍스처 EXEC 가 추적 대상을 건드리지 않는다는 것은 미증명"** — 우리
기계에서 그 전이를 색이 바뀌는 채로 직접 돌리지는 않았다. 다만 근거는 이미
있다: X.Org 의 `MGASubsequentCPUToScreenTexture` 는 **텍스처 EXEC 를 반복**
하면서 한 번 설정한 컬러·알파에 의존한다(`mga_storm.c:419-431` 대 `549-565`).
그것이 곧 "텍스처 EXEC 가 그 상태를 안 건드린다"의 증거다.

✅ **delay 를 기본값으로 올리지 않는다.** 트랩 승인 수정은 옳지만 복구 경로는
아직 한 번도 실행된 적이 없다(폴 인덱스 최대 2025, 한계 100000). 고의로
시간 초과를 주입해 복구가 완료를 보고 트랩을 지우고 가속을 유지하는지
확인하기 전에는 승격하지 않는다. 살아 있는 채로 켤 수 있으므로 잃는 것은 없다.

⚖️ **회귀 스크립트가 튜닝 상태를 스스로 설정하지 않는다** — "track 켜고 회귀
통과"는 내가 먼저 켜 두었기 때문이고, 스크립트만으로는 재현되지 않는다.
사실이다. 두 러너가 상태를 설정하고 출력하게 고칠 일로 남긴다.

## 3-47. 복구 경로를 일곱 번 돌렸고, 한 번도 잠기지 않았다 (2026-08-25)

트랩 승인 수정이 옳은지는 복구가 실제로 돌아야 알 수 있는데, 이 기계에서
완료 폴이 시간 초과한 적은 한 번도 없다(최대 인덱스 2025, 한계 100000).
그래서 **겪지 않은 시간 초과를 주입**했다: 전용 파라미터
`OSMGAHW3DInject`(0~4)가 다음 N 개 제출에서 완료 폴을 아예 건너뛰고 시간
초과했다고 보고한다. 그 시점에 리스트는 이미 엔진에 넘어가 있다.

### 결과

```
inject 1, delay 0      -- 주입이 프레임의 clear 에 걸렸다
  로그: "the poll gave up but completion arrived during recovery
         (status 80820025, 2076 more spins)"
  카운터: recovery 1 saved, 0 latched
  훅: declined 1, software 0, replayed 0, drawn 20447 (전부)
      fills 21 -> 20, mirrors 693 -> 694

inject 2, delay 0      -- 두 번째가 첫 삼각형 배치에 걸렸다
  submits 2, drawn 0, batches 1, software 992, declined 994, replayed 0
  카운터: recovery 3 saved, 0 latched

delay 2 와 4 에서 반복: 같은 모양, 5 saved -> 7 saved, latched 0

"acceleration DISABLED permanently": 로그에 0 건
그 뒤 새 프로세스: drawn 20447, declined 0, 프레임 16.86 ms
그 뒤 장면 기준선: SCENES_MOVED=0
```

### 두 가지 거절 정책이 각자 주석대로 움직였다

- **거절된 clear** 는 revoke 없이 Mesa 의 clear 로 물러난다 — "반쯤 된 clear 는
  같은 색을 덮어쓰면 끝난다. 두 번째 패스가 첫 번째가 남긴 것에 의존하지 않기
  때문이다."
- **검증을 통과한 뒤 실패한 삼각형 배치** 는 재생하지 않고 그 프로세스의
  가속을 포기한다 — "일부가 이미 화면에 있을 수 있고, 다시 그리면 두 번
  그려진다."

그래서 내가 계획서에서 걱정한 이중 그리기는 **일어날 수 없다**. 이 경로에서
재생되는 것은 없다. 대가는 그 프로세스가 가속을 잃는 것이고, 그림은 옳다
(992 삼각형이 Mesa 래스터라이저로 갔고 기준선은 그대로다).

### 교차검토가 잡은 내 과장 두 가지

❌ **"delay 를 바꿔가며 시험했다"** — 아니다. 주입은 폴 루프 **전체**를
건너뛰므로 `IODelay` 도 실행되지 않는다. delay 2 와 4 에서의 반복은 같은
코드를 다시 돈 것이고, 진짜 시간 초과에서 delay 가 무엇을 하는지는 재지
않았다. 재려면 엔진이 100 ms 넘게 걸려야 하는데 만들 수 없다.

⚖️ **"복구가 DMA 포인터가 끝에 닿았음을 확인한다"** — 정확히는 `ENGSTATUS` 의
세 비트 술어(트랩 켜짐 + 엔진 유휴 + ENDPRDMASTS)를 본다. 포인터를 직접 읽어
`tail3` 와 비교하지는 않는다. 드라이버 주석의 표현을 그대로 옮긴 것이지만,
상태 비트와 포인터 비교는 다르다.

### `rc3 = 1` 은 아직 하지 않는다

교차검토의 제안: 복구가 완료 술어를 확인했으면 드라이버가 **성공**을 보고해야
하고, 그러면 프로세스가 가속을 잃지 않는다. 일리가 있다.

다만 정상 성공 경로에는 **settle read** 가 있고 복구 경로에는 없다. 그것은
완료 검사가 아니라 **CPU 가시성 수리**다 — 창의 첫 64 바이트에 엔진이 쓴 것이
바이트 64 이후를 읽기 전까지 낡은 채로 남을 수 있다는 실측에서 나온 것이고,
`AUTO` 일 때 배치가 그 범위를 건드릴 수 있으면 실행된다. 그러니 settle 없이
성공을 보고하는 것은 계약을 바꾸는 일이다. 옮긴다면 **블록 전체를 공통
후처리로 빼내** 두 경로가 같은 논리를 타야 한다.

그리고 이것이 고치는 상황은 **아직 한 번도 일어난 적이 없다**(진짜 시간
초과 0 회). 안전 경로의 의미를 바꾸는 값어치와 재부팅 값어치를 견주어,
지금은 하지 않는다. 확인해야 할 것도 남아 있다: 이 기계의 정상 동작에서
settle read 가 실제로 발동하는지(`overlap3` 조건) 아직 안 쟀다.

### 이제 delay 를 기본값으로 올려도 되는가

막고 있던 이유("복구 경로가 한 번도 안 돌았다")는 해소됐다 — 일곱 번 돌았고
한 번도 안 잠겼다. 한계값은 이미 delay 로 나뉘어 있어 최악 벽시계 시간이
늘지 않는다(4 us 에서 20000 x 5.08 us = 102 ms, 원래 100000 x 1.08 = 108 ms).
남은 것은 승격 자체가 재부팅을 쓴다는 점뿐이다.

## 3-32. 미러가 프레임의 전부이고, 그것은 장부가 아니라 계약 문제다 (2026-08-24)

`glClear` 를 가속하고 나니 512×384 프레임 146.7 ms 중 clear 가 ~0, 삼각형이 ~0,
나머지 전부가 미러다. 미러의 실제 속도를 두 크기에서 쟀다:

```
128x96 :    49152 B /   9.753 ms ->  5.04 MB/s
512x384:   786432 B / 146.665 ms ->  5.36 MB/s
```

두 크기가 일치한다 — 이 기계의 **uncached VRAM 읽기 속도**이고, "VRAM 에서 그리고
시스템 RAM 으로 배달한다"는 구조가 프레임마다 무는 값이다.

**아래의 상한은 훑기 한 번을 가정한 것이고, 실제로 잰 clear+그리기 프레임은 두 번
훑는다 — `3-28b` 참조. 그 작업부하의 천장은 이 표의 절반이다.**
훑기 한 번 기준: 640×480 4.4 fps, 800×600 2.8 fps, 1024×768 **1.7 fps**.
clear+그리기 기준(`3-28b` 을 고치기 **전**): 640×480 2.18 fps, 800×600 1.40 fps,
1024×768 0.85 fps.
clear+그리기 기준(**지금**, clear 가 표면을 읽지 않고 배달한 뒤): 640×480
**4.36 fps**, 800×600 **2.79 fps**, 1024×768 **1.70 fps** — 훑기 한 번으로 돌아왔다.

**더티 사각형은 이 작업부하를 못 돕는다** — 프레임마다 표면 전체를 지우면 바뀐
화소가 전부이고, 전부는 어차피 배달해야 한다. 부분만 바뀌는 작업부하에서만 값이
있으므로, 그것부터 재야 판단할 수 있다. 계획과 그것을 접은 이유는 `M1_4EB`.

넘으려면 **소유권 계약**을 바꿔야 한다(앱이 실제로 볼 때만 읽어오기, 또는 표면을
치환하지 않기). 그건 재고 나서 설계한다.

## 3-33. ~~mmap 창의 시작이 `rowBytes` 가 아니라 `width*bpp` 에서 나온다~~ — **해결·실기 확인(2026-08-24)**

오프스크린 창의 시작을 정할 때 보이는 표면의 끝을 `wr->width * bytesPerPixel *
wr->height` 로 잡는다(`OpenStepMGAReplacementDisplay.m:2164-2166`). 디스플레이의
`rowBytes` 가 `width * bpp` 보다 크면(행마다 패딩이 있으면) 이 값이 실제 끝을
**과소평가**하고, 오프스크린 창이 스캔아웃의 꼬리와 겹칠 수 있다.

### 재고 나니 질문이 틀렸다

`rowBytes` 에는 **대입이 딱 하나** 있고(`.m:2073`), 그 식이 `.m:2164` 의 식과
글자까지 같다: `width * bytesPerPixel`. 그러니 "행마다 패딩이 있으면" 이라는 전제
자체가 이 드라이버에서는 성립하지 않는다. 패딩은 어디서도 만들어지지 않는다.

진짜로 물어야 했던 것은 **하드웨어가 스캔아웃하는 pitch 가 그 값과 같은가** 이다.
그건 `rowBytes` 가 아니라 CRTC[19] + CRTCEXT0 두 비트이고,

```
wd = width >> (4 - bppShift)        (.m:1800)   bppShift: 32bpp 2, 16bpp 1, 8bpp 0
pitch = wd * 16 bytes
```

단위가 16바이트라는 것은 1024×32bpp 에서 `wd=256`, `256*16=4096=1024*4` 로 맞고,
X.Org 의 mga 드라이버가 **같은 식과 같은 시프트 표**를 쓴다(`mga_dacG.c:1380`,
`mga_driver.c:2243-2246`) — 독립 구현이 같은 답을 낸다.

**시프트는 버림이다.** 행이 16바이트의 배수가 아니면 pitch 가 행보다 **짧게**
프로그램되어 화면이 어긋난다. 그러니 원래 걱정했던 "창이 스캔아웃 꼬리를 덮는다"
보다 **먼저, 더 크게** 깨진다.

파이썬으로 게시 중인 5해상도 × 5포맷 = **25조합 전수 확인: 불일치 0.** 필요한
배수는 32bpp 4화소·16bpp 8화소·8bpp 16화소이고 게시 폭은 모두 16의 배수다.

엔진 쪽도 따로 본다. X.Org 는 G 계열 스캔아웃 폭을 8bpp 64화소·16/32bpp 32화소로
올림한다(`mga_dacG.c:2291-2294`). 우리 폭 중 800 은 64의 배수가 아니지만, **엔진을
쓰는 경로는 전부 `bytesPerPixel != 4` 에서 되돌아가고**(`.m:2572, 2811, 2972,
3064, 3482, 3529, 4462, 5344, …`) 32bpp 기준 32화소 배수는 다섯 폭 모두 만족한다.

### 들어간 것 (실기 적용됨; 부팅 로그에 발동 흔적 없음 — 예측대로다)

산술은 그대로 두고 **검사 하나**를 넣었다 — `osmgaModePitchIsExact()`, 그리고
`selectModeFromConfig` 끝에서 고른 짝이 그것을 통과하지 못하면 기본 모드로
되돌린다. 오늘은 절대 발동하지 않는다. 넣는 이유는 이것이 **코드의 성질이 아니라
표 두 개에 적힌 숫자의 성질**이기 때문이고, 다음에 폭을 추가하는 사람이 그것을
깨는 자리이기 때문이다(`OSMGA_CMD_MMAP_BASE` 검사와 같은 취지).

**창 시작만 올림하지 않는 이유**: 같은 가정을 쓰는 자리가 셋이다 — 게시되는
`rowBytes`/`memorySize`(`.m:2073-2080`), 부팅 때 화면을 지우는 루프
(`.m:2514-2519`), 그리고 mmap 창의 시작(`.m:2164`). 창만 고치면 나머지 둘과
스캔아웃 어긋남이 그대로 남는다. 진짜로 패딩 pitch 를 지원하려면 pitch 를 올림해
**프로그램하고 그것을 `rowBytes` 로 게시하고** 모든 범위를 거기서 계산해야 한다.
그건 이 항목이 요구한 적 없는 별개의 기능이다.

### 덮지 않는 것

`rowBytes` 를 저장소 안에서 다시 쓰는 곳은 없다(전수 grep). 그러나
`IOFrameBufferDisplay` 나 윈도서버가 **게시 뒤에 구조체를 고치지 않는다는 증명은
없다** — 둘 다 바이너리다. 지금 쓰는 모드에 대해서는 간접 증거가 있다: 엔진
경로들이 매 호출 `di->rowBytes / 4` 를 새로 읽어 목적지 보폭으로 쓰는데
(`.m:3535, 4367, …`) 1024×768×32 에서 그림이 맞는다. 다른 모드에 대해서는 재지
않았다.
