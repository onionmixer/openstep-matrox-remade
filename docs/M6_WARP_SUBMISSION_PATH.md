# M6 — 커널의 WARP 제출 경로 (2026-08-29, 코딩 전)

## 0. 이 단계의 경계

버전 10 계약과 유저랜드 절반은 착지했다(M5 §15).  남은 것은 **커널이 WARP
배치를 실제로 실행하는 것**이다.

**이 단계에 넣지 않는 것:**
- 훅의 라우팅 결정(어느 삼각형을 WARP 로 보낼지) — 정책이 T7·T8 을 기다린다
- `osmgaHW3DWarpAdmits` 를 넓히는 것 — 같은 이유

**그리고 v9 경로는 한 줄도 바뀌지 않는다.**

## 1. 스냅샷 — TOCTOU 는 이미 답이 있다

`:6327` 이 v9 에서 하는 것을 그대로 한다: **개수를 한 번만 읽고, 검사 전에
복사한다.**  주석이 이유를 적어 놨다 — *"reading it again after the copy would
reintroduce the same window it is here to close."*

WARP 판:

```
nr = runCount, nv = vtxCount            한 번만 읽는다
상한만 먼저 본다 (nr <= 16, nv <= 720)
복사 = fixed + MAX_RUN*16 + nv*32       run[] 은 통째로 (256 바이트)
스냅샷의 개수를 읽은 값으로 고정
그다음 osmgaHW3DValidateWarp
```

`run[]` 을 통째로 복사하면 부분 복사의 경계가 **정점 수 하나**에만 걸린다.

**메모리**: WARP 스냅샷은 23,412 바이트다.  v9 스냅샷(23,868)과 **공용체로
저장소를 나눠 쓴다** — 둘이 동시에 살 이유가 없고 BSS 23 KiB 는 커널에서
값싸지 않다.

## 2. 정점은 어디에 놓는가

**클라이언트가 쓰기 가능한 배치에서 DMA 하면 안 된다** — 검증 뒤 카드가 읽기
전에 바뀔 수 있다.  지금 인코더가 목록 영역으로 옮겨 쓰는 이유가 그것이고,
정점도 같아야 한다.

```
링 64 KiB = 배치 24 KiB | 목록 36,880 | 2차 4,080
                          ^^^^^^^^^^^^ 상태 목록들 + 정점 배열

16 런 × 460 =  7,360
720 정점 × 32 = 23,040
합            30,400 / 36,880     여유 6,480     (python)
```

## 3. 런마다 상태 목록

하네스의 `osmgaDmaBuildTriangleList` 가 이미 만든다(22 블록).  바뀌어야 하는
것은 **입력**이다:

| 목록이 쓰는 것 | 지금 | 생산 |
|---|---|---|
| `DSTORG`·`PITCH`·`ZORG` | 인자 | `state` |
| 클립 | `OSMGA_M3_CLIP_*` 상수 | 목적지 사각형 ∩ scissor |
| 텍스처 | `OSMGAM3Tex` | `state.tex*` |
| `DWGCTL`·`ALPHACTRL` | 인자 | `run[i]` |
| `WFLAG`·`FOGCOL`·`PLNWT`·`MACCESS`·`TDUALSTAGE` | 커널 상수 | 그대로 |

**텍스처 정책은 v9 인코더가 이미 갖고 있다**(`:13106` — clamp/repeat, pow2,
pitch==width).  하지만 **WARP 는 폭·높이를 다른 부호화로 원한다**
(`osmgaHW3DWarpTexDim`).  그러니 블록을 그대로 못 쓰고 **같은 정책에서 다른
부호화를 내는** 함수가 필요하다.

## 4. 제출 순서

D2-2c/d/e/f 가 실기로 확정한 것만 쓴다:

```
런마다:
  1  GENERAL:  PRIMADDRESS = list | 0x0,  PRIMEND = listEnd
               포인터 도달 + SOFTRAPEN + ENDPRDMASTS,  ICLEAR
  2  VERTEX :  PRIMADDRESS = vtxBase + first*32 | 0x3
               PRIMEND     = vtxBase + (first+count)*32
```

D2-2f 는 **같은** 컨텍스트가 두 정점 제출 사이에 산다는 것만 보였다.  런
경계는 **바뀐** 컨텍스트이므로 매 런이 새 GENERAL 목록을 낸다 — 참조보다
보수적이지만 실증된 순서다.

## 5. 완료·펜스·버퍼 재사용

```
정점 버퍼 재사용   PRIMADDRESS 가 지나가면 자유 (D2-2f, 펜스 불필요)
결과를 읽을 때     DWGSYNC (3-139)
텍스처 덮어쓰기·목적지 CPU 접근·present   DWGSYNC 필수 (M2 §10)
배치 끝            펜스 -> WIADDR2 = SUSPEND -> !wbusy
```

`wbusy` 는 완료 비트가 아니다(3-189).  suspend 뒤에만 의미가 있다.

## 6. 실패 정책 — 타임아웃은 거절이 아니다

```
검증 실패   제출 전이다.  아무것도 안 그리고 UNSUPPORTED, 훅이 사다리꼴로
            다시 만든다.  부작용 없음.
타임아웃    아래 층으로 재생하지 않는다.  엔진을 격리한다.
```

⚠ **하네스를 그대로 베끼면 안 된다**: `runWarpDepthQualificationTest` 는 실패
시 `stormBusy` 를 **잡은 채로 둔다**(시험의 안전 장치다).  생산 경로가 그러면
2D 블릿까지 영구히 소프트웨어로 떨어진다.

## 7. 층 간섭

T6 이 보였다 — 사다리꼴이 사이에 끼면 **상태 전체 재발행**이 필요하고, 그러면
WARP 는 정확히 돌아온다.  순서는 **펜스 → suspend → quiesce → 다른 층**.
커널이 **마지막 제출의 층**을 기억하고, 바뀌었으면 첫 런에서 재발행을 강제한다.

## 8. 마이크로코드

`osmgaWarpUcodeResident` 를 그대로 쓴다 — **언로드가 금지라 수명은 드라이버와
같다.**

## 10. 질문 2 는 내 하네스가 이미 답했다 (2026-08-29, codex 회신 전)

*"한 배치 안에서 GENERAL 과 VERTEX 제출을 번갈아 내는 것이 안전한가"* 를
물어 놓고, **그것을 이미 25 번 하고 있었다.**

`runWarpDepthQualificationTest` 의 호출 순서를 뽑아 보면:

```
G V G V G V G V G V V V G V G V G V G V G V G V G V
GENERAL 목록 13,  VERTEX 제출 15,  모드 전환 25 회 — 한 실행 안에서
```

그리고 **그 실행 전체가 실기에서 통과했다**(2026-08-29 01:39, T0~T6 전부).
`VVV` 구간은 T3 의 네 위상이 상태 목록 하나를 공유한 것이고, 그것도 D2-2f 가
이미 증명한 형태다.

→ **1 차 DMA 의 모드를 배치 중간에 바꾸는 것은 실증됐다.**  M6 §4 의 순서에
새로운 위험이 없다.

### 10.1 참조에는 선례가 없고, 없는 것이 맞다

DRM 을 확인했다.  참조는 **1 차 채널을 정점 모드로 두지 않는다** — 정점은
**2 차 채널**로 가고(`mga_state.c:679`, `MGA_SECADDRESS, (address |
MGA_DMA_VERTEX)`), 그 레지스터 쓰기 자체가 1 차 GENERAL 목록 안에서 일어난다.
1 차는 늘 GENERAL 이다(`mga_dma.c:216`, `:911`).

즉 **참조에 선례가 없는 것은 이 경로가 위험해서가 아니라 참조가 2 차 DMA 를
쓰기 때문**이다.  이 프로젝트는 2 차 DMA 의 네 번 NO-GO 를 우회가 아니라
제거하려고 1 차 VERTEX 모드로 갔고(D2-2c), 그래서 선례가 없는 것이 예상된
결과다.

**질문 2 는 철회한다.**  열세 번째다 — 이번에는 저장소의 문서가 아니라
**내가 방금 짠 하네스**가 답을 갖고 있었다.
