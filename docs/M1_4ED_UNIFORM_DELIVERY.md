# M1-4ED — 지워진 표면은 읽어서 배달하지 않는다

**날짜**: 2026-08-24
**상태**: 구현·측정 완료 (재부팅 불필요 — 라이브러리만)
**출발점**: `REMAINING_WORK` §3-28b — 한 프레임이 표면을 두 번 훑는다

---

## 무엇이 문제였나

이 백엔드는 색 버퍼를 비디오 메모리에 두고 그린 뒤, **렌더 괄호가 끝날 때마다**
표면 전체를 앱의 배열로 복사한다(미러). 미러는 uncached VRAM 을 **5.36 MB/s** 로
읽는다.

`glClear` 는 `Driver.Clear` 를 부른 **직후 자기 렌더 괄호를 연다**
(`buffers.c:280` → `:296`/`:313`). 그래서 clear + 삼각형 프레임은:

```
clear 괄호   → 미러 (표면 전체 훑기 1)
삼각형 괄호  → 미러 (표면 전체 훑기 2)
glFinish     → Driver.Finish 도 같은 함수지만 이미 깨끗해서 아무 일도 안 함
```

첫 번째 훑기 사이에 **앱의 배열을 읽은 사람은 없다.** 순수한 낭비다.

## 왜 그냥 건너뛸 수 없나

앱은 GL 호출 사이에 자기 배열을 그냥 읽을 수 있고, 이 백엔드는 그것을 볼 수 없다.
아는 지점은 `OSMesaMakeCurrent`·`glFinish`·`glFlush`·`glReadPixels`·문맥 파괴뿐.
미루면 그 사이에 낡은 것을 보게 된다.

## 무엇을 했나 — 배달은 하되, 읽지 않는다

**전면 clear 뒤 표면은 값 하나다.** 그 값을 앱 배열에 **쓰는** 것은 시스템 RAM
쓰기이고, 배달되는 바이트는 글자 그대로 같다.

```
                     미러(VRAM 읽기)   상수 채우기(시스템 RAM)
   128x96                9.170 ms            0.030 ms
   512x384             146.722 ms            0.585 ms
   1024x768            586.890 ms            2.316 ms
```

1344 MB/s 대 5.36 MB/s — **250배**.

### 기구: 다음 soil 이 가져가는 일회용 표시

`osmgaMesaSoil`(RenderStart)이 무조건 더럽힘 표시를 하는 것은 **바꿀 수 없다** —
OSMesa 가 설치하는 직접 기록자들이 스팬을 거치지 않고 표면에 쓰므로, 비어 보이는
괄호가 실제로는 비어 있지 않을 수 있다. 그러니 clear 가 미리 표시를 지워도 괄호가
다시 세운다.

그래서 **일회용 표시**를 쓴다:

1. `osmgaMesaClearOnEngine` 이 clear 를 가져갔고 **표면 전체**(`all` 참, 즉 시저
   없음)를 덮었으면 `hookPendingUniform` 을 세우고, 배달할 낱말과 문맥과 **그
   시점의 배치 수**를 기록한다.
2. `osmgaMesaSoil` 이 그것을 **가져가고 지운다.** 다른 어떤 괄호도 이미 쓰인
   표시를 본다.
3. `osmgaMesaMirror` 가 표시를 가진 괄호에서, **스팬 기록이 없고 배치 수가 그대로**
   이면 표면을 읽는 대신 낱말을 앱 배열에 쓴다.

`Driver.Clear` 는 이 Mesa 에서 `buffers.c:280` 한 곳에서만 불리고 `RENDER_START`
가 `:296` 에서 바로 뒤따른다(사이에는 ASSERT 와 DEBUG 전용 블록뿐). 전수 grep 으로
확인했다.

### 두 겹의 방어 — 조용히 프레임을 잃는 실패 하나를 막는다

표시가 **그린 괄호**로 새면 그린 것 위에 clear 색을 칠하고 아무 말도 하지 않는다.
그것만은 두 번 막는다:

- **스팬 기록 없음**: Mesa 가 표면에 그리면 이 파일이 볼 수 있다.
- **배치 수 그대로**: 엔진이 그리면 스팬을 하나도 안 쓰므로 **볼 수 없다.** 그래서
  clear 자신의 배치 이후 하나라도 더 나갔으면 평범한 미러로 돌아간다.

### 낱말은 어디서 오나 — 표면에서 **읽지 않는다**

처음 계획은 submit 이 돌아온 뒤 표면의 픽셀 하나를 읽는 것이었다. **그건 틀렸고
교차검토가 잡았다.** 이 저장소는 이미 기록해 두었다(`OpenStepMGAHW3D.h`,
`REMAINING_WORK` §3-18): 제출이 돌아온 뒤 클라이언트의 **첫 읽기는 낡은 것을 돌려줄
수 있고**, 특히 창의 **첫 64바이트 안**이 그렇다. 내가 읽으려던 곳은 창의 첫
낱말 — 바로 그 범위이고, 기록이 "아무것도 정하지 못하는 유일한 오프셋" 이라고
부르는 곳이다.

그래서 낱말은 **OSMesa 자신이 계산한 것**을 받는다. `clear_color`(`osmesa.c`)가
`PACK_RGBA` 로 만드는 `clearpixel` 이 그것이고, 그 값이 소프트웨어 clear 가 쓰는
바로 그 낱말이다. 표면을 읽지도, 픽셀 배치를 두 번째로 아는 곳을 만들지도 않는다.
표면이 잡힐 때 한 번 더 건네므로 `glClearColor` 를 한 번도 부르지 않는 문맥도 옳다
(기본값의 packed 낱말은 0 이고 OSMesa 문맥은 CALLOC 된다).

## 잰 것

### 전제부터 (`tcu`)

네 가지 clear 색 — 검정, 흰색, 채널이 잘리는 색, 알파가 1 미만인 색 — 각각에 대해
**196608 화소 전부가 서로 같고**, 소프트웨어 clear 가 쓰는 낱말과 **비트까지 같다**
(알파 포함). clear 는 대각선을 공유하는 삼각형 **둘**로 그려지므로 이음매가 생길 수
있었는데, 없다.

### 검증 (`tuf`) — 전부 통과

```
after glClear alone the array is one value        yes  (armed 1 filled 1)
and it is the colour software would write         yes  (0xff3f7fbf 양쪽 다)
a triangle drawn after a clear survives           yes  (1440 화소, 배치 1)
the clear armed once and delivered once           yes
a scissored clear does not arm the delivery       yes  (armed 0)
and leaves what is outside the box alone          yes
a padded array is filled only where the picture is yes (패딩 12288칸 전부 보존)
```

### 이득

```
                      전         후
clear 만 (512x384)   146.667    1.517 ms      (96배)
clear+삼각형          292.488  147.616 ms      (1.98배)

크기 스윕 (clear+삼각형, ns/화소)
  128x96             1520.35   807.08
  512x384            1485.07   748.91
  1024x768           1487.40   759.49
```

훑기 한 번의 예측값은 746.3 ns/화소다. 프레임은 이제 **정확히 한 번** 훑는다.

### 천장 (clear+그리기 프레임)

```
640x480    2.18 → 4.36 fps
800x600    1.40 → 2.79 fps
1024x768   0.85 → 1.70 fps
```

## 남은 것

남은 한 번의 훑기는 **그리기의 결과를 배달하는 것**이고, 지금 계약에서는 줄일 수
없다. 줄이려면 §3-32 가 말한 소유권 계약 변경이나, 그려진 사각형만 배달하는 더티
사각형이 필요하다 — 후자는 전면 clear 작업부하에서 값이 없다는 것이 이미 기록돼
있다(`M1_4EB`).

**세지 않은 것**: 한 프레임에 여러 번 플러시되는 장면은 괄호마다 배달하므로 더
훑을 수 있다. 아직 재지 않았다.
