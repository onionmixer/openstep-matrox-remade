# M15 — WARP 층은 빠른가 (2026-08-29, 코딩 전)

층이 존재하는 이유가 이것이다.  그림은 `M12` 가 검증했고 알려진 차이 셋은
크기가 재졌다.  **출하 여부를 정하는 남은 질문은 값을 하는가**이다.

## 1. 이미 참인 것

* `res.dwords` 는 **두 층이 비교 가능하다**.  v10 경로가 정점을 자기
  집계에 더한다(`:11215`, `encoded += nv * sizeof(OSMGAHW3DVertex)/4`).
  그러므로 양쪽 다 "커널이 인코딩해 보낸 dword" 를 뜻한다.
* `submitCount` 와 `submitDwords` 는 두 층 다 센다(`M12` Stage 0 이 고쳤다).
* 그리고 **`submitUs` 는 아니다.**  타이밍은 `osmgaMesaSubmitBatch`(v9 경로)
  안에 있고 WARP 플러시는 `OSMGAMesaProbeSubmit` 을 직접 부른다.  그래서
  **WARP 팔은 ioctl 시간을 0 으로 보고한다.**  비교 전에 반드시 고쳐야 한다
  — `M12` Stage 0 이 고친 계정 눈멂과 같은 부류이고, 그때 정확성 카운터만
  고치고 시간은 안 고쳤다.

## 2. 잴 것

같은 라이브러리, 새 프로세스, 두 팔, 반복.

```
장면 벽시계 시간
제출 수, dword, dword/제출
ioctl 안의 마이크로초, us/제출
유저랜드 시간 = 벽시계 - ioctl
```

마지막이 핵심이다.  두 층이 갈리는 곳이 대부분 거기다 — 사다리꼴은
유저랜드에서 평면을 풀고 변을 걷고, WARP 은 정점 셋을 싣고 만다.

## 3. 부하

```
mesh16     512 삼각형, 무텍스처·무깊이   저장소에서 가장 큰 반복 부하
텍스처 부하  ?                            사다리꼴의 일이 크게 달라진다
                                          (삼각형마다 tmr 기울기, 쪼개짐)
```

## 4. 미리 적는 예측 (틀릴 수 있게)

* WARP 이 삼각형당 dword 를 덜 보낸다: 정점 24 dword + 분할상환된 상태
  목록 대 사다리꼴의 그룹 다섯 x 5 dword x 사다리꼴 하나나 둘.
* WARP 의 유저랜드 시간이 더 짧다.
* **그러나** WARP 은 **런** 단위로 제출하고 런은 `dwgctl`·`alphactrl` 이
  바뀔 때마다 끊긴다.  사다리꼴은 사다리꼴 180 개까지 한 배치에 담는다.
  그러므로 제출 **횟수**는 WARP 이 불리할 수 있고, `3-46` 의 비용 모형은
  제출당 **85.4 us 고정**이라고 말한다 — 목록을 아무리 줄여도 안 줄어드는
  값이다.

## 5. 잘못 잴 수 있는 길

```
미러          mesh16 은 브래킷마다 표면을 미러한다.  3-46 이 512x384 에서
              146 ms 로 쟀다.  미러가 지배하면 두 팔이 미러를 잰다.
OSMesa 버퍼   실제 프레임이 아니다
마이크로코드  첫 제출이 WARP 마이크로코드를 놓는다 — 한 번뿐인 비용이
              프레임당 숫자에 들어가면 안 된다
계측 비용     gettimeofday 가 제출당 둘, 4.58 us.  두 팔에 똑같이 켜야 한다
```

## 7. 수정된 설계

### 7.1 끝점을 셋으로 나눈다 — 하나에서 다른 하나를 유도하지 않는다

```
enqueue 비용    present 모드(미러 억제).  완료에 대해 아무 주장도 안 한다
완료 비용       가벼운 동등한 펜스.  대량 되읽기 없음
전달된 프레임   미러를 켠 채로.  OSMesa 전달의 정직한 비용으로 따로 발표
```

### 7.2 판정 지표는 **계측 없는** 실행에서 온다

계측된 실행은 **기전을 설명**할 때만 쓴다(제출 수, 점유, 런 길이).

### 7.3 부하 행렬 — `mesh16` 은 첫 줄이지 판정이 아니다

```
1  균질 불투명        mesh16, 512 삼각형
2  텍스처            사다리꼴의 일이 크게 달라진다
3  깊이 + 오버드로   ** 깊이를 넉넉히 벌린다 ** (M13 의 시작값 차이 때문)
4  상태 교대          dwgctl/alphactrl 이 바뀌며 WARP 의 런을 끊는다
5  용량 경계          16 런 / 720 정점 / 180 사다리꼴 근처
```

각 측정마다 **양쪽 팔이 같은 일을 했음**을 기록한다: 소스 삼각형, `warp`,
`traps`, 거절, 소프트웨어 재생.

### 7.4 단위

판정은 **프레임**이다.  삼각형당은 오해를 부른다 — 상태 변경과 제출당 고정
비용은 삼각형의 것이 아니다.  제출당은 진단용이다.

### 7.5 아직 답이 없는 질문 — 정책

층은 오늘 환경변수로 고른다.  드라이버가 **무엇을, 언제** 고를 수 있는가?
브래킷마다?  프레임마다?  `RenderFinish` 전에 알 수 있는가?  **이 질문에
답하기 전에는 출하 결론이 없다.**

## 8. 먼저 할 것 (Phase 1)

1. WARP 플러시에 제출 타이밍을 붙인다 — v9 와 대칭으로.  **계측이 켜졌을
   때만** 도는 것도 v9 와 같게.
2. 행렬 1 행(`mesh16`)을 present 모드에서, 계측 없이, 두 팔 · 반복 · 순서
   섞어서.
3. 계측을 켜고 같은 것을 한 번 더 — 제출 수와 점유를 설명하기 위해서만.

출하 결론은 §7.5 가 열려 있는 동안 나오지 않는다.

## 9. Phase 1 결과 (2026-08-29) — **WARP 이 3.65% 빠르고, 내 예측 둘은 틀렸다**

`mesh16`(512 삼각형), present 모드(미러 억제), **계측 없이**, 프레임 25 회에
워밍업 4 회 버리고, 팔마다 독립 실행 넷을 **AB BA AB BA** 로.

```
팔          실행  제출  dword/프레임  중앙값 us   p75    최대
사다리꼴     1     225      13120        4259     4264   8424
사다리꼴     2     225      13120        4235     4241   7678
사다리꼴     3     225      13120        4247     4256   7681
사다리꼴     4     225      13120        4249     4256   7769
WARP         1     225      13248        4094     4098   4230
WARP         2     225      13248        4090     4094   4251
WARP         3     225      13248        4095     4107   7527
WARP         4     225      13248        4099     4106   7508
```

**양쪽 팔이 같은 일을 했다** — 여덟 실행 전부 `drawn 12800, software 0,
declined 0`, 그리고 층이 완전히 갈린다(`warp 12800/traps 0` 대
`warp 0/traps 12800`).  "빠른 팔이 그냥 덜 그렸다" 가 아니다.

```
합산(팔마다 100 프레임)
  사다리꼴 중앙값 4249 us     WARP 중앙값 4094 us
  WARP 이 -3.65%,  프레임당 -155 us,  삼각형당 -0.303 us
```

실행 간 흩어짐은 사다리꼴 24 us, WARP 9 us — 차이 155 us 보다 훨씬 작다.

### 9.1 예측 둘이 틀렸다

* **"WARP 이 삼각형당 dword 를 덜 보낸다"** — 틀렸다.  WARP 13248,
  사다리꼴 13120.  WARP 이 프레임당 **1% 더 보낸다**(정점 512 x 24 = 12288
  dword 가 그 자체로 거의 전부다).
* **"WARP 이 더 자주 제출해서 불리할 수 있다"** — 이 부하에서는 틀렸다.
  **둘 다 프레임당 정확히 9 회**.  이 메시는 상태가 균질해서 런이 끊길
  일이 없다.  상태가 교대하는 부하(행렬 4 행)가 이 예측이 살아 있는
  유일한 자리다.

그러므로 이득은 **목록에 있지 않다**.  유저랜드다 — 평면을 풀지 않고 변을
걷지 않는 것.  이것은 이 측정이 *가리키는* 곳이지 이 측정이 *증명한* 것은
아니다.

### 9.2 이 수가 말하지 **않는** 것

```
완료         아무 말도 안 한다.  enqueue 끝점 하나뿐이다
전달         미러를 껐다.  OSMesa 전달 비용은 따로 재야 한다
부하         행렬의 1 행뿐 — 텍스처·깊이·상태 교대·용량 경계가 남았다
정책         §7.5 가 열려 있다.  드라이버가 무엇을 언제 고르는가
```

**출하 결론은 여기서 나오지 않는다.**
