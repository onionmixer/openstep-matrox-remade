# M1-4c8 — 이중선형 필터를 연다 (2026-08-22)

## 1. 왜 막혀 있었나

관문은 `GL_NEAREST` 만 받았다.  커널은 `TEXF_BILIN` 을 이미 지원하고 탐침
§7 이 그 배치가 **받아들여진다**는 것까지 확인했지만, **그림을 아무도 보지
않았다.**  그래서 열 수 없었다.

## 2. 엔진의 이중선형을 쟀다

자기 이름을 담은 텍스처로는 섞임을 볼 수 없다 — 텍셀 10 과 11 사이의 어떤
가중치도 10 아니면 11 로 반올림된다.  이웃 텍셀을 **0 과 255** 로 칠하면
돌아오는 바이트가 곧 **가중치**다(1/255 분해능).

한 텍셀을 64 걸음으로 걸었다(§26):

```
   nearest   0 (행 전체가 한 텍셀 안이므로)
   bilinear  127 119 111 ... 15 7 0 7 15 ... 111 119
```

**텍셀 경계에서 127, 텍셀 중심에서 0.**  곧 텍셀 **중심**을 기준으로 섞는다.
python 신탁 `u' = u·N − 0.5, i = floor(u'), f = u' − i, (1−f)T[i] + f T[i+1]`
(가중치 절단)에 대고 **32 개 값이 전부 일치**한다.

## 3. 네 모서리가 모두, 곱 가중치로 들어간다

§26 은 u 만 걷는다 — v 를 못 보고 모서리 가중치도 못 본다.  세 채널에 세
모서리를 담고(`a(1−b)`, `(1−a)b`, `ab`) 대각선을 걸었다(§28):

```
    col  R a(1-b)  G (1-a)b   B ab
      0      0      0      0
     16     63     63     63
     32      0      0    255
```

**9 개 지점 전부 예측과 일치**한다.  두 텍셀만 섞거나 축별 가중치를 따로
절단했다면 어긋났을 값들이다.

## 4. 가장자리는 `GL_CLAMP_TO_EDGE` 다

`GL_NEAREST` 에서는 `GL_CLAMP` 와 `GL_CLAMP_TO_EDGE` 가 같은 텍셀을 준다.
선형에서는 갈린다 — Mesa 는 `GL_CLAMP` 에서 `i0 = −1` 이나 `i1 = width` 를
그대로 두고 `sample_2d_linear` 가 그 자리에 **테두리 색**을 넣는다
(`texture.c`, `useBorderColor`).

바깥 두 텍셀을 흰색으로 칠하고 양 끝의 바깥쪽 반 텍셀을 걸었다(§27):

```
   low  edge  255 255 255 255 255 255 255 255
   high edge  255 255 255 255 255 255 255 255
```

검은 테두리가 섞였다면 127 쯤이었을 자리다.  텍스처 **완전히 바깥**도
쟀다(§29): 축마다 독립으로 가장 가까운 가장자리 텍셀을 주고, 두 축 모두
바깥이면 모서리 텍셀을 준다.  **음수 좌표는 커널이 거절**하므로
소프트웨어가 그린다 — 틀린 그림이 아니라 안 받는 것이다.

## 5. 관문

```c
if (MinFilter != MagFilter)              거절;   /* 엔진엔 스위치가 하나뿐 */
if (MagFilter == GL_NEAREST)             CLAMP 또는 CLAMP_TO_EDGE;
else if (MagFilter == GL_LINEAR)         CLAMP_TO_EDGE 만;  BILIN 켬;
else                                     거절;   /* 밉맵 필터 넷 */
```

`MinFilter == MagFilter` 가 필요한 이유: GL 은 **조각마다** 둘 중 하나를
고르고, 한 삼각형 안에서 확대와 축소가 섞일 수 있으며 축마다 다를 수도 있다.
엔진에는 그 선택이 없다.  둘을 같게 요구하면 그 선택이 **의미를 잃는다**.
Mesa 는 `MinFilter == GL_LINEAR`(밉맵 아님)일 때 축소도 같은
`sample_2d_linear` 를 쓴다(`texture.c:1108`).

## 6. 끝단 결과

같은 장면을 가속·비가속으로 그려 화소를 대조했다:

| | nearest | linear |
|---|---|---|
| 색이 다른 화소 | 24 / 25964 (0.09%) | 257 / 25964 (0.99%) |
| 채널 최대 차이 | 16 (텍셀 위상) | **1** |
| 커버리지 차이 | 10 (변 규칙) | 10 |

선형의 257 은 **전부 한 단계**다 — Mesa 는 네 가중치를 반올림하고
(`(GLint)(w*SCALE + 0.5F)`) 엔진은 절단하므로, 엔진이 계통적으로 한 단계
낮다.  다른 텍셀을 고른 것이 아니다(그랬다면 차이가 컸을 것이다).

## 7. 그러다 알파를 찾았다 — 별개의 결함

비교에서 알파 마스크를 걷었더니 **모든 화소에서** 다르다: 소프트웨어 255,
하드웨어 0.  `GL_REPLACE` + `GL_RGB` 는 알파가 **조각의 것**이어야 하고,
인코더는 그것을 `ALPHASTART` 에 넣는다.

레지스터 참조가 이유를 말한다: `TDUALSTAGE0` 을 0 으로 쓰는데 0 은
`ALPHA_SEL_ARG1` — **현재 텍스처의 알파**다.  `ALPHA_SEL_ARG2`(0x40000000) 과
`ALPHA_ARG2_DIFFUSE`(0) 이 보간된 알파다.

읽은 것을 **측정으로 확정**했다(§30): 텍스처 알파 0xAB, 삼각형 알파 0x55 →
화소 `ab000404`.  **텍스처의 것이 이긴다.**

이중선형이 만든 문제가 아니다 — `GL_NEAREST` 에서도 똑같이 틀렸고, 알파
마스크를 씌운 비교가 그걸 여태 가리고 있었다.  고치는 것은 커널 한 비트이고
재부팅이 필요하다.
