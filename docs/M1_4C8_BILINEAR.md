# M1-4c8 — 이중선형 필터를 연다 (2026-08-22)

## 1. 왜 막혀 있었나

관문은 `GL_NEAREST` 만 받았다.  커널은 `TEXF_BILIN` 을 이미 지원하고 탐침
§7 이 그 배치가 **받아들여진다**는 것까지 확인했지만, **그림을 아무도 보지
않았다.**  그래서 열 수 없었다.

## 2. 엔진의 이중선형을 쟀다

자기 이름을 담은 텍스처로는 섞임을 볼 수 없다 — 텍셀 10 과 11 사이의 어떤
가중치도 10 아니면 11 로 반올림된다.  이웃 텍셀을 **0 과 255** 로 칠하면
돌아오는 바이트가 곧 **가중치**다(1/255 분해능).

한 텍셀을 64 걸음으로 걸었다(§26):

```
   nearest   0 (행 전체가 한 텍셀 안이므로)
   bilinear  127 119 111 ... 15 7 0 7 15 ... 111 119
```

**텍셀 경계에서 127, 텍셀 중심에서 0.**  곧 텍셀 **중심**을 기준으로 섞는다.
python 신탁 `u' = u·N − 0.5, i = floor(u'), f = u' − i, (1−f)T[i] + f T[i+1]`
(가중치 절단)에 대고 **32 개 값이 전부 일치**한다.

## 3. 네 모서리가 모두, 곱 가중치로 들어간다

§26 은 u 만 걷는다 — v 를 못 보고 모서리 가중치도 못 본다.  세 채널에 세
모서리를 담고(`a(1−b)`, `(1−a)b`, `ab`) 대각선을 걸었다(§28):

```
    col  R a(1-b)  G (1-a)b   B ab
      0      0      0      0
     16     63     63     63
     32      0      0    255
```

**9 개 지점 전부 예측과 일치**한다.  두 텍셀만 섞거나 축별 가중치를 따로
절단했다면 어긋났을 값들이다.

## 4. 가장자리는 `GL_CLAMP_TO_EDGE` 다

`GL_NEAREST` 에서는 `GL_CLAMP` 와 `GL_CLAMP_TO_EDGE` 가 같은 텍셀을 준다.
선형에서는 갈린다 — Mesa 는 `GL_CLAMP` 에서 `i0 = −1` 이나 `i1 = width` 를
그대로 두고 `sample_2d_linear` 가 그 자리에 **테두리 색**을 넣는다
(`texture.c`, `useBorderColor`).

바깥 두 텍셀을 흰색으로 칠하고 양 끝의 바깥쪽 반 텍셀을 걸었다(§27):

```
   low  edge  255 255 255 255 255 255 255 255
   high edge  255 255 255 255 255 255 255 255
```

검은 테두리가 섞였다면 127 쯤이었을 자리다.  텍스처 **완전히 바깥**도
쟀다(§29): 축마다 독립으로 가장 가까운 가장자리 텍셀을 주고, 두 축 모두
바깥이면 모서리 텍셀을 준다.  **음수 좌표는 커널이 거절**하므로
소프트웨어가 그린다 — 틀린 그림이 아니라 안 받는 것이다.

## 5. 관문

```c
if (MinFilter != MagFilter)              거절;   /* 엔진엔 스위치가 하나뿐 */
if (MagFilter == GL_NEAREST)             CLAMP 또는 CLAMP_TO_EDGE;
else if (MagFilter == GL_LINEAR)         CLAMP_TO_EDGE 만;  BILIN 켬;
else                                     거절;   /* 밉맵 필터 넷 */
```

`MinFilter == MagFilter` 가 필요한 이유: GL 은 **조각마다** 둘 중 하나를
고르고, 한 삼각형 안에서 확대와 축소가 섞일 수 있으며 축마다 다를 수도 있다.
엔진에는 그 선택이 없다.  둘을 같게 요구하면 그 선택이 **의미를 잃는다**.
Mesa 는 `MinFilter == GL_LINEAR`(밉맵 아님)일 때 축소도 같은
`sample_2d_linear` 를 쓴다(`texture.c:1108`).

## 6. 끝단 결과

같은 장면을 가속·비가속으로 그려 화소를 대조했다:

| | nearest | linear |
|---|---|---|
| 색이 다른 화소 | 24 / 25964 (0.09%) | 257 / 25964 (0.99%) |
| 채널 최대 차이 | 16 (텍셀 위상) | **1** |
| 커버리지 차이 | 10 (변 규칙) | 10 |

선형의 257 은 **전부 한 단계**다 — Mesa 는 네 가중치를 반올림하고
(`(GLint)(w*SCALE + 0.5F)`) 엔진은 절단하므로, 엔진이 계통적으로 한 단계
낮다.  다른 텍셀을 고른 것이 아니다(그랬다면 차이가 컸을 것이다).

## 7. 그러다 알파를 찾았다 — 별개의 결함

비교에서 알파 마스크를 걷었더니 **모든 화소에서** 다르다: 소프트웨어 255,
하드웨어 0.  `GL_REPLACE` + `GL_RGB` 는 알파가 **조각의 것**이어야 하고,
인코더는 그것을 `ALPHASTART` 에 넣는다.

레지스터 참조가 이유를 말한다: `TDUALSTAGE0` 을 0 으로 쓰는데 0 은
`ALPHA_SEL_ARG1` — **현재 텍스처의 알파**다.  `ALPHA_SEL_ARG2`(0x40000000) 과
`ALPHA_ARG2_DIFFUSE`(0) 이 보간된 알파다.

읽은 것을 **측정으로 확정**했다(§30): 텍스처 알파 0xAB, 삼각형 알파 0x55 →
화소 `ab000404`.  **텍스처의 것이 이긴다.**

이중선형이 만든 문제가 아니다 — `GL_NEAREST` 에서도 똑같이 틀렸고, 알파
마스크를 씌운 비교가 그걸 여태 가리고 있었다.  고치는 것은 커널 한 비트이고
재부팅이 필요하다.

## 8. 고침 — `TDUALSTAGE0` 의 알파 선택자 (재부팅 필요)

```c
MGA_TDUALSTAGE0, MGA_TDS_ALPHA_SEL_ARG2,   /* 0x40000000 */
```

다른 필드는 전부 0 이므로 ARG2 는 `DIFFUSE` — 삼각형이 `ALPHASTART` 로 싣는
보간된 알파다.  색 선택자는 다른 필드라 `ARG1`(현재 텍스처) 그대로이고,
`TDUALSTAGE` 는 텍스처 블록에서만 쓰이므로 비텍스처 경로는 닿지 않는다.

### 재부팅 뒤 확인

| 확인 | 기대 |
|---|---|
| §30 (텍스처 0xAB, 삼각형 0x55) | 화소의 상위 바이트가 **55** |
| §31 (기울어진 알파 0x20 + 4c) | `20 28 30 38 40 48 50 58` |
| 끝단 대조의 알파 불일치 | 25964 → **0** |
| 색 결과 (nearest 24, linear 257) | **변하지 않아야** 한다 |

§31 은 교차검토가 더하라고 한 것이고 옳았다: §30 은 한 점의 상수 알파만
보므로 **증분이 무시되거나 어긋나 있어도** 통과한다.  지금 커널에서 §31 은
`ab ab ab ...` 로 정확히 붉게 나온다 — 고쳐졌는지를 가릴 수 있는 계기다.

## 9. 재부팅 뒤 — 절반만 고쳐졌고, 그 절반이 규칙을 말해줬다 (2026-08-22)

### 9-1 들어간 것은 맞다

| 확인 | 결과 |
|---|---|
| §30 (텍스처 0xAB, 삼각형 0x55) | **55** — 조각의 알파가 이긴다 |
| 색 (nearest / linear) | **24 / 257**, 최대차 16 / 1 — 그대로 |

### 9-2 그런데 알파는 절반만

끝단 대조에서 알파 불일치가 25964 → **12982**, 정확히 절반이다.  그리고
갈라지는 기준은 **열의 홀짝**이었다:

```
   y=100 행:  40:ff 41:00 42:ff 43:00 44:ff 45:00 ...
```

### 9-3 내 시험이 그걸 못 봤다

§31 은 `c += 2` 로 **짝수 열만** 찍고 있었다.  하필 맞는 쪽만 본 것이다.
모든 열을 찍으니:

```
   alpha across the row:  20 ab 28 ab 30 ab 38 ab 40 ab 48 ab 50 ab 58 ab
   wanted                 20 24 28 2c 30 34 38 3c 40 44 48 4c 50 54 58 5c
```

**홀수 열은 여전히 텍스처의 0xAB 를 가져간다.**

### 9-4 읽기: `TDUALSTAGE0/1` 은 직렬 두 단계가 아니라 **레인 두 개**다

엔진이 짝수 열과 홀수 열을 서로 다른 반쪽으로 그리고, 두 레지스터가 그
레인 하나씩의 텍스처 환경 워드라면 관측이 그대로 설명된다.  그리고 이것은
좌표 쪽에서 이미 본 **열 홀짝 미세 구조**(§22·§25)와 같은 원인이 된다 —
따로 놀던 두 이상 현상이 하나가 된다.

X.Org 의 mga 드라이버가 뒷받침한다: 텍스처가 하나일 때 두 번째 워드를 0 으로
두지 않고 **첫 번째를 복사**한다(`mga_exa.c`, `if (!pMask) ds1 = ds0`).

### 9-5 고침, 그리고 그것을 증명할 대조군

```c
TDUALSTAGE0 = MGA_TDS_ALPHA_SEL_ARG2;
TDUALSTAGE1 = MGA_TDS_ALPHA_SEL_ARG2;
```

"이제 된다"는 위 읽기를 **증명하지 않는다** — 두 번째 워드에 무엇을 써도
달라졌을 수 있다.  증명하는 것은 **두 워드를 바꿔 넣었을 때 홀짝이 뒤집히는
것**이고, 다른 어떤 설명도 그걸 예측하지 않는다.  그래서 진단 플래그 둘을
같이 넣어 한 번의 재부팅으로 대조군까지 얻는다(§32).  플래그는 커널 자신의
두 상수 중 어느 레인이 어느 것을 받을지만 고르며, 클라이언트가 레지스터에
값을 넣지 못한다.

```
   neither    모든 열이 보간 알파
   TDS1ZERO   짝수만        (지금 상태의 재현)
   TDSSWAP    홀수만        <- 이 줄이 판별자다
```

### 9-6 교차검토 판정

| codex 주장 | 검증 | 결과 |
|---|---|---|
| 열 홀짝은 직렬 2단계로는 설명 안 되고 2-레인이 맞다; 좌표 쪽 홀짝과 같은 원인 | 내 관측과 일치, 그리고 두 이상 현상을 하나로 묶는다 | ✅채택 |
| 복사가 맞다 — 두 워드가 같으면 어느 레인이 어느 것인지가 무의미해진다 | 맞다 | ✅채택 |
| 그래도 레인 대응은 **뒤집기 시험**으로 확인하라 | §32 로 넣었다 | ✅**채택 — 이것이 증명을 만든다** |
| `PREVSTAGE` 식 pass-through 를 지어내지 말고 복사해라 | 근거 타당(색 ARG2 가 diffuse 로 갈 위험) | ✅채택 |
| `TDUALSTAGE1` 이 0 이 아니면 두 번째 텍스처가 켜질 위험 — 그러면 **전면** 파손이지 홀수 열만은 아니다 | 산술이 아니라 예측이지만 판별 가능하다; §32 가 RGB 도 함께 본다 | ⚖️부분채택 |

## 10. 대조군이 통과했고, 알파는 끝났다 (2026-08-22)

### 10-1 뒤집힘이 나왔다

```
   both words = ALPHA_SEL_ARG2   20 24 28 2c 30 34 38 3c ...   even ok, odd ok
   stage 1 left at zero          20 ab 28 ab 30 ab 38 ab ...   even ok, odd no
   the two exchanged             ab 24 ab 2c ab 34 ab 3c ...   even no, odd ok
```

세 번째 줄이 두 번째의 거울이다.  다른 설명은 이 뒤집힘을 예측하지 않으므로
**`TDUALSTAGE0` 은 짝수 열, `TDUALSTAGE1` 은 홀수 열** — 직렬 두 단계가 아니라
**레인 하나씩의 텍스처 환경 워드**다.

### 10-2 끝단

| | nearest | linear |
|---|---|---|
| 색 | 24 / 25964 (최대차 16) | 257 / 25964 (최대차 1) |
| **알파** | **0** | **0** |
| 커버리지 | 소프트웨어만 10 | 소프트웨어만 10 |

알파는 끝났고 색은 정확히 있던 자리에 있다.

### 10-3 레인은 **화면**에 고정이다

알파는 이제 레인 표지자다(두 번째 워드를 0 으로 두면 lane 1 이 텍스처의
0xAB 를 남긴다).  왼쪽 변을 옮겨 가며 찍으면:

```
   left edge 0, screen x 0..11:  .1.1.1.1.1.1
   left edge 1, screen x 1..12:  1.1.1.1.1.1.
   left edge 2, screen x 2..13:  .1.1.1.1.1.1
   left edge 3, screen x 3..14:  1.1.1.1.1.1.
```

**lane 1 은 언제나 홀수 화면 x** 다.  프리미티브가 어디서 시작하든 같다.

### 10-4 그런데 좌표의 홀짝은 **그 홀짝이 아니다**

레인이 밝혀졌으니 좌표 미세 구조도 같은 원인이길 기대했다.  같은 시작·같은
증분으로 왼쪽 변만 옮겨 재니:

```
   left edge 0  00000000000000000001111111111111   turns at column 19, screen x 19
   left edge 1  00000000000000000001111111111111   turns at column 19, screen x 20
```

전환이 **같은 화면 x** 가 아니라 **같은 상대 열**에 남는다.  좌표 쪽은
**프리미티브에 고정**이고 레인은 **화면에 고정**이다 — **다른 두 홀짝**이다.
가설은 반증됐다.

### 10-5 그래서 좌표 잔차는 여기서 멈춘다

| | |
|---|---|
| 크기 | 좌표 5 단위 이내 (텍셀 16384 대비) |
| 끝단 영향 | nearest 24 / 25964 (0.09%), 전부 위상 경계의 한 텍셀 |
| | linear 257 / 25964 (0.99%), 전부 한 단계 |
| 성격 | **프리미티브 상대 열의 홀짝에 민감한 좌표 양자화 잔차** |
| 상태 | **유계이고 규칙은 미상**. 레인과는 무관함이 측정으로 밝혀졌다 |

추측으로 보정하면 오차를 없애는 게 아니라 **옮길** 가능성이 크다 — §11 에서
띠별 정확 보정이 정확히 그랬다.  "기전을 안다"와 "유계임을 안다"는 다른
주장이고, 여기서 참인 것은 뒤쪽이다.

### 10-6 교차검토 판정

| codex 주장 | 검증 | 결과 |
