# M1-4 4a0.3 — 색·깊이·텍스처를 함께 잡는 VRAM 배치

2026-08-21.  `M1_4_TEXTURE_PLAN.md` §4b(2) 가 텍스처를 막는다고 지목한 항목.
텍스처 작업(4b·4c·4d) 중 **이것이 먼저**다.

## 1. 지금 무엇이 문제인가

세 영역이 한 창을 쓰는데, **주인이 없다.**

* 색은 창 맨 앞에서 시작한다 (`Buffer.c:414` 부근).
* 깊이는 색 바로 뒤에 페이지 정렬해서 붙는다 (`Buffer.c:144-176`).
* 텍스처는 아직 없다.
* 커널은 셋의 범위가 겹치는 것을 **일부러 허용한다**:
  `OpenStepMGAReplacementDisplay.m:3520-3525` 가 `colourStart/End`,
  `depthStart/End`, `texStart/End` 를 **모두 창 전체**로 놓는다.
  검사는 "창 안이냐"만 본다.

그리고 깊이는 **게을리** 잡힌다 — Mesa 가 깊이 버퍼를 달라고 할 때 비로소.
그래서 텍스처를 색 바로 뒤에 두면, 나중에 깊이가 그 자리를 그대로 가져간다.
커널은 막지 않는다.  **막지 않는 것이 커널의 결정이므로, 유저랜드가 정해야 한다.**

## 2. 창이 얼마나 되는지 (실측, 추측 아님)

`test/openstep-mga-caps-client.c` 를 실기에서 돌려 받은 값:

```
vram    +4194304, 3145728 bytes        (창 = VRAM +4 MiB, 3 MiB)
```

끝은 7 MiB 다.  `OpenStepMGAReplacementDisplay.m:206` 이 그렇게 잘라 놓았다:

```c
/* Only VRAM proven real by the working 1600x1200x32 scanout (7.32 MiB). */
#define OSMGA_S1_VRAM_PROVEN    (7UL * 1024UL * 1024UL)
```

보드에는 더 있을 수 있으나(§1-2 의 미착수 항목) **실증되지 않았으므로 안 쓴다.**
지금 필요한 것도 아니다 — 아래 표를 보면 시험 해상도에서는 남는다.

## 3. 배치 규칙 (제안)

창 앞에서부터, **순서를 고정한다**:

```
[ 색 ][ 정렬 ][ 깊이 예약 ][ 정렬 ][ 텍스처 아레나 ............ ] 창 끝
```

핵심은 **깊이를 예약한다**는 것이다.  실제로 깊이를 요청했는지와 **무관하게**
자리를 비워 둔다.  그래야 텍스처가 먼저 올라가 있어도 나중의 깊이 요청이
그 위에 앉지 않는다.  대안 — "필요할 때 앞에서부터 채우기" — 는 두 순서를
모두 다뤄야 하고, 그 두 순서 중 하나는 반드시 나중에 잊힌다.

예약 크기는 색 표면에서 바로 나온다: `height * stride * 2`.  16 비트가 아닌
깊이는 이 백엔드가 애초에 거절하므로(`Buffer.c:105`) 다른 크기가 올 수 없다.

계산한 값(페이지 8192).  **`stride == width` 일 때의 값**이다 —
예약은 `height * stride * 2` 이고 stride 는 호출자의 행 길이라 width 보다
클 수 있다(`Buffer.c:383`):

| 표면 | 색 | 깊이 예약 뒤 | 텍스처 아레나 |
|---|---|---|---|
| 320×240 | 307200 | 466944 | **2678784 (2.55 MiB)** |
| 640×480 | 1228800 | 1843200 | 1302528 (1.24 MiB) |
| 800×600 | 1920000 | 2891776 | 253952 (0.24 MiB) |
| 1024×768 | 3145728 | 4718592 | **0 — 창을 넘는다** |

1024×768 에서는 색 하나가 창 전체다.  **깊이도 지금 이미 못 잡는다**
(`tail >= avail` 에서 걸린다).  그러니 이건 새 제약이 아니라 이미 있던 제약이
드러난 것이고, 그 경우 텍스처 가속은 **거절해야 한다 — 조용히 겹치면 안 된다.**

## 4. 예약이 낭비인 경우

깊이가 올 수 없는 표면(`bufStride != bufWidth` 면 `Buffer.c:115` 가 거절한다)
에서도 예약한다.  낭비는 320×240 에서 153600 바이트, 아레나의 5.7% 다.
**단순한 규칙 하나가 두 경로를 가진 규칙보다 낫다**는 판단이고, 값을 적어 둔다.

## 5. 무엇을 만드는가 (이 단계의 범위)

만드는 것은 **아레나의 경계**이지 그 안의 할당 정책이 아니다.
할당·해제·상주는 4c 의 일이다.

```c
/* 텍스처가 살 수 있는 곳.  색과 깊이 어느 쪽과도 겹치지 않는다. */
int OSMGAMesaBufferTextureArena(unsigned long *origin, unsigned long *bytes);
```

* 색 표면이 없으면 0 을 돌려준다.
* 아레나가 비면(1024×768) 0 을 돌려준다.  **0 이 곧 "텍스처 가속 없음"이다.**
* 창 끝을 넘지 않는다.

## 6. 어떻게 증명하는가

호스트에서 돌릴 수 있는 산술 시험 + 실기 시험 하나.

1. **겹치지 않음** — 여러 표면 크기에 대해 색·깊이 예약·아레나 세 구간이
   서로소이고 전부 창 안임을 확인한다.  경계값(창에 딱 맞는 크기, 한 바이트
   모자란 크기, 페이지 경계에 걸치는 크기)을 포함한다.
2. **순서 무관** — 텍스처 아레나를 먼저 물어보고 **그 다음에** 깊이를
   요청해도 깊이 원점이 달라지지 않는다.  이것이 이 단계의 존재 이유이므로
   이 시험이 없으면 아무것도 증명되지 않는다.
3. **실기** — 아레나 시작에 알려진 값을 쓰고, 깊이를 잡고, 삼각형을 그린
   다음 그 값이 그대로인지 읽는다.  **쓰기는 아레나 안에서만** 한다.

## 7. 안 하는 것

* 창을 넓히지 않는다.  `OSMGA_S1_VRAM_PROVEN` 을 올리려면 그 VRAM 이 진짜
  있음을 먼저 증명해야 하고, 그건 커널 변경이라 재부팅이 필요하다.
  지금 필요하지도 않다.
* 창은 **모드가 바뀌어도 다시 계산되지 않는다** — 초기화 때 한 번이다(§8).
  이 사실에 기대는 것이 아니라, 기대도 되는지 확인한 것이다.
* 아레나 안의 할당기를 만들지 않는다 (4c).

## 8. codex 교차검토 판정 (2026-08-21)

### 내가 틀린 것 먼저

* **"창 시작은 모드에 따라 움직인다"(§7) 는 사실이 아니다.**  창은 초기화에서
  한 번 계산되어 `:2190` 에 저장되고, `:2250` 에서 지워질 뿐이다 —
  `osmgaMmapWindowStart` 에 대입하는 곳은 저 둘뿐이고(전수 grep),
  `enterLinearMode` 는 창을 다시 계산하지 않는다.  움직이는 게 위험이 아니라
  **모드가 바뀌어도 안 움직이는 것**이 위험이다.  동적 모드 변경이 가능해지면
  그때는 낡은 창 값이 드라이버 버그가 된다.
* **"백엔드가 16비트 아닌 깊이를 거절한다"도 문자 그대로는 거짓이다.**
  `Buffer.c:97` 이 `depthMapped != 0` 이면 **검사 전에** 그 포인터를 돌려준다.
  검사(`:105` 의 `bytesPerValue != 2`)는 그 뒤다.  다른 크기를 새로 잡지는
  않으므로 예약 크기 계산은 무사하지만, 서술은 틀렸고 캐시 경로는 결함이다.

### 판정에 따른 최종 설계

1. **아레나 API 는 ctx 를 받는다** — `bufBound == ctx` 일 때만 답한다.
   `bufMapped != 0` 만으로는 부족하다(크기 다른 재바인딩이 거절돼도 매핑은 산다).
2. **예약은 패딩하지 않는다.**  `depthEnd = depthStart + height*stride*2` 이고,
   **텍스처 시작만** 페이지로 올린다.  기존 깊이 할당이 길이를 정확히 두는 것과
   같은 이유다(`:148`, `:155`).
3. §3 의 표는 **`stride == width` 일 때의 값**이라고 못 박는다.
4. 다음 두 결함은 아레나가 상태를 갖기 전에 고친다 — 별도 변경으로:
   * 깊이 캐시가 `(ctx, width, height, bytesPerValue)` 를 확인하고 돌려주게.
   * 포크한 자식이 물려받은 매핑을 그대로 받지 못하게 (빠른 경로에서 닫는다).
5. **알려진 한계로 적는다**: 프로세스 간 소유권 없음; 래스터 시험이 켜져 있으면
   창 시작(=색 표면 자리)에 쓴다.

### 시험을 실패 가능하게 만들기

* **시험 2** — "아레나 물어보고 깊이 잡아도 원점이 그대로"는 겹쳐도 통과한다.
  대신: 하드웨어 깊이가 **실제로 잡혔는지** 요구하고, 원점의 **정확한 기댓값**을
  주장하고, **두 반열린 구간이 서로소임**을 주장하고, 깊이를 먼저 잡는 대조군도
  돌린다.
* **변이 시험** — `textureStart = depthStart` 로 일부러 틀리게 만든 빌드에서
  시험이 **반드시 실패해야** 한다.  이걸 통과하면 시험이 아무것도 안 보는 것이다.
* **시험 3** — 아레나 **전체**에 무늬를 깔고, 깊이 표면 **전체**를 덮는 그리기를
  하고, 가속 제출이 실제로 성공했는지 확인한 뒤에 무늬를 다시 읽는다.

## 9. 결과 (2026-08-21 실기 측정)

`test/openstep-mga-mesa-arena-test.c`:

```
[320x240 row 320 (arena first)] colour origin 4194304
   arena origin 4661248 bytes 2678784   depth origin 4505600
  depth origin equals the independent one      ok
  arena and depth are disjoint                 ok
  arena starts after the colour surface        ok

   pattern kept 262144/262144 words

[320x240 row 320 (depth first)]   ... 같은 값, 같은 통과
[320x240 row 352 (arena first)] stride 352 -> arena 4710400, 깊이 없음

[1024x768 row 1024]             arena none

```

* **§3 의 표가 실측과 일치한다** — 320×240 에서 2678784, 640×480 에서 1302528.
  계산해 놓고 재서 같은 값을 받았다.
* **두 순서가 같은 답을 준다.**  아레나를 먼저 묻든 깊이를 먼저 잡든 원점이
  같다 — 예약의 목적이 그것이었다.
* **1024×768 은 아레나가 없다**고 답한다.  겹치는 작은 아레나를 주지 않는다.
* 패딩된 행(352)에서는 예약이 stride 로 계산되어 아레나가 뒤로 밀리고,
  깊이는 (지금도) 거절된다.  보수적이고 맞다.
* **자기검사가 통과한다** — 같은 서로소 판정을 깊이 원점과 같은 값에 겨누면
  거절한다.  판정이 실패할 수 있음을 증명하지 않으면 통과는 의미가 없다.

## 10. 이 단계에서 함께 고친 결함 둘

교차검토가 찾아냈고, 아레나가 상태를 갖기 전에 고쳐야 했다.

1. **깊이 캐시가 검사보다 먼저 반환했다** (`Buffer.c:97`).  32비트 깊이를
   요구한 호출자도, 다른 크기나 다른 컨텍스트도 16비트 버퍼를 받아 갔다.
   이제 `(ctx, width, height, bytesPerValue)` 를 확인하고 돌려준다.
2. **포크한 자식이 물려받은 매핑을 그대로 받았다.**  `OSMGAMesaProbeRun` 이
   pid 변화를 보고 전부 놓아주는데, 색·깊이 양쪽의 빠른 경로가 그 호출보다
   **먼저** 반환했다.  probe 호출을 두 함수 모두에서 빠른 경로 앞으로 올렸다.
