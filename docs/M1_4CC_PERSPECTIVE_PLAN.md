# M1-4cc — 원근 보정 계획 (2026-08-23, 착수 전)

## 1. 지금 상태

커널은 `TEXCTL` 에 **`NOPERSP` 를 켜고** H 계열(`TMR4`, `TMR5`, `TMR8`)을
**자기가** 쥔다 — `TMR8 = 1<<16`, 곧 `w = 1`.  Mesa 관문은 삼각형 세 꼭짓점의
`Win[][3]`(= 1/w)이 **정확히 같지 않으면 거절**한다(`hookTexPersp`).  그래서
직교·2D 장면은 전부 가속되고 원근 장면은 소프트웨어로 간다.

## 2. 무엇이 어려운가 — 좌표 경계

`NOPERSP` 를 끄면 엔진이 표본하는 좌표가 **`s/q`** 가 된다.  커널의 안전은
"클라이언트가 무엇을 보내든 주소가 텍스처 안에 머문다"에 서 있는데, 나눗셈이
들어오면 **`q → 0` 에서 좌표가 발산**한다.  그래서 H 계열을 클라이언트에게
그냥 넘길 수 없다 — 지금 커널이 쥐고 있는 이유가 그것이다.

## 3. 경계는 세울 수 있다 (증명 스케치)

`s`, `t`, `q` 는 전부 **평면**(화면 좌표의 선형함수)이다.  커널이 인코딩하는
단위는 사다리꼴이고 그 영역은 **볼록**하다.

`q > 0` 인 볼록 영역에서 `s/q` 는 **준선형(quasi-linear)** 이므로 최대·최소가
**꼭짓점에서** 잡힌다.  따라서:

1. 클라이언트가 `q` 평면(시작과 두 기울기)을 보낸다.
2. 커널이 사다리꼴 **네 모서리**에서 `q` 를 계산한다.
3. 어느 하나라도 `q <= q_min` 이면 **거절**한다 (`q_min` 은 여유를 둔 양수).
4. 아니면 네 모서리에서 `s/q`, `t/q` 를 계산하고 **기존 도달 검사**를 그
   값들에 적용한다.

이러면 나눗셈이 있어도 경계가 유한하고, 검사는 지금과 같은 모양이다.

## 4. 재기 전에는 열지 않는다 (지금까지의 방식)

| 재야 할 것 | 왜 |
|---|---|
| `NOPERSP` 를 끄면 엔진이 실제로 `s/q` 를 쓰는가 | 읽은 것이지 잰 것이 아니다 |
| `TMR8`(q 시작)과 `TMR4/5`(q 기울기)의 고정소수점 형식 | 색·깊이·알파에서 이미 세 번 틀렸던 자리다 |
| 나눗셈의 정밀도 — 몇 비트에서 끊기는가 | 이미 좌표에 **유효비트 16개** 사다리가 있다; 나눗셈이 그 위에 무엇을 더하는지 |
| `q` 가 작을 때의 거동 | `q_min` 을 **측정으로** 정해야 한다, 고르지 말고 |

## 5. 순서

1. 커널에 **측정용** 경로: 클라이언트가 H 계열을 보낼 수 있게 하되 §3 의 경계를
   그대로 적용한다.  경계가 먼저다 — 재기 위해 안전을 미루지 않는다.
2. 탐침으로 §4 를 잰다.
3. Mesa 쪽: 빌더가 `s/w`, `t/w`, `1/w` 평면을 풀고 관문의 아핀 제한을 푼다.
4. 끝단 대조: 원근 장면을 소프트웨어와 화소 단위로 맞춰 본다.

1 이 커널 변경이므로 재부팅이 필요하다.

## 6. 교차검토가 계획을 두 군데 고쳤다

### 6-1 증명이 더 강해진다 (그리고 내 서술은 느슨했다)

"준선형이라 극값이 꼭짓점"보다 깔끔한 형태가 있다.  볼록결합
`P = Σ λᵢ Cᵢ` 에 대해 `q` 가 아핀이면

```
   q(P) = Σ λᵢ q(Cᵢ) ≥ min q(Cᵢ) > 0
```

이므로 네 모서리가 양수면 **내부에서 0 으로 내려갈 수 없다**.  그리고

```
   s(P)/q(P) = Σ  [ λᵢ q(Cᵢ) / Σ λⱼ q(Cⱼ) ] · s(Cᵢ)/q(Cᵢ)
```

로 `s/q` 가 모서리 값들의 **볼록결합**이다 — 사이에 있음이 바로 나온다.

### 6-2 `q_min` 의 역할을 내가 잘못 적었다

"`q → 0` 이면 좌표가 발산한다"고 썼는데, **모서리에서 `s/q` 를 함께 묶으면
그렇지 않다**: `q = ε`, `s = uε` 이면 `s/q = u` 로 `ε` 과 무관하다.  실수
산술에서는 `q_min` 이 필요 없다.

`q_min` 이 필요한 이유는 **하드웨어 나눗셈기의 유한 산술** — 정규화, 중간
폭, 포화, 반올림 — 때문이고, 따라서 **그림의 품질이 아니라 고정소수점 계약**
에서 유도해야 한다.  포맷과 나눗셈기 의미를 모르는 채로 그림이 상해 보이는
자리를 고르는 것은 안전 근거가 아니다.

### 6-3 그리고 순서가 바뀐다 — 먼저 잴 것은 **가져오기 범위**다

§3 의 증명은 **내가 평가한 영역**에만 적용된다.  엔진의 변 걷기가 한 화소라도
넘어가면 증명이 무너진다.  그리고 다른 장면에서 잰 **10 화소의 커버리지
차이는 그 경계가 아니다** — 그것은 Mesa 규칙과의 차이이지 "엔진이 내 모형을
얼마나 넘는가"가 아니고, 버려지는 조각·필터 이웃·선반입은 보이는 화소 밖을
읽을 수 있다.

그래서 **원근보다 먼저** 잴 것:

1. 엔진이 실제로 텍셀을 **가져오는** 범위 (그린 화소의 범위가 아니라)
2. 고정소수점 계약 — 레지스터 형식, 설정 반올림, 화소마다의 누산, 가장 작은
   양수 분모에서의 나눗셈기 거동, 몫의 반올림·포화, 선형 필터의 이웃 가져오기

이 둘이 정해지기 전에는 안전 증명이 **가능한지조차** 알 수 없다.

### 6-4 대안에 대한 판정

교차검토는 **커널이 검증된 꼭짓점에서 H 계열을 직접 만드는 쪽**을 고른다 —
나눗셈 경계를 없애지는 않지만, 클라이언트가 임의의 분모 평면을 위조하지
못하게 하고 커널이 분모의 범위를 **검증된 기하에서** 세우게 한다.  아핀
세분(subdivision)은 오늘의 안전 증명을 지키지만 **원근 보정이 아니라 근사**
이므로 "원근 보정"의 구현으로는 고르지 않는다 — 별도의, 그렇게 이름 붙인
대체 경로라면 몰라도.

| codex 주장 | 처리 |
|---|---|
| 볼록결합 형태가 더 강하고 깔끔하다 | ✅채택 — §6-1 로 대체 |
| `q_min` 은 실수 증명에는 필요 없다; 나눗셈기 때문이다 | ✅**채택 — 내가 틀렸다** |
| 증명은 평가한 영역에만 적용된다; 한 화소 넘침이 무너뜨린다 | ✅채택 |
| 10 화소 커버리지 차이는 안전 여유가 아니다 | ✅**채택 — 그것은 Mesa 와의 차이지 엔진의 범위가 아니다** |
| 가져오기 범위와 고정소수점 계약을 **먼저** 재라 | ✅채택 — §6-3 이 새 순서다 |
| 커널이 H 를 만들고, 세분은 원근 보정이 아니다 | ✅채택 |

## 7. 무엇이 주소를 붙잡는가 — 재고 나서 (2026-08-23)

헤더의 근거는 "좌표가 **잰 범위** 안에 머물 것"이다.  그것은 **아무도 안 본
곳에 가지 말라**는 규칙이지, 주소를 텍스처 안에 붙잡는 장치가 아니다.  붙잡는
것은 **주소 지정 방식** — 클램프면 포화하고, repeat 이면 마스크된다.

허용 범위의 **끝**에서 확인했다:

```
   clamped    1 spans -> v 63 u 63   4 spans -> 63 63   8 spans -> 63 63
   repeating  1 spans -> v 63 u 63   4 spans -> 63 63   8 spans -> 63 63
```

원근에서 나눗셈이 좌표를 크게 만들 수 있으므로 이 구분이 중요하다.  다만
**잰 것은 8 스팬까지**이고, 몫은 그보다 커질 수 있다 — 그 너머는 여전히
미지다.

## 8. 그래서 다음 커널 단계의 모양

교차검토의 권고("클라이언트가 분모 평면을 위조하지 못하게 하라")와 §3 의
경계를 합치면:

* 클라이언트는 `q` 를 **커널이 정한 고정소수점의 평면**으로 보낸다
  (`TMR8 = 1<<16` 이 `q = 1` 이므로 그 축척을 그대로 쓴다).
* 커널이 사다리꼴 네 모서리에서 `q` 를 계산하고, 양수 여유를 확인하고,
  모서리에서 `s/q`·`t/q` 를 계산해 **기존 도달 검사**를 적용한다
  (§6-1 의 볼록결합이 그 넷으로 전체를 덮는 근거다).
* 커널이 `TMR4/5/8` 을 **직접 써 넣고** `NOPERSP` 를 끈다.
* 걷기 넘침 여유는 §6-3 대로 **모서리를 넓혀** 잡는다.

커널이 형식을 **정하므로** "형식을 모르면 경계를 못 세운다"는 순환이 풀린다.
형식이 하드웨어와 맞는지는 알려진 원근 도형을 그려 **그림으로** 확인한다.

이것이 다음 커널 변경이고 재부팅이 필요하다.  이번 회차 끝에 서둘러 쓰지
않고 여기까지를 기록으로 남긴다.

## 9. 형식은 참고 구현이 확정해 준다 (2026-08-23)

`xf86-video-mga` 의 `mga_exa.c` 는 아홉 개 TMR 을 **3×3 사영 변환**으로 적어
두었고 원소가 **전부 16.16** 이다.  그리고 `setTMIncrementsRegs` 는 **분자 두
행만** 텍스처 단위의 고정소수점으로 옮긴다 — `20 − log2(폭) − 16` 만큼 자리
이동 — 반면 **분모 행은 그대로** 쓴다.  변환 없는 경우의 분모 행은
`0, 0, 1<<16`.

이 변환이 **우리 측정과 교차검증된다**: 64 폭이면 자리이동이 −2 이므로
16.16 의 한 텍셀(`1<<16`)이 레지스터 단위 `1<<14 = 16384` 가 되는데, 그게 이
드라이버가 실기에서 잰 텍셀 크기다.

덤으로 하나 더 맞춰졌다: 참고 구현의 배치가 `TMR0=X_incx, TMR1=Y_incx,
TMR2=X_incy, TMR3=Y_incy` 인데, **검증기 코드가 이미 그렇게 쓰고 있다**
(`u` 는 `tmr[0]·dx + tmr[2]·dy`, `v` 는 `tmr[1]·dx + tmr[3]·dy`).

## 10. 나눗셈 없는 경계 (구현함)

좌표 = `s · 65536 / q` 이고 기존 규칙은 `0 ≤ 좌표 ≤ TEX_COORD_MAX` 인데
그 상한이 65536 의 배수이므로, 규칙은 **나눗셈 없이**

```
   0 ≤ s   그리고   s ≤ (TEX_COORD_MAX >> 16) · q
```

가 된다.  `q = 65536` 에서 `128 × 65536 = 8388608 = TEX_COORD_MAX` 로
**지금의 아핀 경계와 항 대 항으로 같다** — 그래서 아핀 경로를 이 식으로 다시
쓴다고 동작이 바뀌지 않는다.  32비트를 넘지 않게 `Q_MAX = 2^23` 으로 두면
`128·q ≤ 2^30` 이다.

`Q_MIN`·`Q_MAX` 는 **안전 논거가 아니다**(§7).  나눗셈기의 입력을 아무도 안
본 범위 밖으로 내보내지 않으려는, 좌표 경계와 **같은 종류**의 규칙이고,
검증기 자신의 산술을 long 안에 두는 역할도 한다.

분모의 **행 색인**은 v 처럼 배치를 가로질러 누적하는지 u 처럼 다시 시작하는지
**재지 않았다**.  그래서 두 경우를 **모두** 검사한다 — 어느 쪽이든 안전하고,
비교 하나 값이다.

## 11. 재부팅 뒤

§42 가 한 번의 그리기로 답한다: `s` 를 텍셀 8 에 고정하고 `q` 를 열마다
1/64 씩 올리면, 나눗셈이 있으면 텍셀이 `8 7 6 5 5 4 4 4` 로 물러난다.
평평한 8 이면 평면이 무시된 것이고, 그 밖이면 형식이 다른 것이다.

그다음이 교차검토가 고른 그림 시험 — 심하게 단축된 사각형을 **대각선을 반대로
잡아** 두 번 그려, 사영 나눗셈이면 두 그림이 같고 아핀이면 대각선에서 꺾인다.

## 12. 엔진은 나눈다 (2026-08-23)

```
   측정   8 7 6 5 5 4 4 4
   python 8 7 6 5 5 4 4 4      s * 65536 / q, 텍셀 16384
```

`NOPERSP` 를 끄면 엔진이 **정말 나누고**, 분모 행이 **16.16** 인 것도, 검증기가
받아들이는 것도 확인됐다.  탐침 전체와 GL 시험 전체가 **0 실패** — 아핀 경계를
`s ≤ (limit>>16)·q` 로 다시 쓴 것이 `q = 65536` 에서 동작을 바꾸지 않는다는
확인이기도 하다.

## 13. 내가 곧바로 만든 실수 하나

다음 측정(분모의 행 색인이 누적인가 재시작인가)이 **좌표 오류로 거절**됐다.
원인은 엔진이 아니라 **내가 둔 기울기 상한**이었다: `Q_MAX/4096`, 곧 화소당
1/32 로 두었는데 이는 **거꾸로 한 산술**이다 — 기울기를 넘침이 아니라 좌표
범위로 묶은 것이고, 행당 1/16 이라는 **평범한** 분모를 거절한다.

기울기는 `q` 를 **평가하는 것이 long 을 벗어나지 않게** 하는 만큼만 묶으면
된다.  그리고 교차검토가 이어서 짚은 대로, 최대 span 을 여기 적어 넣는 것도
취약하다 — **배치가 선언한 표면 크기**에 대고 묶는 것으로 바꿨고, 검사 자체가
넘치지 않게 나눗셈으로 썼다:

```
   |dq/dx| <= ((1<<30) - Q_MAX) / (2 * dstWidth)
   |dq/dy| <= ((1<<30) - Q_MAX) / (2 * dstHeight)
```

실제로 기울기를 제한하는 것은 이것이 아니라 **모서리 검사**다 — 그리는 화소
위에서 `q` 가 `[Q_MIN, Q_MAX]` 안에 있어야 한다.
