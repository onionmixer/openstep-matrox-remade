# M1-4cc — 원근 보정 계획 (2026-08-23, 착수 전)

## 1. 지금 상태

커널은 `TEXCTL` 에 **`NOPERSP` 를 켜고** H 계열(`TMR4`, `TMR5`, `TMR8`)을
**자기가** 쥔다 — `TMR8 = 1<<16`, 곧 `w = 1`.  Mesa 관문은 삼각형 세 꼭짓점의
`Win[][3]`(= 1/w)이 **정확히 같지 않으면 거절**한다(`hookTexPersp`).  그래서
직교·2D 장면은 전부 가속되고 원근 장면은 소프트웨어로 간다.

## 2. 무엇이 어려운가 — 좌표 경계

`NOPERSP` 를 끄면 엔진이 표본하는 좌표가 **`s/q`** 가 된다.  커널의 안전은
"클라이언트가 무엇을 보내든 주소가 텍스처 안에 머문다"에 서 있는데, 나눗셈이
들어오면 **`q → 0` 에서 좌표가 발산**한다.  그래서 H 계열을 클라이언트에게
그냥 넘길 수 없다 — 지금 커널이 쥐고 있는 이유가 그것이다.

## 3. 경계는 세울 수 있다 (증명 스케치)

`s`, `t`, `q` 는 전부 **평면**(화면 좌표의 선형함수)이다.  커널이 인코딩하는
단위는 사다리꼴이고 그 영역은 **볼록**하다.

`q > 0` 인 볼록 영역에서 `s/q` 는 **준선형(quasi-linear)** 이므로 최대·최소가
**꼭짓점에서** 잡힌다.  따라서:

1. 클라이언트가 `q` 평면(시작과 두 기울기)을 보낸다.
2. 커널이 사다리꼴 **네 모서리**에서 `q` 를 계산한다.
3. 어느 하나라도 `q <= q_min` 이면 **거절**한다 (`q_min` 은 여유를 둔 양수).
4. 아니면 네 모서리에서 `s/q`, `t/q` 를 계산하고 **기존 도달 검사**를 그
   값들에 적용한다.

이러면 나눗셈이 있어도 경계가 유한하고, 검사는 지금과 같은 모양이다.

## 4. 재기 전에는 열지 않는다 (지금까지의 방식)

| 재야 할 것 | 왜 |
|---|---|
| `NOPERSP` 를 끄면 엔진이 실제로 `s/q` 를 쓰는가 | 읽은 것이지 잰 것이 아니다 |
| `TMR8`(q 시작)과 `TMR4/5`(q 기울기)의 고정소수점 형식 | 색·깊이·알파에서 이미 세 번 틀렸던 자리다 |
| 나눗셈의 정밀도 — 몇 비트에서 끊기는가 | 이미 좌표에 **유효비트 16개** 사다리가 있다; 나눗셈이 그 위에 무엇을 더하는지 |
| `q` 가 작을 때의 거동 | `q_min` 을 **측정으로** 정해야 한다, 고르지 말고 |

## 5. 순서

1. 커널에 **측정용** 경로: 클라이언트가 H 계열을 보낼 수 있게 하되 §3 의 경계를
   그대로 적용한다.  경계가 먼저다 — 재기 위해 안전을 미루지 않는다.
2. 탐침으로 §4 를 잰다.
3. Mesa 쪽: 빌더가 `s/w`, `t/w`, `1/w` 평면을 풀고 관문의 아핀 제한을 푼다.
4. 끝단 대조: 원근 장면을 소프트웨어와 화소 단위로 맞춰 본다.

1 이 커널 변경이므로 재부팅이 필요하다.

## 6. 교차검토가 계획을 두 군데 고쳤다

### 6-1 증명이 더 강해진다 (그리고 내 서술은 느슨했다)

"준선형이라 극값이 꼭짓점"보다 깔끔한 형태가 있다.  볼록결합
`P = Σ λᵢ Cᵢ` 에 대해 `q` 가 아핀이면

```
   q(P) = Σ λᵢ q(Cᵢ) ≥ min q(Cᵢ) > 0
```

이므로 네 모서리가 양수면 **내부에서 0 으로 내려갈 수 없다**.  그리고

```
   s(P)/q(P) = Σ  [ λᵢ q(Cᵢ) / Σ λⱼ q(Cⱼ) ] · s(Cᵢ)/q(Cᵢ)
```

로 `s/q` 가 모서리 값들의 **볼록결합**이다 — 사이에 있음이 바로 나온다.

### 6-2 `q_min` 의 역할을 내가 잘못 적었다

"`q → 0` 이면 좌표가 발산한다"고 썼는데, **모서리에서 `s/q` 를 함께 묶으면
그렇지 않다**: `q = ε`, `s = uε` 이면 `s/q = u` 로 `ε` 과 무관하다.  실수
산술에서는 `q_min` 이 필요 없다.

`q_min` 이 필요한 이유는 **하드웨어 나눗셈기의 유한 산술** — 정규화, 중간
폭, 포화, 반올림 — 때문이고, 따라서 **그림의 품질이 아니라 고정소수점 계약**
에서 유도해야 한다.  포맷과 나눗셈기 의미를 모르는 채로 그림이 상해 보이는
자리를 고르는 것은 안전 근거가 아니다.

### 6-3 그리고 순서가 바뀐다 — 먼저 잴 것은 **가져오기 범위**다

§3 의 증명은 **내가 평가한 영역**에만 적용된다.  엔진의 변 걷기가 한 화소라도
넘어가면 증명이 무너진다.  그리고 다른 장면에서 잰 **10 화소의 커버리지
차이는 그 경계가 아니다** — 그것은 Mesa 규칙과의 차이이지 "엔진이 내 모형을
얼마나 넘는가"가 아니고, 버려지는 조각·필터 이웃·선반입은 보이는 화소 밖을
읽을 수 있다.

그래서 **원근보다 먼저** 잴 것:

1. 엔진이 실제로 텍셀을 **가져오는** 범위 (그린 화소의 범위가 아니라)
2. 고정소수점 계약 — 레지스터 형식, 설정 반올림, 화소마다의 누산, 가장 작은
   양수 분모에서의 나눗셈기 거동, 몫의 반올림·포화, 선형 필터의 이웃 가져오기

이 둘이 정해지기 전에는 안전 증명이 **가능한지조차** 알 수 없다.

### 6-4 대안에 대한 판정

교차검토는 **커널이 검증된 꼭짓점에서 H 계열을 직접 만드는 쪽**을 고른다 —
나눗셈 경계를 없애지는 않지만, 클라이언트가 임의의 분모 평면을 위조하지
못하게 하고 커널이 분모의 범위를 **검증된 기하에서** 세우게 한다.  아핀
세분(subdivision)은 오늘의 안전 증명을 지키지만 **원근 보정이 아니라 근사**
이므로 "원근 보정"의 구현으로는 고르지 않는다 — 별도의, 그렇게 이름 붙인
대체 경로라면 몰라도.
