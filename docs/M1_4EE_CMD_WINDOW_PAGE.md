# M1-4EE — 클라이언트가 커널의 커맨드 리스트를 매핑하고 있었다

**날짜**: 2026-08-24
**상태**: 고침·빌드·설치 (재부팅 대기)
**출발점**: 매 부팅 찍히던 `M1-0: FAIL` 을 왜 아무도 안 보는지 물어본 것

---

## 시작: 항상 실패하는 자가진단

부팅마다 이 세 줄이 찍히고 있었다. 오늘만 다섯 번, 글자까지 같다.

```
M1-0: cmd last (4000e000) -> -1, wanted accept
M1-0: vram 400000..700000, cmd base 40000000 bytes 65536 phys 20000; 14 cases, 1 wrong
M1-0: FAIL -- see the cases above; do not map anything until this is clean
```

드라이버가 스스로 "깨끗해질 때까지 아무것도 매핑하지 말라" 고 적어 놓고, 그
아래에서 계속 매핑하고 있었다.

**그 FAIL 자체는 버그가 아니었다.** 자가진단의 `cmd last` 기대값이
`osmgaMmapCmdBytes`(=할당 전체 65536)에서 나오는데, 핸들러는 의도적으로 **배치만**
허용한다. 배치/링 분리가 들어올 때 기대값이 따라오지 않았고, 그 뒤로 계속 낡은
기대에 대해 실패해 왔다. **항상 실패하는 시험은 아무도 읽지 않는 시험이다.**

## 그 뒤에 있던 것

64 KiB `IOMallocLow` 블록 하나를 둘로 나눠 쓴다 — 앞은 클라이언트가 쓰는 배치,
뒤는 **커널이 만드는 DMA 커맨드 리스트**. 핸들러의 주석이 왜 나눴는지 말한다:

> 클라이언트가 리스트를 매핑할 수 있으면, 검증이 끝난 뒤 엔진이 읽기 전에 목록을
> 덮어쓸 수 있다 — 검사받지 않은 명령이 엔진에 닿고, validate-then-encode 분리
> 전체가 무의미해진다.

그 약속을 지키는 검사는 `rel >= OSMGA_HW3D_BATCH_BYTES` 하나다. 그런데

- `PAGE_SIZE` 는 이 기계에서 **8192**,
- `OSMGA_HW3D_BATCH_BYTES` 는 **28672 = 3.5 페이지**,
- 커널은 받아들인 오프셋마다 **페이지 통째로** 매핑한다.

검사는 **페이지의 시작**에 대해 묻는데 노출되는 것은 **페이지 전체**다. 페이지 정렬
`rel` 중 28672 미만인 것은 0, 0x2000, 0x4000, **0x6000** 이고, 마지막 것이 덮는
범위는 `[0x6000, 0x8000)` — 리스트는 `0x7000` 에서 시작한다.

**즉 리스트의 첫 4096바이트가 매핑된다.** 그리고 이건 가상의 공격자 얘기가 아니다:
클라이언트는 창 전체(`OSMGA_CMD_WINDOW_LEN = BATCH_BYTES`)를 매핑하므로 **가속을
쓰는 모든 프로세스가 이미 그 페이지를 읽고 쓸 수 있다.**

## 증명 — 읽기만으로

논증이 아니라 기계에 물었다(`tcw`, 신규). 리스트가 있어야 할 자리에서 8 dword 를
읽고, 평범한 경로로 배치를 하나 제출하고, 다시 읽었다. **쓰지 않았다** — 거기에
쓰는 것이 위험한 행위이고, 요점은 그것이 불가능해야 한다는 것이지 해 보면 어떻게
되는지가 아니다.

```
   dword   before      after
       0   151503ae    151503ae
       1   00400000    00400000
       2   004c0000    00500000   <-- changed
       3   00000000    00000000
       5   1a191800    1a191800
       6   000c4434    000c4074   <-- changed
```

8 중 6이 0이 아니고, 배치를 내자 2가 바뀌었다. 클라이언트가 **살아 있는 리스트를
보고 있다.**

세 번째 근거: 저장소의 `S4A_VRAM_MMAP_PLAN.md` 가 `_smmap` 을 역분석해 놓았고,
검증 루프가 `off += page_size` 로 돌며 `vm_object_special` 이 **페이지마다 한 번씩**
핸들러를 부른다고 적혀 있다. 실측·문서·교차검토가 같은 답을 낸다.

## 왜 고치기가 간단하지 않았나 — 두 번 틀렸다

**첫 계획: 리스트를 줄여 배치를 32 KiB(4페이지)로.** 죽었다. 인코더의 최악값을
헤더의 선언값이 아니라 **코드에서 직접 세니** `(5 + 9T + 3) × 5` dword 이고
T=200 이면 **9040 dword = 36160 바이트**다. 32 KiB 리스트는 8192 dword 뿐이다.
같이 세어 본 교차검토도 같은 숫자를 냈다.

덤으로 나온 것: 헤더의 `OSMGA_HW3D_ENC_TRI_BLK` 가 **8인데 실제는 9**다(텍스처
프리미티브가 블록 하나를 더 낸다). 선언된 상한이 **과소평가**였다 — 상한이 틀려도
되는 방향이 아니다. 오늘 안 터진 건 리스트가 어쩌다 충분히 컸기 때문이다.

**둘째 계획: 할당을 69632 로 키운다.** 이것도 죽었다. **`dma_buf_alloc` 이
0x10000 초과를 거부한다** — 이 저장소가 IDA 로 확인해 이미 적어 둔 사실이고
(`.m:211-215`, `S5_HW3D_DMA_FEASIBILITY.md:67`), 나는 그걸 확인하지 않고 계획을
세웠다. 교차검토가 짚었다.

**두 할당으로 나누는 것**도 값이 비싸다: page_size 초과 요청은 64 KiB 대형 풀
블록을 하나씩 먹으므로 **conventional memory(640 KiB 미만, ISA DMA 와 공유) 에서
128 KiB** 를 가져가게 된다.

## 들어간 것

한 할당(64 KiB) 안에서 배치가 **페이지의 정수 배**가 되도록 양쪽을 맞바꿨다.
`sizeof(OSMGAHW3DBatch) = 108 + 132·T`, 리스트 최악값 `(8 + 9T)·20` 로 놓고
파이썬으로 풀면 한 할당에 들어가는 최대 T 는 **185**이고, 여유를 두어 **180** 을
골랐다.

```
OSMGA_HW3D_MAX_TRI      200   -> 180
OSMGA_HW3D_BATCH_BYTES  28672 -> 24576   (정확히 세 페이지)
OSMGA_HW3D_RING_OFFSET  = BATCH_BYTES     (이제 페이지 배수)
리스트                   36864 -> 40960 바이트 (10240 dword)
OSMGA_HW3D_ENC_TRI_BLK  8     -> 9
OSMGA_HW3D_VERSION      8     -> 9
```

검산: 배치 구조체 23868 ≤ 24576(708 남음), 인코더 최악 32560 ≤ 40960(8400 남음),
선언 상한 32640 ≤ 40960.

**T 를 줄이는 값은 Mesa 경로에서 0이다.** 훅은 삼각형 하나당 사다리꼴 1~4개를
`built[4]` 로 담아 배치 하나를 낸다 — 200 이든 180 이든 근처에도 안 간다. 처음에
"180마다 flush 한다" 고 적었는데 **그런 누산기는 없다**; 교차검토가 짚었고 소스로
확인했다(`OpenStepMGAMesaHook.c:357`, `:1630`).

그 밖에:

- 핸들러는 이제 **`RING_OFFSET` 에 대해** 묻고, 페이지 전체가 그 아래 있는지를
  언더플로 없이 따로 검사한다. 오늘은 같은 숫자지만 지키는 대상은 링이다.
- **init 에서 검사한다**: `RING_OFFSET` 이 `PAGE_SIZE` 의 배수이고 `BATCH_BYTES`
  이상이며 할당보다 작지 않으면 **창을 아예 등록하지 않는다.** `PAGE_SIZE` 는
  런타임 상수라 공유 헤더의 컴파일 시 검사로는 못 잡는다.
- **할당을 0으로 채운다.** `IOMallocLow` 는 아레나에 있던 것을 그대로 주고,
  클라이언트는 자기 배치보다 넓게 매핑하므로 그 차이는 아무도 안 본 커널 메모리
  였다(24576 − 23868 = 708 바이트, 고치기 전에는 32768 − 26508 = 6260).
- `osmgaMmapCmdBytes` 가 **매핑 가능한 크기**를 담는다. 자가진단의 `cmd last` 가
  저절로 옳아진다 — 변수가 드디어 시험이 가정하던 뜻이 되었기 때문이다.

## 이번엔 잡았을 시험

빠져 있던 것은 케이스 하나가 아니라 **성질**이었다. 자가진단에 블록의 **모든
페이지**를 도는 검사를 넣었다:

> 어떤 페이지든, 받아들여지는 것과 `rel + PAGE_SIZE <= RING_OFFSET` 이 같아야
> 한다.

목록은 누가 그때 떠올린 것만큼만 좋다. 이 성질은 오프셋 하나에 대한 것이 아니라
**페이지의 끝**에 대한 것이고, 그렇게 물으면 28 KiB 분리는 첫 부팅에 걸렸다.
`tcw` 는 유저랜드 쪽 회귀로 남는다 — 고친 뒤에는 읽을 것이 없다고 말하고 끝난다.

## 아직 남은 것 (고치지 않음)

교차검토가 짚은 **소유권** 문제는 별개이고 더 크다: 매핑된 배치는 **전역 하나**이고
`open`/`mmap` 경로에 클라이언트별 상태가 없다. 저장소 자신의 `S4A_VRAM_MMAP_PLAN`
(:294)이 이 고정 공유 매핑은 **단일 클라이언트 smoke test 용**이며 Mesa 가 쓰기
전에 클라이언트별 핸들이 필요하다고 적어 두었다. 이 문서는 그것을 고치지 않는다.
