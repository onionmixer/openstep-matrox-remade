# M20 — (B) 를 설계하기 전에 잰다 (2026-08-29, 코딩 전)

`M19` 는 두 후보를 다 보류했다.  (A) 는 기본값이 될 수 없고, (B) 는
**영역 소유권 설계**다.  그런데 그 설계를 하기 전에 물어야 할 것이 있다:

> **(B) 는 이 부하에서 얼마나 벌 수 있나?**  그 답이 작으면 설계 자체를
> 하지 않는다.

`M18 §9` 가 이미 그 규율을 한 번 썼다 — `sub` 최적화를 재 보니 평범한
기하에서 이득이 0 이어서 짓지 않았다.  같은 순서를 다시 밟는다.

## 1. 남은 미측정 항목 — codex 가 짚은 것

> 129 가 **실제 바이트 복사 수**인지 미러 훅 호출 수인지 계측하라;
> 겹치는 사각형이 있으면 "화소 x 복사" 가 진짜 예산이다

`Buffer.c:517` 에 이미 게이트가 있다:

```c
if (bufMapped == 0 || bufApp == 0 || !bufDirty)
    return;
```

그러므로 `hookMirrors` (호출)와 실제 복사는 **다를 수 있다**.
`M19 §2` 의 산술(228.2 대 예측 229.3)은 129 가 전부 복사했음을 **시사**하나,
시사는 측정이 아니다.

## 2. 그리고 내가 놓친 것 — `glClear` 가 전체를 더럽힌다

브래킷마다 미러가 돈다.  그런데 가속된 `glClear` 는 **표면 전체**를 쓴다.
프레임마다 지우는 응용에서는 **지우기 브래킷의 더러운 영역이 표면 전체**이고
(B) 가 거기서는 아무것도 못 번다.

`M19 §6` 의 "상한 4.6 배" 는 **teapot 이 덮는 화소 비율(21.6%)** 로 셈한
것인데, 그것은 **틀린 셈**이다.  (B) 가 복사하는 것은 덮은 화소가 아니라
**브래킷의 외접상자**이고, 83 개 삼각형이 모델 전체에 흩어진 브래킷의
외접상자는 그 브래킷이 덮는 것보다 훨씬 크다.  그리고 지우기 브래킷은
전체다.  **상한이 4.6 배보다 낮을 수도, 다를 수도 있다.**

## 3. 그러므로 재는 것

```
M1  실제 복사 수 대 훅 호출 수          Buffer.c 에 복사 카운터 하나
M2  브래킷마다의 더러운 외접상자         훅이 이미 창 좌표를 안다
    그 합(화소) 대 129 x 307200
```

M2 의 규칙은 codex 의 것을 그대로 쓴다 — **변환·클립된 삼각형의
외접상자 ∩ 시저** — 그리고:

```
가속 지우기가 있었으면        그 브래킷은 표면 전체
소프트웨어가 하나라도 그렸으면 그 브래킷은 표면 전체 (우리는 못 본다)
```

teapot 은 소프트웨어가 0 이므로 이 부하에서 나오는 수는 **최선의 경우**다.
그렇게 **적는다** — 일반값이 아니다.

## 4. 계측은 시험 전용이 아니다 — 그래서 값이 싸야 한다

M2 는 삼각형마다 6 번의 비교다(꼭짓점 3 개 x min/max 2 축).  빌더는 이미
삼각형마다 그보다 훨씬 많은 일을 한다.  그러나 **출하 경로에 계측을 남기지
않는다**: `OSMGA_MESA_INST_*` 스위치 아래 둔다.

## 7. 비용이 화소인지를 **쟀다** — 논증하지 않았다

`OSMGAMesaBufferMirrorBox()`(시험 전용, 더러움 플래그를 안 건드린다)로
같은 복사를 모양만 바꿔 가며 시간을 쟀다.  129 개의 52x52 상자는 **6708 행**
이고 전체 표면 한 번은 480 행이니, 행에 값이 있으면 여기서 드러난다.

```
모양          화소     행    시간        ns/화소   us/행
전체        307200    480   229.175 ms   746.0    477.4
52x52         2704     52     2.033 ms   751.7     39.1
한 행          640      1     0.476 ms   744.3    476.4
한 열          480    480     0.630 ms  1311.9      1.3
절반 행     153600    240   114.552 ms   745.8    477.3
절반 열     153600    480   114.688 ms   746.7    238.9
```

**절반 행과 절반 열이 같은 값이다** — 행이 두 배인데 0.1% 차이다.
행 하나의 고유 비용은 약 **0.57 us** 이고, 52 화소 너비 행에서 **1.5%** 다.
teapot 이 실제로 쓰는 52x52 에서 751.7 대 746.0, **0.8%**.

**값은 화소다.**  그리고 미러 비용이 세 갈래로 같은 수에 모인다:

```
직접 시간 측정          229.175 ms
teapot 29.432 s / 128    229.938 ms
512x384 의 146.722 스케일 229.253 ms      퍼짐 0.32%
```

## 8. 결과 — `M19` 의 **두 수가 다 틀렸다**

```
                    호출  실복사   미러가 옮긴 화소    좁히면
사다리꼴 / WARP      129     128        39628800       348845
```

두 층에서 **예산이 완전히 같다**(348845) — 상자는 기하의 성질이지 층의
성질이 아니다.  그리고 **좁히지 못하는 브래킷이 0 개**였다: 이 부하에서는
쓰는 주체가 전부 보였다.

```
             M19 가 말한 것   실제
(A) 지연         64.5 배      29.7 배
(B) 좁히기        4.6 배      36.9 배 (사다리꼴) / 44.4 배 (WARP)
```

**(A) 를 과대평가했다** — 29.432 를 통째로 미러로 쳤는데 미러가 아닌 일이
0.549 s 있다.  **(B) 를 8 배 과소평가했다** — 모델 전체가 덮는 비율(21.6%)을
브래킷 하나의 상자인 것처럼 썼다.  실제로는 브래킷이 **129 개**이고 하나가
**패치 하나**라 표면의 **0.88%** 다.

**그러므로 (B) 가 (A) 보다 낫고, 게다가 의미를 바꾸지 않는다.**
`M19 §8` 의 처분("(A) 만이 길이다")을 **뒤집는다**.

## 9. 그래도 지금 짓지 않는 이유는 남아 있다

이 부하에서 쓰는 주체가 전부 보였다는 것은 **이 부하의 사실**이지 계약이
아니다.  설계가 아직 정해야 하는 것:

```
가속 지우기      지금은 브래킷 전체를 더럽다고 친다(보수적).  제 사각형을
                 써야 한다 -- 프레임마다 지우는 응용에서는 그게 전부다
영역 대 상자     지금은 브래킷당 외접상자 하나.  흩어진 기하에서 과다청구
보이지 않는 쓰기 `RenderStart` 가 accum·bitmap·clear·copypix·drawpix·
                 readpix·teximage 를 다 연다고 주석이 말한다.  그 목록이
                 **완전한지**는 계약으로 못박아야 하고, 새 경로가 생기면
                 전체를 더럽다고 말할 자리가 있어야 한다
```

**측정이 설계를 정당화했다.  설계는 아직 하지 않았다.**
