# §3-12 — 엔진을 GL 규칙에 맞춘다 (계획, 2026-08-21)

앞선 회차: `M1_4A2_COVERAGE_RESULT.md` 가 **무엇이 어긋나는지**를 확정했다.
이 계획은 **그것을 고친다.**

## 1. 확정된 사실 (다시 재지 않는다)

- GL 규칙을 python 정수 연산으로 세워 채점했더니 **Mesa 소프트웨어는
  139/139 로 정확**하고 **엔진이 벗어난다**(119/139, 75/139).
- 원인: 엔진은 화소의 **왼쪽 위 모서리**에서, GL 은 **중심**에서 표본한다.
- D3-2 의 변 걷기를 시뮬레이터로 세워 실측을 **139/139·138/138 재현**했다.
- §3-12 에 적힌 수정법(시작 열만 치우침)은 **부족하다**: 300 개 중 13 개.

## 2. 무엇이 부족했나 — 안 건드린 손잡이

백엔드가 엔진에 넘기는 값 중 **두 개를 스스로 묶어 두고 있었다.**

1. **`AR0`/`AR6` 를 사다리꼴 높이 `h` 로 못박았다.** 이건 변이 나누는
   **분모**인데, 긴 변의 진짜 높이는 `H`(삼각형 전체)이지 `h` 가 아니다.
2. **`xSplit` 을 정수 나눗셈으로 구한다** — 긴 변이 중간 y 를 지나는 위치를
   반올림해 버리고, 아래 사다리꼴은 그 반올림된 값에서 다시 시작한다.

이 둘을 풀면 손잡이가 충분해진다.

## 3. 설계 — python 으로 검증됨

### 3-1. 걷기의 닫힌 형태 (검증: 넓은 스윕에서 불일치 0)

```
N_k = max(0, ceil((|dx|*k - e) / dy))      x_k = x0 + sgn * N_k
AR1 = -|dx| - e                             (기존 규약 그대로)
```

`max(0, ·)` 이 필요하다 — 누산기는 0 아래로는 배수(drain)하지 않는다.
**지난 회차에 쓴 닫힌 형태는 이 클램프가 없어 틀렸다.**

### 3-2. 규칙이 요구하는 경계

변이 `(xa, ya)` 에서 높이 `H` 동안 `D` 만큼 이동할 때, 행 `y = ya + k0 + k`
에서 GL 이 요구하는 경계는

```
B = xa + ceil( (2*D*(k0+k) + D - H) / (2*H) )
```

(`k0` 는 이 사다리꼴이 그 변의 몇 번째 행부터 쓰는지 — 아래 사다리꼴의 긴
변은 `k0 = my - ty`.)

### 3-3. 그래서 엔진에 넣을 값

**AR 쌍을 2 배로 키운다.** 기울기는 그대로이고, 반 화소가 **정수로**
표현된다.

```
AR0/AR6 = 2*H                     (사다리꼴 높이가 아니라 변의 진짜 높이)
AR2/AR5 = 2*|D|
e       = H - |D| - 2*|D|*k0 - (D < 0 ? 1 : 0)
AR1/AR4 = -2*|D| - e
FXBNDRY = 변의 시작 정점 xa       (아래 참조)
```

`e` 는 커질 수 있는데, `e` 를 `dy` 만큼 옮기면 걷기가 정확히 한 열
움직이므로 **남는 몫을 시작 열에 접어 넣는다.** 그러면

- `e` 는 `[0, dy)` 로 들어가고,
- **`N_0 = 0` 이 보장된다** — 즉 0 행에서 도약이 없다. FXBNDRY 에 적은 열이
  곧 첫 행의 열이다. (하드웨어가 큰 도약을 어떻게 처리하는지 몰라도 되게
  만드는 것이 이 정규화의 요점이다.)

### 3-4. `xSplit` 을 없앤다

사다리꼴 둘의 변을 **원래 변 그대로** 쓴다:

```
위: (t→m, k0=0)   와  (t→lo, k0=0)
아래: (m→lo, k0=0) 와  (t→lo, k0=my-ty)   ← 같은 긴 변, 이어서 걷는다
```

좌우 배정은 **삼각형마다 한 번** 외적 부호로 정한다.

### 3-5. 검증 결과 (python, 무작위 정수 삼각형 300 개)

| 설계 | 규칙과 일치한 행 | 완전히 맞은 삼각형 |
|---|---|---|
| 현재 (`e=0`, `AR0=h`, `xSplit`) | 36.5% | **0/300** |
| 오차항만 조정 | 73.5% | 13/300 |
| 오차항 + 시작 열 자유 | 92.2% | 2/40 |
| **이 설계** | **100.0%** | **300/300** |

좌우를 사다리꼴마다 **고정**해도 100% 이고, 300 개 중 **변이 교차한 경우는
0** 이었다(하드웨어는 행마다 좌우를 바꿀 수 없으므로 이게 필요했다).

**그리고 저 300 개에는 구멍이 있었다** — 무작위 생성에서 `y` 가 서로 다른
삼각형만 골랐다. **실제로 잰 도형 1 이 평평한 밑변**인데 그 종류를 한 번도
안 넣은 것이다. 메우고 다시 쟀다:

| 종류 | 결과 |
|---|---|
| y 세 개가 다름 (원래 시험) | 300/300 |
| **평평한 밑변/윗변** (둘이 y 공유) | **300/300** |
| **중간 정점이 긴 변 위** (외적 0) | **200/200** (13 개가 실제 collinear) |
| 높이 1 화소 | 200/200 |
| 아주 얇음 (x 폭 ≤ 2) | 200/200 |
| 높이 0 (세 점이 한 행) | 빈 결과 = 규칙과 일치 |

좌우 배정이 뒤집힌 경우(`L > R`)는 **한 번도 없었다.**

레지스터 크기: `AR0/AR6 ≤ 432`, `AR2/AR5 ≤ 606`, `|AR1/AR4| ≤ 893`.
현재 한계 `maxEdgeWalk = 16384` 안에 넉넉히 든다.

## 4. 그러면 커널을 건드려야 한다

`hw3d/OpenStepMGAHW3D.c:286` 이 **`ar0 == h` 를 강제**한다. 이 설계는 바로
그걸 깬다. 그 검사가 왜 있는지는 주석이 적어놨다:

> 0 인 분모는 누산기를 안 줄여서 변이 끝없이 걷는다 — 기울기 한계가
> 의미를 잃는다.

### 4-1. 처음 쓴 대체안은 틀렸다 (내가 내 계획을 쳐서 찾음)

처음에 이렇게 쓰려 했다:

```
ar0 > 0 && ar6 > 0
ceil(|ar2| * h / ar0) <= maxEdgeWalk
```

**이건 구멍이 있다.** `AR1` 은 `-|dx| - e` 이므로 클라이언트가 `AR1` 을
**양수**로 크게 주면 `e` 가 음수가 되고, 걷기는 **0 행에서 통째로
도약한다.** 변위(`ar2`)가 0 이어도 그렇다. python 으로 확인:

```
ar0=1, ar2=0, ar1=+16384, h=1  ->  0 행 도약 16384 열
                                    내 이동량 검사는 travel=0 으로 보고 통과시킴
```

**지금 커널의 `ar0 == h` 도 같은 구멍이 있다** — 그러니 회귀는 아니지만,
"더 강하다"는 주장은 근거 없이 셌던 것이다.

### 4-2. 실제로 묶는 검사

변위가 아니라 **시작 열로부터의 실제 이탈**을 묶는다. 0 행 도약이 자연히
포함된다.

```
e      = -ar1 - |ar2|                       (AR1 규약을 되푼 것)
N_last = max(0, ceil((|ar2|*(h-1) - e) / ar0))
요구:   ar0 > 0 && ar6 > 0
        N_last <= maxEdgeWalk
        시작 열과 시작 열 ± N_last 가 모두 [0, clipX1+1] 안
```

넘침: `h <= clipY1+1-y` 로 이미 묶여 있고 `|ar2| <= 16384` 이므로
`|ar2|*(h-1)` 은 32 비트 안에 든다. `ar0 > 0` 을 **먼저** 검사해 0 나눗셈을
막는다.

python 검증: 위 적대적 사례는 **거절되고**, 우리 설계의 변은 무작위 삼각형
400 개어치가 **전부 통과**한다.

이건 지금 커널보다 **실제로 더 강하다**(위 구멍을 막는다). 그리고 하드웨어의
진짜 방어는 여전히 `CXBNDRY/YTOP/YBOT` 이다 — 드라이버가 블록으로 좁혀
프로그램하고 있고, 코드 주석이 그렇게 적어놨다.

## 5. 이 수정이 **고치지 못하는 것** (미리 적는다)

도형 3(Mesa 가 자른 삼각형)의 **227** 은 이걸로 0 이 되지 않을 수 있다.
Mesa 의 클리퍼가 만드는 새 정점은 **정수가 아니고**, 훅이 `(long)` 으로
자른다 — §3-12 (2) 의 나머지 절반이다. 이 계획은 **정수 정점 삼각형을
정확히** 만든다. 소수 정점은 AR 쌍을 2 가 아니라 `2*S` 로 키워 같은 방식으로
담을 수 있어 보이지만, **이번에는 하지 않는다.** 한 번에 하나씩.

그러므로 성공 기준에 도형 3 을 넣지 않는다.

## 7-1. 이미 확인한 것 (python)

- 접기가 **항상** `0 <= e < dy` 와 `N_0 = 0` 을 준다 — 무작위 변 20000 개에서
  위반 0. 즉 **FXBNDRY 에 적은 열이 곧 첫 행의 열**이고, 색·깊이·알파 평면이
  그 열에 걸려 있어도 어긋나지 않는다.
- 닫힌 형태 `N_k = max(0, ceil((|dx|k - e)/dy))` 가 넓은 스윕에서 걷기와
  불일치 0.

## 8. 확인 안 된 가정 (실기가 판정해야 함)

**엔진이 `AR0 ≠ 행 수` 를 받아들이는가.** D3-2 는 `AR0 = h` 인 경우만
실증했다. 분모와 행 수가 다른 경우는 아무도 재지 않았다. 4 단계 뒤 첫
측정이 이걸 먼저 답한다 — 만약 엔진이 분모를 행 수로 무시한다면 이 설계는
무너지고, 그때는 §5 의 `2*S` 방향으로 다시 생각한다.
