## 2. 무엇이 부족했나 — 안 건드린 손잡이

백엔드가 엔진에 넘기는 값 중 **두 개를 스스로 묶어 두고 있었다.**

1. **`AR0`/`AR6` 를 사다리꼴 높이 `h` 로 못박았다.** 이건 변이 나누는
   **분모**인데, 긴 변의 진짜 높이는 `H`(삼각형 전체)이지 `h` 가 아니다.
2. **`xSplit` 을 정수 나눗셈으로 구한다** — 긴 변이 중간 y 를 지나는 위치를
   반올림해 버리고, 아래 사다리꼴은 그 반올림된 값에서 다시 시작한다.

이 둘을 풀면 손잡이가 충분해진다.

## 3. 설계 — python 으로 검증됨

### 3-1. 걷기의 닫힌 형태 (검증: 넓은 스윕에서 불일치 0)

```
N_k = max(0, ceil((|dx|*k - e) / dy))      x_k = x0 + sgn * N_k
AR1 = -|dx| - e                             (기존 규약 그대로)
```

`max(0, ·)` 이 필요하다 — 누산기는 0 아래로는 배수(drain)하지 않는다.
**지난 회차에 쓴 닫힌 형태는 이 클램프가 없어 틀렸다.**

### 3-2. 규칙이 요구하는 경계

변이 `(xa, ya)` 에서 높이 `H` 동안 `D` 만큼 이동할 때, 행 `y = ya + k0 + k`
에서 GL 이 요구하는 경계는

```
B = xa + ceil( (2*D*(k0+k) + D - H) / (2*H) )
```

(`k0` 는 이 사다리꼴이 그 변의 몇 번째 행부터 쓰는지 — 아래 사다리꼴의 긴
변은 `k0 = my - ty`.)

### 3-3. 그래서 엔진에 넣을 값

**AR 쌍을 2 배로 키운다.** 기울기는 그대로이고, 반 화소가 **정수로**
표현된다.

```
AR0/AR6 = 2*H                     (사다리꼴 높이가 아니라 변의 진짜 높이)
AR2/AR5 = 2*|D|
e       = H - |D| - 2*|D|*k0 - (D < 0 ? 1 : 0)
AR1/AR4 = -2*|D| - e
FXBNDRY = 변의 시작 정점 xa       (아래 참조)
```

`e` 는 커질 수 있는데, `e` 를 `dy` 만큼 옮기면 걷기가 정확히 한 열
움직이므로 **남는 몫을 시작 열에 접어 넣는다.** 그러면

- `e` 는 `[0, dy)` 로 들어가고,
- **`N_0 = 0` 이 보장된다** — 즉 0 행에서 도약이 없다. FXBNDRY 에 적은 열이
  곧 첫 행의 열이다. (하드웨어가 큰 도약을 어떻게 처리하는지 몰라도 되게
  만드는 것이 이 정규화의 요점이다.)

### 3-4. `xSplit` 을 없앤다

사다리꼴 둘의 변을 **원래 변 그대로** 쓴다:

```
위: (t→m, k0=0)   와  (t→lo, k0=0)
아래: (m→lo, k0=0) 와  (t→lo, k0=my-ty)   ← 같은 긴 변, 이어서 걷는다
```

좌우 배정은 **삼각형마다 한 번** 외적 부호로 정한다.

### 3-5. 검증 결과 (python, 무작위 정수 삼각형 300 개)

| 설계 | 규칙과 일치한 행 | 완전히 맞은 삼각형 |
|---|---|---|
| 현재 (`e=0`, `AR0=h`, `xSplit`) | 36.5% | **0/300** |
| 오차항만 조정 | 73.5% | 13/300 |
| 오차항 + 시작 열 자유 | 92.2% | 2/40 |
| **이 설계** | **100.0%** | **300/300** |

좌우를 사다리꼴마다 **고정**해도 100% 이고, 300 개 중 **변이 교차한 경우는
0** 이었다(하드웨어는 행마다 좌우를 바꿀 수 없으므로 이게 필요했다).

**그리고 저 300 개에는 구멍이 있었다** — 무작위 생성에서 `y` 가 서로 다른
삼각형만 골랐다. **실제로 잰 도형 1 이 평평한 밑변**인데 그 종류를 한 번도
안 넣은 것이다. 메우고 다시 쟀다:

| 종류 | 결과 |
|---|---|
| y 세 개가 다름 (원래 시험) | 300/300 |
| **평평한 밑변/윗변** (둘이 y 공유) | **300/300** |
| **중간 정점이 긴 변 위** (외적 0) | **200/200** (13 개가 실제 collinear) |
| 높이 1 화소 | 200/200 |
| 아주 얇음 (x 폭 ≤ 2) | 200/200 |
| 높이 0 (세 점이 한 행) | 빈 결과 = 규칙과 일치 |

좌우 배정이 뒤집힌 경우(`L > R`)는 **한 번도 없었다.**

레지스터 크기: `AR0/AR6 ≤ 432`, `AR2/AR5 ≤ 606`, `|AR1/AR4| ≤ 893`.
현재 한계 `maxEdgeWalk = 16384` 안에 넉넉히 든다.

## 4. 그러면 커널을 건드려야 한다

`hw3d/OpenStepMGAHW3D.c:286` 이 **`ar0 == h` 를 강제**한다. 이 설계는 바로
그걸 깬다. 그 검사가 왜 있는지는 주석이 적어놨다:

> 0 인 분모는 누산기를 안 줄여서 변이 끝없이 걷는다 — 기울기 한계가
> 의미를 잃는다.

### 4-1. 처음 쓴 대체안은 틀렸다 (내가 내 계획을 쳐서 찾음)

처음에 이렇게 쓰려 했다:

```
ar0 > 0 && ar6 > 0
ceil(|ar2| * h / ar0) <= maxEdgeWalk
```

**이건 구멍이 있다.** `AR1` 은 `-|dx| - e` 이므로 클라이언트가 `AR1` 을
**양수**로 크게 주면 `e` 가 음수가 되고, 걷기는 **0 행에서 통째로
도약한다.** 변위(`ar2`)가 0 이어도 그렇다. python 으로 확인:

```
ar0=1, ar2=0, ar1=+16384, h=1  ->  0 행 도약 16384 열
                                    내 이동량 검사는 travel=0 으로 보고 통과시킴
```

**지금 커널의 `ar0 == h` 도 같은 구멍이 있다** — 그러니 회귀는 아니지만,
"더 강하다"는 주장은 근거 없이 셌던 것이다.

### 4-2. 실제로 묶는 검사

변위가 아니라 **시작 열로부터의 실제 이탈**을 묶는다. 0 행 도약이 자연히
포함된다.

```
e      = -ar1 - |ar2|                       (AR1 규약을 되푼 것)
N_last = max(0, ceil((|ar2|*(h-1) - e) / ar0))
요구:   ar0 > 0 && ar6 > 0
        N_last <= maxEdgeWalk
        시작 열과 시작 열 ± N_last 가 모두 [0, clipX1+1] 안
```

넘침: `h <= clipY1+1-y` 로 이미 묶여 있고 `|ar2| <= 16384` 이므로
`|ar2|*(h-1)` 은 32 비트 안에 든다. `ar0 > 0` 을 **먼저** 검사해 0 나눗셈을
막는다.

python 검증: 위 적대적 사례는 **거절되고**, 우리 설계의 변은 무작위 삼각형
400 개어치가 **전부 통과**한다.

이건 지금 커널보다 **실제로 더 강하다**(위 구멍을 막는다). 그리고 하드웨어의
진짜 방어는 여전히 `CXBNDRY/YTOP/YBOT` 이다 — 드라이버가 블록으로 좁혀
프로그램하고 있고, 코드 주석이 그렇게 적어놨다.

## 7-1. 이미 확인한 것 (python)

- 접기가 **항상** `0 <= e < dy` 와 `N_0 = 0` 을 준다 — 무작위 변 20000 개에서
  위반 0. 즉 **FXBNDRY 에 적은 열이 곧 첫 행의 열**이고, 색·깊이·알파 평면이
  그 열에 걸려 있어도 어긋나지 않는다.
- 닫힌 형태 `N_k = max(0, ceil((|dx|k - e)/dy))` 가 넓은 스윕에서 걷기와
  불일치 0.
- **`FXBNDRY` 가 범위를 벗어나지 않는다.** 접기는 시작 열을 옮기므로
  검증기의 `left/right <= clipX1+1` 에 걸릴 수 있다고 의심했는데, 화면 안에
  드는 삼각형 3000 개(사다리꼴 5960 개)에서 **벗어난 경우 0**, 그리고
  **`left > right` 인 경우도 0** 이었다. 접힌 시작 열은 언제나 **실제로
  그려지는 첫 열**(`N_0 = 0`)이라 삼각형 안에 있고, 따라서 클립 안에 있다.
- 색·깊이·알파 평면은 사다리꼴의 `(left, y)` 에 걸려 있는데, **적어 넣는
  시작 열이 곧 첫 그려지는 열**임을 변 11924 개에서 확인했다(불일치 0).
  그러므로 평면 계산은 그대로 두면 된다.

## 7-2. codex 교차검토 — 무엇이 맞았고 무엇이 이미 답이 있었나

**신뢰하지 않고 하나씩 확인했다.**

### 맞았다 (셋)

**(가) 접기는 일반적으로 성립하지 않는다.** `N_k = max(0, ...)` 의 클램프
때문이다. codex 의 반례를 그대로 돌렸다 — `dy=10, A=1, e=15` 에서 접기 전은
0 행부터 `0,0,0,...`, 접은 뒤는 `-1,-1,-1,...`. **다르다.**

그러나 **우리 구성은 `e >= dy` 를 만들지 않는다**:

```
e_before = H - |D| - 2|D|k0 - (D<0)  <=  H,   dy = 2H
=> e_before - dy <= -H <= -1                  (H >= 1)
```

무작위 변 50000 개에서 `max(e_before - dy) = -2`. 그리고 접은 결과와 안 접은
결과가 **4000/4000 변에서 동일**하다. → **전제로 명시하고 단정(assert)한다.**
"접기는 일반 변환"이라고 적지 않는다.

*(내 첫 확인은 헛돌았다 — `worst = 0` 으로 시작해 `max` 를 걸어서, 값이 전부
음수인데 초기값 0 이 찍혔다. 다시 쟀다.)*

**(나) 양 끝만 봐서는 두 변이 교차하지 않음을 증명 못 한다.** 두 단조 걷기의
차는 단조가 아니다. 실제 사례를 찾았다 — 0 행과 마지막 행은 순서가 맞는데
36 행에서 `L=50 > R=49`. **우리 구성은 4000 삼각형에서 교차 0** 이지만,
**적대적 클라이언트는 만들 수 있다.** 지금 커널도 못 막는다(FXBNDRY 시작만
본다). → 검증기는 **행마다** 유효한 반열린 span 을 요구해야 한다. 비용은
`h + N_last` 이고 `N_last <= clipX1+1` 이 이미 요구되므로 묶여 있다.

**(다) 첫 재부팅을 Mesa 측정이 아니라 능력 탐침으로 써라.** 이게 내 순서보다
낫다. 검증기 완화 + 최소 raw-trap 탐침을 한 빌드에 넣고, **Mesa 경로를 켜기
전에** `AR0 = h` 대 `AR0 = 2H` 를 알려진 변 하나로 먼저 가른다. 실패해도
"Mesa 산술 버그"로 오독하지 않는다.

보강: `mesa/` 에 이미 `getenv` 패턴이 있으므로(`OSMGA_PROBE_ENV`) 새 생성기를
**런타임 선택**으로 두면 한 번의 부팅에서 두 경로를 다 잰다.

### 이미 소스에 답이 있었다 (셋)

- **"`h == 0` 을 `h-1` 앞에서 걸러라"** — 이미 걸린다:
  `OpenStepMGAHW3D.c:235` 가 `t->h <= 0` 을 거절한다.
- **"하한을 0 으로 두지 말고 목적지 왼쪽 경계로"** — 3D 경로는 `clipX0 = 0`

### 맞지만 이미 우리 구성이 그렇다 (둘)

- `-1` 항은 **올림을 부호 반전할 때 생기는 정수 항등식**에서 온다. 변을
  **위→아래로 정규화**해야만 성립한다 — 우리는 언제나 y 로 정렬해 그렇게
  만든다.
- 위 사다리꼴의 마지막 행은 `my-1`, 아래의 첫 행은 `my` 라 **한 행을 공유하지
  않는다.** 요구할 것은 "만난다"가 아니라 **각 행이 정확히 한 사다리꼴에
  속하고 그 행에서 전체 변 규칙을 받는 것**이고, 이걸 직접 확인했다 —
  아래 사다리꼴의 긴 변이 전체 변의 `k0+k` 행과 **4000/4000 일치**.

### 받아들이되 범위는 지킨다 (둘)

- **퇴화 경우를 빈 span 에 기대지 말고 명시적으로 처리하라.** 실측은
  100% 지만 명시적 경로가 더 튼튼하다 — 넣는다.
- **커버리지만으로는 보간(색·깊이·알파)이 맞는지 모른다.** 맞다. 두 색
  도형이 색 일부를 보지만 깊이·알파는 안 본다. 성공 기준에 추가한다.

## 8. 확인 안 된 가정 (실기가 판정해야 함)

**엔진이 `AR0 ≠ 행 수` 를 받아들이는가.** D3-2 는 `AR0 = h` 인 경우만
실증했다. 분모와 행 수가 다른 경우는 아무도 재지 않았다. 4 단계 뒤 첫
측정이 이걸 먼저 답한다 — 만약 엔진이 분모를 행 수로 무시한다면 이 설계는
무너지고, 그때는 §5 의 `2*S` 방향으로 다시 생각한다.

## 10. 첫 실기 측정 — 나빠졌고, 이유가 값어치 있었다 (2026-08-21)

탐침은 통과했다: 엔진이 `AR0` 을 존중한다(20/20 행, "무시" 예측은 2/20).
그런데 커버리지는 **나빠졌다** — shape 1 은 119/139 → 80/139, shape 2 는
75/139 → **2/139**.

### 10-1. 내 탐침이 새것 둘 중 **하나만** 쟀다

이번 인코딩이 새로 한 것은 둘이다: `AR0 ≠ h`, 그리고 **`AR1 ≠ AR2`**.
탐침은 `AR0` 만 갈랐고 **오차항은 `e = 0` 으로 두었다.** D3-2 의 원래
적합도 `AR1 == AR2` 에서만 이뤄졌다.

**그 제약 아래에서는 서로 다른 두 점화식이 똑같은 화소를 낸다.** 그러니
D3-2 는 고를 수 없었고, 나는 틀린 쪽을 골랐다.

### 10-2. 드러낸 것: 변위가 0인 변

축에 나란한 사각형의 세로 변은 변위가 **0** 이다. 아무것도 누적되지 않는
규칙은 변을 움직일 수 없다. **그런데 엔진은 둘째 행부터 한 열 옮겼다**
(측정: `{(0,0): 1, (1,1): 139}`).

### 10-3. 실제 규칙 (세 방향으로 측정)

```
a = AR1 - AR2 ;  0 행은 FXBNDRY 자리에 그대로 나온다
행 사이:  a += AR2 ;  a < 0 인 동안:  x += sgn ;  a += AR0
```

즉 **0 행은 걸음이 없고, 오차항의 부호가 내가 가정한 것과 반대**다.

codex 가 대안 가설("옛 규칙 + 시작 시 한 번의 캐리")과 `a <= 0` 변형을
내놨고, **그 예측을 python 으로 먼저 확인한 뒤** 판별 탐침을 돌렸다:

| 후보 | 판별 band | 대조군 band |
|---|---|---|
| **`a < 0` (이 규칙)** | **8/8** | **20/20** |
| `a <= 0` | 7/8 | 11/20 |
| 옛 규칙 + 시작 캐리 | 6/8 | 1/20 |

그리고 이 규칙은 **오늘 실기가 그린 것 전체를 정확히 재현한다** —
shape 1·2·4·5 가 138/138, 139/139, 138/138, 140/140.

### 10-4. 같은 틀린 점화식이 **세 곳**에 있었다

생성기, **생성기의 레지스터를 걷는 시험**, 그리고 **커널 검증기**. 그래서
호스트 시험이 코드와 사이좋게 통과했다 — 둘이 같은 가정을 공유했다.
검증기는 고치기 전까지 **정확한 삼각형 810 개 중 199 개를 거절**했다.

### 10-5. 다시 세운 뒤

| 확인 | 결과 |
|---|---|
| python, 무작위+corpus 409 삼각형 | **47230/47230 행 정확** |
| 실기 C 시험, 810 삼각형 | **194400 행 어긋남 0, 커널 거절 0** |
| 커널 검증기 시험 | **0 실패** |

검증기 사례 하나는 값이 아니라 **뜻이 바뀌었다**: 높이 1인 사다리꼴은
전이가 없어 **변위가 아무리 커도 움직이지 않는다.** 그래서 "한 행에 예산
전부"는 이제 통과이고, 사각형을 벗어나는 것은 **두 행짜리 짝**이다.

### 10-6. 결론짓지 말아야 할 것

D3-2 의 20행 적합은 점화식을 확정한 것이 **아니었다** — `AR1 == AR2` 아래의
**동치류**를 확정했을 뿐이다. 제약이 걸린 실험에서 나온 유일해는 그 제약
밖에서 유일하지 않다.

### 12-1. shape 3 의 남은 차이 — 논증이 아니라 측정으로

227 → **110** 행으로 줄었다. 남은 것이 정말 §5 에 적어둔 절단인지,
**틀릴 수 있는 형태로** 물었다. 도형 8 = 도형 1 을 **반 화소 옮긴 것**,
잘림 없음. 훅이 `(long)` 으로 자르므로 백엔드가 받는 것은 도형 1 이다.

| 예측 | 결과 |
|---|---|
| `hardware(8) == hardware(1)` 화소 단위로 | **참, 0 개 차이** |
| `software(8) != software(1)` | 참, 139 행 차이 |
| `hardware(8)` 을 **잘라낸** 삼각형의 규칙에 대고 | **139/139 EXACT** |

**소수 정점에서 남는 차이는 오직 절단이다.** 다른 원인은 필요 없다.

### 12-2. 검증기 비용 — 재 봤다

교차검토가 "행마다 걷는 검증기는 면적에 비례해 3 억 8 천만 번이 된다"고
경고했다. **그렇지 않다**: 행 루프는 행마다 한 번이고, 안쪽 루프는 한
방향으로만 움직이며 사각형을 벗어나는 즉시 거절되므로 **열 이동 총량이
폭으로 묶인다.** 비용은 `행 + 폭`이지 `행 × 폭`이 아니다.

측정(`hw3d/test-hw3d-validate-cost.c`): 1600x1200, **200 삼각형 × 1200 행,
전폭을 가로지르는 변** — 20000 회에 34 초, **한 번에 1.7 ms**.

### 12-3. 교차검토에서 받아들인 것 — 아직 못 본 것

- **평면 정착(색·깊이·알파)은 이 측정이 증명하지 못한다.** 이 도형들은
  전부 `GL_FLAT` 이라 기울기가 0 이고, 정착이 어긋나도 **보이지 않는다.**
  두 색 사각형은 소유 경계만 보여줄 뿐이다. → Gouraud 기울기 + 알파 + 깊이
  기울기를 가진, **분할되는** 삼각형으로 따로 재야 한다. (다음 항목)
- 이 세 도형의 행별 span 비교가 못 보는 것: 다른 기울기 잔여류, 음수 좌표,
  클립 경계 접촉, 과다그리기(같은 색이면 중복 쓰기가 안 보인다), 읽어오는
  사각형 **밖**의 쓰기.
- 공통 오류 방지 규칙: **주 신탁은 DDA 가 아니라 기하여야 한다.**
  `coverage-compare.py` 의 신탁은 이미 그렇다 — 화소 중심 반평면 검사이고
  AR 레지스터를 쓰지 않는다. 지난 회차에 코드와 사이좋게 틀렸던 것은
  레지스터를 걷는 호스트 시험 쪽이었고, **틀렸다고 말해준 것은 기하 신탁**
  이었다. 그 구조를 유지한다.
