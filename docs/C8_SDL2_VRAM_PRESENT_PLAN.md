# C8 — SDL2 를 VRAM 에서 바로 내보내기

> **결과 (2026-08-29).**  `(가)` 를 실측했다.  320x240 에서 wall 1847.41 →
> **11.42 ms**, 0.54 → **87.53 fps** (**162 배**), 되읽기 6400 회 → **0 회**.
> 800x600 에서 **54.60 fps**, 도장 **3.69 ms** — 이 저장소의 AppKit 창 데모가
> 내던 present 3.69 ms 와 같은 값이고 그 52 fps 를 넘는다.
> 자세한 것은 §10.

## 1. 무엇이 측정되었나 (2026-08-29)

`가` 안(SDL2 백엔드의 `OSMESA_Y_UP` 을 1 로)이 **가속을 되살렸다**.
`sdlteapot_hybrid 320 240`, `OSMGA_MESA_WARP=1`:

```
surface is the engine's : yes
drawn by the card       : 204800   (batches 6400)
of those, WARP took     : 204800   (trapezoids 0)
left to Mesa / refused  : 0 / 0
surface read back       : 6400 copies   (6800 mirror calls)

render + finish : 1835.60 ms
SDL swap        :    0.82 ms
wall            : 1847.41 ms  (0.54 fps)
```

카드가 삼각형을 **전부** 그렸다.  그런데 0.54 fps 다.

## 2. 비용은 어디에 있나 — 추정이 아니라 계산

320x240 = 76,800 화소, 되읽기 746 ns/화소:

```
전체 표면 1 회        76800 * 746ns =   57.29 ms
프레임당 회수         6400 / 200    =   32
프레임당 예측         57.29 * 32    = 1833.4 ms
실측                                 1835.60 ms
비                                      0.999
```

되읽기가 차지하는 몫은 **render+finish 구간의 99.88%**, **wall 의 99.24%**
다.  wall 에는 계측되지 않은 10.99 ms 가 남는다 (이벤트 처리, 서버, 루프).

`SDL swap 0.82 ms` 로부터 **"AppKit 이 싸다"를 결론짓지 않는다.**  그 값은
`SDL_GL_SwapWindow` 호출이 돌아오기까지만 잰 것이고, 이 데모에는 창 서버가
실제로 그렸는지 기다리는 fence 가 없다.  glwin 의 62.79 ms 는 서버 대기를
포함한 값이므로 둘은 같은 것을 재지 않았다.  present 의 이득은 그 비교와
무관하게 성립한다: **프레임당 1.83 초짜리 되읽기 32 회가 통째로 사라진다.**

프레임당 32 회인 이유: 미러는 렌더 브래킷이 닫힐 때마다 돈다.  주전자
한 프레임이 32 배치이므로 32 번 닫힌다.

### 2.1 좁힌 미러는 이 문제에 손대지 못한다

`OSMGA_MESA_NARROW=1` 로 다시 재보니 1835.06 ms — 차이가 없다.
**환경변수가 아니기 때문이다.**  좁히기는 `OSMGAMesaHookNarrowMirror(int)`
라는 함수이고, 전수 grep 결과 **저장소 안에서 아무도 부르지 않는다**
(시험 전용 경로를 빼면 호출자 0).  M21 이 41.4 배를 실측해 놓고도 그
이득은 어떤 응용에도 닿지 않는다.  이것은 별개의 결함이고 §7 에 남긴다.

설령 켠다 해도 이 데모에는 거의 소용이 없다: 주전자가 창을 거의 다
채우므로 32 개 브래킷의 더티 박스가 각각 표면만 하다.

## 3. 그러면 무엇을 해야 하나

**되읽기를 줄이는 게 아니라 없애는 것이다.**  드라이버에 이미 그 길이 있고,
이 저장소의 창 데모가 그 길로 800x600 에서 52 fps 를 낸다:

```
OSMGAMesaBufferPresentMode(1)     호출자의 배열을 낡은 것으로 선언한다.
                                  미러도, clear 의 상수 전달도, 재바인드
                                  import 도 전부 선다.
OSMGAMesaBufferPresentRect(sx,sy,w,h, dx,dy, &verdict)
                                  커널이 VRAM→VRAM 으로 화면에 찍는다.
                                  버스를 건너는 것이 없다.
```

glwin 의 present 는 3.69 ms 였고 AppKit 경로는 62.79 ms 였다.

## 4. 설계상의 진짜 문제 — 계층

`libSDL2.a` 는 **stock Mesa 와도 링크되어야 한다** (`sdlteapot_sw` 가 그렇다).
`OSMGAMesaBuffer*` 는 `libGL_mga.a` 에만 있다.  SDL2 백엔드가 이 심볼을
직접 부르면 stock 빌드가 **링크되지 않는다**.

따라서 다음 중 하나여야 한다:

```
(가) 응용이 직접 present 한다        SDL2 무변경
(나) SDL2 가 훅을 등록받는다          아래 참조 -- 공개 심볼이 늘지 않는다
(다) libSDL2 두 벌                    릴리스 행렬 2 배
(라) 런타임 심볼 조회                 정적 링크에서 취약
```

`(다)` 와 `(라)` 는 값이 너무 비싸다.

**`(나)` 가 공개 심볼을 늘린다고 적었던 것은 틀렸다.**  `SDL_SetWindowData`
와 `SDL_GetWindowData` 는 **이미 이 라이브러리에 정의되어 있다** (실기의
`nm libSDL2.a` 로 둘 다 `T` 확인).  응용이

```c
SDL_SetWindowData(win, "OSMGA.present", &hooks);
```

로 함수 포인터 구조체를 걸어 두면, 백엔드는 `SDL_GetWindowData` 로 꺼내
**일반 함수 포인터만 호출한다** — `OSMGAMesaBuffer*` 라는 이름이 SDL2 안에
전혀 나타나지 않으므로 stock Mesa 링크가 깨지지 않고, 836 심볼 매니페스트도
그대로다.  남는 비용은 심볼이 아니라 **문서화된 opt-in 규약과 수명주기**다.

## 4.5 세 번째 길 — 미러를 프레임당 32 회에서 1 회로

`§2.1` 은 **좁히기**를 배제했을 뿐, **횟수**를 배제하지 않았다.  둘은 다른
것이다: 좁히기는 사각형의 넓이를 줄이고, 이 길은 복사의 회수를 줄인다.

미러는 `ctx->Driver.RenderFinish` 에 걸려 있다 — 즉 **프레임이 아니라 원시
묶음마다** 돈다.  주전자 한 프레임이 32 배치이므로 32 회다.  `Finish`/`Flush`
에도 같은 함수가 걸려 있고, 그 둘은 프레임당 2 회 불려 이미 깨끗한 표면을
본다 (미러 호출 34, 복사 32).

```
지금            34 회 호출 / 32 회 복사   1835.60 ms   0.54 fps
프레임 경계만    2 회 호출 /  1 회 복사      57.29 ms  17.5 fps  (예측)
```

**32 배.**  그리고 이 길은 SDL 의 정상 swap 을 그대로 쓰므로 AppKit 의
expose·가림·z-order 합성을 하나도 건드리지 않는다.

**공짜는 아니다.**  OSMesa 의 계약에서 호출자는 `glFinish` 뒤에 자기 배열을
읽을 수 있고, 드라이버가 무조건 미루면 그 계약이 깨진다.  그러므로 명시적
opt-in 이어야 한다 — "다음 동기점까지 호출자 배열은 낡은 것으로 취급하라"를
응용이 선언하는 형태.  `PresentMode` 가 이미 그 성질의 선언이므로 모양은
새로 만들 것이 아니다.

## 5. 그래서 순서 — 두 가지를 재고 나서 `(나)` 를 판단

C7 이 스스로 적어둔 규칙이 이것이다: *"측정 없이 백엔드를 고치는 것은
M19 에서 한 번 밟은 순서다."*

**`(가)` 가 `(나)` 와 "같은 숫자"를 만든다고 적었던 것은 틀렸다.**  둘은
다른 것을 잰다:

```
(가)      VRAM present 의 실측 하한, 방향, 클리핑, 커널 승인
          -- 창 계약을 우회한 상태에서
(나)      그 위에 SDL 창 백엔드로서의 수명주기 비용
          -- expose, 가림, 이동, 비활성, z-order
```

`(가)` 는 `(나)` 의 **사전 관문**이다: `(가)` 가 실패하면 `(나)` 는 볼 것도
없고, `(가)` 가 통과해도 `(나)` 의 비용은 아직 재지 않은 것이다.

그리고 `4.5` 를 **함께** 잰다.  둘 중 무엇이 답인지는 두 숫자를 나란히
놓아야 정해진다.

`(가)` 로 데모가 하는 일:

```
문맥 생성 직후          OSMGAMesaBufferPresentMode(1)
프레임 끝               SDL_GL_SwapWindow 를 부르지 않는다
                        OSMGAMesaBufferPresentRect(...) 로 직접 찍는다
```

창의 화면 위치는 `SDL_GetWindowPosition` 이 준다.  glwin 의 변환:

```
dstX = p.x
dstY = screenH - (p.y + H)        (AppKit 은 아래가 0, 스캔아웃은 위가 0)
음수/화면밖은 srcX/srcY 를 밀고 pw/ph 를 깎아 잘라낸다
```

SDL 의 `SDL_GetWindowPosition` 은 **이미 위가 0 인 좌표를 준다** — 추측이
아니라 확인된 사실이다: 포트가 `screen_frame.origin.y + height - y - h` 로
AppKit 의 아래-0 좌표로 **변환해서** 창을 놓고(`OPENSTEP_FrameForContent`),
`windowDidMove:` 는 그 역변환으로 SDL 에 돌려준다.  그러므로 present 의
dstY 에 뒤집기가 필요 없다.

**그러나 남는 전건은 좌표계가 아니라 동기성이다.**  SDL 의 값은 이동
이벤트가 처리된 뒤의 캐시다.  glwin 이 서버에 위치를 직접 묻고 이동 중
프레임을 건너뛰는 이유가 그 지연이다 — 좌표계가 맞아도 이 가드를 빼면
드래그 잔상이 난다.

## 5.5 `(가)` 의 치명적 한계 — expose 가 도장을 덮는다

계획의 첫 판은 이것을 다루지 않았다.  SDL 뷰의 `drawRect:` 는

```objc
if (_bitmap != nil) { [_bitmap drawInRect:[self bounds]]; }
```

를 **무조건** 먼저 한다.  `(가)` 는 `SDL_GL_SwapWindow` 를 부르지 않으므로
그 비트맵은 첫 내용에 멈춰 있고, 노출·가림 복원 때마다 **낡은(또는 빈)
비트맵이 VRAM 도장 위에 그려진다.**  그 뒤 다음 present 까지 화면이 돌아오지
않는다.

메모리 안전 문제는 아니지만 **일반 창으로는 못 쓴다.**  그러므로 `(가)` 의
범위를 이렇게 못박는다:

```
(가) 는 glwin 과 동등한 "직접 도장 데모" 다.
     expose 직후 즉시 재present 하고,
     이동·가림·비활성·이벤트대기에 glwin 과 같은 가드를 둔다.
     이 가드 없이 나온 fps 는 성능 마이크로벤치일 뿐이며,
     그렇게 보고한다.
```

`4.5` 에는 이 문제가 **없다** — 정상 swap 이 매 프레임 비트맵을 갱신한다.

## 6. 방향 — 이 변경이 방향 문제를 흡수한다

운영자가 방금 확인했다: `가` 를 넣은 하이브리드도 **여전히 뒤집혀 있다.**
그럴 만하다 — `가` 는 방향에 대해 **중립**이다:

```
Y_UP=0 + 뒤집는 복사   = 뒤집기 두 번 = 항등
Y_UP=1 + 안 뒤집는 복사 = 항등
```

두 조합이 같은 그림을 낸다.  즉 뒤집힘은 복사에서 온 적이 없다.
그런데 present 로 가면 **blit 은 행을 뒤집지 못한다** — glwin 이 절두체의
top/bottom 을 바꾸고 컬링을 끄는 이유가 그것이다.  `(가)` 를 하면 이
데모도 같은 절두체를 쓰게 되고, 방향은 거기서 결정된다.

**그러므로 방향은 추측하지 않고 시험으로 고정한다** (§7 의 회귀 시험).

## 10. 실측 (2026-08-29)

`sdlteapot_hybrid`, `OSMGA_MESA_WARP=1`, 200 프레임.
`OSMGA_SDLTEAPOT_PRESENT=1` 이 도장 경로를 고른다.

```
320x240                 SDL swap        VRAM 도장
  render + finish       1835.60 ms        10.44 ms
  전달                      0.82 ms         0.62 ms
  wall                  1847.41 ms        11.42 ms
  fps                        0.54           87.53
  되읽기                     6400 회            0 회
  미러 호출                  6800 회         6600 회

800x600                                 VRAM 도장
  render + finish                         14.27 ms
  도장                                      3.69 ms
  wall                                    18.31 ms
  fps                                        54.60
  프레임 물러남                                  2 회
```

세 가지가 확인된다.

1. **되읽기가 0 이 된다.**  `PresentMode(1)` 이 미러를 세우므로 호출 6600 회가
   전부 복사 없이 돌아간다.  §2 의 진단이 맞았다.
2. **도장 값이 창 데모와 같다.**  800x600 에서 3.69 ms — glwin 이 낸 것과
   같은 숫자다.  SDL2 가 그 경로를 그대로 쓰고 있다는 뜻이다.
3. **가속은 그대로다.**  drawn 204800, warp 204800, 사다리꼴 0, 거부 0 —
   전달을 바꾸어도 카드가 그리는 몫은 달라지지 않았다.

### 10.1 `4.5` 는 재지 않았고, 그 판단을 남긴다

도장이 162 배를 냈고 `4.5` 의 예측은 32 배였다.  이 데모에는 도장이 답이다.
그러나 `4.5` 를 폐기하지는 않는다: **호출자 배열을 정말 읽어야 하는 응용**
(오프스크린 렌더, `glReadPixels`, 화면 밖 합성) 은 도장을 쓸 수 없고, 그런
응용에는 32 배가 그대로 남아 있다.  별건으로 남긴다.

### 10.2 방향은 델리버리 문제가 아니었다

`openstep-sdl-gl-orientation` 을 2D/GL × 소프트웨어/가속 네 경우로 돌렸더니
**비트맵 배치가 넷 다 같았다.**  SDL 도 드라이버도 뒤집지 않는다.
주전자가 뒤집혀 보인 것은 `tea.c` 에서 잘라 온 `teapot()` 이 **뚜껑으로 서
있기** 때문이고 — 이 저장소의 오프라인 주전자가 같은 사실을 이미 기록해
두었다 — SDL 데모에 그 반 바퀴가 빠져 있었다.  한 줄로 고쳤다.

도장 경로에서는 절두체가 다르다: **blit 은 행을 뒤집지 못하므로 투영이
뒤집는다** (glwin 과 같다).  `projection()` 이 전달 방식에 따라 고른다.
