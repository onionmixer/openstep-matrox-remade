# M1-3M — 32 화소가 아닌 pitch 를 그리지 않게 한다 (§3-21)

`M1_3L_PLAN.md` §6 과 `REMAINING_WORK §3-21` 위에서 세운다. 아직 코드 없음.

## 1. 확정된 사실

목적지 pitch 는 **32 화소의 배수**여야 한다. 세 갈래가 같은 값이다:

- 실기 12 개 너비, 예외 없이 갈림 (64·320·352·640·800 정상 /
  322·324·328·333·336·369·655 붕괴). python 으로 2·4·8·16·64 를 전부
  시험했고 **32 만** 가른다.
- `xf86-video-mga` `mga_exa.c:869` — *"Pitch alignment is in sets of 32
  pixels… so it's 128 bytes"*, `pixmapPitchAlign = 128` (÷4 = 32 화소).
- 같은 저장소 `mga_dacG.c:2294` — G 계열 DAC 의 `Roundings[3] = 32`
  (4 바이트/화소). 2 바이트/화소도 32 이므로 16 비트 깊이도 같다.

**지금은 아무도 확인하지 않는다.** Mesa 는 표면 보폭을 그대로 넘기고
(`OpenStepMGAMesaHook.c:124`), 검증기는 `dstPitch != 0` 과
`dstWidth <= dstPitch` 만 본다(`OpenStepMGAHW3D.c:132`). 배치는 **수락되고**
엉뚱한 자리에 그린다 — 거절이라도 되면 revoke 로 소프트웨어에 떨어질 텐데
그러지도 않는다.

## 2. 어떤 너비가 걸리나 (python)

익숙한 너비 대부분은 통과한다: 160, 256, 320, 352, 384, 480, 512, 640,
768, 800, 1024, 1152, 1280, 1600, 1920.

**걸리는 것: 240, 400, 720.** 흔치 않은 것은 아니다.

## 3. 두 갈래

| 안 | 내용 | 얻는 것 | 잃는 것 |
| --- | --- | --- | --- |
| **(A) 거절** | 보폭이 32 의 배수가 아니면 가속하지 않는다 | 작고 확실하다 | 240/400/720 등에서 가속이 없다 |
| (B) 패딩 | 색 표면의 보폭을 32 로 올린다 | 모든 너비에서 가속 | 아래 문제 |

### (B) 가 지금 안 되는 이유

깊이 공유가 막는다. 커널은 깊이 보폭을 **색 pitch 에서 유도한다**
(`zstride = (pitchBytes/4) * DEPTH_BYTES`). 그런데 Mesa 3.4 의 소프트웨어
깊이는 `DepthBuffer + Width*y + x` 로 **너비 보폭을 가정한다** — 그래서
`OpenStepMesaAccelDepthBuffer` 가 `bufStride != bufWidth` 면 거절한다.

보폭을 패딩하면 색은 괜찮지만(Mesa 는 색에 row length 를 쓴다) **깊이는
어긋난다.** 둘을 떼려면 계약에 깊이 pitch 를 따로 넣어야 하고, 그건 이
회차의 크기가 아니다.

**그러므로 이번에는 (A) 를 한다.** 패딩이 위험해서가 아니다 — **색만
놓고 보면 패딩은 안전하다.** Mesa 는 색에 row length 를 쓰고, 커널은
클라이언트가 준 pitch 를 그대로 쓴다. 막는 것은 **깊이 공유 하나**이고,
그것 때문에 깊이를 쓰는 장면이 소프트웨어로 갈 뿐 틀리게 그려지지는
않는다. (B) 는 `REMAINING_WORK` 에 **색 전용 최적화**로 세우고, 완전한
하드웨어 깊이까지 가려면 계약에 깊이 pitch 를 따로 넣어야 한다는 것을
함께 적는다.

## 4. 어디를 고치나 — 두 군데, 이유가 다르다

### (a) 선택기가 미리 거절한다 (`mesa/OpenStepMGAMesaHook.c`)

```
보폭 % 32 != 0  ->  NULL 을 돌려 소프트웨어로 보낸다
```

**여기가 먼저인 이유**: 커널만 막으면 첫 삼각형이 제출됐다가 거절되고,
`hookDeclined++` 와 **revoke** 가 걸려 그 프로세스의 가속이 통째로 꺼진다.
그 삼각형은 이미 잃은 것이다(주석에 그렇게 적혀 있다). 선택기가 미리
거절하면 **아무것도 잃지 않고** 소프트웨어로 간다.

### (b) 검증기가 거절한다 (`hw3d/OpenStepMGAHW3D.c`)

```
dstPitch % 32 != 0  ->  E_DSTPITCH
```

**여기도 막는 이유**: 검증기는 Mesa 만을 위한 것이 아니다. 날 클라이언트도
같은 ioctl 로 들어오고, 커널이 하드웨어가 못 지키는 값을 받아 그리면
**커널이 창 밖을 건드릴 수도 있다** — 지금 도달 검사는 `pitchBytes` 로
계산하는데, 하드웨어가 다른 pitch 로 걷는다면 그 계산이 보증하는 것이
없다. 새 오류 코드는 만들지 않고 기존 `E_DSTPITCH` 를 쓴다.

**상수는 한 곳에 둔다** — 계약 헤더에 `OSMGA_HW3D_PITCH_ALIGN 32` 로 놓고
양쪽이 그것을 본다. 두 군데에 32 를 적으면 언젠가 갈린다.

## 4b. 상수를 화소로 쓸 것인가 바이트로 쓸 것인가 — 화소다

참조 표를 바이트로 환산해 보면 상수가 아니다:

| 바이트/화소 | 화소 | 바이트 |
| --- | --- | --- |
| 1 | 64 | 64 |
| 2 | 32 | 64 |
| 3 | 64 | 192 |
| **4** | **32** | **128** |

그리고 **바이트 규칙으로는 측정을 설명하지 못한다.** 네 값의 최대공약수는
64 바이트인데, 무너진 336 화소는 `336 × 4 = 1344` 바이트로 **64 의
배수다.** 그러니 규칙은 화소 단위이고 심도마다 다르다 — 참조 표 그대로다.

우리 3D 경로는 **4 바이트/화소로 고정**돼 있다(`runHW3DSubmit` 이
`f3->bytesPerPixel != 4` 면 `IO_R_RESOURCE` 를 돌려준다). 그러므로 이
경로에서 32 화소는 정확하다. 상수 옆에 **심도별 값이라는 것과, 이 문이
4 바이트/화소만 통과시킨다는 것**을 함께 적는다.

## 4c. 검증기를 막으면 지금 도는 것이 깨지는가 — 안 깨진다 (확인함)

검증기는 드라이버 안에서 **네 곳**이 부른다: `runHW3DSubmit` 과 MMIO 쪽
세 곳. 뒤 세 곳은 `lim.pitchBytes = di->rowBytes` 를 쓴다.

```c
/* OpenStepMGAReplacementDisplay.m:2039 */
displayInfo->rowBytes = r->width * f->bytesPerPixel;
```

즉 `rowBytes / 4 == width` 다. 그리고 이 드라이버가 내놓는 너비는
**640, 800, 1024, 1280, 1600** — **다섯**이고 python 으로 확인하니 전부
32 의 배수다. 그러므로 새 검사는 드라이버 자신의 호출자를 하나도 막지 않는다.

(처음에 "넷"이라고 적었다. `1600x1200` 을 빠뜨렸다 — 결론은 그대로지만
하나 틀린 셈은 세지 않은 셈이다. codex 가 잡았다.)

## 4d. codex 교차검토 — 재검증 결과

**소스에서 확인해 받아들인 것**

1. **모드는 다섯이다** (위). 내 셈이 하나 틀렸다.
2. **검증이 "revoke 가 안 걸렸다"를 증명하지 못한다.** `zagree` 는
   `hookDrawn` 만 본다. 첫 제출이 거절돼 revoke 가 걸려도 뒤 패스는
   똑같이 "가속 안 됨"으로 보인다. `OSMGAMesaHookDeclined()` 는 **이미
   내보내져 있다**(`OpenStepMGAMesaHook.h:41`) — 시험이 안 쓸 뿐이다.
   거절된 너비마다 그 증분이 **0** 이어야 한다.
3. **계약 시험이 하나로는 모자란다.** 두 개가 필요하다:
   - `dstWidth=64, dstPitch=1023` → `E_DSTPITCH` — 술어가 **pitch** 이지
     너비가 아님을 보인다.
   - `dstWidth=333, dstPitch=352` → **수락** — 실수로 `dstWidth % 32` 를
     강제하지 않았음을 보인다. 이쪽이 더 중요하다: 아래의 모든 계산
     (색 도달, 깊이 도달, `MGA_PITCH`, `YBOT`)을 모는 것은 pitch 다.
4. **버퍼 생성 시점에도 거절한다.** 선택기만 막으면, 가속을 절대 못 쓸
   표면을 VRAM 에 잡아 두고 소프트웨어가 거기 그린 뒤 **매 프레임 통째로
   미러**한다 — 평범한 소프트웨어보다 느리다. 생성에서 거절하면 OSMesa 가
   애플리케이션 버퍼를 그대로 쓴다.
   → 세 겹이 된다: **생성 / 선택기 / 검증기.**
5. **`E_DSTPITCH` 주석에 "정렬 안 됨"을 넣는다.**

**고쳐서 받아들인 것**

- codex 는 패딩을 미루는 내 근거가 "Mesa 와 커널이 다른 주소를 계산한다"
  라고 읽고 반박했다. **계획은 그렇게 말하지 않았다** — 색은 Mesa 가
  row length 를 쓰므로 괜찮고 **깊이**가 어긋난다고 적었다. 다만 codex 의
  다듬음은 받는다: 패딩은 **색 전용 최적화로는 안전**하고, 막는 것은 깊이
  공유뿐이다. 그렇게 다시 적는다.

## 5. 안 하는 것

- **보폭을 몰래 바꾸지 않는다.** 클라이언트가 준 보폭을 드라이버가 조용히
  올리면, 클라이언트가 계산한 주소와 커널이 그리는 주소가 갈린다.
- **원인을 새로 주장하지 않는다.** 32 는 원본이 말하는 값이고, 왜 32 인지는
  이 저장소가 답할 것이 아니다.
- **모드 설정 경로는 안 건드린다.** 디스플레이 보폭은 이미 하드웨어가 정한
  것을 쓴다.

## 6. 검증 (재부팅 1 회 — 검증기가 커널 안에 있다)

1. `zagree` 를 32 의 배수인 너비(320, 352, 640, 800)에서 돌린다 —
   **전과 같아야 한다**(커버리지 98~100%, worst 2).
2. 32 의 배수가 아닌 너비(322, 324, 328, 333, 336, 369, 655)에서 돌린다 —
   이제 **가속이 아예 안 걸려야** 한다(`pass1=0`). 커버리지 불일치는
   0 이어야 한다: 양쪽 다 소프트웨어이므로 같은 그림이다.
3. **`OSMGAMesaHookDeclined()` 의 증분이 0 이어야 한다** — 거절된 너비마다.
   이것 없이는 "선택기가 미리 막았다"와 "제출했다가 거절돼 revoke 됐다"를
   구분할 수 없다. 함수는 이미 있고 시험이 부르기만 하면 된다.
4. **계약 시험 두 개**, 날 클라이언트로 직접:
   - `dstWidth=64, dstPitch=1023` → `E_DSTPITCH` (술어가 pitch 다)
   - `dstWidth=333, dstPitch=352` → **수락** (너비에 32 를 강제하지 않았다)
5. 생성 시점 거절이 들었는지 — 걸리는 너비에서 `OSMGAMesaBufferOrigin()` 이
   0 이어야 한다. 그러면 VRAM 표면을 잡지도, 매 프레임 미러하지도 않는다.

검증.

## 8. 결과 — 유저랜드 쪽 (2026-08-21, 재부팅 전)

### 검증기 (호스트/타깃 단위 시험, 재부팅 불필요)

```
ok    a pitch that is not a multiple of 32 pixels    16
ok    an unaligned width inside an aligned pitch      0
```

기존 사례도 전부 통과한다(`all cases behave as specified (0 failing)`).
두 번째 줄이 중요하다 — **너비에 32 를 강제하지 않았다.** 333 화소짜리
그림이 352 화소 pitch 안에 있는 것은 정상이고, 아래의 모든 계산을 모는
것은 pitch 다.

### Mesa 쪽

| 너비 | 결과 | 거절 횟수 |
| --- | --- | --- |
| 320, 640, 352 | **전과 완전히 같다** (커버리지 100%/100%/98%, worst 2) | 0 |
| 333, 336, 655, 369 | `surface origin 0 — refused at creation` | **0** |

**거절이 0 이라는 것이 핵심이다.** 선택기나 커널이 나중에 막았다면
`hookDeclined` 가 올랐을 것이고, 그러면 삼각형 하나를 잃고 그 프로세스의
가속이 통째로 꺼졌을 것이다. **생성에서 막았으므로 아무것도 제출되지
않았고 아무것도 잃지 않았다.** 표면을 VRAM 에 잡지도, 매 프레임 미러하지도
않는다.

`OSMGAMesaHookDeclined()` 를 시험이 부르게 한 덕분에 이것을 구분할 수 있다
— 그 전에는 "선택기가 미리 막음"과 "제출 후 거절되어 revoke" 가 똑같이
보였다.

### 남은 것

커널의 검증기 backstop 은 설치했고 **재부팅 뒤에 확인한다.** 날
클라이언트가 정렬 안 된 pitch 를 직접 제출했을 때 `E_DSTPITCH` 가 나오는지.


## 9. 커널 backstop 검증 (2026-08-21, 재부팅 뒤)

설치 21:32, 부팅 11:26:36, 321904 바이트.

라이브러리를 우회하는 날 클라이언트가 `dstPitch` 를 직접 골라 제출한다:

| pitch | 32 배수 | 디스플레이 보폭 이하 | 결과 |
| --- | --- | --- | --- |
| 1024 | 예 | 예 | 그린다, 40 중 0 |
| **992** (32×31) | **예** | **예** | **수락** |
| **1023** | **아니오** | **예** | **거절, verdict 16 = `E_DSTPITCH`** |
| 1056 (32×33) | 예 | **아니오** | 거절, verdict 16 |

**992 대 1023 이 새 검사를 가리는 쌍이다** — 너비도 같고 둘 다 보폭 아래라
다른 조건이 걸릴 여지가 없다.

`1056` 은 제가 잘못 고른 것이다. 드라이버에는 **pitch 가 디스플레이 보폭을
넘을 수 없다**는 기존 규칙이 있고 주석에 이유까지 적혀 있다(그 폭이 레지스터
에서 이미 통한다고 알려진 값이다). 정렬은 맞았지만 그 규칙에 걸렸다.

`992` 에서 시험이 `40 of 40 runs short` 를 찍는데, 그건 클라이언트가 여전히
1024 보폭으로 색인하기 때문이다 — 엔진이 992 로 걸었다면 당연한 결과이고,
**틀렸다는 증거도 맞다는 증거도 아니다.** 여기서 필요한 것은 "거절되지
않았다" 하나였고 그것은 확인됐다. 제대로 된 양성 시험(요청한 pitch 로
색인해 그려진 자리를 확인하는 것)은 `REMAINING_WORK` 로 세운다.
