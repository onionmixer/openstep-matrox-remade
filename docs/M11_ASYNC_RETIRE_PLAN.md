# M11 — 비동기 제출: 지연 은퇴 계획 (2026-08-31, 코딩 전)

## 0. 목표와 경계

레벨 프레임 153 ms 중 제출이 66.4 ms(155회 × 429 µs)다.  제출 ioctl 은
배치마다 엔진이 **완전히 배수될 때까지** CPU 를 세운다.  이 계획은 그 배수
대기를 **다음 엔진 접촉 시점으로 미뤄** CPU(Mesa T&L, 86.6 ms)와 엔진
rasterisation 을 겹치게 한다.

**넣지 않는 것**: 인터럽트 완료 통지(폴링 유지), SECADDRESS/2차 DMA(금지
승계 — 7f8d58a §7.1), v9 사다리꼴 경로 변경, 2D 경로 변경, 링 구조 변경.

## 1. 확인된 사실 (전부 열어서 확인)

### 1-1. 현 v10 제출은 세 단계 전부 동기다 (`.m:11176-11506`)

```
stormBusy 클레임 -> 스냅샷 복사 -> 검증 -> 인코딩       (CPU, 동기 유지 대상)
osmgaStormWaitIdle -> warp_init 6 MMIO + WMISC 확인      (.m:11362-11380)
런마다:  GENERAL 발사 -> 포인터+SOFTRAPEN+ENDPRDMASTS 스핀 -> ICLEAR
         VERTEX 발사  -> 포인터 도달 스핀                 (.m:11430-11480)
배치 끝: osmgaWarpFenceAndStop                            (.m:11483)
         = DWGSYNC 태그 -> 태그 도달 스핀
           -> WIADDR2=SUSPEND -> WBUSY|WBUSY1|DWGENGSTS 전부 0 스핀
                                                          (.m:11107-11147)
stormBusy 해제 -> 반환
```

- 런 중간 대기는 **DMA 소비** 대기다(T9: 포인터 도달 시 `DWGENGSTS=1` —
  그리기는 아직 진행 중인데 다음 상태 목록을 내도 깊이가 새지 않았다,
  M7 §9.5).  끝의 FenceAndStop 만이 **rasterisation 완료** 대기다.
- 실측 429 µs/제출은 v9 모형(85.4 µs 고정 + 132.4 ns/dword, 497 dw → 151 µs)
  의 ~2.8배 — 차액 ~278 µs 의 소재는 **미계측**이다(배수 대기 + warp_init +
  StormWaitIdle + per-run 스핀).  → Phase 0 이 잰다.

### 1-2. 참조는 배수를 기다리지 않는다

- DRM: `prim.tail` 스탬프 + `PRIMADDRESS` 추월 확인으로 버퍼 재사용.  대기·
  idle 확인·2차 상태 폴링이 **없다**(커밋 1b49954 — 자기 클립 루프가 증명).
- DRM 의 WARP suspend 는 primary 스트림 안에서 파이프 전환 시에만,
  Windows 드라이버는 MMIO suspend 를 **아예 안 한다**(f1fa010).
- 우리의 배치 끝 SUSPEND+배수는 프로브 계보(정지 상태 판독용)에서 왔다 —
  생산 경로에서 매 배치 필요하다는 실증은 없다.  단 **warp_init(WIADDR2 재설정
  포함)를 배치마다 하는 현 구조에서는 init 전에 파이프가 서 있어야 한다** —
  그래서 "빼기"가 아니라 "미루기"다.

### 1-3. 은퇴를 요구하는 접촉 지점 (전수)

**커널** — `stormBusy` 클레임 지점 전부(2D blit `.m:5507`, 채우기, v9 제출,
present/미러 ioctl, 셀프테스트).  클레임 성공 직후가 은퇴 자리다.

**유저랜드** — CPU 가 엔진의 목적지·소스를 만지는 곳:
- 텍스처 업로드: `Texture.c:245-256` 이 이미 초크포인트다 — 배치가 참조할
  수 있는 영역에 쓰기 전에 `OSMGAMesaHookFlushPending()` 을 부른다.
  비동기화 후에는 flush 가 "제출"이지 "완료"가 아니므로 여기에 은퇴가 붙는다.
- 미러 복사(비 present 모드): `Buffer.c` Mirror/MirrorNarrow 가 표면을 읽는다.
- 소프트웨어 span/line 재생: 표면에 CPU 로 쓴다.
- glReadPixels, 표면 unbind, 컨텍스트 파괴.

**present 모드(= glquake)에서는 미러가 꺼져 있다**(`Buffer.c:481,547,571`).
남는 유저랜드 은퇴는 텍스처 업로드(1.35회/프레임 실측)와 소프트 재생(정상
0회)뿐 — **이득은 present 모드에서만 온전하다.**  OSMesa 미러 모드는 bracket
마다 표면을 읽으므로 매 배치 은퇴가 강제되고 이득이 없다.  그래도 옳아야
한다(은퇴가 있으므로 옳다, 빨라지지 않을 뿐).

### 1-4. 제약 (금지 대조 완료)

- ioctl 문맥에서 IOSleep = 머신 정지(`.m:951`, 2026-07-20 실증) → 은퇴도
  bounded spin 이어야 한다.
- 타임아웃 = `stormBlitFailed` 래치(락 안에서) 후 `stormBusy` 해제, 재생
  없음, 링·마이크로코드 유지 (M6 §6/§11.1).  이 정책은 그대로다.
- 검증·인코딩은 동기 유지 — verdict 는 지금처럼 ioctl 반환값에 실린다.
  비동기화되는 것은 **성공 경로의 완료**뿐이다.
- 클레임은 refuse-rather-than-wait(`.m:5507`) — 은퇴 스핀은 클레임을 잡은
  쪽이 한다(잡기 전 대기 금지 원칙과 충돌하지 않는다).

## 2. 설계 — 지연 은퇴

새 상태 하나: `osmgaWarpPending` (stormLock 아래에서만 읽고 쓴다).

```
runHW3DSubmitWarp 성공 경로:
  ... 마지막 런의 VERTEX 포인터 소비 확인까지 그대로 ...
  osmgaWarpPending = 1        <- FenceAndStop 을 하지 않는다
  stormBusy 해제, 반환

osmgaWarpRetire (내부 헬퍼, stormBusy 를 잡은 쪽이 부른다):
  if (!osmgaWarpPending) return 1;
  ok = osmgaWarpFenceAndStop(base, 호출처 라벨)
  osmgaWarpPending = 0
  if (!ok)  stormBlitFailed = YES  (현행 타임아웃 정책 그대로)
  return ok
```

**은퇴 호출 지점**:
1. v10 제출 진입 — `stormBusy` 클레임 직후, `osmgaStormWaitIdle`/warp_init 전.
   (다음 배치가 오기 전에 엔진이 이미 끝났으면 스핀 0 에 가깝다 — 이게 이득.)
2. 모든 `stormBusy` 클레임 지점 공통 — 클레임 성공 직후 `osmgaWarpRetire`.
   지점이 흩어져 있으므로 클레임을 헬퍼로 뽑거나, 각 지점에 한 줄씩.
3. 새 ioctl `OSMGA_IOC_RETIRE` — 유저랜드 접촉 지점용.  클레임→은퇴→해제만
   한다.  실패는 status 로 알린다(래치는 커널이 이미 걸었다).

**유저랜드**:
- 훅에 `hwPending` 플래그 — 제출 성공 시 세움, RETIRE 후 내림.
- RETIRE 를 부르는 곳: 텍스처 업로드 초크포인트(`FlushPending` 직후),
  Mirror/MirrorNarrow 진입, 소프트웨어 재생 직전(`osmgaMesaSoftly` 의 표면
  쓰기 전), ReadPixels 래퍼, unbind/파괴.  전부 이미 함수 하나씩으로 모여
  있는 자리다.
- 은퇴 실패(=래치)는 다음 제출이 ENODEV 로 돌아오며 기존 revoke 경로를 탄다.

**링 재사용 안전**: 다음 배치의 인코딩은 리스트/정점 영역을 재기록하지만,
이전 배치의 DMA 소비는 per-run 포인터 대기가 이미 보장했다(그 대기는 남긴다).
엔진이 소비 후에도 링을 다시 읽지 않는 것은 DRM aging 의 전제와 같고
D2-2f/T9 가 실증했다.  클라이언트 배치 영역은 스냅샷 복사라 무관.

**실패의 지연 발견**: 엔진 실행 실패는 은퇴 시점에 드러난다.  그 배치의
소스는 유저랜드 pendSrc 에서 이미 사라졌으므로 재생할 수 없다 — 그러나
현행 정책도 타임아웃은 "아래 층으로 재생하지 않는다"(M6 §6)이므로 **정책이
바뀌지 않는다**.  래치 후 모든 가속이 꺼지는 것도 동일하다.

## 3. 무엇이 겹쳐지고, 얼마나 (상한)

배수 대기 비중을 x ms/프레임이라 하면, 제출 사이 CPU 간격(평균 0.56 ms)이
엔진 배치 시간보다 길 때 x 전부가 사라진다.  x 는 미계측 — **Phase 0 이
잰 뒤에 Phase 1 을 결정한다.**  상한: 429-151 = 278 µs/제출 × 155 = 43 ms
(전부 배수 대기일 때).  하한: 0 (전부 warp_init/StormWaitIdle 일 때).

## 4. 단계 (재부팅 2회 예산)

**Phase 0 — 계측 (재부팅 1)**: `runHW3DSubmitWarp` 의 네 구간(StormWaitIdle,
warp_init, per-run 스핀 합, FenceAndStop 스핀)별 스핀 수를 정적 카운터에
누적하고 기존 파라미터 채널(OSMGAHW3DSites 방식)로 노출.  IODelay 나 시계를
넣지 않는다 — 스핀 수 × 폴 비용으로 충분하다(REMAINING_WORK 3-46 방식).
glquake 100프레임 → FenceAndStop 비중 판정.
- **중단 조건**: FenceAndStop 스핀 비중이 제출 시간의 ~15% 미만이면 Phase 1
  을 하지 않는다(수익 < 10 ms).

**Phase 1 — 지연 은퇴 (재부팅 1)**: §2 구현 + 프로브 행렬(M10 §8 형식):
```
1  v9 제출 (대조군)
2  v10 제출 -> 즉시 v10 제출     은퇴가 제출 진입에서 도는지 (연속 배치)
3  v10 제출 -> RETIRE ioctl      유저랜드 은퇴 경로
4  v10 제출 -> 2D blit           클레임 지점 은퇴
5  v10 제출 -> 되읽기 (RETIRE 뒤) 화소 정확성 1176/1176
6  v9 제출 (대조군)              v10 pending 이 v9 을 오염시키지 않는지
```
glquake 100프레임 ×2 (WARP): ms/프레임, 제출 us, 드랍·거절 0 확인.
시험은 각 60초 이내.

## 5. codex 에 묻는 것

1. per-run DMA 소비 대기(포인터 스핀)도 미룰 수 있는가 — 다음 발사 직전에
   이전 포인터 도달을 확인하는 형태(DRM 이 하는 방식).  아니면 GENERAL→VERTEX
   순서 보장 때문에 지금처럼 즉시 대기가 필요한가?
2. 은퇴 지점 전수(§1-3, §2)에 빠진 곳이 있는가?  특히 모드 변경·리셋·
   revertToVGAMode·화면 끄기 경로가 pending 중에 올 수 있는가?
3. `osmgaWarpPending`/`stormBusy` 의 동시성: 클레임-은퇴-해제 순서에 두
   클라이언트가 끼어들 구멍이 있는가?
4. 은퇴 실패의 유저랜드 통지(다음 ioctl ENODEV + 기존 revoke)로 충분한가,
   RETIRE ioctl 의 반환값에 무엇을 실어야 하나?
5. Phase 0 의 스핀 계측 설계가 배수 비중을 실제로 가르는가?  스핀 1회의
   비용이 구간마다 달라(레지스터 읽기 수) 왜곡될 여지는?
6. 미러(비 present) 모드에서 이득 0 이라는 판단이 맞는가?
7. present 모드에서 화면에 그리는 중 ioctl 이 반환되면, 윈도서버의 커서
   그리기 등 **드라이버를 거치지 않는** VRAM 접촉과 경합하는가?
   (커서는 HW 커서인가?)
8. 빠진 것.

## 6. 자체 확인 (codex 회신 전)

- **§5-7 커서**: HW 커서가 아니다.  IOFrameBufferDisplay 의 커서는 커널이
  CPU 로 백킹스토어↔프레임버퍼를 복사하는 소프트웨어 커서이고(`.m:5578-5583`),
  엔진 블릿과 같은 사각형에서 충돌할 수 있음이 이미 적혀 있다.  호출 문맥이
  인터럽트 레벨일 수 있어 락도 대기도 못 건다(`statCursorWhileBusy` 는 세기만
  한다).  **이 충돌은 오늘도 있다** — 동기 ioctl 이 도는 동안에도 커서 콜은
  도착한다.  비동기화는 노출 시간을 넓힐 뿐 새 종류의 충돌을 만들지 않는다.
  present 모드에서 게임 창 위에 커서가 있는 경우가 그 사각형이다.
- **present ioctl 은 stormBusy 를 클레임하고 StormWaitIdle 후 엔진 블릿을
  낸다**(`.m:6351-6420`) — §2 의 클레임 지점 은퇴로 덮인다.
- **revertToVGAMode 를 우회해 osmgaVgaRestore 를 직접 부르는 실패 경로**가
  있다(`.m:4644-4652`, PLL 미락) — 호출자가 이미 엔진을 클레임한 상태다.
  모드 진입은 pending 이 있을 수 없는 시점(부팅)이지만, 은퇴를 클레임 헬퍼에
  넣으면 자동으로 덮인다는 논거를 codex 에 확인시킨다.

### 판정: **짓지 않는다 (W5 §11 재확인).**

바뀐 것은 워크로드뿐이다(사다리꼴 21 ms 프레임 → WARP 153 ms 프레임, 제출
66 ms).  이득의 크기가 커졌어도 W5 가 센 구조적 봉쇄 — 직접 VRAM 매핑에
drain 을 끼울 수 없음, 소프트웨어 커서 충돌에 완화책 없음, 완료 주체 부재,
모드 강행 경로, 오류 귀속 8갈래 — 는 하나도 변하지 않았고, codex 의 10개
필수 변경은 동기화 모델과 ABI 의 재설계다.  일곱 번 언 기계에서 할 일이
아니다.
