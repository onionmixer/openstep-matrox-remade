## 2. 실측이 드러낸 진짜 문제

허용은 **좌표 단위 고정값 4096** 이다.  그런데 헤더 371 줄이 말하듯 한 텍셀은
`1 << (20 - log2(size))` 이라 **텍셀 수는 크기에 반비례**한다.  python:

```
 size      8     16     32     64    128    256    512   1024   2048
texels 0.031  0.062  0.125  0.250  0.500  1.000  2.000  4.000  8.000
 x측정     36     71    143    285    571   1142   2283   4566   9132
```

즉 같은 상수가 크기 8 에서는 1/32 텍셀이고 크기 2048 에서는 **8 텍셀**이다.
`TEX_MAX_DIM` 이 2048 이므로 2048 은 실재하는 경우다.

**내가 문서에 틀리게 적었다.** "모든 `q` 에서 정확히 1/4 텍셀"은 `q` 에 대해서만
참이다(python 재확인: `q` 가 8192 든 2^23 이든 좌표 -4096).  크기 축은 확인하지
않았고, 1/4 텍셀인 것은 **크기 64 에서만** 그렇다.  §51 이 쓸어본 크기도 64
하나뿐이다.

codex 가 앞서 "관측보다 지나치게 넓다"고 지적한 것과 **같은 결함**이, 내가 보지
않은 축에서 그대로 남아 있었다.

## 3. 이것이 실제로 해로운가 — 나눠서 봐야 한다

두 가지가 섞여 있어 분리한다.

**(가) 엔진이 그 좌표를 옳게 읽는가.**  엔진은 텍스처 크기와 무관하게 같은 좌표
숫자를 받는다.  §51 이 `-4096 … -16` 을 쓸어 클램프·repeat 모두 GL 과 일치함을
보였다.  따라서 **좌표 범위로서는** 이미 검증된 구간이다.  단 repeat 의 감김
결과는 크기에 따라 다른 텍셀 번호가 되고(크기 64 → 63, 크기 2048 → 2040 예측),
크기 2048 에서는 재보지 않았다.

**(나) 허용의 뜻이 크기마다 달라지는 것.**  허용은 "오차 예산"이 아니라
**"여기까지 재봤다"는 봉투**다.  봉투가 크기에 따라 256 배 달라지는 것은 근거가
크기 하나에서만 나왔기 때문이고, 이건 계량의 문제다.

## 4. 선택지 (python 표는 §2 와 같은 계산)

| | 크기 8 | 크기 64 | 크기 2048 | 새 미검증 구간 |
|---|---|---|---|---|
| **1** 지금 그대로 4096 | 1/32 텍셀 | 1/4 | **8 텍셀** | 없음 |
| **2** 텍셀/4 (크기별) | 1/4 (32768 단위) | 1/4 | 1/4 (128 단위) | **크기 8·16·32 에서 새로 넓어짐** |
| **2b** `min(텍셀/4, 4096)` | 1/32 | 1/4 | 1/4 | 없음 (항상 좁아지기만) |
| **3** 고정 128 단위 | **0.001 텍셀 = 측정치의 1배** | 0.008 | 1/4 | 없음 |

- **3 은 python 이 배제한다**: 크기 8 에서 측정된 이탈(0.000876 텍셀)의 1 배라,
  고치려던 삼각형을 다시 거절한다.
- **2 는 작은 크기에서 허용을 넓힌다** — 크기 8 에서 좌표 -32768 까지 통과하는데
  §51 은 -4096 까지만 쓸었다.  넓히려면 그 구간을 새로 쓸어야 한다.
- **2b 는 어느 크기에서도 넓어지지 않는다.**  뜻은 "1/4 텍셀, 단 실제로 쓸어본
  좌표 범위를 넘지 않는다".

## 5. 아직 재보지 않은 것

- 크기 2048 에서 음수 좌표의 repeat 감김이 2040 을 주는가 (예측일 뿐이다)
- 크기 8 에서 음수 좌표의 클램프·repeat (크기 64 에서만 쟀다)
- 이탈량이 텍스처 크기와 무관하게 텍셀 단위로 일정한지 —
  `이탈(단위) = 0.00135 화소 × 확대율 × SPAN/크기` 라는 유도는 화소 단위 변
  걷기 오차에서 나온 것이고, **측정은 크기 64 한 점뿐이다**

## 7. 교차검토가 내 유도를 뒤집었다

codex 가 짚은 것: 좌표는 **정규화**돼 있어(전체 텍스처 = 2^20, 크기 무관) 같은
사각형에 같은 텍스처를 입히면 `du/dx` 가 크기와 무관하다.  내 §5 유도는
`이탈 = 0.00135화소 × 확대율 × SPAN/크기` 였는데, `확대율 = 크기/화소폭` 이므로

```
   확대율 × SPAN/크기 = (크기/화소폭) × SPAN/크기 = SPAN/화소폭      크기가 약분된다
```

python 재확인: 크기 8·64·256·2048 어디서나 `du/dx = 4946 단위/화소`, 이탈
`6.68 단위`로 **동일**하고, 텍셀로 환산했을 때만 0.000051 … 0.013 으로 달라진다.

**따라서 불변량은 좌표 단위이고, 텍셀이 아니다.**  내 선택지 2·2b 는 틀린
불변량을 고치는 것이었다.  고정 좌표 단위(선택지 1)가 오히려 옳은 모양이다.

## 8. 그리고 실측이 "8 텍셀 문제"를 없앴다 (§52)

크기 64 는 한 텍셀이 16384 단위라 쓸기 값 전부가 **같은 텍셀 안**이다 — §51 은
감김 산술을 구별할 수 없었다.  크기 1024(텍셀 1024)와 2048(텍셀 512)에서는
쓸기가 텍셀 경계를 여러 번 넘는다.  폭은 pitch 필드(≤2047) 때문에 1024 가
한계이므로 8 텍셀 경우는 **v 축(높이 2048)** 으로 잡았다 — 그 사실 자체도
기계로 확인했다(`a 2048-wide texture cannot be described` 통과).

```
   8 wide u     clamp 0 0 0 0 0 0 0      repeat    7    7    7    7    7    7    7
   1024 wide u  clamp 0 0 0 0 0 0 0      repeat 1020 1021 1022 1023 1023 1023 1023
   2048 tall v  clamp 0 0 0 0 0 0 0      repeat 2040 2042 2044 2046 2047 2047 2047
```

python 이 모형과 맞췄다: **`floor(좌표/텍셀) mod 크기`** 가 네 크기 전부에서
관측과 일치하고, 이는 GL_REPEAT 의 정의 그대로다.  클램프는 모든 크기에서 0 —
GL_CLAMP 그대로다.

그러므로 크기 2048 에서 좌표가 **8 텍셀 아래**여도 엔진은 GL 이 규정한 텍셀을
준다.  "8 텍셀"은 결함이 아니라 **허용의 뜻을 텍셀로 환산한 값일 뿐**이다.

## 9. 결론 — 커널은 바꾸지 않는다

| 항목 | 판정 |
|---|---|
| 허용의 모양 (좌표 단위 고정) | **옳다** — 이탈의 불변량이 좌표 단위다 |
| 4096 이라는 크기 | **유지** — 네 크기에서 GL 일치가 실측됐다 |
| "1/4 텍셀"이라는 설명 | **틀렸다** — 크기 64 에서만 참. 문서를 고친다 |
| 선택지 2·2b (텍셀 비례) | **폐기** — 틀린 불변량 |
| 선택지 3 (고정 128) | **폐기** — python: 크기 8 에서 측정치의 1 배 |

허용은 "오차 예산"이 아니라 **"엔진이 GL 과 일치함을 여기까지 재봤다"는 봉투**다.
이 틀은 §52 로 뒷받침된다: 봉투 안에서는 엔진이 실제로 GL 이다.

**커널 변경 없음 → 재부팅 불필요.**  바뀌는 것은 탐침(§52 추가, 낡은 단언
뒤집기)과 문서뿐이다.

## 11. 유도된 상한(선택지 5)을 지금 쓰지 않는 이유

변 걷기는 누산기가 음수인 동안 `lx` 를 한 칸씩 옮기므로 정수 `x` 는 참 변에서
**1 화소 미만** 어긋난다.  따라서 이탈은 `|tmr[0]|`(u), `|tmr[2]|`(v) 로 **증명
가능하게** 묶인다 — 매직 넘버 없이.

그런데 이것을 쓰면 기울기가 작을 때 허용이 0 에 가까워져 음수 좌표를 **거절**한다.
§52 가 보인 대로 그 좌표들은 엔진이 GL 대로 그린다.  즉 **옳게 그려질 것을 막는**
쪽으로의 조임이고, 얻는 정확성은 없다.  유도된 상한은 "허용이 잘못된 것을
들여보낸다"는 증거가 나왔을 때 꺼낼 카드로 남긴다.

## 12. 이 측정이 실제로 여는 것

§52 는 곁가지로 더 큰 것을 보였다: 엔진의 클램프·repeat 이 음수 구간에서
**GL 그 자체**다.  지금 허용이 -4096 에서 끊기는 것은 하드웨어 한계가 아니라
**쓸어본 범위의 한계**다.  `glTexCoord2f(-1.0, 2.0)` 같은 평범한 타일링이 아직
소프트웨어로 가는데, 이는 별도 항목으로 세울 값어치가 있다.

## 13. 2 라운드 — 확인이 아니라 반증을 돌렸다

codex 2 라운드는 "일곱 점은 쓸기가 아니다", "선형 필터의 음수 위상은 재본 적이
없다", "확인 말고 반증을 설계하라"였다.  모두 타당해서 그대로 했다.

### 13-1 §53 경계 걷기 — 모형이 견뎠다

한 텍셀이 512 단위인 2048 높이에서 `p = -530 … -508` 을 **한 단위씩** 걸었다.

```
   2046 2046 2046 2047 2047 ... 2047        계단은 p = -527 에 한 번뿐
```

python 이 전체 23 개 값을 재현하는 편향을 찾았더니 **+15 하나뿐**이었고, 이는
산술 예측(엔진 +511, 커널 −496)과 정확히 같다.  계단이 다른 자리였거나, 둘
이상이었거나, 없었다면 모형이 죽었다.  §51·§52 는 값들이 경계에서 멀어 편향을
가릴 수 없었는데 — 그 사실도 여기서야 분명해졌다.

곁가지로, **절단(truncate toward zero) 모형은 §52 가 이미 죽였다**: `p = -16`
에서 절단은 텍셀 0 을 요구하는데 관측은 2047 이었다.

### 13-2 §54 주기성 — 일곱 경계 전부

```
   p=-528  2046 / p=-527  2047        p=-2064 2043 / p=-2063 2044
   p=-1040 2045 / p=-1039 2046        p=-2576 2042 / p=-2575 2043
   p=-1552 2044 / p=-1551 2045        p=-3088 2041 / p=-3087 2042
                                      p=-3600 2040 / p=-3599 2041
```

허용 안에 들어가는 일곱 경계 전부가 512 단위마다 **같은 위상**으로 되풀이된다.

### 13-3 §55 선형 필터의 음수 이음매 — 새 결함 아님

허용은 필터를 보지 않으므로 **BILIN + REPEAT + 음수**가 통과하는데, 이 조합은
재본 적이 없었다.  마지막 행에만 빨강을 넣어 되돌아온 빨강이 곧 그 행의
가중치가 되게 했다.

```
   p -800 … -270 (32 단위 간격)
     0   6  22  38  54  70  86 102 118 134 150 166 182 198 214 230 246
```

python 이 GL 의 straddle 규칙(`위치 − 0.5` 를 사이에 두는 두 탭)과 맞췄다:
정확한 `a·b/255` 기준 잔차 1.5 레벨, 엔진의 알려진 곱셈 형태
`(a·(b+1))>>8` 기준 **최대 1 레벨**.  이는 이미 기록해 둔 "선형 가중치 반올림은
항상 한 단계" 와 **같은 차이**이고 음수 때문에 생긴 것이 아니다.

## 14. 표현을 고친다

§51 은 **일곱 표본**이지 구간 전수가 아니다.  구간을 실제로 한 단위씩 걸은 것은
§53(23 단위)이고, 경계만 훑은 것은 §54(일곱 곳)이다.  M1-4D2 §9-3 의 "그 폭
전체를 쓸어"도 같은 과장이라 함께 고친다.

정확한 문장은 이것이다:

> **−4096 은 좌표 단위의 보수적 봉투다.**  이 안에서 시험한 좌표·모드에 대해
> 실기가 GL 과 같은 주소지정을 돌려주었다.  하드웨어 한계도 아니고, 변 걷기
> 오차 예산도 아니다.

## 15. 남긴 것

- **작은 `q` 에서의 음수 경계.**  `Q_MIN` 근처에서 분모가 작을 때 나눗셈의 기록된
  잔차가 경계를 한 텍셀 옮길 수 있다.  §53 은 아핀(`q = 65536`)에서만 걸었다.
- **빌더 쪽 기울기 진단.**  `|tmr[0]|`(u)·`|tmr[2]|`(v) 를 넘는 음수 시작은 변
  걷기가 만들 수 없으므로 빌더 버그다.  커널을 조이지 않고 빌더에서 알린다.
- **진짜 음수 텍스처 좌표.**  §52·§53·§55 가 보인 것은 엔진의 클램프·repeat 이
  음수 구간에서 GL 그 자체라는 것이다.  `glTexCoord2f(-1, 2)` 같은 평범한 타일링이
  아직 소프트웨어로 가는 이유는 하드웨어가 아니라 **봉투의 폭**뿐이다.
