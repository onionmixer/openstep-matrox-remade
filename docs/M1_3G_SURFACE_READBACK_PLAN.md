# M1-3g: 그려진 표면을 클라이언트에게 돌려주는 방법

**상태**: 계획. 코드는 한 갈래가 빌드까지 됐으나 **설치하지 않았다** — 이
문서의 검토가 끝나기 전에는 아무것도 고정되지 않는다.

## 1. 무엇이 문제인가 (측정됨)

클라이언트가 VRAM을 **믿고 읽을 수 없다.**

| 관측 | 값 |
| --- | --- |
| 제출 직후 첫 읽기 | 그리기 **이전** 값 |
| 이웃 낱말을 먼저 읽음 | 그것도 낡았다가, 잠시 뒤엔 정확 |
| 뒤에서부터 검사 | 낡은 것 0개 |
| 드라이버가 **캐시 없이** 같은 물리 메모리를 먼저 읽음 | **효과 없음** (4095/4096) |
| 클라이언트가 아무 데나 한 번 읽음 | 효과 있음 (4096/4096) |

**커널 쪽 캐시 없는 읽기가 효과가 없다**는 것은 "커널이 한 번 읽어주면
모두에게 풀린다"만 배제한다. 내가 거기서 "그러므로 클라이언트 매핑이
캐시되어 낡은 줄을 쥔다"로 간 것은 **너무 멀리 간 것이었다.**

### 그리고 그 결론은 같은 기계의 기존 측정과 모순된다

`S4A_VRAM_MMAP_PLAN.md §9-1`의 stale-cache 게이트는 **캐시를 의도적으로
오염시킨 뒤** 확인했다:

```
OSMGA_VRAM_CACHE  row0 before=a5000000 after=5aa55aa5 -> COHERENT
OSMGA_VRAM_CACHE  row1 before=a5000400 after=5aa55aa5 -> COHERENT
```

유저스페이스가 옛 값을 읽어 캐시에 올린 뒤 엔진이 같은 VRAM을 덮어썼고,
다시 읽으니 **새 값이 보였다.** **유저 매핑은 엔진 쓰기와 일관하다**가
이미 실증돼 있었다.

**그 시험과 지금의 차이는 매핑이 아니라 경로다**: 그때는 MMIO로 몰던
2D 블릿, 지금은 **M1 primary DMA**. 그러므로 의심해야 할 곳은 매핑이
아니라 **완료 판정**이다 — `ENDPRDMASTS`는 명령 스트림을 다 **읽었다**는
뜻이지 그 쓰기가 **도착했다**는 뜻이 아닐 수 있다.

`S4A_VRAM_MMAP_PLAN.md §7-1`이 이미 차단 요건으로 적어뒀다: `d_mmap`이
PFN을 돌려주는 이 경로에는 **uncached나 write-combining을 요청할 공개
수단이 없다**. 헤더를 다시 뒤져도 없다.

**왜 지금 중요한가**: M1 되비추기가 VRAM을 읽는다. 지금 맞는 것은 표면
전체를 복사하느라 캐시 줄이 밀려나기 때문일 뿐이고(§3-12, §3-13의 dirty
사각형으로 좁히는 순간 사라진다), **보장이 아니다.**

## 1-b. 그래서 진짜 질문이 바뀌었다

**"클라이언트가 VRAM을 읽을 수 있는가"가 아니라, "M1의 완료 판정이 쓰기가
도착했음을 뜻하는가"이다.** 후자가 아니라면 고칠 곳은 완료 판정이지
읽는 쪽이 아니다.

## 2. 선택지

### (가) 커널이 복사해 준다 — ioctl

드라이버가 창을 **캐시 없이 한 번 별칭 매핑**해 두고, ioctl 하나가
`copyout`으로 행마다 옮긴다.

- **장점**: 클라이언트가 VRAM을 아예 안 읽는다. 커널은 캐시 없는 별칭을
  만들 수 있다는 것이 이미 실증됨(`osmgaMapUncachedBlock`, H1 S2).
- **단점**: 프레임마다 커널 진입 + 복사. `copyout`이 유저 주소를 받는
  새 표면(검증 필요).
- **미검증**: 캐시 없는 별칭 읽기가 **실제로** 정확한 값을 주는가.
  §1의 표는 커널 읽기가 *클라이언트를 위해* 소용없다는 것만 보였지,
  커널이 읽은 값이 옳은지는 재지 않았다. **이것을 먼저 재야 한다.**

### (나) 유저 매핑을 캐시 없이 얻는 다른 경로

- **장점**: 되면 가장 싸다 — 복사가 아예 없다.
- **단점**: `d_mmap`에 수단이 없다(계획서·헤더 확인). `IODisplay`의
  `IO_DISPLAY_CACHE_*`는 프레임버퍼 매핑용이고 이 경로에 자동 적용되지
  않는다.
- **미검증**: `d_mmap`이 돌려주는 PFN의 상위 비트가 캐시 속성으로
  해석되는 커널 구현이 있는지. **아직 안 봤다.**

### (다) 클라이언트가 읽기 전에 캐시를 무효화한다

- **단점**: 유저스페이스에 일반적인 캐시 플러시 API가 없다(계획서 §7-1).
- 사실상 불가.

### (라) 지금처럼 두고, 되비추기를 좁히지 않는다

- **장점**: 코드 변경 0.
- **단점**: **우연에 기댄다.** 표면이 작아지거나 dirty 사각형을 넣는 순간
  깨지고, 깨지는 방식이 "가끔 픽셀 하나"라 가장 찾기 어렵다.

## 3. 정해야 할 것

1. **(가)를 하기 전에**: 커널이 캐시 없는 별칭으로 읽은 값이 정확한가?
   재지 않았다. 이것이 아니면 (가) 전체가 무의미하다.
2. **(나)를 배제하기 전에**: PFN 상위 비트 관례가 이 커널에 있는가?
3. (가)라면 복사를 **언제** 하는가 — 제출 끝에 자동으로? 별도 ioctl로?
   Mesa 훅은 `RenderFinish`에서 되비추므로 별도 호출이 자연스럽다.
4. (가)라면 엔진이 같은 메모리에 그리는 중일 수 있다 — `stormBusy`를
   잡아야 하는가?

## 4. 아직 하지 않은 것

- 1번 측정. **이것이 다음 작업이다.**
- 2번 조사.

## 5. 검토 결과 반영 (2026-08-21)

계획을 검토에 보냈고, **선택지가 아니라 전제가 틀렸다**는 답을 받았다.
트리에서 확인했고 맞았다(§1-b).

- **(나)는 닫혔다.** 이 트리의 커널 재구성이 보여주듯 `_smmap`은
  `physical_address = callback_return << page_shift`만 하고 플래그를
  뽑지 않는다. PFN에 비트를 넣으면 **캐시 속성이 아니라 물리 주소 비트가
  된다** — 위험하기만 하다.
- **(가)의 코드는 설치하지 않고 걷어냈다.** 기대던 전제가 흔들렸다.
- **(가)를 언젠가 하더라도 `stormBusy`를 잡아야 한다** — 지금 짰던 것은
  안 잡았다. 그리고 `copyout`은 폴트·수면할 수 있으므로 스핀락을 들고
  건너면 안 된다.
- **새 선택지 하나**: 목적이 화면에 올리는 것이라면 VRAM에 둔 채 **엔진으로
  블릿**하면 CPU 읽기가 아예 없어진다. M2에서 다시 볼 것.

## 6. 다음 작업 — 가장 작은 결정적 실험

**복사 ioctl을 짓지 않는다.** 대신 제출 경로에 **진단만** 넣는다:

1. 결과를 독립적으로 아는 고정 배치를 그린다.
2. 완료 판정 직후, 반환 전에 **캐시 없는 별칭으로** 몇 낱말을 읽는다 —
   그린 자리 하나와 안 그린 자리 하나.
3. 그 값을 상태 워드로 돌려준다. **이 실험에서 클라이언트는 VRAM을 읽지
   않는다.**
4. 미리 계산한 기대값과 대조한다.

그러면 "별칭이 그 시점에 M1 결과를 보는가"가 답해진다 — 지금까지 잰 것은
"별칭 읽기가 남의 매핑을 고쳐주는가"뿐이었다.


## 7. 답 (2026-08-21) — **읽기가 아니라 쓰기였고, 뒤가 아니라 앞이었다**

계획대로 진단만 넣고 쟀다. 커널이 완료 판정 직후 캐시 없는 별칭으로 본 값:

```
#1 forward pass                          -> 40          (그린 값)
#2 same batch again, over fresh sentinels -> 5a5a5a5a   (미청소값)
#3 reversed pass                          -> 3f0040     (그린 값)
#4 a bounds case                          -> c86432     (그린 값)
```

**#1과 #3은 완료 시점에 그린 값이 보인다 — 완료 판정은 건전하다.**
#2만 커널조차 미청소값을 본다. 클라이언트가 4095를 보는 것이 바로 #2다.

이어서 두 실험:

| 실험 | 결과 | 뜻 |
| --- | --- | --- |
| 제출 후 (0,0)을 다섯 번 연속 읽음 | 전부 `5a5a5a5a` | **늦은 게 아니라 잃었다** |
| 제출 **전에** 그 영역을 한 번 읽음 | `00000040` ×5, **4096/4096** | **원인은 이것** |

### 그래서 원인은

**클라이언트 자신의 VRAM 쓰기가 아직 도착하지 않은 채 엔진이 그리고,
그 쓰기가 나중에 착지해 그려진 값을 덮는다.**

내가 처음 세운 방향과 **정반대**다: 늦는 것은 엔진의 쓰기가 아니라
**클라이언트의 쓰기**이고, 문제가 생기는 지점은 제출 **뒤**가 아니라
**앞**이다.

**write-combining이 이 그림에 정확히 맞는다**: WC 버퍼는 **그 CPU의
읽기**로 배출되지 다른 주체의 읽기로는 안 된다. 그래서
- 클라이언트가 제출 전에 읽으면 고쳐지고,
- 드라이버가 캐시 없는 별칭으로 읽어줘도 소용없었고,
- S4a의 일관성 게이트는 통과했다 — 그 시험은 엔진이 그리기 **전에**
  `before=` 값을 읽었고, 그 읽기가 버퍼를 배출시켰다.

### 다음 — 계획부터

고칠 자리는 **제출 경로의 앞**이다. ioctl은 **클라이언트 스레드에서**
실행되므로, 드라이버가 거기서 목적지를 한 번 읽으면 **같은 CPU의 읽기**가
되어 WC 버퍼를 배출시킬 수 있다. **이것은 가설이고, 다음 작업은 그것을
재는 것이다** — 클라이언트에서 읽기를 빼고 드라이버가 대신 읽었을 때
4096이 나오는지.

`§6`의 진단은 목적을 다했으니 그때 같이 정리한다.

# M1-3h: 클라이언트의 쓰기를 제출 앞에서 배출시키기

**상태**: 계획. 코드 없음. **검토 전에는 아무것도 고치지 않는다.**

## 1. 가설

`§7`에서 확정된 것: 클라이언트의 VRAM 쓰기가 아직 도착하지 않은 채 엔진이
그리면 그 쓰기가 나중에 착지해 그려진 값을 덮는다. **제출 전에 그 CPU가
한 번 읽으면** 없어진다.

**가설**: ioctl은 **클라이언트 스레드에서** 실행되므로, 드라이버가 제출
경로의 **맨 앞**에서 목적지를 한 번 읽으면 같은 CPU의 읽기가 되어 같은
효과를 낸다. 그러면 클라이언트는 아무것도 몰라도 된다.

## 2. 이 가설이 기대는 것 — 각각 미검증

1. **ioctl이 클라이언트 스레드에서 도는가.** 그렇게 알고 있지만
   확인한 적 없다. 아니라면(예: 별도 커널 스레드로 넘어간다면) 가설
   전체가 무너진다.
2. **한 번의 읽기가 *전부*를 배출시키는가.** WC 버퍼는 여러 개이고 각각
   다른 줄을 담는다. 한 주소를 읽는 것이 **다른 주소를 담은 버퍼**까지
   배출시킨다는 보장이 있는가? 클라이언트가 두 낱말만 읽고 4096픽셀이
   전부 옳아진 것은 그렇다는 **증거**지만 **증명은 아니다** — 그 두
   읽기가 우연히 필요한 버퍼들을 밀어냈을 수도 있다.
3. **드라이버가 어디를 읽어야 하는가.** 목적지 첫 낱말? 클라이언트가
   실제로 무엇을 썼는지 드라이버는 모른다. 2번이 참이면 아무 데나 한 번,
   거짓이면 **알 수 없다**.

## 3. 선택지

### (가) 드라이버가 제출 앞에서 한 번 읽는다
- **장점**: 클라이언트가 아무것도 안 해도 된다. 이미 있는 별칭으로 된다.
- **위험**: §2의 2번이 거짓이면 **가끔** 틀린다 — 가장 나쁜 실패 방식.

### (나) 계약이 클라이언트에게 요구한다
- "제출 전에 목적지를 한 번 읽어라"를 헤더에 적고, Mesa 백엔드가 지킨다.
- **장점**: 클라이언트가 자기가 쓴 곳을 안다 — §2의 3번이 사라진다.
- **단점**: 다른 클라이언트가 잊으면 조용히 틀린다.

### (다) 직렬화 명령
- 드라이버가 WC 버퍼를 확실히 비우는 명령을 실행한다.
- **미조사**: 이 커널/컴파일러에서 무엇을 쓸 수 있는가. 486에는 `wbinvd`가
  있으나 과하고 비싸다.

### (라) 애초에 클라이언트가 VRAM에 쓰지 않게 한다
- 미청소값 채우기·클리어를 엔진에게 시킨다. Mesa의 `glClear`는 이미
  소프트웨어가 VRAM에 쓴다 — **되비추기와 같은 문제를 안고 있다.**

## 4. 다음 측정 (코드보다 먼저)

**(가)를 짓기 전에 §2의 2번을 잰다.** 클라이언트가 **아주 멀리 떨어진 한
낱말만** 읽고 제출했을 때 4096이 나오는가? 나오면 "한 번의 읽기가 전부를
배출한다"가 크게 뒷받침된다. 안 나오면 (가)는 못 쓴다.

이건 **유저랜드만**이라 재부팅이 필요 없다.

## 5. 검토 결과 — **§4의 측정이 실제 경로를 쓰지 않았다**

검토가 셋을 짚었고 트리에서 확인했다.

### 5-1. 내 측정과 Mesa 의 경로가 다르다 (가장 큰 것)

| | 제출 경로 | 실행 스레드 |
| --- | --- | --- |
| 지금까지의 측정 (`setIntValues:`) | Mach RPC | **드라이버 태스크의 다른 스레드** |
| Mesa 의 실제 경로 (`ioctl`) | syscall | **클라이언트 스레드** |

ioctl 콜백은 `_ioctl` → `fioctl` → cdevsw 항목으로 **동기 호출**된다(작업
큐 없음, 커널 바이너리에서 확인됨). 그러므로 **ioctl 경로에서는 드라이버의
읽기가 이미 클라이언트 CPU의 읽기다.**

→ **Mesa 경로에는 이 문제가 아예 없을 수도 있다.** 그것부터 재야 한다.

### 5-2. "읽기 한 번이 전부를 배출한다"는 전제가 약하다

일반 x86에서 **한 WC 주소의 평범한 읽기가 다른 주소를 담은 버퍼까지
배출한다는 보장은 없다.** 그리고 결정적인 반증거가 트리에 있다:
**제출 경로는 DMA 를 걸기 전에 이미 `MGA_ENGSTATUS` 를 읽는다**
(`osmgaR32` 두 번, `PRIMADDRESS`/`PRIMEND` 쓰기보다 앞). 아무 읽기나
전부를 배출한다면 이 버그는 애초에 설명하기 어렵다.

### 5-3. WC 라는 것 자체가 실증되지 않았다

`d_mmap`이 캐시 모드를 못 싣는다는 것은 **PFN 에 속성을 넣을 수 없다**는
뜻이지 결과 매핑이 무엇인지를 말하지 않는다. 가르는 방법은 실제
**PTE 의 PCD/PWT 비트와 MTRR** 을 보는 것이고, **`S4A_VRAM_MMAP_PLAN.md`
가 이미 그것을 다음 판별자로 지목해 뒀다.**

### 5-4. 그래서 (가)가 가장 나쁘게 실패한다

미증명이고 주소에 민감한 타이밍 효과를 **보이지 않는 드라이버 보장**으로
바꾸는 것이라, 특정 클리어·정렬·기계에서만 틀리면서 **성공을 보고한다.**

## 6. 고친 계획

1. **ioctl 경로가 같은 증상을 보이는가** — 유저랜드만, 재부팅 없음.
   안 보이면 문제의 범위가 훨씬 좁아진다(RPC 경로만).
2. 보인다면 **PTE/MTRR 로 메모리 타입을 확정**한다.
3. 그 다음에야 울타리든 읽기든 고른다. **울타리라면 명시적으로 고른
   명령**이지 "아무 읽기"가 아니다.

**(가)는 1·2 없이는 짓지 않는다.**


## 7. 측정 1 을 재봤다 (2026-08-21) — **아직 구분되지 않는다**

`§6`의 1번을 쟀다. 두 경로 모두 반복을 **프로그램 안**에 넣었다 — 셸 루프는
이 링크에서 `?` 만 찍고 죽고, 무엇보다 **증상이 간헐적**이라 몇 번 통과하는
것으로는 아무것도 못 말한다.

```
ioctl (Mesa 가 쓰는 경로) : 0 of 40 runs short
RPC   (setIntValues:)     : 1 of 40 runs short, worst 4080 of 4096
```

### 이걸로는 아무 말도 못 한다

| | 짧게 나온 횟수 | 95% 구간 |
| --- | --- | --- |
| ioctl | 0 / 40 | 0.0% .. 6.0% |
| RPC | 1 / 40 | 0.3% .. 11.1% |

**Fisher 정확검정 양측 p = 1.000.** 두 비율은 통계적으로 전혀 구분되지
않는다. 처음에 "RPC 는 사실상 매번 실패한다"고 적었던 것은 **사전 읽기를
넣기 전의 기억**이었고, 같은 규모로 재보니 2.5% 다.

**따라서 "결함이 제출 방식을 따라간다"는 결론은 근거가 없다. 취소한다.**

### 게다가 두 시험은 같은 것을 그리지 않는다

| | 그리는 것 | 화소 |
| --- | --- | --- |
| C(ioctl) 클라이언트 | 삼각형 하나 | 380 |
| ObjC(RPC) 클라이언트 | 텍스처 띠 | 4096 |

**10배 이상 차이 난다.** 화소당 확률이 같다면 작은 쪽이 덜 걸리는 게
당연하다. 지금 비교는 경로 차이와 크기 차이가 뒤엉켜 있어서, 설령 숫자가
갈렸더라도 어느 쪽 때문인지 말할 수 없었다.

### 대신 새로 나온 것: **잃은 양이 정확히 한 캐시라인**

이번에 짧았던 실행은 4096 중 **4080** — 즉 **16 dword = 64 바이트**를
잃었다. 예전 관측은 1 화소였다. 잃는 양이 1 에서 16 으로 바뀌는데 16 이
하필 64 바이트라는 것은, 잃는 단위가 **화소가 아니라 버스/캐시 전송
단위**라는 쪽을 가리킨다. 이는 "클라이언트의 sentinel 쓰기가 뭉쳐 있다가
엔진이 그린 뒤에 내려앉는다"는 §7 이전의 가설과 맞고, 그 가설은
`S4A_VRAM_MMAP_PLAN.md` 가 물어둔 **매핑의 메모리 타입(WC 인가)** 질문과
바로 이어진다.

### codex 교차검토 (계획 단계, gpt-5.6-terra) — 재검증한 결과

**받아들인 것**

- **Q1 문구**: `p = 1.000` 은 "차이가 없다"가 아니라 **"이 표본은 아무 말도
  못 한다"** 다. 양쪽 다 주장할 수 없다. 문구를 그렇게 고쳤다.
- **Q2 과대주장**: "연속 16 dword 면 캐시라인/쓰기결합 확정"은 틀렸다.
  64 바이트 단위로 움직이는 것은 CPU 캐시라인 말고도 여럿이다 — 호스트
  브리지의 posted-write, PCI 버스트, 카드 안의 쓰기 버퍼, Storm 의 전송
  단위. **오프셋만으로는 이것들을 못 가른다.** 그래서 1번의 결론을
  "확정"에서 "정렬이 주소 쪽인지 좌표 쪽인지 가른다"로 낮췄다.
- **Q4**: 화소 수(380 대 4096) 말고 사각형 정렬·크기도 다르다. 다만 **목적지
  기준은 양쪽 다 4 MB 로 같다** — 직접 확인했다(`VRAM_BLOCK`, `COLOUR_ORG`).
- **Q5 의 새 실험**: **sentinel 을 CPU 가 아니라 엔진이 쓰게 하고 비교한다.**
  내가 안 적었던 것이고, 지금까지 나온 것 중 가장 날카롭다. 손실이 사라지면
  잃는 쪽은 **엔진이 아니라 CPU 쓰기**로 좁혀진다.

**받아들이지 않은 것 (근거를 대조해 확인함)**

- **Q3 의 메커니즘은 틀렸다.** codex 는 "앞 시행의 count 가 짧았을 시행을
  고쳐준다"고 했다. 두 루프의 실제 순서를 읽어보면 한 시행은
  `fill → (settle) → submit → count` 이고, 앞 시행의 count 는 다음 시행의
  **fill 앞**에 온다. 우리가 잰 "고쳐주는 읽기"는 **fill 과 submit 사이**의
  읽기다. 그 자리에 count 는 없다.
- **다만 결론은 다른 길로 옳다.** count 가 모든 라인을 읽어 두므로,
  **시행 0 만 차가운 라인에 쓰고 나머지 39 는 따뜻한 라인에 쓴다.**
  지금까지 결함을 보여준 단발 관측은 **전부 차가운 실행**이었다. 결함이 찬
  라인을 필요로 한다면 이 루프는 양쪽 다 과소평가한다.
- **"시행마다 새 영역"은 안 쓴다.** 40 × 4096 화소를 겹치지 않게 잡을 창이
  없고, 무엇보다 **시행마다 정렬이 달라져** 알아내려는 것과 교란된다.
- **"드라이버가 uncached alias 로 확인해 나쁜 오프셋을 돌려준다"도 지금은
  안 한다.** 드라이버 변경 = 재부팅이고, **그 답은 이미 있다** — M1-3g 에서
  드라이버의 alias 는 완료 시점에 그려진 값을 읽는다.

## 8. 1 회차 계측 결과 (2026-08-21) — **무작위가 아니었다**

계측만 넣고(동작 변경 없음) 돌렸다. 네 번 연속:

```
through the RPC, no read between fill and submit: 1 of 40 runs short, worst 4080 of 4096
```

**네 번 다 똑같다.** "간헐적"이 아니라 **결정적**이다. 40 회 중 정확히 한 번,
정확히 16 dword.

그리고 어디를 잃었는지:

```
trial 0 came up 16 short, at:
   byte       0  x= 0 y= 0  mod32= 0 mod64= 0
   byte       4  x= 1 y= 0  ...
   ...
   byte      60  x=15 y= 0  mod32=28 mod64=60
   in 1 contiguous stretch(es)
```

**바이트 0..63, 끊김 없이 한 덩어리, 정확히 64 바이트.** 그리고 **언제나
시행 0** 이다.

### 두 번째로 보면 이미 들어와 있다

처음엔 세는 패스가 끝난 뒤에 다시 봤더니 `nothing is stale any more` 였다.
그래서 오프셋을 **세는 그 패스에서** 잡도록 고쳤다. 위 숫자는 첫 접촉에서
찍은 것이다. 즉 **잃은 게 아니라 늦은 것**이고, 한 번 훑고 지나가면 들어와
있다. `§7` 이전에 "lost, not late" 라고 적었던 것은 화소 하나짜리 다른
프로브에서 나온 것이었다 — **이 관측이 그것을 뒤집는다.**

### 시행 0 이 특별한 이유는 캐시가 아니다

`§7` 에서 "시행 0 만 캐시가 차갑다"고 적었다. 코드를 다시 읽으니 그게 아니다.
40 회 블록 바로 앞에서 **배치를 새로 만든다**:

```c
memset(batch, 0, sizeof *batch);
... triCount = 1; dstorg = COLOUR_ORG; texState(batch); rect(...);
```

앞 절은 검증기 거부 시험이라 `tmr` 을 망가뜨려 놓은 상태였다. 그러니
**시행 0 은 엔진 상태가 바뀐 뒤의 첫 제출**이다. 시행 1..39 는 전부 같은
상태의 반복 제출이고, 하나도 안 잃는다.

**그리고 이건 이미 M1-3g 때 의심했던 것이다** — 클라이언트 주석에 그대로
남아 있다: *"the second pass runs with the texture unit already programmed…
the first pixel after the unit is set up is being lost."* 거기서 놓쳤던
것을 40 회 반복이 되살렸다.

### 남은 교란 하나

바이트 0 은 **동시에** 64 바이트 경계이자 사각형의 첫 화소다. 그래서 아직
"주소 정렬을 따른다"와 "처음 건드리는 자리를 따른다"를 못 가른다.

### 대조군 C 는 이미 있었다 — 그리고 경로 차이를 통째로 설명한다

C(ioctl) 클라이언트를 다시 읽었다. 배치를 만든 다음 **40 회 블록에 들어가기
전에 한 번 제출한다**:

```c
memset(batch, 0, sizeof *batch);
... dstorg = VRAM_BLOCK; ... BuildTriangle(...); triCount = n;
rc = OSMGAMesaProbeSubmit(&res);      /* <-- 여기, 루프 밖 */
...
for (trial = 0; trial < 40; trial++) { ... }
```

그래서 **C 쪽 시행 0 은 상태 변경 뒤 첫 제출이 아니다.** 그 첫 제출은 이미
루프 밖에서 써버렸다. 그리고 C 는 0/40 이다.

ObjC 쪽은 루프 바로 앞에서 배치를 새로 만들고 **그 첫 제출이 시행 0** 이다.
그래서 1/40 이다.

**즉 "경로가 다르다"고 보였던 것은 전부 이 배치 재구성 위치 차이다.**
ioctl 이냐 RPC 냐와는 아무 상관이 없었다. `§7` 의 철회가 옳았을 뿐 아니라,
이제는 왜 갈렸는지까지 설명된다 — 새 코드 한 줄 없이, 기존 소스를 읽어서.

계획의 **C 는 이미 답이 나왔다.** 남은 것은 B 와 D 다.

### 다음 (계획, 아직 코드 아님)

- **B. 시행마다 상태를 바꾼다** — 그러면 40 회 다 짧아야 한다. 그렇게 나오면
  "상태 변경 뒤 첫 전송"이 확정된다.
