# M1-4D8 — 축소에서 선형 필터가 걸리지 않는다 (계획)

## 1. 결함 (실측)

`GL_LINEAR` 텍스처를 **축소**해 그리면 하드웨어가 점 표본을 한다.  32 화소에
텍스처 4 장(화소당 2 텍셀), `MinFilter = MagFilter = GL_LINEAR`:

```
   # minlin: drawn 2 software 0 unsupported 0 declined 0
   공통 1024 화소 중 어긋남 1024 (100%)  최대 채널 차 9

   (40,40)  하드웨어 (24, 20, 2)   소프트웨어 (15, 11, 0)
```

`R = 24` 는 텍셀 1 의 값(`1*16+8`)이다 — 점 표본이다.  소프트웨어의 15 는 텍셀
0(8)과 1(24)의 혼합이다.  **관문은 이것을 통과시킨다.**

## 2. 원인

`OpenStepMGAMesaHook.c:571` 의 관문은 이렇게 적혀 있다:

> 엔진에는 필터 스위치가 **하나뿐**이고 λ 개념이 없는 반면 GL 은 화소마다
> MinFilter 와 MagFilter 중에서 고른다.  둘이 같기를 요구하는 것이 그 선택을
> 무의미하게 만든다.

**전제가 틀렸다.**  `xf86-video-mga` 의 `mga_reg.h:576-580` 이 `TEXFILTER`
(0x2c58)에 **두 필드**를 적어둔다:

```
   MGA_MIN_NRST   0x00000000     MGA_MAG_NRST   0x00000000
   MGA_MIN_BILIN  0x00000002     MGA_MAG_BILIN  0x00000020
   MGA_MIN_ANISO  0x0000000D
```

그리고 인코더는 **MAG 만** 쓴다:

```c
   MGA_TEXFILTER, MGA_TEXFILTER_ALPHA | (0x10UL << 21) |
                  ((texFlags & TEXF_BILIN) ? 0x20UL : 0UL)
```

`0x20` 은 `MGA_MAG_BILIN` 이다.  MIN 필드는 0 — nearest — 으로 남는다.

지금까지 이것이 드러나지 않은 이유는 **모든 장면이 확대**였기 때문이다.
`tilebnd` 는 축소지만 nearest 라 해당이 없다.

## 3. 고침 (제안)

`TEXF_BILIN` 일 때 MIN 필드도 bilinear 로 놓는다:

```c
   ... | ((texFlags & TEXF_BILIN) ? (0x20UL | 0x02UL) : 0UL)
```

한 줄이다.  다만 확인해야 할 것이 있다.

## 4. 확인해야 할 것

1. **`0x2` 가 정말 MIN bilinear 인가.**  근거는 `mga_reg.h` 한 곳뿐이고, 이
   저장소는 그 헤더가 `mga_exa.c` 와 어긋난 전례가 있다(M1-4C 계열).  실기에서
   재야 한다 — 축소 장면이 소프트웨어와 맞아떨어지면 맞는 것이다.
2. **확대가 망가지지 않는가.**  MIN 을 켜는 것이 MAG 경로에 영향을 주는지는
   모른다.  기존 아홉 기준값이 전부 유지되어야 한다.
3. **`(0x10 << 21)` 이 무엇인가.**  코드에도 참조에도 설명이 없다.  MIN 필드와
   같은 레지스터이므로 상호작용이 없다고 단정할 수 없다.
4. **λ 는 여전히 없다.**  MIN/MAG 가 따로 있어도 **어느 쪽을 쓸지 고르는 것**은
   하드웨어가 화소마다 한다 — 그것이 λ 다.  하드웨어가 그 선택을 하는지, 아니면
   MIN 을 켜면 늘 MIN 을 쓰는지 모른다.  이것이 미프맵으로 가는 문의 손잡이다.
5. **관문을 풀 수 있는가.**  `MinFilter == MagFilter` 요구는 "스위치가 하나"라는
   틀린 전제에서 나왔다.  둘이 따로면 `GL_NEAREST`/`GL_LINEAR` 조합도 표현할 수
   있다 — 4 번이 답을 주면 관문을 넓힐 수 있다.

## 5. 순서

1. 커널 한 줄을 고치고 재부팅한다
2. `minlin` 이 소프트웨어와 맞는지 본다.  맞으면 `0x2` 가 MIN bilinear 다
3. 기준값 아홉 개가 유지되는지 본다
4. **λ 를 잰다**: 같은 삼각형이 한쪽은 확대되고 다른 쪽은 축소되도록 그려,
   하드웨어가 화소마다 고르는지 본다.  고른다면 미프맵의 절반은 이미 있다
5. 4 의 답에 따라 관문을 넓힌다

## 6. 물어볼 것

1. `0x2` 를 근거 하나로 쓰는 것이 맞는가.  다른 확인 방법이 있는가?
2. 4 번(λ 선택)을 어떻게 재는 것이 가장 값싼가?
3. MIN 을 켜면 확대가 달라질 수 있다고 보는가 — 어떤 기전으로?
4. 내가 못 본 위험이 있는가?

## 7. 들어갔다 (재부팅 대기)

### 7-1 커널

- `OSMGA_HW3D_TEXF_BILINMIN` (`0x100`) 새 플래그
- 인코더가 `TEXFILTER` 의 **두 필드**를 쓴다: `0x20` (MAG), `0x02` (MIN)
- 훅은 `GL_LINEAR` 일 때 **둘 다** 켠다 — `minlin` 결함이 그것으로 고쳐진다

두 비트를 하나로 합치지 않은 이유가 있다: **따로여야 λ 를 물을 수 있다.**

### 7-2 λ 판별 (§70)

같은 삼각형 안에서 배율이 변하려면 원근이 필요한데, 탐침은 그 대신 **행마다 다른
기울기**로 배율을 바꾼다 — 화소당 1/4 텍셀부터 16 텍셀까지 일곱 단계.  텍셀이 0 과
255 로 번갈아 있어 혼합이면 중간값이 나온다.

세 조합을 나란히 본다:

```
   neither    (두 필드 다 nearest)
   MAG only   (지금까지의 동작)
   MIN only   (새 비트만)
```

**MIN-only 가 배율 1 을 경계로 갈라지면 — 넘는 쪽은 혼합, 못 미치는 쪽은 점
표본 — 엔진이 화소마다 고른다는 뜻이고, λ 가 있다.**  한쪽으로만 나오면 두 필드는
독립이 아니고, `MIN` 을 켜는 것은 "항상 축소 필터"라는 뜻이다.

### 7-3 되돌릴 근거

훅이 두 비트를 다 켜므로, λ 가 없고 `MIN` 이 확대까지 먹으면 **기준값 아홉 개가
즉시 말해준다.**  그러면 훅에서 `BILINMIN` 을 떼고 인코더의 한 줄만 남긴다.

### 7-4 재부팅 뒤

1. `minlin` — 소프트웨어와 맞아야 한다.  맞으면 `0x2` 가 MIN bilinear 다
2. 기준값 아홉 개 — 확대가 망가지지 않았는지
3. §70 — λ 가 있는지
4. 탐침 §1…§70 전부

등호 관문이 살아 있는 한 **MIN 과 MAG 가 언제나 같은 필터**이므로, 하드웨어가

## 9. 재부팅 검증 — 셋 다 답이 나왔다

### 9-1 `0x2` 는 MIN bilinear 다

```
   minlin:  어긋난 화소 1024,  최대 채널 차  9 -> 1
```

점 표본이 사라졌다.  남은 것은 전 채널 균일한 **+1** 로, `tile lin` 과
`bandseam` 에서 본 **양수 잔여의 반올림 서명**과 같은 성질이다 — 새 결함이 아니다.

### 9-2 확대는 망가지지 않았다

기준값 아홉 개 전부 유지.  탐침 §1…§70 **0 실패**.

### 9-3 λ 가 있다 (§70)

| 배율(텍셀/화소) | 1/4 | 1/2 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|---|---|
| 둘 다 nearest | 0 | 0 | 0 | 255 | 0 | 0 | 0 |
| **MAG 만** | **95** | **63** | 0 | 255 | 0 | 0 | 0 |
| **MIN 만** | 0 | 0 | 0 | **127** | **127** | **127** | **127** |

**두 필드가 상보적이다.**  MAG 는 배율 1 미만에서만, MIN 은 1 초과에서만 듣는다.
λ 가 없다면 켠 쪽이 **전 구간**에서 들어야 한다 — 어느 쪽도 그러지 않는다.

> **엔진은 화소마다 MIN 과 MAG 중에서 고른다.  이 경로에 λ 가 있다.**

배율 정확히 1 은 두 행 다 0 인데, 그 자리에서는 표본이 텍셀 중심에 앉아 혼합
가중치가 0 이 되므로 어느 쪽이 골라져도 점 표본처럼 보인다 — 모순이 아니라
**분별력이 없는 지점**이다.

## 10. 그래서 열린 것

1. **관문을 넓힐 수 있다.**  `MinFilter == MagFilter` 요구는 "스위치가 하나"라는
   틀린 전제에서 나왔다.  둘이 따로 있고 하드웨어가 고르므로,
   `GL_NEAREST`/`GL_LINEAR` 조합을 그대로 표현할 수 있다.
2. **미프맵이 사정권에 들어왔다.**  `TF_minfilter` 에 `mm1s 0x8`, `mm2s 0x9`,
   `mm4s 0xa`, `mm8s 0xc` 가 있고, λ 가 있으므로 레벨 선택의 절반은 이미 있다.

### 11-2 미프맵 — 크고 미지수가 많은 쪽

`mm1s/mm2s/mm4s/mm8s` 의 뜻과 레벨 원점을 모른다.  `TEXORG` 는 하나뿐이고

**순서**: 11-1 을 먼저 한다.  11-2 는 레지스터의 뜻을 먼저 재는 별도 조사다.

## 13. 두 가지를 더 갈랐다

### 13-1 남은 +1 은 MIN 경로의 것이 아니다 (`maglin`)

codex 가 "같은 반올림이라 부르는 것이 편해 보인다"고 했다.  타당해서 **확대판
쌍둥이**를 만들었다 — 같은 텍스처, 같은 필터, 같은 비교, 다른 경로.

```
   minlin (축소, MIN 경로) : 1024 화소, 전 채널 +1
   maglin (확대, MAG 경로) : 4096 화소, R·G 전부 +1, B 는 1024 개만
```

**확대 쪽에도 똑같이 나타난다.**  MIN 경로가 들여온 것이 아니다.
(B 가 갈리는 것은 B 채널의 인접 텍셀 차가 1 이라 혼합이 훨씬 민감하기 때문이다.)

### 13-2 선택은 프리미티브 **안에서** 일어난다 (§71)

codex 의 가장 날카로운 지적: §70 의 일곱 행은 **각각 별개의 등배율 드로우**라,
프리미티브마다 한 번 고르는 것과 구별되지 않는다.

그래서 배율이 **한 프리미티브 안에서** 1 을 가로지르게 만들었다 — 등배율로는
불가능하므로 분모에 기울기를 준다.  MIN 만 bilinear, MAG 는 nearest:

```
   열      1     2     3     4     5     6     7  …    13     14     15
   배율 2.205 2.048 1.908 1.782 1.668 1.564 1.470 … 1.050  0.997  0.949
   빨강   95    62   102   142   240   172    25  …   162      0    255
   판정 혼합  혼합  혼합  혼합  혼합  혼합  혼합  …  혼합   점표본 점표본
```

**배율이 1 아래로 떨어지는 열이 정확히 14 이고, 점 표본을 하는 열이 정확히
14·15 다.**  텍스처가 0 과 255 뿐이므로 중간값은 혼합일 수밖에 없다.

> 선택은 프리미티브 단위가 아니라 **그 안에서** 이뤄진다.

## 16. 선택자는 두 축을 본다 (§72)

GL 의 λ 는 두 축 배율의 **큰 쪽**이다.  한 축만 보는 선택자라면 "u 는 느리고 v 는
빠른" 경우에서 GL 과 갈린다 — 그리고 그건 넓힌 관문이 통과시킬 경우다.

```
   u 빠름, v 느림   du 65536  dv  4096   빨강 127  혼합   GL 은 MIN
   u 느림, v 빠름   du  4096  dv 65536   빨강 127  혼합   GL 은 MIN   <- 판별
   둘 다 느림       du  4096  dv  4096   빨강 255  점표본 GL 은 MAG
```

**셋 다 GL 과 일치한다.**  판별 경우가 점 표본이 아니다.

## 17. 관문을 넓혔다

codex 가 제시한 구조 그대로:

- `MinFilter` 가 `GL_NEAREST`/`GL_LINEAR` 가 아니면 거절
- `MagFilter` 도 따로 같은 검사 — **이게 없으면** 등호를 떼는 순간
  `GL_NEAREST_MIPMAP_NEAREST` + `GL_NEAREST` 같은 조합이 뚫린다
- 두 비트를 각자의 필터에서 낸다
- 래핑은 **어느 한쪽이라도** 선형이면 좁은 집합만
- 미프맵 필터 넷은 계속 거절

### 17-1 네 조합 × 두 영역 (`fmix`)

```
   확대   NN 0/4096   NL 0/4096   LN 0/4096   LL 4096/4096 (1 레벨)
   축소   NN 0/1024   NL 0/1024   LN 0/1024   LL 1024/1024 (1 레벨)
```

여덟 칸 전부 하드웨어로 그려진다(`drawn 2 software 0`).  섞인 조합은 이전에는
아예 그릴 수 없었다.

## 18. 그리고 "한 레벨"의 정체가 바뀌었다

`LL` 만 어긋나는 것이 이상해 파고들었다.  **하드웨어끼리 비교하면 NL 과 LL 이
확대에서 완전히 같다** — 화소마다 고른다는 것과 정확히 일치한다.  갈리는 쪽은
**소프트웨어**였다.

`Mesa-3.4.2/src/texture.c:1928`:

```c
   GLboolean needLambda = (GLboolean) (t->MinFilter != t->MagFilter);
```

Mesa 는 **두 필터가 다를 때만** λ 를 계산하고 `sample_lambda_2d` 를, 같으면
`sample_linear_2d` 를 쓴다.  **서로 다른 함수다.**

같은 하드웨어 출력을 두 경로에 각각 대보면:

```
   확대: 하드웨어 vs Mesa 의 λ 경로      0 / 4096 어긋남
         하드웨어 vs Mesa 의 빠른 경로  4096 / 4096 (1 레벨)
   축소: 하드웨어 vs Mesa 의 λ 경로      0 / 1024
         하드웨어 vs Mesa 의 빠른 경로  1024 / 1024 (1 레벨)
```

> **하드웨어는 Mesa 의 λ 경로와 정확히 일치한다.**  오랫동안 "엔진의 반올림"이라
> 불러온 한 레벨 차이는, 적어도 선형 장면들에서는 **Mesa 의 두 경로 차이**다.

이는 `tilelin`(16384), `maglin`, `minlin` 의 기준값 설명을 바꾼다 — 그 셋은 모두
`MinFilter == MagFilter == GL_LINEAR` 라 Mesa 가 빠른 경로를 탄다.  **엔진이
틀린 것이 아니라 비교 대상이 두 개였다.**
