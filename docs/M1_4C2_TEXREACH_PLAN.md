# M1-4 4b 를 막는 것 — 텍스처 좌표 도달 검사가 표면 전체를 본다

2026-08-22.  **커널 변경이므로 재부팅이 필요하다.**

## 1. 측정한 사실

`test/openstep-mga-hw3d-texreach-probe.m` 는 배치를 **하나도 바꾸지 않고**
목적지 폭 선언만 바꾼다.  삼각형도, 텍스처도, 모든 TMR 값도 그대로다.

```
   triangle 32 wide, one texture across it, tmr0 = 32768
   the bound is 8388608 (8 << 20)

   surface W  reach at W-1   verdict
   64         2064384        0 (accepted)
   128        4161536        0 (accepted)
   256        8355840        0 (accepted)
   320        10452992       13 (texture coordinate)
   512        16744448       13 (texture coordinate)
   1024       33521664       13 (texture coordinate)
```

**같은 삼각형이 표면 폭 256 에서는 그려지고 320 에서는 거절된다.**
바뀐 것은 배치가 선언한 폭 하나뿐이므로 다른 설명이 없다.

원인은 `hw3d/OpenStepMGAHW3D.c:199-203` 이다:

```c
if (!osmgaHW3DCoord(b->state.tmr[6], b->state.tmr[0],
                    b->state.tmr[2], lim->clipX1, lim->clipY1) || ...
```

그리고 `lim.clipX1 = dstW3 - 1`, `lim.clipY1 = dstH3 - 1`
(`OpenStepMGAReplacementDisplay.m:3613-3614`) — **표면 전체**다.
검사는 삼각형의 기울기를 표면의 마지막 열까지 연장해서 본다.

## 2. 이것이 4b 에 무슨 뜻인가

삼각형 하나에 텍스처 한 장을 씌우면 `tmr0 = (1<<20)/삼각형너비` 이므로,
표면 끝에서의 도달은 `(W-1)·(1<<20)/삼각형너비` 다.  한계 `8<<20` 을 넘지
않으려면 **삼각형 너비 ≥ (W-1)/8** 이어야 한다:

| 표면 | 그릴 수 있는 가장 좁은 텍스처 삼각형 |
|---|---|
| 320×240 | 폭 40, 높이 30 |
| 640×480 | 폭 80, 높이 60 |
| 1024×768 | 폭 128, 높이 96 |

**실제 장면의 삼각형은 대부분 그보다 작다.**  그러므로 4b 를 유저랜드에서
아무리 옳게 만들어도 대부분의 텍스처 삼각형이 커널에서 거절된다.
이것이 4b 를 막는 것이고, **유저랜드에서 우회할 방법이 없다** — 배치가
선언하는 목적지 폭은 그리는 표면의 폭이지 고를 수 있는 값이 아니다.

## 3. 고치는 방법

검사의 뜻은 그대로 두고, **얼마나 멀리까지 보느냐**만 바꾼다.

지금: 좌표 평면을 표면의 마지막 열·행까지 연장해서 본다.
바꾼 뒤: **실제로 그려지는 마지막 열·행까지만** 본다.

그 값은 이미 커널이 알고 있다.  검증기는 삼각형마다 두 변을 행 단위로
걸으며 `lx`/`rx` 를 굴리고, 범위 밖으로 나가면 `E_TRICROSS` 로 거절한다
(`OpenStepMGAHW3D.c:338-356`).  그 걸음에서 최대값을 함께 모으면 된다.
새 비용은 비교 몇 개이고, **프로토콜은 바뀌지 않는다.**

모으는 값(텍스처를 쓰는 삼각형에 대해서만):

```
bx1 = max over textured triangles, over rows, of (rx - 1)   /* 오른쪽은 배타적 */
by1 = max over textured triangles of (t->y + t->h - 1)
```

그리고 검사를 `lim->clipX1, lim->clipY1` 대신 `bx1, by1` 로 한다.

* **의미가 바뀌지 않는다.**  좌표는 여전히 화면 원점 기준의 평면으로
  다뤄지고, 시작값도 그대로다.  보는 끝점만 가까워진다.
* **여전히 보수적이다.**  D3-4b 는 `v` 의 원점이 프리미티브(`YDSTLEN`)라고
  밝혔는데, 절대 행 `by1` 을 쓰는 것은 그보다 크게 잡는 쪽이다.
* 텍스처 삼각형이 없으면 지금처럼 검사 자체를 건너뛴다.

### 순서를 바꿔야 한다

좌표 검사는 지금 삼각형 순회(`:206`)보다 **먼저** 있다(`:199`).
상자를 모으려면 순회 뒤로 옮겨야 한다.  옮기면서 **거절 코드는 그대로**
`E_TEXCOORD` 를 쓴다 — 클라이언트가 이미 그 코드를 읽고 있다.

## 4. 무엇이 위험한가

* **거절이 느슨해진다.**  지금 거절되던 배치 일부가 통과하게 되는데,
  그게 이 변경의 목적이다.  다만 *너무* 느슨해지면 안 된다: 상자는
  걸음이 이미 `0 ≤ lx, rx ≤ clipX1+1` 로 묶어 둔 값에서 나오므로
  표면 밖으로는 못 간다.  **그 성질에 기대므로, 그 성질이 유지되는지
  같은 변경에서 확인한다.**
* **빈 삼각형**(`h == 0` 이거나 모든 행이 `lx == rx`)은 상자에 아무것도
  더하지 않는다.  그러면 `bx1` 이 초기값으로 남는데, 그 상태로 검사하면
  **아무 좌표나 통과**한다.  초기값을 0 이 아니라 "없음"으로 두고,
  텍스처 삼각형이 하나라도 그려지지 않으면 좌표 검사를 건너뛰는 것이
  맞다 — 그리는 화소가 없으면 좌표도 없다.  **이 구멍을 시험한다.**

## 5. 함께 넣지 않는 것

교차검토가 제안한 "커널이 목적지에서 깊이 예약을 유도해 텍스처 시작을
검사한다"는 **이번에 넣지 않는다.**  옳은 방향이지만 유저랜드의 배치 정책을
커널에 박는 것이고, 지금 통과하는 raw 클라이언트들과의 상호작용이 확인되지
않았다.  텍스처 올리기(4c)가 실제로 생겨서 그 상호작용을 알게 된 뒤에,
그때의 커널 변경에 태운다.  **필요한 수정과 위험한 정책을 한 재부팅에
묶지 않는다.**

## 6. 어떻게 증명하는가

1. **호스트 시험** (`hw3d/test-hw3d-validate.c` 계열) — 좁은 삼각형이
   넓은 표면에서 통과하고, 진짜로 범위를 넘는 좌표는 여전히 거절된다.
   빈 삼각형만 있는 텍스처 배치가 **통과하지 않는지** 반드시 포함한다.
2. **실기**: 같은 probe 를 다시 돌려 여섯 폭 전부가 승인되는지 본다.
   지금은 256 까지만 승인이다.  **바뀐 뒤에도 진짜 위반이 거절되는지**
   보려면, 도달이 정말로 한계를 넘는 배치(예: 삼각형 자체가 넓고 기울기가
   가파른 것)를 같은 probe 에 넣는다 — 전부 통과하는 시험은 시험이 아니다.
3. 기존 텍스처 클라이언트(`openstep-mga-hw3d-tex-client.m`)가 그대로
   PASS 하는지 — 느슨해진 검사가 다른 것을 망가뜨리지 않았다는 확인.

## 7. 좌표 원점을 쟀다 — 설계가 바뀐다 (2026-08-22)

계획을 쓸 때 `M1_4_TEXTURE_PLAN.md` 의 "TMR 시작값은 화면 원점 기준"을
믿었다.  **틀렸다.**  `test/openstep-mga-hw3d-texorigin-probe.m` 는 똑같은
텍스처 사각형을 TMR 을 하나도 바꾸지 않고 두 자리에 그린다:

```
   columns 0..63    verdict 0   row 0: first 0 last 63   equal-to-first 1 of 64
   columns 64..127  verdict 0   row 0: first 0 last 63   equal-to-first 1 of 64
```

TMR6 = 0 인데 64..127 자리의 사각형도 **텍셀 0 에서 다시 시작한다.**
화면 원점이라면 그 자리의 u 는 64 텍셀을 넘어 포화해서 63 한 값으로
깔렸어야 한다.  **좌표 원점은 프리미티브다.**

그래서 두 가지가 따라온다:

1. **음수 시작 문제는 없다.**  x=0 이 아닌 삼각형도 TMR6 = 0 이면 된다.
   (계획을 쓰던 중 이것이 두 번째 장애물인 줄 알았다.  아니었다.)
2. **검사의 올바른 범위는 삼각형 자신의 폭·높이다.**  표면 폭은 애초에
   좌표가 정의되는 구간이 아니었다.  그러니 이 변경은 "표면에서 그려지는
   상자로 느슨하게 하는 것"이 아니라 **"좌표가 실제로 정의된 구간을 쓰는
   것"**이다.

### 왜 "전체 클립이 옳다"를 받지 않는가

드라이버가 자기 안전 논거를 적어 두었다
(`OpenStepMGAReplacementDisplay.m:526-530`):

> *"Containment differs from the depth work: the texture unit only reads, so a
> wrong coordinate reads the wrong VRAM rather than writing outside it.  The
> single write is the destination, bounded by the clip we measured."*

즉 **메모리 안전은 좌표 한계가 아니라 목적지 클립이 지킨다.**  좌표 한계는
"잰 만큼만 믿는다"는 보수성이지 안전 경계가 아니다.  게다가 창은 이 장치를
연 클라이언트가 통째로 mmap 할 수 있으므로, 창 안의 엉뚱한 읽기는 클라이언트가
직접 읽을 수 있는 것을 읽는 것이다.

그리고 §7 이 원점을 재면서 문제의 성격이 바뀌었다: 표면 폭은 **좌표가 정의된
구간이 아니었다.**  전체 클립을 유지하는 것은 보수적인 것이 아니라 **틀린
구간을 재는 것**이다.

다만 codex 가 옳은 부분은 남긴다: **그려지는 상자가 인출 영역이라고 주장하지
않는다.**  주장하는 것은 *좌표가 프리미티브 구간에서 정의된다는 측정*뿐이고,
검사는 그 구간에 대해 한다.

## 9. 고친 설계

* 텍스처를 쓰는 삼각형마다, 변 걷기에서 **비어 있지 않은 행에 대해서만**
  `bx0 = min lx`, `bx1 = max (rx-1)` 을 모은다.  `lx == rx` 인 행은 열이
  없으므로 건드리지 않는다(언더플로도 막는다).
* 그 삼각형의 구간은 `spanX = bx1 - bx0`, `spanY = t->h - 1` 이다.
  배치는 텍스처 상태가 하나뿐이므로 **최대값**을 쓴다.
* **텍스처 삼각형 중 하나라도 그려지는 화소가 없으면, 그 배치는 예전처럼
  전체 클립으로 검사한다.**  빈 스팬도 인코더가 EXEC 하므로 인출이 없다고
  말할 근거가 없다.  이것이 §4·§6 의 모순을 없애는 답이다: **건너뛰지 않고,
  느슨하게도 하지 않는다.**
* 좌표 검사를 삼각형 순회 뒤로 옮기되, `E_TEXCOORD` 를 돌려주기 전에
  `badTri = 0` 으로 되돌린다 — 이것은 배치 전역 상태의 잘못이지 어느
  삼각형의 잘못이 아니다.
* `clipX1/clipY1` 에 기대는 다른 검사(목적지·깊이 도달, 행 담기, 변 담기,
  하드웨어 CX/Y 클립 프로그래밍)는 **하나도 건드리지 않는다.**

## 10. 시험 (판정에서 요구한 것)

* 호스트 — 넓은 표면 위의 좁은 텍스처 삼각형이 통과한다.
* 호스트 — **실제로 그려지는 끝점에서** 한계를 넘는 좌표는 여전히 거절된다.
* 호스트 — 높이가 있고 모든 스팬이 빈 텍스처 삼각형은 **예전 검사가 걸려서**
  여전히 `E_TEXCOORD` 다.
* 호스트 — 순회 뒤 거절에서 `badTri == 0`.
* 호스트 — 잘못된 삼각형과 잘못된 좌표가 같이 있으면 어느 것이 먼저 나오는지
  고정한다(순서가 바뀌는 것은 이 변경의 알려진 결과다).
* 실기 — probe 여섯 폭이 모두 승인되고, **그리고** 진짜 위반 하나는 여전히
  거절된다.  verdict 만 보지 않고 그려진 화소도 읽는다.
* 실기 — 기존 텍스처 클라이언트가 그대로 PASS.
