# M1-4d1 — 원근을 Mesa 쪽에서 여는 계획 (2026-08-23)

**코드는 안 건드렸다.** 이 문서가 교차검토 대상이다.

## 1. 읽어서 확인한 것 (추측 아님)

| 사실 | 근거 |
|---|---|
| `1/w` 는 `VB->Win.data[idx][3]` 에 있고 관문이 이미 읽는다 | `OpenStepMGAMesaHook.c:265` |
| 관문은 세 `1/w` 가 **정확히** 같지 않으면 소프트웨어로 보낸다 | 같은 곳, `hookTexPersp` |
| `glTexCoord4f` 의 `q ≠ 1` 도 따로 거절한다 | `:271-276` |
| 텍스처가 켜지면 **배치당 프리미티브 하나** | `:370` `cnt = texOn ? 1 : n` |
| 평면 풀이는 화면 좌표 `Win[0]`, `Win[1]` 로 한다 | `OpenStepMGAMesaTriangle.c:668-685` |
| 정점 구조체에 `w` 가 없다 | `OSMGAMesaVertex` |

**배치당 하나**라는 것이 크다 — 엔진의 `q` 행 색인은 배치를 가로질러
누적하는데(측정됨) `tmr[8]` 은 배치당 하나뿐이다.  프리미티브가 하나면
누적분이 0 이라 그 충돌이 **애초에 생기지 않는다.**

**화면 규약을 몰라도 된다**는 것도 중요하다: 분자와 분모를 **같은 좌표계에서
같은 방식으로** 푸므로, Y 방향이든 화소 중심 위상이든 몫에서 상쇄된다.
교차검토가 가장 흔한 실패로 꼽은 자리를 구조적으로 피한다.

## 2. 무엇을 계산하나

원근 보정은 `s/w` 와 `1/w` 를 화면에서 선형 보간하고 나누는 것이다.  엔진은
`분자 × 65536 / q` 를 준다.  그러므로 정점마다

```
   qw  = 1/w                      (Win[3])
   s_reg = λ · qw · s · us        us 는 지금 쓰는 텍셀 축척
   t_reg = λ · qw · t · vs
   q_reg = λ · qw · 65536
```

로 두고 **셋 다 화면 평면으로 푼다**.  그러면

```
   s_reg · 65536 / q_reg = s · us      ← 원근 보정된 값
```

이고 λ 는 몫에서 사라진다.

## 3. λ 는 무엇으로 정하나

λ 는 사영 자유도이므로 **검증기가 받아 줄 수 있는 만큼 크게** 잡는다 —
가산 `E ≤ 512` 의 상대 크기가 `q` 에 반비례하기 때문이다(오차 ≤ `2048/q` 텍셀).

제약(전부 프리미티브 단위):

| 제약 | 식 |
|---|---|
| 분모 하한 | `λ · qw_min · 65536 ≥ Q_MIN` |
| 분모 상한 | `λ · qw_max · 65536 ≤ Q_MAX` |
| 분자 시작 | `|λ · qw · s · us| ≤ 2^23` (세 꼭짓점) |
| 분자 기울기 | `|d(λ·qw·s·us)/dx| ≤ room/ex`, `dy` 는 `room/ey` |
| 분모 기울기 | 인코더의 `budget/mdx`, `budget/mrow` |

`λ_min`(하한들) > `λ_max`(상한들) 이면 **소프트웨어로 보낸다.**  틀린 그림을
그리지 않고 거절하는 쪽이다.

**분자 기울기 제약이 걱정된다** — 그 경계는 아핀 시절 것(분자가 곧 좌표이던
때)이라 원근에서는 과도하게 엄격하다.  얼마나 자주 물리는지 **재고 나서**
커널을 손댈지 정한다.

## 4. 관문에서 바꿀 것

* 세 `1/w` 가 같아야 한다는 조건을 **뺀다**.
* `glTexCoord4f` 의 `q ≠ 1` 거절은 **유지한다** (사영 텍스처는 별개 문제).
* 빌더가 λ 를 못 찾으면 소프트웨어로.

## 5. 재는 것 (열기 전과 후)

1. 원근 사각형을 **대각선을 반대로** 잡아 두 번 그린다.  사영이면 두 그림이
   같고 아핀이면 대각선에서 꺾인다 — 교차검토가 고른 그림 시험.
2. 소프트웨어 경로와 화소 대조.  기존 잔차(위상 24, 선형 257)와 견준다.
3. **폴백 비율** — λ 를 못 찾아 소프트웨어로 가는 프리미티브가 얼마나 되나.

## 6. 검토에 묻고 싶은 것

1. 분자·분모를 같은 좌표계에서 풀면 화면 규약이 상쇄된다는 논증이 맞는가?
2. λ 를 상한들의 최소로 잡는 것 말고 더 나은 선택 규칙이 있는가?
3. `1/w` 가 **음수이거나 0** 인 정점(카메라 뒤/평면 위)은 어떻게 되나?  Mesa 가
   클리핑 뒤에 넘겨주므로 안 생긴다고 봐도 되는가?
4. 내가 못 본 제약이 있는가?

## 7. 교차검토 재검증 — 내 1번 논증이 틀렸다 (2026-08-23)

### 7-1 몫은 좌표 규약 오차를 상쇄하지 않는다

나는 "분자와 분모를 같은 좌표계에서 풀므로 Y 방향이나 반 화소 위상이 몫에서
상쇄된다"고 적었다.  **python 으로 재보니 틀렸다.**  평면을 `x` 대신 `x+0.5`
에서 평가하면:

```
   x=  0.0  좌표        0.0 -> 1027.0    차 0.063 텍셀
   x= 32.0  좌표    80659.7 -> 82216.5   차 0.095 텍셀
   x= 64.0  좌표   209715.2 -> 212349.0  차 0.161 텍셀
   x=127.0  좌표  1016558.4 -> 1032381.8 차 0.966 텍셀
```

`N(x+δ)/Q(x+δ) ≠ N(x)/Q(x)` 이고, **`w` 가 작은 쪽으로 갈수록 커진다** — 반
화소가 거의 텍셀 하나가 된다.  아핀에서는 같은 반 화소가 장면 축척에 비례한
고정된 분수였는데, 원근에서는 **증폭된다.**

### 7-2 그래서 접근이 달라진다

규약이 맞는지를 **가정하지 않고 측정한다.**  아핀 경로가 소프트웨어와 맞는다는
사실이 앵커가 옳다는 증거이긴 하나, 원근에서는 같은 크기의 위치 오차가 훨씬
크게 나타나므로 **약한 증거**다.

끝단 대조에서 볼 것은 **잔차의 개수가 아니라 자리**다:

* 잔차가 기존 수준(위상 24 정도)에 머물면 앵커가 맞다.
* 잔차가 **`w` 가 작은 쪽으로 갈수록 커지면** 앵커가 반 화소 어긋난 것이다.

이 구분은 개수만 보면 안 보인다.

### 7-3 이음매는 무시할 수 있다

λ 는 정확한 산술에서 상쇄되고 남는 것은 레지스터 반올림뿐이다.  분자 1 단위가
`4/q` 텍셀이므로:

```
   q =   8192 -> 0.00049 텍셀      q = 65536 -> 0.00006 텍셀
   q = 2^20   -> 0.000004 텍셀
```

**λ 를 최대로 잡는 규칙이 가산 오차와 이음매 오차를 동시에 줄인다.**

### 7-4 `w ≤ 0`

`-w ≤ x ≤ w` 는 `w ≥ 0` 을 함의한다(python 으로 구간이 비는 것 확인).  그래도
**직접 거절한다** — `w = 0` 은 특이점이고, 아주 작은 양수 `w` 는 `Q_MAX` 상한이
자연히 거른다.
