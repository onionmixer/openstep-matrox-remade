# M1-4DA — 텍스처 + 블렌딩 (계획)

## 1. 무엇이 막고 있나

블렌딩 자체는 이미 된다.  엔진이 `(a·src + (255−a)·dst)/255` 를 하고, 관문이
`GL_SRC_ALPHA` / `GL_ONE_MINUS_SRC_ALPHA` 와 `GL_FUNC_ADD` 만 통과시킨다.

막는 것은 **텍스처와 함께일 때** 뿐이고, 이유가 코드에 적혀 있다
(`OpenStepMGAMesaHook.c:833`):

> 블렌딩은 텍스처 옆에서 거절된다: 블렌딩이 꺼져 있으면 알파 문제가 아예 생기지
> 않고, 사다리꼴을 두 번 그리는 것 — 일부만 제출된 분할 삼각형에 소프트웨어
> 재그리기가 겹치는 것 — 은 같은 화소에 **같은 값을 다시 쓰는** 것이지 더하는
> 것이 아니다.

### 1-1 왜 부분 제출이 생기나

`tmr` 은 **배치** 상태다.  그리고 엔진은 `u` 를 **프리미티브마다 자기 첫 행의
왼쪽 끝에서 다시 씨를 뿌린다**(실측, `OpenStepMGAHW3D.c:118` 부근).  그래서
사다리꼴마다 자기 앵커가 필요하고, 텍스처 배치는 **사다리꼴 하나**만 담는다.

삼각형 하나가 사다리꼴 여럿을 내면 배치도 여럿이고, **뒤 배치가 거절되면 앞은
이미 그려진 뒤**다.  그때 소프트웨어가 삼각형 전체를 다시 그린다.

### 1-2 그게 얼마나 흔한가 (실측)

`tc` 하네스의 일반 삼각형은 전부 `n = 2` 다.  가로 변을 가진 삼각형만 `n = 1` 이고,
그건 축 정렬 사각형을 이루는 것들이다.

> **`n == 1` 로 제한하는 것은 일반 기하를 거의 못 덮는다.**

## 2. 선택지

| | 내용 | 재부팅 | 정확성 |
|---|---|---|---|
| **A** 제출 ioctl 에 **모의 실행(dry run)** 을 더한다.  훅이 모든 사다리꼴을 먼저 검증하고, 전부 통과할 때만 제출 | 필요 | 정확 |
| **B** 배치가 삼각형마다 `tmr` 을 담게 한다 — 한 배치에 전부 | 필요 | 정확, 형식 변경이 큼 |
| **C** 클라이언트가 검증기 소스를 링크해 스스로 검증 | 불필요 | **불완전** — 클라이언트의 `lim` 이 커널 것보다 느슨하면 위험이 되돌아온다.  `caps` 는 `clip`·영역 경계를 주지 않는다 |
| **D** `n == 1` 일 때만 허용 | 불필요 | 정확하지만 §1-2 로 거의 못 덮는다 |

A 가 가장 작고 정확하다.  B 는 `tmr` 9 워드 × 200 삼각형 = 7.2 KB 가 28 KB 배치에
더해지는 형식 변경이라, 얻는 것에 비해 크다.

## 3. A 의 모양

- 제출 경로에 "검증만 하고 돌아온다"는 길을 낸다.  배치 구조는 **바꾸지 않는다**
  (크기 정적 단언이 있다) — ioctl 파라미터 쪽에 낸다
- 훅은 텍스처 + 블렌딩일 때: `n` 개 사다리꼴을 **전부 모의 실행**하고, 하나라도
  거절되면 **아무것도 제출하지 않고** 소프트웨어로 간다
- 전부 통과하면 그때 차례로 제출한다

### 3-1 남는 틈

모의 실행과 실제 제출 사이에 상태가 바뀔 수 있는가?  같은 스레드가 연달아
호출하고 그 사이에 배치를 고치지 않으므로 아니다.  다만 **커널이 그 사이에 모드를
바꿀 수** 있다 — 그러면 실제 제출이 거절되고 위험이 돌아온다.  드문 경우지만
**가능성으로 적어 둔다.**

### 3-2 대가

사다리꼴마다 ioctl 이 하나 더 든다.  블렌딩이 켜진 텍스처에서만.

## 4. 확인해야 할 것

1. 엔진의 블렌딩이 **텍스처 색과 함께** 옳게 도는가.  블렌딩은 색이 정점
   보간에서 올 때만 측정됐다 — 텍스처가 원천일 때는 재본 적이 없다
2. 알파는 어디서 오는가.  `TEXF_TEXALPHA` 가 `Av = At` 와 `Av = Af` 를 가른다.
   블렌딩은 **그 알파**를 쓴다 — GL 의 규칙과 맞는지 재야 한다
3. 목적지 알파.  관문은 이미 Mesa 가 소프트웨어 알파 버퍼를 들고 있으면 거절한다
4. 겹치는 삼각형에서 그리는 **순서**가 보이는가 (블렌딩은 순서에 민감하다)

## 5. 물어볼 것

1. A 와 B 중 어느 쪽인가.  내가 B 의 비용을 과대평가하고 있는가?
2. §3-1 의 틈이 실제로 문제가 되는가.  막는 값싼 방법이 있는가?
3. §4 중 **먼저** 재야 할 것은?  특히 텍스처 알파와 블렌딩의 상호작용
4. 내가 못 본 위험이 있는가

## 6. 실측이 두 번째 장애물을 찾았다 (§76)

교차검토가 오기 전에 §4-2(텍스처 알파와 블렌딩)를 먼저 쟀다.  틀리면 거절이
아니라 **잘못된 그림**이 되는 쪽이기 때문이다.  그리고 그게 옳았다.

### 6-1 텍스처 알파가 블렌드에 닿지 않았다

알파 0…224 를 담은 흰 텍셀 여덟 개를 배경 `0x204060` 위에 `BLEND_OVER` 로 그렸다:

```
   alpha   0   32  64  96      alpha 128   32  64  96
   alpha  32   32  64  96      alpha 160   32  64  96
   alpha  64   32  64  96      alpha 192   32  64  96
   alpha  96   32  64  96      alpha 224   32  64  96
```

**여덟 개가 전부 배경 그대로**다 — 블렌드가 알파 **0** 을 썼다.

### 6-2 원인은 `ALPHACTRL` 의 선택자다

생성된 기술서:

```
   AC_alphasel  비트 24-25   fromtex(0) / diffused(1) / modulated(2) / trans(3)
```

그리고 `OSMGA_MESA_BLEND_OVER = 0x01000154` 의 비트 24-25 는 **1 = diffused** 다.
탐침은 `ALPHASTART` 를 쓰지 않으므로 그 보간 알파가 0 이었다.  **엔진이 블렌드에
실패한 것이 아니라, 시킨 대로 한 것이다.**

### 6-3 이 저장소가 이미 예측해 두었다

`docs/D3_5_ALPHA_BLEND_PLAN.md:305`:

> `fromtex` 도 결국 보간기 값을 쓸 수밖에 없다.  **텍스처를 묶으면 두 값이
> 갈릴 것이며, 그때는 `diffused` 를 명시해야 한다.**

블렌딩을 색만으로 재던 시절에 적힌 말이고, 텍스처를 묶자 정확히 그렇게 됐다.

### 6-4 `fromtex` 로 바꾸니 닿는다

```
   alpha   0   32  64  96      alpha 128  144 160 176
   alpha  32   60  88 116      alpha 160  172 184 196
   alpha  64   88 112 136      alpha 192  200 208 216
   alpha  96  116 136 156      alpha 224  228 232 236
```

램프가 살아났다.  다만 **산술은 아직 못 가렸다** — 정확한 `a·b/255` 보다 일관되게
+1 이고, python 이 맞춰본 여덟 형태 중 **셋**(반올림·올림·`(a(s+1))>>8 +
((256−a)d)>>8`)이 여덟 행 모두에 맞는다.  여덟 점으로는 갈리지 않는다.
**미해결로 남긴다.**

## 7. 그래서 장애물은 둘이다

| | 무엇 | 성격 |
|---|---|---|
| **가** | 부분 제출 (사다리꼴마다 배치) | 두 번 섞인다 — **배치 구조** |
| **나** | `AC_alphasel` 이 텍스처 환경을 따라가지 않는다 | 잘못된 알파로 섞는다 — **인코딩** |

**나** 가 더 값싸고 더 위험하다.  GL 이 요구하는 대응은:

```
   RGB  + REPLACE    Av = Af       -> diffused
   RGBA + REPLACE    Av = At       -> fromtex
   any  + MODULATE   Av = Af · At  -> modulated
```

세 값 모두 하드웨어에 있고, 지금은 `diffused` 하나로 굳어 있다.
