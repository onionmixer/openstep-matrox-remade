# M1-4d0 — 검증기가 `TMR1`/`TMR2` 를 뒤바꿔 읽는다 (계획, 2026-08-23)

**코드는 아직 안 고쳤다.** 이 문서가 교차검토 대상이다.

## 1. 무엇이 어긋나 있나

**빌더**(`OpenStepMGAMesaTriangle.c:454-457`)는

```
   tmr[0] = u 의 dx        tmr[1] = u 의 dy
   tmr[2] = v 의 dx        tmr[3] = v 의 dy
```

로 쓰고, 그 옆에 **측정 근거**가 붙어 있다 — 반대로 두면 소프트웨어 경로와
4410 화소 중 2157 이 어긋나고, 이대로 두면 0 이다.

**검증기**(`OpenStepMGAHW3D.c`)는 반대로 읽는다:

```
   513-516   tmr[1] 을 x 폭으로, tmr[2] 를 y 높이로 묶는다
   538-539   u 에 tmr[2]·dy 를,  v 에 tmr[1]·dx 를 더한다
   568-572   행 걷기에서도 같다
```

## 2. 측정으로 확인했다

`ds/dy` 를 크게(`COORD_MAX/16`) 주고 `dt/dx = 0` 으로 32 행을 그리면, 올바른
읽기에서는 u 가 상한을 넘으므로 **거절**되어야 한다.  실측 **verdict 0 —
통과**한다.  검증기가 `tmr[2]`(=0)를 u 의 y 기울기로 보기 때문이다.

## 3. 무엇이 위험한가, 그리고 무엇은 아닌가

* **주소 안전은 영향 없다** — 클램프/마스크가 색인을 텍스처 안에 붙잡는다.
* 깨진 것은 **"잰 범위 안에 머문다"** 는 규칙, 곧 검증기의 존재 이유다.
  좌표가 아무도 안 본 영역으로 나가도 거절되지 않는다.
* 지금까지 안 드러난 이유: 탐침 대부분이 `tmr[1] = tmr[2] = 0` 이고, GL 경로는
  실제로 범위를 안 벗어나므로 **통과 여부가 같았다**.

## 4. 내가 이 자리를 잘못 읽었던 것

이번 세션에서 나는 "검증기의 배치가 `mga_exa.c` 와 정확히 일치하므로
교차검증된다"고 적었다.  **틀렸다.**  `mga_exa.c` 는 `TMR1 = Y_incx`(= dt/dx)
라 하고 `mga_storm.c` 의 주석은 `TMR1 = "sy inc"`(= ds/dy)라 하여 **두 참고
소스가 서로 다르다**.  우리 빌더는 `mga_storm.c` 쪽을 따르고 **실기 측정으로
확정**했다.  나는 잘못된 읽기를, 하필 그 잘못과 같은 편인 참고 소스에 대고
확인했다.

## 7. 고쳤다 (재부팅 대기, 2026-08-23)

### 7-1 세 자리

```
   기울기 크기 검사   tmr[1] 을 높이로, tmr[2] 를 폭으로  (축을 따라간다)
   상자 경로          u 에 tmr[1]*dy,  v 에 tmr[2]*dx
   행 걷기            같은 자리 두 곳과 오른쪽 끝점
```

기울기 검사도 함께 바꾼 것이 중요하다 — 좌표 평가만 고치면 **범위 증명이
여전히 부실하다**(교차검토 지적, 검산: `u` 의 `dy` 로 인한 변위는
`|ds/dy| × 높이` 이므로 축을 따라야 한다).

### 7-2 헤더에 의미를 못 박았다

```
   u = tmr[6] + tmr[0]*dx + tmr[1]*dy
   v = tmr[7] + tmr[2]*dx + tmr[3]*dy
```

읽는 쪽은 **기억이 아니라 이 네 식**을 써야 한다.  참고 소스가 서로 다르다는
사실(`mga_exa.c` 대 `mga_storm.c`)도 함께 적었다 — 잘못된 읽기가 검사를
통과한 경로가 그것이었다.

### 7-3 회귀 시험

미분을 **하나씩만** 켜고 **폭 ≠ 높이** 인 도형으로, 자기 축에서는 범위를
벗어나고 다른 축에서는 안 벗어나는 기울기를 python 으로 골랐다
(`COORD_MAX/10`: 31 걸음이면 넘고 7 걸음이면 안 넘는다).

고치기 전 커널에서 실행하면:

```
   ok    ds/dx wide      verdict 1
   FAIL  ds/dy tall      verdict 0   <- 뒤바뀜이 잡힌다
   FAIL  dt/dx wide      verdict 0   <- 뒤바뀜이 잡힌다
   ok    dt/dy tall      verdict 1
```

**뒤바뀐 검증기는 각 쌍에서 정확히 하나씩 통과시킨다** — 예측한 무늬 그대로다.
고친 커널에서는 넷 다 거절되어야 한다.

### 7-4 교차검토 판정

| codex 주장 | 내 검증 | 결과 |
|---|---|---|
| 기울기 검사도 **span 을 바꿔야** 한다; 좌표만 고치면 증명이 여전히 부실 | 검산 — 변위는 `기울기 × 자기 축 span` | ✅**채택, 이것이 빠졌으면 절반만 고쳤을 것** |
| 지금까지의 측정은 무효가 아니라 **해석**이 재검토 대상 | 확인 — 원근 측정은 전부 `tmr[1]=tmr[2]=0` 이라 영향 없음 | ✅채택 |
| 재발 방지는 헤더보다 **미분 하나씩·비대칭 도형 회귀 시험** | 그렇게 만들었고 실제로 잡힌다 | ✅**채택 — 이것이 핵심이다** |
| 이름 붙인 접근자로 원시 첨자를 없애라 | 타당하나 이번엔 안 했다 — 커널·빌더가 다른 언어 경계를 넘는다 | ⏭️미착수로 적어 둠 |

## 8. 재부팅 뒤 — 고쳐졌고, 시험의 구멍도 메웠다 (2026-08-23)

### 8-1 회귀 시험이 뒤집혔다

```
   ok  ds/dx wide    ok  ds/dy tall    ok  dt/dx wide    ok  dt/dy tall
```

옛 커널에서 `ds/dy`·`dt/dx` 두 쌍만 통과하던 것이 넷 다 거절된다.  **시험의
판별력이 두 커널에서 실증**됐다.

### 8-2 GL 경로가 조용히 떨어지지 않았다

기울기 경계가 축을 바꿔 묶이므로 세로로 긴 프리미티브에서 **더 빡빡**해진다 —
그래서 단언만 보지 않고 그림을 대조했다:

| 장면 | 색 | 알파 | 하드웨어 화소 |
|---|---|---|---|
| nearest | 24 (이전 24) | 0 (0) | 25964 (25964) |
| linear | 257 (257) | 0 (0) | 25964 |
| RGBA | 24 (24) | 24 (24) | 25964 |

**전부 동일**하고 `software 0` 이다.  조용한 폴백이면 차이가 0 으로 줄어
**개선처럼 보였을** 것이므로, 수치가 같다는 것이 답이다.

### 8-3 내 시험에 있던 구멍

§8-1 의 네 경우는 **기울기 크기 검사만으로도** 거절된다 — 좌표 평가가
고쳐졌는지는 말하지 않는다.  그래서 크기 검사가 허용하는 **정확히 그 기울기**에
시작을 범위 절반에 두어, 마지막 행에서만 벗어나는 쌍을 더했다.  둘 다 거절.

그리고 **"기울기만으로는 합법"을 측정으로** 만들었다 — 같은 기울기를 시작 0
에서 보내면 **통과**한다(verdict 0).  이 대조군이 없으면 위 두 거절이 무엇
때문인지 말할 수 없다.

### 8-4 같은 종류의 결함이 다른 곳에도 있는가 (교차검토 1번)

색·깊이·알파도 `[시작, dx, dy]` 로 같은 모양이다.  확인한 결과 **검증기는
그것들을 아예 보지 않는다** — 주소 안전과 무관하기 때문이다(색은 포화하고,
깊이·알파는 표면 경계가 따로 지킨다).  그러므로 그 자리에는 뒤바뀔 검증기가
없다.  빌더↔하드웨어 쪽은 색 경로가 소프트웨어와 99% 이상 일치한다는 기존
측정이 뒤바뀜을 배제한다(뒤바뀌면 텍스처 때처럼 대량으로 어긋난다).

### 8-5 너무 엄격해지지 않았는가 (교차검토 2번)

`ey = h − 1` 이므로 경계는 **정확하다**.  python 으로 확인: 높이 32 면 허용
최대 기울기 `room/31 = 270600` 이 마지막 행에서 `8388600 ≤ room` 으로 통과하고,
한 단위 더는 `8388631 > room` 으로 거절된다.  높이 1 이면 `ey = 0` 이라 dy
검사를 건너뛴다.  off-by-one 없음.

### 8-6 교차검토 판정

| codex 주장 | 내 검증 | 결과 |
|---|---|---|
| 색·깊이·알파에 같은 결함이 있을 수 있다 | 검증기가 그것들을 **안 본다**는 것을 확인 | ⚖️**부분채택** — 지적은 타당했으나 이 검증기에는 해당 없음 |
| 경계가 반대로 **너무 엄격**할 수 있다 (`range/(h−1)` 이어야) | `ey = h−1` 이 이미 그렇다. python 으로 양쪽 끝 확인 | ❌**기각(이미 정확함)** |
| 그림으로 드러내려면 라우팅 결정도 보이게 그려라 | 타당하다 — 다만 검증기 결함은 그림을 왜곡하지 않고 **거절**로 나타나므로, 여기서는 수치 대조가 더 직접적이다 | ⚖️부분채택 |
| 이름 붙인 접근자로 재발을 막아라 | 타당하나 커널·빌더가 다른 빌드 경계에 있어 공유가 간단치 않다 | ⏭️**미착수로 적어 둔다** |
