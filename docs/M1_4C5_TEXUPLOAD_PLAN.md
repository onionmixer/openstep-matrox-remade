# M1-4 4c — 텍스처를 VRAM 에 올리고 거기 있게 한다

2026-08-22.  **유저랜드만 바뀐다.**

## 1. 지금 어디까지 와 있나

* 빌더가 사다리꼴마다 TMR 여섯 값을 정확히 낸다 (`M1_4C3` §8, 독립 오라클).
* 레지스터 배정과 엔진의 상수(+511)를 측정으로 확정했다 (`M1_4C3` §9·§10).
* 커널이 실제 텍스처 삼각형을 받아들이고 그린다 (`M1_4C4`).
* 아레나가 색·깊이 뒤에 자리를 갖는다 (`M1_4C1`).

**없는 것은 텍스처를 거기 올리는 일뿐이다.**  지금 그림 시험은 raw 프로브가
아레나에 직접 써 넣는다.  GL 프로그램은 아직 아무것도 못 한다.

## 2. Mesa 가 무엇을 주는가 (읽어서 확인)

* `dd.h:504` `TexImage`, `:517` `TexSubImage` — 이미지가 바뀔 때.
* `dd.h:785` `BindTexture`, `:790` `DeleteTexture`.
* `types.h:216` `gl_texture_image.DriverData`, `:826`
  `gl_texture_object.DriverData` — **드라이버가 쓸 수 있는 슬롯이 이미 있다.**
  상주 기록을 여기 둔다.
* `types.h:208` `gl_texture_image.Data` — 이미지 바이트.
* `:198-207` 크기와 `WidthLog2` 등.

## 3. 만드는 것

### 3-1 아레나 할당기 (`OpenStepMGAMesaTexArena.c`)

아레나는 `OSMGAMesaBufferTextureArena` 가 주는 `[origin, origin+bytes)` 다.
그 안을 나눠 쓰는 가장 단순한 것: **고정 개수의 구간 기록 + 최초적합 + 인접
병합**.  텍스처는 많아야 몇 개이고 크기도 크므로 정교한 할당기는 필요 없다.

```c
int  OSMGAMesaTexAlloc(unsigned long bytes, unsigned long *origin);
void OSMGAMesaTexFree(unsigned long origin);
void OSMGAMesaTexFreeAll(void);       /* 표면이 바뀔 때 */
```

**아레나가 움직이거나 사라지면 모든 상주가 무효다.**  아레나의 원점을 들고
있다가 달라지면 전부 버린다 — 색 표면이 다시 묶이면 그렇게 된다.

### 3-2 상주 기록

`image->DriverData` 에 다음을 둔다:

```c
typedef struct {
    unsigned long origin;    /* VRAM 오프셋 */
    unsigned long bytes;
    unsigned long arena;     /* 어느 아레나에서 났는지 -- 바뀌면 무효 */
    unsigned long w, h, pitch;
} OSMGAMesaTexRes;
```

`gl_texture_object` 가 아니라 **image** 에 두는 이유: 크기와 내용은 이미지의
것이고, 객체는 여러 레벨을 갖는다.  지금은 레벨 0 만 올린다.

### 3-3 올리기

`TexImage`/`TexSubImage` 에서 바로 올리지 않고 **표시만 해 둔다**.  실제
복사는 그 텍스처로 처음 그릴 때 한다.  이유: 올릴 곳(아레나)이 그리기
시작 전에는 없을 수 있고, 한 번도 안 쓰는 텍스처를 올리는 것은 낭비다.

포맷은 지금 하나뿐이다 — 커널이 `TEXFMT_TW32` 만 받는다.  Mesa 의 이미지는
`GL_RGBA` 등 여러 포맷이므로 **32비트로 펴서** 쓴다.  엔진의 화소 배치는
`0x00RRGGBB` 다(`Buffer.c` 가 색 표면에 대해 그렇게 적어두었다).

### 3-4 무효화

`TexImage`, `TexSubImage`, `TexParameter`(감싸기·필터가 바뀌면), `BindTexture`,
`DeleteTexture` 에서 기록을 무효로 한다.  **Mesa 의 `Dirty` 목록에 기대지
않는다** — `M1_4_TEXTURE_PLAN.md` §4b 가 이미 그 이유를 적어두었다:
상태 갱신에서 지워지고 `TexSubImage2D` 는 거기 올리지도 않는다.

`DeleteTexture` 는 아레나를 돌려준다.  `OpenStepMesaAccelReleaseBuffer` 도
전부 돌려준다 — **지금 그것이 색과 깊이만 푸는 것이 누수의 자리**다.

## 4. 무엇을 안 하는가

* 밉맵.  레벨 0 만.
* `GL_REPEAT`.  커널이 `CLAMPUV` 를 고정한다.
* 여러 텍스처 유닛.
* 압축 포맷.
* **선택기는 아직 `TEXTURE_BIT` 를 받지 않는다** (4d).  그러니 이 단계가
  끝나도 GL 프로그램은 여전히 소프트웨어로 그린다 — 시험은 백엔드를 직접
  부른다.

## 5. 어떻게 증명하는가

1. **할당기 단위 시험** (호스트) — 최초적합·병합·고갈·이중 해제.
   경계값을 포함한다.
2. **올리기 시험** (실기) — 알려진 이미지를 올리고 VRAM 을 읽어 바이트가
   그대로인지.  포맷 변환이 맞는지 여기서 드러난다.
3. **무효화 시험** (실기) — 올린 뒤 `glTexSubImage2D` 로 한 텍셀을 바꾸고,
   다시 그렸을 때 **바뀐 값이 보이는지**.  포인터가 그대로라서 못 잡는
   경우가 이 단계의 고전적인 실패다.
4. **누수 시험** — 컨텍스트를 만들고 텍스처를 올리고 부수기를 반복해도
   아레나가 다시 가득 차지 않는지.
5. **그림 시험** — 올린 텍스처로 삼각형을 그려 화소가 오라클과 맞는지.
   지금 raw 프로브가 하는 일을, 올린 텍스처로.

## 6. 위험

* **아레나가 작다.**  1024×768 에서는 아예 없다(`M1_4C1` §3).  그 경우
  할당은 실패해야 하고, 실패는 소프트웨어로 가는 것이지 그리다 마는 것이
  아니다.
* **크기 제한**: 커널이 2048×2048, 피치 2047 텍셀까지 받는다.
* **512×512 RGBA 는 1 MiB** 다.  320×240 표면의 아레나가 2.55 MiB 이므로
  두 장이면 절반이 넘는다.  고갈은 예외가 아니라 일상이다.

### 7-1 내가 먼저 확인한 것

* Mesa 는 `DriverData` 를 **전혀 건드리지 않는다** — 트리 전체에서 언급이
  주석 둘뿐이고, `teximage.c:738` 은 프록시를 비울 때도 *"DriverData 만 빼고"*
  라고 적어두었다.
* `glTexImage2D` 는 **기존 이미지 구조를 재사용**하고 `Data` 만 해제한다
  (`teximage.c:1497-1503`, `:1376-1379`).  그러니 `DriverData` 가 살아남고,
  **`TexImage` 에서 반드시 무효화해야 한다.**
* `Driver.DeleteTexture` 는 이미지 해제보다 **먼저** 불린다
  (`texobj.c:505`, `:634`, `context.c:526`) — 기록을 풀 기회가 있다.
  그 뒤 `gl_free_texture_object` 가 이미지를 훅 없이 해제하므로
  (`texobj.c:147-157`), **`DeleteTexture` 가 객체의 모든 레벨을 돌아야 한다.**

## 8. 고친 설계

1. **아레나 매핑을 먼저 만든다.**  `OSMGAMesaBufferTextureMap()` 이 아레나를
   `mmap` 하고 CPU 포인터를 준다.  페이지 정렬은 아레나 원점이 이미 지킨다.
2. **세대**: 표면이 묶일 때마다 `texEpoch++`.  상주 기록은 자기 세대를 들고
   있고, 다르면 무효다.  원점 비교는 쓰지 않는다.
3. **받아들이는 것**: 2D, 레벨 0, 테두리 0, 압축 아님, `GL_RGBA`
   (`abgr8888`), 폭·높이 ≤ 2047.  나머지는 상주를 만들지 않는다 —
   그러면 선택기가 나중에 소프트웨어로 보낸다.
4. **무효화**: `TexImage`, `TexSubImage`, `DeleteTexture` 셋뿐.
5. **바이트**: Mesa 의 `Data` 는 R,G,B,A 순의 바이트다.  목적지는
   `0x00RRGGBB` 라는 **숫자**다.  포인터 캐스트로 옮기지 않고 바이트를 읽어
   숫자를 만든다 — 엔디안에 기대지 않는다.

## 9. 고친 증명

1. **할당기** (호스트) — 최초적합·병합·고갈·이중 해제, 그리고 **세대가
   바뀌면 옛 기록이 거부되는지**.
2. **바이트 순서** (실기) — `glTexImage2D` 로 각 채널이 다른 값인 텍셀을
   올리고 VRAM 을 읽어 `0x00RRGGBB` 인지.  네 채널이 같은 값이면 뒤섞임을
   못 잡으므로 **네 채널을 다르게** 한다.
3. **재정의** (실기) — 같은 객체에 `glTexImage2D` 를 **다른 크기로** 다시
   하고, 옛 자리가 반환됐는지 할당기 상태로 확인한다.
4. **부분 갱신** (실기) — `glTexSubImage2D` 로 한 텍셀만 바꾸고 그 텍셀이
   VRAM 에서 바뀌었는지.
5. **삭제** (실기) — `glDeleteTextures` 뒤 할당기가 그 자리를 돌려받았는지.
   그리고 참조가 남아 있으면 아직 안 돌려주는지.
6. **그림** (실기) — 올린 텍스처로 삼각형을 그린다.  선택기가 아직
   `TEXTURE_BIT` 를 안 받으므로 **백엔드를 직접 부르고**, 제출한
   `texorg`·`texPitch`·`texFormat` 을 함께 단언한다.  화소만 보면 소프트웨어로
   통과할 수 있다.
