# M19 — 진짜 응용에서 가속이 480 배 느리다 (2026-08-29, 코딩 전)

지금까지의 측정은 전부 합성 고정물이었고, `M15` 는 미러를 **일부러 껐다**
(present 모드) — enqueue 비용을 분리하려고, 그리고 그렇게 적었다.  실제
모델을 한 번 돌리자 다른 그림이 나왔다.

## 1. 사실

Utah teapot, 640x480, 두 개:

```
경로          두 teapot     총합
소프트웨어      0.061 s     0.096 s
사다리꼴       29.364 s    29.433 s
WARP          29.349 s    29.412 s
```

**가속이 480 배 느리다.**  그리고 그리기는 멀쩡하다:

```
surface walked back     : 129 times
source triangles drawn  : 16106
submissions             : 193   (83 sources per submission)
triangles left to Mesa  : 0
refused as unsupported  : 0
share drawn by the card : 100%
```

되돌림도, 거절도, 소프트웨어 폴백도 없다.  **되읽기가 전부다.**

## 2. 산술이 닫힌다

```
29.432 s / 129 미러 = 228.2 ms/미러
REMAINING_WORK 가 512x384 에서 잰 값 146.722 ms
640x480 은 화소가 1.56 배 -> 229.3 ms 예상
```

**228.2 대 229.3** — 미러 비용 모형이 그대로 맞는다.

그리고 응용은 표면을 **한 번** 읽는다(TIFF 를 쓸 때).  그러므로
**129 번 중 128 번이 낭비**이고 그것이 실행의 **99.2%** 다.

## 3. 왜 이렇게 되나

미러는 **렌더 브래킷이 닫힐 때마다** 돈다(`Hook.c` 의 `RenderFinish`).
이유는 문서에 있다 — 엔진이 그린 것은 이 라이브러리가 볼 수 없으므로,
브래킷이 무엇을 그렸는지 모른 채로 표면을 응용 배열과 맞춰 두어야 한다.

OSMesa 에서는 응용이 배열 포인터를 쥐고 **언제든 말없이 읽을 수 있다.**
그래서 미러가 성급하다.

## 4. 후보 둘

```
(A) 미러를 미룬다        읽을 자격이 생기는 지점(glFinish?)까지.
                         129 -> glFinish 횟수.  그러나 finish 없이 읽는
                         응용의 의미가 바뀐다 — 소프트웨어 경로에서는
                         부분 결과가 보이던 것이 안 보이게 된다
(B) 미러를 좁힌다        그린 사각형만 복사한다.  의미는 그대로이고
                         각 미러가 싸진다.  teapot 의 브래킷 하나는
                         표면의 작은 부분만 건드린다
```

`bufDirty` 는 **플래그**이지 사각형이 아니다(`Buffer.c`).  (B) 는 그것을
사각형으로 만드는 일이다.

## 5. codex 에 물을 것

1. (A) 와 (B) 중 어느 쪽인가, 아니면 둘 다인가?  (A) 의 의미 변화가
   실제로 허용되나 — OSMesa 계약은 finish 없이 읽는 것을 무엇이라 하나?
2. (B) 의 사각형은 어디서 오나 — 커널이 클립 상자를 알고, 훅은 제출한
   사다리꼴의 y 범위를 안다.  어느 쪽이 옳은 출처인가?
3. 이 480 배가 **이 응용만의 것**인가?  offscreen + 되읽기가 흔한 형태인가,
   아니면 present 모드로 화면에 그리는 것이 실제 사용례인가?
4. `M15` 의 결론(WARP 이 3.5~26% 빠르다)이 이것 때문에 무효인가, 아니면
   서로 다른 끝점을 재는 별개의 참인가?
5. 빠뜨린 것.

## 6. 두 후보의 상한 — 재고 나서 말한다

```
(A) glFinish 까지 미룬다   teapot 은 finish 를 두 번 한다 -> 129 -> 2
                           29.432 s -> 약 0.456 s   (64.5 배)
(B) 그린 사각형만 복사      teapot 이 표면의 21.6% 를 덮는다 -> 상한 4.6 배
                           그리고 브래킷 하나의 외접상자는 그 브래킷이
                           실제로 덮는 것보다 크다
```

## 7. codex 교차검토 판정

| codex 주장 | 검증 | 결과 |
|---|---|---|
| **(A) 를 기본값으로 두면 안 된다** — 이 트리의 OSMesa 헤더에는 *"읽기 전에 `glFinish`"* 같은 규칙이 **없다**.  `glEnd`/`glClear` 뒤의 날 읽기가 다른 것을 보게 된다 | 논리 + 헤더 | ✅ **채택.  기본값은 지금 그대로** |
| 대신 **명시적 옵트인 계약**으로 — 그리고 `glFinish` 만이 아니라 `OSMesaGetColorBuffer`·재바인드·해제까지 덮어야 한다.  `glFlush` 는 완료 보장이 아니다 | 논리 | ✅ **채택** |
| **(B) 의 사각형 출처가 둘 다 틀렸다** — 커널의 클립은 **천장**이지 쓴 화소가 아니고(대개 표면 전체), 훅의 사다리꼴 y 범위는 부족하며 `fxbndry` 는 x 경계가 아니다.  보수적 경계는 **변환·클립된 삼각형의 외접상자 ∩ 시저** | 논리 | ✅ **채택.  내 두 후보 출처가 다 틀렸다** |
| 그리고 그것으로도 **엔진이 쓴 것만** 덮는다 — 소프트웨어 폴백, 픽셀 전송, OSMesa 의 빠른 경로가 각자 영역을 보고하거나 **전체를 더럽다고** 해야 한다.  지금 `RenderStart` 가 무조건 더럽히므로 엔진 사각형만 더해서는 옳으면서 이득일 수 없다 | 논리 | ✅ **채택.  (B) 는 `bufDirty` 리팩터가 아니라 영역 소유권 설계다** |
| 129 가 **실제 바이트 복사 수**인지 미러 훅 호출 수인지 계측하라; 겹치는 사각형이 있으면 "화소 x 복사" 가 진짜 예산이다 | 논리 | ✅ **채택 — 아직 안 쟀다** |
| `M15` 는 자기 끝점에서 여전히 참이나 **표제를 좁혀야 한다** — 전달된 teapot 에서 WARP 대 사다리꼴은 **0.05%** 이고 미러가 층 차이를 완전히 가린다 | 측정과 대조: 29.349 대 29.364 초 = 0.05% | ✅ **채택** |

## 8. 그러므로

**기본 전달은 그대로 둔다.**  (A) 는 기본값이 될 수 없고, (B) 는
`bufDirty` 를 사각형으로 바꾸는 일이 아니라 **모든 쓰는 주체의 영역
소유권**을 정하는 일이다.  이 부하에 대해 128 번의 되읽기를 없앨 수 있는
길은 **명시적 지연 전달 모드** 하나뿐이고, present 모드가 그 소유권 계약의
원리를 이미 보여 준다.

**측정은 남기고 최적화는 하지 않는다** — 설계가 있어야 할 자리에 리팩터를
넣지 않는다.

## 9. 덤 — 진짜 모델에서 그림은 어떤가

같은 teapot 을 세 경로로 그려 화소를 비교했다(640x480, 307200 화소):

```
경로         다른 화소   1 레벨    2..8    8 초과
사다리꼴          409      406        0        3     (0.13% / 0.001%)
WARP           36808    35846      914       48    (11.98% / 0.016%)
```

**WARP 의 11.7% 는 선언된 한 레벨 잘라내기**이고, 부드럽게 음영진 모델에서는
거의 모든 내부 화소가 그렇게 반올림된다 — 놀랄 일이 아니라 예상된 것이다.

**관용치를 넘는 것은 0.31%(962 화소)** 이고, 사다리꼴은 0.001%(3 화소)다.
절대값으로는 작지만 **300 배** 차이다.
