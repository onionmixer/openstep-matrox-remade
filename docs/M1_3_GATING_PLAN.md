# M1-3 게이팅 — 언제 하드웨어를 쓰고 언제 소프트웨어로 두는가

기준일: 2026-08-20
상태: 계획. **codex 교차검토 1회 완료(2026-08-20)** 후 개정판 — §5-3이 새로 생겼고 §5-2가 정정됐다.
선행: M1-2g 완료. `M1_3_MESA_BACKEND_PLAN.md`의 전제 문서.

## 0. 요구사항 (operator, 2026-08-20)

| 상황 | 결과 |
| --- | --- |
| 우리 pkg 미설치 | **소프트웨어 렌더링** (지금과 동일) |
| pkg 설치, 우리 드라이버가 디스플레이를 소유 | 하드웨어 가속이 **가능** |
| 그 위에서 Configure.app의 `Mesa Acceleration`이 켜짐 | 하드웨어 가속이 **동작** |

세 단계가 **독립**이라는 점이 요점이다. 2번이 참인데 3번이 거짓이면
소프트웨어로 돌아야 하고, **그 판단이 런타임에 일어나야 한다.**

## 1. 왜 이것을 먼저 정하는가

M1-3a를 먼저 짜면 "우리 하드웨어가 있다"를 전제한 코드가 된다. 게이팅을
나중에 끼우면 **되돌림 경로가 시험되지 않은 채 남는다** — 그리고
되돌림은 정상 경로보다 **더 자주 쓰일** 코드다(가속을 끈 사용자가 다수일
것이므로).

## 2. 라이브러리는 **하나**다

두 벌(`libGL` 소프트웨어판/하드웨어판)을 만들어 고르게 하지 않는다.
**하나가 실행 시점에 탐지한다.**

이유:
- 두 벌이면 **소프트웨어 경로가 시험되지 않는다** — 개발자는 하드웨어판만
  돌린다.
- pkg를 지우면 라이브러리도 사라져 원래 Mesa로 돌아가야 하는데, 두 벌이면
  어느 것이 남았는지가 설치 상태에 얽힌다.
- 같은 pkg가 **우리 드라이버가 아닌 기계**에서도 동작해야 한다(요구 1).

## 3. 탐지 — "우리 파라미터에 답하면 우리다"

새 읽기 파라미터를 드라이버에 더한다:

```
"OSMGAHW3DCaps"  ->  [magic, version, flags, maxTri, clipW, clipH, ...]
```

라이브러리는 `IODeviceMaster`로 `Display0`을 찾아 이 파라미터를 읽는다.

| 결과 | 뜻 | 동작 |
| --- | --- | --- |
| `lookUpByDeviceName` 실패 | 디스플레이가 없다 | 소프트웨어 |
| `getIntValues` 실패 | **우리 드라이버가 아니다** | 소프트웨어 |
| `magic`이 다름 | 우리 것인데 다른 무언가 | 소프트웨어 |
| `version`을 모름 | pkg 스큐 | 소프트웨어 |
| `flags`에 ENABLED 없음 | Configure에서 껐다 | 소프트웨어 |
| 전부 통과 | | 하드웨어 |

**"파라미터에 답하는가"가 곧 신원 확인이다.** 다른 드라이버는 그 이름을
모르므로 `getIntValues`가 실패한다 — 별도의 식별 수단이 필요 없다.

### 3-1. 버전 핸드셰이크가 필요한 이유

배치 구조체는 `magic`/`version`을 이미 갖고 있고 커널이 검사한다. 그런데
**그것은 제출 시점**이다. 드라이버만 새 pkg이고 라이브러리가 낡았다면
(또는 반대라면) 구조체 배치가 달라 **제출이 거부되거나 더 나쁘게는 엉뚱한
필드로 해석된다.**

→ 탐지 시점에 **양쪽이 버전을 확인**하고, 모르는 버전이면 **가속을 아예
켜지 않는다.** 거부를 처리하는 것보다 시작하지 않는 것이 낫다.

## 4. Configure.app 스위치

`Mesa Acceleration`을 `Instance0.table`/`Default.table`에 더하고 C1의
인스펙터에 체크박스를 하나 더한다. **기존 두 개(`Storm 2D Test`,
`VRAM Mmap`)와 같은 방식**이므로 새 기법이 필요 없다.

### 4-1. 다른 스위치와의 관계

3D 경로는 **명령 창과 VRAM 창**을 쓴다. 그것은 `VRAM Mmap`이 cdevsw를
등록해야 존재한다.

**`Mesa Acceleration`이 `VRAM Mmap`을 함의하게 한다** — 켜면 드라이버가
등록을 시도하고, 실패하면 `flags`에 ENABLED를 **넣지 않는다.**
사용자가 스위치 두 개의 관계를 알 필요가 없어야 한다.

**개발용 스위치들과는 독립이다.** `Storm 2D Test`/`DMA Ring Test`/
`WARP Test`/`Raster Test`는 부팅 프로브이고 가속과 무관하다.

## 5. 되돌림 규율 — **끈적하게(sticky), 조용히**

가속을 켠 뒤에도 실패할 수 있다: 장치가 안 열림, mmap 실패, 제출 거부,
DMA 타임아웃.

**규칙**

1. **어느 실패든 그 컨텍스트에서 가속을 영구히 끈다.** 반쯤 동작하는
   경로는 소프트웨어보다 나쁘다 — 프레임마다 다르게 실패한다.
2. **끄는 것은 조용히, 단 한 번은 알린다.** 첫 실패에 `syslog` 한 줄.
   그 뒤로는 침묵. 프레임마다 로그를 뱉으면 그 자체가 고장이다.
3. **그림은 계속 나와야 한다.** 되돌림 뒤 소프트웨어 경로가 그 프레임을
   완성한다. 사용자가 알아채는 것은 느려짐뿐이어야 한다.
4. **부분적으로 그려진 프레임을 남기지 않는다.** 배치를 제출하다 실패하면
   그 배치의 삼각형들을 **소프트웨어로 다시 그린다.** 그러려면 배치를
   비우기 전까지 정점 인덱스를 들고 있어야 한다(§5-1).

### 5-1. 되돌림이 배치 설계에 거는 조건

배치에 삼각형을 쌓아 두었다가 제출이 실패하면, 그 삼각형들을 소프트웨어로
다시 그려야 한다. 따라서 **배치와 나란히 그 삼각형들의 정점 인덱스도
쌓아 둔다.**

비용은 삼각형당 4워드(`v0,v1,v2,pv`)이고, 200개면 3.2 KiB다. 유저랜드
메모리이므로 문제되지 않는다.

**이것을 처음부터 넣는다.** 나중에 끼우면 되돌림 경로가 시험되지 않는다.

## 5-2. Mesa가 이것을 실제로 허용하는지 — 트리로 확인했다

### 탐지를 어디에 두는가

`dd.h:66-69`가 못박는다: 훅 포인터는 **드라이버의 `MakeCurrent`에서 처음
초기화**한다. 그것이 컨텍스트당 가장 이른 지점이다.

단 `gl_pipeline_init`은 **컨텍스트 생성 때 한 번**(`context.c:978`)
불린다. 즉 `MakeCurrent`에서는 **파이프라인 단계를 등록할 수 없다.**

→ **파이프라인 단계를 등록하지 않는다.** 우리에게 필요한 것은 프리미티브
훅뿐이고, 그것은 `UpdateState`에서 설치된다. 등록하지 않으면
`RegisterPipelineStages`가 `NULL`이라 Mesa가 기본 파이프라인을 쓴다
(`pipeline.c:184-190`) — **즉 "안 하는 것"이 곧 stock 동작이다.**

### 가속을 안 켰을 때 stock과 같아지는가 — **초안이 부정확했다**

초안은 "훅을 전부 `NULL`로 두면 된다"고 썼다. **`UpdateState`는 예외다.**
`gl_update_state`가 그것을 **무조건** 부른다(`state.c:1111`, 가드 없음).
`NULL`이면 죽는다. 교차검토가 짚었고 원본으로 확인했다.

정확한 서술: **우리 것을 설치하지 않고 포트의 기존 `UpdateState`를
그대로 둔다.** 나머지 프리미티브 훅은 `NULL`이어도 되고,
`Driver.TriangleCaps`가 0이면 `IndirectTriangles = ctx->TriangleCaps & ~0`
이 전부 켜져 `DD_SW_RASTERIZE`가 더해지며(`state.c:1091-1092`) Mesa가 스스로
소프트웨어 함수를 고른다(`state.c:1119-1124`).

**`ctx->TriangleCaps`는 건드리지 않는다** — 그것은 Mesa의 살아 있는 GL 상태
마스크이지 우리 것이 아니다. 우리가 만지는 것은 `ctx->Driver.TriangleCaps`
뿐이다.

### 중간에 끄는 것 — **여기가 §4-3 요령의 진짜 이유다**

상태가 바뀌면 Mesa가 훅을 지우고 `UpdateState`를 부르므로
(`state.c:1098-1111`), 그때 설치하지 않으면 소프트웨어로 채워진다.

**그런데 상태가 안 바뀌면 Mesa는 다시 묻지 않는다.** 우리 훅이 설치된 채로
계속 불린다. 따라서 **중간에 끄려면 우리 훅이 계속 불리면서 스스로
소프트웨어 함수에 넘겨야 한다.**

→ `M1_3_MESA_BACKEND_PLAN.md` §4-3의 저장된 소프트웨어 포인터는
**기하 단위 되돌림을 위한 편의가 아니라, 끈적한 비활성화의 필수 조건**이다.
둘이 같은 기제를 쓴다.

**이것을 M1-3a에서 함께 검증한다** — 훅이 설치된 상태에서 플래그를 끄면
그림이 소프트웨어와 같아지는가.

그리고 **훅을 도중에 바꿔치기하는 방법은 통하지 않는다**: `gl_render_vb`가
디스패치 표를 루프 **전에** 잡는다(`vbrender.c:680-684`, 루프는 `:704`).
그 VB는 이미 잡힌 표로 끝까지 간다. **넘겨받아 위임하는 것만이 방법이다.**

## 5-3. **우리 포트는 OSMesa다** — 그리고 그것이 이 단계의 의미를 정한다

교차검토는 X/Mesa 경로로 답했다(`xmesa1.c`의 `XMesaCreateContext` 등).
**우리 포트는 그것이 아니다.** 빌드 스크립트가 `osmesa.o`와
`OSMesaCreateContext`의 존재를 확인한다
(`build/build-openstep-mesa342.csh:21-28`). 구조적 답(생성 시점 훅이 있다,
`UpdateState`는 무조건 불린다)은 그대로 유효하지만 **위치는 다르다** —
`src/OSmesa/osmesa.c`의 `OSMesaCreateContext`(`:101`)와
`osmesa_update_state`(`:82`)다.

### OSMesa가 "시스템 RAM에 그린다"는 것은 **제약이 아니었다**

초안은 이렇게 적었다: OSMesa는 호출자 버퍼에 그리고 Storm 엔진은 VRAM만
쓰므로 **가속 경로가 프레임마다 되읽어 복사해야 한다.** 그래서 이 단계는
속도와 무관하다고 결론지었다.

**operator 지적으로 다시 보니 그 전제가 틀렸다.**

`OSMesaMakeCurrent(ctx, buffer, type, w, h)`는 **버퍼 포인터를 인자로
받는다**(`osmesa.c:371-382`). 그것이 `malloc`한 메모리여야 한다는 제약은
어디에도 없다. **S4a로 유저랜드가 VRAM을 mmap할 수 있으므로 그 포인터를
그냥 넘기면 된다.**

맞춰야 할 것도 OSMesa가 전부 제공한다:

| 필요 | OSMesa |
| --- | --- |
| G450의 32bpp 배치 | `OSMESA_BGRA`(0x1) / `OSMESA_ARGB`(0x2) (`osmesa.h:76-77`) |
| 행 간격 = VRAM pitch | `OSMESA_ROW_LENGTH` → `ctx->rowlength` (`osmesa.c:427`) |
| 상하 방향 | `OSMESA_Y_UP` (`osmesa.h:87`) |

→ **되읽기가 사라진다.**

```
소프트웨어 경로: OSMesa의 span 함수가 매핑된 VRAM에 직접 쓴다
하드웨어 경로:   우리 훅이 DMA로 같은 VRAM에 그린다
```

**둘이 같은 곳에 쓴다.** 그리고 §5의 되돌림이 훨씬 단순해진다 —
소프트웨어로 넘어가도 그림이 **같은 버퍼에 계속 쌓인다.** §5-1의
"반쯤 그려진 프레임"이 프레임 단위 문제에서 삼각형 단위 문제로 줄어든다.

### OSMesa를 **대체하지 않는다**

"어차피 Mesa에 붙일 거면 OSMesa를 대신 만들면 되지 않나"는 자연스러운
물음이고, **필요 없다**고 본다:

- OSMesa가 하는 일(span 쓰기, clear, 컨텍스트 관리)을 다시 짜는 것은
  **소프트웨어 경로를 새로 만드는 것**이다. 그것은 이미 실기에서 도는
  검증된 코드다.
- 대체가 벌어 줄 유일한 것은 **화면에 올리기**인데, 그것은 OSMesa 때문이
  아니라 **WindowServer와의 협조가 없어서** 막혔다(S5 §2).
  **M2의 문제이지 OSMesa의 문제가 아니다.**
- 더블 버퍼링과 flip도 OSMesa 위에서 된다 — VRAM에 앞/뒤 버퍼를 잡고
  뒤 버퍼를 `OSMesaMakeCurrent`에 주고, 교체 때 포인터를 바꾼다.

### 그래도 이 단계는 여전히 정확성 시험이다

되읽기가 없어졌으니 "속도일 수 없다"의 이유 하나는 사라졌다. **남은
이유는 화면에 못 올린다는 것**이다. 오프스크린 용도(스크린샷, 오프스크린
합성)에는 그 자체로 쓸모가 있으나 **일반 사용자가 체감하는 변화는 M2
전까지 없다.**

### 확인 완료 — 교차검토 후 원본으로 재확인했다

| # | 항목 | 결과 |
| --- | --- | --- |
| 1 | 바이트 순서 | **`OSMESA_ARGB`** (little-endian). `osmesa.c:156-161`에서 `bshift=0, gshift=8, rshift=16, ashift=24` → 워드가 `0x00RRGGBB` |
| 2 | `ROW_LENGTH` | 색 경로 전부가 `rowaddr[]`를 거친다(`:286`, `:553`). 전체 클리어도 `rowlength*height`를 쓴다(`:663`) |
| 3 | `Y_UP` | 기본값 **참**(`:252`). 우리 프레임버퍼는 base가 맨 윗줄이므로 **0으로 꺼야 한다** |
| 4 | 깊이 버퍼 | **주소를 지정할 수 없다.** `OSMesaGetDepthBuffer`는 **읽기 전용**(`:480-497`) |

**1번은 우리 실측과 대조해 확인했다.** D3-0에서 빨강 200·초록 100·파랑 50을
넣었을 때 되읽은 값이 `0x00c86432`였다 — R이 비트 16-23, G가 8-15, B가 0-7.
`OSMESA_ARGB`의 little-endian 배치와 **정확히 같다.** 바이트 순서를 추론한
것이 아니라 **이미 측정된 픽셀값과 맞춘 것**이다.

### 4번 — 깊이는 공유할 수 없다. 그런데 형식은 맞는다

색은 같은 버퍼를 공유해도 **깊이는 안 된다.** 우리 하드웨어 깊이는 VRAM에
있어야 하고 Mesa의 깊이는 `MALLOC`으로 잡힌 시스템 RAM이다
(`buffers.c:560`, `depth.c`). **되돌림이 프레임 중간에 일어나면 소프트웨어가
하드웨어의 깊이를 못 본다.**

**그런데 형식이 맞는다.** `config.h:145`가
`DEFAULT_SOFTWARE_DEPTH_BITS 16`이고 그 경로가 `GLushort zbuffer[]`를 쓴다
(`depth.c:168`). **우리 하드웨어 깊이도 16비트다**(D3-3, `MACCESS`의
`zwidth` 기본값).

→ 되돌림 시 **VRAM 깊이를 Mesa의 깊이 버퍼로 16비트 그대로 복사**하면
된다. 변환이 필요 없다. 실패라는 드문 경로에서만 치르는 비용이다.

**남은 것은 stride와 상하 방향**이다 — 색은 `ROW_LENGTH`/`Y_UP`으로
맞추는데 깊이에는 그런 손잡이가 없다. **M1-3d(깊이) 전에 정한다.**

**깊이를 쓰지 않는 동안에는 이 문제가 없다.** M1-3a~c는 영향받지 않는다.

## 6. 검증 방법

각 단계가 **독립적으로 확인 가능**해야 한다.

- **V-G1 (pkg 없음)**: 라이브러리를 걷어내고 원래 Mesa로 돌린 뒤 예제가
  그대로 동작하는가. 이건 사실상 "우리가 아무것도 안 깼는가"다.
- **V-G2 (드라이버가 우리 것이 아님)**: 탐지가 실패하는 경로를
  **강제로** 태운다 — 파라미터 이름을 일부러 틀리게 한 빌드로. 소프트웨어로
  그려지고 **그림이 옳은가.**
- **V-G3 (스위치 off)**: `Mesa Acceleration = No`로 부팅. `flags`에
  ENABLED가 없고 소프트웨어로 그려지는가.
- **V-G4 (스위치 on)**: 켜고 부팅. 하드웨어로 그려지고 **G3의 그림과
  픽셀 단위로 같은가**(±1).
- **V-G5 (런타임 실패)**: 제출이 거부되도록 일부러 잘못된 배치를 만들어
  **되돌림이 실제로 일어나고 그림이 완성되는지** 본다. 로그가 **한 줄만**
  나오는지도 본다.
- **V-G6 (버전 스큐)**: 라이브러리의 기대 버전을 하나 올린 빌드로 —
  가속이 **켜지지 않고** 소프트웨어로 그려지는가.

**V-G2·V-G5·V-G6이 이 계획의 핵심이다.** 정상 경로는 어차피 M1-3에서
확인되고, **여기서 확인할 것은 실패 경로**다.

## 7. 이 계획이 `M1_3_MESA_BACKEND_PLAN.md`에 거는 변경

- M1-3a에 **탐지와 되돌림을 먼저 넣는다.** 훅을 채우기 전에.
- 배치가 정점 인덱스를 함께 보관한다(§5-1).
- 모든 단계의 검증에 **"가속을 끄면 같은 그림"** 을 더한다.

## 8. 결정하지 않은 것

- pkg가 무엇을 담고 어떻게 설치하는지. **이 문서는 라이브러리가 하나이고
  런타임에 탐지한다는 것만 정한다.**
- 여러 디스플레이. 지금은 `Display0` 하나를 본다.
- 프로세스마다 탐지 비용. 컨텍스트 생성 시 한 번이며 측정하지 않았다.

## 9. 논리 재검토 (2026-08-20, operator 요청)

세 가지를 다시 따졌다: 우리 드라이버를 안 쓸 때의 되돌림, pkg가 만드는
OpenGL 라우팅 변경, 그리고 **우리 것이 아무것도 없어도 포팅된 Mesa가
소프트웨어로 멀쩡히 도는가.**

### 9-1. 라우팅 — **바꿀 것이 없다. 정적 라이브러리다**

`packaging/openstep/OpenStepMesa342Libraries.info`가 못박는다:

> Intel i486-only **static** OpenGL 1.2, GLU and OSMesa libraries

`/LocalDeveloper`에 **정적 라이브러리**로 깔린다. 공유 라이브러리가 아니다.

**결과가 여러 가지로 단순해진다:**

- **가로챌 동적 링크가 없다.** `dlopen`도, shlib 그림자도, `LD_PRELOAD`류도
  필요 없다.
- **선택은 앱을 빌드할 때 일어난다.** 이미 빌드된 바이너리는 자기 안에
  링크된 사본을 계속 쓴다 — 우리가 무엇을 설치하든 영향이 없다.
- **기존 Mesa pkg의 산출물을 건드릴 이유가 없다.**

### 9-2. ~~따라서 우리 pkg는 두 번째 라이브러리를 넣는다~~ — **철회됨(§11)**

> **이 절은 틀렸다.** 앱이 `-lGL_mga`로 링크해야 하므로 앱의 빌드를
> 바꾼다. §11-1이 대신한다: **설치된 `libGL.a`를 제자리에서 교체한다.**

기존 `libGL.a`를 **덮어쓰지 않는다.** 같은 Mesa 소스에 우리 백엔드를 더해
빌드한 **별도 이름**(예: `libGL_mga.a`)을 넣는다.

| 상황 | 앱이 링크한 것 | 결과 |
| --- | --- | --- |
| 우리 pkg 미설치 | `libGL.a` | 소프트웨어. **우리가 손댄 것이 없다** |
| 설치했으나 앱이 stock을 링크 | `libGL.a` | 소프트웨어 |
| `libGL_mga.a` 링크, 드라이버 없음/스위치 off | — | 탐지 실패 → **소프트웨어** |
| `libGL_mga.a` 링크 + 드라이버 + 스위치 on | — | 하드웨어 |

**3번 줄이 성립하는 이유가 중요하다**: `libGL_mga.a`의 소프트웨어 경로는
stock과 **같은 소스**다. 가속을 켜지 않으면 stock과 같은 코드가 돈다.

→ operator 요구("우리 것이 없어도 Mesa가 소프트웨어로 이상 없이")는
**우리가 stock 산출물을 건드리지 않는 것만으로 충족된다.** 되돌림 코드의
정확성에 기대지 않는다 — **가장 강한 형태의 보장**이다.

### 9-3. 정정 — "되읽기가 사라진다"는 **조건부였다**

§5-3에서 "VRAM을 버퍼로 주면 되읽기가 사라진다"고 썼다. **누가 주는지를
빼먹었다.**

`OSMesaMakeCurrent(ctx, buffer, ...)`를 부르는 것은 **애플리케이션**이다.
앱이 평범한 메모리를 주면 우리는 VRAM에 그린 뒤 **거기로 복사해야 한다.**
되읽기는 앱이 협조할 때만 사라진다.

### 9-4. 그리고 투명한(앱 수정 없는) 가속에는 **논리적 구멍**이 있다

앱 버퍼를 그대로 두고 가속하려면 두 가지 중 하나여야 한다:

**(가) 하드웨어는 VRAM, 소프트웨어는 앱 버퍼.**
→ **깨진다.** 한 프레임의 일부가 VRAM에, 일부가 RAM에 그려지고 **둘이
서로를 모른다.** 프리미티브 단위 되돌림(§5-2가 끈적한 비활성화 때문에
**필수**라고 결론지은 것)이 있는 한 이 조합은 성립할 수 없다.

**(나) 내부적으로 VRAM에 그리고 앱이 볼 때 복사.**
→ 논리적으로는 성립하나 **앱이 언제 자기 버퍼를 읽는지 우리가 모른다.**
OSMesa의 계약은 "렌더 후 이미지가 네 버퍼에 있다"이고, 앱이 `glFinish`를
부르리라는 보장이 없다. **닫을 수 없는 위험이다.**

### 9-5. ~~결론 — 가속은 앱이 명시적으로 선택한다~~ — **철회됨(§11)**

> **이 절은 틀렸다.** 앱의 소스를 바꾼다. §11-2가 대신한다:
> **libGL 안에서 렌더 대상을 바꿔치기하고 앱은 모른다.**

앱이 우리 진입점을 불러 **VRAM 버퍼를 받아 간다**:

```c
/* libGL_mga.a에만 있다 */
void *MGAMesaAllocBuffer( OSMesaContext ctx, GLsizei w, GLsizei h );
```

그러면 소프트웨어와 하드웨어가 **같은 버퍼**를 쓰고 §9-4의 구멍이 사라진다.
되돌림이 프리미티브 단위로 일어나도 그림이 한 곳에 쌓인다.

**앱 수정이 필요하다는 것이 비용이다.** 그러나
- 투명 모드는 §9-4대로 **정확하지 않거나 닫을 수 없는 위험을 남긴다**
- 정적 링크이므로 **어차피 앱을 다시 빌드해야 가속이 붙는다**(§9-1)

→ **이미 다시 빌드해야 하는데 한 줄을 더 못 고칠 이유가 없다.**

### 9-6. 이 결론이 바꾸는 것

- `M1_3_MESA_BACKEND_PLAN.md`의 검증이 더 쉬워진다: **같은 앱이 두 버퍼로
  두 번 그리고 비교**한다(하나는 malloc, 하나는 VRAM).
- Configure.app 스위치는 여전히 필요하다 — **가속용으로 빌드된 앱도** 꺼야
  할 때가 있다.
- 스위치가 꺼지면 우리 진입점은 **평범한 메모리를 돌려주면 된다.** 앱은
  차이를 모르고, 소프트웨어로 그려진다. **되돌림의 가장 단순한 형태다.**

## 10. 공유 버퍼의 동기화 — 교차검토가 더 나은 지적을 했다

§9-5에서 소프트웨어와 하드웨어가 **같은 VRAM 버퍼**를 쓰기로 했다. 그러면
"CPU가 읽기 전에 DMA가 끝났는가"를 따져야 한다. 교차검토에 읽기 경로를
열거해달라고 물었더니 **질문 자체가 좁았다고 답했다.**

### 10-1. 읽기만이 아니라 **쓰기끼리도 부딪친다**

> 읽기 전에만 울타리를 치는 것으로는 부족하다. 나중의 소프트웨어 쓰기가
> **먼저 큐에 들어간 DMA 쓰기에 질 수 있다.**

맞는 지적이다. DMA가 픽셀 P에 쓰도록 큐에 들어간 뒤 CPU가 P에 쓰면,
**뒤늦게 착지한 DMA가 CPU의 결과를 덮는다.** 읽기 API에만 울타리를 치면
이걸 놓친다. → 울타리는 **하드웨어→소프트웨어 전환**에 쳐야 한다.

### 10-2. 확인한 읽기 경로

원본에서 두 개를 직접 확인했다:

- **소프트웨어 블렌딩은 목적지를 일반적으로 읽는다.** `blend.c:888`이
  `/* Read span of current frame buffer pixels */` 주석과 함께
  `gl_read_rgba_span(ctx, ctx->DrawBuffer, ...)`를 부른다. `DST_*` 인자를
  쓸 때만이 아니다 — **블렌드 식이 목적지 색을 먹기 때문이다.**
- 나머지: `glReadPixels`(`readpix.c`), `glCopyPixels`(`copypix.c`),
  `glLogicOp`(`logic.c`), `glColorMask` RMW(`masking.c`),
  누적버퍼(`accum.c`), **마스크가 걸린 `glClear`**(`buffers.c:113,128` —
  OSMesa의 빠른 클리어가 `:603-605`에서 거부하고 코어로 넘긴다).

### 10-3. 그리고 **dd 훅을 거치지 않는 읽기가 있다**

`osmesa.c:1260-1265`의 `PLOT` 매크로:

```c
GLuint *ptr4 = PIXELADDR4(X,Y);
pixel |=((((((*ptr4) >> rshift) & 0xff)*msavalue+rvalue)>>8) << rshift);
...
*ptr4 = pixel;
```

**버퍼를 직접 읽고 고쳐 쓴다.** dd 읽기 훅을 거치지 않는다. 알파
블렌딩된 선을 그리는 최적화 경로 셋이 이렇게 되어 있다.

→ **읽기 훅에 울타리를 치는 설계는 애초에 불완전하다.** 이 경로를 못 잡는다.

### 10-4. 그런데 **지금 우리 제출은 동기다** — 전부 아직 죽은 문제다

우리 제출 경로를 확인했다
(`OpenStepMGAReplacementDisplay.m`, M1-2c 경로):

```c
osmgaW32(base, MGA_PRIMEND, (listPhys + tail * 4UL) | MGA_DMA_GENERAL);
for (spins = 0UL; spins < OSMGA_S1_SPIN_LIMIT; spins++) {
    status = osmgaR32(base, MGA_ENGSTATUS);
    if ((status & MGA_DMA_DONE_MASK) == MGA_DMA_DONE_VALUE) break;
}
...
if (!osmgaStormWaitIdle(base)) goto unmap;
```

**DMA 완료까지 돌고 나서 엔진 유휴까지 기다린 뒤에 돌아온다.** 제출
ioctl이 반환한 시점에 in-flight DMA는 없다.

→ §10-1~10-3의 모든 위험이 **오늘은 발생하지 않는다.** 커널이 이미 매
제출마다 울타리를 치고 있다.

### 10-5. 그래서 실제 결론

**동기 제출을 유지하는 한 동기화 작업이 필요 없다.** 이것을
M1-3의 전제로 **명시적으로 기록한다.**

비용은 성능이다 — 배치마다 엔진 유휴를 기다린다. 언젠가 이걸 없애고 싶어질
것이고, **바로 그때 §10-1~10-3이 살아난다.** 그때의 규칙을 지금 적어둔다:

1. **울타리는 Mesa의 읽기 경로가 아니라 우리 훅 안에 친다.** §10-3의
   우회 경로 때문에 읽기 훅 가로채기는 원리적으로 불완전하다.
2. 우리 삼각형 훅이 **소프트웨어로 되돌리기로 결정하는 순간** 엔진 유휴를
   기다린다. 그 지점은 우리가 온전히 통제한다.
3. 프레임을 앱에 넘기기 전에도 기다린다.

→ 이 규칙은 **읽기 경로를 하나도 열거하지 않고도 안전하다.** 어떤 CPU
접근이든 그 앞에 하드웨어→소프트웨어 전환이 반드시 있기 때문이다.

**비동기 제출은 M1 범위 밖이다.** `REMAINING_WORK.md`에 남긴다.

## 11. 요구사항 재확인 (2026-08-20) — §9-2와 §9-5를 뒤집는다

operator가 못박았다:

> application 은 빌드가 그냥 진행되어야 합니다. driver 및 mesa에 우리가 넣을
> 드라이버에 따라 **OPENSTEP 의 재부팅 수준에서** software 렌더링과 하드웨어
> 가속이 변경되어야 합니다.
>
> 물론 application 의 빌드시에 **Mesa 자체가 있어야 한다는 사실은 변함이
> 없어야** 합니다.

**§9-2(별도 이름의 두 번째 라이브러리)와 §9-5(앱이 진입점을 호출)는 이
요구를 어긴다.** 둘 다 앱의 빌드나 소스를 바꾼다. 폐기한다.

### 11-1. 올바른 구조

| 층 | 무엇이 결정하나 | 언제 |
| --- | --- | --- |
| 앱 빌드 | `-lGL`. **바뀌지 않는다.** Mesa는 여전히 있어야 빌드된다 | — |
| 어떤 `libGL.a`가 깔려 있나 | 우리 pkg 설치 여부 | 설치 시 |
| 하드웨어를 쓰나 | 드라이버 로드 + Configure.app 스위치 | **재부팅** |

**우리 pkg는 설치된 `libGL.a`를 제자리에서 교체한다.** stock은 보관했다가
제거 시 되돌린다. 앱의 빌드 명령은 그대로다 — `-lGL`이 무엇을 집는지가
달라질 뿐이다.

- Mesa pkg만 → stock `libGL.a` → **항상 소프트웨어**
- Mesa pkg + 우리 pkg → 백엔드가 든 `libGL.a` → **런타임에 결정**
- 드라이버 없음 / 스위치 off → 탐지 실패 → **소프트웨어**

→ 세 요구가 모두 충족된다. **재부팅 수준의 전환**이고, 앱은 모른다.

### 11-2. 그러면 §9-4의 구멍을 실제로 막아야 한다

앱이 `OSMesaMakeCurrent(ctx, pixels, ...)`에 **자기 배열**을 넘긴다
(`examples/osmesa-clear.c:11`). 앱을 못 고치니 우리가 처리한다.

**렌더 대상을 안에서 바꿔치기한다:**

1. 가속이 가능하면 같은 크기의 **VRAM 버퍼**를 잡고, Mesa가 그리로 그리게
   한다. 앱의 포인터는 기억해 둔다.
2. **소프트웨어도 하드웨어도 VRAM에 그린다.** → §9-4의 분기가 사라진다.
   프리미티브 단위 되돌림이 일어나도 그림이 한 곳에 쌓인다.
3. VRAM을 앱 버퍼로 **비춘다(mirror).**

`ROW_LENGTH`와 `Y_UP`(§8)이 이 바꿔치기를 가능하게 하는 손잡이다.

### 11-3. 언제 비추는가 — **정직하게 미해결이다**

앱은 GL 호출 **사이에서만** 자기 버퍼를 볼 수 있다(단일 스레드).
그러므로 **그릴 때마다 비추면 항상 옳다.** 다만 호출마다 VRAM→RAM 복사가
붙고, **PCI 되읽기는 느리다.**

싼 쪽은 `glFinish`/`glFlush`에서만 비추는 것이다. 그런데 **이 트리의
`osmesa.h`와 `docs/`에 "읽기 전에 `glFinish`를 불러라"는 계약이 없다.**
확인했고, 없었다. 그러니 "앱이 부를 것"이라고 **가정하지 않는다.**

세 가지 안을 남긴다:

| 안 | 정확한가 | 비용 |
| --- | --- | --- |
| (가) 그리는 호출마다 dirty 사각형만 비춤 | **항상 옳다** | 호출당 되읽기 |
| (나) `glFinish`/`glFlush`/컨텍스트 전환에서만 | 앱이 부를 때만 | 프레임당 한 번 |
| (다) 앱 버퍼를 `vm_protect`로 막고 **읽기 폴트에서** 비춤 | **항상 옳다** | 폴트 처리, Mach 예외 포트 |

**(가)로 시작한다.** 옳은 것을 먼저 돌리고, 재고 나서 (다)를 검토한다.
(나)는 근거가 없으므로 **기본값으로 쓰지 않는다.**

> (다)는 Mach에서 이상한 기법이 아니다 — OPENSTEP의 VM 자체가 그렇게
> 동작한다. 다만 M1 범위 밖이다.

**검토한 뒤 버린 것**: 앱의 페이지를 `vm_deallocate`하고 그 가상주소에
VRAM을 매핑해 **복사를 아예 없애는** 방법. `malloc`이 준 페이지를 바꿔치면
`free`에서 무너진다. 앱을 못 고치는 이상 쓸 수 없다.

### 11-4. 이것이 M1-3a에 주는 것

M1-3a는 **탐지·게이팅·되돌림**만 한다. 비추기는 M1-3b(색)에서 처음 필요하다.
그러나 **VRAM 버퍼를 잡는 자리는 M1-3a의 `OSMesaMakeCurrent` 경로**이므로,
그 갈림길을 지금 만든다.

## 12. 스위치를 **보고만 하는 것**으로는 부족했다 (2026-08-21, 실측)

§11까지 이 계획은 `Mesa Acceleration`을 **드라이버에서 아무것도 막지 않고
caps로 보고만 하게** 했다. 근거는 "거절을 라이브러리가 하면 스위치가
디스플레이를 깨뜨릴 수 없다"였다.

**실기에서 그 대가가 드러났다.** 스위치를 `No`로 두고 부팅했더니:

```
mach: OpenStepMGA M1-3a: Mesa acceleration switch is No
mach: OpenStepMGA M1-2a: PASS -- the batch drew exactly what MMIO drew
mach: OpenStepMGA M1-2c: PASS -- edges that walk far outside the clip ...
```

**가속을 껐는데 드라이버가 부팅 때 스스로 3D DMA를 돌렸다.**

그리고 교차검토가 더 큰 것을 짚었다: 제출 파라미터
(`OSMGAHW3DSubmit`)가 `osmgaMesaAccelEnabled`를 **보지 않으므로**, 이
인터페이스에 맞춰 쓰인 것은 무엇이든 비트가 꺼져 있어도 그냥 제출할 수
있었다. 즉 `No`의 정직한 뜻은

> "협조하는 libGL은 소프트웨어로 간다"

였지 **"하드웨어 3D에 닿을 수 없다"가 아니었다.** 스위치를 켜고 끄는
사람이 생각할 뜻과 다르다.

### 12-1. 고친 것

1. **제출 경로가 스위치를 검사한다.** 꺼져 있으면 `IO_R_UNSUPPORTED`.
2. **M1 자체 시험 둘도 스위치를 본다.** `Raster Test`는 엔진 탐침을
   요청하는 것이고, `Mesa Acceleration`은 3D 클라이언트 경로가 도는지를
   정한다. 그 경로를 쓰는 시험이므로 **둘 다에 답해야 한다.**

### 12-2. §11의 "깨뜨릴 수 없다"는 여전히 성립한다

거절은 **3D가 쓸 수 없을 때 이미 일어나던 그 거절**이다. 디스플레이가
의지하는 것은 아무것도 바뀌지 않는다 — 스위치는 여전히 초기화 때 한 번
읽히고, `osmgaMesaAccelEnabled` 말고는 어떤 상태에도 영향을 주지 않는다
(교차검토가 Property B로 확인).

**대신 이제 방어가 겹친다**: 라이브러리가 거절하고, 드라이버도 거절한다.
계약이 다른 libGL이 남아 있거나 업그레이드가 반만 됐을 때 후자가 받는다.

### 12-3. 이 스위치가 **끄지 않는 것** — 정확히 적어둔다

처음에 Default.table 주석을 이렇게 썼다: *"이걸 끄면 기계가 스스로 3D
DMA를 시작하지 않는다."* **교차검토가 오해를 부른다고 했고, 확인해보니
맞았다.**

`No`로 부팅한 로그에 `D3-5b`가 여전히 있었고, 그 함수를 세어보니
`PRIMADDRESS`/`PRIMEND`는 **0번**이지만 `DWGCTL`/`EXEC`/`DSTORG`는
**10번** 쓴다. 즉 **DMA는 아니어도 드로잉 엔진은 몬다.**
(`runMmapWindowTest`는 레지스터 접근이 0 — 순수 산술이라 무관하다.)

| 스위치가 끄는 것 | 끄지 않는 것 |
| --- | --- |
| 클라이언트 제출(`OSMGAHW3DSubmit`) | `Storm 2D Test` — MMIO 블릿 |
| `runHW3DBatchTest` | `DMA Ring Test` — **primary DMA** |
| `runHW3DContainmentTest` | `WARP Test` — WARP 레지스터, 일부 DMA |
| | `Raster Test` — MMIO로 드로잉 엔진 |

**이건 결함이 아니라 범위다.** `Mesa Acceleration`은 *3D 클라이언트
경로*의 스위치지 엔진 전체의 차단기가 아니다. 다른 넷은 전부 개발용이고
Default.table에서 `No`다.

→ 출하 설정에서는 넷 다 꺼져 있으므로 **결과적으로는 조용하다.** 그러나
그것은 이 스위치가 해주는 일이 아니다 — **주석이 그렇게 읽히면 안 된다.**
