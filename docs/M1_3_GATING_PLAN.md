# M1-3 게이팅 — 언제 하드웨어를 쓰고 언제 소프트웨어로 두는가

기준일: 2026-08-20
상태: 계획. codex 교차검토 **대기 중**.
선행: M1-2g 완료. `M1_3_MESA_BACKEND_PLAN.md`의 전제 문서.

## 0. 요구사항 (operator, 2026-08-20)

| 상황 | 결과 |
| --- | --- |
| 우리 pkg 미설치 | **소프트웨어 렌더링** (지금과 동일) |
| pkg 설치, 우리 드라이버가 디스플레이를 소유 | 하드웨어 가속이 **가능** |
| 그 위에서 Configure.app의 `Mesa Acceleration`이 켜짐 | 하드웨어 가속이 **동작** |

세 단계가 **독립**이라는 점이 요점이다. 2번이 참인데 3번이 거짓이면
소프트웨어로 돌아야 하고, **그 판단이 런타임에 일어나야 한다.**

## 1. 왜 이것을 먼저 정하는가

M1-3a를 먼저 짜면 "우리 하드웨어가 있다"를 전제한 코드가 된다. 게이팅을
나중에 끼우면 **되돌림 경로가 시험되지 않은 채 남는다** — 그리고
되돌림은 정상 경로보다 **더 자주 쓰일** 코드다(가속을 끈 사용자가 다수일
것이므로).

## 2. 라이브러리는 **하나**다

두 벌(`libGL` 소프트웨어판/하드웨어판)을 만들어 고르게 하지 않는다.
**하나가 실행 시점에 탐지한다.**

이유:
- 두 벌이면 **소프트웨어 경로가 시험되지 않는다** — 개발자는 하드웨어판만
  돌린다.
- pkg를 지우면 라이브러리도 사라져 원래 Mesa로 돌아가야 하는데, 두 벌이면
  어느 것이 남았는지가 설치 상태에 얽힌다.
- 같은 pkg가 **우리 드라이버가 아닌 기계**에서도 동작해야 한다(요구 1).

## 3. 탐지 — "우리 파라미터에 답하면 우리다"

새 읽기 파라미터를 드라이버에 더한다:

```
"OSMGAHW3DCaps"  ->  [magic, version, flags, maxTri, clipW, clipH, ...]
```

라이브러리는 `IODeviceMaster`로 `Display0`을 찾아 이 파라미터를 읽는다.

| 결과 | 뜻 | 동작 |
| --- | --- | --- |
| `lookUpByDeviceName` 실패 | 디스플레이가 없다 | 소프트웨어 |
| `getIntValues` 실패 | **우리 드라이버가 아니다** | 소프트웨어 |
| `magic`이 다름 | 우리 것인데 다른 무언가 | 소프트웨어 |
| `version`을 모름 | pkg 스큐 | 소프트웨어 |
| `flags`에 ENABLED 없음 | Configure에서 껐다 | 소프트웨어 |
| 전부 통과 | | 하드웨어 |

**"파라미터에 답하는가"가 곧 신원 확인이다.** 다른 드라이버는 그 이름을
모르므로 `getIntValues`가 실패한다 — 별도의 식별 수단이 필요 없다.

### 3-1. 버전 핸드셰이크가 필요한 이유

배치 구조체는 `magic`/`version`을 이미 갖고 있고 커널이 검사한다. 그런데
**그것은 제출 시점**이다. 드라이버만 새 pkg이고 라이브러리가 낡았다면
(또는 반대라면) 구조체 배치가 달라 **제출이 거부되거나 더 나쁘게는 엉뚱한
필드로 해석된다.**

→ 탐지 시점에 **양쪽이 버전을 확인**하고, 모르는 버전이면 **가속을 아예
켜지 않는다.** 거부를 처리하는 것보다 시작하지 않는 것이 낫다.

## 4. Configure.app 스위치

`Mesa Acceleration`을 `Instance0.table`/`Default.table`에 더하고 C1의
인스펙터에 체크박스를 하나 더한다. **기존 두 개(`Storm 2D Test`,
`VRAM Mmap`)와 같은 방식**이므로 새 기법이 필요 없다.

### 4-1. 다른 스위치와의 관계

3D 경로는 **명령 창과 VRAM 창**을 쓴다. 그것은 `VRAM Mmap`이 cdevsw를
등록해야 존재한다.

**`Mesa Acceleration`이 `VRAM Mmap`을 함의하게 한다** — 켜면 드라이버가
등록을 시도하고, 실패하면 `flags`에 ENABLED를 **넣지 않는다.**
사용자가 스위치 두 개의 관계를 알 필요가 없어야 한다.

**개발용 스위치들과는 독립이다.** `Storm 2D Test`/`DMA Ring Test`/
`WARP Test`/`Raster Test`는 부팅 프로브이고 가속과 무관하다.

## 5. 되돌림 규율 — **끈적하게(sticky), 조용히**

가속을 켠 뒤에도 실패할 수 있다: 장치가 안 열림, mmap 실패, 제출 거부,
DMA 타임아웃.

**규칙**

1. **어느 실패든 그 컨텍스트에서 가속을 영구히 끈다.** 반쯤 동작하는
   경로는 소프트웨어보다 나쁘다 — 프레임마다 다르게 실패한다.
2. **끄는 것은 조용히, 단 한 번은 알린다.** 첫 실패에 `syslog` 한 줄.
   그 뒤로는 침묵. 프레임마다 로그를 뱉으면 그 자체가 고장이다.
3. **그림은 계속 나와야 한다.** 되돌림 뒤 소프트웨어 경로가 그 프레임을
   완성한다. 사용자가 알아채는 것은 느려짐뿐이어야 한다.
4. **부분적으로 그려진 프레임을 남기지 않는다.** 배치를 제출하다 실패하면
   그 배치의 삼각형들을 **소프트웨어로 다시 그린다.** 그러려면 배치를
   비우기 전까지 정점 인덱스를 들고 있어야 한다(§5-1).

### 5-1. 되돌림이 배치 설계에 거는 조건

배치에 삼각형을 쌓아 두었다가 제출이 실패하면, 그 삼각형들을 소프트웨어로
다시 그려야 한다. 따라서 **배치와 나란히 그 삼각형들의 정점 인덱스도
쌓아 둔다.**

비용은 삼각형당 4워드(`v0,v1,v2,pv`)이고, 200개면 3.2 KiB다. 유저랜드
메모리이므로 문제되지 않는다.

**이것을 처음부터 넣는다.** 나중에 끼우면 되돌림 경로가 시험되지 않는다.

## 5-2. Mesa가 이것을 실제로 허용하는지 — 트리로 확인했다

### 탐지를 어디에 두는가

`dd.h:66-69`가 못박는다: 훅 포인터는 **드라이버의 `MakeCurrent`에서 처음
초기화**한다. 그것이 컨텍스트당 가장 이른 지점이다.

단 `gl_pipeline_init`은 **컨텍스트 생성 때 한 번**(`context.c:978`)
불린다. 즉 `MakeCurrent`에서는 **파이프라인 단계를 등록할 수 없다.**

→ **파이프라인 단계를 등록하지 않는다.** 우리에게 필요한 것은 프리미티브
훅뿐이고, 그것은 `UpdateState`에서 설치된다. 등록하지 않으면
`RegisterPipelineStages`가 `NULL`이라 Mesa가 기본 파이프라인을 쓴다
(`pipeline.c:184-190`) — **즉 "안 하는 것"이 곧 stock 동작이다.**

### 가속을 안 켰을 때 stock과 같아지는가

`TriangleCaps`를 0으로 두고 훅을 `NULL`로 두면
`IndirectTriangles = TriangleCaps & ~0`이 전부 켜지고 `DD_SW_RASTERIZE`가
더해진다(`state.c:1091-1092`). 그러면 Mesa가 스스로 소프트웨어 함수를
고른다(`state.c:1119-1124`).

→ **아무것도 하지 않는 것으로 충분하다.** 지워야 할 잔재가 없다.

### 중간에 끄는 것 — **여기가 §4-3 요령의 진짜 이유다**

상태가 바뀌면 Mesa가 훅을 지우고 `UpdateState`를 부르므로
(`state.c:1098-1111`), 그때 설치하지 않으면 소프트웨어로 채워진다.

**그런데 상태가 안 바뀌면 Mesa는 다시 묻지 않는다.** 우리 훅이 설치된 채로
계속 불린다. 따라서 **중간에 끄려면 우리 훅이 계속 불리면서 스스로
소프트웨어 함수에 넘겨야 한다.**

→ `M1_3_MESA_BACKEND_PLAN.md` §4-3의 저장된 소프트웨어 포인터는
**기하 단위 되돌림을 위한 편의가 아니라, 끈적한 비활성화의 필수 조건**이다.
둘이 같은 기제를 쓴다.

**이것을 M1-3a에서 함께 검증한다** — 훅이 설치된 상태에서 플래그를 끄면
그림이 소프트웨어와 같아지는가.

## 6. 검증 방법

각 단계가 **독립적으로 확인 가능**해야 한다.

- **V-G1 (pkg 없음)**: 라이브러리를 걷어내고 원래 Mesa로 돌린 뒤 예제가
  그대로 동작하는가. 이건 사실상 "우리가 아무것도 안 깼는가"다.
- **V-G2 (드라이버가 우리 것이 아님)**: 탐지가 실패하는 경로를
  **강제로** 태운다 — 파라미터 이름을 일부러 틀리게 한 빌드로. 소프트웨어로
  그려지고 **그림이 옳은가.**
- **V-G3 (스위치 off)**: `Mesa Acceleration = No`로 부팅. `flags`에
  ENABLED가 없고 소프트웨어로 그려지는가.
- **V-G4 (스위치 on)**: 켜고 부팅. 하드웨어로 그려지고 **G3의 그림과
  픽셀 단위로 같은가**(±1).
- **V-G5 (런타임 실패)**: 제출이 거부되도록 일부러 잘못된 배치를 만들어
  **되돌림이 실제로 일어나고 그림이 완성되는지** 본다. 로그가 **한 줄만**
  나오는지도 본다.
- **V-G6 (버전 스큐)**: 라이브러리의 기대 버전을 하나 올린 빌드로 —
  가속이 **켜지지 않고** 소프트웨어로 그려지는가.

**V-G2·V-G5·V-G6이 이 계획의 핵심이다.** 정상 경로는 어차피 M1-3에서
확인되고, **여기서 확인할 것은 실패 경로**다.

## 7. 이 계획이 `M1_3_MESA_BACKEND_PLAN.md`에 거는 변경

- M1-3a에 **탐지와 되돌림을 먼저 넣는다.** 훅을 채우기 전에.
- 배치가 정점 인덱스를 함께 보관한다(§5-1).
- 모든 단계의 검증에 **"가속을 끄면 같은 그림"** 을 더한다.

## 8. 결정하지 않은 것

- pkg가 무엇을 담고 어떻게 설치하는지. **이 문서는 라이브러리가 하나이고
  런타임에 탐지한다는 것만 정한다.**
- 여러 디스플레이. 지금은 `Display0` 하나를 본다.
- 프로세스마다 탐지 비용. 컨텍스트 생성 시 한 번이며 측정하지 않았다.
