# Mesa 스테이징을 재부팅이 지우지 않는 자리로

아직 코드 없음.

## 1. 문제

`/tmp` 는 부팅마다 비워진다. 그런데 Mesa 포트의 스테이징과 빌드가 전부
거기에 있다:

```
stage-openstep-mesa342.csh : stage_root = /tmp/OpenStepMesa342
build-openstep-mesa342.csh : stage_root = /tmp/OpenStepMesa342
build-matrox-mesa.csh      : mesa_src   = /tmp/OpenStepMesa342/src/Mesa-3.4.2
                             out        = /tmp/OpenStepMesaMGA
```

그래서 재부팅할 때마다 **스테이징 → Mesa 빌드 → 가속 libGL 빌드** 셋을
다시 해야 한다. 이번 세션에서만 세 번 했다. 각각 몇 분씩 걸린다.

`build-matrox-mesa.csh` 는 결과 사본을 저장소(`build/mesa/`)에 남긴다 —
그래서 **시험을 링크하는 데는** 재부팅 뒤에도 문제가 없다(실제로 그렇게
했다). 없어지는 것은 **다시 빌드할 능력**이다: 스테이징된 소스 트리와
stock `libGL.a`.

## 2. 왜 지속 위치가 안전한가 (확인함)

`stage-openstep-mesa342.csh` 는 복사 전에

```csh
if (-d $stage_root) rm -rf $stage_root
```

로 **통째로 지우고 시작한다.** 그러니 지속 디렉터리에 두어도 낡은 트리가
남지 않는다. 다시 스테이징하면 언제나 깨끗하다.

`build-openstep-mesa342.csh` 는 `make openstep` 만 하고 clean 하지 않는다.
스테이징을 안 하고 다시 빌드하면 **증분**이 된다 — 그게 바로 원하는 것이다.

## 3. 어디에 둘 것인가

실기 루트 디스크: 2035398 KB 중 **574964 KB 여유**(69% 사용). 스테이징
트리는 15023 KB, 가속 출력은 2058 KB — python 으로 따지면 여유의 **3.0%**
다.

`/usr/local` 은 이미 있고 루트 디스크에 있다. 그 아래에 둔다.

## 3b. codex 교차검토 — 재검증 결과

**소스와 실기에서 확인해 받아들인 것**

1. **하드코딩이 셋이 아니라 일곱이다.** 세어보니
   `stage-`, `build-`, `build-matrox-mesa`, `build-package.csh`,
   `build-split-packages.csh`, `verify-package.csh`,
   `build-package-mesa-consumer.csh` 다. 셋만 덮어쓰면 **패키징 흐름이
   조용히 `/tmp` 를 보다 실패한다** — 세 곳에서만 듣는 변수는 함정이다.
   **일곱 전부에 적용한다.**
2. **`$?VAR` 는 존재만 보지 비어 있음을 못 본다.** 그리고 이 csh 에서
   **`-d ""` 가 참을 돌려준다** — 실기에서 확인했다:
   `csh -f -c 'set v = "" ; if (-d "$v") echo yes'` → `yes`.
   그러니 빈 값이 들어오면 `rm -rf ""` 까지 간다.
3. **임의의 절대경로를 받으면 임의의 재귀 삭제를 허용하는 것이다.**
   `/` 나 `/usr/local` 이 들어오면 그대로 지운다. 그래서 **변수는 경로가
   아니라 *부모* 를 받고, 잎 이름은 스크립트가 고정한다.** 그러면
   `rm -rf` 가 지울 수 있는 것은 언제나 `.../OpenStepMesa342` 뿐이다.
4. **`make openstep` 은 `make dep` 을 하지 않는다** — 최상위 Makefile 을
   읽어 확인했다. 그러니 **Mesa 소스·헤더·플래그가 바뀌면 증분은
   위험하다.** 백엔드만 바뀐 경우는 안전하다(`build-matrox-mesa.csh` 는
   출력 디렉터리를 지우고 네 소스를 매번 다시 컴파일한다).
   그 경계를 문서와 주석에 정확히 적는다.
5. **스테이징이 마지막 `cp` 뒤에만 `$status` 를 본다.** 앞선 복사가
   실패해도 마지막이 성공하면 가려진다. `/tmp` 시절에는 재부팅이 치웠지만
   지속 위치에서는 **부분 트리가 남아 다음 빌드가 받아들일 수 있다.**
   → 모든 복사가 끝난 뒤 **완료 표식**을 남기고, 빌드가 그것을 요구한다.
6. **출력과 스테이징은 형제여야 한다** — 하나가 다른 하나 안에 있으면
   `rm -rf $out` 이 읽고 있던 stock 라이브러리를 지운다.
7. **`build-matrox-mesa.csh` 의 실행 안내가 틀렸다** — `sh` 로 쓰라는데
   csh 문법이다. `csh -f` 로 고친다. (실제로 `csh -f` 로만 돌아간다.)

## 4. 어떻게 (기본값은 안 바꾼다)

`opennstep-mesa342` 는 **따로 공개되는 자립 하위 프로젝트**다. 그 기본
동작을 이 저장소 사정으로 바꾸지 않는다.

- **일곱 스크립트 전부**에서 경로를 환경 변수로 덮어쓸 수 있게 하고,
  변수가 없으면 지금과 **똑같이** `/tmp` 를 쓴다.
- **변수는 경로가 아니라 부모를 받는다.** `OPENSTEP_MESA_STAGE_PARENT`
  (기본 `/tmp`)이고, 잎 `OpenStepMesa342` 는 스크립트가 붙인다. 그러면
  무엇을 넣든 `rm -rf` 의 대상은 `.../OpenStepMesa342` 다.
  가속 출력도 같은 꼴: `OSMGA_MESA_OUT_PARENT`, 잎 `OpenStepMesaMGA`.
- **빈 값을 거절한다.** 이 csh 는 `-d ""` 에 참을 돌려주므로 존재 검사만으로는
  안 된다. 부모가 비었거나 절대경로가 아니면 종료한다.
- **모든 사용처를 따옴표로 감싼다.**
- 스테이징이 끝나면 **완료 표식**을 남기고, 빌드가 그것을 요구한다.
- 우리 쪽 헬퍼(`tools/`)가 그 변수를 지속 위치로 설정한다.

csh 에서는 `if (! $?VAR) setenv VAR 기본값` 꼴이고, 헬퍼는 `set` 이 아니라
**`setenv`** 를 써야 자식 스크립트까지 따라간다.

## 5. 안 하는 것

- **`/tmp` 자체를 지속으로 만들지 않는다.** 시스템 설정을 바꾸는 일이고,
  다른 것들이 `/tmp` 가 비워지기를 기대한다.
- **NFS 마운트 위에 빌드하지 않는다.** 저장소를 빌드 산출물로 더럽히고,
  링크 단계가 느리며, 마운트가 끊기면 빌드가 중간에 죽는다.
- **증분 빌드를 기본으로 삼지 않는다.** 소스를 고쳤을 때 다시 스테이징하는
  것은 여전히 사용자(나)의 책임이다. 스테이징이 지우고 시작하므로 그 방법은
  언제나 있다.

## 6. 검증

1. 변수 없이 스크립트를 돌리면 **지금과 똑같이** `/tmp` 에 만든다.
2. 변수를 주면 그 자리에 만들고, `PASS` 줄이 그 경로를 가리킨다.
3. 재부팅 뒤 **스테이징을 건너뛰고** 가속 libGL 만 다시 빌드해서 성공한다.
4. 다시 스테이징하면 지속 디렉터리가 깨끗이 다시 만들어진다.
