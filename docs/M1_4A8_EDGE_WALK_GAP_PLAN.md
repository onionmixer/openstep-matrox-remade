# 확정했다던 변 걷기가 어떤 레지스터에서 깨진다 (계획, 2026-08-21)

`M1_4A7_DEPTH_FIX_PLAN.md` §9-2 에서 나온 것. 깊이 수정은 **이것이 풀릴
때까지 보류**한다.

## 1. 무엇이 어긋났나 — 지금까지 확보한 사실

도형 4 `(265,10) (313,152) (146,139)`. 빌더가 내놓는 레지스터를 **직접
찍었다**:

```
   [0] y=10 h=129  FXBNDRY left=265 right=265  SGN=2
       AR0=258 AR1=-229 AR2=-238 | AR6=284 AR4=-2 AR5=-96
   [1] y=139 h=13  ... (이쪽은 13/13 정확하다)
```

| 사실 | 근거 |
|---|---|
| 빌더는 맞다 | 호스트 시험에서 규칙과 **0 행 차이**, 커널도 통과 |
| 드라이버는 레지스터를 **그대로** 보낸다 | `MGA_AR0..AR6, MGA_SGN` 을 무가공 전달 |
| 깊이와 무관하다 | 깊이를 꺼도 11629 화소로 동일 |
| 소프트웨어는 맞다 | 규칙 대비 누락 2, 초과 0 |
| **사다리꼴 1 은 맞다** | 13/13 |
| **사다리꼴 0 만 틀리다** | 129 행 중 63(=model k) / 62(=model k+1) |

**모양은 오프셋이 아니라 속도 차이다:**

```
   하드웨어  왼쪽 264 -> 146  (118 열)   오른쪽 266 -> 308  (42 열)
   레지스터  왼쪽          119 열        오른쪽          43 열
```

시작은 **한 열 앞서고**, 끝은 **같다**. 즉 걸음 수가 하나 적다.

## 2. 반증된 가설 (다시 세우지 않기 위해 적는다)

| 가설 | 반증 |
|---|---|
| 깊이의 ZI access type | 깊이를 꺼도 같다 |
| 정점 y 가 정수 아래로 떨어짐 | 단정도로 계산해도 정확 |
| 삼각형이 한 행 밀림 | 하드웨어가 규칙의 **상위집합** |
| 첫 행이 빈 행(`left==right`) | 도형 3 도 그런데 정확하다 |
| 배수 조건이 `a<=0` | 74/129 |
| 시드가 다름(`AR1` 대 `AR1-AR2`, 0 행 배수 여부) | **전수 탐색해도 최고 105/129** |
| 드라이버가 `AR1` 을 덮어씀 | 소스 확인, 그대로 보낸다 |

### 2-1. 더 좁힌 사실 (걸음을 거르는 행을 직접 셈)

```
   하드웨어가 안 움직이는 행 : 11 23 34 46 58 70 82 94 105 117   (10 회)
   모델(0행에서도 배수)      : 12 25 38 51 64 76 89 102 115 128   (10 회)
   간격: 하드웨어 ~12,  모델 ~13
   누적 걸음 k=0/32/64/96/128 : 하드웨어 1 31 60 89 119
                                모델     0 30 60 89 119
```

**거르는 횟수는 같고(각 10 회) 자리만 다르다.** 그래서 끝점은 같고 중간만
어긋난다. 시드를 아무리 옮겨도 간격 분포가 12 대 13 이라 맞출 수 없다 —
전수 탐색이 105/129 에서 멈춘 이유다.

### 2-2. 「반증」이라고 쓴 것 중 지나쳤던 것 (교차검토)

- **가설 2**(정점이 정수 아래로): 내가 **Mesa 의 변환을 내 손으로 다시
  구현해** 확인했다. 그건 Mesa 의 실제 중간값이 아니다. 레지스터 스트림을
  그대로 재생해서 재현되면 이 가설은 무관해진다 — **그것으로 닫는다.**
- **가설 4**(빈 첫 행): 도형 3 은 **무조건적인** `left==right` 규칙만
  배제한다. 이 기울기·부호·높이·`AR0` 조합과 **결합된** 경로는 못 배제한다.
- **가설 5**(`a<=0`): 전역 치환만 배제했다. **정확히 0 일 때만** 다른 비교,
  한쪽 변에만, 또는 설정 경로에서만 다른 경우는 남는다.
- **가설 7**(드라이버가 덮어씀): 소스 확인은 **장치가 실제로 본 워드**의
  증거가 아니다. 패킷 조립·순서·부호확장·주소가 아직 남는다.

## 3. 그래서 추측을 멈추고 **레지스터 공간을 훑는다**

지난번 변 걷기 탐침은 **세 점**만 봤다(`AR1!=AR2` 하나, 대조군 둘). 그
세 점이 전부 맞았기 때문에 규칙을 "확정"이라고 적었다 — **그게 과했다.**

이번에는 raw `hw3d` 클라이언트로 **격자**를 훑는다. Mesa 를 끼우지 않으므로
빌더·훅·클리퍼가 전부 빠지고 남는 것은 엔진뿐이다.

- 왼쪽 변은 세우고, 오른쪽 변에 `(AR6, AR4, AR5)` 를 넣는다. 시작 열이
  같으므로 **그려진 화소 수 = 그 행의 걸음 수**다.
- 격자: `mag` 와 `dy` 를 여러 비율로, `e` 를 `[-(dy), dy]` 범위에서.
  **도형 4 의 값(`AR6=284 AR4=-2 AR5=-96`, h=129)을 반드시 포함**한다 —
  가장 먼저 확인할 것은 "raw 로도 재현되는가" 이다.
- 각 조합마다 **행마다** 모델과 비교하고 **첫 어긋난 행**을 찍는다.
  총합이나 비율이 아니라 어디서 갈리는지가 필요하다.

## 4. 첫 실험을 고쳤다 — 합성 사다리꼴이 아니라 **그대로 재생**

처음에 "raw 클라이언트로 왼쪽 변을 세우고 오른쪽에 값을 넣어, 그려진 화소
수 = 걸음 수" 라고 적었다. **교차검토가 그 fixture 가 나쁘다고 짚었고
맞다**:

- 두 변을 **같은 열에서 시작**시키는 것은 지금 조사 중인 **퇴화 경로를 바로
  밟는 것**이다 — 중립적 시험이 아니다.
- **그려진 화소 수는 걸음 수가 아니다.** 양 끝 소유 규약이 섞여 있다.
- 왼쪽 변을 세우면 좌우 상호작용이 사라진다.
- 사다리꼴 하나는 Mesa 가 보내는 **두 개짜리 배치**를 재현하지 못한다.

**그래서 첫 실험은 이것이다**: 도형 4 의 **두 사다리꼴을 그대로**, 같은
상태·같은 순서로 raw 로 보내고, **사다리꼴 0 을 그린 직후에도** 비트맵을
읽는다.

| 결과 | 뜻 |
|---|---|
| 사다리꼴 0 직후에 이미 어긋남 | 엔진(또는 장치가 본 상태)의 문제 |
| 사다리꼴 1 뒤에만 어긋남 | 배치 상호작용·상태 잔류·겹침 |
| raw 로는 재현 안 됨 | 제출 경로(패킷 조립·순서·캐시된 상태) |

살아남으면 그 다음은 **좁은 경계 탐침**이다: 다른 상태를 고정한 채
`AR0 = 255,256,257,258,259` 만 바꾸고, 좌우 역할을 뒤바꾼 거울판도 함께.
넓은 격자보다 폭·부호·좌우 비대칭 가설에 훨씬 많은 정보를 준다. 그리고
격리 시험에서는 **두 변을 같은 열에서 시작시키지 않는다.**

## 5. 한 번에 하나씩 바꾼다

도형 4 의 조합에서 `AR4` 만, `AR6` 만, `h` 만 바꿔가며 어느 축에서 모델이
깨지는지 좁힌다. 격자 전체를 먼저 돌리면 결과가 많아 읽지 못한다.

## 6. 커널 검증기 — 위험은 「거절」이 아니라 **「통과」** 다

`OpenStepMGAHW3D.c` 의 행별 검사가 **같은 걷기**로 예측한다. 교차검토가
방향을 바로잡았다: 이 사례에서 하드웨어는 모델보다 **바깥으로** 벗어난다.
그러면 검증기는 자기가 허용한 범위 **밖에 쓰는** 배치를 승인할 수 있다.
거절보다 이쪽이 무겁다.

**다만 실제 경계는 검증기가 아니다.** 드라이버는 `CXBNDRY/YTOP/YBOT` 를
블록으로 좁혀 프로그램하고, 코드 주석이 그것을 "진짜 방어"라고 적어놨다.
도형 4 의 초과 83 화소도 전부 목적지 안이다. 즉 검증기는 다중 방어의 한
겹이고, 그 겹이 **믿었던 것보다 약하다**는 것이 이번에 드러난 것이다.

**규칙이 없는 동안 검증기를 「고치지」 않는다** — 지금 있는 것은 규칙이
아니라 정상 사례 모델과 반례 하나다. 한 열 넓혀 두는 것도 임시방편이
아니다(다음 조합은 더 벗어날 수 있다). 이 항목을 **미해결 위험**으로
적어 두고, 규칙이 서면 그때 함께 고친다.

## 7. 성공/실패 기준

- **성공**: 격자 전체에서 화소마다 맞는 규칙을 하나 세우고, 도형 4 와
  이전 세 도형·이전 탐침 세 점을 **동시에** 설명한다.
- **부분**: 어긋나는 영역의 경계를 좌표로 특정한다(예: `mag/dy` 가 어떤 값을
  넘을 때). 그것만으로도 빌더가 그 영역을 피하게 할 수 있다.
- **실패로 적을 것**: 규칙을 못 세우면 못 세웠다고 적고, 그때까지 깊이
  수정과 §3-12 의 나머지를 **보류**한다.

## 9. 결과 (2026-08-21) — **엔진도 모델도 맞았다. 훅의 좌표 캐스트였다.**

계획의 첫 실험(§4)이 한 번에 답을 냈다.

### 9-1. raw 재생 — 어긋남이 재현되지 않는다

빌더가 찍어준 **바로 그 레지스터**를 Mesa 없이 raw 로 보냈다:

```
   pass 1 (사다리꼴 0 만) : 우리 모델과 128/128 행 일치
   pass 2 (둘 다)        : 128/128
   `drain0=True` 변형    : 6/128
```

**엔진은 우리가 준 것을 그대로 걷는다. 확정해 둔 걷기 규칙은 옳다.**
사다리꼴 0 은 10 행을 안 그린다(빈 행) — 모델이 말한 그대로다.

### 9-2. 그러면 Mesa 실행만 다르다 — 어떻게 다른지 역산했다

Mesa 실행의 결과가 raw 보다 **한 행 위**다(`mesa(y) = raw(y+1)`).
정점을 ±1 로 흔든 64 가지 조합을 전부 렌더해 비교했더니 **정확히 하나**가
맞는다:

```
   (265, 9) (313,152) (146,139)      <- 화소마다 EXACT
```

**훅이 첫 정점의 y 를 9 로 받았다.** 창 y 가 10 바로 아래로 나왔고
`(dst).y = (unsigned long)VB->Win.data[idx][1]` 이 잘랐다.

### 9-3. 내가 이 가설을 잘못 기각했다

§2 에 "정점 y 가 정수 아래로 떨어짐 — **반증**: 단정도로 계산해도 정확"
이라고 적었다. **그 계산은 Mesa 가 아니라 내가 다시 구현한 Mesa 였다.**
교차검토가 정확히 그것을 짚었다:

> Reimplementing Mesa's float math is not evidence of Mesa's actual
> intermediate values.

나는 `(ndc*0.5 + 0.5)*size` 로 계산했고 Mesa 는 `WindowMap` 행렬을 곱한다.
대수적으로 같고 **수치적으로 다르다.** 재생 실험이 아니었다면 계속 엉뚱한
곳을 팠을 것이다.

### 9-4. 그래서 무엇이 무죄인가

| | 판정 |
|---|---|
| 엔진 | **맞다** (raw 재생 128/128) |
| 걷기 규칙 | **맞다** — "0 행은 FXBNDRY 자리, 걸음은 행 사이" |
| 빌더 | **맞다** (호스트 시험 0 행 차이) |
| 커널 검증기 | 모델이 옳으므로 **약하지 않다** — §6 의 우려는 해소 |
| 드라이버 제출 경로 | **맞다** |
| **훅의 `(long)` 좌표 캐스트** | **여기다** |

### 9-5. 크기 — 이건 부분 화소 문제가 아니다

§3-12 의 나머지 절반을 "정점의 소수부를 버린다"고만 적어 뒀는데, 이 사례는
**정점 하나를 통째로 한 행 옮기고 삼각형을 83 화소 크게 만들었다.**
`9.99999 → 9` 는 반올림이면 사라진다.

### 9-6. 깊이 작업은 막혀 있지 않다

도형 1·2·3 은 실기 커버리지가 규칙과 **정확히** 일치했으므로(704/704,
703/703, 676/676) 그 정점들은 온전히 전달됐다 — 모델이 아니라 측정이
말한다. **깊이 정착(Z2) 수정은 그대로 진행할 수 있다.**
