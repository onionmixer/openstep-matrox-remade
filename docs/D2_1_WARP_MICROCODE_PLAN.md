# D2-1 — WARP 마이크로코드 배치

기준일: 2026-08-19
상태: **D2-1a / D2-1b 실기 PASS(2026-08-19).** 결과는 §7.
codex 교차검토 1회 완료 후 개정판.
초판의 사실 오류 1건(§1-4)은 검토 전에 자체 발견해 고쳤고, 검토가 그것을
독립 확인했다. 검토가 추가한 항목은 §1-6.

D2-0에서 WARP 파이프가 설정을 받아들이고 suspend 상태로 섰다
(`D2_WARP_ENGINE_PLAN.md` §7). 다음은 **파이프가 실행할 마이크로코드를
카드가 읽을 수 있는 곳에 놓는 것**이다.

## 0. 이 단계가 묻는 것과 묻지 않는 것

**묻는 것**: 16개 파이프의 마이크로코드를 연속 물리 메모리에 256바이트 정렬로
배치하고, 각 파이프의 물리주소표를 만들 수 있는가. 그리고 **써 넣은 바이트가
그대로 남아 있는가**.

**묻지 않는 것**: 파이프 실행. `WIADDR2`에 `WMODE_START`를 쓰는 일은 D2-2이며
별도 계획서 대상이다. 이 단계는 메모리만 다룬다 — D1-1이 링을 조립만 하고
시작하지 않았던 것과 같은 성격이다.

## 1. 확인된 사실

### 1-1. **PCI에서는 VRAM이 아니라 시스템 메모리다**

초기 D2 계획서는 "오프스크린 VRAM에 올린다"고 적었다. **PCI 경로에서는
아니다.** `mga_do_pci_dma_bootstrap`은 마이크로코드 영역을
`_DRM_CONSISTENT`(DMA 일관 시스템 메모리) + `_DRM_READ_ONLY`로 잡는다
(`mga_dma.c:642` 부근), 주석은 *"The proper alignment is 0x100 for this
mapping"*.

즉 **D1과 같은 구조**다 — 연속 물리 메모리에 두고 카드가 버스마스터로 읽는다.
D1에서 그 경로가 이미 실증됐으므로 새로운 미지수가 아니다.

### 1-2. 크기: 18,432 바이트 (18 KiB)

`WARP_UCODE_SIZE(x) = (sizeof(x)/256 + 1) * 256` 을 G400 16종에 적용해
직접 합산했다(`mga_ucode.h` 실측):

| 계열 | 파이프 | 원본 크기 | 정렬 후 |
| --- | --- | --- | --- |
| 단일 텍스처 `tgz*` | 8종 | 824~1000 | 각 1024 |
| 이중 텍스처 `t2gz*` | 8종 | 1080~1256 | 각 1280 |
| **합계** | **16** | | **18,432 (18 KiB)** |

`IOMallocLow` 1회 상한 64 KiB 안에 **넉넉히 들어간다.**
(참고: `mga_drm.h:75`의 `MGA_WARP_UCODE_SIZE 32768`은 상한 선언이며 실제
합계가 아니다. 실측값이 그보다 작다.)

**할당은 페이지 정렬 크기로 한다.** DRM은 총합을 `PAGE_ALIGN`으로 올려
잡는다(`mga_warp.c:83`). 이 커널의 페이지는 **8192**이므로
`PAGE_ALIGN(18432) = 24576`이다. 여전히 64 KiB 풀 블록 하나 안이다.

### 1-3. 파이프 인덱스는 비트 조합이다

`mga_drm.h:50-70`: `F=0x1`(fog), `A=0x2`(alpha), `S=0x4`(specular),
`T2=0x8`(multitexture). 파이프 번호가 곧 그 조합이므로 표는 `[16]` 배열이고
인덱스 계산이 필요 없다. 가장 단순한 파이프는 `MGA_WARP_TGZ = 0`이다.

### 1-4. 배치 순서는 인덱스 순과 같다 — 다만 간격은 균일하지 않다

**초판에서 "배치 순서와 인덱스 순서가 다르다"고 적은 것은 틀렸다.**
`mga_warp_install_g400_microcode`(`mga_warp.c:104-120`)의 설치 순서를
`mga_drm.h`의 비트 조합으로 환산해 대조한 결과 **0,1,2,…,15 정확히 인덱스
순서**이고, 16개 인덱스가 빠짐없이 채워지며 겹침도 없다.

진짜 함정은 다른 데 있다: **간격이 균일하지 않다.**

| 계열 | 인덱스 | 정렬 후 크기 |
| --- | --- | --- |
| `tgz*` (단일 텍스처) | 0~7 | 각 **1024** |
| `t2gz*` (이중 텍스처) | 8~15 | 각 **1280** |

따라서 `addr = base + index * size` 같은 계산은 **성립하지 않는다.** 주소표는
설치하면서 누적한 오프셋으로 채워야 하며, 이는 DRM의 `WARP_UCODE_INSTALL`
매크로가 `pcbase += WARP_UCODE_SIZE(which)`로 하는 일과 같다.

### 1-5. 아레나 소비

`IOMallocLow`는 8 KiB 초과 요청을 64 KiB 풀에서 준다(`dma_buf_alloc`,
S5 §3-2). 18 KiB를 요청해도 **64 KiB 블록 하나를 쓴다.** D1의 링과 별도로
잡으면 conventional memory 아레나에서 **128 KiB**를 쓰게 된다. 아레나 전체
크기는 측정된 바 없고 ISA DMA 사용자와 공유한다.

→ 이 단계에서 **두 번째 64 KiB 할당이 성립하는지 자체가 확인 대상**이다.

### 1-6. 교차검토가 추가한 것

| # | 내용 | 근거 |
| --- | --- | --- |
| 1 | 마이크로코드 버퍼는 **사용하는 내내 살아 있어야 하고 건드리면 안 된다** | DRM은 `dev_priv->warp`를 DMA cleanup/last close까지 유지(`mga_dma.c:957`) |
| 2 | 배치 **뒤에** `warp_init`을 다시 돌려야 한다 | DRM 순서는 설치 → `warp_init`(`mga_dma.c:893`, `:899`)이고, `warp_init`이 `WMISC`에 **`WCACHEFLUSH`**를 쓴다(`mga_warp.c:177`). 캐시를 비우는 단계가 설치 뒤에 와야 의미가 있다 |
| 3 | 첫 하드웨어 fetch 전에 **CPU 스토어 가시성 배리어**가 필요하다 | D1이 링을 되읽고 MMIO 읽기를 뒤따르게 한 것과 같은 이유(`.m:3099` 부근) |
| 4 | 단일 버퍼 분할 대안에 **하드웨어적 반대 근거는 없다** | WARP는 `WIADDR2`, primary DMA는 `PRIMADDRESS/PRIMEND`로 서로 독립. 실제 요건은 **겹치지 않을 것과 수명**이지 별도 할당이 아니다 |
| 5 | G200 배열을 빼는 것은 정당하다 | 이 드라이버는 device `0x0525`의 G450급 revision에만 결합한다(`.m:1197`) |

2번이 D2-0과의 순서를 바꾼다: **D2-0b에서 이미 `warp_init`을 돌렸지만,
D2-1b는 복사 뒤에 그것을 한 번 더 돌려야 한다.** D2-0b는 "시퀀스가 선다"를
증명한 것이고, 실제 캐시 플러시는 마이크로코드가 자리를 잡은 뒤라야 뜻이 있다.

## 2. 가장 큰 미지수

1. **두 번째 64 KiB 할당이 되는가** (아레나 여유)
2. 18 KiB 배열을 커널 드라이버에 링크하면 reloc이 얼마나 커지는가.
   현재 ~174 KiB이며, `kern_loader`가 조용히 실패하는 크기 한계는 모른다.
3. 마이크로코드 원본을 **저장소 어디에 둘 것인가**. 지금은
   `scratch/`(gitignore)에만 있어 사라질 수 있다(S5 §4-4에서 실제로 겪었다).

## 3. 단계

### D2-1a — 소스 반입과 크기 확인 (하드웨어 접촉 0)

`mga_ucode.h`의 **G400 16종만** 추출해 프로젝트 소스로 반입한다. G200 8종은
쓰지 않으므로 제외한다(11,776바이트 절약, 이 카드에 무의미).

- 라이선스: MIT 계열(`Permission is hereby granted, free of charge...`,
  ⓒ1999 Matrox Graphics Inc.). **원문 고지를 파일 상단에 보존한다.**
- 배치: `warp/OpenStepMGAWarpUcode.{h,c}`. 추출은 스크립트로 하고 스크립트도
  커밋해 재현 가능하게 둔다.

**검증 방법**
- V1-1(호스트): 추출 결과의 각 배열 바이트 수가 원본 `mga_ucode.h`와 일치하는지
  스크립트로 대조.
- V1-2(호스트): 정렬 후 합계가 18,432인지.
- V1-3(타깃): 링크 후 reloc 크기를 기록하고 드라이버가 여전히 **로드되는지**.
  `nm -u`로 미해결 심볼 0 확인 — 이 프로젝트에서 로드 실패는 로그 없이 조용히
  일어난다.

### D2-1b — 배치와 되읽기 (하드웨어 접촉 0)

`IOMallocLow`로 두 번째 버퍼를 `PAGE_ALIGN(18432)=24576` 크기로 잡고, 인덱스
순서대로 256바이트 정렬로 복사한 뒤 `warp_pipe_phys[16]`을 채운다. 복사가
끝나면 **`warp_init` 시퀀스를 다시 돌려 `WCACHEFLUSH`를 태운다**(§1-6 2번).
**`WIADDR2`에 `WMODE_START`를 쓰지 않는다** — 파이프는 suspend 그대로다.

이 단계는 파이프를 시작하지 않으므로, 끝에서 버퍼를 해제한다(D1-0과 같다).
**D2-2는 다르다** — 거기서는 버퍼가 살아 있어야 하므로 해제하지 않는다
(§1-6 1번).

**검증 방법**
- V2-1: 두 번째 64 KiB 할당 성공 여부와 물리주소. 실패하면 그 자체가 결과이며,
  링과 마이크로코드를 **한 버퍼에 나눠 담는 안**으로 전환한다.
- V2-2: 복사 후 **전 바이트 비교**(우리가 쓴 것이 그대로 있는가). 체크섬이
  아니라 바이트 단위 — 18 KiB면 부담이 없다.
- V2-3: 16개 주소가 전부 256바이트 정렬이고, 서로 겹치지 않으며, 버퍼 범위
  안인지. 그리고 **인접 주소 간격이 인덱스 0~7에서 1024, 8~15에서 1280**인지
  (§1-4 — 균일 간격 계산을 쓰면 안 되는 이유). 표를 로그로 덤프해 호스트에서
  대조한다.
- V2-4: 물리 연속성을 페이지마다 재확인(D1-0과 같은 방식).
- V2-5: 복사 후 `warp_init` 재실행에서 `WMISC`가 여전히 `0x3`인지.
  마이크로코드가 자리를 잡은 상태에서도 설정이 유지되는지 확인한다.

### D2-2 — 파이프 실행 (별도 계획서)

이 문서의 범위 밖이다. 필요한 것: 2차 DMA(`SECADDRESS`/`SECEND`) 정점 버퍼,
`WR` 레지스터군 설정, 그리고 `WIADDR2 = phys | WMODE_START` 앞의
**`DMAPAD 0xffffffff` 3개**(DRM이 *"Padding required to to hardware bug"*
라 적어둔 회피책, `mga_state.c:344` — D1의 tail 패딩과는 별개).

## 4. 중단 조건

- 두 번째 `IOMallocLow`가 실패하고 단일 버퍼 분할도 성립하지 않음
- 되읽기 바이트 비교 불일치 → 메모리가 우리가 쓴 것을 유지하지 못함
- reloc 증가로 드라이버가 로드되지 않음 → 마이크로코드를 커널에 링크하지 않고
  다른 경로(파일에서 읽기 등)를 검토해야 한다

## 5. 롤백

opt-in `"WARP Test"`를 `No`로 두면 배치 자체가 일어나지 않는다. 소스 반입은
빌드 크기에만 영향을 주며, 되돌리려면 `CFILES`에서 빼면 된다.

## 6. 이 계획이 결정하지 않은 것

- 마이크로코드를 커널에 정적 링크할지, 나중에 유저스페이스에서 밀어넣을지.
  D2-1은 정적 링크로 시작하되 reloc 크기를 보고 재검토한다.
- 16종을 전부 올릴지, D2-2에 필요한 `TGZ` 하나만 올릴지.

  D2-1b는 `WIADDR2`를 건드리지 않으므로 16종을 전부 복사해도 **하드웨어
  위험이 없다** — 메모리 조작뿐이다. 따라서 이 단계는 전부 올린다.
  축소안(`TGZ` 1종, raw 824 / 정렬 1024)은 **D2-2의 위험을 줄이는** 수단이며
  거기서 다시 판단한다. 교차검토도 같은 구분을 지적했다.

| V1-2 | 정렬 후 합계 **18,432** — 계획 계산과 일치 |

| V2-2 | 16개 파이프 전 바이트 되읽기 동일 |

| V2-5 | 배치 후 `warp_init` 재실행에서 `WMISC=3` |

### 7-1. 간격 함정이 실제로 보였다

```
pipe  0=20000  1=20400  2=20800  3=20c00     간격 0x400 = 1024
pipe  4=21000  5=21400  6=21800  7=21c00
pipe  8=22000  9=22500 10=22a00 11=22f00     간격 0x500 = 1280
pipe 12=23400 13=23900 14=23e00 15=24300
```

§1-4가 경고한 대로다. `base + index * size`로 계산했다면 파이프 8부터
어긋났을 것이고, 그 계산은 **조용히 잘못된 마이크로코드를 실행**시켰을
것이다 — 잘못된 주소가 여전히 정렬돼 있고 버퍼 안이므로 정렬·범위 검사로는
잡히지 않는다. 간격 검사만이 잡는다.

### 7-2. 아직 증명되지 않은 것

- 카드가 이 메모리를 **실제로 읽을 수 있는지**는 모른다. `WIADDR2`에
  주소를 준 적이 없다. D1이 같은 아레나에서 primary DMA로 읽는 것은
  증명했으나, WARP fetch가 같은 경로인지는 D2-2에서야 확인된다.
- 마이크로코드 **내용이 이 칩에 맞는지**도 모른다. 바이트가 그대로 있다는
  것과 칩이 그것을 실행한다는 것은 다른 이야기다.

## 8. 다음

D2-2(파이프 실행). 필요한 것은 §3의 D2-2 항목에 적어 두었다. 이 단계는
**처음으로 카드가 3D 파이프를 돌리는 것**이므로 별도 계획서와 교차검토
대상이다.
