# M1-3 — Mesa 하드웨어 백엔드

기준일: 2026-08-20
상태: 계획. **codex 교차검토 1회 완료(2026-08-20)** 후 개정판 — §4가 통째로, §1-1·§4-5가 새로.
선행: M1-2a~2g 완료. **하드웨어 기능과 배관이 전부 실증됐다.**

## 0. 이 문서의 범위

M1-2까지로 **유저랜드가 삼각형을 그릴 수 있다.** 남은 것은 **Mesa가 그
유저랜드가 되게 하는 것**이다.

**이 단계는 지금까지의 어느 단계보다 크고, 성격도 다르다.** D1~D3는
"하드웨어가 무엇을 하는가"를 실측으로 알아내는 일이었고 각 단계가 하루
안팎이었다. 여기는 **소프트웨어 통합**이며, 알아낼 것보다 맞춰야 할 것이
많다.

## 1. 확인된 사실 — 트리를 직접 읽었다

`opennstep-mesa342/upstream/Mesa-3.4.2`가 있고 **소프트웨어 렌더러가
실기에서 이미 동작한다.**

### 1-1. 훅 테이블

`src/dd.h:822-825`가 가속 프리미티브 훅 넷을 정의한다:

```c
points_func   PointsFunc;
line_func     LineFunc;
triangle_func TriangleFunc;
quad_func     QuadFunc;
rect_func     RectFunc;
```

그리고 `:833-842`:

```c
void (*RenderStart)( GLcontext *ctx );
void (*RenderFinish)( GLcontext *ctx );
void (*RasterSetup)( struct vertex_buffer *VB, GLuint start, GLuint end );
```

주석은 이 둘이 "one or more vb flush 앞뒤로" 불린다고 말하고, 곧이어
**"a bit broken at present"** 라고 덧붙인다(`dd.h:835-843`). 초안은 앞부분만
읽고 **배치 경계로 삼으려 했다. 뒷부분이 중요하다** — §4-5.

### 1-2. 삼각형 훅의 시그니처

`src/types.h:117`:

```c
typedef void (*triangle_func)( GLcontext *ctx,
                               GLuint v1, GLuint v2, GLuint v3, GLuint pv );
```

**정점 자체가 아니라 정점 버퍼의 인덱스**를 받는다. 변환된 좌표는
`VB->Win`(`src/vb.h:248`, `GLvector4f`)에 있고, 색은 `VB->ColorPtr->data[]`
(FX가 `fxrender.c:263`에서 그렇게 읽는다), 텍스처 좌표는
`VB->TexCoordPtr[unit]`이다.

→ **우리가 받는 것은 화면 좌표계의 정점 셋이다.** 클리핑·변환·조명은
Mesa가 이미 했다.

### 1-3. FX 드라이버가 참고가 되는 이유

`src/FX/`가 Glide 위의 하드웨어 백엔드이고 **구조가 우리와 같다** —
`RasterSetup`으로 정점을 자기 형식으로 바꾸고, 프리미티브 훅에서 하드웨어에
넘긴다. 우리는 Glide 대신 우리 배치를 쓴다.

**단, FX는 Glide가 삼각형을 받아준다.** 우리 하드웨어는 **사다리꼴만**
받는다(§2-1).

## 2. 가장 큰 미지수

### 2-1. 삼각형 → 사다리꼴 분할은 **우리가 해야 한다**

Storm 엔진의 프리미티브는 `TRAP`/`TEXTURE_TRAP`, 즉 **위아래가 수평인
사다리꼴**이다. OpenGL 삼각형은 임의 방향이다.

일반 삼각형은 **정점 세 개를 y로 정렬해 최대 두 개의 사다리꼴로 나눈다** —
가운데 정점을 지나는 수평선에서 자른다. 이건 표준적인 일이지만
**우리가 처음 짜는 부분**이고, D3-2가 실측한 변 걷기 규칙(`AR`/`SGN`,
`e` 항) 위에서 정확해야 한다.

**여기가 이 단계에서 틀리기 가장 쉬운 곳이다.**

### 2-2. 보간 계수를 정점 셋에서 유도해야 한다

지금까지 시험은 `DR`/`ALPHASTART`/`TMR` 값을 **손으로 정해서** 넣었다.
Mesa 백엔드는 **정점 셋에서 평면 방정식을 풀어** 시작값과 x·y 증분을
계산해야 한다. 색 3채널 + 알파 + 깊이 + 텍스처 좌표 2개 = **7개 평면**.

고정소수점 자리는 전부 실측돼 있다(색·깊이·알파 `<<15`, 텍셀
`1<<(20-log2)`). **미지수는 형식이 아니라 산술의 정확도**다 — 특히
`cc 2.7.2.1`에서 `long long` 없이.

### 2-3. 프레젠테이션이 없다

`S5 §2`가 실측으로 결론지었다: **창 안 가속은 불가능하다.** 그리려면
전체화면을 소유해야 하는데, **그 방법을 우리는 모른다.**

→ **M1-3은 화면에 올리지 않는다.** 오프스크린에 그리고 `glReadPixels`
계열로 되읽어 소프트웨어 렌더러와 비교한다. 프레젠테이션은 M2다.

**이건 회피가 아니라 순서다** — 렌더링이 맞는지 모르는 채로 화면 소유
문제를 붙이면 실패 원인이 두 겹이 된다.

## 3. 단계

### M1-3a — 배관만, 그리고 **되돌림 요령을 먼저 증명한다**

훅 셋을 채우되 `TriangleFunc`는 **호출 횟수를 세고 §4-3으로 얻은
소프트웨어 함수에 그대로 넘긴다.** 우리는 아무것도 그리지 않는다.

**검증**
- 호출 횟수가 그린 삼각형 수와 같은가.
- `RenderStart`/`Finish`가 배치당 한 번씩인가.
- **화면이 소프트웨어 렌더러 단독일 때와 픽셀 단위로 같은가.**
  같아야 한다 — 우리는 전부 넘기고 있으므로. **이것이 §4-3 요령의
  판정이다.** 다르면 요령이 틀린 것이고, 그러면 §4-4의 (나)로 간다.
- 상태를 바꿔가며(블렌딩 on/off, 텍스처 on/off) 반복해 **상태 변경 후에도
  요령이 유효한지** 본다(§4-1이 훅을 지우므로).
- **`GL_QUADS`로도 그려 호출 횟수를 센다.** §4-6대로라면 사각형 하나당
  삼각형 훅이 **두 번** 불려야 한다. 그렇지 않으면 §4-6이 틀린 것이다.
- `glBegin`/`glEnd` 하나에 삼각형을 많이 넣어 **`RenderStart` 쌍이 몇 번
  오는지** 센다. §4-5대로라면 **한 번이 아닐 수 있다.**

**이 단계는 "Mesa가 우리를 부르는가"와 "우리가 되돌릴 수 있는가"를
동시에 답한다. 후자가 §4의 전제이므로 먼저 확인한다.**

### M1-3b — 축 정렬 삼각형 하나

`TriangleFunc`에서 정점을 읽어 **밑변이 수평인 삼각형**만 처리하고 나머지는
소프트웨어로 넘긴다. 사다리꼴 하나로 표현된다.

**검증**: 같은 삼각형을 소프트웨어 렌더러로도 그려 **픽셀 단위 비교**.
±1 허용(반올림). D3-2가 이미 사다리꼴 기하를 실측했으므로 **대조군이
두 개**다 — 소프트웨어 Mesa와 우리 커널 프로브.

### M1-3c — 일반 삼각형: 분할

§2-1의 분할을 넣는다.

**검증**: 무작위 삼각형 100개를 소프트웨어와 비교. **틀린 픽셀 수의
분포**를 보고한다 — "몇 개 틀림"이 아니라 **어디가 어떻게 틀린지**.
가장자리 한 줄이 어긋나는 것과 절반이 어긋나는 것은 다른 문제다.

### M1-3d — 보간: 색 → 깊이 → 텍스처

§2-2의 평면 방정식을 채널별로 하나씩 켠다. 각 단계에서 소프트웨어와 비교.

**한꺼번에 켜지 않는다** — D3-3a의 교훈이다.

### M1-3e — 상태 매핑

`glDepthFunc`/`glBlendFunc`/`glEnable(GL_TEXTURE_2D)`를 우리 `dwgctl`·
`alphactrl`로. 하드웨어가 `glBlendFunc` 인자와 1:1이므로 기계적이다
(D3-5 §8). **하드웨어에 없는 조합은 소프트웨어로 되돌린다.**

## 4. 되돌림(fallback) — 초안이 틀렸다, 기제는 **상태 단위**다

초안은 "훅 안에서 처리 못 할 프리미티브를 소프트웨어로 넘긴다"고 썼다.
**Mesa 3.4.2가 제공하는 기제는 그것이 아니다.** 트리를 읽어 확인했다.

### 4-1. 실제 기제 — 능력(capability) 광고

`state.c:1090-1102`가 관련 상태가 바뀔 때마다 이렇게 한다:

```c
ctx->IndirectTriangles = ctx->TriangleCaps & ~ctx->Driver.TriangleCaps;
ctx->IndirectTriangles |= DD_SW_RASTERIZE;
ctx->Driver.PointsFunc = NULL;
ctx->Driver.LineFunc = NULL;
ctx->Driver.TriangleFunc = NULL;      /* 훅을 전부 지운다 */
...
/* 그 다음 드라이버가 다시 설치한다 */
```

즉 **상태가 바뀔 때마다 훅이 지워지고 드라이버가 다시 고른다.**
드라이버는 `Driver.TriangleCaps`로 **자기가 구현하는 기능**을 광고하고,
Mesa는 `TriangleCaps & ~Driver.TriangleCaps`로 **드라이버가 못 하는 것**을
소프트웨어 경로로 돌린다. 깃발 목록은 `types.h:1497-1525`
(`DD_TRI_CULL`, `DD_TRI_OFFSET`, `DD_TRI_UNFILLED`, `DD_FLATSHADE` 등).

FX는 `DD_TRI_CULL|DD_TRI_OFFSET|DD_TRI_LIGHT_TWOSIDE`를 광고한다
(`FX/fxdd.c:1167`).

**→ 되돌림의 자연스러운 단위는 프리미티브가 아니라 상태다.**

### 4-2. 소프트웨어 함수 포인터는 **저장되지 않는다**

`gl_set_triangle_function`(`triangle.c:1523-1533`)은 이렇게 시작한다:

```c
if (ctx->Driver.TriangleFunc) {
    /* Device driver will draw triangles. */
    return;
}
```

**우리 훅을 설치하면 Mesa는 소프트웨어 함수를 아예 고르지 않는다.**
그리고 소프트웨어 삼각형 루틴은 전부 `triangle.c`의 `static`이라
**이름으로 부를 수 없다**(`:640`, `:885`, `:1428` 등).

→ **훅 안에서 "이건 못 하겠으니 소프트웨어로"라고 넘길 대상이 없다.**

### 4-3. 그래도 프리미티브 단위 되돌림은 가능하다 — 다만 요령이다

`gl_set_triangle_function`은 `triangle.h:38`에 선언된 **공개 함수**다.
따라서 드라이버가:

1. `ctx->Driver.TriangleFunc`를 잠시 `NULL`로 두고
2. `gl_set_triangle_function(ctx)`를 불러 Mesa가 고르게 하고
3. 그 포인터를 저장한 뒤
4. 자기 훅을 되돌려 놓는다

**정본에 없는 요령이므로 그렇게 표시한다.** 상태가 바뀔 때마다 다시
해야 하고(§4-1), 저장한 포인터가 그 상태에 맞는 것인지 우리가 책임진다.

### 4-3b. 함수 포인터가 **둘**이다 — 재귀 함정

`ctx->Driver.TriangleFunc`와 `ctx->TriangleFunc`는 다른 것이다.
뒤엣것은 디스패치 래퍼(`types.h:1825`)로, `Driver`의 것에서 복사되거나
코어의 셋업 래퍼로 대체된다(`vbrender.c:758`).

**우리 훅 안에서 `ctx->TriangleFunc`를 부르면 우리 자신으로 재귀할 수
있다.** 되돌림에는 §4-3으로 저장한 `Driver.TriangleFunc`만 쓴다.

### 4-4. 이것이 §3의 단계 나누기를 바꾼다

M1-3b를 "축 정렬 삼각형만 처리"로 잡았는데, **축 정렬 여부는 상태가 아니라
기하**라서 §4-1의 기제로는 표현되지 않는다. 둘 중 하나다:

- **(가)** §4-3의 요령을 M1-3b부터 쓴다. 기하로 나눌 수 있게 된다.
- **(나)** M1-3b를 "가장 단순한 **상태**만 처리"로 바꾸고 **분할은 처음부터
  완성**한다.

**(가)를 택한다.** (나)는 §2-1의 분할이 첫 단계부터 정확해야 해서,
"작은 단계로 나눠 실패 원인을 하나로 유지한다"는 이 프로젝트의 방식과
어긋난다. 요령이 정본에 없다는 점은 **M1-3a에서 먼저 검증한다**(§3).

### 4-5. **`RenderStart`/`RenderFinish`는 배치 경계가 아니다**

초안은 이 둘로 배치를 열고 닫으려 했다. **성립하지 않는다.**

- 일반 VB 렌더러는 **VB 하나마다** `RenderStart` … `RenderFinish`를 부른다
  (`vbrender.c:698`, `:724`, `:727`). 따라서 `glBegin`/`glEnd` 하나가 여러
  VB에 걸치면 **쌍이 여러 번** 온다 — `dd.h:835`의 "at most once"와 반대다.
- 더 나쁘게, **드라이버가 파이프라인 단계를 교체하면 아예 안 불린다.**
  FX가 `fxDDMergeAndRender`를 렌더 단계로 등록하는데(`fxpipeline.c:123`),
  그 경로는 프리미티브를 디스패치하면서(`fxcva.c:474`) `RenderStart`를
  전혀 부르지 않는다(`fxcva.c:422`).

**→ 이 훅들은 "일반 경로의 알림"이지 정확성이 걸린 경계가 아니다.**

**설계를 바꾼다: 배치 경계는 *브래킷*이 아니라 *플러시 지점*이다.**
배치를 다음 중 무엇이든 일어나면 비운다:

| 플러시 계기 | 왜 |
| --- | --- |
| 배치가 참(삼각형 200개) | 구조적 상한 |
| `Driver.UpdateState` — 상태가 바뀜 | 상태가 배치 단위이므로 필수 |
| `RenderFinish` | 오면 좋고, 안 와도 위의 것들이 덮는다 |
| 프레임버퍼 읽기(`glReadPixels` 등) | 결과를 보기 전에 그려져 있어야 한다 |
| `glFlush`/`glFinish`/버퍼 교체 | 명시적 |

**"안 와도 덮인다"가 요점이다** — 안 오는 훅에 정확성을 걸지 않는다.

### 4-6. `QuadFunc`를 비워도 사각형이 소프트웨어로 가지 않는다

코어의 `basic_quad`가 **`Driver.TriangleFunc`를 두 번 부른다**
(`quads.c:44`, `:75`). 즉 `QuadFunc`를 `NULL`로 두면 사각형이
**우리 삼각형 훅으로 들어온다.**

**받아들여도 되지만 모르고 있으면 안 된다** — "삼각형만 구현했으니 사각형은
소프트웨어겠지"가 틀린 가정이다. M1-3a의 호출 횟수 검증에 `GL_QUADS`를
넣어 이것을 실측한다.

## 5. 검증 방법 — 소프트웨어 렌더러가 대조군이다

**같은 Mesa가 같은 장면을 두 번 그린다** — 한 번은 소프트웨어로, 한 번은
우리 백엔드로. 이보다 나은 대조군은 없다.

- 픽셀 단위 비교, ±1 허용
- 틀린 픽셀의 **분포**를 보고(가장자리인가 내부인가)
- 되돌림이 일어난 프리미티브 수를 센다 — **0이라고 가정하지 않는다**

## 6. 이 계획이 결정하지 않은 것

- 전체화면 소유(M2).
- 텍스처 업로드 경로. S4a로 유저랜드가 VRAM에 직접 쓸 수 있으므로 CPU
  복사가 가능하다.
- 성능. **이 단계의 목표는 정확성이지 속도가 아니다.**

## 7. 정직한 규모

M1-3a는 하루 규모다. M1-3c(분할)와 M1-3d(보간)는 **아니다.**
`S5 §5`가 "차원이 다른 규모"라고 한 것 중 실제로 남은 것이 이 둘이다.
