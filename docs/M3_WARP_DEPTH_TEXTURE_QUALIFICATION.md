# M3 — WARP 의 깊이·텍스처 자격검증 (2026-08-28, 코딩 전)

지금까지의 WARP 증명은 **전부 깊이를 끄고 텍스처 레지스터를 0 으로** 돌렸다.
M2 §11 이 이것을 진짜 blocker 로 지목했다.

## 0. 이미 확립된 것 — 다시 묻지 않는다

M2 에서 세 번 같은 실패를 했으므로, 이번엔 먼저 훑었다.
**아래는 전부 사다리꼴 경로로 실기 확인이 끝났다**(`docs/TEST_STATUS.md`):

| | 결과 |
| --- | --- |
| 깊이 비교 일곱 | 전부 소프트웨어와 일치. `GL_NEVER` 는 거절 — `zmode` 1 은 **예약값** |
| `glDepthMask` | **접근 유형이 그것이다 — `ZI` 는 비교하고 쓰고, `I` 는 비교만** |
| 깊이 보간 | 중심 잔차 −0.5, 클램프 발동 0 |
| 공유 변 | 색·깊이 모두 이음매 없음 |
| 알파 시험 일곱 | 전부 일치. 비교하는 것은 **텍스처 스테이지의** 알파, 버린 프래그먼트는 깊이도 안 쓴다 |
| `CLAMPUV` | **가져오는 주소**를 텍스처 안에 묶는다(실측). 그래서 좌표 행렬을 아예 안 묶는다 |
| 텍스처 크기 | 2 의 거듭제곱일 필요 없음. 상한 2048. 피치는 텍셀 단위 |

**이것들은 그리기 엔진의 성질이고, WARP 는 그 엔진에 먹이를 줄 뿐이다.**
WARP 가 바꾸는 것은 **보간기 셋업을 누가 계산하는가** 하나다.

그러므로 자격검증의 질문은 좁다: **WARP 가 같은 셋업을 만드는가.**

## 1. 참조가 정한 정점 규약 (실측 아님, 소스)

`mgavb.c:88-92`:

```
rhw = win[3]                       Mesa 의 1/w
z   = depth_scale * win[2]         depth_scale = 1/(2^bits − 1)  ->  z ∈ [0,1]
x   =  win[0] + xoffset
y   = −win[1] + yoffset            <- Y 가 뒤집힌다
```

`mga_xmesa.c:364-378`: `depth_scale` 은 16/24/32 비트에 대해
`1/0xffff`, `1/0xffffff`, `1/0xffffffff`.

`mgavb.c:40-41`, `:78-83` (원근 텍스처):

```
tu0 = s,  tv0 = t                  정규화 좌표 그대로 — 텍셀로 스케일하지 않는다
q 가 있으면:  rhw *= q,  tu0 /= q,  tv0 /= q
```

**우리 `OSMGAMesaVertex` 와 그대로 맞는다** — `s`/`tc` 가 이미 *"NORMALISED, not
multiplied by the texture's size"* 이고 `qw`(= Win[3])와 `tq` 를 따로 갖고 있다:

```
rhw = qw * tq
tu0 = s  / tq
tv0 = tc / tq
z   = (z_field / 256) / (2^bits − 1)
y   = 뒤집기 필요
```

**이 변환은 전부 유저랜드에서 double 로 한다.** 커널은 비트 패턴을 검증만 한다.

## 2. 신탁은 소프트웨어가 아니라 **사다리꼴 경로**다

사다리꼴 경로는 이미 소프트웨어와 일치함이 증명됐다. 그러므로 같은 기하를
두 경로로 그려 **픽셀·깊이를 직접 비교**하면 된다. 신탁이 같은 기계 안에 있어
빠르고, 불일치의 원인이 **WARP 의 셋업 하나로 좁혀진다.**

## 3. 물을 것 — 여섯

| | 질문 | 왜 열려 있나 |
| --- | --- | --- |
| **T1** | WARP 의 `z ∈ [0,1]` 이 사다리꼴의 `z0/zdx/zdy` 와 같은 깊이 코드를 내는가 | 우리 실행은 전부 깊이 꺼짐. `z=0.5f` 를 보냈지만 아무도 읽지 않았다 |
| **T2** | `atype = ZI` 로 WARP 가 깊이를 **쓰는가** | `ZI`/`I` 의 뜻은 알지만 WARP 가 그 경로를 먹이는지는 미확인 |
| **T3** | 정규화 `tu0/tv0` 로 실제 텍스처가 나오는가 | 텍스처 레지스터를 전부 0 으로만 돌렸다 |
| **T4** | 원근(`rhw` 가 정점마다 다른 양수)이 참조 규칙대로 되는가 | §1 은 소스일 뿐 실측이 아니다 |
| **T5** | 필터 footprint 가 `CLAMPUV` 안에 묶이는가 | bilinear/mipmap 은 점보다 넓게 읽는다(3-217~218). 사다리꼴에서 실측했지만 WARP 가 좌표를 몰 때도 같은지 |
| **T6** | WARP → 사다리꼴 → WARP 전환이 상태를 오염시키지 않는가 | D2 는 **같은 컨텍스트**가 두 VERTEX 제출 사이에 사는 것만 증명했다 |

## 4. 설계 — 한 부팅에 순서대로, 앞이 뒤를 gate

D2 하네스(오프스크린 블록 + 전수 픽셀 맵 + `DWGSYNC` 펜스 + 실패 정책)를 그대로 쓴다.
블록을 **색과 깊이 두 개** 매핑한다.

```
T1  깊이 읽기      WARP 삼각형 하나, atype I(비교만), ZLT, 미리 채운 깊이 버퍼
                  -> 같은 기하를 사다리꼴로도. 색 픽셀 맵이 같아야 한다
T2  깊이 쓰기      atype ZI, NOZCMP, 삼각형 하나
                  -> 깊이 버퍼를 읽어 사다리꼴 결과와 코드 단위로 비교
T3  텍스처        4×4 알려진 텍스처, nearest + clamp, 사각형(삼각형 2)
                  -> 색 픽셀 맵을 사다리꼴과 비교
T4  원근          같은 사각형, 정점마다 다른 양의 rhw
                  -> 사다리꼴과 비교
T5  필터          bilinear, 텍스처 가장자리를 넘는 좌표
                  -> 텍스처 **밖**에 카나리를 두고 안 읽혔음을 본다
T6  층 전환       WARP -> 사다리꼴 -> WARP, 사이에 펜스
                  -> 세 결과가 모두 맞아야 한다
```

**T1 이 실패하면 T2 이하는 무의미하다** — 깊이 코드 규약이 틀린 것이므로.

## 5. 무엇이 무엇을 뜻하는가

| 관측 | 결론 |
| --- | --- |
| 전부 일치 | WARP 가 사다리꼴과 같은 셋업을 만든다. ABI 를 확정할 수 있다 |
| T1 이 **일정한 오프셋**만큼 다름 | `depth_scale` 규약이 다르다 — 상수 하나로 고칠 수 있다 |
| T1 이 **비선형**으로 다름 | z 가 `[0,1]` 이 아니거나 `rhw` 로 나뉜다(원근 깊이). 규약 재조사 |
| T3 이 **텍셀만큼 밀림** | `tu0` 가 정규화가 아니라 텍셀 단위다 |
| T5 에서 카나리가 읽힘 | **봉쇄 실패** — `CLAMPUV` 가 WARP 경로에서는 다르게 동작한다. 즉시 중단 |
| T6 오염 | 층 전환마다 WARP 그림자를 전부 dirty 로 해야 한다 |

## 6. 봉쇄는 바뀌지 않는다 — 한 곳만 빼고

`TEXCTL` 은 계속 **커널 소유**이고 `CLAMPUV` 는 계속 켜진다. 봉쇄 논증은
그대로다(`HW3D.h:286`). WARP 는 좌표를 만들 뿐 **클램프 하드웨어를 우회하지 않는다**
— 라고 보지만 **그것이 T5 다.** 증명 전까지는 가정하지 않는다.

## 7. 범위 밖

- mipmap(3-217 의 세 번째 footprint) — nearest 와 bilinear 가 먼저다
- 이중 텍스처(파이프 8~15)
- 스텐실
- 성능. 이 단계는 **정확도만** 본다

## 8. codex 에 물을 것

1. §0 이 맞나 — 깊이 비교·`ZI`/`I`·알파·`CLAMPUV` 가 **엔진의 성질**이고 WARP 가
   그것을 바꾸지 않는다는 전제. 반증이 있나.
2. §1 의 정점 규약이 맞나. 특히 `z = depth_scale * win[2]` 가 `[0,1]` 이고
   **원근으로 나뉘지 않는다**는 것. WARP 가 z 를 `rhw` 로 나누나?
3. 사다리꼴 경로를 신탁으로 쓰는 것이 건전한가.
4. T1~T6 의 순서와 gate 가 맞나. 빠진 시험이 있나.
5. T5 의 카나리 배치가 필터 footprint 를 실제로 잡나.
6. WARP 가 깊이를 쓸 때 `MACCESS.zwidth` 와 `ZORG` 정렬(128)이 어떻게 걸리나.
7. 빠진 것.


## 11. T3~T6 — 레지스터 구성은 확보, 그러나 질문이 하나 남는다

사다리꼴 텍스처 경로(`osmgaTextureSetup`, 실기 검증됨)에서 그대로 가져온다:

```
TEXCTL2   = G400_MAGIC | CKSTRANSDIS
TEXCTL    = PITCHLIN | (pitch<<9) | TAKEY | CLAMPUV | TW32
TEXFILTER = ALPHA | (0x10 << 21)
TEXWIDTH  = ((dim-1)<<18) | (((8-log2dim)&63)<<9) | log2dim     (HEIGHT 동일)
TEXTRANS  = TEXTRANSHIGH = 0x0000ffff
DWGCTL    = (GOURAUD & ~OPCODE_MASK) | TEXTURE_TRAP
```

**빠지는 것 둘, 그리고 그것이 요점이다:**

- **`TMR0..TMR8` 을 쓰지 않는다.** 사다리꼴 경로는 좌표 행렬을 CPU 로 계산해
  아홉 레지스터에 싣는다. **WARP 가 그것을 정점에서 만든다** — 이 시험의 전부다.
- **`NOPERSP` 를 켜지 않는다.** 사다리꼴은 affine 평면을 먹이므로 켠다.
  WARP 는 `rhw` 로 원근을 한다. T3 은 `rhw = 1` 이므로 수학적으로 같고,
  T4 가 그것을 `rhw` 를 바꿔 가른다.

### 11.1 미해결 — `TDUALSTAGE0` 이 텍스처에서 무엇이어야 하나

| 근거 | 값 | 맥락 |
| --- | --- | --- |
| 실기 검증된 사다리꼴 텍스처 경로(`osmgaTextureSetup`) | **`0`** | `TEXTURE_TRAP` |
| 사양서 4-42 | **`color0sel = '11'`(`0x00600000`)** | *"Gouraud shaded trapezoids"* |
| 지금의 WARP 목록 | `0x00600000` | 무텍스처, 4-42 를 따름 |

**둘이 충돌하는지, 아니면 4-42 가 `opcode = trap` 에만 걸리는지 모른다.**
`TEXTURE_TRAP` 은 다른 opcode 다. 틀리면 색이 텍스처가 아니라 diffuse 로
나오거나 그 반대다 — hang 이 아니라 그림이 틀린다.

### 11.2 T3~T6 설계

```
T3  nearest + clamp, 8x8 이상, 주소 부호화 텍셀, rhw = 1
    -> 사다리꼴 오라클과 픽셀 비교
    -> TDUALSTAGE0 을 0 과 0x00600000 두 번 돌려 §11.1 을 실측으로 가른다
T4  qw 와 tq 를 독립적으로 바꾸고 z 도 함께 바꾼다
    -> z 가 rhw 로 나뉘지 않음의 직접 시험
T5  bilinear, min 과 mag 각각
    -> 텍스처 앞뒤와 행 패딩에 가드 텍셀(주소 디코드 가능)
    -> 출력에 그 값이 섞여 나오는지로 fetch 주소를 본다
T6  펜스 -> suspend -> quiesce -> 사다리꼴 -> 전체 재발행 -> 재시작
```

### 11.3 codex 에 물을 것

1. **§11.1 이 핵심이다.** `TEXTURE_TRAP` 에서 `TDUALSTAGE0` 은 무엇이어야 하나.
   4-42 의 요구가 `opcode = trap` 전용인가. 두 값을 다 돌려 보는 것이 맞나.
2. `NOPERSP` 를 WARP 에서 끄는 것이 맞나. 켜면 `rhw` 가 무시되나?
3. `TMR0..8` 을 안 쓰는 것이 정말 맞나 — WARP 가 그 레지스터를 **쓰는가**,
   아니면 다른 경로로 텍스처 기울기를 넣는가.
4. T3 의 8×8 주소 부호화 텍셀 설계가 fetch 주소를 실제로 드러내나.
5. T5 의 가드 텍셀 배치(앞·뒤·행 패딩)가 bilinear footprint 를 잡나.
6. 빠진 것.
