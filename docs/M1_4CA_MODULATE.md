# M1-4ca — `GL_MODULATE` (2026-08-22, 재부팅 대기)

## 1. 왜 이것이 다음인가

`GL_MODULATE` 는 GL 의 **기본** 텍스처 환경 모드다.  `GL_REPLACE` 만 받는
동안 이 백엔드는 "표본기 시연"이고, 이것을 받아야 보통의 고정기능 텍스처링이
된다.  교차검토도 남은 것 중 첫째로 꼽았다.

## 2. 네 가지 조합, 코드 경로가 아니라 워드 넷

Mesa 의 표(`texture.c`, `apply_texture`):

```
   RGB   REPLACE   Cv = Ct      Av = Af
   RGBA  REPLACE   Cv = Ct      Av = At
   RGB   MODULATE  Cv = Cf Ct   Av = Af      <- 알파는 건드리지 않는다
   RGBA  MODULATE  Cv = Cf Ct   Av = Af At
```

레지스터에서 ARG1 은 텍스처, ARG2 는 (피연산자 필드를 0 으로 두면) 보간값이고
`SEL` 이 무엇을 내보낼지 고른다:

```
   색   SEL_ARG1 (0)          또는 SEL_MUL (0x00600000)
   알파 SEL_ARG1 (0) / SEL_ARG2 (0x40000000) / SEL_MUL (0xc0000000)
```

그래서 위 표는 워드 네 개다.  `TEXF_MODULATE` 하나가 더해졌다.

## 3. 곱은 규칙이지 이상값이 아니다

Mesa 의 곱은

```
   PROD(A, B) = (A * (B + 1)) >> 8        (texture.c:2367)
```

이고 `A*B/255` 와 **다르다** — 192 × 192 에서 Mesa 는 144, 반올림 몫은 145.
맞춰야 할 것은 Mesa 이므로 엔진을 **Mesa 에 대고** 재야 한다.
(교차검토는 `a*b/255` 기준의 145 를 예로 들었는데, 여기서 기준은 그것이
아니다.)

## 4. 재기 전에는 관문을 열지 않는다

커널에 조합을 넣되 **Mesa 쪽 관문은 아직 `GL_REPLACE` 만** 받는다.  엔진의
곱이 Mesa 와 다르면 모든 화소가 어긋나므로, 먼저 재고 그다음에 연다.

§35 가 한 번의 그리기로 곡선 전체를 잰다: 텍스처의 빨강이 텍셀마다 0, 4,
8 … 로 오르고 삼각형의 빨강은 128 로 고정이므로, 열 c 는 `PROD(128, 4c)` 다.
초록은 255 에 대고, 파랑은 0 에, 알파는 255 에 대고 끝을 확인한다.

예상(Mesa):

```
   red   0 16 32 48 64 80 96 112 ...
   green 200   blue 0   alpha 128
```

## 5. 잰 결과 — 엔진의 곱은 Mesa 의 곱이 아니다 (2026-08-23)

### 5-1 첫 시험은 아무것도 증명하지 못했다

§35 는 조각의 빨강을 128 로 고정하고 텍셀의 빨강만 걸었고, 64 열이 전부
Mesa 와 맞았다.  **그게 증거가 아니다**: python 으로 확인하니 조각값 128 에서는
후보 규칙들이 **한 점도 갈리지 않는다.**  약한 자리에서 일치한 것이다.

### 5-2 두 피연산자를 모두 움직였다

텍셀의 빨강은 열을 따라, 조각의 빨강은 색 보간기의 y 증분으로 **행을 따라**
올려 한 번의 그리기로 64×64 표를 얻었다(§36).  4096 표본을 다섯 규칙에 대고
세면:

```
     Mesa   /255    >>8   +128 approx
     1163      4   2613    751      4
```

`/255` 계열이 남긴 **4 개**는 대칭 쌍이다 — (188,196)과 그 거울, (208,236)과
그 거울 — 그리고 넷 다 정확한 몫이 **반올림 경계 바로 위**(144.502, 192.501)
인데 엔진이 내림한다.  그래서 규칙이 정해진다:

```
   엔진   (a * b * 257 + 32768) >> 16        255 로 나누는 통상적 근사
   Mesa   (a * (b + 1)) >> 8                 더 거친 근사
```

격자에서 이 후보가 정확반올림과 갈리는 자리는 **정확히 그 네 쌍**이고 다른
곳은 없다.  즉 실측이 후보를 **골라낸다**.

### 5-3 맞출 수는 없다

텍셀이 255 면 두 규칙 모두 조각값 그 자체가 되므로 `a' = a` 로 못 박히고,
조각 색을 미리 편향시켜 맞출 여지가 **남지 않는다.**  65536 쌍 중 **18736
(28.6%)** 이 어긋나고 차이는 언제나 1 이며, 엔진이 더 큰 쪽이 17260, 작은 쪽이
1476 로 **한쪽으로 치우쳐** 있다.

### 5-4 그런데 흰색에서는 정확히 같다

모든 텍셀값에서 두 규칙이 일치하는 조각값은 **0, 128, 254, 255** 뿐이고,
그중 255 는 GL 의 **기본 정점색**이다.  실제로 재 보면:

| 장면 | 색이 다른 화소 | 최대차 |
|---|---|---|
| MODULATE, 정점색 흰색(기본) | **24** (위상 화소뿐) | 16 |
| MODULATE, 단색 (0.6,0.8,0.35) | 11025 / 25964 | 13 |
| MODULATE, 정점마다 다른 색 | 8516 / 16384 | **1** |

단색 장면의 11025 중 **11001 이 한 단계**이고 **두 단계 이상은 24** — 이미
알려진 위상 화소 그 개수다.  곱의 오차와 텍셀 선택의 오차가 **깨끗이
갈린다**(교차검토가 요구한 분리).

즉 **조명 없는 텍스처 프로그램은 소프트웨어와 동일**하고, 어긋남은 정점색을
쓸 때만 나타난다.

### 5-5 그래서 연다 — 다만 예외로 명시한다

이것은 앞선 두 예외(변 규칙 10 화소, 이중선형 한 단계 1%)와 **같은 급이
아니다.** 28.6% 는 훨씬 넓고 치우쳐 있다.  "하드웨어가 더 정확하다"는 사실이나
**호환성의 근거는 아니다** — 이 저장소의 기준은 Mesa 다.  그래도 여는 이유는:

* `GL_MODULATE` 는 GL 의 **기본** 환경 모드다.  막으면 보통의 프로그램은
  **한 번도 가속되지 않는다.**
* 기본 정점색에서는 **정확히 일치**한다.
* 맞출 방법이 없다(§5-3).  결합기는 고정 기능이다.

### 5-6 독값이 또 한 번 값을 했다

교차검토가 옳게 짚었다: RGB 텍스처만으로는 "알파는 `Af` 를 통과"와
"`Af × 1`" 을 구분할 수 없다.  그런데 이 백엔드는 RGB 텍셀의 알파를 **0**
으로 둔다.  그래서 RGB+MODULATE 의 알파가 **255** 로 나온 것은, 알파 선택자가
색의 곱과 **독립**임을 그대로 증명한다 — 곱해졌다면 0 이었을 것이다.
