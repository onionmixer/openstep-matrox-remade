# W15 — AR/DR/ALPHA 의 예약 비트 (2026-08-28, 코딩 전)

W11 §8.1 의 검토가 W12 를 보며 지적했다: **원점 셋은 전수 감사가 아니다.**
같은 모양의 결함이 다른 레지스터에도 있다. 위험도는 낮지만 실재한다.

---

## 1. 결함

인코더가 클라이언트 값을 **부호 있는 채로 캐스팅해 그대로** 쓴다(`:10173`):

```c
v[2]  = (unsigned long)t->ar1;              /* 음수면 0xFFxxxxxx */
v[8]  = t->dr[0];  ...  v[16] = t->dr[8];
v[20] = t->a0;  v[21] = t->adx;  v[22] = t->ady;
```

그런데 이 레지스터들은 **32 비트가 다 값이 아니다**(사양서 전수 추출):

| 레지스터 | 값 필드 | 예약 |
| --- | --- | --- |
| `AR0` `AR2` `AR4` `AR5` `AR6` | `<21:0>` | `<31:22>` |
| `AR1` | `<23:0>` | `<31:24>` |
| `DR4 6 7 8 10 11 12 14 15` | `<23:0>` | `<31:24>` |
| `ALPHASTART` `ALPHAXINC` `ALPHAYINC` | `<23:0>` | `<31:24>` |
| **`DR0` `DR2` `DR3`** (Z) | **`<31:0>`** | **없음 — 문제 없음** |

사양서의 표준 문구: *"Reserved. When writing to this register, the bits in
this field **must be set to '0'**."*

**음수를 32 비트로 캐스팅하면 예약 비트가 전부 1 이 된다.**

## 1.1 검증기가 현재 무엇을 막는가 (python)

```
OSMGA_HW3D_EDGE_WALK = 16384

  AR1 AR2 AR4 AR5   +-16384 로 묶임      -> 필드에 들어간다 (크기는 안전)
  AR0 AR6           > 0 만 검사, 상한 없음 -> 임의값 가능
  DR4..DR15         검사 없음             -> 임의값 가능
  ALPHA*            검사 없음             -> 임의값 가능
```

**두 가지가 다른 문제다:**

1. **크기** — 값이 필드에 안 들어갈 수 있다 (AR0·AR6·DR·ALPHA)
2. **인코딩** — 들어가는 값도 32 비트 표현이 예약 비트를 침범한다 (전부)

`AR1`·`AR2`·`AR4`·`AR5` 는 1 번이 이미 막혀 있고 2 번만 남았다.

---

## 2. 고치는 방식 — **W12 와 반대로, 여기서는 마스킹이 옳다**

W12 는 거부했다. 정렬 안 된 원점은 **다른 주소**이므로 마스킹하면 요청과
다른 곳에 그린다.

**여기는 다르다.** 22 비트 필드에 대한 `-1` 은 `0x3FFFFF` 가 **정확한 2 의
보수 표현**이다. 32 비트 `0xFFFFFFFF` 를 마스킹하는 것은 **의미를 바꾸는 것이
아니라 옳게 인코딩하는 것**이다.

> **크기는 거부하고, 인코딩은 마스킹한다.**
>
> - 값이 부호 있는 필드에 **안 들어가면 거부** — 마스킹하면 조용히 다른 값이 된다
> - 들어가면 **필드 폭으로 마스킹** — 이것이 하드웨어가 기대하는 표현이다

### 2.1 어디에 무엇을

| | 어디 | 왜 |
| --- | --- | --- |
| 크기 검사 | **검증기** (`hw3d/`, 이식 가능) | 호스트에서 시험된다 |
| 마스킹 | **인코더** (드라이버) | 값이 레지스터로 가는 지점 |

**둘 다 필요하다.** "필드에 들어간다" 와 "예약 비트가 0 이다" 는 다른 성질이다 —
음수는 들어가면서도 상위 비트가 서 있다. 검증기가 전자를, 인코더가 후자를 맡는다.

### 2.2 오류 코드

`OSMGA_HW3D_E_TRIFIELD 23` 하나를 **append** 한다. 코드를 필드마다 만들면
스물 몇 개가 늘어난다.

> **정정 (§7.5)**: 초안은 *"`badTri` 와 로그로 좁힌다"* 고 썼다. **로그는
> 그러지 않는다** — 내가 W12 에서 쓴 로거는 정렬 코드 셋만 특별 처리하고
> 나머지는 판정 번호만 찍는다(`:943`). 좁히려면 **그 로거를 고쳐야 한다.**

### 2.3 ★ 표현 규약을 먼저 못박는다

`dr[]`·`a0`·`adx`·`ady` 는 `unsigned long` 이다. 그러면 `0x00ffffff` 이
**두 가지**를 뜻할 수 있다:

- 24 비트 필드에 담긴 `-1` 의 **원시 인코딩**
- 부호 없는 정수 **16,777,215** (24 비트 부호 있는 필드에 **안 들어간다**)

**둘 중 무엇인지 정해지기 전에는 "필드에 들어간다" 가 정의되지 않는다.**

생산자가 답을 준다 — `osmgaFixed`(`mesa/OpenStepMGAMesaTriangle.c`):

```c
return (unsigned long)(long)((s >= 0.0) ? (s + 0.5) : (s - 0.5));
```

**부호확장된 32 비트다.** 그러므로 규약은:

> **`unsigned long` 담개는 부호확장된 C `long` 값을 나른다.** 검증기는
> `(long)` 으로 해석해 부호 있는 필드에 들어가는지 본다. 따라서
> `0x00ffffff` 은 `+16,777,215` 이고 **거부된다** — 그것이 이 규약에서 옳다.

### 2.4 ★ 판정과 인코딩을 한 곳에서

검사와 마스킹에 상수를 두 벌 두면 갈라진다. **`hw3d/` 에 검사·인코딩을 함께
하는 헬퍼 하나**를 두고 검증기와 인코더가 **같은 것을 부른다.**

```c
/* 표현 가능하면 1 을 돌려주고 *out 에 정규 워드를 넣는다. */
int osmgaHW3DField(long v, unsigned bits, unsigned long *out);
```

**그리고 이것이 V3 을 진짜 호스트 시험으로 만든다** — 인코더는 드라이버 안의
정적 Objective-C 라 호스트가 링크할 수 없지만, 이 헬퍼는 이식 가능하다.

## 3. 그림이 바뀌면 — **내 잘못일 가능성이 먼저다**

초안은 *"달라진다면 하드웨어가 예약 비트를 읽고 있었다는 뜻"* 이라고 썼다.
**너무 유리한 읽기다.** 달라지는 이유는 이쪽이 더 많다:

- 잘못된 값 인덱스를 마스킹했다
- 부호 표현 판정을 틀리게 구현했다
- 마스킹된 값이 **dirty 추적기**(`:10194`)와 다르게 상호작용한다 — 값이
  바뀌면 "변했다" 판정이 달라져 블록이 더/덜 나간다
- 회귀 비교가 애초에 불안정하다

> **차이는 "큰 발견" 이 아니라 "멈추고 조사할 것" 이다.**

그리고 **"하드웨어가 읽는 값이 같다" 도 문자 그대로는 거짓이다.** 제출되는
32 비트 워드는 **바뀐다**. 같은 것은 **문서화된 값 필드**뿐이고, 사양서는
예약 비트에 1 을 쓰면 아무 일도 없다고 **약속하지 않는다** — 0 을 쓰라고만
한다. 그러므로 **위험은 "0" 이 아니라 "문서화된 의미 기준으로 낮음" 이다.**

## 4. 검증

| # | 시험 | 하드웨어 |
| --- | --- | --- |
| V1 | 각 필드의 최대·최소 경계 양쪽 (호스트) | **불필요** |
| V2 | 경계 밖 값이 `E_TRIFIELD` 로 거부된다 | **불필요** |
| V3 | 음수가 마스킹 뒤 예약 비트 0 이다 | **불필요** |
| V4 | 회귀 15/15 가 **같은 그림**을 낸다 | 안전 |

**하드웨어 위험이 없다.** 새로 쓰는 레지스터가 없고, 쓰는 값의 하드웨어
의미가 같다.

## 5. 하지 않는 것

- **`DR0`·`DR2`·`DR3`(Z) 은 건드리지 않는다** — `<31:0>` 이라 예약 비트가 없다
- **`SGN` 은 이번이 아니다** — 비트 플래그라 성격이 다르고, 검증기가 이미
  `E_TRISGN` 으로 모르는 방향을 거부한다
- **`ALPHACTRL` 은 이미 마스킹된다**(`OSMGA_HW3D_AC_CLIENT`)
- **교차 필드 제약**(`SRC_ALPHA_SATURATE` 와 목적지 `ZERO` 조합 금지 등)은
  별건이다. W11 §8 검토가 지적했고, 여기서 섞지 않는다

---

## 6. codex 에 물을 것

- 필드 폭 표가 맞는가 — 특히 `AR3` 은 `<23:0>` + `<26:24>` 로 다른 모양이다
  (지금 인코더가 `AR3` 을 쓰지 않는데, 맞는가?)
- 마스킹이 옳다는 판단 — 하드웨어가 22 비트 2 의 보수를 기대한다는 근거가
  사양서에 있는가, 아니면 내 추론인가
- `AR0`·`AR6` 의 상한을 무엇으로 잡아야 하는가 (지금은 `> 0` 뿐)
- `DR`·`ALPHA` 의 값이 실제로 무엇인지 — Mesa 가 보내는 범위를 알면 경계를
  더 좁힐 수 있는가
- V4 에서 "같은 그림" 을 어떻게 판정하는가 (기존 비교 도구가 있는가)

## 7. codex 교차검토 판정 — 다시 전부 채택

| # | 지적 | 검증 | 판정 |
| --- | --- | --- | --- |
| 1 | 마스킹은 옳다 (좁게) | 사양서가 *"two's complement"* 명시 | ✅ **확인** |
| 2 | 필드 표는 맞다. 단 `DR5·DR9·DR13` 은 안 나간다 | `osmgaDmaReg` | ✅ |
| 3 | `AR0`·`AR6` 에 22 비트 상한이 필요하다 | `:595` 에 상한 없음 | ✅ |
| 4 | **표현 규약이 미정의** — 담개가 `unsigned long` | `osmgaFixed` | ✅ **핵심** |
| 5 | 무위험·같은그림 주장이 틀렸다 | dirty 추적기 등 | ✅ |
| 6 | **Mesa 판정 목록에 넣어야 한다** | `osmgaMesaVerdictNamesTriangle` | ✅ **누락 발견** |
| 7 | 로그가 좁혀 준다는 주장이 거짓 | 내 W12 로거 `:943` | ✅ **내 거짓말** |

### 7.1 ★ 4 번 — 규약이 없으면 시험도 정의되지 않는다

`0x00ffffff` 이 `-1` 의 원시 인코딩인지 `+16,777,215` 인지 정해야 **"필드에
들어간다" 가 뜻을 갖는다.** 생산자가 `(unsigned long)(long)` 으로 부호확장
하므로 규약은 **부호확장**이다(§2.3). **이것을 안 적었으면 V1·V2 가 무엇을
시험하는지 나도 몰랐을 것이다.**

### 7.2 ★ 6 번 — 이 수정은 Mesa 를 함께 고쳐야 한다

`osmgaMesaVerdictNamesTriangle()` 은 **삼각형을 지목하는 판정**의 목록이다.
새 코드를 넣지 않으면 Mesa 가 배치 수준으로 보고 **나머지 전체를 재생**하며,
그것이 **가속 취소 카운트에 들어간다.**

**드라이버만 고치면 한 삼각형의 거부가 가속 전체를 끄는 쪽으로 샌다.**

### 7.3 ★ 그리고 이 결함은 이 저장소가 이미 알고 있었다

`OpenStepMGAMesaTriangle.c` 의 클램프 주석:

> *"at the fifteen-bit scale that **no longer fits the field the engine
> reads**: 255 * 119 becomes 0x3B448000, of which **the hardware would see
> 0x448000, or +137, and paint a gradient nobody asked for**."*

**하드웨어가 필드로 잘라 읽는다는 것이 관측돼 있고, Mesa 가 유저랜드에서
클램프로 막고 있다.** 커널은 안 본다.

- 그래서 **거부가 옳다**: 안 들어가는 값을 마스킹하면 하드웨어가 이미 만들던
  그 틀린 값을 그대로 만든다. 거부는 **조용한 오작동을 거부로 바꾼다.**
- 그리고 **커널이 신뢰 경계다**. Mesa 가 스스로를 지키는 것과 커널이 검사하는
  것은 다른 이야기이고, 다른 클라이언트나 Mesa 의 버그는 지금 무방비다.

### 7.4 경계 (python)

```
AR0 AR6           1 .. 2,097,151          (22비트, 양수. 상한이 없었다)
AR1 AR2 AR4 AR5   현행 +-16,384 유지       (필드보다 훨씬 좁다)
DR x9  ALPHA x3   -8,388,608 .. 8,388,607  = 9.15 로 [-256.0, +256.0)
DR0 DR2 DR3       손대지 않는다             (<31:0>, 예약 없음)
```

`maxEdgeWalk` 에서 `AR0`/`AR6` 의 더 좁은 경계를 끌어내지 **않는다** —
검증기가 삼각형 높이와 묶는 것을 이미 한 번 철회했고(`:601`), 그 이유가
분할된 삼각형의 긴 변이다.

### 7.5 내 거짓말 하나

§2.2 가 *"`badTri` 와 로그로 좁힌다"* 고 썼다. **로거는 그러지 않는다** —
W12 에서 내가 쓴 것이고, 정렬 코드 셋만 특별 처리한다. **좁히려면 로거도
고쳐야 하고, 그것을 계획에 넣는다.**

---

## 8. 착수 조건

1. **표현 규약을 헤더에 적는다** — 담개는 부호확장된 `long`
2. **`osmgaHW3DField()` 하나**를 `hw3d/` 에 두고 검증기·인코더가 함께 쓴다
3. `AR0`·`AR6` 에 22 비트 상한
4. **아홉 개** DR 만 (`dr[9..11]` 은 패딩)
5. **`E_TRIFIELD` 를 Mesa 판정 목록에 넣는다**
6. 로거가 `badTri` 와 필드를 찍게 한다
7. 호스트 시험이 **정규 워드 자체**를 확인한다 (판정만이 아니라)
8. V4 의 판정 기준을 **객관적으로** 정한다 (기존 비교 도구 사용)
