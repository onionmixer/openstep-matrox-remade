# D3-2 — 기울어진 사다리꼴 (사각형 → 삼각형)

기준일: 2026-08-19
상태: **실기 PASS(2026-08-19).** 결과는 §6.
codex 교차검토 1회 완료 후 개정판이며, 초판의 봉쇄 서술은 §3-1에서 정정했다.

D3-0/D3-1로 색 보간이 완전히 확인됐지만, 지금까지 그린 것은 **전부 축에 정렬된
사각형**이다. Mesa의 `TriangleFunc`를 채우려면 기울어진 변이 필요하다.

## 1. 확인된 사실 — XAA에 레시피가 있다

`mgaSubsequentSolidFillTrap`(`mga_storm.c:1567-1590`)이 정확히 이 일을 한다:

```c
sdxl = (dxL < 0);   ar2 = sdxl ? dxL : -dxL;    /* = -|dxL| */
sdxr = (dxR < 0);   ar5 = sdxr ? dxR : -dxR;    /* = -|dxR| */

DWGCTL = FilledRectCMD & ~(MGADWG_ARZERO | MGADWG_SGNZERO);
AR0 = dyL;          AR1 = ar2 - eL;     AR2 = ar2;
AR4 = ar5 - eR;     AR5 = ar5;          AR6 = dyR;
SGN = (sdxl << 1) | (sdxr << 5);
FXBNDRY      = ((right + 1) << 16) | (left & 0xffff);
YDSTLEN+EXEC = (y << 16) | h;
DWGCTL = FilledRectCMD;                  /* 원복 */
```

### 1-0. 전사가 맞다는 독립 근거

같은 파일에 **두 번째 구현**이 있다 — `mgaSubsequentPatternFillTrap`
(`mga_storm.c:1695-1719`). 패턴 채우기용이고 호출 경로가 다른데,
`AR0`~`AR6`·`SGN`·`FXBNDRY`·`YDSTLEN+EXEC` 배치가 **한 글자도 다르지 않다**
(`SGN` 계산 방식만 `(sdxl<<1)|(sdxr<<5)` 대 `sdxl|sdxr`로 표기가 다를 뿐 값은
같다). 서로 독립된 두 곳이 같은 레시피를 쓰므로 옮겨 적은 것이 맞다.

### 1-0-1. `AR3` — 조사해서 닫았다. **쓰지 않는다.**

처음에 나는 이렇게 적었다: X.Org DDX 색상 확장 경로에
`OUTREG(MGAREG_AR3, 0); /* crashes occasionally without this */`가 있으니
**"비용이 없으니 우리도 0으로 두자"**. operator가 그것을 반려했다 —
*"증상이 가끔 죽는다로 되어있으면 곤란합니다. 이후 확인해야할 내용이 되어야
합니다. 비용이 없어도 불안한 점을 남겨둘 수는 없습니다."*

조사한 결과 **결론이 뒤집혔다. `AR3`를 쓰지 않는 것이 맞다.**

| 사실 | 근거 |
| --- | --- |
| 원본 OPENSTEP `MatroxMGA`는 **드로잉 엔진을 아예 쓰지 않는다** | `AR3`(0x1c6c)·`FXBNDRY`(0x1c84) 참조 **0건**. 검색 방법은 대조군으로 검증했다 — CRTC `0x1fd4` 4건, DAC `0x3c00` 6건이 정상 검출됨 |
| DDX의 **복사 경로**가 `AR3`에 소스 주소를 넣는다 | `mgaSubsequentScreenToScreenCopy`(`mga_storm.c:1390`, `:1398`), `_FastBlit`(`:1466`, `:1479`, `:1491`) |
| DDX의 **사다리꼴 경로는 `AR3`를 건드리지 않는다** | `mgaSubsequentSolidFillTrap`(`:1566`~`:1590`) 참조 **0건** |
| 둘은 **같은 가속 테이블**에 등록돼 X가 수시로 번갈아 호출한다 | `infoPtr->SubsequentScreenToScreenCopy`(`:647`), `SubsequentSolidFillTrap`(`:656`) |
| 사이에 지우는 곳도 없다 | `mgaSetupForSolidFill` 계열에 `AR3` **0건** |
| `AR3`를 0으로 미는 곳은 **BITBLT/ILOAD 계열뿐**이다 | 색상 확장 계열(`:1768`, `:1813`, `:1836`, `:1901`, `:2098`, `:2166`~`:2193`)과 `MGAStormEngineInit`의 1×1 더미 BITBLT(`:1178`) |

**즉 출하된 드라이버는 복사가 남긴 `AR3`를 그대로 둔 채 사다리꼴을 그린다.**
우리 노출 지점("S2/S3의 BITBLT가 남긴 `AR3` → `TRAP`")은 **DDX가 프로덕션에서
늘 하는 일**이다. `AR3`는 BITBLT/ILOAD 계열의 소스 주소지정 레지스터이고
사다리꼴과 무관하다.

→ **D3-2는 `AR3`를 쓰지 않는다.** 근거 없는 쓰기를 하나 더 넣는 것이고,
출하 동작에서 벗어나는 쪽이다.

**남는 범위(작아졌다)**: 우리가 나중에 색상 확장/ILOAD를 구현하면 그때는
`AR3` 정리가 실제로 필요하다. 그것만 `REMAINING_WORK.md`에 남긴다.

### 1-1. 결정적인 한 줄

**`ARZERO`와 `SGNZERO`를 지워야 한다.** 우리가 지금까지 쓴 DWGCTL은 S1에서
물려받아 둘 다 켜져 있었고, 그래서 `AR`/`SGN`이 무시되고 축 정렬 사각형만
나왔다. 이 두 비트를 지우는 것이 사각형과 사다리꼴을 가르는 지점이다.

### 1-2. 변(edge) 파라미터

XAA 규약대로 각 변은 Bresenham 3요소다: `dx`, `dy`, 오차 `e`.
`AR2`/`AR5`가 `-|dx|`이고 `AR1`/`AR4`가 `-|dx| - e`이며, `SGN`의 bit1/bit5가
좌/우 변의 x 방향 부호다.

### 1-3. 레지스터는 전부 DMA 주소지정 가능

`AR0`~`AR6`는 `0x1c60`~`0x1c78`, `SGN`은 `0x1c58` — 전부 그룹0.
(이번 단계는 MMIO로 하되, 나중에 링으로 옮길 때 걸릴 것이 없음을 확인해 둔다.)

## 2. 가장 큰 미지수

- **보간과 기울어진 변이 같이 되는가.** XAA의 레시피는 `SOLID` 채우기용이다.
  `MGADWG_I`(보간)와 조합했을 때도 성립하는지는 소스에 없다.
- 오차항 `e`의 정확한 의미. XAA 호출자가 계산해서 넘기므로 이 파일만으로는
  정의를 알 수 없다. **`e = 0`으로 시작한다.**

## 3. D3-2 — 한 부팅에 세 실험

64행 블록을 나눠 쓴다. 실패했을 때 원인이 갈리도록 **대조군을 먼저** 둔다.

| 행 | 내용 | 확인하는 것 |
| --- | --- | --- |
| 0~19 | 기울기 모드인데 **양변 모두 수직** | `ARZERO`/`SGNZERO`를 지우는 것 자체가 그리기를 깨지 않는가 |
| 20~39 | **평평한 색** 직각삼각형 | 기울기 셋업이 되는가 |
| 40~59 | **Gouraud** 직각삼각형 | 보간과 기울기가 공존하는가 |
| 60~63 | 그리지 않음 | 세로 경계 |

**대조군(0~19행)이 이번 설계의 핵심**이다. 이것이 사각형으로 나오면
"비트를 지운 것"과 "기울기 셋업"이 분리된다 — 삼각형이 안 나왔을 때 어느
쪽 문제인지 바로 알 수 있다. codex 제안이다.

### 3-0. X를 안쪽으로 넣고 가드 열을 둔다

지금까지 프로브는 `OSMGA_S1_X = 0`, 즉 블록 왼쪽 끝에서 시작했다. 기울어진
변은 **음의 방향으로 벗어날 수 있으므로** 그것을 관측할 여지가 없었다.

이번에는 x를 **8만큼 안쪽**에 두고 그린다(x 8~55). 열 0~7과 56~63은 sentinel로
남겨 두고 끝에 확인한다. 그래야 잘못된 변 이동이 실제로 잡히고, `CXBNDRY`가
기울어진 스팬에도 듣는지가 검증된다. 이것도 codex 제안이다.

### 3-1. 봉쇄 — 초판이 틀렸다

초판은 `FXBNDRY`/`YDSTLEN` 사각형이 쓰기 범위를 가둔다는 전제로 적혀 있었다.
**`ARZERO`를 지우면 그렇지 않다.** 그 둘은 변의 **출발점과 행 수**일 뿐이고,
변이 잘못 설정되면 스팬이 그 밖으로 걸어나간다.

실제 하드 경계는 **`CXBNDRY`(x)와 `YTOP`/`YBOT`(y)** 이며, 우리
`osmgaStormInitState`가 매 그리기 전에 좁혀 잡는다. XAA도 solid fill에
하드웨어 클리핑을 광고하며 같은 레지스터를 쓴다(`mga_storm.c:663`, `:1197`).
근거는 충분하나 **기울어진 스팬에 대한 클리핑은 아직 실측된 적이 없고**,
§3-0의 가드 열·행이 그것을 본다.

### 3-2. 그리기 뒤 DWGCTL 원복

XAA는 기울어진 그리기 **직후 `DWGCTL`을 원래 값으로 되돌린다**
(`mga_storm.c:1588`). 우리도 각 프로브 뒤에 되돌린다 — `ARZERO`/`SGNZERO`가
지워진 상태가 다음 그리기로 새어 나가지 않게.

### 3-3. 변 파라미터

세 실험 모두 20행, x 8~55(48 넓이):

| | 왼쪽 변 | 오른쪽 변 | 초기 FXBNDRY |
| --- | --- | --- | --- |
| 대조군 | `dx=0, dy=20` | `dx=0, dy=20` | `(56<<16)\|8` |
| 삼각형 | `dx=0, dy=20` | `dx=47, dy=20` | `(9<<16)\|8` |

`eL = eR = 0`. **이 값이 옳다는 증거는 없다** — XAA 호출자가 계산해 넘기는
Bresenham 초기 오차항이고 그 계산은 이 트리에 없다. 수직 변에서는 문제가
없을 것으로 보지만, 기울어진 변에서는 계단이 한 행/픽셀 어긋날 수 있다.
그것은 이번 단계의 판정을 바꾸지 않는다(삼각형인지 사각형인지를 볼 뿐이다).

**검증 방법**
- V2-1: 밴드별로 **행마다 채워진 첫 x·마지막 x·개수**를 기록한다. 대조군은
  전 행이 8~55로 같아야 하고, 삼각형 밴드는 폭이 단조 증가해야 한다.
- V2-2: **가드 열 0~7, 56~63과 가드 행 60~63이 sentinel 그대로**인지.
  기울어진 스팬에 클리핑이 듣는다는 증거.
- V2-3: 아래 밴드에서 색이 여전히 보간되는지.
- V2-4: 2D 회귀(S1/S2/S3)와 D1/D2 통과, 화면 무변화.
- V2-5: `AR3`를 **쓰지 않은 채**(S2/S3가 남긴 값 그대로) 위 전부가 통과하는지.
  §1-0-1이 예측하는 결과이며, 어긋나면 그 조사가 틀린 것이므로 즉시 멈춘다.

### 3-4. 예측값 — 실행 **전에** 독립 모델로 계산해 둔다

처음에는 코드에 넣을 값을 손으로 검산했는데, 그것은 **내가 쓴 공식을 다시
계산한 것**이라 산술만 확인할 뿐 옳은지는 증명하지 못한다. operator 지적으로
Python에 변 걷기 모델을 따로 세워 예측을 뽑았다.

모델이 곧바로 문제를 드러냈다: **Bresenham 누산 규약을 모르는데, 규약에 따라
결과가 완전히 달라진다.**

- **규약 A** — 행마다 `acc += dy`, `acc >= 0`인 동안 `x++` 및 `acc -= |dx|`
- **규약 B** — 행마다 `acc += |dx|`, `acc >= 0`인 동안 `x++` 및 `acc -= dy`

`dxR=47, dyR=20`에 대한 예측:

| 행 | 대조군(양변 수직) | 삼각형 규약A | 삼각형 규약B |
| --- | --- | --- | --- |
| 0 | 8..55 (48) | 8..8 (1) | 8..10 (3) |
| 5 | 8..55 (48) | 8..10 (3) | 8..22 (15) |
| 10 | 8..55 (48) | 8..12 (5) | 8..33 (26) |
| 15 | 8..55 (48) | 8..14 (7) | 8..45 (38) |
| 19 | 8..55 (48) | 8..16 (9) | 8..55 (48) |

**나는 규약 B를 기대하고 있었고, 규약 A 결과(폭 9)가 나왔다면 "기울기가
동작하지 않는다"로 오독했을 것이다.** 예측을 미리 적어두지 않았다면 그렇게
됐다.

두 규약이 크게 갈리는 것은 오히려 좋은 성질이다 — **측정된 폭이 규약을
알려준다.** 그래서 기하를 바꾸지 않고 그대로 둔다(45°짜리로 바꾸면 A는 22,
B는 20으로 거의 구분이 안 된다).

읽는 법:
- 행19 폭이 **48**이면 규약 B, **9**면 규약 A
- 둘 다 아니고 전 행이 48이면 `ARZERO`/`SGNZERO`가 안 먹은 것(기울기 없음)
- 대조군이 48이 아니면 그 앞에서 이미 깨진 것이므로 삼각형 밴드는 읽지 않는다

`e = 0`은 여전히 추측이며, 오차항이 다르면 계단이 한두 픽셀 어긋난다. 그것은
규약 판정을 바꾸지 않는다(9 대 48의 차이는 ±2로 흔들리지 않는다).

## 4. 중단 조건

- 폭이 단조 증가하지 않음 → 변 셋업이 틀렸다. `e`의 의미부터 다시 본다.
- 블록 밖 오염 → 즉시 중단.
- 위쪽 절반은 삼각형인데 아래쪽이 아니면 → 보간과 기울기가 공존하지 않는
  것이며, 그 자체가 중요한 결과다.

## 5. 이 계획이 결정하지 않은 것

- 삼각형 하나를 사다리꼴 몇 개로 나눌지(일반 삼각형은 보통 둘).
- 색 보간의 시작값·증분을 삼각형 꼭짓점에서 어떻게 유도할지 — 이번에는
  사각형 때와 같은 값을 그대로 쓴다.

## 6. 실행 결과 (2026-08-19) — PASS

```
band0 (대조군, 양변 수직)  8..55(48) 8..55(48) 8..55(48) 8..55(48) 8..55(48)
band1 (평평한 색 삼각형)   8..8(1) 8..20(13) 8..32(25) 8..44(37) 8..53(46)
band2 (Gouraud 삼각형)     8..8(1) 8..20(13) 8..32(25) 8..44(37) 8..53(46)
guard columns/rows disturbed in 0 px
```

네 가지가 한 번에 확인됐다:

| 확인된 것 | 근거 |
| --- | --- |
| `ARZERO`/`SGNZERO`를 지우는 것이 그리기를 깨지 않는다 | 대조군이 전 행 폭 48 |
| **기울어진 변이 동작한다** | 폭이 1 → 13 → 25 → 37 → 46으로 단조 증가 |
| **보간과 기울기가 공존한다** | band2가 band1과 동일 기하 |
| **클립이 기울어진 스팬에도 유효하다** | 가드 열·행 0 px. 지금까지 한 번도 측정된 적 없던 것 |

### 6-1. 규약이 가려졌다 — 예측을 미리 적어둔 값어치

| 행 | 측정 | 규약A 예측 | 규약B 예측 |
| --- | --- | --- | --- |
| 0 | 8..**8** | 8..8 | 8..10 |
| 5 | 8..**20** | 8..10 | 8..22 |
| 10 | 8..**32** | 8..12 | 8..33 |
| 15 | 8..**44** | 8..14 | 8..45 |
| 19 | 8..**53** | 8..16 | 8..55 |

**규약 B다** — x가 행마다 `|dx|/dy`(= 47/20 ≈ 2.35)씩 전진한다. 규약 A였다면
폭 9짜리 조각이 나왔을 것이고, §3-4에 예측을 적어두지 않았다면 **올바른
결과를 "기울기 실패"로 오독했을 것이다.**

### 6-2. `e` — 정정. 오차는 훨씬 작다 (미해결, 매우 작음)

처음에 "측정이 예측보다 일관되게 1~2 px 짧다"고 적었는데 **과장이었다.**
그 비교에 쓴 모델이 임의 매개변수(`acc0 = -dy - e`)였기 때문이다.

하드웨어에 실제로 들어가는 레지스터 값으로 모델을 다시 세우면:

```
acc0 = AR4 = -|dx| - e
행마다:  acc += |dx|            (= |AR5|)
         acc >= 0 인 동안:  x++,  acc -= dy    (= AR6)
```

이 모델의 예측과 측정:

| e | 예측(행 0/5/10/15/19) | 측정과 일치? |
| --- | --- | --- |
| 0 | 9, 20, 32, 44, 53 | 행0만 1 어긋남 |
| 1~5 | **8, 20, 32, 44, 53** | **전부 일치** |

즉 `e = 0`은 **첫 행에서만 1 px 어긋나고** 나머지는 정확하다. 훨씬 작은
오차이며, 앞 서술은 잘못된 모델이 만든 착시였다.

### 6-3. 20행 전부로 확정 — 유일해가 나왔다

계단 전체를 기록했다:

```
band1 last-x per row: 8 11 13 16 18 20 23 25 27 30 32 34 37 39 41 44 46 48 51 53
```

이 20점에 대해 모델이 **유일하게 `e = 1`에서만** 정확히 일치한다
(5점일 때는 1~5가 모두 맞았다). 표본을 늘린 것이 값어치를 했다.

**해석에 주의가 필요하다.** 우리는 `AR1`/`AR4`에 `-|dx| - 0 = -47`을 썼는데,
하드웨어는 모델의 `acc0 = -48`처럼 행동했다. 즉:

> **하드웨어의 실효 초기 누산값 = 우리가 쓴 `AR4` − 1**

같은 값을 `acc >= 0` 대신 `acc > 0`으로 비교하는 것으로도 설명된다. 둘을
구분하지 않았고 구분할 필요도 없다 — **예측에 필요한 규칙은 확정됐다.**

### 6-4. 확정된 변 걷기 규칙 (20/20 행 일치)

```
쓸 값:   AR0 = dyL,  AR1 = -|dxL| - eL,  AR2 = -|dxL|
         AR4 = -|dxR| - eR,  AR5 = -|dxR|,  AR6 = dyR
         SGN = (dxL<0 ? 2 : 0) | (dxR<0 ? 0x20 : 0)
         FXBNDRY = ((right+1) << 16) | (left & 0xffff)
         YDSTLEN + EXEC = (y << 16) | h
         DWGCTL 은 ARZERO/SGNZERO 를 지운 값, 그린 뒤 원복

동작:    acc = AR4 - 1
         행마다:  acc += |dx|
                  acc >= 0 인 동안:  x += sign,  acc -= dy
```

`e = 0`으로 쓰면 시작 행이 1 px 좁게 나온다. 정확한 삼각형이 필요하면
`AR4`에 1을 더해 보정하면 된다.
