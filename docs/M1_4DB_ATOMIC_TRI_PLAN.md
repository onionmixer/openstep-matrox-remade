# M1-4DB — 삼각형 하나를 원자적으로

## 1. 막고 있는 것

텍스처 + 블렌딩이 `OpenStepMGAMesaHook.c:833` 에서 거절된다.  이유는 블렌딩
자체가 아니라 **배치 쪼개기**다.

```c
    int nb = texOn ? n : 1;          /* Hook.c:403 */
```

텍스처가 켜지면 사다리꼴 하나가 배치 하나다.  두 번째가 검증기에 거절되면 첫
번째는 **이미 그려진 뒤**이고, 소프트웨어가 삼각형 전체를 다시 그린다.  같은
픽셀을 두 번 쓰는 셈인데, 지금은 블렌딩이 꺼져 있어 같은 값이 다시 들어가므로
무해하다.  블렌딩을 켜면 그 픽셀은 **두 번 섞인다.**

(기존 주석은 `GL_LESS` 깊이 검사도 근거로 들었다.  그건 근거가 못 된다 — 깊이
검사는 꺼져 있을 수 있고, 같은 z 를 다시 쓰면 `GL_LESS` 는 통과하지 못하지만
깊이가 없으면 아무것도 막지 않는다.  이 문장은 지운다.)

## 2. 왜 쪼개져 있었나

`tmr[6]`, `tmr[7]`, `tmr[8]` 은 **사다리꼴의 첫 행 왼쪽 끝에서의 값**이다.
빌더가 원점 `(ox, oy)` 를 넣어 만든다:

```c
    tmr[6] = round(uplane->at_a + uplane->dx*ox + uplane->dy*oy);   /* Triangle.c:574 */
    tmr[7] = round(vplane->at_a + vplane->dx*ox + vplane->dy*oy);
    tmr[8] = round(qplane->at_a + qplane->dx*ox + qplane->dy*oy);
```

`tmr[0..5]` 는 평면의 기울기라 **삼각형 전체에서 같다**.  원점에 의존하는 것은
**시작값 셋뿐이다.**  그런데 시작값이 배치 상태에 들어 있으니 사다리꼴마다
배치가 하나여야 했다.

## 3. 고치는 방법 — 시작값을 삼각형 항목으로 내린다

`OSMGAHW3DState` 에서 `tmr[6]`, `tmr[7]`, `tmr[8]` 을 빼고 `OSMGAHW3DTri` 에
넣는다:

```c
    long tu0, tv0, tq0;      /* 이 사다리꼴 첫 행 왼쪽 끝에서의 u, v, q */
```

기울기 `tmr[0..5]` 는 상태에 남는다.  인코더는 TMR6/7/8 을 상태 블록이 아니라
**삼각형 루프 안에서** 낸다.

이건 codex 가 좁힌 "행렬 두 벌"보다 작다.  달라지는 건 세 long 이지 아홉이
아니고, 둘로 못 박히지도 않는다.

## 4. 크기

실측(실기에서 `sizeof`):

```
    OSMGAHW3DBatch  24092 bytes (limit 28672)      여유 4580
    OSMGAHW3DTri      120  x MAX_TRI 200
```

`+12 × 200 = 2400` → 26492, **2180 남는다.**  정적 단언
(`OpenStepMGAHW3D.h:616`)이 계속 지킨다.

## 5. bias 는 나빠지지 않는다

bias 는 배치 단위다 — `osmgaHW3DTexBiasFor(reach->uMax)`.  배치가 커지면
느슨해질까 걱정했는데, **훅은 GL 삼각형마다 제출한다** (`Submit` 이 `bi` 루프
안에 있고 배치를 걸쳐 누적하지 않는다).  묶은 뒤에도 배치 하나 = GL 삼각형
하나이므로 **배치별 bias 가 곧 삼각형별 bias** 다.  지금(사다리꼴별)보다는
느슨하지만, 두 사다리꼴은 같은 평면의 인접 구간이라 도달 범위가 거의 같다.

느슨해지는 방향은 **안전한 쪽**이다: 도달 범위가 커지면 bias 가 작아지고,
잔차는 `A − B ≥ 0` 을 유지한다 — 경계 정렬 좌표가 아래 텍셀로 떨어지는 일은
여전히 없다.  다만 잔차의 **크기**는 커질 수 있어서, 그게 기준 장면을
움직이는지 확인해야 한다.

## 6. 검증기

`tmr[6]/[7]/[8]` 을 읽는 곳은 넷뿐이고 전부 삼각형 루프 안이다:

| 위치 | 하는 일 |
|---|---|
| `HW3D.c:83` | `q(dx,dy) = tmr[8] + tmr[4]·dx + tmr[5]·dy` |
| `HW3D.c:295-298` | 시작값 범위 검사 (루프 **앞**으로 옮겨둔 것 — 다시 안으로) |
| `HW3D.c:597-598` | `tmr[8]` 의 q 범위 |
| `HW3D.c:639-642, 692-697` | 행 순회 |

전부 `t->tu0` 등으로 바꾼다.  **295-298 은 루프 앞에서 안으로 돌아가야 한다** —
이전 커밋에서 오버플로 때문에 일부러 앞으로 뺐던 것이라, 삼각형마다 그
검사가 기울기 검사보다 먼저 오도록 순서를 지켜야 한다.

## 7. 버전

`OSMGA_HW3D_VERSION` 4 → 5.  Mesa 가 불일치를 거절한다
(`OpenStepMGAMesaProbe.c:145`).  커널과 Mesa 를 **함께** 설치해야 하고, 커널
변경이므로 **재부팅이 필요하다.**

## 8. 원자성을 직접 시험한다

"두 번째가 거절되면 첫 번째도 안 그려진다"를 논증이 아니라 **측정**으로
확인한다:

- 사다리꼴 둘짜리 삼각형을 만들고, 두 번째의 `dwgctl` 을 검증기가 반드시
  거절하는 값으로 **일부러** 망가뜨린다
- 제출 → 거절 확인 (`res.triangle == 1`)
- **VRAM 을 읽어 첫 번째 사다리꼴 영역이 배경 그대로인지 확인**

이게 통과해야 `Hook.c:833` 의 관문을 연다.  통과하기 전에는 열지 않는다.

## 11. 계획을 흔든 것 — v 의 행은 배치 안에서 누적된다

codex 회신을 기다리는 동안 검증기에서 `texSpanY` 를 발견했고, 이게 4단계를
직접 흔든다.  `M1_4C3_TEXCOORD_PLAN.md:11` 에 실측으로 적혀 있다:

| 축 | 행 인덱스 | 어떻게 쟀나 |
|---|---|---|
| `u` | **프리미티브마다 다시 심긴다** | 행 기울기를 줘도 두 프리미티브가 같은 텍셀에서 시작 |
| `v` | **배치 안에서 누적된다** | 높이 5, 11, flat 7, 3 에서 v = 3, 8, 19 |
| `q` | v 와 같다 | 두 프리미티브 사이에 틈을 두니 먼 쪽이 자기 화면 위치가 아니라 앞의 행 수가 남긴 값을 읽었다 (`HW3D.c:643-648`) |

검증기는 이걸 이미 정확히 모형화하고 있다 — `tmr[1] * dy` (u) 대
`tmr[3] * (texSpanY + dy)` (v), `texSpanY += t->h` (`HW3D.c:785`).  비대칭은
버그가 아니라 **잰 것**이다.

그리고 그 문서가 지금 상황을 미리 적어 뒀다:

> Mesa 는 삼각형 하나를 배치 하나로 보내므로 v 의 누적은 지금 문제가 아니다
> (배치마다 다시 심긴다 — 잰 값).  **묶어 보내게 되면 그때 다시 본다.**

지금이 그때다.

### 그래서 시작값만 옮기면 틀린다

사다리꼴 둘을 한 배치에 넣으면 두 번째의 행 인덱스는 0 이 아니라 `S` 에서
시작한다 (`S` = 앞선 텍스처 프리미티브들의 높이 합).  빌더가 만든
`tv0 = vplane(lx0, y0)` 을 그대로 쓰면 두 번째 사다리꼴은 `tmr[3]·S` 만큼
어긋난다.

### 보정은 클라이언트가 한다

엔진이 계산하는 값이 진짜 평면값이 되려면

```
    tv0_k = vplane(lx0_k + ½, y0_k + ½) − tmr[3] · S_k
    tq0_k = qplane(lx0_k + ½, y0_k + ½) − tmr[5] · S_k
    tu0_k = uplane(lx0_k + ½, y0_k + ½)          (u 는 보정 없음)
```

**커널이 아니라 빌더가 뺀다.**  그러면 검증기의 누적 모형은 **한 줄도 바뀌지
않는다** — `tmr[7] + tmr[2]·dx + tmr[3]·(texSpanY + dy)` 가 보정된 시작값과
만나 정확히 참 좌표를 준다.  도달 범위도 그대로 참값이다.  커널에 새 산술이
없으니 새 오버플로 표면도 없다.

대신 **보정된 시작값 자체가 범위를 벗어날 수 있다** — 참 좌표는 멀쩡한데
`tmr[3]·S` 가 크면 `tv0` 이 `COORD_MAX` 를 넘는다.  그건 시작값 검사에 걸려
거절되고, 소프트웨어로 떨어진다.  안전한 방향이지만 **멀쩡한 삼각형을 거절할
수 있다.**  사다리꼴 둘, `S` = 첫 사다리꼴 높이(≤ 화면 높이)이므로
`tmr[3]·S` 는 삼각형 자신이 이미 겪는 세로 변화량과 같은 크기다 — 즉 실질적인
손실은 거의 없어야 한다.  **측정해서 확인한다.**

### 4단계를 고친다

4. 빌더/훅: `built[]` 에 시작값을 채우되 **두 번째 사다리꼴의 v·q 시작값에서
   `기울기 × 앞 높이` 를 뺀다**.  `nb = texOn ? n : 1` 제거.

## 13. 유일한 부분 기각 — 누적 모형은 남긴다

codex 는 "TMR 을 트랩마다 쓰면 V·Q 가 다시 심기니 `texSpanY` 를 걷어내라"고 한다.
**전제가 측정된 적이 없다.**  `HW3D.c:172-175` 가 잰 것은 "제출마다 새로
심긴다"이고, 제출 경로에는 TMR 쓰기 말고도 유휴 대기·DMA 설정이 들어 있어
**원인이 갈리지 않는다.**  배치 **중간**의 TMR 쓰기가 누산기를 다시 심는지는
아무도 재지 않았다.

그래서 고르지 않고 **오차의 방향**을 본다:

| 진실 | 검증기가 `texSpanY` 를 쓴다면 |
|---|---|
| 다시 심긴다 | 실제보다 **큰** 행 인덱스를 경계로 삼는다 → 더 많이 거절 → **안전**(과엄격) |
| 계속 누적된다 | 정확 |

반대로 `texSpanY` 를 걷어냈는데 진실이 누적이면 **과소 경계 = 봉쇄 구멍**이다.
도달 범위도 마찬가지다 — 크게 잡으면 bias 가 작아지고 잔차는 `A − B ≥ 0` 을
유지한다(정확도만 손해).

**그러므로 검증기의 누적 모형은 그대로 둔다.**  두 가설 모두에서 안전한 쪽이다.
재부팅 뒤 §78 로 재고, 진실이 "다시 심긴다"이면 그때 조인다.

클라이언트 쪽 보정(§11)은 **환경변수로 가른다** — `OSMGA_TMR_RESEED`.  기본은
"다시 심긴다"(보정 없음), 끄면 §11 의 보정을 넣는다.  한 번의 재부팅으로 두
가설을 다 잰다.  검증기는 어느 쪽이든 안전하므로 이 스위치는 커널을 건드리지
않는다.

## 14. 고친 순서

1. 헤더: `tu0/tv0/tq0` 를 `OSMGAHW3DTri` 로, 버전 5, **DMA 용량 정적 단언 추가**
2. 검증기: 네 곳 + `osmgaHW3DQAt` 가 트랩을 받게 + 시작값 검사를 codex 순서로
   + `badTri` 에 트랩 번호 남기기.  **`texSpanY` 는 그대로**
3. 인코더: TMR6/7/8 을 삼각형 루프 안, 그 트랩의 `YDSTLEN + EXEC` 앞
4. 빌더: 원근 깃발을 `qplane` 에서 직접 (반올림된 시작값이 아니라) 돌려주기.
   훅: `nb = texOn ? n : 1` 제거, `OSMGA_TMR_RESEED` 로 보정 가르기
5. 시험과 **독립 오라클**을 새 계약으로 (`test-hw3d-reach.c:64` 등)
6. 호스트 시험 7종 → 빌드 → 설치 → **재부팅 요청**
7. 재부팅 뒤:
   - §78 **다시 심기는가** — 두 트랩 한 배치, v 기울기를 알고 읽는다
   - §79 **원자성** — 양성 대조 포함, 깊이 영역까지, 제출 1회·`triCount == 2`
   - §80 **문턱** — 트랩 0 은 `2^20` 이하, 트랩 1 은 그 위.  옛 단일 트랩 제출과
     트랩 0 을 비교
   - 기준 장면 열 개 → 관문 열기 → 블렌딩 장면
