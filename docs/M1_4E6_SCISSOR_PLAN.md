# M1-4E6 — `glScissor`

## 1. 지금

시저가 켜지면 `RasterMask` 허용 목록에서 걸린다.  그래서 **시험들이 시저를
"소프트웨어 강제 스위치"로 쓰고 있다** — `depth-agree`, `tdf`, `tbf`, `tat`,
`tpo` 가 전부 전화면 시저로 경로를 바꾼다.

## 2. 엔진에는 클립이 있고, 이미 쓰고 있다

`CXBNDRY`(비트 0-15 왼쪽, 16-31 오른쪽, **오른쪽 포함**), `YTOP`, `YBOT`.
그리고 배치 경로가 그리기 **직전에** 목적지 창 전체로 세운다:

```c
    osmgaStormInitState(mmioBase, dstP3, 0UL, dstW3 - 1UL, 0UL,
                        (dstH3 - 1UL) * dstP3);
```

`.m:3744`.  즉 시저는 **이미 있는 클립을 좁히는 것**이다.

## 3. 그래서 안전 논증이 짧다

커널이 **교집합**을 프로그래밍한다:

```
   실제 클립 = 클라이언트가 요청한 상자  ∩  목적지 창
```

교집합은 **넓힐 수 없다.**  클라이언트가 무엇을 보내든 오늘의 클립보다 넓어질
수 없으므로, 봉쇄는 **한 글자도 약해지지 않는다.**  검증기는 상자가 잘
형성됐는지(`x0 ≤ x1`, `y0 ≤ y1`)만 보면 되고, 값의 크기는 볼 필요가 없다.

빈 교집합은 그리기를 **건너뛴다** — `CXBNDRY` 에 `x0 > x1` 을 넣는 것은
문서에 없는 상태다.

## 4. y 는 뒤집지 않는다

훅은 `yUp` 이 아니면 물러난다(`Hook.c:1258`).  그러니 Mesa 의 창 y 가 곧
드라이버의 행 색인이고, GL 시저의 좌하단 원점 상자가 **그대로** 행 범위
`Y … Y+Height−1` 이다.  뒤집을 것이 없다.

`YTOP`/`YBOT` 은 **픽셀 오프셋**이지 행 번호가 아니다 — 위 호출이
`(dstH3−1) * dstP3` 를 넘긴다.  그러니 행에 피치를 곱해야 한다.

## 5. 무엇이 바뀌나

| 자리 | 바뀔 것 |
|---|---|
| `OSMGAHW3DState` | `scissorX0/Y0/X1/Y1` 과 켜짐 표지 |
| 버전 | 6 → 7 |
| 검증기 | 상자가 잘 형성됐는지만 |
| 제출 경로 | `osmgaStormInitState` 에 **교집합**을 넘긴다.  비면 안 그린다 |
| Mesa | 관문이 `SCISSOR_BIT` 를 받고, 상자를 싣는다 |

**커널 변경이므로 재부팅이 필요하다.**

## 6. 그런데 시험들이 시저로 소프트웨어를 강제한다

이걸 받아들이는 순간 **다섯 시험의 강제 방식이 무효가 된다** — 시저가 더 이상
관문을 막지 않으므로 "소프트웨어" 쪽도 하드웨어로 돌게 된다.

그러면 그 시험들은 **하드웨어를 하드웨어와 비교**하게 되고 전부 통과한다 —
조용히 공허해진다.  이것이 이 변경의 가장 큰 위험이고, **먼저** 고쳐야 한다.

대안: `OSMGA_MESA_ACCEL=0` 을 쓴다.  이미 장면 러너들이 그렇게 하고, 그건
프로브 자체를 끄므로 관문과 무관하다.

## 7. 어떻게 재나

1. 상자 안팎: 시저 상자를 화면 가운데 두고, 안은 그려지고 밖은 안 그려지는지
2. **경계**: `CXBNDRY` 의 오른쪽이 포함이므로 `x1` 이 정확히 마지막 열인지.
   한 열 어긋나면 GL 과 다르다
3. 소프트웨어와 화소 단위 비교 — GL 이 정한 것이므로 **차이가 0** 이어야 한다
4. 빈 상자: `glScissor(0,0,0,0)` 이면 아무것도 안 그려져야 한다
5. 창 밖으로 나간 상자: 교집합이 창이어야 한다

## 8. 교차검토에 물을 것

- §3 의 "교집합은 넓힐 수 없다"가 정말 봉쇄를 안 건드리나.  클립이 좁아지는
  것이 다른 무엇을 깨나
- `YTOP`/`YBOT` 이 픽셀 오프셋인 것이 맞나.  `dstorg` 가 더해지나
- §6 의 다섯 시험을 어떻게 고쳐야 하나.  `ACCEL=0` 이 정말 등가인가
- 빈 상자에서 그리기를 건너뛰는 것과 클립을 비우는 것 중 어느 쪽인가
- GL 시저와 하드웨어 클립의 의미가 다른 곳 (깊이·스텐실 쓰기, 클리어)

## 9. codex 교차검토 판정 (14차)

| codex 주장 | 검증 방법 | 결과 |
|---|---|---|
| **빈 시저가 계획 안에서 모순이다.** `x0 ≤ x1` 을 요구하면서 `glScissor(0,0,0,0)` 이 아무것도 안 그려야 한다고 했다 — 포함 상자에서 `w=0` 은 `x1 = x0−1` 이다 | 맞다.  반열린 `x,y,w,h` 로 담아야 한다 | ✅**사실 — 내 §3 과 §7-4 가 모순** |
| **`ACCEL=0` 은 등가가 아니다** — 프로브만 끄는 게 아니라 VRAM 표면 대체와 공유 깊이 할당까지 끈다.  `depth-agree` 는 비교 자체를 못 한다 | 프로브가 "한 번만 결정"함을 확인했고(`Probe.c:2`), 시험들은 **한 프로세스 안에서** 두 경로를 오간다 | ✅**사실 — 내가 먼저 우려했고 codex 가 더 깊게 짚었다** |
| 시저로 강제하는 시험이 다섯이 아니라 **열** 이고, `gl-test` 는 시저가 **거절되는지를 단언**한다 | `grep` 으로 확인: 열 개 파일 | ✅사실 |
| `YTOP`/`YBOT` 은 픽셀 오프셋이고 X.Org 는 `y2·width + YDstOrg` 로 적는다.  이 백엔드는 `YDSTORG=0`·`DSTORG=0` 을 쓰는데 `state.dstorg` 는 검증에만 쓴다 — **원점이 더해지는지 미확정** | 인코더가 목록에서 `DSTORG` 를 다시 쓴다.  **클립이 오늘 실제로 무는지 안 쟀다** | ✅**채택 — 첫 측정이 이것이어야 한다** |
| 봉쇄는 **교집합을 커널이 계산하고 검증은 전체 창으로 유지할 때만** 성립한다.  시저를 도달범위/bias 의 새 경계로 쓰지 마라 | 맞다 — 좁은 시저는 보수적 폴백만 만들어야지 검증을 느슨하게 하면 안 된다 | ✅채택 |
| 클리어는 이 백엔드가 Mesa 에 위임하므로 하드웨어 클립을 안 쓴다.  분리를 명시하고 시저 클리어 회귀를 더하라 | `Hook.c:1207` | ✅채택 |
| 버전 6→7 은 맞으나 **드라이버와 libGL 을 함께** 설치해야 한다 | 확립된 절차 | ✅사실 |

## 10. 순서를 바꾼다

시저를 받는 순간 열 개 시험의 강제 방식이 **조용히 공허해진다.**  그러니
**먼저** 그것을 고친다 — Mesa 만 바뀌고 재부팅이 필요 없다.

`ACCEL=0` 은 못 쓴다(§9).  그러니 **경로만** 바꾸는 시험용 스위치를 둔다:
프로브도, VRAM 대체도, 공유 깊이도 그대로 두고 chooser 만 물러나게 한다.

그러고 나서 커널을 바꾸고, **첫 측정은 "좁은 클립이 실제로 무는가"** 다 —
`YTOP`/`YBOT` 에 원점이 더해지는지가 거기서 갈린다.
