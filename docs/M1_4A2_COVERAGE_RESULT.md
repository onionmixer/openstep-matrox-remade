# M1-4a2 / §3-27 — 커버리지 차이를 마스크로 잰 결과 (2026-08-21)

계획: `M1_4A2_COVERAGE_PLAN.md`.
도구: `test/openstep-mga-mesa-coverage-test.c`, `test/coverage-sweep.csh`,
`test/coverage-compare.py`.

## 0. 이 회차가 바꾼 것 한 줄

**"알려진 커버리지 불일치"는 논증이었다. 이제 측정이고, 원인이 확정됐고,
§3-12 에 적혀 있던 고칠 방법은 재 보니 부족하다.**

## 1. 어떻게 쟀나

같은 프로그램을 프로세스 둘로 돌린다 — `OSMGA_MESA_ACCEL=0` 이면
소프트웨어, 아니면 엔진. 커버리지를 **행별 런**으로 찍고(빈 행 포함),
python 이 비교한다. 넓이는 세지 않는다: 같은 숫자가 반 픽셀 가장자리
규칙에서도, 가운데 구멍에서도, 이음매 틈에서도 나온다.

일곱 도형, 각 3회, 두 경로를 번갈아. 모든 가속 실행이 `drawn>0`,
`software=declined=unsupported=0` — **되돌림 경로가 섞이지 않은 순수
하드웨어 실행**임을 실행 자체가 증명한다(가속을 켠 것만으로는 증거가
안 된다).

## 2. 깨끗하게 나온 것

| 확인한 것 | 결과 |
|---|---|
| 3회 재현 | 두 경로 모두 **완전히 같음** |
| 순수 하드웨어 | 7/7 도형 |
| 구멍·끊긴 행 | **없음** (양쪽) |
| 감는 방향 불변 (도형 1 vs 4) | **각 경로 안에서 정확히 동일** |
| 대각선 공유 사각형 — 틈 | **없음** (양쪽) |
| 대각선 공유 사각형 — 겹침(두 순서, 두 색) | **순서 의존 화소 0** (양쪽) |

즉 엔진이 그린 그림은 **빈틈없고 겹치지 않고 결정적이며 방향에
무관하다.** 이것들은 사실 GL 이 요구하는 불변량이고, 넘어갔다.

## 3. 어긋나는 것 — 그리고 어느 쪽이 틀렸나

**소프트웨어를 정본으로 삼지 않았다.** GL 규칙(화소 중심 표본 + top-left)
자체를 `coverage-compare.py` 안에 정수 연산으로 구현해 **양쪽을 규칙에
대고** 채점했다:

```
   shape 1 software: 139/139 rows match the rule exactly   EXACT
   shape 1 hardware: 119/139
   shape 2 software: 139/139 rows match the rule exactly   EXACT
   shape 2 hardware:  75/139
   shape 4 software: 139/139 rows match the rule exactly   EXACT
   shape 4 hardware: 119/139
```

**Mesa 소프트웨어는 규칙과 정확히 일치한다. 어긋나는 쪽은 하드웨어다.**

차이는 전부 런의 양 끝이고 방향이 한쪽으로 쏠린다(음수 = 하드웨어가
좁음):

| 도형 | 왼쪽 끝 차이 | 오른쪽 끝 차이 |
|---|---|---|
| 1 (평평한 밑변) | 0:119, +1:20 | 0:119, −1:20 |
| 2 (중간 y 에서 분할) | −1:17, 0:116, +1:5 | 0:89, −1:40, **−2:9** |
| 3 (잘린 삼각형) | 0:236 | 0:9, **−1:227** |

§3-25 때의 그 **227** 이 그대로 재현됐고, 이제 그것이 무엇인지 안다:
**236 행 중 227 행에서 오른쪽 끝이 정확히 한 화소 좁다.** 넓이가 아니라
가장자리다.

그리고 **넓이로는 절대 안 보였을 것 하나**: 도형 2 의 **40 행을 하드웨어가
통째로 안 그린다.** 소프트웨어는 2 화소짜리 런을 그린다.

## 4. 원인 — 확정

D3-2 가 20/20 행으로 확정해 둔 변 걷기 규칙을 python 시뮬레이터로 세우고
실측과 맞췄다:

```
acc = AR1 - 1 ;  행마다 acc += |dx| ;  acc >= 0 인 동안 x += sgn, acc -= dy
AR1 = -|dx| - e     (우리 Mesa 백엔드는 e = 0 으로 쓴다)
```

**도형 1 은 139/139 행, 도형 2 는 138/138 행을 정확히 재현했다.**
시뮬레이터가 예측한 40·179 행은 span 이 비어 엔진이 안 그린 것이 맞다.

잔차를 보면 하드웨어 열은 **정수 y 에서** 왼쪽 `ceil(x)`, 오른쪽
`floor(x) − 1` 이고 139/139 전부 맞는다. 즉:

> 엔진은 화소의 **왼쪽 위 모서리**에서 표본하고,
> GL 은 화소의 **중심**에서 표본한다.

코드 주석이 말하는 그대로다 — 부호는 `SGN` 이 따로 싣고 엔진은 **크기만**
걷기 때문에, 양쪽 변이 시작 정점에서 **바깥쪽으로 올림**된다.

### 4-1. §3-12 의 진단은 불완전했다

§3-12 는 원인을 "우리가 정점 좌표의 소수부를 버린다(`(long)` 캐스트)"로
적었다. **이 측정의 도형 1·2·4 는 꼭짓점이 전부 정수라 버릴 소수부가
없는데도 어긋난다.** 그러므로 절단은 원인의 일부일 뿐이고, 정수 정점에서도
남는 진짜 원인은 **표본점이 다르다는 것**이다. 두 번째 원인이며, 여기서는
지배적이다.

## 5. 고치는 법 — §3-12 의 스케치로는 부족하다 (python 으로 확인)

§3-12 은 "`FXBNDRY` 시작 열을 소수부만큼 치우치면 될 것 같다"고 적었다.
검증된 시뮬레이터로 **무작위 정수 삼각형 300 개**를 GL 규칙에 대고 쟀다:

| AR1/AR4 오차항 규칙 | 규칙과 일치한 행 | 완전히 맞은 삼각형 |
|---|---|---|
| `e = 0` (현재) | 36.5% | **0/300** |
| `e = (h − |dx|)/2` | 73.5% | 13/300 |
| `e = (h − |dx| − 1)/2` | 73.8% | 11/300 |

**오차항만으로는 못 닿는다.** 시작 열까지 변마다 자유롭게 두고 전수
탐색해도(삼각형 40 개) **행 92.2%, 완전히 맞은 삼각형 2/40** 이다.

→ 남은 몫은 **분해 자체**다. 우리는 정수 중간 정점 `m->y` 에서 쪼개고
`xSplit` 을 정수 나눗셈으로 구한다. 규칙은 그 위치에 그런 이음매가 있다고
가정하지 않는다.

**주의:** 이 탐색은 변마다 따로(greedy) 점수를 매겼으므로, "닿을 수 없다"가
아니라 **"이 두 손잡이로는 닿지 못했다"** 로 읽어야 한다.

## 6. 판정

가장자리에만 있고, 결정적이고, 빈틈·겹침·방향 의존이 없다. 그래서 이것은
**기록되는 호환성 결과**다 — "무해"라고 적지 않는다. 무해 여부는 신탁
(`P3_REFERENCE_ORACLE.md`)과 규격이 정할 일이고, 지금 확정된 것은
**하드웨어가 GL 규칙에서 벗어나는 방식과 그 크기**다.

## 7. 이 시험 자신의 결함 셋 (전부 결함을 통과로 보이게 했다)

계획서가 "먼저 기준을 적는다"고 했는데, 적어 놓은 기준 셋이 틀렸다.

1. **"가장자리" 판정에 한 화소 여유를 심었다.** 소프트웨어 런 끝의
   `{a−1,a,b,b+1}` 만 가장자리로 쳐서, 오른쪽이 **두 화소** 짧은 9 행의
   둘째 화소가 "안쪽 차이"로 세어졌다. 양방향으로 틀린 답이다. 런은 하나로
   이어져 있으니 차이는 **구성상** 끝에 있다 — 보고할 것은 여유가 아니라
   **얼마나 벗어났는지의 분포**다.
2. **행 범위를 각 경로 자신의 출력에서 잡았다.** 그래서 하드웨어가 통째로
   빠뜨린 40 행이 검사 범위 밖으로 나가 **누락으로 세어지지 않았다.**
   codex 가 "런 0 개도 결함"이라고 짚은 바로 그 경우인데, 고쳐 놓고도
   범위를 교차 비교하지 않아 반만 고쳤던 셈이다.
3. **두 색 도형에 단색 검사를 들이댔다.** 6·7 번은 행마다 런이 둘인 것이
   정상인데 "런이 하나여야 한다"로 재서 **모든 행을 broken 으로** 찍었다.
   그 도형에서 볼 것은 런 개수가 아니라 **런 사이에 클리어색이 있는가**다.

  받는다.
