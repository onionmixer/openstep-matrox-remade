# M1-3j — 고침을 확정한다

`M1_3I_SETTLE_PLAN.md` §10 의 측정 위에서 세운다. 아직 코드 없음.

## 1. 무엇이 확정됐나

- 매핑된 창의 **첫 64 바이트**가 한 덩어리다. 고정된 한 자리이고 페이지마다
  있는 것이 아니다.
- **제출 직전의 마지막 읽기**가 그 안이면 그 제출이 거기에 쓴 것이 늦게
  보이고, 바이트 64 이상이면 안 그렇다. **쓰기는 무관하다.**
- 클라이언트 읽기든 **커널의 언캐시드 별칭 읽기든 똑같이** 낫게 한다.
  경계는 양쪽 다 바이트 64 다 (안쪽 240/240 짧음, 바깥쪽 320/320 깨끗).
- 늦은 것이지 잃은 것이 아니다.

## 2. 실제로 무엇이 걸리나 — 소스에서 확인했다

**Mesa 의 색 표면은 정확히 창 시작에 놓인다:**

```c
/* mesa/OpenStepMGAMesaBuffer.c:284 */
bufOrigin = probe.caps[OSMGA_HW3D_CAP_VRAMOFF];
```

`VRAMOFF` 는 `osmgaMmapWindowStart` 다. **그러므로 실제 경로가 걸린다.**

**미러가 바이트 0 부터 읽는다:**

```c
/* mesa/OpenStepMGAMesaBuffer.c, OSMGAMesaBufferMirror */
src = (const unsigned long *)bufMapped;
... d[x] = s[x];        /* 첫 읽기가 s[0] -- 죽은 구간 안 */
```

정상 상태에서는 미러의 **마지막** 읽기가 높은 주소라 다음 제출이 해제되고,
그래서 그 다음 미러의 `s[0]` 이 맞는 값을 본다. **노출되는 자리는 첫
프레임**, 그리고 앱이 표면의 낮은 주소를 읽고 나서 그리는 모든 경우다
(`glReadPixels` 등).

## 3. 먼저 풀어야 할 것 — §3-19 (A 단계, 유저랜드, 재부팅 없음)

`REMAINING_WORK §3-19`: **`mmap` 의 오프셋이 무시된다.** 시험 클라이언트로
쟀고, 페이지 정렬된 오프셋에서도 그랬다.

이것이 지금 갑자기 중요해졌다:

```c
/* mesa/OpenStepMGAMesaBuffer.c:92 -- 깊이 버퍼를 0 이 아닌 오프셋에 매핑한다 */
mmap((caddr_t)addr, ..., OSMGAMesaProbeDeviceFd(),
     (long)(probe.caps[OSMGA_HW3D_CAP_VRAMOFF] + tail))
```

오프셋이 정말 무시된다면 **깊이 매핑이 색 표면 위에 겹친다.** 엔진은
`depthOrigin` 을 제대로 받으므로 그리기는 맞지만, **클라이언트가 쥔 깊이
포인터가 틀린 곳을 가리킨다.** 지금 아무도 그걸 읽지 않아서 안 드러났을
수 있다.

**그리고 그 포인터는 그냥 굴러다니는 것이 아니다.** Mesa 가 그것을
`ctx->gl_buffer->DepthBuffer` 에 꽂는다:

```c
/* opennstep-mesa342/.../osmesa.c:476 */
ctx->gl_buffer->DepthBuffer = accelDepth;
ctx->gl_buffer->UseSoftwareDepthBuffer = GL_FALSE;
```

소프트웨어 래스터라이저는 폴백할 때 그 버퍼를 **읽고 쓴다.** 오프셋이
무시된다면 소프트 경로의 깊이 쓰기와 `glClear(GL_DEPTH_BUFFER_BIT)` 가
**색 표면 위에 떨어진다.** 아직 안 드러난 것은 지금까지 시험이 하드웨어
경로만 탔기 때문일 수 있다.

그리고 "창의 첫 페이지를 안 내준다" 같은 고침은 전부 이것에 기댄다.

**재는 법**

1. 두 헬퍼(`mapDevice`, `mapWindow`)가 `mmap()` 의 반환값을 버리고
   `vm_allocate` 주소를 돌려준다. 반환값을 받아 **찍고**, 요청한 주소와
   같은지 확인한다.
2. 오프셋 `N` 으로 매핑한 뒤 그 자리에 표식을 쓰고, 오프셋 0 매핑에서
   `N` 만큼 떨어진 곳을 읽어 같은 값이 나오는지 본다. 같으면 오프셋이
   먹은 것이고, 창 시작에서 나오면 무시된 것이다.

## 4. 무엇을 내보낼 것인가 (B 단계)

| 안 | 내용 | 비용 | 문제 |
| --- | --- | --- | --- |
| (a) | 제출마다 무조건 정착 읽기 | 제출마다 언캐시드 읽기 1 회 | 안 걸리는 대다수에도 비용을 문다. 재기 전에는 기본값으로 못 삼는다 |
| (b) | `dstorg == 창 시작` 일 때만 | 사실상 0 | **술어가 좁다** — 겹침이 조건이지 같음이 아니다 |
| (c) | Mesa 가 그 자리를 피한다 | VRAM 64 바이트 | Mesa 만 보호한다. 그리고 **§3-19 에 기댄다** |
| (d) | 드라이버가 창의 첫 페이지를 안 내준다 | VRAM 8 KiB (0.26%) | **§3-19 에 기댄다.** 오프셋이 무시되면 클라이언트가 자기 위치를 잘못 알게 되어 **더 나빠진다** |
| **(e)** | **쓰기 범위가 창의 첫 64 바이트와 겹칠 때만 정착 읽기** | **겹칠 때만 읽기 1 회** | **§3-19 에 안 기댄다. 계약도 안 바꾼다. 날 클라이언트도 보호한다** |

**(e) 를 고른다.**

- 안 걸리는 제출에는 비교 하나뿐이다.
- 걸리는 제출에는 이미 측정으로 통한다고 확인된 읽기 하나다.
- caps 도, Mesa 도, 매핑도 안 건드린다 — **§3-19 가 무엇으로 밝혀지든
  영향받지 않는다.**
- 손잡이는 남긴다. 기본값을 "겹칠 때 자동"으로 하고, 손잡이로 강제 켜기·
  끄기를 할 수 있게 한다(측정 재현용).

### 술어 (python 으로 확인함)

겹침은 범위 검사로 쓴다:

```
first = org
last  = org + (rows - 1) * pitchBytes + widthBytes     /* 하나 지난 자리 */
겹친다 <=> !(last <= WS || first >= WS + 64)
```

| 경우 | 겹치나 |
| --- | --- |
| Mesa 색 표면(창 시작) | **예** |
| 한 행 아래 | 아니오 |
| 768 행 색 버퍼 뒤의 깊이 | 아니오 |
| 바이트 64 에서 끝나는 목적지 | **예** |
| 바이트 64 에서 시작하는 목적지 | 아니오 |

앞으로만 나아가는 배치에서는 `org < WS + 64` 로 줄어들지만, **코드는 범위
검사로 쓴다** — 줄어드는 것은 배치의 성질이지 검사의 성질이 아니다.

**색과 깊이 둘 다** 본다. 엔진은 `zorg` 에도 쓴다. 다만 **깊이는 자기
보폭을 쓴다** — 검증기에서 확인했다:

```c
/* hw3d/OpenStepMGAHW3D.c:158 */
unsigned long zstride = (lim->pitchBytes / 4UL) * OSMGA_HW3D_DEPTH_BYTES;
```

화소 × 2 바이트다. 색 크기로 깊이 범위를 잡으면 **두 배**로 잡는 셈이고,
그것은 안전한 쪽이지만 구분을 감춘다. 그러니 따로 계산한다:

```
색   : dstorg .. dstorg + (rows-1)*pitchBytes       + dstWidth*4
깊이 : zorg   .. zorg   + (rows-1)*(pitchBytes/4)*2 + dstWidth*2     (anyZI 일 때만)
```

**스냅샷과 검증을 마친 뒤에** 계산한다. 기존 오버플로 검사 앞에 검사되지
않은 덧셈을 새로 만들지 않는다.

## 4b. codex 교차검토 — 재검증 결과

**소스에서 확인해 받아들인 것**

- **깊이 범위는 자기 보폭을 쓴다** (위). 검증기에서 확인했다.
- **노출 시점의 표현이 부정확했다.** "첫 프레임"이 아니라
  **"창 매핑에 대한 마지막 읽기가 낮은 자리였던 뒤의 첫 제출"** 이다.
  그리고 "앱이 낮은 자리를 읽는다"는 **이 VRAM 매핑을 통한 읽기**여야 한다
  — OSMesa 앱 버퍼를 읽는 것은 해당되지 않는다.
- **미러의 첫 워드를 두 번 읽는 것으로는 안 된다.** 워드 0 이 고쳐져도
  워드 1..15 가 복사 전에 고쳐졌다는 보장이 없다. 유저랜드 우회를 굳이
  한다면 `src[16]` 을 한 번 버리고 읽는 것이다. 어차피 드라이버 쪽이
  맞는 층이다 — 날 클라이언트와 미러 아닌 경로도 보호한다.
- **A 단계에 관측이 셋 필요하다.** 표식 하나로는 원래 값이 우연히 같아도
  "오프셋이 먹었다"고 잘못 읽는다. `B[0]` 과 `B[N]` 을 서로 다른 값으로
  두고, **`mmap()` 이 실제로 돌려준 주소를 통해** 세 번째 값을 쓴 뒤 둘 다
  읽는다. 건드린 워드는 되돌린다.
- **반환값을 찍는 것만으로는 부족하다** — 이후 접근이 그 반환 주소를 써야
  한다. 지금 헬퍼는 색·깊이 양쪽에서 반환값을 버린다.
- **출시 시험은 강제켬·자동·강제끔을 따로 덮는다.** 별칭이 없거나 길이가
  워드 16 에 못 미치는데 "자동으로 정착했다"고 보고하는 일이 없어야 한다.
- **주장을 하드웨어 범위 안에 둔다.** 이 G450/OPENSTEP 구성에서 잰 것이고,
  다른 MGA 부품이나 다른 aperture 로 일반화하지 않는다.

**받아들이되 내 몫이 남은 것**

- codex 는 (e) 가 §3-19 와 무관하다는 데 동의했다. 이유도 같다 — 술어는
  **검증된 스냅샷의 `dstorg`/`zorg`** 로 계산하지, 클라이언트 포인터로
  계산하지 않는다.

## 4c. 그 지적을 파다가 나온 별개의 버그 — 깊이 매핑이 4 KiB 로 정렬한다

codex 가 `mesa/OpenStepMGAMesaBuffer.c:77` 의 `+4095 & ~4095` 를 짚었다.
확인하니 이 기계의 `PAGE_SIZE` 는 8192 이고, `d_mmap` 은 페이지 정렬이
아닌 물리 주소를 **거절한다**:

```c
if ((phys & ((unsigned long)PAGE_SIZE - 1UL)) != 0UL)
    return -1;
```

python 으로 따졌다. 두 번 틀렸다. 처음엔 크기 여섯 개를 손으로 골라
"지금은 우연히 괜찮다"고 적었는데 **그건 표본을 고른 것이라 주장이 못
된다.** 전수로 다시 돌렸더니 이번엔 **보폭을 디스플레이 보폭으로 놓은
것이 틀렸다** — 이 경로는 `bufStride != bufWidth` 면 아예 안 타므로
보폭이 곧 버퍼 너비다.

세 번째가 맞다. `h*w*4` 가 8192 의 배수인 것은 `h*w` 가 **2048 의 배수**
일 때뿐이고, 아니면 4096 반올림이 4096 의 배수에만 떨어져 그중 절반이
어긋난다. 너비 1..1024 × 높이 1..768 의 786432 조합 중 **395172 개
(50.2%)가 실패한다:**

| 크기 | tail | tail % 8192 | 깊이 mmap |
| --- | --- | --- | --- |
| 320x240 | 307200 | 4096 | **거절** |
| 640x480 | 1228800 | 0 | ok |
| **800x600** | 1921024 | 4096 | **거절** |
| 1024x768 | 3145728 | 0 | ok | 실패하면 `OpenStepMesaAccelDepthBuffer` 가 0 을 돌려주고
Mesa 는 **말없이 소프트웨어 깊이 버퍼를 계속 쓴다.**

지금 시험이 768 이라 안 걸렸을 뿐이다. `REMAINING_WORK §3-20` 으로 세운다.

## 5. 안 하는 것과 그 이유

- **원인을 안다고 적지 않는다.** 왜 64 바이트인지, 왜 창 시작 한 자리인지
  모른다. 고침은 경험적이고, 그렇게 적는다.
- **`dstorg == 창 시작` 로 좁히지 않는다** (codex 지적, 옳다).
- **무조건 읽기를 기본으로 하지 않는다** — 비용을 안 쟀다.

## 6. 순서

A(§3-19, 유저랜드) → 결과 기록 → B 코드 → 빌드 → 설치 → 재부팅 요청 →
검증(모드 5 로 80 시행, 겹칠 때 0/80, 안 겹칠 때도 0/80).

**B 는 A 의 답에 의존하지 않는다** — 그것이 (e) 를 고른 이유다. A 는
독립된 미해결 항목으로서 풀되, B 를 막지 않는다.
