# M1-4 — 엔진이 더하는 511 을 보정한다

2026-08-22.  **커널 변경이므로 재부팅이 필요하다.**

## 1. 값이 있는 차이가 됐다

같은 텍스처 장면을 두 경로로 그려 비교했다(`M1_4C6` §8-3):

```
   하드웨어 25964 화소,  소프트웨어 25974
   공통 25964 중 색이 다른 것 137 (0.53%)
   차이는 전부 정확히 텍셀 하나, 언제나 하드웨어가 앞선다
```

원인은 잰 값이다: 엔진은 텍셀을 `floor((u + 511) / 텍셀크기)` 로 고른다
(`M1_4C3` §10 — 증분을 전부 0 으로 두고 시작값을 쓸어 얻었고, u 와 v 가
같은 값을 준다).  `511 = 2^9 − 1` 이고, 512 는 텍스처 한 장(2^20)을 최대
텍스처 2048 로 나눈 값이다.

## 2. 어디서 빼는가 — 커널 인코더

교차분석의 권고를 받는다: **빌더에서 빼고 검증기를 푸는 것이 아니라,
인코더가 레지스터를 쓰기 직전에 뺀다.**

* 프로토콜과 검증기는 **논리 좌표**를 그대로 쓴다.  `tmr[6]`·`tmr[7]` 은
  클라이언트가 뜻한 값이고 `0..room` 이라는 계약도 그대로다.
* 유저랜드에서 빼면 흔한 경우(`s = 0` 인 꼭짓점)에 시작값이 음수가 되고
  검증기가 거절한다.  검증기를 풀면 "음수 텍스처 좌표"와 "보정 전 값"이
  같은 것이 되어, 검사가 무엇을 지키는지 흐려진다.

```c
/* OpenStepMGAReplacementDisplay.m, 텍스처 상태 블록 */
MGA_TMR0 + 24UL, (unsigned long)(b->state.tmr[6] - OSMGA_HW3D_TEX_BIAS),
MGA_TMR0 + 28UL, (unsigned long)(b->state.tmr[7] - OSMGA_HW3D_TEX_BIAS),
```

`OSMGA_HW3D_TEX_BIAS` 는 헤더에 잰 값으로 적고, **어떻게 쟀는지도 적는다.**

## 3. 위험 — 음수 시작값

보정하면 레지스터에 음수가 들어간다(논리 0 이면 −511).  **하드웨어가 음수
시작을 어떻게 다루는지는 안 쟀다.**  헤더가 그렇게 적어두었고, 클라이언트는
검증기 때문에 음수를 보낼 수 없어서 잴 방법도 없었다.

이제는 잴 수 있다: 보정을 넣으면 논리 0 이 레지스터 −511 이 되고,
그 결과를 **화소로 본다**.

* 하드웨어가 부호를 제대로 보면: −511 + 511 = 0 → 텍셀 0.
* 부호를 못 보면(큰 양수로 읽으면): 좌표가 치솟아 `CLAMPUV` 가 마지막
  텍셀로 붙인다 → 텍셀 63.  **눈에 띄게 다르다.**

증분에 대해서는 이미 부호가 통한다는 것을 쟀다(`texreach-probe` §14 —
`TMR0` 과 `TMR3` 의 음수가 반영된다).  시작값도 같은 레지스터 파일이므로
그럴 가능성이 높지만, **가능성은 측정이 아니다.**  틀리면 그림이 즉시
틀리고, 되돌리는 것은 상수를 0 으로 두는 한 줄이다.

## 4. 무엇을 재나

1. **논리 0 에서 텍셀 0** — 보정 뒤 레지스터가 −511 인 경우.  이것이
   §3 의 위험을 가르는 시험이다.
2. **소프트웨어와의 차이가 137 에서 줄어드는지** — 같은 장면, 같은 비교.
   0 이 되지 않아도 좋다(엔진의 기울기 의존 항이 열 단위쯤 남는다) 하지만
   **줄어야 한다.**
3. **커버리지 10 화소는 그대로여야 한다** — 그건 텍스처와 무관한 규칙 차이다.
4. **기존 텍스처 시험 전부** — raw 클라이언트, 도달 probe, 업로드, 그림.
5. **호스트 136 사례**와 사다리꼴 불변식 — 검증기는 안 건드리므로 그대로.

## 5. 되돌리는 법

상수를 0 으로 두면 지금 동작으로 돌아온다.  그러니 이 변경은 한 줄과
한 상수다.

### 6-1 고친 판별 시험

1. **영-기울기 전환점**: `texreach-probe` §16 이 지금 `15873` 을 준다.
   보정 뒤에는 **정확히 16384** 여야 한다.  이것이 "패치가 실려서 실제로
   나갔는가"를 가른다.
2. **소프트웨어와의 차이**: 137 에서 **줄어야** 한다.  0 이 아니어도 좋다 —
   기울기 의존 항이 남는다.
3. 커버리지 10 화소는 그대로.
4. 기존 텍스처 시험 전부, 호스트 136 사례, 사다리꼴 불변식.

## 7. 재부팅 뒤 결과 — 넣었다가 도로 뺐다 (2026-08-22)

### 7-1 판별 시험은 통과했다

교차분석이 고른 판별자대로, **영-기울기 쓸기의 전환점이 15873 → 정확히
16384** 로 움직였다(두 축).  패치가 실려서 실제로 나갔다는 뜻이다.

### 7-2 노린 것도 얻었다

| | 보정 전 | 보정 후 |
|---|---|---|
| 소프트웨어와 다른 화소 | 137 / 25964 (0.53%) | **24 (0.09%)** |
| 커버리지(소프트웨어에만) | 10 | 10 |
| 하드웨어에만 | 0 | 0 |

잔차 24 는 **양방향**이 됐다((0,−1) 19, (1,0) 5) — 보정 전에는 전부 하드웨어가
앞섰다.  즉 과보정된 자리가 생겼다.

### 7-3 그런데 다른 넷이 한 텍셀씩 낮아졌다

그중 하나는 측정이 아니라 **정확성** 사례다: 32 열 삼각형에 열당 32768 을
주고 열 c 에서 텍셀 2c 를 기대하는데 1024 중 1004 가 틀렸다.

계수만으로는 진단이 안 된다.  실제 값을 찍었다:

```
   (0,0) got u=0 want 0      (3,0) got u=6 want 6
   (1,0) got u=2 want 2      (4,0) got u=7 want 8
   (2,0) got u=4 want 4      (5,0) got u=9 want 10
```

**열 0~3 은 맞고 4 부터 하나씩 뒤진다.**  상수 오프셋이라면 첫 열부터
어긋나야 한다.  이건 **누적이 조금씩 모자라게 도착하는** 모양이고, 시작에서
511 을 빼면 그 모자람이 텍셀 경계를 넘게 된다.

### 7-4 그래서 되돌렸다

상수는 시작에 대해서는 맞다(§7-1, 그리고 §17 이 증분 0~32768 아홉 크기에서
전부 511 을 준다 — **기울기에 의존하지 않는다**).  틀린 것은 **그 뒤에
무슨 일이 일어나는지**이고, 그걸 모르는 채로 커널이 좌표를 손대게 두지
않는다.  헤더의 상수는 0 으로 두고 이야기를 그 옆에 적었다.

### 7-6 다음 측정

문턱이 아니라 **누적**을 봐야 한다: 시작을 고정하고 열을 따라가며 텍셀
경계가 어디서 벌어지는지를 재면, 열마다 얼마씩 모자라는지 나온다.
그게 규칙이지 상수가 아니다.
