# W5 — 비동기 제출 설계 (2 판)

**1 판은 codex 교차검토에서 "이 설계로는 짓지 말라" 는 판정을 받았고, 전부
확인했다.** 가장 중요한 정정 셋:

1. **FETCHED 로 리스트를 재사용할 수 없다.** 우리 인코더 주석 자신이
   *"the card reads a little past PRIMEND"* 라고 적는다(`:9611`). DRM 도 G400
   매뉴얼 4-16 쪽을 인용해 같은 말을 한다. **그 주석을 눈앞에 두고 못 봤다.**
   → RETIRED 로 바꾸면 **오늘 워크로드에서 이득이 똑같고(8.81 ms) 위험한 실기
   실험이 통째로 없어진다.**
2. **커서 위험은 실재하고, 내 "정정" 이 원래 초안보다 더 틀렸다.**
   duty cycle 을 다시 계산하니 **65.4% → 82.2% (+16.9 포인트)** 로 **넓어진다.**
3. **drain 목록이 열둘이 아니라 최소 스물둘이고, 그중 하나는 원리적으로 막을
   수 없다** — 유저랜드가 VRAM 을 직접 매핑한다.

판정표는 §12.


W4 §6 은 **설계 문서가 나오기 전에는 Stage B 코드를 쓰지 않는다**고 못박았다.
이 문서가 그것이다. **여기에는 코드가 없고, 이 문서만으로 착수하지도 않는다.**

## 0. 금지 목록 대조 — 설계 **전에** 했다

`W2_WARP_RENDER_PATH_PLAN.md` §7 의 표를 다시 읽었다.

| 금지 | 이 설계와의 관계 |
| --- | --- |
| 시저 + 계측을 같은 실행에 | **이 설계는 시저를 쓰지 않는다.** 계측을 넣는다면 A0 처럼 시저와 코드로 상호배타 |
| 제출마다 `gettimeofday` | 넣지 않는다 |
| 이상 징후 후 재시도 | §8 의 실패 정책이 이것을 그대로 따른다 |
| `SECADDRESS` 회수 절차 없이 쓰기 | **이 설계는 2 차 DMA 를 쓰지 않는다.** Stage C 는 여전히 닫혀 있다 |

## 1. 이득과, 그것을 얻으려면 무엇을 포기해야 하는가

```
지금        draw 13.18 ms  =  호스트 8.46 + 막히지 않은 꼬리 0.35 + 엔진 대기 4.37
완전히 겹침 draw  8.81 ms  =  max(8.46 + 0.35, 4.37)
            draw 만 1.50 배,  프레임 전체 21.27 -> 16.90 ms = 1.26 배
```

**폴 조건을 PRIMADDRESS 비교로 바꾸는 것만으로는 0 이 나온다.** 같은 스레드가
같은 자리에서 막힌다. 겹치려면 **SUBMIT 의 계약이 "완료"에서 "수락"으로**
바뀌어야 하고, 그 순간 아래 전부가 새로 필요해진다. **1.26 배의 값이 그
전부보다 큰지는 이 문서의 마지막 질문이다(§10).**

## 2. 지금의 계약, 그리고 무엇이 그것에 기대고 있는가

`OSMGA_IOC_SUBMIT` 은 **완료를 반환한다**. 돌아왔다는 것은:

- 엔진이 이 목록을 다 그렸다
- 표면을 CPU 가 읽어도 된다
- 리스트 버퍼와 스냅샷을 재사용해도 된다
- `stormBusy == NO` 이므로 다른 엔진 사용자가 들어와도 된다
- 오류가 있었다면 **이 반환값에 들어 있다**

**다섯 가지 전부가 비동기에서 거짓이 된다.** 하나씩 대책을 세운다.

---

## 3. 펜스 — 상태는 둘이 아니라 다섯이다

1 판은 FETCHED / RETIRED 둘로 잡았다. **모자란다.**

| 상태 | 성립 | 무엇을 허락하는가 |
| --- | --- | --- |
| PUBLISHED | `PRIMEND` 쓰기가 순서지어짐 | — |
| **FETCHED** | `PRIMADDRESS == 발행한 end` | **아무것도.** §4 참조 |
| FENCE-SIGNALED | `SOFTRAPEN` 관측 | 오류 귀속의 시작점 |
| **RETIRED** | 지금의 완료 예측 전체 + 최종 idle | 다른 엔진 사용자, 리스트 재사용 |
| **CPU-VISIBLE** | RETIRED + 정착 읽기(`:5928`) | **CPU 의 표면 읽기** |

**다섯 번째를 1 판이 빠뜨렸다.** 이 기계에는 완료·최종 idle 뒤에도 첫 색
바이트가 낡아 있을 수 있고, 언캐시드 읽기 하나가 그것을 해결한다는 것이
이미 기록돼 있다. DRM 에는 없는 항목이고 **이 플랫폼 고유의 가시성 결함**
이므로 계약에서 뺄 수 없다.

## 4. FETCHED 로는 리스트를 재사용할 수 없다 — 설계의 중심 정정

우리 인코더가 SOFTRAP 뒤에 패딩 블록을 넣으면서 이유를 적는다(`:9611`):

> *"The trap has to be INSIDE what PRIMEND covers, and **the card reads a
> little past PRIMEND**, so a padding block has to follow it."*

DRM 도 같다(`mga_dma.c:132`): *"the card actually (partially?) reads the first
of these commands. See page 4-16 in the G400 manual."*

**그러므로 `PRIMADDRESS == end` 는 카드가 그 버퍼 읽기를 멈췄다는 뜻이 아니다.**
더 긴 다음 리스트가 이전 리스트의 패드 영역을 덮으면, 카드가 읽고 있는 바이트를
바꾸는 것이다.

### 그래서 (A) 안을 이렇게 고친다

**진입에서 FETCHED 가 아니라 RETIRED 를 기다린다.** 그리고 그것이 손해가 아니다:

```
FETCHED 진입 대기   max(6.48, F) + 1.98 + 0.35
RETIRED 진입 대기   max(6.48, 4.37) + 1.98 + 0.35 = 8.81 ms
```

오늘 `RETIRED = 4.37 < 6.48` 이므로 **두 값이 같다.** FETCHED 는 **오늘 한 푼도
더 주지 않으면서 문서화되지 않은 read-ahead 위에 올라선다.**

> **그리고 이것이 실기 실험 하나를 통째로 없앤다.** 1 판 §9-4 는 "FETCHED 로
> 리스트를 재사용해도 되는지 실기로 확인" 을 Stage B 의 첫 질문으로 삼았다.
> 그 실험은 **문서화되지 않은 read-ahead 가 언제 멈추는지를 덮어쓰기로
> 알아보는 것**이고, 하드 프리즈 일곱 번을 겪은 기계에서 할 일이 아니다.
> **RETIRED 로 바꾸면 그 질문 자체가 사라진다.**

1 판이 적은 "여유 2.11 ms" 는 **RETIRED 기준의 여유**이지 FETCHED 여유가
아니었다. A0 은 `F` 를 잰 적이 없다 — 완료 예측이 성립한 **뒤에만** 표본했다.

## 5. drain 지점 — 1 판은 절반도 세지 못했다

### 5.1 커널, `stormBusy` 를 claim 하는 넷 (1 판이 맞게 찾음)

`doDisplayBlitSrcX:` `:4626` · `setIntValues:` `:4977` ·
`runHW3DPresent:` `:5217` · `claimEngineForMode` `:6097`

모드 변경은 **유계 대기가 끝나면 busy 인 채로 모드를 프로그래밍한다**(`:2278`
이 그렇게 적는다). 리셋·격리 절차가 없는 한 그것을 비동기 정책으로 둘 수 없다.

### 5.2 1 판이 빠뜨린 것 — 열 갈래

| 갈래 | 어디 | 왜 위험한가 |
| --- | --- | --- |
| **다음 3D 제출** | `:5737`, `:5841` | CPU 상태 쓰기·트랩 ack·도어벨 전에 **RETIRED 필요** |
| 소프트웨어 재생 | `Hook:834`, `:968`, `:1014`, `:1040`, `:1067` | 앞부분이 수락된 직후 거절된 삼각형을 **같은 표면에** 재생 |
| Mesa 색 스팬 래퍼 | `Hook:2450`~`2512` | 지금은 동기 flush 에 기대고 있다. **flush 는 drain 이 아니다** |
| **깊이 접근** | `Buffer:255`, Mesa `depth.c` 다섯 곳 | 색 래퍼를 **거치지 않는다.** "깊이 접근" 이라고 한 줄 쓴 것은 계획이 아니다 |
| `glReadPixels`(깊이) | `readpix.c:771` | **RenderFinish 전에 읽는다** — 1 판의 "RenderStart/Finish 로 감싸임" 은 색에만 참 |
| `OSMesaGetColorBuffer` | `osmesa.c:860` | 공개 API 로 들어오는 미러 입구 |
| 버퍼 bind/rebind | `Buffer:479`, `:793`, `:882` | 앱 배열을 CPU 로 표면에 복사 |
| **텍스처 수명** | `Texture:111`, `:244`, `:293` | 업로드가 **인플라이트 배치가 아직 샘플링할 텍셀을** 덮는다. 삭제는 아레나 블록을 회수 |
| 컨텍스트/라이브러리 해제 | `Buffer:649`, `osmesa.c:358`, `Probe:212` | 매핑을 drain 없이 푼다. fork 정리 포함 |
| 드라이버 해제 | `:3025`, `:3601`, `:6446` | `free` 가 MMIO 매핑을 drain 없이 푼다 |

### 5.3 원리적으로 막을 수 없는 것

**유저랜드가 VRAM 을 직접 매핑한다**(`:2305`, `:2514`). 클라이언트 신원도 없고
VM fault 개입도 없다. **커널은 평범한 load/store 앞에 drain 을 끼워 넣을 수
없다.** 지금은 제출이 동기라서 반환 시점이 곧 안전 시점이고, 비동기는 그
보증을 없앤다. 이것은 drain 을 "빠뜨린" 것이 아니라 **드라이버가 제공할 수
없는** 것이다.

**대책은 둘뿐이다**: 그 매핑 ABI 를 닫거나, 비동기를 **명시적으로 opt-in 한
클라이언트에게만** 주고 나머지에게는 지금의 동기 계약을 유지한다.

### 5.4 정정 — `OSMGAMesaBufferFill` 은 drain 이 아니다

1 판이 이것을 표면 쓰기로 세었다. `bufApp` 만 쓴다. **잘못 센 것이고, 빼면
목록이 하나 줄고 신뢰도는 는다.**

## 6. 커서 — 1 판의 "정정" 이 초안보다 더 틀렸다

초안: *"비동기가 창을 프레임 전체로 넓힌다"* — 과장.
1 판의 정정: *"duty cycle 이 95.8% 에서 94.7% 로 내려간다"* — **더 틀렸다.**

**`stormBusy` 는 ioctl 안에서만 잡힌다.** 기하 2.10 과 CPU 빌드 4.38 은 ioctl
**앞**이라 claim 되지 않는다. 그것을 세어 넣은 것이 95.8% 의 정체다.

```
claim/프레임 = clear 3.49 + ioctl 6.70 + present 3.71 = 13.90 ms
duty cycle 오늘        13.90 / 21.27 = 65.4%
(A) 안에서             13.90 / 16.90 = 82.2%      +16.9 포인트
present 만             17.4%  ->  22.0%
```

**넓어진다. codex 가 맞고 내가 두 번 틀렸다.**

그리고 **G450 에는 하드웨어 커서가 있다.** X.Org 는 G450 급에서 기본으로 쓰고
(`mga_driver.c:2548`), 전용 버퍼에 CPU 로 싣고(`mga_dacG.c:1944`), RAMDAC
레지스터로 보이기·숨기기·이동을 한다(`mga_dacG.c:1959`, `:1983`, `:2258`) —
**그리기 엔진을 전혀 쓰지 않는다.** 이 드라이버는 그것을 꺼 두었고(`:219`),
그래서 상위 클래스가 CPU 로 프레임버퍼에 그린다.

**그러므로 완화책이 있다: 하드웨어 커서를 구현하는 것.** 1 판이 "완화책을
모른다" 고 쓴 것은 틀렸다. 다만 그것은 **이 작업의 선행 조건**이지 곁다리가
아니다.

`statCursorWhileBusy` 는 **오프스크린 3D 와의 무해한 겹침까지 세므로** 실제
충돌을 분리하지 못한다. **재는 것은 완화가 아니다.**

## 7. 오류 귀속 — 동기 실패가 넷, 비동기 실패가 넷

1 판은 "검증·인코딩 실패는 동기이므로 거절·좁히기 로직이 안 바뀐다" 고 썼다.
**절반만 맞다.**

**동기로 남는 실패 넷**: 인코더 용량, 사전 idle, 사전 DMA 정숙, FIFO 진입.
뒤의 셋은 검증 거절이 아니다 — **좁히기로 대응할 수 없는 것들이다.**

**그리고 현행 코드에 잠복 버그가 있다.** 인코더가 0 을 돌려주면
`osmgaHW3DLast[0]` 은 **검증기의 OK 가 그대로 남고**, `rc3` 은 0 이라 ioctl 은
실패한다. 훅은 `verdict == OSMGA_HW3D_OK` + 실패를 보고
**"a batch failed after the engine had it" 으로 가속을 회수한다**
(`Hook:925`) — 좁히기가 아니라 회수다.

> 오늘 도달 불가다(리스트 영역 40,960 B, 최악 28~33 KB). **잠복이고 비동기가
> 이것을 깨우지 않는다.** 그래도 적어 둔다 — 비동기 설계가 이 verdict 경로에
> 손대는 순간 살아난다.

**비동기로 미뤄지는 실패 넷**: 완료 타임아웃, 복구 폴 타임아웃, 최종 idle
실패, 모드 epoch 변경(`:6084`).

**그리고 1 판이 아예 안 다룬 것**: *누가 타임아웃을 발견하는가.*

## 8. 완료를 알아차릴 주체가 없다 — 가장 깊은 문제

```
$ grep interruptOccurred|IOScheduleFunc|timeoutOccurred|attachInterrupt  -> 없음
```

**이 드라이버에는 인터럽트 핸들러도 타이머도 없다.** 완료를 아는 유일한 방법이
누군가 폴링하는 것이고, ioctl 이 일찍 반환하면 **다음 ioctl 이 올 때까지 아무도
폴링하지 않는다.**

결과: `stormBusy` 가 잡힌 채 남는다. 그러면 **present·2D·모드 변경이 다음 3D
제출이 올 때까지 막힌다.** 3D 가 멈춘 순간(마지막 프레임, 앱 종료) **엔진이
영구히 busy 로 보인다** — arm B 에서 내가 이미 한 번 만든 상태다.

**이것을 풀지 않으면 비동기는 성립하지 않는다.** 선택지:

- 인터럽트 핸들러를 붙인다 — DRM 이 하는 것(`mga_irq.c:73`). **가장 큰 변경**
  이고 §3-62 의 "완료 토폴로지" 미해결 후보 한복판이다.
- 타이머/워커로 폴링한다 — MMIO 트래픽이 늘고 "버스 중재" 후보를 건드린다.
- **다른 엔진 사용자가 진입할 때 대신 폴링한다.** 추가 액터가 없고 트래픽도
  안 는다. present 는 어차피 프레임마다 오므로 실용적이다. **가장 싸다.**

## 9. `stormLock` 안에서 기다리면 안 된다

1 판은 "진입 대기가 `stormLock` 안에 있으므로 직렬화가 유지된다" 고 썼다.
**지금 코드는 일부러 그렇게 하지 않는다** — 소유권만 락 안에서 바꾸고
(`:5434`), 하드웨어 대기는 락을 놓고 한다. 심플락을 쥔 채 MMIO 를 폴링하면
커서·모드·인터럽트 레벨 호출자를 막고, **진행에 필요한 바로 그 주체를 막을 수
있다.**

## 10. 인플라이트 서술자가 필요하다

지금 완료 꼬리는 **스택 지역변수**에 기댄다: 리스트 end, 모드 epoch, 정착 모드,
겹침 상태, 오류 상태. **ioctl 이 반환하면 그것들이 사라진다.** 세대 번호
하나로는 부족하고, 미결 제출 하나를 기술하는 **영속 구조체**가 필요하다.

## 11. 그래서 결론 — 짓지 않는다, 그리고 무엇을 대신 하는가

**이득**: 프레임 1.26 배 (47.0 → 59.2 fps). 산술은 맞다.

**정정**: CPU 빌드는 프레임의 33% 가 아니라 **20.6%** 다(33% 는 draw 대비).

**비용**: §5 의 drain 스물 남짓, 그중 **하나는 원리적으로 불가능**(직접 VRAM
매핑). §6 의 커서는 **하드웨어 커서 구현이 선행 조건**. §8 의 완료 주체 부재는
**해결 없이는 설계가 성립하지 않는다.** §7 의 오류 귀속 여덟 갈래.

**그리고 이 설계가 바꾸는 것이 정확히 §3-62 가 못 닫은 "완료 토폴로지" 다.**
일곱 번 언 기계에서, 미해결 후보 한복판을, 1.26 배를 위해.

### 판정: **Stage B 는 짓지 않는다.**

대신, 위험 순서대로:

1. **CPU 빌드 프로파일** (§13). 순수 호스트, 실기 위험 없음. **단, 계측이
   시저와 코드로 상호배타여야 한다** — "위험 없음" 이라고 쓴 1 판은 그 조건을
   빠뜨렸다.
2. **하드웨어 커서.** 그 자체로 옳고(CPU 가 프레임버퍼에 그리는 것을 없앤다),
   비동기의 선행 조건이며, **비동기를 안 하더라도 이득이다.**
3. 그다음에 비동기를 다시 본다 — **완료 주체(§8)에 대한 답을 들고.**

### 내가 틀렸던 것 — 다섯

1. **FETCHED 를 재사용 경계로 삼았다.** 반증이 **내 파일 안 주석**에 있었다.
2. **duty cycle 을 두 번 틀렸다.** 초안은 과장, "정정" 은 반대로 틀림.
3. **drain 을 절반만 셌고**, 하나는 잘못 셌다.
4. **"커서 완화책을 모른다"** — 하드웨어 커서가 있다.
5. **완료를 알아차릴 주체를 아예 생각하지 않았다.**
