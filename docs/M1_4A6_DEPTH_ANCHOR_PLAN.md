# §3-12 — 깊이는 어디에 걸려 있나 (계획, 2026-08-21)

색·알파는 끝났다(`M1_4A5_ATTRIB_FIX_PLAN.md` §8). 깊이는 **일부러 손대지
않았다** — 반 화소가 16 비트 코드로 여러 단계가 되고, 깊이 시험이 켜져
있으면 커버리지까지 흔들기 때문이다. 이제 깊이를 잰다.

## 0. 감사 결과 (먼저 확인함)

평면 원점을 계산하는 곳은 `OpenStepMGAMesaTriangle.c` 에 **셋뿐**이다:
알파(고침), 색(고침), 깊이(안 고침). 훅이 거는 것은 `TriangleFunc` 하나이고,
Mesa 의 `basic_quad` 가 `TriangleFunc` 를 두 번 부르므로 **사각형도 우리
경로**를 탄다(`quads.c:53`). 선·점은 소프트웨어로 간다.

## 1. 깊이에는 원인이 **셋** 있을 수 있다

색은 둘이었다. 깊이는 하나 더 붙는다:

| | 무엇 | 코드 |
|---|---|---|
| Z1 | **정점 z 를 자른다** | `(dst).z = (unsigned long)VB->Win.data[idx][2];` (훅) |
| Z2 | 평면을 화소 **모서리**에서 읽는다 | `ox = left - a->x; oy = y - a->y;` |
| Z3 | 고정소수점 출력을 **절단**한다 | `t->z0 = osmgaFixed(at)` (`osmgaStartFixed` 를 안 거친다) |

Z1 은 색에 없던 것이다. 색의 정점값은 `glColor4ub` 의 바이트라 이미 정수였다.
깊이의 정점값은 변환을 거친 **창 z** 라 소수부가 있고, 그것을 버린다.

## 2. 이상적 모델의 2×2 로는 부족하다 — **레지스터 프로그램을 그대로 흉내 낸다**

처음에 「정확한/자른 정점 z」 × 「모서리/중심」 의 2×2 를 세우려 했다.
**교차검토가 옳게 짚었다**: 색에서는 `hw = floor(정확한 평면)` 이 화소별
항등식으로 성립해 사슬 전체가 한 번에 검증됐지만, 깊이는 `z0`·`zdx`·`zdy`
가 **각각 따로** `osmgaFixed` 를 거친다. 그러면 모서리→중심 보정이
이상적 float 기울기로 계산한 값과 **더 이상 같지 않고**, 덧셈으로 분리되지도
않는다. 게다가 **Z1 은 절편만이 아니라 기울기까지 바꾼다** — 자른 정점으로
푼 평면은 계수가 통째로 다르다.

우리는 **소스를 가지고 있으므로 레지스터를 캡처할 필요가 없다.** python 이
빌더가 하는 일을 그대로 다시 한다:

```
정점 → (자르거나 안 자르고) 평면 해 → 클램프 → osmgaFixed → z0, zdx, zdy
예측 = (z0 + i*zdx + j*zdy) >> 15        화소마다
```

- 하드웨어가 **이 예측과 화소마다 맞으면**, 엔진은 우리가 준 것을 그대로
  칠하는 것이고 결함은 전부 **우리 산술**에 있다 — 그러면 무엇을 고칠지
  분명하다.
- **안 맞으면** 그것은 "세 번째 결함"이 아니라 **모델이 아직 불완전하다**는
  뜻이다. 교차검토의 이 구분을 기준에 적어 둔다.

그리고 「자른 정점 + 모서리」, 「정확한 정점 + 중심」 같은 조합은 이 흉내
안에서 **매개변수를 바꾸는 것**으로 얻는다. 별개의 모델이 아니다.

### 2-1. x·y 도 잘린다 — 오염을 막는다

훅은 `x`·`y` 도 같은 캐스트로 자른다. 그러면 **평면 자체가 달라져** Z1 을
따로 볼 수 없다(교차검토 지적). 그래서 **창 좌표가 정수인 정점만 쓴다** —
색에서 쓴 것과 같은 방식이고, 그러면 x·y 절단이 항등이 된다.

## 3. 대조군 둘 — 각각 원인 하나를 지운다

색에서 파랑이 한 일을 깊이에서도 시킨다.

- **대조 A (Z2 를 지운다)**: `dz/dx + dz/dy = 0` 인 삼각형. 정착은 이런
  평면을 움직일 수 없다. 교차검토가 "**인코딩된** 기울기가 상쇄해야 의미가
  있다"고 짚어서 확인했다 — `osmgaFixed` 는 부호에 대칭이라
  (`s>=0 ? s+0.5 : s-0.5`) `osmgaFixed(d) + osmgaFixed(-d) = 0` 이
  19999 개 값에서 예외 없이 성립한다. **대조군은 성립한다.**
- **대조 B (Z1 을 지운다)**: 창 z 가 **정확히 정수**가 되는 정점. 자를
  소수부가 없다. 다만 교차검토가 옳게 지적했듯 **16 비트 읽기로는 이것을
  확인할 수 없다** — 같은 양자화 칸 안의 어떤 값이든 같은 코드를 낸다.
  그러므로 대조 B 의 타당성은 §4 의 보정에 **전적으로 기댄다.** 보정이
  §4-4 를 통과하지 못하면 대조 B 를 쓰지 않는다.

둘을 따로, 그리고 둘 다 만족하는 것도 하나 만든다.

## 4. 창 z 를 안다고 가정하지 않는다 — **보정한다**

`VB->Win.data[i][2]` 는 내부 값이다. 유도해서 쓰면 유도가 틀렸을 때
결론이 통째로 틀린다. 그래서 **먼저 잰다**:

**투영은 `glOrtho` 다.** 창 z 는 NDC z 에 대해 아핀이지 시점 z 에 대해서는
아니므로, 원근을 쓰면 이 보정이 성립하지 않는다(교차검토). 직교로 고정하고
그 사실을 여기 적어 둔다.

1. 물체 z 를 여러 값으로 두고 **평평한**(기울기 0) 삼각형을 소프트웨어로
   그린다. 표본은 0·0.5·1 부근과 **예측되는 16 비트 코드 경계 바로
   아래위**를 포함한다 — 평평한 도형은 값이 아니라 **양자화 칸**만 알려주므로,
   칸 한가운데만 재면 비아핀도 아핀처럼 보인다(교차검토).
2. 깊이 버퍼를 읽어 물체 z → 깊이 코드 대응을 **측정**한다.
3. python 이 그 대응이 아핀인지 확인하고 계수를 뽑는다.
4. 그 계수로 세운 평면이 **소프트웨어의 기울어진 삼각형과 화소마다 맞는지**
   확인한다. 맞아야 신탁으로 쓴다. 안 맞으면 거기서 멈춘다.

색에서 소프트웨어가 중심 모델과 맞은 것이 신탁을 뒷받침했듯이.

## 5. 재는 조건

- `glDepthFunc(GL_ALWAYS)`, `glDepthMask(GL_TRUE)`, `glClearDepth` 로 미리
  칠하고, **깊이 시험이 커버리지를 흔들지 않게** 한다.
- `OSMesaGetDepthBuffer` 로 16 비트 버퍼를 직접 읽는다 (`bpv == 2` 단정).
- 두 경로가 **같은 깊이 버퍼**를 쓰는지 먼저 확인한다
  (`OSMGAMesaBufferDepthOrigin() != 0`). 아니면 비교가 성립하지 않는다.
- 커버리지를 먼저 확인하고 **양쪽이 덮은 화소만** 비교한다.
- 순수 하드웨어 실행임을 단정한다(`software = declined = unsupported = 0`).

## 6. 성공/실패 기준 (숫자를 미리 적는다)

- **소프트웨어**는 「정확한 정점 z + 중심」모델과 맞아야 한다. 아니면 §4 의
  보정이 틀린 것이고 멈춘다.
- **하드웨어(지금)**: 「자른 정점 z + 모서리」가 맞을 것으로 본다.
  각 효과의 크기를 따로 보고한다.
- **대조 A** 에서 정착 성분이 0 이어야 한다. 움직이면 정착이 아니다.
- **대조 B** 에서 Z1 성분이 0 이어야 한다.
- **결함으로 볼 것**: 흉내와 하드웨어가 화소마다 맞는데도 **규칙**에서
  벗어남 — 그러면 고칠 곳이 우리 산술이고 어디인지도 안다.
- **결함이 아니라 「모델 미완성」으로 볼 것**: 흉내가 하드웨어와 안 맞음,
  잔차가 `left(row)` 를 따라 계단을 만듦, 두 사다리꼴 절편이 다름.
  교차검토가 옳다 — 이것들은 아직 안 세운 양자화 단계의 증거이지
  드라이버 결함이라고 단정할 것이 아니다. **그때는 모델을 마저 세운다.**
- 커버리지의 **대칭차를 따로 보고한다**. "양쪽이 덮은 화소만" 은 비교
  규칙일 뿐이고, 덮임이 갈리는 것 자체가 봐야 할 증거다.

## 7. 이 회차에 고치지 않는다

색에서 A 와 B 를 따로 해서 값을 봤다. 깊이는 원인이 **셋**일 수 있으니
더욱이 재고 나서, 하나씩 고친다. **Z1 은 훅에 있고 x·y 절단(§3-12 의
나머지 절반)과 같은 줄**이므로, 고칠 때 그 둘의 관계를 먼저 정리해야 한다.

## 8. 안 보는 것

- 깊이 **시험**의 동률 동작(`GL_LEQUAL` 경계). 값이 맞은 뒤에 볼 일이다.
- polygon offset. 아직 경로가 없다.
- 스텐실. 없다.

## 9. 결과 (2026-08-21) — 세 원인 모두 확인, 크기는 천 배 차이

### 9-1. 보정 (§4 의 관문)

401 개 표본으로 물체 z → 깊이 코드를 쟀다:

```
   code == round(32767.5 * (1 - z_obj))   :  401 / 401 일치
   끝점을 잇는 직선에서 최대 편차 0.50 코드 (= 양자화 그 자체)
```

그리고 **기울어진 삼각형에서 소프트웨어를 화소마다 예측한다**:
도형 2 는 **681/681**, 도형 1 은 696 중 7 개만 다른데 그 7 개는 정확한 값이
전부 `x.502` 근처 — Mesa 의 11 비트 고정소수점이 동률에서 다르게 반올림한
것이다. **보정을 신탁으로 쓴다.**

### 9-2. 흉내가 하드웨어를 정확히 재현한다

레지스터 프로그램을 python 으로 그대로 다시 했다:

| 정점 z | 표본점 | 도형 1 | 도형 2 |
|---|---|---|---|
| 정확 | 모서리 | 420/704 | 398/703 |
| 정확 | 중심 | 0/704 | 0/703 |
| **자름** | **모서리** | **704/704** | **703/703** |
| 자름 | 중심 | 0/704 | 0/703 |

**엔진은 우리가 준 것을 그대로 칠한다.** 그러므로 결함은 전부 우리
산술이고, 교차검토가 경고한 "모델 미완성" 은 해당하지 않는다 — 모델이
완성됐다.

### 9-3. 세 원인의 크기 (16 비트 깊이 코드)

| | Z2 정착 | Z1 정점 절단 | Z3 출력 절단 |
|---|---|---|---|
| 도형 1 | **+2662.36** | −0.42 | −0.50 |
| 도형 2 | **−2612.89** | −0.44 | −0.50 |

삼각형 자신이 40000 코드를 걸친다. **정착 하나가 그 6.5%, 깊이 범위 전체의
4%** 다. 나머지 둘은 **한 코드 미만**이다.

즉 깊이에서 실제로 문제인 것은 **Z2 하나**이고, 그것은 색·알파에 이미 적용한
바로 그 한 줄이다. Z1·Z3 은 반 코드짜리라 급하지 않다.

### 9-4. 계획이 틀렸던 곳 — `GL_ALWAYS`

커버리지를 깊이에서 떼어내려고 `glDepthFunc(GL_ALWAYS)` 를 골랐는데,
**백엔드 선택자는 `GL_LESS` 만 받는다**(`OpenStepMGAMesaHook.c:377`).
그래서 첫 실행은 가속을 켜 놓고도 `drawn=0` 이었다 — 측정 조건을 깨끗하게
만들려던 선택이 **측정 대상을 꺼버린 것**이다.

`GL_LESS` + 깊이를 far 로 클리어하면 아무것도 거절되지 않아 같은 효과가
나고, 분석이 **far 값에 닿은 화소가 없음을 단정**한다(둘 다 없음).

"순수 하드웨어 실행임을 단정한다"는 기준이 이걸 잡았다.

### 9-5. 대조군은 쓰지 않았다

계획은 대조군 둘(기울기 상쇄, 정수 창 z)을 준비했지만, **흉내가 화소마다
정확해서 필요가 없어졌다** — 매개변수를 켜고 끄는 것이 대조군보다 깨끗하게
원인을 가른다. 대조군은 나중에 회귀 시험으로 남길 수 있다.

## 10. 다음 — 고치기 (별도 계획·교차검토)

Z2 만 먼저. 색·알파와 같은 한 줄이고, 예측은 위 표의 +2662/−2613 이 0 으로
가는 것이다. **깊이 시험이 켜진 채 커버리지가 안 변하는지**를 같이 봐야 한다.
