# M1-4 B7 — 한 화소보다 좁은 삼각형

2026-08-22.  **유저랜드만 바뀐다. 재부팅 불필요.**

## 1. 무엇이 잘못됐나 (측정)

`test/openstep-mga-mesa-sliver-test.c` 는 폭이 다른 슬리버를 같은 자리에 그린다.
고치기 전:

| 폭 | 하드웨어가 칠한 화소 | 소프트웨어 | 계기 |
|---|---|---|---|
| 0.25 | **0** | 25 | drawn=0 software=0 unsupported=0 |
| 0.50 | **0** | 51 | 〃 |
| 0.75 | **0** | 34 | 〃 |
| 0.90 | **0** | 27 | 〃 |
| 1.50 | 40 | 41 | drawn=1 |
| 4.00 | 120 | 120 | drawn=1 |

**1 화소보다 좁은 삼각형이 통째로 사라졌다.**  카운터에도 안 잡히고
소프트웨어로도 안 갔다.

원인은 `OpenStepMGAMesaTriangle.c:676` 이다.  변의 좌우를 정하는 외적을
**whole pixel 로 줄여서** 낸다:

```c
cross = ((lo->x - t->x) / OSMGA_MESA_SUBONE) * ((m->y - t->y) / OSMGA_MESA_SUBONE)
      - ((lo->y - t->y) / OSMGA_MESA_SUBONE) * ((m->x - t->x) / OSMGA_MESA_SUBONE);
if (cross == 0L)
    return 0;                 /* <- "그릴 것 없음" 으로 답했다 */
```

줄인 이유는 주석에 있다: 1/256 단위로 곱하면 32비트를 넘는다(측정된 예:
2,490,957,824).  그건 사실이다.  틀린 것은 **넘침을 피하려고 정밀도를 버린
것**과, 버린 결과인 `cross == 0` 을 *넓이 없음*과 같은 답으로 쓴 것이다.
훅은 `n == 0` 을 "그릴 것 없음"으로 받아 소프트웨어로도 안 넘긴다.

## 2. 응급 처치는 이미 했다

`cross == 0` 을 `OSMGA_MESA_TRI_UNSUPPORTED` 로 바꿨다.  넓이가 있는지는
**그 위에서 이미 정확히**(double 로) 검사하므로, 여기 도달했다는 것은
"넓이는 있는데 이 반올림으로는 좌우를 못 가린다"는 뜻이고, 그건 이 함수가
가진 다른 답이다.  측정하니 네 슬리버가 소프트웨어로 넘어가 25/51/34/27 을
그린다.

**하지만 그건 되돌림이지 해결이 아니다.**  오라클과 대면 소프트웨어는
그 폭들에서 24/48/32/27 대신 25/51/34/27 을 칠한다 — 자기 규칙만큼 어긋난다.
하드웨어는 그릴 수 있으면 정확하다(폭 1.5 에서 오라클 40, 하드웨어 40,
소프트웨어 41).

## 3. 제대로 된 답 — double 로 정확히 낸다

곱이 32비트를 넘는 것은 맞지만, **double 은 넘지 않는다.**  계산했다:

```
좌표 한계 8192 px -> 1/256 단위로 2^21
차의 최대 2^22,  곱의 최대 2^44,  두 곱의 차까지 2^45
signed long 한계 2^31  -> 넘는다
double 이 정수를 정확히 담는 한계 2^53  -> 2^45 는 한참 안쪽
```

그러므로 **1/256 단위 그대로 double 로 외적을 내면 잘림이 없고 부호가 정확하다.**
좌표가 ±8192 px 안이라는 것은 `osmgaCoordOK` 가 이 지점보다 먼저 보장한다.

이 파일은 이미 같은 기법을 쓴다: 넓이 0 검사(`:539`)가 double 로 나눈 뒤
곱한다.  둘째 외적만 정수로 남아 있었다.

**Mesa 자신도 그렇게 한다.**  `tritemp.h:148` 이
`area = eMaj.dx * eBot.dy - eBot.dx * eMaj.dy` 를 부동소수로 내고
`:294` 가 `ltor = (oneOverArea < 0.0F)` 로 좌우를 정한다.  우리만 정수로
줄이고 있었다.

## 4. 바꾸는 것

* `long cross` → `double crossD`, 1/256 차를 그대로 곱해서.
* 쓰이는 곳은 **부호뿐**이다 — `:732, :733, :749, :750` 의 `cross < 0L`.
  `crossD < 0.0` 으로 바꾼다.
* `crossD == 0.0` 은 **닿을 수 없다**: 넓이 0 은 `:539` 가 이미 걸렀고
  공선성은 정점 순서와 무관하다.  그래도 방어로 남기되 `UNSUPPORTED` 를
  돌려준다(0 이 아니라).
* §2 의 응급 처치는 그대로 둔다 — 닿지 않게 되지만, 닿으면 옳은 답이다.

## 5. 이 변경이 없애는 것

주석이 적어둔 다른 위험도 같이 사라진다:

> *"one classified the wrong way comes out with its span inverted, which the
> kernel refuses and the software path then draws correctly."*

**부호가 정확해지면 이 원인으로 잘못 분류되는 삼각형이 없다.**  커널이
거절하고 소프트웨어가 다시 그리는 일이 **이 원인으로는** 없어진다 —
검증기의 다른 거절까지 사라지는 것은 아니다.

## 6. 어떻게 증명하는가

1. **슬리버 시험** — 여섯 폭 전부 하드웨어가 그리고(`unsupported=0`),
   화소 수가 **오라클과 같다**(24/48/32/27/40/120).  지금은 소프트웨어
   숫자(25/51/34/27)를 물려받고 있으므로, 이 값이 바뀌는 것이 곧 증거다.
2. **사다리꼴 불변식** — 410 삼각형 98640 행.  다만 이 시험의 정점은
   `v->x = x * OSMGA_MESA_SUBONE` 로 만들어져 **전부 whole pixel 격자 위**다
   (`test-mesa-trapezoid.c:186-190`).  그러니 이 시험은 소수 좌표의 외적을
   **전혀 밟지 않는다** — 회귀는 잡지만 이 변경을 가르지는 못한다.
   가르는 것은 1번이다.
3. **커버리지·이음매·메시** — 기존 시험이 그대로 통과해야 한다.
4. **일부러 틀린 빌드** — `crossD` 의 부호를 뒤집으면 시험이 **반드시**
   실패해야 한다.  통과하면 부호를 아무도 안 보고 있는 것이다.

## 7. 안 하는 것

* 오버플로 때문에 정수로 줄인 다른 곳은 건드리지 않는다.  여기만 부호가
  필요하고 여기만 double 로 충분하다는 것을 계산했다.
* 소프트웨어의 커버리지 차이는 고치지 않는다.  그건 Mesa 의 규칙이다.

## 8. 결과 (2026-08-22)

### 8-1 슬리버가 하드웨어로 돌아왔고, 규칙과 정확히 맞는다

```
# cancellation probe: determinant 1.0 (want 1.0)
# width winding painted drawn software unsupported
0.25 fwd  22  1 0 0        0.25 rev  22  1 0 0
0.50 fwd  49  1 0 0        0.50 rev  49  1 0 0
0.75 fwd  33  1 0 0        0.75 rev  33  1 0 0
0.90 fwd  27  1 0 0        0.90 rev  27  1 0 0
1.50 fwd  40  1 0 0        1.50 rev  40  1 0 0
4.00 fwd 120  1 0 0        4.00 rev 120  1 0 0
```

**열두 경우 전부 `drawn=1`** — 되돌림이 하나도 없다.  그리고 **양쪽 감김이
같은 값**을 준다: 분류가 정점 순서에 안 흔들린다.

### 8-2 오라클과의 차이는 전부 정밀도 예산이다

이상적인 1/256 오라클은 24/48/32/27/40/120 인데 실측은 22/49/33/27/40/120 이다.
남는 −2/+1/+1 을 설명해야 한다.  빌더는 삼각형마다 실을 수 있는 서브픽셀
정밀도 `sub` 를 고르는데, 이 슬리버들(높이 60)에서는 `sub = 7`, 즉 **1/128
격자**다.  그 격자로 꼭짓점을 양자화한 뒤 오라클을 다시 평가하면:

| 폭 | 1/256 오라클 | **1/128 오라클** | 실측 |
|---|---|---|---|
| 0.25 | 24 | **22** | 22 |
| 0.50 | 48 | **49** | 49 |
| 0.75 | 32 | **33** | 33 |
| 0.90 | 27 | **27** | 27 |
| 1.50 | 40 | **40** | 40 |
| 4.00 | 120 | **120** | 120 |

**여섯 개 전부 일치한다.**  설명되지 않는 화소가 하나도 없다.  하드웨어는
자기가 실을 수 있는 정밀도에서 규칙과 정확하고, 남은 차이는 커널의 변 예산이
정하는 것이지 이 코드의 결함이 아니다.

### 8-3 부호를 아무도 안 보고 있지는 않다 (변이 시험)

`crossD < 0.0` 을 `> 0.0` 으로 뒤집어 빌드하니:

* 사다리꼴 불변식: *"the builder does NOT cover the rule, or the kernel refuses it"*
* 슬리버 시험: 열두 경우 전부 **0 화소**

두 시험 모두 부호를 실제로 관측하고 있다.  되돌려서 다시 통과시켰다.
