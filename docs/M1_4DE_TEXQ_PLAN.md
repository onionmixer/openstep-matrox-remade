# M1-4DE — `glTexCoord4f` 의 `q ≠ 1`

## 1. 지금은 소프트웨어로 간다

```c
    if (VB->TexCoordPtr[0]->size > 3 &&
        (data[v0][3] != 1.0F || data[v1][3] != 1.0F || data[v2][3] != 1.0F)) {
        hookTexPersp++;
        (void)osmgaMesaSoftly(...);
        return;
    }
```

`OpenStepMGAMesaHook.c`.  투영 텍스처(그림자 맵, 슬라이드 프로젝터, 반사)는
전부 여기서 걸린다.  그리고 **텍스처 행렬**이 투영이면 응용이
`glTexCoord2f` 만 써도 여기 걸린다 — 이 검사가 보는 것은 행렬을 지난 뒤의
`TexCoordPtr` 이기 때문이다 (`stages.c:511`).

## 2. 엔진은 이미 할 수 있다 — 기계가 같다

GL 이 프래그먼트에 주는 좌표는 `s/q` 다.  화면에서 **선형인 것**은 `s/w` 와
`q/w` 이고, 그 비가 `s/q` 다.

엔진은 `TEXTURE_TRAP` 에서 정확히 두 평면의 비를 계산한다:

```
   u = (TMR6 + TMR0·dx + TMR1·dy) / (TMR8 + TMR4·dx + TMR5·dy)
```

지금 드라이버는 분자에 `s·(1/w)`, 분모에 `(1/w)` 를 넣어 원근 보정을 시킨다
(`osmgaPerspPlanes`, `qa = a->qw`, `na = ua·qa`).  Mesa 의
`Win.data[i][3]` 은 `1/w` 다 — `Mesa-3.4.2/src/xform.c:169` 의
`vProj[i][3] = oow` 로 확인했다.

그러니 `q ≠ 1` 은 **분모를 `q·(1/w)` 로 바꾸는 것**이 전부다.  분자는 그대로
`s·(1/w)` 이고, 비는 `s/q` 가 된다.

**커널은 손대지 않는다.**  분모 평면은 이미 임의이고 `[Q_MIN, Q_MAX]` 로
묶여 있으며, λ 축척이 이미 그 안에 맞춘다.

## 3. 그러면 무엇을 고쳐야 하나

| 자리 | 지금 | 바뀔 것 |
|---|---|---|
| 정점 | `qw = 1/w` | `tq` (텍스처 q) 를 함께 싣는다 |
| 아핀 지름길 | `a->qw == b->qw == c->qw` | **`tq` 도 같아야 한다** |
| `osmgaPerspPlanes` | `qa = a->qw`, `na = ua·qa` | 분자와 분모를 **따로** — §3-0 |
| 범위 사전검사 | `s·2^20` 을 `COORD_MAX` 와 | **`(s/q)·2^20`** 을 |
| 관문 | `q ≠ 1` 이면 거절 | `q ≤ 0` 이면 거절 |

### 3-0 분자와 분모를 갈라야 한다 — 위 표의 첫 판이 틀렸다

`qa` 하나만 `qw·tq` 로 바꾸면 안 된다.  `na = ua · qa` 이므로 분자도 같이
곱해지고,

```
   na / qa = (s·qw·tq) / (qw·tq) = s        <- s/q 가 아니라 s
```

가 된다.  `q` 가 통째로 약분돼 **아무 일도 일어나지 않는다** — 그런데 아핀
지름길은 이미 우회했으므로, 결과는 "느려지고 똑같은 그림"이 아니라
"원근 경로로 돌면서 q 를 무시한 그림"이다.

필요한 것은:

```
   분자    ua · qw            (그대로)
   분모    qw · tq            (혼자 바뀐다)
   비      ua / tq = s/q
```

즉 `osmgaPerspPlanes` 에 분모용 값을 **따로** 들여야 한다.  Mesa 소프트웨어가
그렇게 한다 — `tritemp.h:813` 이 분자를 `s·invW` 로, `821` 이 분모를
`q·invW` 로 만들고, `size <= 3` 이면 분모가 그냥 `invW` 다.

### 3-1 아핀 지름길이 왜 `tq` 도 봐야 하나

`w` 가 셋 다 같아도 `q` 가 다르면 `s/q` 는 화면에서 **선형이 아니다** — 두
선형 함수의 비다.  지금 조건은 `w` 만 보므로, `q` 가 다른데 `w` 가 같은
삼각형을 아핀으로 풀어 **틀린 그림**을 그린다.  이건 관문을 여는 순간
생기는 결함이므로 같이 고쳐야 한다.

### 3-2 범위 사전검사가 왜 틀리나

지금 검사는 `ua = s·2^20` 을 `[-SPAN, COORD_MAX]` 에 넣는다.  `q ≠ 1` 이면
**좌표는 `s/q`** 이고 `s` 가 아니다.  `q = 4` 이면 `s = 8` 이 좌표 2 를
뜻하는데 검사는 8 을 보고 거절한다(혹은 `q = 1/4` 이면 반대로 통과시킨다).
좌표로 검사해야 한다.

## 4. `q ≤ 0` 은 거절한다

`w ≤ 0` 을 거절하는 것과 같은 이유다 — 삼각형 안에서 분모가 0 을 지나면
좌표가 발산하고, 그건 보간할 것이 아니라 특이점이다.  `qlo <= 0.0` 검사가
이미 `osmgaPerspPlanes` 에 있으니 `q·(1/w)` 에 대해 그대로 작동한다.

부호가 섞이는 경우도 그 검사가 잡는다.

## 5. 어떻게 재나

블렌드 장면에서 쓴 구조를 그대로 쓴다 — **하드웨어와 소프트웨어를 각각 자기
산술로** 채점한다.  다만 여기서는 오라클이 블렌드가 아니라 **좌표**다:

1. `q` 를 정점마다 다르게 준 사각형을 그린다.  텍셀이 자기 이름을 담으므로,
   각 화소가 **어느 텍셀을 골랐는지** 그대로 읽힌다
2. python 이 `s/q` 를 정확히 풀고, 표본점(화소 중심)과 잘림 규칙으로 어느
   텍셀이어야 하는지 계산한다 — 이건 이미 §51 계열이 확립한 규칙이다
3. 하드웨어·소프트웨어·python 셋을 비교한다.  소프트웨어가 python 과 맞아야
   python 이 옳다는 것이 서고, 그 다음에 하드웨어를 본다

### 5-1 공허하지 않게

- `q` 가 세 정점에서 **모두 달라야** 한다.  둘만 다르면 한 변에서 상수다
- `q` 가 1 을 포함하면 안 된다 — 포함하면 그 정점 근처는 옛 경로와 같다
- `q` 범위가 좁으면 `s/q` 가 `s` 와 비슷해져서 아무것도 안 가른다.  넓게
- **아핀 지름길이 실제로 안 타는지** 확인한다.  `w` 를 셋 다 같게 두고 `q` 만
  다르게 준 삼각형이 §3-1 의 경우이고, 그게 이 계획이 고치는 결함이다

## 6. 교차검토에 물을 것

- §2 의 "분모를 `q·(1/w)` 로" 가 정말 GL 을 주는가.  Mesa 소프트웨어가
  실제로 무엇을 계산하는지로 확인해 달라
- λ 축척(`lamLo`/`lamHi`)이 `q` 가 들어오면 깨지는 곳이 있나 — 분모가 이제
  `q/w` 라 범위가 넓어진다
- §3-2 의 범위검사 수정이 놓치는 경우
- `q` 가 아주 크거나 아주 작을 때 `Q_MIN`/`Q_MAX` 에 부딪히는 방식
- 이 변경이 `q = 1` 인 기존 경로를 **비트 단위로** 그대로 두는가

## 8. 됐다

```
   texq   drawn 2  software 0  texpersp 0     엔진에서 돈다
   texq   하드웨어 대 소프트웨어   3 화소       (persp 6, perspfar 9 와 같은 급)
   texq   대 q=1 대조군        15873 화소       공허하지 않다

   q with a perspective projection too            ok

   a q ratio it cannot, which must fall back      ok
```

세 화소는 전부 **t 축에서 한 텍셀 위**이고 `u` 는 정확히 일치한다 — 잔차가
음수가 되지 않는다는 설계 그대로이고, 기존 원근 기준값들과 같은 성격이다.

## 9. 가는 길에 걸린 것

### 9-1 계획이 틀렸다 (codex 가 잡았다)

`qa` 하나만 `qw·tq` 로 바꾸면 `na = ua·qa` 때문에 분자도 같이 곱해져
`q` 가 통째로 약분된다.  분자와 분모를 갈라야 한다 — §3-0.

### 9-2 시험이 두 번 공허했다

1. **텍스처가 꺼져 있었다.**  q 자기시험 구간에서 `glEnable(GL_TEXTURE_2D)`
   를 안 했다.  훅은 텍스처가 없으면 `tq` 를 1 로 강제하므로, 세 경우가 전부
   "통과"하면서 아무것도 묻지 않았다.  솔버 계측을 붙여서야 드러났다 —
   `tri qw 1 1 1  tq 1 1 1`
2. **정점을 memset 한 시험들**은 `tq = 0` 이 되어 0 으로 나누고, `nan` 은
   모든 비교에서 거짓이라 범위 검사가 **공허하게 통과**한다.  생성자들이 1 을
   넣게 고쳤고, 빌더도 `!(tq > 0)` 이면 거절한다

### 9-3 한계가 1024 가 아니다

codex 는 분모의 동적 범위 `Q_MAX/Q_MIN = 1024` 를 한계로 들었고 나도 그렇게
시험을 짰다.  512 를 "여유 있게 안쪽"으로 골랐는데 **거절됐고, 거절이
옳았다.**

λ 는 분모의 바닥과 분자의 천장을 **동시에** 만족해야 하고, 분자는 좌표 곱하기
q 를 싣는다.  좌표가 텍스처 `C` 장을 덮으면

```
   qhi/qlo  <=  COORD_MAX · Q_ONE / (Q_MIN · C · SPAN)
```

python: `C = 1/4` 이면 256, `C = 1` 이면 **64**, `C = 2` 면 32.  1024 는 분모
혼자의 범위일 뿐 결합 제약이 아니다.  시험은 16(안쪽)과 256(바깥)으로 고쳤다.
