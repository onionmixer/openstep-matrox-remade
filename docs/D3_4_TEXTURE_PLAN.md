# D3-4 — 텍스처 매핑

기준일: 2026-08-19
상태: 계획. **codex 교차검토 1회 완료(2026-08-19)** 후 개정판 — §1-4~1-6, §4.
선행: D3-0/1/2 완료(색 보간·기울어진 변). D3-3(Z)은 **진행 중이며 이 계획의
전제가 아니다** — 텍스처와 깊이는 서로 독립이다.

## 0. 왜 이 단계는 D3-3보다 상황이 좋은가

D3-3(깊이)이 막힌 이유는 `atype ZI`에 **선례가 없어서**였다. `MGADWG_ZI`
(`mga_reg.h:168`), `MGA_ATYPE_ZI`(`mga_drv.h:427`), `DC_atype_zi`
(`mgareg_flags.h:248`) 셋 다 정의만 있고 사용 0건이며, DDX의 ROP→atype 표
(`mga_storm.c:1024-1045`)에도 없다.

**텍스처는 정반대다. 동작하는 구현이 둘 있다.**

| 구현 | 파일 | 성격 |
| --- | --- | --- |
| EXA Composite | `mga_exa.c:395-436`, `:520-604` | 2D 가속. 텍스처 사각형 |
| Xv 오버레이 | `mga_video.c:806-833` | 비디오 스케일링 |

### 0-1. 그리고 **WARP가 없다**

이것이 이 단계의 핵심 소견이다. `mga_exa.c`에서 `WIADDR`/`WARP`/`WVRTXSZ`/
`WACCEPTSEQ`/`WMISC` 검색 결과가 **0건**이다. EXA는 DRI 없이 동작하는 순수
2D 경로이고, 그 경로가 텍스처 유닛을 쓴다.

→ **텍스처는 WARP 없이 동작한다는 것이 우리 추정이 아니라 출하 코드의 사실
이다.** 경로 B(직접 래스터화)에 텍스처가 붙는다는 근거가 D3-0~2의 어떤
근거보다 강하다.

## 1. 확인된 사실

### 1-1. DWGCTL은 우리가 이미 돌리는 값에서 **1비트 차이**다

```c
/* mga_exa.c:520-522 */
cmd = MGADWG_TEXTURE_TRAP | MGADWG_I | 0x000c0000 |
      MGADWG_SHIFTZERO | MGADWG_SGNZERO | MGADWG_ARZERO;
```

= `0x06 | 0x70 | 0x000c0000 | 0x4000 | 0x2000 | 0x1000` = **`0x000C7076`**

우리의 실증된 Gouraud 값은 **`0x000C7074`**(`MGA_DWGCTL_GOURAUD`)다.
**opcode만 `TRAP`(4) → `TEXTURE_TRAP`(6)으로 바뀐다.** atype은 그대로 `I`,
`SOLID`는 그대로 꺼져 있다.

기울어진 변을 쓰려면 D3-2와 같이 `ARZERO`/`SGNZERO`를 지운다
(`MGA_DWGCTL_SLOPED`). 첫 시험은 축 정렬 사각형이므로 그대로 둔다.

### 1-2. 필요한 레지스터가 전부 group1이다 → DMA로 보낼 수 있다

| 레지스터 | 주소 | 용도 |
| --- | --- | --- |
| `TMR0`~`TMR8` | 0x2c00~0x2c20 | 텍스처 좌표 3×3 행렬 |
| `TEXORG` | 0x2c24 | 텍스처 VRAM 바이트 오프셋 |
| `TEXWIDTH` | 0x2c28 | 폭 인코딩 |
| `TEXHEIGHT` | 0x2c2c | 높이 인코딩 |
| `TEXCTL` | 0x2c30 | 포맷·pitch·클램프 |
| `TEXCTL2` | 0x2c3c | 스테이지 제어 |
| `TEXFILTER` | 0x2c58 | 필터링 |
| `TDUALSTAGE0/1` | 0x2cf8/0x2cfc | 텍스처 결합기 |
| `ALPHACTRL` | 0x2c7c | 블렌딩 |

전부 `0x2c00`~`0x2cfc` 범위이므로 우리 DMA 인코더의 group1 규칙
(`((reg-0x2c00)>>2)|0x80`)에 그대로 들어간다. 최대 인덱스는 `TDUALSTAGE1`의
`0xbf`로 한 바이트에 맞는다. **인코더를 고칠 필요가 없다.**

### 1-3. 레시피 (EXA에서 그대로)

```
TEXWIDTH  = (w-1)<<18 | ((8 - log2w) & 63)<<9 | log2w        (mga_exa.c:430)
TEXHEIGHT = (h-1)<<18 | ((8 - log2h) & 63)<<9 | log2h        (mga_exa.c:431)
TEXCTL    = MGA_PITCHLIN(0x100) | ((pitch & 2047)<<9)
            | MGA_NOPERSPECTIVE(0x00200000) | MGA_TAKEY(0x02000000)
            | 포맷                                            (mga_exa.c:406)
TEXCTL2   = MGA_G400_TC2_MAGIC(0x8000) | MGA_TC2_CKSTRANSDIS(0x10)
TEXFILTER = MGA_FILTERALPHA(0x00100000) | (0x10<<21)
            | MGA_MAG_NRST(0) | MGA_MIN_NRST(0)              (mga_exa.c:408)
TEXORG    = 텍스처의 VRAM 바이트 오프셋                       (mga_exa.c:429)
```

포맷은 32bpp가 `MGA_TW32`(6)다(`mga_exa.c` `mgaGetTexFormat`의
`PICT_x8r8g8b8 → MGA_TW32`).

`MGA_CLAMPUV`(0x18000000)는 EXA가 **repeat이 아닐 때** 켠다. 우리도 켜되
**봉쇄 수단으로 삼지 않는다**(§1-6 2번, §4).

### 1-4. `TMR` 좌표 행렬 — **초안이 2^16배 틀렸다**

인자 순서와 레지스터 순서가 다르므로 함수 본문을 그대로 읽는다
(`mga_exa.c` `setTMIncrementsRegs`):

```c
setTMIncrementsRegs(pPix, X_incx, X_incy, X_init,
                          Y_incx, Y_incy, Y_init,
                          H_incx, H_incy, H_init,
                          mga_fx_width_size, mga_fx_height_size)
{
    int decalw = mga_fx_width_size - 16;      /* <- 이 -16 */
    int decalh = mga_fx_height_size - 16;
    if (decalw >= 0) { X_incx <<= decalw; X_incy <<= decalw; X_init <<= decalw; }
    else { decalw = -decalw; X_incx >>= decalw; X_incy >>= decalw; X_init >>= decalw; }
    ... 같은 식으로 Y 계열에 decalh ...
    TMR0=X_incx  TMR1=Y_incx  TMR2=X_incy  TMR3=Y_incy
    TMR4=H_incx  TMR5=H_incy  TMR6=X_init  TMR7=Y_init  TMR8=H_init
}
```

호출자는 `mga_fx_width_size = 20 - src_w2`를 넘기고
(`mga_exa.c:650-651`, `:657-658`), `src_w2 = MGA_LOG2(width)`
(`mga_exa.c:610`)다. 따라서

```
decalw = (20 - log2w) - 16 = 4 - log2w
```

**64×64 텍스처면 `decalw = -2`, 즉 왼쪽이 아니라 오른쪽 시프트 2다.**

| | 값 |
| --- | --- |
| 이 문서 초안 | `TMR0 = 1<<30 = 0x40000000` |
| codex 교차검토 답 | `0x40000000` |
| **실제** | **`0x00004000`** |

**둘 다 틀렸고, 틀린 방식도 같다** — `- 16`을 빠뜨려 `decal = 20 - log2w`로
계산했다. codex는 `decalw = mga_fx_width_size - 16`을 **자기가 인용해
놓고** 그 다음 줄에서 `decal = 14`로 계산했다. **근거는 맞고 결론이
틀린 전형**이다.

내부 정합성 확인: `decal = 4 - log2w`면 텍셀 한 칸의 값은 `1 << (20-log2w)`
이고, 이는 "좌표의 소수부가 `20 - log2w` 비트"라는 뜻이다. 16×16 텍스처는
`decal = 0`이 되어 **16.16 고정소수점 그대로**가 된다 — 변환이 항등이 되는
크기가 정확히 하나 존재하고 그것이 16이라는 점이 계산을 뒷받침한다.

**64×64 항등 설정** (`srcx = srcy = 0`):

| 레지스터 | 값 | 유래 |
| --- | --- | --- |
| `TMR0` (X_incx) | `0x00004000` | `(1<<16) >> 2` |
| `TMR1` (Y_incx) | 0 | |
| `TMR2` (X_incy) | 0 | |
| `TMR3` (Y_incy) | `0x00004000` | `(1<<16) >> 2` |
| `TMR4` (H_incx) | 0 | |
| `TMR5` (H_incy) | 0 | |
| `TMR6` (X_init) | 0 | `srcx` decal 대상 |
| `TMR7` (Y_init) | 0 | `srcy` decal 대상 |
| `TMR8` (H_init) | `0x00010000` | **decal 대상 아님** |

`TMR8`이 decal을 받지 않는 것은 codex 지적이 맞았고 본문에서 확인했다
(H 계열은 두 시프트 블록 어디에도 없다).

일반식은 `1 텍셀 = 1 << (20 - log2(크기))`이며 드라이버는 이 식으로 짠다.

### 1-5. 나머지 레지스터 — 확인된 값

| 레지스터 | 값 | 근거 |
| --- | --- | --- |
| `TDUALSTAGE0` = `TDUALSTAGE1` | **`0x00000000`** | 색·알파 모두 "현재 텍스처"(`C_ARG1_CUR`=0, `A_ARG1_CUR`=0)를 `SEL_ARG1`(둘 다 0)로 고르면 0이다. `mga_reg.h:637`, `:650` |
| `ALPHACTRL` | **`0x00000101`** | `MGA_ALPHACHANNEL`(0x100) \| `MGA_SRC_ONE`(1) \| `MGA_DST_ZERO`(0) = 불투명 치환. `mga_reg.h:587`, `:596`, `:605` |
| `TEXTRANS`/`TEXTRANSHIGH` | **둘 다 `0x0000ffff`** | DRM이 텍스처 상태 emit마다 이 값을 쓴다. `mga_state.c:151-152`, `:196-197`, `:236-237` |

`ALPHACTRL`을 **반드시 쓴다.** EXA는 매번 쓰지만 단색·복사 경로는 안 쓰므로
(`mga_video.c:825`, `mga_storm.c:352-357`) BIOS나 이전 시험이 남긴 값이
그대로 남아 있을 수 있다. 우리 드라이버는 지금까지 한 번도 쓴 적이 없다.

`TEXTRANS`도 쓴다. EXA는 `MGA_TAKEY`를 켜면서 `TEXTRANS`를 안 쓰는데,
DRM은 항상 쓴다. **어느 쪽이 옳은지 소스로 못 가르므로 방어적으로 DRM
쪽을 따른다** — 비용이 두 워드다.

## 2. 단계

### D3-4a — 항등 매핑 사각형 하나

**"뭔가 그려졌다"로 끝내지 않는다. 어느 텍셀이 어디로 갔는지를 본다.**

1. 오프스크린에 **64×64 텍스처**를 CPU로 만든다. 텍셀 `(u,v)`의 값을
   `0x00 | (u<<16) | (v<<8)` 같은 **좌표를 되읽을 수 있는 패턴**으로 채운다.
2. 다른 오프스크린 블록에 `TEXTURE_TRAP | I`로 64×64 사각형을 그린다.
   `TMR`은 항등(§1-4), `DSTORG`는 색 블록.
3. 되읽어 **픽셀 `(x,y)`의 값이 텍셀 `(x,y)`의 값과 같은지** 센다.

**검증 방법**

- **V4a-1 (주 판정)**: 64×64 = 4096 픽셀 중 몇 개가 항등 매핑을
  만족하는가. 4096이면 좌표 변환까지 확정. **0이면 그리기 자체가 실패**이고
  D3-3a와 같은 상황이므로 격리 사다리로 간다.
- **V4a-2 (부분 실패 진단)**: 항등이 아니면 **실제로 어느 텍셀이 왔는지**를
  행 0과 열 0에서 보고한다. 일정한 배수/오프셋이면 `TMR` decal 시프트가
  틀린 것이고, 그 배수가 정답을 준다. **"안 맞음"으로 끝내지 않는다.**
- **V4a-3**: 텍스처 영역이 **변하지 않았음**을 확인한다(읽기 전용이어야
  한다). 변했다면 `TEXORG`와 `DSTORG`가 겹쳤거나 우리가 주소를 잘못 준
  것이다.
- **V4a-4 (봉쇄)**: 색 가드(그린 사각형 바깥 행·열)가 무변.
- **V4a-5**: 2D 회귀·화면 무변화.

### D3-4b — 확대/축소와 기울어진 변 (D3-4a PASS일 때만)

`TMR0`/`TMR3`를 2배·1/2배로 바꿔 스케일이 예상대로 나오는지, 그리고
`MGA_DWGCTL_SLOPED`로 `ARZERO`/`SGNZERO`를 지워 **삼각형에 텍스처가
붙는지** 본다. Mesa에 필요한 최소 집합은 여기까지다.

### D3-4c — 원근 보정 (범위 밖, 기록만)

`MGA_NOPERSPECTIVE`를 끄면 `TMR4`/`TMR5`/`TMR8`의 W 성분이 살아난다.
Mesa 3.4.2의 텍스처 품질에 영향을 주지만 **동작 여부와 무관**하므로 뒤로
미룬다.

## 3. 중단 조건

- 텍스처 영역이 변함 → 즉시 중단(V4a-3). 주소 계산이 틀린 것이다.
- 가드 오염 → 즉시 중단.
- 2D 회귀 또는 화면 이상.

## 4. 안전 — 텍스처는 **읽기만** 하므로 깊이보다 쉽다

전부 오프스크린이다. `TEXORG`(읽기)와 `DSTORG`(쓰기)를 **서로 다른 블록**에
두고 둘 다 실증 7 MiB 안에 넣는다. 겹치면 V4a-3이 잡는다.

**봉쇄 논리가 D3-3과 다르다.** 좌표 계산이 틀리면 텍스처 유닛이 **엉뚱한
VRAM을 읽지만, 쓰지는 않는다.** 이 단계에서 쓰기는 목적지 하나뿐이고 그것은
하드웨어 클립이 막는다 — 그 클립은 D3-2에서 실측으로 확인했다.

따라서 §1-6 2번(`MGA_CLAMPUV`가 주소 계산 전인지 후인지 모름)은 **이 단계의
안전을 좌우하지 않는다.** 켜두되 기대지 않는다. 최악은 잘못된 색이 나오는
것이지 VRAM 오염이 아니다.

D3-3a-1이 미해결로 남긴 **"깊이 쓰기가 하드웨어 클립을 지키는가"** 는 이
단계와 무관하다 — 여기서는 깊이를 쓰지 않는다(`atype I`, `ZI` 아님).

## 5. 이 계획이 결정하지 않은 것

- 텍스처를 VRAM 어디에 둘지의 상시 배치(지금은 시험용 고정 오프셋).
- Mesa의 텍스처 업로드 경로(시스템 RAM → VRAM). ILOAD를 쓸지 CPU 복사를
  쓸지는 별도 문제이며, CPU 복사가 이미 실증돼 있다(S4a).

## 6. D3-4a 결과 (2026-08-19) — **PASS, 항등 매핑 4096/4096**

```
drawn 4096, identity 4096 of 4096; texel step 4000; texture dirty 0, colour guard 0
row0 x=0,16,32,48,63 -> 40 100040 200040 300040 3f0040
col0 y=0,16,32,48,63 -> 40   1040   2040   3040   3f40
```

픽셀 `(x,y)`가 전부 텍셀 `(x,y)`를 받았다. 표본에서 행 0의 `u`가
0/0x10/0x20/0x30/0x3f로 `x`를 정확히 따르고, 열 0의 `v`가 `y`를 따른다.
**"뭔가 그려졌다"가 아니라 좌표 변환이 맞다는 것까지 확인됐다.**

텍스처 영역 무변(`texture dirty 0`) — `TEXORG`(6 MiB)와 `DSTORG`(4 MiB)가
겹치지 않았다. 색 가드 0.

### 6-1. `-16` 정정이 결정적이었다

`texel step 4000`으로 항등이 나왔다. §1-4에서 정정한 `decal = 4 - log2(폭)`
가 맞았다는 뜻이다. 초안과 codex가 공유했던 `0x40000000`이었다면 좌표가
2^16배로 튀어 아무것도 맞지 않았을 것이다.

**교차검토가 같은 실수를 했으므로 걸러진 것은 검토가 아니라 함수 본문을
직접 읽은 것이다.** 그리고 "16텍셀에서 decal이 0이 된다"는 정합성 확인이
부호를 확정했다.

### 6-2. §1-6의 미지수 처리

| # | 미지수 | 결과 |
| --- | --- | --- |
| 1 | `MGA_TAKEY`의 의미 | **영향 없음이 실측됨.** `TEXTRANS`/`TEXTRANSHIGH`를 DRM처럼 `0x0000ffff`로 채운 상태에서 항등이 나왔다. 의미는 여전히 미상이나 이 구성에서 무해하다 |
| 2 | `MGA_CLAMPUV`의 클램프 시점 | **미해결 유지.** 이번엔 텍스처 밖을 샘플하지 않았으므로 시험되지 않았다. D3-4b의 축소 시험이 처음으로 밖을 건드린다 |
| 3 | `DR4`~`DR15`가 결과에 섞이나 | **안 섞인다.** `DR`에는 D3-3c가 남긴 값(파랑 200 등)이 있었는데 결과가 순수 텍셀 값이다. `TDUALSTAGE0/1 = 0`이면 diffuse가 안 들어온다 |

3번은 부수 소득이다 — 이전 프로브가 남긴 `DR` 값이 그대로 있었던 것이
**오히려 대조군 역할**을 했다.

## 7. D3-4b — 스케일과 기울어진 변 (다음 단계)

Mesa에 필요한 최소 집합의 나머지다. **실증된 바탕에 한 번에 하나씩만
더한다** — D3-3a의 교훈이다.

| 밴드 | 바탕 | 더하는 것 | 무엇을 가른다 |
| --- | --- | --- | --- |
| A | D3-4a 항등 | **2배 확대** (`TMR0`/`TMR3` = `step*2`) | 스케일이 예상대로인가 |
| B | D3-4a 항등 | **1/2 축소** (`= step/2`) | 텍스처 **밖**을 처음 샘플한다 → §1-6 2번 |
| C | D3-4a 항등 | **기울어진 변** (`ARZERO`/`SGNZERO` 지움) | 삼각형에 텍스처가 붙는가 |
| D | D3-2 사다리꼴 | **기울어진 변 + 깊이** | `D3_3_DEPTH_PLAN.md` §8-3 |

### 검증 방법

- **V4b-A**: 픽셀 `x`가 텍셀 `2x`를 받는가(`x < 32`). `x ≥ 32`는 텍스처
  밖이므로 **클램프 여부가 여기서도 보인다**.
- **V4b-B**: 픽셀 `x`가 텍셀 `x/2`를 받는가. 64픽셀이 32텍셀을 덮으므로
  **밖을 샘플하지 않는다** — A와 B 중 밖을 건드리는 것은 A다. (초안에서
  A/B를 반대로 적었다가 계산해 보고 고쳤다.)
- **V4b-C**: D3-2가 실측한 변 걷기 규칙대로 삼각형 모양이 나오고, 그 안에서
  텍셀이 좌표를 따르는가.
- **V4b-D (봉쇄)**: **깊이 가드**. 기울어진 변에서 깊이 쓰기가 클립을
  지키는지는 아직 한 번도 확인되지 않았다(`D3_3_DEPTH_PLAN.md` §8-3).
- **V4b-E**: 색 가드·텍스처 무변·2D 회귀·화면 무변화.

### 중단 조건

- 텍스처 영역이 변함 → 즉시 중단.
- **깊이 가드 오염 → 즉시 중단.** 기울어진 변에서 깊이가 클립을 안 지키면
  깊이 봉쇄를 `ZORG` 배치만으로 다시 설계해야 한다.
- 색 가드 오염, 2D 회귀, 화면 이상.
