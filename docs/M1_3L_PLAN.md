# M1-3L — 새로 하드웨어 깊이를 타게 된 크기가 실제로 맞게 그리는가

`M1_3K_PLAN.md` §E 뒤에 온다. 아직 코드 없음.

## 1. 왜 필요한가

§3-20 을 고쳐 320x240, 333x222, 800x600 이 하드웨어 깊이를 받게 됐다.
**증명한 것은 할당과 원점뿐이다** — 그 크기에서 실제로 맞게 그리는지는 안
쟀다. 그리고 이 고침은 성능이 아니라 **어느 코드 경로가 도는지**를 바꿨다:
전에는 통째로 소프트웨어로 떨어지던 장면이 이제 하드웨어 깊이를 탄다.

`test/openstep-mga-mesa-depth-agree.c` 가 바로 그 질문을 위해 이미 있다.
같은 삼각형을 가속으로 한 번, 강제 소프트웨어로 한 번 그리고 깊이 버퍼를
두 번 떠서 비교한다. **크기가 `64x64` 로 박혀 있다.**

## 2. 무엇을 바꾸나

### (a) 크기를 인자로

`W`/`H` 를 `argv` 로 받고 배열을 `malloc` 으로 바꾼다. 삼각형은 창 좌표
`1.5..40.5` 에 고정돼 있으므로 64 이상이면 어느 크기에서도 같은 도형이
그려진다 — **비교 대상이 크기에 따라 달라지지 않는다.** 시험할 크기가 전부
64 보다 크다는 것은 python 으로 확인한다.

### (b) 섞어 그리는 패스 하나

지금은 가속 한 번, 소프트웨어 한 번을 **각각 깨끗한 버퍼에** 그린다. 섞이지
않는다. 세 번째 패스를 더한다:

1. `glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT)`
2. **소프트웨어로** 삼각형을 그린다 (scissor 로 거절시킨다)
3. **가속으로** 같은 삼각형을 그린다
4. 깊이 버퍼를 뜬다

`GL_LESS` 이므로, 두 경로가 같은 z 를 낸다면 두 번째 그리기는 **한 화소도
못 쓴다** — 같은 값은 `LESS` 를 통과하지 못한다. 그러니

> **3 번 패스가 2 번 패스와 다른 화소 수 = 하드웨어 z 가 소프트웨어 z 보다
> 작게 나온 화소 수**

이것은 예측이고, 앞의 두 패스에서 잰 발산과 대조할 수 있다. 섞었을 때의
위험을 **숫자 하나로** 준다.

### (c) 보고는 원시 수치로

기존 시험의 방침을 지킨다 — 원시 수치만 찍고, **유도는 python 에서** 한다.

## 2b. codex 교차검토 — 재검증 결과

**소스에서 확인해 받아들인 것**

1. **예측이 커버리지를 빼먹었다.** 하드웨어가 덮고 소프트웨어가 안 덮은
   화소에는 클리어값(65535)이 들어 있고, `hw_z < 65535` 이므로 그것도
   통과한다. 정확한 예측은

   ```
   섞은 뒤 바뀐 화소 = hw_only + count(hw_z < sw_z)
   ```

2. **반대 순서가 빠졌다.** SW→HW 는 하드웨어가 이기는 쪽만 본다. HW→SW 도
   재야 **순서 무관성**이라는 진짜 주장이 성립한다. 두 최종 버퍼는 모두
   두 단독 스냅샷의 **화소별 최솟값**과 같아야 한다.
3. **검사 영역이 좌하단 36x36 뿐이다.** python 으로 따졌다:
   800x600 에서 이 시험은 버퍼의 **0.27%** 만 본다(1296 / 480000). 그런데
   바뀐 것은 **깊이 할당의 원점과 크기**다 — 나쁜 원점이나 짧은 매핑이
   드러날 자리는 **먼 행**이고, 그곳을 한 번도 안 읽는다.
   → 같은 삼각형을 **먼 구석에도 한 번 더** 그리고 두 영역을 다 검사한다.
4. **경계 버그.** 행 진단이 `for (y = 1; y < 42; y++)` 로 무조건 돈다.
   41 행짜리 버퍼면 끝을 넘어 읽는다. 모든 루프를 런타임 `W`/`H` 로 묶는다.
5. **부호 있는 분류로 보고한다** — `hw_only`, `sw_only`, `hw<sw`, `같음`,
   `hw>sw`, `섞은 뒤 바뀜`. 절대값 히스토그램만으로는 예측을 못 검증한다.
6. **"바뀐 화소"는 깊이 워드가 바뀐 것**이지 색이 아니다. 두 삼각형이 다
   흰색이라 색은 통과해도 같을 수 있다.
7. **패스 3·4 에서도 가속 카운터를 본다.** 첫 패스가 가속됐다고 상태 전이
   뒤에 다시 가속을 잡았다는 보장이 없다.
8. **클리어 직후 클리어값 워드 수를 세어** 65535 라는 전제를 확인한다.
9. `glDepthMask(GL_TRUE)` 와 `glClearDepth(1.0)` 을 명시한다.

**내가 먼저 잡은 것**

- 섞기 패스의 수는 **한쪽만** 센다(하드웨어가 더 작은 절반). 1·2 패스의
  양쪽 발산과 **대조하는** 값이지 같은 것을 다시 재는 값이 아니다.
  codex 의 2 번(반대 순서)이 나머지 절반을 채운다.

**받아들이되 이번 회차에서는 안 하는 것**

- 41x41 최소 기하: 경계를 런타임으로 묶고 나면 안전하지만, 이번 회차의
  질문(새로 켜진 크기가 맞게 그리는가)과 다른 질문이다. **다음으로 미룬다.**
- 창 용량 한계 근처 크기: `1024x768` 이 이미 용량으로 깊이를 못 받는다는
  것을 알고 있고, 그 경계는 별도로 다룬다.

## 3. 재는 것

codex 말대로 **친숙한 해상도보다 페이지 패딩으로 고르는 편이 더
가른다** — 옛 버그의 방아쇠가 색 표면 뒤의 패딩이었기 때문이다.
python 으로 골랐다:

| 크기 | 색 바이트 | 패딩 | 왜 |
| --- | --- | --- | --- |
| 64x64 | 16384 | 0 | 이미 통과한 것 — 대조군 |
| 640x480 | 1228800 | 0 | 고침 전에도 하드웨어 — 회귀 확인 |
| 320x240 | 307200 | 4096 | 고침이 바꾼 것 |
| 800x600 | 1920000 | 5120 | 고침이 바꾼 것 |

| **369x111** | 163836 | **4** | 패딩이 0 바로 위 |
| **655x222** | 581640 | **8184** | 패딩이 한 페이지 바로 아래 |

마지막 두 개가 새로 더한 것이고, 패딩의 양쪽 끝을 짚는다.

각 크기에서:

- 1 번 패스가 정말 가속됐는가 (`OSMGAMesaHookDrawn` 이 늘었는가)
- 2 번 패스가 정말 소프트웨어인가
- 깊이 발산 (`worst`, `sum/n`, 히스토그램)
- 커버리지 불일치 (`cover`)
- **3 번 패스에서 바뀐 화소 수**

## 4. 무엇을 안 하나

- **삼각형을 크기에 맞춰 키우지 않는다.** 키우면 크기마다 다른 도형을
  비교하게 되어, 발산이 커진 것이 크기 때문인지 도형 때문인지 못 가른다.
- **원인을 새로 주장하지 않는다.** 발산이 크기에 따라 달라진다면 그것은
  관측이고, 설명은 따로 세운다.

## 5. 순서

계획 교차검토 → 재검증 → 시험 수정 → 실기 측정 → python 으로 정리 →
기록. **드라이버는 안 건드리므로 재부팅은 없다.**

## 6. 결과 (2026-08-21) — 순서는 무관하고, **너비가 문제다**

### 예측은 일곱 크기 전부 맞았다

`섞은 뒤 바뀐 화소 = hwOnly + count(hw<sw)`, 반대 순서는 `swOnly + count(hw>sw)`.
**일곱 크기 전부 정확히 일치했다.** 그리고 두 순서 모두 최종 깊이 버퍼가
두 단독 스냅샷의 **화소별 최솟값**과 같다 (`mix1NotMin = mix2NotMin = 0`,
모든 크기에서). **순서 무관성은 성립한다.**

가속 여부도 매 패스에서 옳았다 — 1 번과 3·4 번의 하드웨어 그리기는 가속되고
소프트웨어 패스는 안 된다. 소프트웨어 패스 뒤에도 하드웨어를 되찾는다.

클리어값도 세었다 — 매번 전 워드가 65535 다. 가정이 아니라 측정이다.

### 규칙: **너비가 32 의 배수여야 한다**

12 개 너비에서 **예외 없이 갈린다.** python 으로 확인했다 — 2, 4, 8, 16, 64
는 전부 못 가르고 **32 만 가른다**:

- 16 은 336 에서 깨진다 (336 = 16×21, 무너짐)
- 8 은 328 에서, 4 는 324 에서, 2 는 322 에서 깨진다
- 64 는 352 와 800 이 64 의 배수가 아닌데 멀쩡해서 깨진다

**그리고 원본이 그렇게 말한다.** 예상 못 한 결과였으므로 X.Org 의
`xf86-video-mga` 를 뒤졌다 — 두 곳에서 따로 나온다:

- `mga_exa.c:869` — *"Pitch alignment is in sets of 32 pixels, and we need to
  cover 32bpp, so it's 128 bytes."* 그리고 `pixmapPitchAlign = 128`.
  128 ÷ 4 = **32 화소**.
- `mga_dacG.c:2294` — G 계열 DAC 의 `Roundings[3] = 32` (4 바이트/화소).

**실기 12 개 너비, DDX 의 주석과 상수, DAC 의 반올림 표 — 셋이 같은 값이다.**

드라이버는 지금 그것을 확인하지 않고 받아들이고, 하드웨어는 지킬 수 없다.

### 이건 깊이 고침이 만든 게 아니라 드러낸 것이다

이 크기들은 §3-20 전에는 깊이 매핑이 실패해 `DEPTH_BIT` 가 켜진 장면이
통째로 소프트웨어로 떨어졌다. 그래서 **깊이를 쓰는 프로그램에서는 가려져
있었다.** 깊이를 안 쓰는 프로그램은 예나 지금이나 그 너비에서 가속을 타고,
**그때도 틀리게 그렸을 것이다.**

`REMAINING_WORK §3-21` 로 세운다. 고침은 계획을 세우고 교차검토를 거친다.
