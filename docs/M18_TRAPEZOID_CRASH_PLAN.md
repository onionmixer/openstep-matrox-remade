# M18 — 사다리꼴 층의 0 나누기 (2026-08-29, 코딩 전)

`M17 §11` 이 찾은 크래시.  **출하 중인 층**이고 **유저랜드**이므로 재부팅은
필요 없지만, 합법적인 GL 삼각형이 프로세스를 죽인다.

## 1. 인과 사슬 — 코드에서 끝까지 확인했다

```
1  빌더가 sub(하위화소 비트)를 EDGE_WALK 한계에 맞을 때까지 줄인다
   (Triangle.c:1310-1329).  넓은 삼각형일수록 sub 가 낮아진다
2  osmgaEdgeRegs 가 HH = height >> (8 - sub) 를 만든다 (:365-375)
3  1/256 단위 높이가 1 인 변은 sub < 8 이면 HH == 0 이 된다
4  Q2 = 2*M*HH = 0,  그리고 *x0 = osmgaCeilDiv(P0, Q2) (:378-379)
5  osmgaCeilDiv 는 `long q = a / b;` 이고 주석이 `/* b > 0 */` 다 (:284-291)
   -> 정수 0 나누기 -> SIGFPE
```

python 으로 확인: `sub = 8` 일 때만 `HH = 1` 이고, `sub` 가 0~7 이면 전부
`Q2 = 0` 이다.  **전제조건이 문서화돼 있고 호출자가 그것을 어긴다.**

재현 조건 넷이 왜 필요한지도 이 사슬이 설명한다:

```
길이 >= 40    넓어야 sub 가 8 아래로 내려간다
수평 밑변     두 꼭짓점의 y 가 같아 남은 변의 높이가 1 스텝이 된다
높이 <= 0.005 그래야 꼭대기가 밑변에서 한 스텝 안에 있다
위상 0.5      다른 위상에서는 rL == rT 라 사다리꼴을 아예 안 만든다
```

## 2. 건너뛰면 안 된다 — 그 삼각형은 보인다

```
소프트웨어   40 화소  (140,120) .. (179,120)   밑변이 표본 행에 얹혀 한 줄 전체
사다리꼴     크래시
WARP          0 화소                            (이미 M17 §10 의 138 개 중 하나)
```

`den == 0`("넓이 없는 삼각형은 화소를 안 덮는다") 의 선례를 따라 조용히
버리면 **40 화소를 잃는다.**  크래시는 아니지만 결함이다.

## 3. 제안 — 거절한다, 죽지도 버리지도 않는다

빌더에는 이미 "이 기하는 표현할 수 없다" 의 답이 있다:
`OSMGA_MESA_TRI_UNSUPPORTED`.  훅이 그것을 받아 **소프트웨어로 재생**하고,
소프트웨어는 40 화소를 옳게 그린다.

```
고른 sub 에서 어느 변의 높이가 0 으로 줄어들면
  -> OSMGA_MESA_TRI_UNSUPPORTED
  -> 훅이 소프트웨어로 (기존 경로, 이미 시험됨)
```

검사는 **`osmgaEdgeRegs` 를 부르기 전에** 있어야 한다 — `osmgaFirstDrawn`
이 그것을 먼저 부르므로(`:419-420`) 거기서 이미 죽는다.

## 4. codex 에 물을 것

1. 거절이 옳은 답인가, 아니면 `sub` 를 그 변이 살아남는 값으로 **되올리는**
   것이 옳은가?  후자는 그림을 유지하지만 `sub` 를 줄이게 만든
   `EDGE_WALK` 한계와 충돌한다 — 그 한계를 넘기면 무엇이 깨지나?
2. 검사를 변마다 하나, 사다리꼴마다 하나?  두 변이 다 걷기에 들어간다
3. 정상 기하에서 이 거절이 얼마나 자주 불리나 — 재야 하나, 아니면 조건이
   충분히 좁아 잴 것도 없나?
4. `osmgaCeilDiv` 의 `/* b > 0 */` 는 주석일 뿐이다.  방어를 함수 안에도
   두어야 하나, 아니면 호출자가 지키게 하고 주석을 단언으로 바꿔야 하나?
5. 이 사슬에서 **다른** 0 나누기가 더 있나 — `Q2` 말고 `M`, `step`,
   `osmgaFloorDiv` 의 제수는?
6. 빠뜨린 것.

## 6. `osmgaCeilDiv` 안에서 막으면 **더 나쁘다**

같은 `HH == 0` 이 `osmgaFirstDrawn` 의 걷기 증분 `2*HH` 를 0 으로 만든다.
그 루프는

```c
while (lacc < 0L) { lx += lsgn; lacc += ldy; }
```

이고 `ldy == 0` 이면 **끝나지 않는다.**  즉 나눗셈만 막으면 크래시가
**행(hang)** 으로 바뀌고, 이 기계에서 행은 **재부팅**을 뜻하는 반면 죽은
클라이언트는 아무 비용도 아니다.  그래서 검사는 **부르기 전에** 있다.

## 8. 그리고 공정한 비교가 나왔다 — 두 층이 다 흔들리지만 정도가 다르다

사다리꼴이 이제 완주하므로 **두 층이 다 그린 188 개**에서 비교할 수 있다:

```
              소프트웨어와 다른 삼각형   놓친 화소 / 더 그린 화소
사다리꼴          58  (30.9%)                28 /  57
WARP             106  (56.4%)               443 / 143

둘 다 다름 55,  WARP 만 51,  사다리꼴만 3
```

**근퇴화 기하에서 흔들리는 것은 WARP 만이 아니다** — 출하 중인 층도
30.9% 에서 소프트웨어와 갈린다.  그러나 **WARP 이 훨씬 심하다**: 비율이
거의 두 배이고 **놓친 화소가 16 배**(443 대 28)이며, 사다리꼴의 불일치는
거의 WARP 의 부분집합이다(사다리꼴만 틀리는 것은 3 개).

## 9. 그리고 그 "나중의 최적화" 는 하지 않는다 — 재 보니 이득이 없다

codex 가 짚은 것: `sub` 를 고르는 쪽이 **모든 꼭짓점 쌍**을 재는데, 수평
밑변은 레지스터를 내지 않으므로 걷는 변만 보면 더 높은 `sub` 를 지킬 수도
있다.  짓기 전에 python 으로 두 고르개를 나란히 돌렸다.

먼저 한계가 어디서 무는지:

```
2*(dd+hh) <= 16384,  sub=8 이면 step 1 이므로 dd+hh <= 8192 in 1/256
  -> |dx| + |dy| 가 32 화소를 넘는 변이 하나라도 있으면 sub 가 8 아래로
```

그리고 이득:

```
mesh16 512 개                     더 높은 sub: 0 개
평범한 삼각형 7 가지 크기         더 높은 sub: 0 개
근퇴화 가족 480 개                더 높은 sub: 64 개
크래시 재현자                     sub 7 -> 8
```

**평범한 기하에서는 이득이 0 이다.**  이유가 분명하다 — 평밑 삼각형에서
`dd+hh` 를 지배하는 것은 밑변이 아니라 **긴 옆변**이다(밑변 40 이면
`dd+hh` 40, 옆변은 60).  codex 의 가설은 재현자에서만 참이었다.

이득이 전부 **근퇴화 영역**에 있고, 그 영역은 `M17 §12` 가 WARP 을
내보내기로 하고 `M18` 이 사다리꼴에서 거절하기로 한 바로 그곳이다.
그러므로 **출하 중인 빌더의 `sub` 고르개를 건드릴 이유가 없다** — 돌아올
것 없는 위험이다.

**최적화를 짓기 전에 쟀고, 재보니 하지 않는 것이 답이었다.**
