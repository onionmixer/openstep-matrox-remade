# M17 — WARP 이 거절해야 하는 것 (2026-08-29, 코딩 전)

`M16 §11` 이 정한 계약: **백엔드 선택은 관측 가능해서는 안 된다.**
`M16 S4-e` 가 그 계약을 어기는 사례를 하나 찾았다.

## 1. 사실

얼어붙은 슬리버(crossfind #2), 훅이 받은 좌표로:

```
경로         화소   소프트웨어와
소프트웨어     4     --
사다리꼴       4     일치     (TRICROSS 로 거절하고 되돌린다)
WARP           2     3 개 빠지고 1 개 더 있음
```

기하:

```
크기        1.3984 x 87.0273 화소
넓이        1.0526 px^2
넓이/둘레   0.0060 화소   (평균 두께의 절반)
넓이/외접   0.0086
```

사다리꼴이 "맞는" 이유는 **되돌림**이다.  그 층도 이 삼각형을 직접 그리지
않는다.

## 2. 정해야 할 것

WARP 을 이런 기하에서 떼어 놓는 규칙.  두 제약이 있다:

* **사다리꼴 빌더를 돌리게 하면 안 된다** — 그러면 WARP 의 셋업 이득 일부를
  버리고, 그 층 구현의 우연에 WARP 의 범위가 묶인다(`M16 §11`).
* **이기는 프리미티브를 잃으면 안 된다** — 측정된 이득이 3.5~26% 다.

## 3. 후보

```
(1) 넓이 문턱        2*|area| < T 면 거절.  교차곱 하나
(2) 두께 문턱        area / 가장 긴 변 < T.  슬리버에 더 충실
(3) v9 의 검사를 공유  복제가 아니라 진짜 함수를 부른다
```

(3) 은 codex 가 복제보다 낫다고 한 쪽이지만, 그것이 곧 §2 의 첫 제약을
어긴다.  (1) 은 유저랜드 삼각형당 교차곱 하나 — WARP 이 피하려는 바로 그
종류의 일이지만 아주 작다.

## 4. 문턱을 **재서** 정한다 — 하나의 슬리버에 맞추지 않는다

이것이 계획의 중심이다.  사례 하나로 규칙을 만들면 그 하나에 맞춘 규칙이
나온다.  저장소는 v9 에 대해 이미 옳은 방법을 썼다: `crossfind.c` 가 **진짜
빌더와 진짜 검증기를 몰아** 거절되는 삼각형을 찾았다.

같은 방법을 신탁에 대고 쓴다:

```
근퇴화 삼각형을 넓은 범위로 만든다 (넓이·두께·종횡비·방향을 쓸어서)
각각을 WARP 으로, 그리고 소프트웨어로 그린다
어긋나기 시작하는 곳을 찾는다
문턱은 그 경계에서 나온다 — 슬리버 하나에서가 아니라
```

경계가 넓이가 아니라 다른 양(두께? 종횡비?)에 있다면 그것이 규칙의 모양을
정한다.

## 5. codex 에 물을 것

1. 문턱을 **재서** 정하는 이 방식이 옳은가, 아니면 근퇴화 기하에서 "경계"
   자체가 잘 정의되지 않아 다른 접근이 필요한가?
2. 규칙이 유저랜드 정책(`osmgaMesaWarpTakes`)에 있어야 하나, 커널 검증기
   (`osmgaHW3DWarpAdmits`)에 있어야 하나?
3. 잘못 거절될 **옳은** 얇은 삼각형이 있을 텐데(사다리꼴로 가므로 그림은
   맞다), 그 비용을 어떻게 재나?
4. 넓이·두께 말고 이 불일치를 더 잘 예측하는 양이 있나?
5. 빠뜨린 것.

## 7. 계약을 고친다 — 관용치는 계약의 일부다

`M16 §11` 은 "백엔드 선택은 관측 가능해서는 안 된다" 고만 적었다.  그런데
이 프로젝트는 이미 **측정되고 문서화된 차이 셋을 받아들인다.**  그대로 두면
계약이 스스로와 모순되고 시험할 수가 없다.  고쳐 적는다:

> 받아들여진 그리기는 **선언된 층 관용치 안에서** 소프트웨어와 일치해야
> 한다.  관용치는 열린 면허가 아니라 이 셋이고, 이 셋뿐이다:
>
> ```
> 색     한 레벨 낮음                        (M12 §8)
> 깊이   한 코드 + (|dz/dx|+|dz/dy|)/16      (M12 §9, M13)
> 소유권 변에 붙은 화소의 귀속               (M12 §3)
>        -- 단 커버리지는 정확하다: mesh16 은 gap 0, extra 0 이고
>           움직인 것은 승자뿐이었다
> ```

슬리버는 이 셋 **밖**이다.  소프트웨어가 그리는 화소를 **비워 둔다** —
귀속이 아니라 **커버리지**가 틀렸고, 그것은 선언된 어디에도 없다.

## 8. 규약 결함이 아니다 — 재서 배제했다

규칙을 설계하기 전에, 이것이 정밀도 한계가 아니라 **넘겨주는 방식**의
문제일 가능성을 닫아야 한다.

```
병진   하위 화소 오프셋 15 개    15/15 전부 불일치
순열   여섯 꼭짓점 순서(양 감기) 6/6 전부 동일하게 불일치
       (소프트웨어는 여섯 순서에서 같은 집합을 그린다 — 순서 무관)
```

**위상 사고도, 감기 규약도, 꼭짓점 순서도 아니다.**  기하 자체다.

## 9. 그러므로 다음은 규칙이 아니라 특성화다

codex 가 승인한 것은 쓸기를 **특성화**로 쓰는 것이지 스칼라 문턱을 뽑는
것이 아니다.  그리고 다음 셋을 먼저 정해야 한다:

```
분류기의 목표      무엇을 분리하려는가
위상 완비 행렬     하위 화소 위상·감기·방향·크기·높이·클리핑을 층화
결정 지점          정점 변환 뒤 (Hook.c:1313 이후)
혼합 층 비용 예산  얼마를 넘으면 그 규칙은 출하하지 않는가
"간단한 규칙 없음" 도 유효한 결과
```

**비용 기준을 재기 전에 적는다**: 대표 부하에서 plain 이득(3.5%)을 규칙이
잡아먹거나, 거절이 만든 조각남이 섞인 장면을 되돌림 기준선보다 나쁘게
만들면, **전역 WARP 정책으로 출하하지 않는다.**
