# M22 — 남은 0.453 초 (2026-08-29, 코딩 전)

`M21` 이 미러를 500 배에서 걷어내자 진짜 사실이 드러났다:

```
두 teapot, 640x480
  소프트웨어          0.059 s
  가속, 좁힌 미러     0.713 s      = 미러 0.260 + 나머지 0.453
```

**그리기 경로만으로도 대체하려는 소프트웨어보다 7.7 배 느리다.**
미러가 그것을 덮고 있었을 뿐이다.

## 1. 0.453 초가 갈 수 있는 곳

```
F  Mesa 앞단        glVertex/법선/조명/변환/클립.  두 팔에 공통이다
B  훅의 조립        삼각형 16106 개를 사다리꼴이나 WARP 정점으로
I  ioctl            제출 193 회.  커널 인코딩 + 엔진 + spin 대기 포함
M  미러             0.260 s, 이미 안다
```

`T_acc = F + B + I + M`,  `T_sw = F + R` (R 은 소프트웨어 래스터화).

## 2. 재는 법 — 이미 있는 것부터

`OSMGAMesaHookSubmitStats()` 가 여섯 개를 준다: 제출 수, **누적 µs**,
dword, spin 합, spin 최대, spin 한 제출 수.  `OSMGA_MESA_INST_TIME` 이
켜져 있을 때만 µs 가 움직인다.

```
I  = submitUs                                   (있다, 켜기만 하면 된다)
F  = 컬링으로 래스터화만 없앤 실행 시간
     glEnable(GL_CULL_FACE); glCullFace(GL_FRONT_AND_BACK)
     -> 변환과 조명은 그대로 돌고 아무것도 래스터화되지 않는다
R  = T_sw - F
B  = T_acc - M - I - F
```

세 번 재면 넷이 다 나온다.

## 3. 이미 아는 실마리

`spin` 은 커널이 엔진을 기다린 횟수다.  `I` 가 크고 `spin` 이 크면
**엔진이 병목**이고, `I` 가 크고 `spin` 이 0 이면 **인코딩·시스템콜**이며,
`I` 가 작으면 병목이 `B` 나 `F` 다.  세 갈래가 서로 다른 다음 작업을
가리키므로, 이 측정 하나가 방향을 정한다.

`M15` 는 배치 enqueue 비용이 사다리꼴보다 WARP 이 3.5~26% 싸다고 했다 —
그것은 여전히 참이지만 **전체의 어느 조각에 대한 것인지** 이제 알 수 있다.

## 4. 안전

전부 유저랜드 계측이고 그리기를 바꾸지 않는다.  `INST_TIME` 은 제출마다
`gettimeofday` 두 번(약 9 us)을 더하므로 **그 실행의 총시간은 오염된다** —
그래서 총시간은 계측 없는 실행에서 따로 잰다.  `M15` 에서 같은 함정을
한 번 밟았다.

## 5. codex 에 물을 것

1. `GL_FRONT_AND_BACK` 컬링이 Mesa 3.4.2 에서 **조명과 변환을 그대로
   돌리고 래스터화만 없애나**?  컬링이 파이프라인의 어디에서 일어나며,
   변환보다 먼저 잘라내는 지름길이 있나?
2. `F` 를 그렇게 재면 두 팔에서 같은 값인가 — 가속 라이브러리는 컬링된
   삼각형에 대해 훅을 아예 안 부르나?
3. `submitUs` 가 커널의 인코딩과 엔진 대기를 **둘 다** 포함한다.  그 둘을
   가르려면 무엇이 필요한가 — `spins` 로 충분한가, 아니면 커널 쪽 계측이
   필요한가?  (커널 변경은 재부팅을 뜻하므로 마지막 수단이다)
3. 16106 삼각형 / 193 제출 = 제출당 83 개.  `M15` 는 배치가 클수록
   유리하다고 했는데 왜 이렇게 작은가 — Mesa 의 정점 버퍼 한계인가?
4. 이 분해에서 내가 틀릴 수 있는 곳.
5. 빠뜨린 것.
