# M13 — WARP 깊이 시작값 프로브 (2026-08-29, 코딩 전)

`M12 §9.4` 가 남긴 미해결 하나를 가른다.

## 1. 설명할 관측

`seam` 도형 B(= 도형 A 를 **37/128 화소** 옮긴 것, z 는 같은 창공간 평면에서
옴)에서 WARP 의 깊이 평면 **상수만** 어긋난다.  기울기는 6ppm 이내로 정확.

```
WARP  A 상수 오차  -0.480    <- 알려진 잘라내기
WARP  B 상수 오차  +3.446
차이               +3.93 코드
3.93 / (60.37+40.11) = 5/128 = 37/128 - 1/4
```

## 2. 왜 지금 이걸 재는가 — 미리 정한 결정

`polyoffset` 의 `units +8` 은 깊이를 **8 코드** 움직인다.  이 오차는 그
**49%** 다.  즉 decal 여유의 절반이고, 엄격한 깊이 비교·동일평면·z-fighting
경계, 그리고 두 층을 섞은 프레임의 의미적 안정성에 닿는다.

확인되면 할 일을 **미리 정한다**:

* `TEST_STATUS` 에 층의 성질로 크기와 조건을 적는다.
* **보정하지 않는다.**  아핀 사례에 맞춘 보정이 원근이나 커버리지를 깨뜨릴
  수 있고 마이크로코드는 열어볼 수 없다.
* 수가 조용히 커지지 못하도록 회귀 고정물을 남긴다.
* 결정 하나에 먹인다: 폴리곤 오프셋·decal 을 쓰는 프레임을 사다리꼴로
  보낼 것인가.

어느 것도 하지 않을 거라면 짧은 확인만 하고 멈춘다.

## 5. 설계

### Z0 — 우리가 **보낸** 정점이 옳은가 (하드웨어 스윕 전에, 거의 공짜)

훅은 자기가 받은 창 좌표를 float 로 기록해 둔다(`OSMGAMesaHookLastWin`,
`coord-probe` 가 쓰는 것).  도형 B 의 삼각형을 그리고 그 아홉 float 를
읽어, **호스트 python 이** `osmgaFix` 와 `OSMGAMesaBuildWarpVertex` 를
그대로 재현해 우리가 보내는 32 바이트 정점의 float32 비트를 만든다.

그 세 점이 정하는 평면이 의도한 평면과 같은가?

* 다르면 → **결함은 빌더에 있고 마이크로코드가 아니다.**  스윕 불필요.
* 같으면 → 우리가 보낸 것은 옳고, 차이는 그 뒤에 있다.  Z1 로 간다.

C 는 아홉 float 를 찍는 작은 프로그램 하나뿐이고, 판단은 전부 python 이다.

### Z1 — 위치인가 제출한 z 인가 (결정적)

**삼각형 하나**, `t = 0..127` step 1, 무작위 순서, 팔 셋(소프트웨어·사다리꼴·
WARP), 두 스윕:

```
Z1a  평면 고정   z = f(옮겨진 정점)        위치와 제출 z 가 함께 움직인다
Z1b  z 고정      기하를 옮기고 평면 절편을 -K*t/128 만큼 같이 옮겨
                 제출되는 정점 z 가 모든 t 에서 동일하도록 한다
```

주 관측량은 **화소별 차분** `D_t(x,y) − D_0(x,y)`, 삼각형 안쪽 깊숙한
고정 표본 격자에서.  t 마다 평균·로버스트 평균·평면 적합(절편과 두 기울기
차)·행별/열별 평균을 남긴다.

```
Z1a 에 톱니, Z1b 에 없음   -> 효과는 제출한 z 를 따른다 (H5)
둘 다 톱니                 -> 위치를 따른다 (H1/H2)
둘 다 평평                 -> 병진이 원인이 아니었다
```

내림과 반올림은 `t = 17..31` 이 가른다(python: `t=20` 에서 `+15.70` 대
`-9.42`).

### Z2 — 격자의 모양 (Z1 이 "위치" 라고 말한 경우에만)

X 만·Y 만·대각선, 기울기 부호 반전, 정수 기준 위치 여러 곳, 감기 반전.

## 8. Z0 결과 (2026-08-29) — **우리가 보내는 정점은 옳다**

`test/openstep-mga-warp-depth-z0-probe.c` 가 한 삼각형을 그리고 세 가지를
찍는다: 훅이 **받은** 창 좌표(float, 자기 고정소수 변환 전), `osmgaFix` 가
그것으로 만드는 값, 그리고 **진짜 빌더**(`OSMGAMesaBuildWarpVertex`)가
내놓는 IEEE-754 워드.  판정은 전부 python 이다 — 빌더를 빌더로 판정할 수는
없다.

python 이 우리가 보내는 세 float32 점을 지나는 평면을 정확히 풀어 의도한
평면과 대조했다:

```
도형   기울기 오차 dz/dx   dz/dy      화소 중심에서의 오차
A      -0.000005          +0.000017   -0.0001 · +0.0000
B      -0.000005          -0.000011   +0.0001 · -0.0003
```

**±0.0003 코드.**  설명할 차이 3.93 코드보다 **네 자릿수 아래**이고, 두
도형이 똑같이 정확하다.  덤으로 `osmgaFix` 재현이 기록된 float 와 정확히
일치함도 확인됐다(단언으로 박아 뒀다).

그러므로:

* **빌더는 결백하다.**  차이는 정점이 이 라이브러리를 떠난 **뒤**에 생긴다.
* 커널은 정점 워드를 그대로 복사한다(`vtx[i] = sv[i]`)—변환하지 않는다.
* 남는 것은 **마이크로코드**다.

이것이 Z1 을 정당화한다.  그리고 **H5(제출한 z 를 따른다)는 아직 살아
있다**: 보내는 *평면*은 같지만 보내는 *z 값*은 다르므로, z 값 양자화라면
여전히 움직인다.  Z1b 가 그것을 가른다.

## 9. Z1 결과 (2026-08-29) — **위치를 따르고, 격자는 1/16 이며, 내림이다**

두 스윕 x 세 팔 x 두 패스, `t = 0..127`, 프로세스 안에서 순서를 섞어서.

주 관측량은 `D_t(x,y) − D_0(x,y) − (기대_t − 기대_0)` 의 고정 표본 격자
평균 — "초과분" 이다.

```
스윕  팔          t 전 구간 범위   패스1 대 패스2 최대차   층 이상 t
a     소프트웨어        0.059            0.000              0
a     사다리꼴          0.039            0.000              0
a     WARP              5.497            0.000              0
b     소프트웨어        0.059            0.000              0
b     사다리꼴          0.039            0.000              0
b     WARP              5.504            0.000              0
```

### 9.1 위치다, 제출한 z 가 아니다

**스윕 b 는 제출하는 z 워드를 모든 t 에서 동일하게 유지한다.**  그런데
톱니가 그대로다(5.504 대 5.497).  그러므로 효과는 **정점 위치**를 따른다.
**H5 는 반증됐다.**

사다리꼴과 소프트웨어는 두 스윕 모두 평평하다(0.04~0.06 코드) — 층 무관
가설 H4 도 배제.

### 9.2 격자는 1/4 가 아니라 **1/16** 이다 — 내가 틀렸다

초과분을 `K x (t mod P)/128` 에 맞춰 보면:

```
P =  4 (1/32 화소)   최악 잔차   3.145 코드
P =  8 (1/16 화소)   최악 잔차   0.011 코드   <== 맞는다
P = 16 (1/8  화소)   최악 잔차   6.291 코드
P = 32 (1/4  화소)   최악 잔차  18.851 코드
P = 64 (1/2  화소)   최악 잔차  43.971 코드
```

**128 개 t 전부에 대해 최악 0.011 코드.**  다른 격자는 3~44 코드 어긋난다.

`M12 §9.4` 와 이 문서 §1 이 말한 **"1/4 화소" 는 틀렸다.**  도형 B 의
`37/128` 은 잔여 5 를 주는데 `37 mod 32 = 5` 이고 `37 mod 8 = 5` 라 **한
점으로는 두 격자를 가를 수 없었다.**  codex 가 "`t` 를 한 화소 전체로
늘려라" 고 한 것이 정확히 이것을 갈랐다.

### 9.3 내림이지 반올림이 아니다

```
내림          최악 잔차 0.011 코드
최근접 반올림 최악 잔차 6.285 코드
```

주기 안에서 값이 단조 상승하다가 경계에서 떨어진다:
`0.00 0.78 1.56 2.36 3.13 3.93 4.71 5.49` 그리고 리셋.

### 9.4 크기와 결정

깊이 오차의 상한은 **한 화소 대각선어치 깊이 기울기의 1/16** 이다:

```
상한 = (|dz/dx| + |dz/dy|) / 16
이 평면(60.37, 40.11)에서 6.28 코드,  관측 최대 5.50 (= K x 7/128)
polyoffset 의 units +8 (8 코드) 대비 69%
```

가파른 다각형일수록 비례해서 커진다 — 그리고 그것은 `glPolygonOffset` 의
factor 항이 스케일하는 바로 그 양이다.

**보정할 수 없다**(§2 의 사전 결정대로, 그리고 이제 이유가 구체적이다):

* 보내는 x, y 를 미리 1/16 로 스냅하면 **커버리지가 움직인다** — 지금
  사다리꼴과 바이트 단위로 같은 그 커버리지가.
* 정점 z 로 상쇄할 수도 없다.  필요한 보정량은 **화소마다** 다른 것이
  아니라 평면 전체의 상수인데, 그 상수는 `gx·frac16(x) + gy·frac16(y)` 로
  **평면의 기울기**를 알아야 나온다.  기울기를 유저랜드에서 풀지 않는 것이
  이 층의 존재 이유다.

### 9.5 아직 열려 있는 것

Z1 은 x 와 y 를 **함께** 옮겼다.  그러므로 "두 축이 각각 1/16 로 내림된다"
와 "대각선 방향으로만 그렇다" 를 가르지 못한다.  상한 식은 두 축 각각을
가정한 것이고, 그 가정은 **Z2**(X 만·Y 만)가 확인해야 한다.  적어 둔다.
