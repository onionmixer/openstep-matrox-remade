# M1.4EB — 미러 좁히기는 이 작업부하를 못 돕는다 (계획 중단)

## 무엇을 하려 했나

`glClear` 를 가속하고 나니 512×384 프레임 146.7 ms 중 clear 가 ~0, 삼각형이 ~0,
나머지 전부가 미러였다. 그래서 저장소가 코드에 적어둔 유일한 열린 작업 — 미러를
실제로 건드린 곳으로 좁히기 — 을 계획했다.

설계는 이랬다: 불리언 `bufDirty` 를 **상자**로 바꾸고, OSMesa 의 스팬/픽셀 기록기
다섯 개를 `Driver.Clear` 처럼 감싸 각자 쓰는 범위를 합집합에 보태고, 엔진 배치와
가속 clear 도 자기 상자를 보태고, 미러는 합집합만 복사한다. 의심스러우면 전면.

## 왜 중단하는가 — codex 지적이 옳다

**프레임마다 표면 전체를 `glClear` 하면 더러운 상자는 곧 표면 전체다.** 바뀐 픽셀이
전부이므로 애플리케이션 버퍼도 전부 받아야 하고, 장부를 어떻게 적든 그 전송은
없앨 수 없다. 내가 잰 작업부하가 바로 그것이다.

즉 직전에 내가 "미러가 프레임의 전부이니 좁히는 것이 남은 유일한 항목"이라고 한 것은
**이 작업부하에 대해 틀렸다.** 더티 사각형은 표면의 일부만 바뀌는 작업부하 —
지우지 않고 조금씩 덧그리는 종류 — 에서만 값을 낸다.

## 그 전에 내가 직접 찾은 구멍 두 개 (계획 자체의 결함)

계획을 세우는 동안, codex 답이 오기 전에 두 가지가 나왔다. 둘 다 사실이었다.

1. **"소프트웨어 쓰기는 전부 스팬 다섯 개를 지난다"는 거짓이다.** OSMesa 는
   `ctx->Driver.LineFunc = choose_line_function(ctx)` 를 설치하고(`osmesa.c:1895`),
   `OSMESA_ARGB` + 평면 셰이딩 + 폭 1 이면 `flat_rgba_line` / `flat_rgba_z_line` 을
   고른다. 이들은 `PIXELADDR4()` 로 버퍼에 **직접** 쓴다. codex 는 깊이 시험이 있는
   삼각형 빠른 경로(`smooth_rgba_z_triangle`, `flat_rgba_z_triangle`)도 마찬가지임을
   덧붙였고, 우리 훅은 거절한 삼각형을 바로 그 함수에 넘긴다.
2. **감싸는 자리가 틀렸다.** 포트의 훅은 `osmesa.c:1912` 에서 불리는데 스팬 함수는
   `:1917` 이후에 설치된다. 거기서 감싸면 직후에 덮어써진다. (`Clear` 가 되는 것은
   그것만 훅보다 **앞서** 설치되기 때문이다.) `RENDER_START` 는 버퍼를 건드리는 모든
   경로가 지나므로 `RenderStart` 에서 감싸는 것이 대안이지만, 그러려면 osmesa.c 에
   두 번째 훅을 넣거나 매 렌더마다 다시 감싸야 한다.

## 그래서 남는 것은 구조적 비용이다

미러의 실제 속도를 두 크기에서 쟀다:

```
128x96 :    49152 바이트 /   9.753 ms ->  5.04 MB/s   198 ns/byte
512x384:   786432 바이트 / 146.665 ms ->  5.36 MB/s   187 ns/byte
```

두 크기가 일치한다. 이것이 이 기계의 **uncached VRAM 읽기 속도**이고, "VRAM 에서
그리고 시스템 RAM 으로 배달한다"는 지금 구조가 프레임마다 무는 값이다. 미러가
프레임의 전부일 때 도달 가능한 상한:

| 해상도 | 표면 | 프레임 | 상한 |
| --- | --- | --- | --- |
| 640×480 | 1.23 MB | 229 ms | 4.4 fps |
| 800×600 | 1.92 MB | 358 ms | 2.8 fps |
| 1024×768 | 3.15 MB | 587 ms | 1.7 fps |

이 벽을 넘으려면 장부가 아니라 **소유권 계약**을 바꿔야 한다 — 애플리케이션이
실제로 볼 때만 읽어오거나, 아예 표면을 치환하지 않거나. 그건 이 회차의 범위가
아니고, 무엇보다 **재기 전에는 설계하지 않는다**는 이 프로젝트의 방식대로 먼저
"부분만 바뀌는 작업부하"를 따로 재야 판단할 수 있다.
