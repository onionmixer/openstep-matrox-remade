# M1-4c9 — `GL_RGBA` 텍스처 (2026-08-22)

## 1. 왜 이제야 되나

`GL_REPLACE` 는 두 형식에서 색은 같고(`Cv = Ct`) **알파만 다르다**:

```
   GL_RGB    Av = Af   (조각의 알파)
   GL_RGBA   Av = At   (텍셀의 알파)
```

엔진은 원래 **언제나 텍스처의 것**을 줬다 — RGBA 에는 맞고 RGB 에는 틀렸다.
`M1_4C8` 에서 그것을 **언제나 보간된 것**으로 바꿨다 — RGB 에는 맞고 RGBA 에는
틀리다.  그래서 알파 출처는 **배치마다 고르는 것**이 되어야 한다.

## 2. 들어간 것

| 자리 | 바뀐 것 |
|---|---|
| 업로드 | `GL_RGBA` 는 원본 알파를 상위 바이트에 싣는다 |
| | `GL_RGB` 는 상위 바이트를 **0 으로 둔다** (0xFF 가 아니다) |
| 커널 | `OSMGA_HW3D_TEXF_TEXALPHA` — 서면 두 레인 다 `ALPHA_SEL_ARG1`(텍스처), 아니면 `ALPHA_SEL_ARG2`(보간) |
| 관문 | `img->Format == GL_RGBA` 를 받고 플래그를 세운다 |

### 왜 RGB 의 알파를 0 으로 두는가

읽힐 일이 없는 값이다.  **읽히면 알파 채널이 새까매져서 소리를 지른다** —
지난 결함이 정확히 그렇게 잡혔다.  255 를 넣으면 같은 결함이 다시 숨는다.
이것은 **독값**이고, 관문이 `GL_REPLACE` 하나만 받는 동안에만 안전하다.
텍스처 알파를 참조할 수 있는 모드를 열 때 다시 봐야 한다.

### 저장 형식으로 고른다

`img->Format` 은 호출자가 넘긴 `format` 이 아니라 **`internalFormat` 에서
나온다**(`texformat.c:262/268`).  그래서 RGB 화소를 RGBA 텍스처에 올려도
여기서는 `GL_RGBA` 로 읽히고, 그것이 맞다 — Mesa 가 표본하는 것이 그것이다.
교차검토가 짚은 지점이고, 소스로 확인했다.

## 3. 고치기 전 상태 (대조군)

커널이 아직 플래그를 모르는 채로 RGBA 장면을 그려 둔 값:

```
   겹침 25964   색 24   알파 25762 다름
   하드웨어 알파  {128: 25964}          <- 정점 알파 하나로 고정
   소프트웨어 알파 {85: 294, 99: 292, ...}  <- 텍셀마다 다름
```

색이 24 로 그대로인 것이 형식이 색 경로를 건드리지 않는다는 확인이다.

## 4. 재부팅 뒤 확인

| 확인 | 기대 |
|---|---|
| RGBA 장면의 알파 불일치 | 25762 → **0** |
| RGBA 장면의 색 | **24** 그대로 |
| RGB 장면(nearest/linear) | 색 24 / 257, 알파 **0** — 회귀 없음 |
| §32 세 줄 | 그대로 (플래그가 안 선 경우의 동작이 안 바뀜) |
| GL 단언 "RGBA 가 엔진에 닿는다", "알파가 텍스처의 것" | 통과 |

교차검토가 더하라고 한 것 중 **아직 안 한 것**: 같은 텍스처 객체를 RGBA 로
올렸다가 RGB 로 다시 정의했을 때 잔류본이 버려지고 알파 출처가 따라 바뀌는지.
`TexImage` 훅이 잔류를 버리는 것은 코드로 확인했지만 **측정하지 않았다.**

## 5. 재부팅 뒤 — 되었다 (2026-08-22)

| 장면 | 색 | 알파 |
|---|---|---|
| RGB nearest | 24 / 25964 (최대차 16) | **0** |
| RGB linear | 257 (최대차 1) | **0** |
| RGBA nearest | 24 (최대차 16) | **24** (최대차 8) |
| RGBA linear | 257 (최대차 1) | **158** (최대차 1) |

GL 단언: `an RGBA texture reaches the engine ok`,
`and its alpha is the texture's, not the fragment's ok  alpha 17`.

### 5-1 남은 24 는 알파 결함이 아니다 — 증명

"색이 다른 24 곳과 알파가 다른 24 곳이 같으니 알파는 맞다"는 것은 **논증이지
증명이 아니다.**  교차검토가 짚었다: 하드웨어가 색과 알파 모두에서 같은
*엉뚱한 이웃 텍셀*을 표본해도 같은 교집합이 나온다.

그래서 텍셀 신원으로 검정했다.  이 텍스처는 R 이 텍셀의 x 를, G 가 y 를,
B 가 x+y 를 이름하고 알파는 그와 무관한 식(`8x + 3y + 17`)이다.  그러면
**하드웨어 알파가 하드웨어 RGB 가 지목하는 텍셀의 알파와 같은가**를 물을 수
있다:

```
   하드웨어가 그린 화소 25964
   RGB 세 채널이 한 텍셀을 정확히 지목한 화소 25964
   그중 알파가 그 텍셀의 알파와 다른 것 0
```

**전부 일치**한다.  올리기·선택·전달에 결함이 없고, 남은 24 는 순전히
**어느 텍셀을 고르는가**의 문제 — 이미 유계로 적어둔 좌표 위상 잔차다.
그것은 색에도 똑같이 나타나며 알파만의 문제가 아니다.

### 5-2 선형에서의 알파

RGBA + 선형의 알파 차이 **158 은 전부 한 단계**이고, 색의 257 과 같은
성질이다(Mesa 는 네 가중치를 반올림하고 엔진은 절단한다).  채널마다 반올림
경계를 따로 넘으므로 자리가 겹치지 않는 것도 예상대로다.

### 5-3 객체 수명과 형식 전환

교차검토가 요구한 것들을 측정했다:

```
   redefined RGBA -> RGB, the alpha follows       ok  alpha 255
   redefined RGB -> RGBA, the alpha follows       ok  alpha 17
   two formats in one frame keep their own alpha  ok  rgba 17, rgb 255
```

양방향 재정의와 **한 프레임 안에서 두 형식이 번갈아 살아 있는 경우**까지
맞다.  플래그가 굳어 있으면 어느 한쪽이 반드시 틀리는 시험들이다.

## 6. 알아 둘 한계 (교차검토가 짚음)

OpenGL 의 **기본** 축소 필터는 `GL_NEAREST_MIPMAP_LINEAR` 다.  관문은
`MinFilter == MagFilter` 를 요구하므로, 필터를 손대지 않은 프로그램은
**가속되지 않고 소프트웨어로 간다**.  틀린 그림이 아니라 안 받는 것이지만,
"보통의 GL 프로그램이 그냥 빨라진다"는 아직 아니라는 뜻이다.
